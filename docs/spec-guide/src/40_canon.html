第 4 部

Canon：「整合単位」の実装

WBAI の山川さんは「整合単位」というコンセプトを提唱しました。CoBRAC はこれを Canon という仕様に落とし込んでいます。Canon は、回路の定義が互いに一致していなければならないプロジェクト（BRA）のまとまりです。同じ Canon の中では、同じ UC Descriptor の回路は、どのプロジェクトでも同じ Uniform / Collection の区別・同じ分解・同じ Circuit ID と正式名になります。

範囲どのプロジェクトどうしで定義をそろえるか ＝ Canon のメンバー（1 プロジェクトは 1 Canon まで）
中身何をそろえるか ＝ 共有層（回路・接続・文献）。機能や役割は役割層としてプロジェクトに残す
手続きどうそろえるか ＝ 生成時の制約（rev に固定）と、取り込み時の審査（push → PR → 人の承認 → 新しい rev）

4.1 「整合単位」というコンセプト

BRA は ROI × TLF ごとに作られます。同じ脳領域は多くの BRA に現れますが、各 BRA が独立に回路を定義すると、同じ神経集団が BRA ごとに別の粒度（ある BRA では 1 つの UC、別の BRA では層ごとに分けた Collection）、別の分け方、別の名前になり、BRA どうしを合わせて 1 つの脳のモデルとして読むことができません。

「整合単位」は、回路の定義を互いに整合させる BRA の範囲を、1 つの単位として明示的に扱うというコンセプトです。脳全体のすべての BRA を 1 つの定義に強制的にそろえるのではなく、「この範囲の中では定義を 1 つにする」という単位を置くことで、次の 2 つを両立させます。

単位の中では、定義が 1 つ
同じ回路は同じ ID・名前・粒度・分解で、送り手は常に Uniform。単位の中の BRA は、そのまま組み合わせて読める。
単位ごとに、粒度を選べる
ネットワーク水準の粗い単位と、層・細胞種水準の細かい単位を並べて持てる。目的の違う BRA 群を、無理に 1 つの粒度へ押し込まない。

※ この節の説明は、Canon の仕様から読み取れる範囲で整合単位の考え方を整理したものです。コンセプトそのものの定義は、山川さんの原典の資料を参照してください。

CoBRAC の第 3 部の命名規則（UC Descriptor）は「同じ集団かどうか」を判定できるようにするもので、整合単位は「同じ集団なら、定義も同じであるべき範囲」を決めるものです。両者は組になって働きます。

4.2 Canon の定義と、整合単位との対応

Canon の定義

Canon は、1 人のユーザーのプロジェクトのうち、回路の定義が一致していなければならないものの集合です。Canon の中では、同じ UC Descriptor は同じ Uniform / Collection の区別と同じ分解（Sub-Circuits）を持ち、プロジェクトをまたぐ接続は送り手が Uniform であり続けます。Uniform かどうかは Canon の外では HCD ごとに決まり（3.9）、Canon の中では固定されます。異なる Canon は異なる粒度を選べます（ネットワーク水準の粗い Canon と、層水準の細かい Canon を並べて持つ、など）。なお「Canon」という名前は仮のものです。

整合単位のコンセプトの各要素は、Canon では次のように実装されています。

整合の保ち方（取り込むとき）push → PR → 衝突ルールとシステムの検査・AI レビュー → 人の承認（4.6〜4.8）。AI は所見を出すだけで、承認の代わりにはならない。
単位どうしの関係Canon から Canon への PR（4.11）。取り込んだエントリには経由した Canon と rev（via）が残る。

4.4 スナップショットの構造：共有層と役割層

Canon の 1 つの rev は、1 つの不変な JSON（S3 の canons/{canonId}/rev/{n}/canon.json）です。中身は、プロジェクトをまたいで 1 つに決める共有層と、プロジェクトごとに持つ役割層に分かれます。

  • 回路は正規化した UC Descriptor をキーにします（第 3 部）。プロジェクトの JSON は Circuit ID で接続を書くので、push のときに Descriptor に解決します。Descriptor の無い UC は取り込まれず、一覧で示されます。
  • 接続は（送り手, 受け手, Reference ID）をキーにし、文献の欄と引用文の照合状態を持ちます。文献は Reference ID をキーにし、照合状態を持ちます。
  • すべてのエントリは来歴（どのプロジェクトのどの rev から、どの PR で入ったか、別の Canon を経由したなら via = <canonId>@<rev>）と、それを push したプロジェクトの一覧（sources）を持ちます。状態は valid / flagged（Collection に変わった回路に接続が残る、など）/ invalidated です。
  • プロジェクトがエントリを使わなくなっても、Canon からは消しません。差分では「プロジェクトで使わなくなった」と表示するだけです。
  • 保存済みの回路は SABRA の境界変更（v0.24.0）や旧い命名の形があっても書き換えません。比べるときに現在の形に直します（currentCanonSnapshot）。
  • 仮説（仮説モード、第 2 部）は共有層に入れません。push のとき、仮説の付いた接続、仮説の集団で終わる接続、集団そのものが仮説の UC、仮説の性質は共有層から外し、そのプロジェクトの役割層（roles[].hypotheses）にだけ置きます。

典拠：packages/shared/src/canon.ts・canonMerge.ts（canonFromProject・diffCanon）

4.5 Canon に従って作る：生成時の制約

Canon に参加したプロジェクトは、1 つの rev に固定（pin、Projects.canonRevision）されます。参加したときは最新の rev に固定され、そのプロジェクト自身の PR が承認されると新しい rev に進みます。そのほかは所有者が「最新の rev にする」で進めます。

  1. Canon を渡す（ワーカー＝プログラム）：ワーカーはジョブ（解説記事を除く）の開始時に、Canon の項目（読み取りだけ）と固定された rev のスナップショットを読み、作業フォルダのプロジェクトのフォルダの隣に読み取り専用の canon/ を置きます。このフォルダは S3 に戻しません。空の Canon（rev 0）や見つからない Canon は、その実行では無効になるだけです。
  2. 指示する：HCD の仕様に「Canon for this run」の節が加わります（canonSpecNote）。Canon の Circuit ID・正式名・伝達物質・修飾・Source of ID をそのまま使う／Canon の Collection は Collection のまま、その Sub-Circuits で接続する（単位全体の証拠は UC の接続に relation < で付ける）／Uniform の回路を分割しない（この TLF でどうしても細かく分ける必要があれば、理由を decision_log.md に書いてユーザーに質問する）／Canon の接続と文献を使うときは記録をそのまま写す／新しいエントリは粒度方針に従う（push のときに Canon に提案される）。ワークフローの骨格は変わりません。
  3. 作る（CoBRAC エージェント＝LLM）：エージェントは canon/ を読み、それに従って uc.json などを書きます。
  4. 検査して差し戻す（ワーカー）：HCD の検査の後で、結果を Canon と照合します（canonGenerationProblems）。エラーの衝突 C1・C2c・C3・C4・C5・C6・C8 は検証器の問題として修正ターンでエージェントに戻し、C2b・C7・C8b・C9b・C12 はチャットに表示するメモにとどめます（エージェントには戻さない）。C8c・C9c はハーネスの文献と引用文の照合に任せます。仮説は、この照合では証拠と同じに扱い、Canon の制約を緩めません。Canon で確認済みの文献・引用文と同一のものは、もう一度照合しません（reference_check.json / quote_check.json に「checked in Canon …」と記録）。
canon/ のファイル（Circuit ID は現在の形で書き出す）

README.mdCanon の名前・ID・rev、粒度方針、ファイルの説明
circuits.jsonCanon のすべての回路（Circuit ID、UC Descriptor、正式名、uniform、Sub-Circuits、性質、Output Semantics、状態）
connections.jsonUC どうしの接続（論文ごとに 1 件。文献の欄と引用文の照合状態つき。quoteCheck が verified で始まれば照合済み）

典拠：packages/shared/src/canonConstraints.ts（canonAgentFiles・canonSpecNote・canonGenerationProblems）、packages/worker/src/pipeline.ts

4.6 push と PR：Canon に取り込む

  1. push（完了した参加プロジェクトの画面の「Canon に push」、POST /projects/{id}/canon/push。押すのは所有者、オーケストレーターの計画では計画ランナー）：API（プログラム）がワークスペースの uc.json・connections.json・references.json・frg.json・meta.json・reference_check.json・quote_check.json を canonFromProject で Canon の形に変換し、最新の rev と比べ（diffCanon）、PR として保存します（PR の項目と、ペイロード・差分を canons/{canonId}/pr/{no}/ に）。同じプロジェクトの未処理の PR は置き換えられます。…/canon/preview は PR を作らずに同じ差分を見せます。
  2. 審査：所有者か共同編集者が PR の画面で確かめます（4.8）。
  3. 判断（人）：承認（メモ任意）／変更を依頼（メモ必須。PR は開いたまま）／却下（メモ必須）。変更の依頼と却下のメモは、送った側も履歴で読めます。送った側は取り下げられます。
  4. 承認の書き込み（API）：承認のリクエスト（POST /canons/{id}/pulls/{no}/approve）は、衝突ごとの選択 choices（Canon の値のまま canon か、取り込む側の値 incoming）を持ちます。push 後に最新の rev が進んでいれば、まず現在の head に対して判定し直します。承認は rev n+1 を書き、headRevision を条件付きで進め（同時の承認は 409）、rev の記録（REV#）を残します。却下は理由が必要で（…/reject）、送った側は …/withdraw で取り下げます。

典拠：packages/api/src/lib/canonOps.ts（pushProject・approvePullRequest）、packages/shared/src/canonMerge.ts

4.7 衝突ルール（C1〜C13）

PR の差分は、Canon の値と取り込む側の値を項目ごとに比べ、次の衝突を判定します（packages/shared/src/canonMerge.ts）。Canon の分解の部分集合であることは衝突になりません。

  • 通常のエラーは承認を止めます。C1 と C2c は、取り込む側の定義を採って解決できます。そのとき、Collection に変わった回路で終わる接続は flagged になり、変わった回路を使うプロジェクトが影響として一覧されます。
  • 警告（要確認の項目）は、「Canon の値のまま」か「取り込む側の値」かを選ぶ（C7・C9b・C12）か、確認して了承する（C2b・C8b）まで承認できません。情報（C13）は承認を止めません。
  • これらのコードは CoBRAC の Canon 独自の体系で、BRA のエラーコード（Master）とは別です。

4.8 審査：検査・AI レビュー・共同編集者・まとめて承認

PR の画面は審査のための画面です（v0.20.0 から）。システム（API のプログラム）と AI（LLM のジョブ）が補助し、承認・変更の依頼・却下は人（所有者か共同編集者）だけが行います。衝突ルール（4.7）が承認を止めるかどうかを決めます。

審査の材料

GET /canons/{id}/pulls/{no} は、読むたびに材料を計算して返します（保存はしない）：差分とその基準の rev、システムの検査（checks）、差分の各項目の両側の値（entries）、図（graph：PR が持ち込む回路、その接続が終わる Canon の回路、変わるものの Canon での隣の回路と、その間の Canon の接続。最大 60 回路）、来歴（provenance：送り元、その現在の rev、まだあるか、head）、履歴、審査する人には最新の AI レビュー。

変更の依頼・コメント・履歴

  • 変更を依頼（POST …/pulls/{no}/request-changes { note }）：PR は開いたまま reviewState = changes_requested と reviewNote を持ちます。送った側が新しく push すると、新しい PR が置き換えます。
  • コメント（POST …/pulls/{no}/comments { text, item? }）：所有者・共同編集者と PR を送った人が、PR 全体か差分の 1 項目（<種類>:<キー>）に書けます。
  • 履歴：Canons テーブルの追記専用の項目 PEV#{prNo}#{at}#{nonce} に、pushed・superseded・rebased（承認時に新しい head に対して判定し直した）・comment・changes_requested・approved（rev と衝突の選択つき）・rejected・withdrawn・ai_requested を残します。AI レビューの終わりはそのジョブから読みます。v0.20.0 より前の PR は、push と判断を PR# の項目から組み立て直して表示します。

AI レビューのジョブ（LLM、所見だけを出す）

  1. 依頼（人）：審査する人（所有者か共同編集者）が、開いている PR について POST …/pulls/{no}/ai-review { model?, locale } を送ります。1 つの PR で同時に 1 件だけです。モデルは依頼した人のキーとティアで確かめ（requireModel。デフォルトの API キーの Tier 1 はそのモデルだけ）、ワーカーでも確かめます（planRunKey）。
  2. 材料（API）：buildCanonAiPacket が差分・衝突・検査・変わった項目の両側・文献を最大 15 万文字にまとめ、canons/{id}/pr/{no}/ai/{jobId}/input.json に書き、ジョブ（type とモード canon-review、projectId = Canon ID、reviewPrNo、reviewLocale）を積みます。
  3. 実行（ワーカーが LLM を 1 ターン動かす）：Web 検索なし・コマンドもファイルも使わずに材料だけを読み、固定の出力スキーマ（要約、重さと理由・項目・検査・Reference ID つきの指摘、確かめるべき点、項目ごとのコメント案）で返させます。その形でなければ 1 回だけ頼み直します。
  4. 検証（ワーカー）：材料に無い項目・検査・論文を指す部分は除き、件数を数えます（parseCanonAiReview）。結果は result.json に、利用量と費用はジョブに記録し、依頼した人の利用量（デフォルトのキーならその利用量にも）に入ります。

出力に判定の欄は無く、プロンプトは承認や却下を勧めることを禁じています。ディスパッチャーと janitor はこのジョブについてプロジェクトに触れません（止まったレビューのジョブはリトライせず、もう一度実行するよう促すメッセージで失敗にする）。

共同編集者と、だれが判断したか

  • 所有者は、Canon の画面で、相手が登録に使ったメールアドレスを入れて既存のユーザーを共同編集者に追加します（POST /canons/{id}/editors { email }。大文字小文字は区別しない。招待メールは無く、未登録のアドレスは 404 で、先にサインアップしてもらうよう求める）。外すのは DELETE /canons/{id}/editors/{userId} で、共同編集者は自分で抜けることもできます。所有者には共同編集者のメールアドレスが、共同編集者には名前だけが見えます。
  • 共同編集者は Canons テーブルの EDITOR#{userId} の項目で表され、本人のユーザーの editorCanons に並び、Canon の一覧の「共有された Canon」から開きます。
  • 共同編集者ができること：Canon・参加プロジェクト（名前と ROI / TLF だけ。所有者のプロジェクトへのリンクは無い）・rev・PR の閲覧、コメント、AI レビュー（自分のキーかデフォルトの API キーで、自分が使えるモデルで。ジョブと費用は本人のもの）、変更の依頼・承認・却下、自分の Canon からの PR の送信（相手が非公開でも、PR を受け付けない設定でも）。所有者だけ：設定、参加プロジェクト（push は参加プロジェクトから行い、参加プロジェクトは所有者のもの）、公開、共同編集者の管理、削除。管理者は閲覧だけです。
  • 承認は 1 人で足ります。PR は approvals（{ userId, name, at }）を持ち、将来 Canon に requiredApprovals を持たせられる構造です（未設定 = 1、まだ設定も表示もできない）。
  • PR には承認・却下・取り下げをした人と時刻（decidedBy / decidedByName / decidedAt）、変更を依頼した人と時刻（reviewedBy / reviewedByName / reviewedAt）が、rev（REV#）には承認者（approvedBy / approvedByName / approvedAt）が記録されます。PR の画面には「… が承認 → rev n」「… が却下」「… が変更を依頼」（メモと時刻つき）の帯が出て、履歴には各操作の人が、Canon の rev の一覧には承認者が出ます。

まとめて承認

Canon の画面の PR の一覧で、エラーの衝突も要確認の項目も無く、変更を依頼していない未処理の PR にチェックを入れ（全選択も可）、「まとめて承認」を押すと、選んだ PR を番号の順に 1 件ずつ承認します（POST /canons/{id}/pulls/approve-many、1〜50 件）。1 件ごとに直前の承認でできた最新の Canon に対して判定し直し、見つからない・処理済み・新しい head に対してブロックする衝突がある・承認数が足りない・head の競合、のどれかで止まり、残りは承認しません。結果には承認した件数と、どの PR でなぜ止まったかが出ます。承認者は 1 件ずつ承認したときと同じように記録されます。

  • 押せるのは 1 件ずつの承認と同じく、所有者か共同編集者です。PR 番号が 1〜50 件でなければ 400。重複は除き、順番は保ちます。1 件ずつ POST …/pulls/{no}/approve と同じ関数（approvePullRequest、衝突の選択なし）で、読み直した Canon に対して承認し、必要なら差分を取り直して rebased として記録します。
  • 止まる理由は、見つからない（not_found）、開いていない（closed）、新しい head に対してブロックする衝突がある（conflicts、その数 blocking）、承認数が足りない（approvals）、head の競合（race）です。1 件の承認中の予期しないエラー（ペイロードが無い、AWS のエラーなど）も、その PR で race として止まり、途中で Canon が削除されたら not_found で止まります（まだ 1 件も承認していなければ 404）。どの場合も、すでに行った承認は必ず結果に返ります。
  • 応答は { approved: [{ prNo, revision }], stopped: { prNo, reason, blocking? } | null } です。画面は件数を示す確認を出してから実行します。

典拠：packages/api/src/app.ts（Canon の PR のルート）、packages/api/src/lib/canonOps.ts・canonReview.ts、packages/shared/src/canonReview.ts・canonAiReview.ts、packages/worker/src/canonReview.ts

4.9 rev への追従

プロジェクトのヘッダーに、所属する Canon と従っている rev が出ます（例「rev 1（最新 2）」）。GET /projects/{id}/canon は、固定した rev と最新の rev を、そのプロジェクトが使う定義について比べ、次のどれかを返します。

状態意味利用者の操作
current最新の rev に固定されている—
behind（新しい rev あり）Canon は進んだが、このプロジェクトが使う定義は変わっていない「最新の rev にする」（POST /projects/{id}/canon/pull）で、次の実行から従う
affected（影響する変更あり）使っている回路が Collection / Uniform に変わった、Sub-Circuits や ID が変わった、使っている接続の端が Collection になった。変更の一覧と追加指示の文が付く「Canon に合わせる」で固定を進め、プロジェクトを直す追加指示を送る

4.10 Canon の作り方と、プロジェクト作成時の選択

  • 空の Canon を作る：サイドバーの「Canon」で「新しい Canon」を作り、名前と粒度方針を書きます。既存のプロジェクトは「プロジェクトを追加」で入れられます。
  • 作成画面で選ぶ：入力欄の下の「Canon」ボタン（開くと一覧が出て、数が多ければ検索できるポップオーバー）で、「なし」／「既存の Canon」（最初の実行から最新の rev に従う。選んだ Canon はボタンに名前と rev が出る）／「既存のプロジェクトから新しく作る」（入力欄の下に設定の欄が開く）を選びます。設定画面で決めた既定の Canon（Users.defaultCanonId）には「既定」が付き、指定しなければそれが使われます（無ければなし）。
  • API：POST /projects は canon（{ mode: "none" } / { mode: "existing", canonId } / { mode: "new", name, policy, seeds, choices, actions }）を受け取ります。プロジェクトを作る前にこの指定を検証し、プロジェクトは最初のジョブを積む前に Canon に入るので、最初の実行から Canon に従います。

既存のプロジェクトを種にして新しく作る

  1. 名前と粒度方針を書き、どの Canon にも入っていない完了済みの自分のプロジェクト（複製も可）を優先する順に選びます（上が優先。番号が付き、矢印で並べ替えられる）。プレビューに rev 1 の中身が出ます。
  2. POST /canons/seed-preview が合成します（composeSeeds）。最初の種が rev 1 の土台になり、以降の種は衝突ルールで順に合わせます。種どうしでは、C1 / C2c を先の種の定義を残して解決することもできます（後の種は更新が必要と印が付き、その Collection への接続は flagged）。
  3. 衝突を決めきれない種は、rev 1 に対する未処理の PR にする（既定）か、外します。画面には「残りを優先順で決める」「残りを PR にして保留する」があります。
  4. プロジェクトの作成が種の承認を兼ねます。rev 1 は PR なしで書かれ（source: "seed"）、外さなかった種と新しいプロジェクトが rev 1 に固定されたメンバーになります。

4.11 公開・複製・Canon から Canon への PR

公開

  • プロジェクトと Canon は private（既定）か public で、切り替えられるのは所有者だけです（PUT /projects/{id}/visibility、PUT /canons/{id}/visibility）。いつでも非公開に戻せます。
  • プロジェクトを公開できるのは、成果物があり、ID がランダムな形か <userKey>-<seq> の形のとき（旧形式の名前の ID は不可）です。
  • 公開したものは Catalog テーブルに行（kind = project / canon）を持ち、非公開にするか削除すると行を消します。一覧と閲覧のたびに、プロジェクトや Canon そのものの状態を確かめ直します。
  • 公開ライブラリ（/explore）：ログインした誰でも、公開プロジェクト（概要・回路の一覧・レポート）と公開 Canon（粒度方針・rev・メンバー数・公開されたメンバー。Canon ID もここに出る）を一覧・閲覧できます。チャットの履歴・費用・メールアドレスは出ません。何を見せ何を見せないかの詳細は第 7 部です。
  • 公開 Canon は、所有者が acceptPullRequests を止めない限り、ほかのユーザーの Canon からの PR を受け付けます。承認するのはいつも所有者（と共同編集者）です。

複製

公開プロジェクトは、「複製」（POST /public/projects/{id}/clone）で自分の新しい非公開プロジェクトとして写せます。元のプロジェクトは読むだけで変わりません。

項目内容
新しいプロジェクト新しい Project ID、名前は元の名前 + 「 (clone)」、元の Contributor、状態は COMPLETED。元の調査モード・SABRA の境界（sabraBoundary）・ハーネスのルール、仮説モードの設定を引き継ぐ。clonedFrom に元の ID・その rev・所有者の userKey・名前・時刻を残す
写すものワークスペース（フォルダ名と、テキストファイル中の元の Project ID を語単位で新しい ID に書き換える）、グラフの JSON、解説記事とその図（HCD・FRG・表データ・レポート・解説記事）
写さないものチャットの履歴、ジョブ、メッセージ、利用量、グラフの配置、添付した参考資料、BRA xlsx（元の ID を含むので、XLSX の段を未実行にして、追加指示で作り直す）
複製の数Catalog テーブルの clones の行に数え、元の所有者にはプロジェクトの画面と公開ライブラリで見える

複製の最初の版の親は、写した公開プロジェクトの版です（第 5 部）。

Canon から Canon への PR

  • Canon の所有者は、Canon の画面の「別の Canon に PR を送る」から、自分の Canon の最新 rev を別の Canon に PR として送れます（POST /canons/{target}/pulls { sourceCanonId }。…/pulls/preview で先に差分を見られる）。送り元は自分が所有する Canon で、空（rev 0）なら 409、同じ Canon には送れません。
  • 送り先は、自分の Canon、自分が共同編集者の Canon、PR を受け付けるほかのユーザーの公開 Canon です。ほかのユーザーの非公開の Canon は 404、PR を止めた公開 Canon は 403 です。
  • ペイロードは送り元のスナップショットそのもの（canonFromCanon）で、エントリは元のプロジェクトの来歴を保ち、via = <送り元>@<rev> を記録します。役割層には送り元のすべての参加プロジェクトが入ります。受け取った側は、プロジェクトからの push と同じ衝突ルール・選択・承認で審査します。
  • 送り元の Canon には、送ったことの記録（OUT#{target}#{no}）だけが書かれ、送った PR とその状態を一覧できます（GET /canons/{id}/outgoing）。送った人は PR を開いて取り下げられますが、審査はできません。同じ Canon から同じ送り先への未処理の PR は、新しい PR が置き換えます。

典拠：packages/api/src/app.ts（公開・複製・Canon → Canon のルート）、packages/shared/src/publish.ts・canonMerge.ts
