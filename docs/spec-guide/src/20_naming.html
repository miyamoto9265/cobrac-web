第 2 部

回路の命名

CoBRAC は、HCD のすべての回路を SABRA の単位（アンカー）に結びつけ、それより細かい集団の性質を facet として足して名前を付けます。アンカーと facet を決まった順に並べたものが UC Descriptor で、機械が比べるためのキーになります。人が読む別名の Circuit ID は、この Descriptor から機械的に作ります。この規則は CoBRAC が先行して使っている提案で、WBAI の組織の規則としてはまだ採択されていません（2.13）。

アンカー回路が属する SABRA の単位です。HOMBA:12261（VTA）や BNA:57-58（A4ul）のように書き、どの回路にも必ず 1 つ以上あります。
facetSABRA の単位より細かい性質です。軸:値 の形で、part・lay・cell・nt・mol・in・out・resp・side の 9 本の軸を決まった順に並べます。
UC Descriptor と Circuit IDHOMBA:10341/mol:DRD1+ がキーで、NACs(DRD1+) がその別名です。同じ集団には、どの BRA でも同じ名前が付きます。

2.1 なぜ名前の規則が必要か

命名の規則ができる前は、エージェントがプロジェクトごとに自由な Circuit ID（PC、GrC、CA3-Pyr、L-DLPFC など）を付けていました（経緯は付録 D）。自由な名前には、次の 2 つの問題があります。

① 同じ集団に別の名前が付くこと
側坐核 shell の DRD1 陽性の集団を、あるプロジェクトは NAc_shell_D1、別のプロジェクトは NACs-DRD1 と書くことがありえます。反対に、同じ文字列が別の集団を指すこともありえます。これでは、プロジェクトをまたいで回路を集計したり、定義をそろえたりできません。
② アトラスとの対応が名前から分からないこと
名前がどの領域を指すかはエージェントの説明文にしか書かれておらず、SABRA のどの単位に当たるかを機械的に検査できません。層・細胞種・投射先で切り出したサブ集団では、とくに書き方の揺れが大きくなります。

WBAI の組織にも、SABRA の単位より細かい回路の書き方を定めた規則はまだありません（ISS-001 は未決です）。データ準備マニュアルやオントロジーの実例でも、CA1_distal、Cx.L2_3PV、M1C.L5PT、BL_fear のように書き方がまちまちです。一方で、層や細胞種で分けた UC が必要なことは、組織の議論でも認められています。UC Descriptor と facet は、この空白を埋めるための規則です。

たとえば、側坐核 shell の DRD1 陽性の集団は、どのプロジェクトでも Descriptor が HOMBA:10341/mol:DRD1+、Circuit ID が NACs(DRD1+) になります。名前が同じなら同じ集団だと分かるため、プロジェクトをまたいで回路を照合できます。Canon（第 5 部）も、この Descriptor をキーにしています。

第 2 部で使う用語

2.2 設計の考え方

命名の規則は、次の 5 つの原則に基づいています。

原則内容と理由
アンカーは常に SABRA の単位SABRA より細かいものは、すべて facet で表す。こうすると、どの回路も SABRA のどこかに必ず結びつく。
UC に採番の ID を付けないSABRA が独自の ID を持たないのと同じ考え方で、既存のアトラスの ID と明示的な属性だけから名前を組み立てる。正規化した Descriptor そのものがプロジェクト横断の一意なキーになるので、中央で番号を払い出すレジストリは要らない。
同じ集団は、どのプロジェクトでも同じ名前プロジェクトによって変わるのは回路の役割だけ。役割とは、ROI の内外、Interface、Output Semantics、Uniform か Collection か、を指す。プロジェクト名の接頭辞も付けない。
種は名前に入れないBRA はヒトの回路と、ヒトへの外挿を扱う。動物の知見に基づく場合は、接続のエビデンスの Taxon に書く。
SABRA の単位そのものの UC が通常facet は、単位より細かい集団が HCD に必要なときだけ足す。回路の働きを説明するために facet を足すことはしない。符号化する内容は Output Semantics に書く。

2.3 アンカー

アンカーは、回路が属する SABRA の単位です。どの回路にも 1 つ以上のアンカーがあり、Descriptor の先頭に置きます。

アンカーの形

形意味例
HOMBA:<id>SABRA の DHBA 側の単位。DHBA 名を持つ HOMBA の項に限るHOMBA:12261（VTA）
BNA:<左>-<右>BNA の新皮質の 1 領域。常に左右のペア（奇数と、奇数 + 1）BNA:57-58（A4ul）
BNAG:<L2 略称>BNA の新皮質の L2 の群（回など）の全体。RCS の結果の分布が広く、1 つの領域に決まらないときに使うBNAG:MFG
A&B複数の SABRA の単位にまたがる回路HOMBA:…&HOMBA:…
  • SABRA: や DHBA: という接頭辞は作りません。SABRA は独自の ID を持たないためです。
  • BNA の担当範囲である新皮質の中をさらに細かく分けるときは、BNA のアンカーの下に part:HOMBA:… として書きます。逆向きに、DHBA のアンカーの下に BNA の領域を part として置くことはしません。
  • 脊髄のように、HOMBA の階層をたどっても DHBA 名を持つ項がない領域は、SABRA の単位になりません。この場合のアンカーには、RCS が返す最も近い DHBA の祖先を使い、細かい部位は part に書きます。投射先や入力元（out / in）の値としては、その項をそのまま書けます。

RCS でアンカーを決める手順

エージェントは、回路の記述を「領域を表す語」と「それ以外の語」に分け、領域の語だけで RCS を検索します。遺伝子や細胞種などの残りの語は、最初から facet になります。RCS の結果によって、アンカーと facet は次のように決まります。

RCS の結果アンカーfacet
DHBA 側で完全に一致する（relation '='、dhba_exact: true）その HOMBA: の項領域以外の語
DHBA 側で、クエリの方が細かい（dhba_exact: false か relation <）RCS が返す、DHBA 名を持つ祖先（sabra.dhba_homba_id）part:<一致した HOMBA の項> と、領域以外の語
BNA 側（atlas: BNA、新皮質）search_bna_candidates の候補のうち、sabra.atlas: BNA の領域のペア。1 つの領域がはっきり優勢でなければ BNAG:<L2>HOMBA の項が BNA の領域より細かければ part:<HOMBA の項>
クエリの方が広い（relation >）A&B、または共通する SABRA の祖先—
候補がない推測しない。利用者に質問する

BNA の領域を 1 つに決める目安は、上位の候補の p_raw が 0.5 以上で、k_papers が 2 以上であることです。

BNA と DHBA の境界

SABRA の仕様（2026-10-04）では、BNA を使うのは新皮質だけです。BNA にはラベルがあっても、新皮質でない領域は DHBA の項で表します。対象は、扁桃体 Amyg、海馬 Hipp、大脳基底核 BG、視床 Tha の皮質下の 36 ラベルと、海馬体・嗅内皮質などの不等皮質です。領域ごとの表し方は次のとおりです。

領域SABRA での単位
新皮質（BNA の皮質ラベル 1–210 のうち 206 ラベル）BNA
扁桃体（BNA の mAmyg・lAmyg）DHBA（AMY と、CEN・BLN・La などの核）
海馬（BNA の rHipp・cHipp）DHBA（HiF と、CA1・DG・S など）。海馬全体は HOMBA:12170
大脳基底核（BNA の vCa・dCa・GP・NAC・vmPu・dlPu）DHBA（Ca・GP・NAC・NACs・Pu など）
視床（BNA の 8 亜領域）DHBA（DTH と、MD・VPL・Pul・LG などの核）
嗅内皮質（BNA の A28/34）と側頭無顆粒島皮質（BNA の TI）DHBA（EC・TI。HOMBA では新皮質の外にある）
嗅皮質・梨状皮質などの不等皮質（BNA にラベルはない）DHBA
  • 境界の正本は RCS が持っています。RCS は、HOMBA の項を返すときに新しい境界での所属のアトラスを付け、BNA の候補を返すときには、新皮質でない領域に「DHBA に属し、SABRA の単位ではない」という印を付けます。CoBRAC が持つ対応表（新皮質でない BNA の領域から、それを含む DHBA の項への表）も、RCS と同じ内容です。
  • 新皮質でない BNA の領域（ラベル 211–246、BNA:115-116、BNA:117-118）と、BNAG:Amyg・BNAG:Hipp・BNAG:BG・BNAG:Tha は、アンカーにも、in / out などの facet の値にも使えません。ワーカーの検査は、その領域を含む DHBA の項を示して直させます。たとえば BNA:223-224 なら HOMBA:10339 NAC、BNAG:BG なら Ca・Pu・NAC・GP を示します。
  • 海馬全体は HOMBA:12170（HiF）で表します。文献が CA1、CA3、DG、海馬台などの特定の領域を挙げていれば、HiF ではなく、その DHBA の項を使います。
  • BNAG:PhG（海馬傍回）は、新皮質の A35/36r・A35/36c・TL・TH と、DHBA で表す A28/34・TI の両方を含むため、回全体のアンカーにはできません。検査は、亜領域（BNA:109-110、BNA:111-112、BNA:113-114、BNA:119-120）か、DHBA の EC（HOMBA:10317）・TI（HOMBA:10330）を使うよう求めます。
  • Canon に従うプロジェクトは、Canon にすでにある Descriptor を、この境界に合わなくてもそのまま使えます。その Descriptor は境界の検査の対象から外れます。この境界より前に作ったプロジェクトと、保存済みの Canon の扱いは付録 C（C.2）にまとめています。

実装

境界の正本は RCS の rcs/sabra.py です。RCS の get_homba_term と search_homba_candidates は新しい境界で sabra.atlas を返し、search_bna_candidates は新皮質でない領域に sabra.atlas: DHBA・sabra_unit: false を付けます。CoBRAC 側の対応表は BNA_DHBA_COUNTERPARTS です。新しいプロジェクトは作成時に sabraBoundary: "neocortex" を持ちます。

典拠：prompts/phases/HCD.md、packages/shared/src/ucNaming.ts、packages/shared/src/harness.ts

2.4 facet

facet は 軸:値[,値…] の形で書き、次の表の順に / でつなぎます。各軸は 1 回までしか書けず、値のない軸は書きません。

順軸内容例
1partアンカーより細かい部位。より細かい HOMBA の項を優先し、なければ短い語part:HOMBA:10341
2lay層lay:L5
3cell形態・細胞クラスcell:pyr、cell:purkinje、cell:pt
4nt伝達物質（Glu GABA Gly ACh DA NE 5HT His pep）nt:DA
5mol分子マーカーと極性（+ - ~hi ~lo）mol:DRD1+
6in入力元で定義される集団in:HOMBA:12261
7out投射先で定義される集団out:HOMBA:10339
8resp反応性・機能的なチューニングresp:rpe
9side左右（left / right の 1 値。付けなければ両側、または左右を区別しない）side:left
facet を使うときの決まり
  • 軸は、集団を選び出す性質にだけ使います。in / out を使うのは、投射によって集団が定義される場合だけです。単に投射するだけなら、接続で表します。
  • mol の値には必ず極性を付けます。遺伝子記号は公式のもの（ヒトなら HGNC）を使い、1 つの Descriptor の中で表記をそろえます。
  • part・in・out の値は、SABRA の単位でなくてもかまいません。たとえば脊髄 HOMBA:AA30565 は DHBA 名を持ちませんが、投射先には書けます。
  • side は常に最後に置きます（2.8）。

典拠：UC_FACET_AXES = ["part", "lay", "cell", "nt", "mol", "in", "out", "resp", "side"]（packages/shared/src/ucNaming.ts）

2.5 UC Descriptor

UC Descriptor は、アンカーと facet を並べた機械向けのキーです。形は次のとおりです。

UC Descriptor = <アンカー>{&<アンカー>}{/<軸>:<値>[,<値>]}
例: HOMBA:10341/mol:DRD1+
    BNA:57-58/lay:L5/side:left
  • 保存先：uc.json の各回路の descriptor に書きます。Circuits.csv と xlsx の Circuits シートの UC Descriptor の列、HCD のグラフのノードの詳細にも表示されます。
  • 比較の前の正規化：2 つの Descriptor を比べるときは、まず正規化します。古い形を現在の形に直し（付録 C）、mol の値をアルファベット順に並べ、全体を小文字にします。このため DRD1+ と Drd1+ は同じものとして扱われます。表示には、大文字小文字を保った元の形を使います。
  • 一意性：1 つの HCD の中で、2 つの回路が同じ正規化 Descriptor を持つことはできません。UC と Collection を合わせて判定します。
  • Uniform かどうかは含めない：Descriptor は「どの集団か」だけを表します。その HCD で UC（葉）なのか、Collection（分解される回路）なのかは含みません（2.9）。

実装

正規化は normalizeUcDescriptor、古い形の読み替えは canonicalUcDescriptor が行います。

典拠：packages/shared/src/ucNaming.ts

2.6 Circuit ID

Circuit ID は、Descriptor を人が読みやすくした別名です。前半にアンカーの略称を置き、facet があれば、その値を括弧の中に並べます。

Circuit ID = <アンカーの略称> [ "(" <項目> { "." <項目> } ")" ]
<項目>     = <語> | ("out-" | "in-") <相手の略称> | "left" | "right"
文字       = A-Z a-z 0-9 . _ ~ -（2026-08-06 の仮仕様）と / +（2026-08-19 に合意）、項目を囲む ( )

前半：アンカーの略称

  • アンカーの SABRA の正式略称を、大文字小文字も含めてそのまま使います。BNA 側は BNA の新皮質の領域の略称（A4ul、A44d、A9/46d）、DHBA 側は DHBA の略称です。たとえば弓状核は、HOMBA の ArH ではなく DHBA の Arc を使います。
  • 略称に加える変換は、空白を _ にすることだけです。該当するのは、BNA の TE1.0 and TE1.2 を TE1.0_and_TE1.2 にする 1 例だけです。/ と + は 2026-08-19 の合意で使える文字に入ったため、A9/46d、A1/2/3ll、V5/MT+ はそのまま使います。
  • 複数の SABRA の単位にまたがる回路（BNAG: や A&B のアンカー）では、暫定的に、共通する BNA の L2 の略称（例：MFG）を使います。共通の L2 がなければ、最初のアンカーの略称を使います。
  • 独自の略称や慣用の略称（NAc、LC）と、SABRA の単位でない細分の略称（片葉の CH10 など）は前半に置きません。これらは括弧の中に part の項目として書きます。

括弧の中：項目

  • Descriptor の facet の値 1 つにつき 1 項目を、facet の順に . で区切って並べます。facet がなければ括弧も書きません（VTA、NAC）。
  • 各軸の項目の書き方は次のとおりです。
    • part：細分の部位を表す短い英単語（floc、rostral）か、広く通用する略称。
    • lay・cell・nt・mol・resp：Descriptor の語をそのまま（L5、pyr、DA、DRD1+、rpe）。
    • out / in：out-<相手の略称> / in-<相手の略称>（out-NAC、in-VTA）。相手が SABRA の単位でなければ HOMBA の略称を使います（脊髄なら out-Sp）。
  • 項目の中に . があると区切りと紛れるため、_ に置き換えます。語の中の - はそのままでかまいません（遺伝子の HLA-A など）。語の末尾の + / - は極性を表します。

使える文字と区切り

記号扱い理由
A-Z a-z 0-9 . _ ~ -使えるWBAI の 2026-08-06 の仮仕様の文字。RFC 3986 の unreserved と同じ
/ +使える2026-08-19 に合意。BNA の正式略称（A9/46d、V5/MT+）をそのまま使うため
( )項目を囲むときだけRFC 3986 の sub-delims で、URL のパスにそのまま置ける。主要な OS のファイル名に使え、bash のブレース展開も起きない。入れ子にはしない
.（括弧の中）項目の区切り使える文字に含まれ、組織の BNA.A8m.L3 型の書き方ともそろう
, : @使わない使える文字の外。, は CSV でクォートが必要になり、テンプレートの Graph Generator（draw.io 用の CSV）で ID が分かれてしまう
{} [] <> ; | と空白使わないそれぞれ、ブレース展開、[U.X] の参照との紛れ、HTML との衝突、Subnodes の区切り、Markdown の表の崩れの原因になる
  • Circuit ID の一意性は、大文字小文字を区別して判定します。BNA と DHBA の正式略称には、大文字小文字だけが違う組が 45 組あるためです（例：CB と cb）。これに対して、Descriptor は小文字にしてから比べます（2.5）。
  • FRG からは U.<Circuit ID> の形で参照します（例：U.NACs(DRD1+)。本文中では [U.A4ul(L5.pt.left)]）。U. の接頭辞は先頭の U. を外すだけで読むため、括弧の中の . とは衝突しません。Interface や Subnodes の ID の分割も、括弧の外の区切りだけで判定します。
  • シェルに渡すときは、Circuit ID を引用符で囲みます（'NACs(DRD1+)'）。Markdown のリンクの URL に ) を入れるときは %29 にします。正規表現に埋め込むときは、( ) . + / をエスケープします。
  • BRA のテンプレート（Template-v2-2 と v2-3）の数式を LibreOffice で再計算した結果、( ) を含む ID で壊れる箇所はありませんでした。テンプレートは ID を EXACT・VLOOKUP・SEARCH・SPLIT で文字列として扱い、括弧を関数として解釈する箇所はありません。括弧の中を , ではなく . で区切るため、Graph Generator の CSV で ID が分かれることもありません。

典拠：packages/shared/src/ucNaming.ts

2.8 左右の扱い

CoBRAC は、左右を 9 本目の facet side で表します。この形にしたのは、WBAI の次の決定に合わせるためです。

  • 2026-07-14 に、Circuit 名から _L / _R を外すことが決まりました。DHBA と海馬の BIF に合わせ、左右の重複は別に分析するという考え方です。
  • 2026-08-06 の仮仕様で Circuit ID の文字が A-Za-z0-9._~- と決まり、08-19 に / と + を加えることで合意しました。@ はこの文字集合の外です。

ただし、左右を ID から完全に外して Descriptor だけに残すと、同じ集団の左と右が 1 つの HCD の中で同じ ID になり、両方を置けません。そのため、左右を区別するときだけ ID にも含める規則としています。規則は次のとおりです。

  • 左右は facet side で表します。値は left か right の 1 つです。付けなければ「両側、または左右を区別しない」という意味になります。
  • アンカーは常に左右のペアです。左の A4ul は BNA:57 ではなく、BNA:57-58/side:left と書きます。
  • Circuit ID には、左右を区別するときだけ、最後の項目として書きます（A4ul(left)、A8m(L3.left)、A4ul(L5.pt.out-Sp.left)）。両側なら A4ul です。左右を区別しないのが既定であるため、2026-07-14 の決定とも矛盾しません。
  • 1 つの HCD に、同じ集団の左と右を別の回路として置けます。A4ul(left) と A4ul(right) は、Descriptor も ID も違うからです。
  • 両側の回路（A4ul）と片側の回路（A4ul(left)）を並べると、ほかの細分と同じく、両側の方を Collection にするよう求められます（cobrac:nested-uc、2.9）。

古いプロジェクトと Canon には、左右をアンカーの側で表した古い形の Descriptor と Circuit ID が残っています。その読み替えの規則は付録 C（C.2）にまとめています。

典拠：packages/shared/src/ucNaming.ts、packages/shared/test/ucNaming.test.ts

2.9 Uniform と Collection

回路が Uniform かどうかは、HCD ごとに決まります。その HCD の葉なら UC で、その HCD がさらに Sub-Circuits に分解するなら Collection（Uniform = FALSE）です。つまり Uniform は、その HCD が選ぶ粒度での判断です。Descriptor はプロジェクト横断のキーのままで、Uniform かどうかを持ちません。そのため、同じ領域が、粗いプロジェクトでは UC、細かいプロジェクトでは Collection になることがあります。この違いをそろえるのが Canon（第 5 部）です。

SABRA の単位の全体を 1 つの UC にするかどうかは、プロジェクトが選びます。どこで分けるかを決めて uc.json に書くのはエージェントで、それが規則に合っているかを検査するのはワーカーです。領域の中の部分が異なる投射や機能を持つなら、エージェントは根拠を示して UC を分け、分けた元の領域を必要に応じて Collection にします。Collection は構成の関係を表すもので、接続の送り手や受け手にも、FRG の葉にもなりません。

分ける基準

  • いつ分けるか：選んだ粒度で、解剖学的または機能的に不均質なときに分けます。たとえば、いくつもの別の領域を含む回や群、投射元や投射先として別々に報告される部分、文献で役割が異なる部分です。領域や名前の付いた部位の違いで十分で、層や細胞種の証拠までは必要ありません。
  • 分けた部分の名前と理由：分けた部分は命名規則で名付けます。分けた理由は、Collection の comments に必ず書きます。
  • 上位のまとまり：分けた領域の親を Collection にすることは推奨ですが、必須ではありません。さらに上のまとまり（名前のあるネットワークなど）は、読み手の助けになるときだけ作ります。
  • 入れ子の禁止：ある回路と、その中のより細かい回路を、両方とも UC にはできません（cobrac:nested-uc）。対象になるのは、同じアンカーで facet の値が部分集合になる 2 つの回路と、アンカーだけの UC とその中の UC です。後者には、同じ側の BNAG 群とそれに含まれる BNA 領域、左右のペアとその片側、& でつないだアンカーとその 1 つ、が含まれます。この場合は、粗い方を collections に移します。
  • 送り手は Uniform：複数の SABRA の単位にまたがる送り手（BNAG 群や、facet のない複数のアンカー）を 1 つの UC のまま残すには、uniformityNote にその理由を書く必要があります。書かれていなければ、部分への分割か、理由の記入を求められます（コード 203）。分割するときも層や細胞種の証拠は必要とせず、領域の全体だけを報告する論文は、relation < で各部分を支えます。単一の領域、左右のペア、facet 付きの UC、受け手にしかならない回路は、この検査の対象になりません。

uc.json での表し方

  • uc.json は、ucs（常に Uniform）と、任意の collections を持ちます。collections の各要素のキーは、circuitId、descriptor、names、sourceOfId、subCircuits、comments です。collections のないファイルも、そのまま有効です。
  • Collection の descriptor は、SABRA の単位か facet 付きの集団を表すときに書きます。複数の単位をまとめただけの Collection（例：Mesolimbic）では空です。
  • Collection の Source of ID は常に collection で、なぜ不均質かを書く comments は必須です。Collection は、Interface、Output Semantics、機能の項目を持ちません。
  • UC は、任意の uniformityNote を持てます。その HCD で均質とみなす理由を書く欄です。Circuits.csv では、Comments の後ろに Uniform in this project: … として付きます。

2.10 ワーカーの検査とエラーコード

HCD の段階の終わりに、ワーカーは uc.json の名前を次の順に検査します。問題があれば、修正ターンでエージェントに戻します。

  1. Descriptor の構文と意味：アンカーの形、BNA の番号（1〜246。ペアは奇数と、奇数 + 1）、facet の順と重複、mol の極性、side の値を検査します。古い形であれば、現在の形での書き直しを求めます（付録 C）。あわせて、新皮質でない BNA の領域や群を使っていないことを検査します（2.3）。Canon にある Descriptor は、この境界の検査から外します。
  2. Descriptor の重複：正規化した Descriptor が、UC と Collection を通じて重ならないことを検査します。
  3. 括弧の中の項目：項目の数が facet の値の数と一致すること、side があるときは最後の項目がその値であること、side がないのに left / right を書いていないことを検査します。
  4. 前半の略称：アンカーの正式略称と、大文字小文字まで一致することを照合します。BNA は CoBRAC が持つ 246 ラベルの表と、HOMBA / DHBA は RCS が返す項と照合します。BNA の担当範囲の HOMBA の項や、DHBA 名を持たない項をアンカーにしていれば、正しいアンカーを示して直させます。RCS に問い合わせられなかったアンカーは、この照合だけを省きます。
  5. 文字：Circuit ID が、使える文字と ( ) だけでできていることを検査します。Descriptor のない Collection の ID も対象です。

このほか、Circuit ID が UC と Collection を通じて重ならないこと、facet のない UC の names が SABRA の正式名で始まることも検査します。

エラーコードの体系

検査のコードは、WBAI の BRA data: Error code List (Master) に合わせています。Master は、BRA のテンプレート（Template-v2-2 / v2-3）が参照する表です。Master にコードのない CoBRAC の検査には、cobrac: で始まるローカルコードを付けます。番号ではなく名前にしているのは、Master の番号と衝突させないためです。

オントロジー報告書の付録 D の番号には、Master にない番号や、Master では別の意味の番号が含まれます。CoBRAC の検査は Master のコードと cobrac: のコードを使います。付録 D の番号との対応は付録 C（C.3）にあります。

2.11 uc.json での書き方

エージェントが書く uc.json では、descriptor が UC Descriptor、circuitId が Circuit ID、sourceOfId が ID の出典です。名前に関わるキーの規則は次のとおりで、ワーカーがスキーマと検査で確認します。BRA の値の規則のうち、文献・接続・FRG に関わるもの（Reference ID、Pointers、relation、Output Semantics など）は第 3 部で扱います。

キー規則
sourceOfId値は 1 つ。DHBA、BNA、MBA、UBERON、collection、makeshift、または Reference ID 1 つ。アンカーだけの UC（side だけを持つ UC も含む）では、1 つの HOMBA / DHBA の項なら DHBA、BNA の領域か群なら BNA。それ以外の UC（facet 付きの UC、複数の HOMBA の項にまたがる UC、HOMBA と BNA にまたがる UC）では、その集団を定義する Reference ID 1 つ。定義する論文がなければ makeshift。Collection は常に collection（コード 108）
names先頭は SABRA の正式名（BNA の領域名、または RCS が返す DHBA 名）。facet 付きの UC は、正式名の後に細かい集団を書く。同義語は ; で区切って後ろに続ける。RCS に問い合わせられなかったときは照合を省く
uniformityNote任意。複数の SABRA の単位にまたがる送り手では必要（2.9）

Source of ID に BNA と書くのは CoBRAC の拡張です。BRA の列挙値には SABRA の BNA 側を表す値がなく、追加を上流に依頼しています（未決、2.13）。それまでは、Review Tool がこれらの行にコード 108 を出す可能性があります。

2.12 他の部での使われ方

使う場所Descriptor と facet の役割
Canon（第 5 部）回路を、正規化した Descriptor をキーにして持つ。プロジェクトの JSON は Circuit ID で接続を書くので、push や PR のときに Descriptor に解決する。Circuit ID は改名されることがあるが、Descriptor は Canon の中で一意だからである。Descriptor のないグループは group:<Circuit ID> がキーになる。「より細かい回路」（衝突 C3）の判定は facet で行い、side も facet として数える。たとえば、Canon に両側の Uniform の A4ul があるときに A4ul(left) を足すと C3 になる。左と右だけなら、別の回路として共存できる。エージェントに渡す canon/ のファイルと、確認済みの引用のキーは、現在の形で書き出す。古い形のキーと ID の比べ方は付録 C にある。
BRA-DB（第 7 部）Circuits.csv の UC Descriptor の列として CSV に入る。BRA-DB の Circuits は Circuit ID（circuit_id）がキーで、同じ集団は同じ ID になるので、複数のプロジェクトの回路が同じ行に集まる。他のプロジェクトが定義した回路は、共有の語彙として扱う。
オーケストレーター（第 6 部）計画の行に付けるアンカー（HOMBA:<id>、BNA:<l>-<r>、BNAG:<L2>）は、Descriptor のアンカーの部分と同じ形で、facet は付けない。完成した行のアンカーは、そのプロジェクトの uc.json のすべての Descriptor から読み直す（6.5）。

典拠：packages/shared/src/canonMerge.ts・canonConstraints.ts、packages/shared/src/planOrder.ts
