3.12 仮説モード

BRA に入れるのは、既定では文献で支持されたデータだけです。仮説モードのプロジェクトに限り、文献が直接は支持しない接続や UC、またはその性質を、仮説として印を付けたうえで含められます。

仮説モードが緩めるのは、「論文の文がその主張そのものを述べている」という 1 つの条件だけです。次のものは、仮説モードでもいつもどおり検査します。

  • DOI / PMID とその照会、引用文の照合、1 接続 1 文献、Pointers（3.8・3.10）
  • 命名と SABRA の境界（第 2 部）
  • スキーマ（余分なキーを許さないまま）、interface、Collection と均質な送り手、FRG の構造
  • 英語で書くこと、レポートの節、Canon（第 5 部）

仮説は開示するためのものです。ハーネスが書くものや求めるものは、調査・実験・検証・予測を提案しません。仮説モードは検査規則の水準（3.8）とは別の設定で、どの世代とも組み合わせられます。

許可・記述・検査の分担

役割すること
利用者作成時に「仮説モード」を選ぶか、フォローアップで「この指示で仮説を許す」をオンにして、許す主張・対象・比率の上限・メモを決める。指示の文章に「仮説で」と書いても範囲は広がらない
API要求を検査し、許可範囲（scope。S1、S2…）としてプロジェクトに保存する
ワーカー許可範囲を依頼文に展開し、仮説を検査し、番号（H1…）と比率を計算して記録し、出力に印を付ける
エージェントまず直接の根拠を探し、見つからないときだけ許可範囲の中で仮説を書く（前提の論文、推論の種類、理由）。レポートの ## Hypotheses で開示する

許可範囲

許可範囲は、どの主張を、どの要素について、どれだけの比率まで仮説にしてよいかを定めます。

  • 作成時：利用者は、許す主張（1 つ以上）、比率の上限（10 / 20 / 30 / 50%、既定 20%）、任意のメモ（200 文字以内）を選びます。プロジェクトは仮説モードになり、対象を HCD 全体とする許可範囲 S1 と、比率の上限を持ちます。
  • フォローアップ：利用者は、許す主張、対象、比率の上限、メモを選びます。対象は「全体」か、グラフで選んだ回路と GN（合計 1〜200 個）です。新しい許可範囲が、それまでで最大の番号に 1 を足した番号で加わり、仮説を許していなかったプロジェクトでも仮説モードになります。ワーカーは指示の後に Hypotheses allowed with this instruction: <scope> (share limit n%) の 1 行を足します。
  • 範囲の判定：対象の回路は、挙げた UC、挙げた Collection の UC（入れ子も展開します）、挙げた GN の下のすべての階層の UC です。接続は、送り手か受け手が対象の回路なら範囲に入ります。UC は、それ自身が対象か、その接続の相手が対象なら範囲に入ります。ある許可範囲が仮説を覆うのは、その仮説のすべての主張を許し、対象がその要素を覆うときです。
  • 文献だけへの復帰：仮説モードのプロジェクトで、ジョブが CSV まで完了し、最後の検査で仮説が 0 件なら、ワーカーはプロジェクトを文献だけのモードに戻します。許可範囲と上限は記録として残ります。
  • 複製：仮説モードかどうか、許可範囲、比率の上限をコピーします。

API の要求の形式とエラーは付録 A.12 に記載しています。

仮説の記録の形式

仮説は、uc.json の UC と connections.json の接続に、任意の hypothesis キーとして書きます。Collection と BIF には付けません。このキーは仮説モードのプロジェクトに見せるスキーマにだけあり、仮説モードでないプロジェクトのスキーマにはありません。

欄値
claims主張。1 つ以上、各 1 回。接続では existence・direction・sign。UC では population・transmitter・modulation・role（role は印を付けるだけ）
basis推論の種類。直接的なものから順に、published（論文が仮説として述べる）、homology（相同性が不確かな他種の領域）、analogy（類似の回路）、indirect（機能的結合・共活性化・損傷・向きのない拡散 MRI など）、model（計算モデルが必要とする）、functional-need（FRG が TLF を実現するためだけに必要）。他種での直接の証拠は、Taxon を付けた通常の証拠として扱う
rationale理由。空でない文で、前提がなぜ仮説を支えるかと、直接の証拠を何で探して見つからなかったかを書く。[Author, Year] の引用は通常どおり検査する。予測・検証・次の手順は書かない
premises前提。references.json の Reference ID を 1 つ以上（通常どおり照会する）。接続では、先頭がそのレコードの最初の文献
scope仮説を許す許可範囲の ID（S<n>）
researchCandidate調査モードだけ。探した記録である research.json の候補（C<n>）で、状態が not_found か weak のもの

ワーカーの検査

仮説の検査で見つかった問題は、すべてエラーとして修正ターンで返します。メッセージは、欄を直す、論文を証拠として引用する、仮説を外す、のどれをすればよいかを示します。仮説の検査は HCD 段階の外のファイルにも依存します（GN の対象を決める frg.json、候補の research.json、レポート）。そのため HCD のファイルが変わっていなくても、FRG と CSV の検査でやり直します。表中の「安全側」は、仕様の要求より厳しくしてある検査を表します。

検査メッセージが求めること
キーのスキーマ（すべてのモード）、空の理由キーを直す
主張・前提の重複1 回ずつ挙げる
references.json にない前提。DOI も PMID もない前提（安全側）照会できる前提を挙げる
接続の最初の前提が、そのレコードの最初の文献でないレコードの論文を先頭にする
存在の仮説なのに測定法が Hypothetical でない。向き・符号の仮説や仮説のないレコードに Hypothetical（安全側）Hypothetical にする、論文の測定法に戻す、またはキーを足す
仮説でないレコードがすでに支える送り手 → 受け手への、存在の仮説仮説のレコードを外す
同じ送り手 → 受け手への 2 つ目の存在の仮説（安全側。比率を水増ししない）1 つにまとめ、ほかの論文は前提と理由に挙げる
集団の仮説なのに Source of ID が makeshift でない。アンカーだけの UC（SABRA の単位そのもの）への集団の仮説（安全側）makeshift にする、facet を足す、または別の主張にする
伝達物質の仮説で値が空、修飾の仮説で値が空（安全側）推定した値を書く
主張と要素を覆う許可範囲がない仮説を外す（許可範囲と、どの許可範囲も許さない主張を示す）

scope が不明、または覆わない（ほかの許可範囲が覆う）覆う許可範囲を書く
調査モードで、researchCandidate がない・候補にない・contradicted（外す）・supported（その証拠を使う）など。調査モードでないのに researchCandidate がある候補を直すか外す
比率が上限を超える仮説を減らす（比率を下げるために接続や UC を足さない）。上限の中で TLF を実現できないなら、ターン終了の message でそう伝える
レポート（後述）節・ID・文を足す

仮説を許していないプロジェクトでは、hypothesis キーを持つ UC や接続があれば、ファイルごとに 1 つのメッセージで返し、論文と引用で支えるか、外すよう求めます。利用者が指示の文章で仮説を頼んでいた場合、エージェントは、「この指示で仮説を許す」をオンにして指示を送り直す必要があることを message で伝えます。文献だけのプロジェクトでは、Hypothetical は普通の列挙値です。文献だけのプロジェクトの依頼文・検査結果・CSV・xlsx は、仮説モードがないときと同じです。

比率・番号・レポート

  • 比率：プロジェクトの版全体で、すべての許可範囲を合わせて数えます。仮説の接続の数を接続のレコードの総数で、仮説の UC の数をすべての UC（ROI の内部と外部。Collection は数えない）の数で割ります。主張の数にかかわらず、要素は 1 回だけ数えます。
  • 上限の計算：許されるのは floor(p × 全体 / 100) 個までです（p は上限の百分率）。整数で計算するので、上限 20% なら 10 件中 2 件は通り、3 件は通りません。上限は 10 / 20 / 30 / 50% で、既定は 20% です。
  • 番号：H1、H2… を、まず uc.json の順に UC へ、次に connections.json の順に接続へ付けます。追加や削除で番号は変わりえます。CSV の注記、仮説の記録、レポートの検査、整合の記録は同じ番号を使います。
  • レポート：仮説が 1 つ以上あれば、## Limitations の前に ## Hypotheses の節を置き、すべての ID を挙げます。節には、ID・要素・主張・推論の種類・前提・理由の表と、上限に対する 2 つの比率を書き、functional-need は太字にします。
  • 根拠だけの経路：ROI の入力から出力まで、仮説の接続を使わない有向の経路がないときは、## Limitations に定型文 "No evidence-only path leads from the ROI inputs to the ROI outputs." を書きます。仮説モードの Limitations には事実だけを書き、今後の研究は書きません。
  • FRG：許可範囲の中では、FRG の指示書（B.6）の手順 5 にある、UC や接続を足さないという制約は仮説を禁じません。その追加は判断ログの revisions に [FRG->HCD][hypothesis] として記録します（3.11）。仮説を証拠に置き換えるのは、指示があったときだけです（[hypothesis] H3 → evidence [Author, Year]）。

画面

  • 作成画面：入力欄のツールバーにある「仮説モード」をオンにすると、許す主張のチェックボックス（存在・向き・符号・集団・伝達物質と修飾・役割。最初はすべてオンで、役割は外せません）、上限（最初は 20%）、任意のメモが出ます。
  • フォローアップ：完了したプロジェクトのエージェント欄に「この指示で仮説を許す」があり、送るたびにオフに戻ります。オンにすると、主張、対象（「全体」か「グラフで選んだ回路・GN」）、上限（最初は「変えない」）が出ます。
  • 表示：ヘッダーとプロジェクトの一覧に「仮説モード」のバッジと、分かれば仮説の件数が出ます。版のタブの生成条件には、根拠のモード・許可範囲・件数と全件数（割合）・上限が出ます。詳細パネルには、仮説ごとの ID、推論の種類、主張、理由、前提、許可範囲が出ます。予測や検証の方法は出しません。

実装

プロジェクトの設定は evidenceMode（strict か hypothesis。値がなければ strict と同じ）、hypothesisScopes、hypothesisMaxShare です。許可範囲の依頼文は prompts/phases/HYPOTHESIS.md、スキーマの出し分けは agentHarnessSchemas です。検査は hypothesisProblems、範囲の判定は scopeTargetCovers、比率は hypothesisShare、番号は hypothesisRecords、仮説の記録のスキーマは HYPOTHESES_SCHEMA です。hypotheses.json は scopes、share、hypotheses[]、evidenceOnlyPath、gns[] を持ち、cross_check.json では hypotheses に記録します。

典拠：prompts/phases/HYPOTHESIS.md、packages/shared/src/hypothesis.ts・hypothesisInput.ts・hypothesisVersion.ts・graphHypothesis.ts、packages/worker/src/hypothesisRules.ts、packages/api/src/lib/hypothesisSettings.ts、packages/web/src/components/hypothesis/、利用マニュアル「仮説モード」

3.13 出力：CSV・xlsx・グラフ

CSV 段階と xlsx 段階は、ワーカーのプログラムだけの処理で、LLM は関与しません。CSV をエージェントに書かせず、同じデータから xlsx とグラフを作るので、別々に書いた表どうしが食い違うことはありません。

成果物作り方

CoBRAC 形式の xlsxCSV から作る。Capability&Mechanism のセルには、Capability、テンプレートの既定の印 <<mechanism to realize the capability>>、Mechanism を入れる
Template-v2-2 の xlsxBRA Data Preparation Manual の公式テンプレートに同じデータを書く（後述）。ダウンロード名は {名前}_{ID}.template-v2-2.bra.xlsx

レポートと判断ログエージェントが書いた文章を、そのまま閲覧・ダウンロードできるようにする

公式テンプレートの生成だけが失敗した場合、CoBRAC 形式の xlsx とグラフがそろった状態でジョブが完了することがあります。必要な形式がそろっているかは、ジョブの状態だけでなく出力で確認してください。完了した結果は、ワーカーが生成条件と一緒に凍結して版にします（4.5）。公式テンプレートの出力ができる前に完了したプロジェクトの扱いは、付録 C に記載しています。

CSV の形式

Project.csv に書く BRA version は CoBRAC-v1-1 です。v1-0 からの列の変更は末尾への追加だけで、v1-0 のすべての列の位置は変わりません。追加した列は次のとおりです。グラフは v1-0 と v1-1 の CSV を列名で読みます。

  • References：Literature type と Alternative URL
  • Circuits.csv：UC Descriptor の後ろに Sub-Circuits と Uniform
  • Connections.csv：Pointers on figure の後ろに、2 つの関係と論文中の表記

公式テンプレートへの書き込み

  • テンプレートが土台：11 枚のシート、見出し、数式、AdminOnly のリスト、入力規則、条件付き書式を残します。テンプレートが取り込む WholeBIF の行（入力欄の下にある IMPORTRANGE の結果）も残します。書くのは投稿者が入力するセルだけで、自動の列と管理用の列は数式のままにします。
  • 行：入力欄の行が足りないときは、投稿者が行うのと同じように、WholeBIF の取り込みの上に行を挿入します。最後の入力行を数式ごとコピーし、下の行への参照をずらします。テンプレートの配置の変化（IMPORTRANGE の行の位置）を検出したら、出力を失敗にします。
  • Reference ID：テンプレートは BibTeX のキーから Reference ID を作ります（Schultz_1997a → Schultz, 1997a）。そこで CoBRAC の ID ごとに、筆頭著者と年からキーを作ります（重なれば次の文字を付けます）。書き込む自由な文章の中の引用も、同じ ID にそろえます。
  • BibTeX：テンプレートの正規表現に合わせ、1 行に 1 項目、= の前後に空白を置きます。ジョブの最後に、ワーカーが DOI を Crossref で、PMID だけの文献を PubMed で照会し、結果を書誌の記録に残します。記録がなければ、references.json と文献の照合の結果から作ります。
  • DHBA の列：テンプレート自身が持つ WholeBIF の Circuits の行（Source of ID が DHBA）を、DHBA のオントロジーとして使います。これは HOMBA の graph_order とは別の番号です。1 つの DHBA 項にアンカーした UC はその行の値を、DHBA 項より細かい UC はその項の graph_order に小数を足した値を書きます。BNA にアンカーした回路、ROI の行、UC Descriptor のない回路は空にします。

テンプレートに書く場所のないもの（UC Descriptor、facet、BNA、CoBRAC の文献の検査など）と、テンプレートの上流に依頼する追加は、別のメモで管理されています。

実装

  • CSV は buildCsvs（Project.csv は buildProjectCsv）、グラフは buildGraphs が作ります。CoBRAC 形式の xlsx は prompts/csv_to_excel.py が対話なしで作ります（引数 --contributor・--project-id・--base-dir・--output）。
  • 公式テンプレートは prompts/templates/Template-v2-2.bra.xlsx で、buildTemplateXlsx（braTemplate.ts）が書きます。表計算のライブラリは Google 固有の部品を落とすので、XML の水準で編集します（xlsxSheet.ts、zip は fflate）。
  • 値の分かる数式セル（References の A / G〜J、Circuits の AO）には Google Sheets の計算結果を表示値として入れ、fullCalcOnLoad で残りを Excel に再計算させます。
  • 入力欄の行は、References 2〜29、Circuits 2〜31、Connections 2〜80、FRG 2〜198 です。行を挿入したときは、ほかのシートからの参照、入力規則の範囲、フィルタ、リンク、名前の定義もずらします。
  • 書誌の照会は bibliography.ts で、1 要求 10 秒、合計 60 秒までです。失敗したものは次のジョブで再試行し、REFERENCE_LOOKUP=off では照会しません。結果は bibliography.json に、照合の結果は reference_check.json にあります。

3.14 解説記事

解説記事は、完成した BRA を、それを作っていない読者に説明する記事です。利用者の求めに応じて作ります。BRA を作る段階の 1 つではなく、BRA の会話とは別の新しい会話で動く LLM のジョブです。

  • 作れるとき：プロジェクトが完了して xlsx まで生成済みで、動いているジョブがないときだけです。利用者は言語とモデルを選び、「記事を作成」を押します。言語は 10 言語から選べ、既定は画面の言語です。モデルの既定はプロジェクトのモデルで、デフォルトの API キーでは利用者の利用承認（4.1）で使えるモデルだけを選べます。
  • 言語ごとの記事：記事は言語ごとに並べて持てます。作り直したときは、新しい記事が検査に通ったときだけ置き換えます。
  • プロジェクトの状態：記事を作っている間、プロジェクトはフォローアップのときと同じく待機中 → 実行中 → 完了と進みます。ただし、段階の状態、プロジェクトの改訂番号、完了時刻、BRA の会話、プロジェクトフォルダは変えません。失敗や取り消しは記事のジョブの状態にだけ残し、プロジェクトは完了に戻します。
  • ワーカー：プロジェクトフォルダを、会話は復元せずに戻し、CSV から図を 3 枚描きます。全回路と接続の図、TLF → GN → UC の木の図、GN ごとの接続の図です。それぞれ幅 980 px 以内の図と 430 px のスマートフォン用の図があり、ラベルは日本語か英語です。そのうえで、Web 検索・RCS・文献のツールを持たない新しい会話を始め、記事の指示書と図の一覧、要約表の事実を送ります。
  • エージェント：成果物（meta.json・report.md・decision_log.md・HCD と FRG の JSON）だけを読み、記事を書きます。データにない事実は足しません。3 枚の図で示せない点があれば、自分で描いた SVG を最大 2 枚足せます。
  • 検査：次の点を検査します。問題は修正依頼として最大 3 回返し、それでも残ればジョブを失敗にします。
    • # のタイトルが 1 つあり、その後に要約表があり、## の節が 5 つ以上あること。最低の長さがあり、指定した言語の文字で書かれていること。
    • ワーカーの図を、それぞれ 1 回ずつ、代替テキストとキャプション付きで埋め込んでいること。ほかの画像は使えません。HTML や手書きの参考文献の一覧がないこと。
    • Circuit ID の間の矢印（`A` → `B`）は、connections.json にある接続だけであること。GN の ID が実在し、節へのリンクが見出しと合っていること。
    • 引用は references.json の ID だけであること。
  • 公開：ワーカーが参考文献の一覧（その言語の見出しと、引用した ID の DOI のリンク）を足し、図と記事を保存します。この実行ではプロジェクトフォルダを S3 に戻しません。SVG はすべて、ワーカーとブラウザの両方で、描画要素と表示属性だけを許す無害化を通します。ブラウザは画像として表示し、記事の欄が 640 px より狭ければスマートフォン用の図を使います。
  • 古さ：記事は、作り始めたときのプロジェクトの改訂番号を持ちます。その後のフォローアップで改訂番号が変わると、記事を「古い」と表示し、作り直しを勧めます。
  • 言語：記事は中心の成果物ではないので、成果物を英語で書くという規則の例外です。CSV・xlsx・グラフの変換は記事を読みません。日本語の記事は敬体の、平易な説明文にします。
  • 使用量：記事のジョブの使用量も、ほかのジョブと同じくプロジェクトの使用量に足します。

実装

記事のジョブの実行モードは article で、作れる条件は stepStates.XLSX = done です。プロジェクトの状態は QUEUED → RUNNING → COMPLETED と進み、revision は変えません。図は buildArticleFigures が描き、名前は circuit・frg・function-map です。指示書は prompts/article.md、検査は checkArticle、無害化は sanitizeSvg です。記事は <ProjectID>/article/<locale>.md と .json、図は article/<locale>/figures/ に保存し、ブラウザはオブジェクト URL の <img> で図を表示します。英語の規則の例外は AGENTS.md に明記されています。

典拠：prompts/article.md、packages/worker/src/article.ts、packages/shared/src/article.ts（checkArticle）・articleFigures.ts・svgSanitize.ts

3.15 長いジョブと保存

長いジョブでは、途中で止まっても作業を失わないことと、会話が大きくなりすぎないことが必要です。この 2 つはワーカーが受け持ちます。

  • 保存：実行中、ワーカーは 5 分ごとにプロジェクトフォルダと Codex の会話を S3 に保存します。Spot の中断を知らせる SIGTERM を受けたときも保存します。ワーカーが定期的に書くハートビートが途絶えたジョブは、janitor が回復を試みます（8.3）。
  • 会話の圧縮：Codex は会話を自動で圧縮します。既定では 75,000 トークンで圧縮し、組織の毎分のトークン上限を 1 回の要求で超えないようにします。コンテキストの窓は 272,000 トークンとして扱います。
  • 大きすぎる会話：会話が大きすぎて再開できない場合は、新しい会話で既存のファイルと判断ログを読んで続けます（3.5）。
  • コンテキストと費用の節約：ツールの結果を小さくし、ファイルを部分的に編集し、修正ターンだけ推論の強さを下げます。

使用量と費用の計算は 9.10 に、API キーなどの秘密情報の守り方は 9.5 に記載しています。

実装

圧縮のしきい値はワーカーの環境変数 CODEX_AUTO_COMPACT_TOKENS（既定 75000）、コンテキストの窓は定数 CODEX_CONTEXT_WINDOW（272000）です。保存とハートビートは index.ts、S3 との同期は s3sync.ts が行います。

典拠：packages/worker/src/codex.ts（CODEX_CONTEXT_WINDOW・turnUsage・sessionTotalUsage）、index.ts（保存とハートビート）、s3sync.ts、env.ts

3.16 完成した BRA の読み方と限界

完了は受理の保証ではない

ジョブの完了は、すべての検査に通ったことや、科学的に正しいことを保証するものではありません。残った警告、照合できなかった引用、調査の不足、仮説への依存は、成果物と一緒に読む必要があります。

検査で分かることの限界

ワーカーの検査と照合（3.10）は、形式と対応を機械的に検査するものです。どの層も、その先の科学的な妥当性までは保証しません。

層結果の限界
JSON Schema正しい形でも、内容が正しいとは限らない
HCD / FRG生物学的・計算論的な妥当性を完全には判定しない
SABRARCS が使えない場合の外部照合には欠落がある
BRA の値許された値を使っていることと、科学的根拠の強さとは別
文献の照合書誌が実在することは、その主張の保証ではない
引用文の照合図の内容や主張の含意までは自動では保証しない
調査検索しなかった文献がないことは証明しない

仮説前提を照合しても、仮説を実証したことにはならない
HCD と FRG の整合記録と調整の仕組みで、所見がすべてゼロになる保証ではない
