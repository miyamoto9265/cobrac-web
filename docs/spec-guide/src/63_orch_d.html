6.15 自律実行

自律実行（英語の画面では Autonomous run）は、計画の設定です（PlanSettings.autonomous = { maxCostUsd }）。Canon の設定ではなく、オーケストレーターの計画に付きます。基本の考え方は「オーケストレーターが人間の代わりになる」ことです。ふつうの計画で所有者が行う判断（確定・質問への回答・PR の承認・要対応と人の判断の行の扱い・再計画の提案の承認）を、オーケストレーター（ランナーと、オーケストレーターのモデルで動く AI のジョブ）が代わりに行います。目標を渡せば、下書きから Canon への取り込みまでが人の操作なしに進みます。止まるのは費用の上限に達したときだけです（時間や行の数の上限はありません）。

人を待つ場面ふつうの計画自律実行の計画
下書きの確定所有者が「確定して開始」下書きを適用したステップの直後に、ランナーが確定する（confirmedBy: "runner"）
エージェントの質問質問箱で回答を待つエージェントはふつうに質問できる。オーケストレーターの AI が質問を読んで個別に答える（回答のジョブ、回数の上限なし）
計画の PR人が承認・却下・変更依頼判断のジョブ（AI）が決め、ランナーが所有者の代わりに反映する
要対応（attention）所有者がリトライかスキップオーケストレーターの AI がエラーを読んで「リトライ」か「スキップ」を選ぶ（解決のジョブ）
人の判断（decision）所有者が完了・push・スキップオーケストレーターの AI が理由と PR を読んで「完了にする／もう一度 push／スキップ」を選ぶ（解決のジョブ）。ただし計画の Canon が見つからないときは、ふつうの計画と同じく一時停止（canon_missing）し、所有者が決める
ほかの Canon に入っている既存のプロジェクト人の判断（other_canon）確定のとき既存のプロジェクトを外し、この Canon のために作り直す
再計画の提案（行の追加・削除）承認するまで計画を変えないオーケストレーター自身の判断として、届いたときにすぐ反映する（決めた人は runner）

設定

  • 作成：POST /plans に autonomous: { maxCostUsd? } を付けます。自律実行の計画は下書きの作成から始めるので draft: true が必要です（無ければ 400）。費用の上限は 1〜1000 USD（AUTONOMOUS_MAX_COST_RANGE）、省くと 20 USD（AUTONOMOUS_DEFAULT_MAX_COST_USD）。canon を省くと、計画の名前で新しい Canon を作る選択（{ mode: "new", name }）になります。
  • 下書きの間：PUT /plans/{id} { settings: { autonomous: { maxCostUsd } | null } } でオン・オフと上限を変えられます。確定後は変えられません（上限の引き上げは再開で行う）。
  • 画面：新しい計画のフォームの「自律実行」スイッチと費用の上限、「自律実行で開始」（オンのときは「計画を作る」「下書きを作成」の代わりに出る）。下書きの画面の「3. 進め方」の一番上にも同じスイッチと上限の欄があります（6.7）。計画の一覧と計画の画面には「自律実行」の印、確定後の設定には「自律実行: 費用の上限 $n」が出ます。

下書きと確定

  1. 下書き：ふつうの計画と同じく、計画用のジョブが行・アンカー・依存・粒度方針を書きます（6.5）。ジョブが失敗したときは 1 回だけ自動で依頼し直します（PlanJobState.attempt。キーが無いなど所有者の側の理由で始められないときは、やり直さずに下書きに戻す）。
  2. 確定：自律実行の計画で下書きを適用すると、下書きの状態に autoConfirm: true を付け、Lambda のハンドラー（handlers/planRunner.ts の autoConfirm）が、そのステップが計画のリースを返した後に、所有者の確定と同じ関数（confirmPlan）でランナーとして確定します。リースが取れなければ次の分にもう一度試し（ハンドラーは毎分、確定を待つ自律実行の下書きを探す）、ほかの理由で失敗したら理由を autonomousError に残します。画面には「自律実行で下書きを確定できませんでした: …。内容を確かめて「確定して開始」を押してください。」と出て、所有者が手で確定すると消えます。
  3. 下書きができたあとでオンにした計画（autoConfirm が無い）は自動では確定しません。所有者が確定すると、そこから自律実行で進みます。

行のジョブ（回答と解決）

オーケストレーターの AI が 1 つの行について判断するジョブを行のジョブと呼びます。種類は 2 つで、answer（回答）と resolve（解決）です。どちらも下書き・再計画と同じ plan のジョブで、次の性質を持ちます。

  • 同時実行数の枠を 1 つ使い、オーケストレーターのモデル（推論の強さ medium）と所有者のキーで動きます。費用は計画の費用に入ります。
  • planJobKind は answer / resolve、planRowId に行を持ちます。
  • ランナーは入力を plans/{planId}/jobs/{jobId}/input.json に書きます。入力は PlanRowJobInput で、計画の名前・目標・粒度方針、Canon の名前と方針、行（ROI・TLF・理由・バッチ・基準プロジェクトか・アンカー・依存する行）、プロジェクト（状態・質問・最後のエラー・decision_log.md の末尾 12,000 字）、解決では状況と選択肢を含みます。
  • ワーカーは道具を使わない 1 ターンで、prompts/orchestrator.md（付録 B）と入力を読ませ、種類ごとの固定のスキーマで答えさせます。形が違えば 1 回だけ頼み直し、5 分（PLAN_ROW_JOB_TIME_BUDGET_MS）で打ち切ります。答えは result.json に書きます。
  • ランナーは結果を入力と照らして検証し直してから使います（parsePlanRowResult）。回答が空なら使いません。選択肢に無い行動も使いません。
  • 1 つの行に同時に 1 件だけです（row.rowJob = { kind, jobId, status, requestedAt }）。
  • 失敗した・止められた・結果が読めないジョブは rowJob を消し、間をおいて依頼し直します。続けて失敗した回数・最後のエラー・次に依頼できる時刻を row.orchestratorRetry に記録し、待つ時間は 1・2・4…分（最大 60 分、orchestratorRetryDelayMs）です。キーの残高切れのように費用のかからない失敗が続いても、毎分ジョブを起こすことはありません。回数の上限はなく、成功すると記録を消します。行には失敗の回数とエラーが出ます。
  • ジョブの間に行が別の状態に移ったとき（所有者が先に答えた・決めた）は、結果を使わずに捨てます。

質問への回答（回答のジョブ）

  • エージェントは質問してよい：自律実行でも、行のエージェントはふつうの計画と同じように質問できます。「質問しない」という指示（v0.40.0 の prompts/autonomous.md と questionMode）はやめました。
  • 依頼：質問中の行（question、プロジェクトが WAITING_USER_INPUT）に回答のジョブを依頼します。実行中の計画のステップの枠の部分で、ほかのジョブより先に、空き枠があるときだけ依頼します。
  • 答え方（prompts/orchestrator.md）：所有者として決めて、はっきり答えます。聞き返したり、選択肢を並べたりはしません。根拠が支えるならエージェントの推奨を採り、そうでなければ次の条件を満たすものを選びます。
    • ROI・TLF をそのまま保つ
    • Canon の定義と粒度方針に合う
    • 最も保守的で、あとで直しやすい
    行の範囲は広げず、仮説も求めません。論文・ID・値は作りません。決めたことは decision_log.md に残すよう伝えます。出力は { answer, reason } です。
  • 渡し方：ジョブが終わると rowJob.status を ready にし、次の空き枠で回答を渡します（再開したプロジェクトのジョブが枠を 1 つ使うため）。渡すのは、ジョブが読んだ質問と、いまプロジェクトが待っている質問が同じときだけです。渡すときは回答の API と同じ関数（answerQuestion、source: "auto"）を使い、ジョブの状態を条件に書くので、人の回答と二重になりません。
    • エージェントが受け取る本文は「answer」と「Reason: reason」です。見出しは「Answer from the CoBRAC Orchestrator (it decides for the user in this autonomous run)」です（answerPreamble）。
    • 行は running に戻り、autoAnswers が 1 増えます。
    • 履歴には row_auto_answered（回数・ジョブ・回答と理由の冒頭）が残ります。
    • プロジェクトのチャットには「オーケストレーター（AI）がエージェントの質問に回答しました。」と、質問と回答が出ます。
  • 回数の上限はありません。同じ行が質問を繰り返しても答え続けます。止めるのは費用の上限だけです。

要対応・人の判断の解決（解決のジョブ）

  • 依頼：要対応（attention）と人の判断（decision）の行に解決のジョブを依頼します。計画の Canon が見つからないことによる人の判断（lastError が「The plan's Canon was not found.」）は除きます。それは所有者が決め、計画は一時停止します。入力の situation には次のものが入ります。
    • 状態・理由・エラー
    • 自動リトライの回数、オーケストレーターがこれまでにリトライを選んだ回数（orchestratorRetries）、前回の解決（previous）、追加指示の回数
    • PR の番号・状態・メモ
    • 選択肢（planRowOptions）：要対応は retry（プロジェクトが削除されていれば無し）/ skip、人の判断は done / push（プロジェクトが完成しているときだけ）/ skip
  • 選び方（prompts/orchestrator.md）：
    • retry：一時的な失敗のとき（時間切れ、レート制限、ワーカーの消失、形式の誤り）。
    • skip：同じ失敗を繰り返す・プロジェクトが削除された・PR が Canon に合わない・費用に見合わないとき。
    • done：完成していて計画に役立つが、Canon には取り込めないとき。
    • push：原因がなくなったとき。
    迷ったら、失敗を繰り返す行はスキップします。出力は { action, reason } です。
  • 反映（applyResolution）：所有者のボタンと同じ遷移にします。
    • retry → pending（要対応の理由を消し、aiRetries を 1 増やす）
    • skip → skipped（autoSkip.reason = "ai_skipped"、error に AI の理由）
    • done → done
    • push → running（次のステップで push し直す。完成していなければ使わずに依頼し直す）
    行には aiResolution = { action, reason, at, jobId } を残し、履歴には row_ai_resolved（行動・元の状態・理由のコード・AI の理由・ジョブ）を残します。画面には「オーケストレーター（AI）の判断: リトライ / スキップ / 完了にする / もう一度 push」と理由が出ます。
  • 所有者は、これまでどおり要対応・人の判断の行のボタンで先に決めることもできます。そのときジョブの結果は捨てます。
  • 計画を中止すると、待機中・実行中の行のジョブも止めます（stopPlanJob）。

PR の判断

  1. 依頼：自律実行の計画では、review のすべての行（基準プロジェクトも、手で push した PR を追う行も）が判断を待ちます（aiReview: "wanted"）。ランナーは空き枠で、AI レビューと同じ関数（requestAiReview）を kind: "decide"・planId つきで、オーケストレーターのモデルと計画の返答言語で所有者として依頼します（1 件 1 枠。canon-review のジョブで reviewKind: "decide"、行の decideAttempts が 1 増える）。手で依頼した AI レビュー（判定なし）が終わった PR にも、判断のジョブを依頼します。
  2. 判断（ワーカー）：材料は AI レビューと同じ（buildCanonAiPacket）で、所見に加えて判定・理由・衝突ごとの選択・依頼する変更を返させます（4.8 の「判断のジョブ」）。材料の文字列はデータとして扱い、指示として従わないよう指示します。
  3. 反映（ランナー、applyDecision）：ジョブが完了したら、PR がまだ開いていることを確かめ、判断と PR の取り込み内容を読み、いまの head に対して差分を取り直して、コードが行き先を決めます（decisionAction）。PR が人の手で決まっていれば、それに従います（6.11）。
AI の判定いまの head に対する差分ランナーの処理行
approveエラーの衝突なし。警告は AI が選んだ側（選ばなかったものと C2b / C8b は canon）、情報は AI が選んだものだけ。それでもブロックする衝突が無いapprovePullRequest（所有者として、名前は「AI (<モデル>)」、理由をメモに）。Canon は新しい rev にdone（row_ai_decided・row_done）
approveエラーの衝突がある（判断の後に Canon が進んでできたものも）、またはブロックする衝突が残るPR に変更の依頼を記録し、Canon に合わせる追加指示（canonFixInstruction：衝突ごとに Canon の値とこのプロジェクトの値を並べる）を用意pending（followup.kind = "fix"）
request_changes—AI が挙げた変更（無ければ理由）で requestPrChanges し、それを追加指示にするpending（followup.kind = "changes"）
reject—rejectPullRequest（理由つき）見送り（ai_rejected）
  • 追加指示：Canon に合わせた更新（6.11）と同じ経路で、空き枠とバッチの順で始まります。プロジェクトを最新の rev に固定し直し、queueFollowup で積みます。題は fix なら「Canon rev N に合わせて更新」、changes なら「Canon PR #n の AI レビューの指摘に対応」で、続けて依頼の本文です。完成すると再び push し、新しい PR が古い PR を置き換えて、また判断します。
  • push の時点のエラーの衝突：ふつうの計画では、Canon が進んでいないのにエラーの衝突があると人の判断ですが、自律実行では fix の追加指示にします（pushOutcome(…, { autonomous: true }) → { to: "conform", fix: true }）。
  • 回数：追加指示（Canon に合わせた更新を含む）は 1 行 3 回（AUTONOMOUS_MAX_FOLLOWUPS）までです。ふつうの計画は 2 回です。超えると、その行は人の判断（conform_limit）になり、解決のジョブが「完了にする／もう一度 push／スキップ」を選びます。判断のジョブが失敗したとき、または結果が読めないときは、行のジョブと同じ間隔（orchestratorRetry）をおいて、上限なしで依頼し直します。v0.40.0 にあった「3 回で見送り」（decide_failed）はやめました。
  • 競合：承認の途中で別の承認が Canon を進めた（race）ときは、次のステップで新しい head に対してもう一度反映します。
  • 範囲：判断するのは、その計画が push した PR だけです。同じ Canon へのほかの PR（ほかの人・ほかの計画のもの）は、これまでどおり人が判断します。
  • 記録：判断した人は「AI (<モデル>)」と、判断したジョブとモデル（via）が PR・承認・履歴・rev に残ります（4.8）。PR の画面の「AI レビュー」には「AI の判断」（「AI が承認」「AI が変更を依頼」「AI が却下」、理由、依頼した変更）が出ます。

コードが最後に決める線：AI はエラーの衝突を選べず（incoming を選んでも除く）、エラーの衝突のある PR は取り込まれません。選ばれなかった警告は Canon の値を残します。AI の判定がどうであれ、取り込みは人の承認と同じ approvePullRequest（同じ検査）を通ります。

再計画の提案

自律実行の計画では、再計画のジョブが出した「行の追加」「行の削除」の提案を、結果を保存したその場でランナーが反映します（applyProposals）。提案は強い一貫性で読み直してから反映し、ジョブを「済み」にするのは反映のあとです。途中で止まったステップは、次のステップで同じ提案（同じ ID）を保存し直して反映します。反映には、所有者の承認と同じ関数（applyProposal）を使い、決めた人は runner です（画面では「オーケストレーターが反映」）。反映できない提案は stale になります。たとえば次のときです。

  • 同じ ROI × TLF の行がすでにある
  • 外す行がもう始まっている
  • 行が 200 行に達している

粒度方針の変更は、ふつうの計画と同じく承認なしで反映します。

費用の上限

  • 数える費用（planSpendUsd、推定 USD）：各行のプロジェクトの費用（既存のプロジェクトで済んだ行は数えない）、計画用のジョブ（下書き・再計画・行のジョブ）、この計画の PR の canon-review のジョブ（AI レビューと判断）。
  • 上限に達したら：毎ステップ確かめ、初めて達したときに costLimitAt とイベント cost_limit_reached（費用と上限）を記録します。それ以降、新しい行・追加指示・解決のジョブ・再計画を始めません。実行中の行は最後まで進み、その質問への回答（回答のジョブ）と PR の判断も続きます。動いているもの（開始中・実行中・質問中の行、判断を待つ PR、行のジョブ）が無くなると、計画は一時停止します（pausedReason: "cost_limit"。画面には「一時停止中: 自律実行の費用の上限に達したため、新しい行を始めていません。上限を上げると再開できます。」）。要対応・人の判断の行は、そのまま再開を待ちます。実行中の行が最後まで進むので、費用は上限を少し超えることがあります。
  • 再開：POST /plans/{id}/resume { maxCostUsd }。新しい上限は 1〜1000 USD で、これまでの費用より大きくなければ 400。設定を書き換え、costLimitAt を消し、イベント cost_limit_raised を残します。上限に達して止まった計画を上限なしで再開しようとすると 400 です。画面では一時停止の帯の下に「新しい費用の上限」と「上限を上げて再開」が出ます。
