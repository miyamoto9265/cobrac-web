第 6 部

CoBRAC オーケストレーター

CoBRAC オーケストレーター（旧称 BRA Planner。コードでは plan・Plans・planId・/plans）は、作りたい BRA（ROI × TLF）を計画にまとめ、所有者が確定すると、同時実行数の上限の範囲で行をバッチごとに自動で作る仕組みです。下書きは LLM に書かせられ、実行順序はコードが計算し、バッチが終わるたびに見直します。計画に Canon を 1 つ決めると、完成した行をその Canon に取り込みながら進みます。

LLM が決めること行（ROI × TLF と理由）、アンカー、依存関係、優先度、粒度方針。再計画では行の追加・削除と粒度方針の提案
コードが決めること実行順序（土台のバッチ・本体のバッチ）、同時実行の枠、状態の遷移、リトライ、Canon への push と追従
人が決めること確定、提案の承認・却下、質問への回答、要対応の行の扱い、Canon の PR の承認（自動では承認しない）。自律実行の計画では、確定・回答・PR の判断も人を待たない（6.15）

6.1 概要と段階

1 件の BRA の作成には中央値で約 48 分かかり、ある領域の機能を一通りそろえるには数十〜百件超の ROI × TLF が必要です。これを 1 件ずつ手で起動すると、どれを先に作るか、何件を同時に動かすか、同じ回路を作る行が同時に走って定義が食い違わないか、どれを Canon に取り込んだか、を人が管理することになります。オーケストレーターはこれらを計画にまとめて自動で進めます。単一の BRA の中身（調査・HCD・FRG）は通常のプロジェクトと同じで、オーケストレーターはその外側の進行管理だけを行います。

段階入ったもの
段階 1：計画とバッチ実行行は資料（CSV / TSV / テキストの一覧）か手入力。順序とバッチは所有者が手で決める。確定後、ランナーが毎分、同時実行数の範囲で行を起動し、状態を追う。Canon も LLM も使わない
段階 2：LLM の下書きと実行順序計画用のジョブ（LLM）が目標と資料から行・アンカー・依存・粒度方針を書く。実行順序はアンカーと依存からコードが計算（土台のバッチ）。バッチごとの並べ直しと再計画（提案）
段階 3：計画の Canon計画ごとに 1 つの Canon。完成した行を自動で push し、本体の行には AI レビューを依頼し、Canon が進んだことによる衝突は更新の追加指示で直す。行は人が PR を承認して完了。「まとめて承認」
v0.37.0モデルを「オーケストレーター」（下書き・バッチ後の再計画・行の PR の AI レビュー）と「エージェント」（各行の BRA）で別々に選ぶ。どちらも「デフォルト」なら確定時に決まり、確定後は両方が表示される。それ以前の計画は 1 つのモデルを両方に使い続ける。粒度方針はオーケストレーターが決める（計画の画面では読み取り専用、API も所有者からの方針を拒む。再計画の方針の変更は承認なしですぐに反映され、決定済みの提案に「オーケストレーターが反映」として残る。行の追加・削除の提案は従来どおり承認を待つ）。日本語の表記を「波」→「バッチ」（「第 1 バッチ」「土台のバッチ」）、「能力リスト」→「資料」に改めた（CSV の列名「バッチ」「batch」も「波」と同じくバッチとして読む）
v0.40.0：自律実行計画の設定「自律実行」（settings.autonomous、費用の上限つき）。下書きのあと自動で確定し、行のエージェントは質問せず推奨案で進み、計画の PR は AI が承認・変更依頼・却下を判断し、進められない行は見送る。費用の上限に達すると新しい行を始めない（6.15）。日本語の表記を「種」→「土台」（「土台のバッチ」）に改めた（コードの seed はそのまま）

6.4 手順 1：計画を作る

  1. サイドバーの「CoBRAC オーケストレーター」で「新しい計画」を押し、右から開くパネルに名前と目標（例「言語の BRA を一通りそろえたい」）を入れる（計画が 1 つも無いときは、フォームが画面に出ている）。
  2. 資料のファイル（CSV・TSV・テキスト・xlsx・PDF、10 個まで）を追加するか、行を貼り付ける。1 行が 1 プロジェクト。
  3. 「計画を作る」は読み込んだ行で計画を作る。「下書きを作成」は計画を作ると同時に下書きを依頼する（目標・ファイル・行のどれかが必要）。
  4. 読めなかった行は、ファイル名・行番号と理由が画面に出る。直して「CSV を読み込む」で追加できる。

一覧の読み取り規則（parsePlanRowsCsv）

  • 見出し行があるときは列名で読みます：ROI（ROI / region / 脳領域）、TLF（TLF / function / capability / 機能 / 能力）、理由（rationale / note / 理由 / 備考）、バッチ（wave / batch / バッチ / 波）、優先度（priority / 優先度）。ほかの列は無視します。
  • 見出し行が無いときは、1 列なら TLF、2 列以上なら ROI・TLF・理由の順です。CSV か TSV、BOM は除き、空行は飛ばします。
  • 取り込まない行（行番号と理由を表示）：ROI も TLF も無い、長すぎる（ROI / TLF 300 字、理由 1000 字）、同じ ROI × TLF の行がある（大文字小文字と空白は無視。計画にある行とも比べる）、バッチが 1〜99 でない、優先度が整数でない、計画の行が 200 を超える。
  • CSV・TSV・テキストは API（プログラム）がすぐに行として読みます（出所 csv。読めない行は file つきで一覧）。xlsx と PDF は保存だけして、下書きのジョブが読みます（計画を作った後で「下書きを作成」を押しても読む）。
  • 添付できる種類は PLAN_ATTACHMENT_EXTS = csv・tsv・txt・xlsx・pdf で、ほかは 400 です。ファイルは POST /uploads で一時置き場に上げてから POST /plans の attachments で渡し（10 個まで）、plans/{planId}/attachments/files/NN-<名前> に移されて META.attachments（kind: "file"、id は f1・f2…、名前、計画の接頭辞からの key、大きさ、種類）に並びます。名前と移動先は先にすべて検査し（..・.・空のパスの区切りは不可。list..v2.xlsx のような名前はよい）、不正なものがあれば何も移さず 400「添付ファイルの名前が不正です」です。
  • 貼り付けた行、添付した CSV・TSV・テキスト、あとから読み込む CSV（「CSV を読み込む」、POST /plans/{id}/rows/import）は、それぞれ 50 万文字まで（PLAN_LIMITS.maxCsvChars）です。

6.5 手順 2：下書きを作成する（LLM のジョブ）

「下書きを作成」を押すと、計画用のジョブ（type: "plan"、1 回の Codex のタスク）が、目標・資料・いまの行を読み、行・アンカー・依存関係・優先度・粒度方針を書きます。モデルはデータを出すだけで、実行順序はコードが計算します（再現でき、バッチごとに安く計算し直せる）。

依頼からジョブの開始まで

  1. 依頼（所有者 → API。POST /plans/{id}/draft { locale? }、または作成時の draft: true。目標・添付・行のどれかが必要）：所有者がジョブを実行できること（キーが無ければ 400、選んだモデルを使えなければ 403）を確かめ、計画のリースを取って DRAFT → DRAFTING（下書きは waiting、イベント draft_requested）。作成時は計画と行をいったん DRAFT で書いてから切り替えるので、ランナーが行の一部しか無い下書き中の計画を見ることはない。依頼そのものは何も積まず、ランナーを 1 回すぐに動かす。下書き中は行を編集できず、画面の帯にジョブの状態（ジョブの空きを待っています／開始を待っています／実行中）と経過時間が出る。
  2. 枠を待つ（ランナー）：全体と所有者の同時実行数に空きがあり（待機・実行・仕上げ中のジョブを数える。行のジョブと同じ枠）、所有者がまだジョブを実行できるときだけ、入力 plans/{planId}/jobs/{jobId}/input.json を書き、ジョブ（type: "plan"、planJobKind: "draft"、projectId = 計画 ID、オーケストレーターのモデル、推論の強さ medium）を積む（queued）。枠が無ければ waiting のまま（枠より先には積まない）。キーが無い・アカウントが無効・選んだモデルを使えなくなったときは、下書きを失敗にして理由とコード（no_key / owner_disabled / model_not_allowed。画面では翻訳して表示）とともに DRAFT に戻す（イベント draft_failed）。
  3. 入力：目標、粒度方針、計画の行（そのまま。優先度・依存・「作り直す」つき）、所有者の削除されていないプロジェクト（新しい順に最大 300 件。成果物つきで完了したものに completed の印）、所有者の Canon と粒度方針（最大 50 件）、実効の同時実行数、下書きなら API が読まなかった添付ファイル（{ id, name, key }。再計画には添付を渡さない）。キーなどの秘密は入れない（API とランナーは鍵を復号しない。ワーカーが通常のジョブと同じく planRunKey で解決して復号する）。

ジョブの中身（ワーカー、runPlanJob）

  • ワーカーは、計画用のジョブがまだ QUEUED のときだけ引き受け、キーを解決・復号し（無ければジョブを失敗に）、QUEUED であることを条件に RUNNING にする（その間に取り消された下書きは取り消されたまま）。
  • 添付ファイルを材料フォルダに写し、xlsx と PDF の本文を参考資料と同じ方法で抽出する（plans/{planId}/attachments/derived/ に残す）。
  • RCS の MCP（search_bna_candidates、search_homba_candidates、get_homba_term、get_sabra_definition）だけを使い、Web 検索も文献ツール（lit）も使わずに LLM を 1 ターン動かす。RCS が設定されていない環境では、アンカーを空にして notes にそう書くよう指示する。依頼文（planJobPrompt）は prompts/plan.md の指示、仕事の種類（DRAFT か REPLAN）、返答の言語、添付ファイルの索引、入力の JSON。
  • 返答は PLAN_RESULT_SCHEMA のオブジェクト（rows・unread・policy・proposals・notes。すべて必須）だけ。読めなければ 1 回だけ頼み直す（PLAN_RETRY_PROMPT）。
  • 時間の予算：7 分（PLAN_JOB_TIME_BUDGET_MS、ワーカーの開始から）。積む・Fargate の起動・ランナーの次のステップ（結果を反映する。最大 1 分後）を含めて、依頼から約 10 分で下書きができる。xlsx / PDF を読む下書きか、入力の行が 20（PLAN_JOB_SHORT_ROWS）を超える下書きは、項目ごとに 1 行を書くので 25 分（PLAN_JOB_LONG_TIME_BUDGET_MS）。超えたターンは打ち切られ、ジョブは「The plan job took longer than its time budget」で失敗する。打ち切り・取り消しのジョブも、使った分（打ち切ったターンはセッションのファイルから測り、SIGTERM のときはそこまでの利用量）を記録する。45 秒ごとにハートビートを送る。
  • 結果は入力の隣の result.json（PlanJobResult：スキーマ cobrac.plan-result/1、種類、計画とジョブの ID、モデル、言語、時刻、検証した行・unread・方針・提案・notes・dropped）に書き、利用量・推定費用とともにジョブを完了にする（失敗ならエラーと利用量を記録して FAILED）。

長い一覧全体で 30 行ほどを超えるときは、1 行あたりのアンカーを 3〜6 個にし、同じ領域は 1 回だけ引いて再利用し、理由と notes を短くする。それでも各項目に行か unread を必ず付ける
順序並べない・バッチに分けない（コードが計算する）
その他文章にモデル名を書かない。入力・添付・RCS だけを使い、Web を検索しない。時間の予算が厳しいので、検索を増やすより根拠のあるアンカーを少なく

検証（プログラム）

LLM が書いた JSON は、そのままでは使いません（parsePlanResult）。入力を指すものだけを残し、ほかは除いて件数（dropped）に数えます。

  • 下書きの行：入力の行は行 ID（ref）で、新しい行はモデルが付けた id で受け取る。ROI・TLF・理由の長さ、id や ROI × TLF の重複、アンカーの正規化（normalizePlanAnchor：HOMBA:<id>、既知の BNA 領域の BNA:<l>-<r>。単一ラベルはペアに、/side:left などの facet は除く。既知の群の BNAG:<L2>。1 行 40 個 MAX_ROW_ANCHORS まで）、依存は下書きの行だけ（自分自身は不可）、優先度は範囲内の整数（でなければ無し）、既存のプロジェクトは入力にある完成したものだけ。行は 200 まで、unread は 200 件（MAX_PLAN_UNREAD）まで。
  • 再計画の提案（30 件 MAX_PLAN_PROPOSALS まで）：add は計画にまだ無い ROI × TLF（依存は入力の行だけ）、remove は始まっていない行（pending・プロジェクト無し・既存でない）、policy はいまの方針と違う文（1 件まで）。下書きの提案と再計画の行は捨てる。
  • RCS が設定されているとき、ワーカーは行と add の提案から、RCS が知らない HOMBA のアンカーと、SABRA が BNA で覆う領域の HOMBA のアンカー（完成したプロジェクトはその領域を BNA の領域で表すので、HOMBA の ID は一致しない）を除いて dropped に数えます。引けなかったアンカーは残します。
  • ランナーは result.json を使う前に、もう一度確かめます（readPlanResult：スキーマ・種類・ジョブ ID が一致し、内容をジョブの input.json に対してもう一度 parsePlanResult に通す）。結果のファイルをそのまま信用することはありません。

適用（ランナー、計画のリースの中で）

  • ランナーはジョブを追い（RUNNING → 下書き running）、完了したら result.json を読みます。
  • ref のある結果の行は、その行を更新します：アンカー（anchorsSource: "predicted"）、依存（行 ID に対応させる）、優先度は行に無いときだけ（ジョブは所有者の優先度を見て返す。CSV の priority 列の値は上書きしない）、理由は行に無かったときだけ。ROI・TLF・出所は変わりません。
  • ref の無い結果の行は新しい pending の行（出所 llm）になります。ただし同じ ROI × TLF の行がすでにあれば、その行を更新します。消えた行を指す ref や、同じ行への 2 つ目の結果の行は捨てます。
  • 行の既存のプロジェクトは、結果の existingProjectId、無ければ matchExistingProject が見つけたもの（6.7）。「作り直す」の行には付けません。結果が触れない行はそのまま残します。
  • 行を自動で並べ（6.6、orderDraft、ordering: "auto"）、結果の方針が空でなければ方針を置き換え、行数を数え直します。計画は 200 行まで（超えた結果の行は dropped）。計画は DRAFT に戻り、下書きは done で unread の一覧と dropped の数を持ちます（イベント draft_applied）。画面には読めなかった項目（ファイル名・場所・理由）と、使わなかった部分の件数が出ます。
  • ジョブが失敗・取り消し・見つからない、または result.json を読めないときは、下書きを failed / cancelled にしてエラーとともに DRAFT に戻します（イベント draft_failed）。もう一度依頼すると、いまの行で新しいジョブが動きます。
  • 「下書きを取り消す」（POST /plans/{id}/draft/cancel、DRAFTING のときだけ）は、待機中か実行中のジョブを止め（ジョブは CANCELLED、Fargate のタスクも停止）、DRAFT に戻します（イベント draft_cancelled）。
