第 6 部

CoBRAC オーケストレーター

CoBRAC オーケストレーター（旧称 BRA Planner。コードでは plan・Plans・planId・/plans）は、作りたい BRA（ROI × TLF）を計画にまとめ、所有者が確定すると、同時実行数の上限の範囲で行をバッチごとに自動で作る仕組みです。下書きは LLM に書かせられ、実行順序はコードが計算し、バッチが終わるたびに見直します。計画に Canon を 1 つ決めると、完成した行をその Canon に取り込みながら進みます。

LLM が決めること行（ROI × TLF と理由）、アンカー、依存関係、優先度、粒度方針。再計画では行の追加・削除と粒度方針の提案
コードが決めること実行順序（種のバッチ・本体のバッチ）、同時実行の枠、状態の遷移、リトライ、Canon への push と追従
人が決めること確定、提案の承認・却下、質問への回答、要対応の行の扱い、Canon の PR の承認（自動では承認しない）

6.1 概要と段階

1 件の BRA の作成には中央値で約 48 分かかり、ある領域の機能を一通りそろえるには数十〜百件超の ROI × TLF が必要です。これを 1 件ずつ手で起動すると、どれを先に作るか、何件を同時に動かすか、同じ回路を作る行が同時に走って定義が食い違わないか、どれを Canon に取り込んだか、を人が管理することになります。オーケストレーターはこれらを計画にまとめて自動で進めます。単一の BRA の中身（調査・HCD・FRG）は通常のプロジェクトと同じで、オーケストレーターはその外側の進行管理だけを行います。

段階入ったもの
段階 1：計画とバッチ実行行は能力の一覧（CSV / TSV / テキスト）か手入力。順序とバッチは所有者が手で決める。確定後、ランナーが毎分、同時実行数の範囲で行を起動し、状態を追う。Canon も LLM も使わない
段階 2：LLM の下書きと実行順序計画用のジョブ（LLM）が目標と資料から行・アンカー・依存・粒度方針を書く。実行順序はアンカーと依存からコードが計算（種のバッチ）。バッチごとの並べ直しと再計画（提案）
段階 3：計画の Canon計画ごとに 1 つの Canon。完成した行を自動で push し、本体の行には AI レビューを依頼し、Canon が進んだことによる衝突は更新の追加指示で直す。行は人が PR を承認して完了。「まとめて承認」
v0.37.0モデルを「オーケストレーター」（計画用のジョブ・再計画・AI レビュー）と「エージェント」（各行の BRA）で別々に選ぶ。粒度方針はオーケストレーターが決める（所有者は編集しない）

計画の状態

自動の一時停止の理由（pausedReason）：no_key（API キーが無い）、owner_disabled（アカウントが無効）、model_not_allowed（選んだモデルをティアが許さなくなった）、canon_missing（計画の Canon が見つからない）。手動は user。

6.4 手順 1：計画を作る

  1. サイドバーの「CoBRAC オーケストレーター」で、名前と目標（例「言語の BRA を一通りそろえたい」）を入れる。
  2. 資料のファイル（CSV・TSV・テキスト・xlsx・PDF、10 個まで）を追加するか、行を貼り付ける。1 行が 1 プロジェクト。
  3. 「計画を作る」は読み込んだ行で計画を作る。「下書きを作成」は計画を作ると同時に下書きを依頼する（目標・ファイル・行のどれかが必要）。
  4. 読めなかった行は、ファイル名・行番号と理由が画面に出る。直して「CSV を読み込む」で追加できる。

一覧の読み取り規則（parsePlanRowsCsv）

  • 見出し行があるときは列名で読みます：ROI（ROI / region / 脳領域）、TLF（TLF / function / capability / 機能 / 能力）、理由（rationale / note / 理由 / 備考）、バッチ（wave / batch / バッチ / 波）、優先度（priority / 優先度）。ほかの列は無視します。
  • 見出し行が無いときは、1 列なら TLF、2 列以上なら ROI・TLF・理由の順です。CSV か TSV、BOM は除き、空行は飛ばします。
  • 取り込まない行（行番号と理由を表示）：ROI も TLF も無い、長すぎる（ROI / TLF 300 字、理由 1000 字）、同じ ROI × TLF の行がある（大文字小文字と空白は無視。計画にある行とも比べる）、バッチが 1〜99 でない、優先度が整数でない、計画の行が 200 を超える。
  • CSV・TSV・テキストはすぐに行として読みます（出所 csv）。xlsx と PDF は保存だけして、下書きのジョブが読みます。ファイルは plans/{planId}/attachments/files/NN-<名前> に移され、名前と移動先は先にすべて検査されます（.. などがあれば何も移さず 400）。

6.5 手順 2：下書きを作成する（LLM のジョブ）

「下書きを作成」を押すと、計画用のジョブ（type: "plan"、1 回の Codex のタスク）が、目標・資料・いまの行を読み、行・アンカー・依存関係・優先度・粒度方針を書きます。モデルはデータを出すだけで、実行順序はコードが計算します（再現でき、バッチごとに安く計算し直せる）。

依頼からジョブの開始まで

  1. 依頼（POST /plans/{id}/draft、または作成時の draft: true）：所有者がジョブを実行できること（キーが無ければ 400、選んだモデルを使えなければ 403）を確かめ、計画のリースを取って DRAFT → DRAFTING（下書きは waiting）。依頼そのものは何も積まない。下書き中は行を編集できない。
  2. 枠を待つ（ランナー）：全体と所有者の同時実行数に空きがあり（行のジョブと同じ枠）、所有者がまだジョブを実行できるときだけ、入力 plans/{planId}/jobs/{jobId}/input.json を書き、ジョブ（オーケストレーターのモデル、推論の強さ medium）を積む（queued）。キーやモデルを使えなくなっていれば下書きは失敗し、理由のコードとともに DRAFT に戻る。
  3. 入力：目標、粒度方針、計画の行（優先度・依存・「作り直す」つき）、所有者のプロジェクト（新しい順、完成したものに印）、所有者の Canon と粒度方針、実効の同時実行数、API が読まなかった添付ファイル。キーなどの秘密は入れない（API とランナーは鍵を復号しない。ワーカーが通常のジョブと同じく復号する）。

ジョブの中身（ワーカー、runPlanJob）

  • 添付ファイルを材料フォルダに写し、xlsx と PDF の本文を抽出する（plans/{planId}/attachments/derived/）。
  • RCS の MCP（search_bna_candidates、search_homba_candidates、get_homba_term、get_sabra_definition）だけを使い、Web 検索も文献ツールも使わずに 1 ターン実行する。指示は prompts/plan.md。
  • 返答は PLAN_RESULT_SCHEMA のオブジェクト（rows・unread・policy・proposals・notes）だけ。読めなければ 1 回だけ頼み直す。
  • 時間の予算：7 分（ワーカーの開始から）。xlsx / PDF を読む下書きか、入力の行が 20 を超える下書きは 25 分。超えたターンは打ち切られ、ジョブは失敗する（使った分の費用は記録される）。45 秒ごとにハートビートを送る。
  • 結果は result.json（cobrac.plan-result/1）に書き、利用量・推定費用とともにジョブを完了にする。

LLM への主な指示（prompts/plan.md）

項目指示
入力の行すべて行 ID で返し、ROI と TLF はそのまま写す。アンカー・依存・既存のプロジェクトを付ける
新しい行能力の一覧からは項目ごとに 1 行（行にできない項目は unread に場所と理由）。広い目標（「言語の BRA を一通り」）なら主な下位機能を 8〜15 行ほど。ほぼ同じ機能に分けない、ROI × TLF を繰り返さない
アンカー行の ROI と、その TLF で主な入力元・出力先になる領域の SABRA の単位を 3〜12 個（ROI を先頭に）。RCS で引き、ID を記憶から書かない。facet を付けない。同じ回路の行には同じアンカーを再利用
依存 dependsOnB の機能が A の機能を組み合わせた合成であるときだけ（例：復唱は音韻処理と発話に依存）。領域を共有するだけでは依存ではない（それはアンカーで分ける）。循環させない
優先度・既存所有者が先にと言った行は高く、任意の行は低く（既定 0）。同じ ROI × TLF の完成したプロジェクトがあれば、その ID
粒度方針計画のプロジェクトの回路をどの細かさで切るかを 1〜3 文で（後で 1 つの Canon に入れられるように）。所有者の Canon で同じ分野のものがあればその方針を採る
順序並べない・バッチに分けない（コードが計算する）

検証と適用

エージェントが書いた JSON は、そのままでは使いません（parsePlanResult）。入力を指すものだけを残し、ほかは除いて件数（dropped）に数えます。ROI・TLF・理由の長さ、ID や ROI × TLF の重複、アンカーの正規化（HOMBA:<id>、既知の BNA 領域の BNA:<l>-<r>。単一ラベルはペアに、facet は除く。既知の群の BNAG:<L2>。1 行 40 個まで）、依存は下書きの行だけ（自分自身は不可）、既存のプロジェクトは入力にある完成したものだけ。RCS が使えるときは、RCS が知らない HOMBA のアンカーと、SABRA が BNA で覆う領域の HOMBA のアンカーも除きます。ランナーは result.json を使う前に、スキーマ・種類・ジョブ ID と内容をもう一度検証します。

適用では、入力の行はアンカー（predicted）・依存・優先度（行に無いときだけ）・理由（無いときだけ）が更新され、ROI・TLF・出所は変わりません。新しい行は pending の行（出所 llm）になります。その後、行は自動で並べられ（6.6、ordering: "auto"）、計画は DRAFT に戻ります。読めなかった項目の一覧と除いた件数が画面に出ます。「下書きを取り消す」でジョブを止められます。
