第 6 部

CoBRAC オーケストレーター

CoBRAC オーケストレーターは、作りたい BRA（ROI × TLF）をミッションにまとめ、同時実行数の上限の範囲で、プロジェクトをバッチごとに自動で作る仕組みです。新しいミッションは自律実行で進みます。所有者が目標と費用の上限を渡すと、オーケストレーターが下書きを書いて確定し、完成したプロジェクトをミッションの Canon に取り込むところまで、人の代わりに判断しながら進めます。PR の承認や質問に所有者が自分で対応する進め方も選べます（6.9）。

オーケストレーターの AI が決めること方針、プロジェクト（ROI × TLF と理由）、アンカー、依存関係、優先度、再計画の提案を決めます。自律実行では、エージェントの質問への回答、PR の承認・変更の依頼・却下、要対応・要判断のプロジェクトの扱いも決めます。
プログラムが決めること実行順序（基準プロジェクトのバッチと本体のバッチ）、同時実行の枠、状態の遷移、リトライ、Canon への push と追従、費用の上限の判定を受け持ちます。AI の答えは検査してから反映します。
所有者が決めることミッションの目標・資料・費用の上限と、一時停止・再開・中止を決めます。人が対応するミッションでは、確定、提案の承認、質問への回答、要対応・要判断のプロジェクトの扱い、PR の承認も所有者が行います。

6.1 概要

BRA を 1 つ作るには数十分かかります（目安は 1.4）。ある領域の機能を一通りそろえるには、数十から百を超える ROI × TLF が必要です。これを 1 件ずつ手で起動すると、次のことを人が管理しなければなりません。

  • どれを先に作るか、何件を同時に動かすか
  • 同じ回路を作るプロジェクトが同時に走って、定義が食い違わないか
  • どのプロジェクトを Canon に取り込んだか

オーケストレーターは、これらをミッションにまとめて自動で進めます。BRA そのものの作り方（調査・HCD・FRG）は通常のプロジェクトと同じで（第 3 部）、オーケストレーターはその外側の進行管理だけを行います。

新しいミッションは自律実行で始まります。自律実行では、確定、エージェントの質問への回答、PR の承認、要対応・要判断のプロジェクトの扱い、再計画の提案の承認を、オーケストレーターが所有者の代わりに行います。止まるのは、費用の上限に達したときだけです（6.8）。新しいミッションのフォームで「PR の承認や衝突にご自身で対応する」をオンにすると人が対応するミッションになり、これらの判断を所有者が行います（6.9）。どちらの進め方でも、Canon に取り込むときの検査は人が承認するときと同じで、エラーの衝突のある PR は取り込まれません（5.2）。

だれが何をするか

主体種類オーケストレーターでの役割
所有者人ミッションを作り、名前・目標・資料・費用の上限を渡す。一時停止・再開・中止と、費用の上限の引き上げを決める。人が対応するミッションでは、下書きを整えて確定し、提案の承認・却下、質問への回答、要対応・要判断のプロジェクトの扱いも決める
Canon の所有者・共同編集者人人が対応するミッションでは、ミッションのプロジェクトが push した PR を審査して承認する（第 5 部）。プロジェクトが完了するのはこの承認のとき。自律実行のミッションの PR も、判断のジョブより先に人が決めればそれに従う
計画用のジョブ（下書き・再計画）LLM のジョブ目標・資料・プロジェクトを読み、RCS でアンカーを検索して、方針・プロジェクト・アンカー・依存・優先度・提案を JSON のデータとして返すだけ。順序は決めず、何も実行しない
プロジェクトのジョブ（回答・解決）LLM のジョブ自律実行のミッションだけ。プロジェクトのエージェントの質問に答え、要対応・要判断のプロジェクトの扱いを選ぶ。ツールを使わず、JSON で答えを返すだけ（6.8）
判断のジョブLLM のジョブ自律実行のミッションだけ。ミッションのすべての PR（基準プロジェクトを含む）について、所見とともに承認・変更の依頼・却下を返す（6.8）
プロジェクトの PR の AI レビューLLM のジョブ人が対応するミッションで、本体のプロジェクトの PR に所見を付ける。承認・却下はしない（5.8）
各プロジェクトの CoBRAC エージェントLLMプロジェクトの BRA を作る。中身は通常のプロジェクトと同じ（第 3 部）
APIプログラムミッションの作成・編集・確定、資料の CSV の読み取り、提案と所有者の判断の受け付け。プロジェクトの作成・リトライ・停止には、画面の API と同じ関数を使う
ミッションランナープログラム毎分、プロジェクトの状態を追い、バッチを進め、空いた枠でプロジェクトと各種のジョブを起動し、完成したプロジェクトを Canon に push する。実行順序を計算し、ジョブの結果を検査してから使う。自律実行のミッションでは、所有者の代わりに下書きを確定し、プロジェクトのジョブ・判断のジョブの結果と再計画の提案を反映する。人が対応するミッションでは、承認・却下・回答をしない
ワーカープログラム計画用のジョブでは、資料をコピーして本文を取り出し、LLM を 1 ターン動かし、返答の形を検査して結果のファイルに書く。プロジェクトでは通常どおりハーネスを進める
ディスパッチャー・janitorプログラム同時実行数の上限を守ってジョブを起動し、止まったジョブを失敗にする。計画用のジョブはどのプロジェクトにも属さない（6.11）

第 6 部では、ミッションランナーを単にランナーと表記します。

実装

コードではミッションを plan、そのテーブルを Plans、ID を planId、画面と API のパスを /plans と呼びます。ミッションランナーは Lambda の planRunner で、実行順序の計算は packages/shared/src/planOrder.ts にあります。自律実行はミッションの設定 settings.autonomous（費用の上限 maxCostUsd を持つ）で表します。

典拠：packages/shared/src/plan.ts・planOrder.ts、packages/api/src/lib/planRunner.ts・planOps.ts、packages/web/src/pages/PlansPage.tsx

6.2 全体の流れ

ミッションは図 6.1 の順に進みます。自律実行のミッションで所有者が操作するのは ① だけで、③ を飛ばし、④ の確定はランナーが行います。

段階自律実行のミッション人が対応するミッション
① ミッションを作る（6.3）名前・目標・資料と費用の上限を入れて「開始」を押す。下書きの依頼までが一度に済む「ミッションを作る」か「下書きを作成」を押す
② 下書き（6.4）計画用のジョブが方針・プロジェクト・アンカー・依存を書き、プログラムが実行順序を計算する（6.5）
③ プロジェクトとバッチを整える行わない所有者がプロジェクト・バッチ・設定・Canon を整える（6.9）
④ 確定下書きを適用した直後に、ランナーが所有者の代わりに確定する（6.8）所有者が「確定して開始」を押す（6.9）
⑤ 実行（6.6）ランナーが毎分、プロジェクトの状態を追い、空いた枠でプロジェクトを始める。自動の順序のミッションはフロー実行で、条件を満たしたプロジェクトから始める（6.5）。手動の順序のミッションはバッチごとに進む
Canon への取り込み（6.7）完成したプロジェクトを push し、判断のジョブが PR を決める（6.8）完成したプロジェクトを push し、人が PR を承認する

6.3 ミッションを作る

サイドバーの上の「＋ ミッション」（または「Canon」の画面の「新しいミッション」）を押すと、メイン画面が新しいミッションの作成画面（/plans/new）になります。新規プロジェクトの画面と同じく、ほかの一覧の上に重ねて開くことはしません。見た目も新規プロジェクトの画面（4.2）とそろえています。中央に見出し「新しいミッション」があり、その下に角の丸い入力のカードが 1 枚あります。カードの中は、左に小さなラベルを付けた「名前」と「目標」の欄が点線で区切られて並び、下の端にツールバーがあります。ツールバーは、左から「＋」（資料）、「自律実行」のチップ、右端の青い丸いボタンの順です。カードの下には、入力が足りないときの案内と「使い方」・(?) が出ます。

自律実行で始める

  1. 名前（200 字まで、必須）と目標（4000 字まで）を入れます。目標は「言語の BRA を一通りそろえたい」のような文で構いません。名前の欄で Enter を押すと目標の欄に移ります。
  2. ツールバーの「＋」を押し、「ファイルを追加」から資料のファイル（CSV・TSV・テキスト・xlsx・PDF、10 個まで）を加えるか、「リストを貼り付ける」でリストを貼り付けます。どちらも任意です。ファイルはカードの中に外せるチップで並び、「＋」に件数が付きます。貼り付けたリストは、カードの中の「リスト」の欄に入り、× で外せます。リストの 1 件が 1 プロジェクトになります。
  3. 「自律実行」のチップに出る費用の上限（「自律実行 ≤ $20」）を確認します。変えるときはチップを押し、開いたメニューの「費用の上限（USD）」に入れます。初期値は 20 で、1〜1000 の範囲で入れられます。上限に達すると新しいプロジェクトを始めず、動いているプロジェクトが終わったところでミッションは一時停止します（6.8）。
  4. 右端の「開始」を押します。ミッションが作られると同時に下書きが依頼され、ミッションの画面に移ります。あとは下書き（6.4）から確定、実行、Canon への取り込みまで、所有者の操作なしに進みます。

このフォームには Canon を選ぶ欄がありません。自律実行で作ったミッションは、ミッションの名前で新しい Canon を作る設定になり、その Canon は確定のときに作られます（6.7）。

名前が空のとき、目標・資料（ファイルか貼り付けたリスト）のどちらもないとき、費用の上限が範囲の外のときは、ボタンを押せません。目標も資料もないときは、カードの下に「目標を書くか、資料を追加してください」と出ます。

人が対応するミッションとして作る

「自律実行」のチップのメニューにあるチェックボックス「PR の承認や衝突にご自身で対応する」をオンにすると、人が対応するミッションを作れます。オンにすると、チップは「ご自身で進める」に変わって費用の上限の欄は使えなくなり、ツールバーの右端が次の 2 つのボタンに替わります（「ミッションを作る」が青い丸いボタンです）。

ボタン動き
「ミッションを作る」読み込んだプロジェクトでミッションを作る。下書きは依頼しない。目標だけで作ったミッションも、あとでミッションの画面の「下書きを作成」を押せる
「下書きを作成」ミッションを作ると同時に下書きを依頼する

どちらのボタンも、目標か資料が必要です。人が対応するミッションでは、下書きのあとで所有者がプロジェクトとバッチを整えて確定します（6.9）。下書きの間は、ミッションの画面の「進め方」で自律実行を入れたり切ったりできます（6.9）。

資料の読み込み

CSV・TSV・テキストの資料と貼り付けたリストは、ミッションを作るときに API がすぐにプロジェクトとして読みます。xlsx と PDF は保存するだけで、下書きのジョブが読みます。ミッションを作ったあとで下書きを依頼したときも、そのジョブが読みます。

プロジェクトとして読めなかったものは、ファイル名・何件目かと理由がミッションの画面に出ます。下書きの間なら、直してから「CSV を読み込む」で追加できます（6.9）。列の読み方と、取り込まないプロジェクトの条件は、次の「実装」に記載しています。

実装

一覧の読み取り規則（parsePlanRowsCsv）：

  • 見出しがあるときは列名で読みます。ROI は ROI / region / 脳領域、TLF は TLF / function / capability / 機能 / 能力、理由は rationale / note / 理由 / 備考、バッチは wave / batch / バッチ / 波、優先度は priority / 優先度 です。ほかの列は無視します。
  • 見出しがないときは、1 列なら TLF、2 列以上なら ROI・TLF・理由の順に読みます。CSV か TSV のどちらでもよく、BOM は除き、空白だけの部分は飛ばします。
  • 取り込まないプロジェクトは、何件目かと理由を表示します。次のどれかに当たるプロジェクトです。
    • ROI も TLF もない
    • 長すぎる（ROI と TLF は 300 字、理由は 1000 字まで）
    • 同じ ROI × TLF のプロジェクトがある（大文字・小文字と空白は無視し、ミッションにあるプロジェクトとも比べる）
    • バッチが 1〜99 でない、または優先度が整数でない
    • ミッションのプロジェクトが 200 を超える
  • CSV・TSV・テキストから読んだプロジェクトの出所は csv です。添付ファイルから読めなかったプロジェクトは、file 付きで一覧にします。
  • 貼り付けたリスト、添付した CSV・TSV・テキスト、あとから読み込む CSV（「CSV を読み込む」、POST /plans/{id}/rows/import）は、それぞれ 50 万文字まで（PLAN_LIMITS.maxCsvChars）です。

添付ファイル：

  • 添付できる種類は PLAN_ATTACHMENT_EXTS = csv・tsv・txt・xlsx・pdf で、ほかは 400 です。
  • 画面はファイルを POST /uploads で一時的な保存先に上げてから、POST /plans の attachments で渡します（10 個まで）。ファイルは plans/{planId}/attachments/files/NN-<名前> に移され、META.attachments に並びます。各項目は kind: "file"、id（f1・f2…）、名前、ミッションの接頭辞からの key、大きさ、種類を持ちます。
  • 名前と移動先は、移す前にすべて検査します。..・.・空のパスの区切りは不可で、list..v2.xlsx のような名前は通ります。不正なものが 1 つでもあれば何も移さず、400「添付ファイルの名前が不正です」を返します。

作成の要求：

  • 自律実行のときの「開始」は、POST /plans に draft: true と autonomous: { maxCostUsd } を付けて送ります。チェックボックスをオンにしたときは autonomous を送りません。API は、autonomous を付けた要求だけを自律実行のミッションにします（API の規則は 6.8）。
  • 目標・資料・プロジェクトのどれもない要求は 400 です。メッセージは、ミッションだけを作るときは「目標・資料・プロジェクトのどれかが必要です」、下書きも依頼するときは「下書きを作成するには目標か資料が必要です」です。

典拠：packages/web/src/pages/PlansPage.tsx（NewPlanForm）、packages/web/src/i18n/autonomous.ts・ja.ts、packages/api/src/lib/planOps.ts（createPlan）、packages/shared/src/plan.ts（parsePlanRowsCsv・PLAN_LIMITS）・planJob.ts（PLAN_ATTACHMENT_EXTS）

6.4 下書き

下書きを依頼すると、計画用のジョブ（1 回の Codex のタスク）が目標・資料・現在のプロジェクトを読み、方針・プロジェクト・アンカー・依存関係・優先度を書きます。モデルはデータを出すだけで、実行順序はプログラムが計算します（6.5）。これにより順序が再現でき、バッチごとに安く計算し直せます。方針はオーケストレーターが書くもので、所有者は編集できません（本節「方針」）。

自律実行のミッションでは、下書きを適用すると、まもなくランナーが確定して実行が始まります。画面の帯には「下書きができました。1 分ほどで自動的に確定して実行を始めます。」と出ます。下書きのジョブが失敗したときは 1 回だけ自動で依頼し直し、確定に失敗したときは理由を画面に出します（6.8）。人が対応するミッションでは、下書きのあとで所有者がプロジェクトとバッチを整えて確定します（6.9）。

依頼からジョブの開始まで

  1. 依頼：作成画面の「開始」「下書きを作成」か、ミッションの画面の「下書きを作成」で依頼します。目標・添付・プロジェクトのどれかが必要です。API は、所有者がジョブを実行できることを確認します（キーがなければ 400、選んだモデルを使えなければ 403）。そのうえでミッションのリースを取り、ミッションを DRAFT から DRAFTING（下書き作成中、6.12）にします。
    • ミッションの作成と同時に依頼するときは、ミッションとプロジェクトをいったん DRAFT で書いてから切り替えます。ランナーが、プロジェクトの一部しかない下書き中のミッションを見ることはありません。
    • 依頼そのものはジョブを積まず、ランナーを 1 回すぐに動かすだけです。
    • 下書き中はプロジェクトを編集できません。画面の帯には「下書きができるまでプロジェクトは編集できません。ふつうは数分で終わります。」と、ジョブの状態（ジョブの空きを待っています／開始を待っています／実行中）が出ます。経過時間は出しません。
  2. 枠を待つ：ランナーは、全体と所有者の同時実行数に空きがあり、所有者がまだジョブを実行できるときだけ、入力を書いてジョブを積みます。数えるのは待機・実行・仕上げ中のジョブで、プロジェクトのジョブと同じ枠を使います。ジョブはオーケストレーターのモデルで、推論の強さ（reasoning effort）は medium で動きます。
    • 枠がなければ待ったままにし、枠より先には積みません。
    • キーがない、アカウントが無効、選んだモデルを使えなくなった、のどれかに当たるときは、下書きを失敗にします。理由を画面の言語で表示し、ミッションを DRAFT に戻します。
  3. 入力：ジョブには次のものを渡します。キーなどの秘密は入れません。API とランナーはキーを復号せず、ワーカーが通常のジョブと同じ方法でキーを解決して復号します。
    • 目標、方針、ミッションのプロジェクト（優先度・依存・「作り直す」の印を含めてそのまま）
    • 所有者の削除されていないプロジェクト（新しい順に最大 300 件。成果物があって完了したものには、完成の印を付ける）
    • 所有者の Canon とその粒度方針（最大 50 件）、実効の同時実行数
    • API が読まなかった添付ファイル（下書きだけ。再計画には添付を渡さない）

ジョブの中身

  • ワーカーは、ジョブがまだ待機中のときだけ引き受けます。キーを解決・復号し（なければジョブを失敗にする）、待機中であることを条件にジョブを実行中にします。その間に取り消された下書きは、取り消されたままです。
  • 添付ファイルを材料のフォルダにコピーし、xlsx と PDF の本文を、参考資料（4.2）と同じ方法で取り出します。
  • RCS の MCP のツールだけを使い、Web 検索も文献ツールも使わずに、LLM を 1 ターン動かします。RCS が設定されていない環境では、アンカーを空にしてその旨をメモに書くよう指示します。
  • 依頼文は、指示書 prompts/plan.md（付録 B）、仕事の種類（下書きか再計画か）、返答の言語、添付ファイルの索引、入力の JSON からなります。
  • 返答は、決まった形の JSON のオブジェクト（プロジェクト・読めなかった項目・方針・提案・メモ・質問。すべて必須）だけです。読めなければ 1 回だけ頼み直します。
時間の予算内容
通常7 分（ワーカーの開始から）。積む時間、Fargate の起動、結果を反映するランナーの次の実行（最大 1 分後）を含めて、依頼から約 10 分で下書きができる
長い下書き25 分。xlsx・PDF を読む下書きか、入力のプロジェクトが 20 を超える下書き。項目ごとに 1 件を書くため
超えたときターンを打ち切り、ジョブは「The plan job took longer than its time budget」で失敗する

打ち切ったジョブや取り消したジョブも、使った分の使用量を記録します。ワーカーは 45 秒ごとにハートビートを送ります。結果は入力の隣の結果のファイルに書き、使用量・推定費用とともにジョブを完了にします。失敗したときは、エラーと使用量を記録してジョブを失敗にします。

下書きの前の質問

下書きのジョブは、プロジェクトを書く前に所有者へ0〜3 個の質問を返せます。目標と資料だけでは、ミッションの範囲（どの機能・領域を入れるか、何件ほどか）・粒度・先に作るプロジェクトが決まらないときに限ります。回答を受けて、もう 1 回だけ追加の質問を返せます。1 回あたり 3 個まで、合わせて 2 回までです。

  1. 質問の可否：ランナーは下書きのジョブの入力に、質問してよいかどうかと、これまでの質問と回答を入れます。質問してよいのは、これまでの回数が 2 回未満で、所有者が質問を飛ばしていないときです。
  2. 質問を返す：LLM は、決めかねることがあるときだけ、検索や資料の精読をせずにすぐ質問を返します。各質問は 1 文で、提案する答えを 2〜4 個付けられます。調べれば分かること、確認のためだけのこと、すでに答えのあることは聞きません。質問しないときは、回答に従って下書きを書きます。
  3. 検査：質問してよい下書きのジョブの質問だけを残します。空の質問は除き、4 個目以降と長すぎる部分は切ります。質問が 1 つでも残れば、その返答のプロジェクトは使いません。質問してはいけないジョブが返した質問は捨てて、除いた件数に数えます。
  4. 回答を待つ：ミッションは下書き作成中のまま、下書きは「回答待ち」になり、質問の回を記録します。この間ランナーは何も積みません。答えられるのは所有者だけなので、自律実行のミッションでも待ちます。ミッションの一覧の「あなたの番」には「オーケストレーターの質問に回答」が出ます。
  5. 回答：画面には質問ごとに、提案の答えのボタンと入力欄が出ます。ボタンを押すと答えが欄に入り、書き換えることもできます。空欄の質問はオーケストレーターの判断に任せます。すべて空欄では送れません。「おまかせで進める」は質問を飛ばし、その下書きではそれ以上質問しません。回答を記録すると下書きは待機中に戻り、ランナーが次の下書きのジョブを積みます。

答えた質問は、ミッションの画面の「作るもの」に「質問と回答 n」として折りたたんで残ります。下書きを新しく依頼すると、質問は最初からやり直します。回答を待つ間も「下書きを取り消す」で下書きに戻せます。

LLM への主な指示

項目指示
入力のプロジェクトすべて rowId で返し、ROI と TLF はそのままコピーする。アンカー・依存・既存のプロジェクトを付ける。理由がないプロジェクトには書き、あるプロジェクトは空で返す（プロジェクトの理由を残す）
新しいプロジェクト資料からは項目ごとに 1 件。機能だけの項目には文献で最も結びつく ROI を補い、領域だけの項目には TLF を補う。プロジェクトにできない項目は、出所・場所・理由を付けて「読めなかった項目」に出す。広い目標（「言語の BRA を一通り」）なら、主な下位機能を 8〜15 件ほど。ほぼ同じ機能に分けず、ROI × TLF を繰り返さない。出所（目標、ファイル名と場所、入力のプロジェクト）を書く
アンカープロジェクトの ROI と、その TLF で主な入力元・出力先になる領域の SABRA の単位を 3〜12 個（ROI を先頭に）。RCS で検索し、ID を記憶から書かない。facet を付けない。同じ回路のプロジェクトには同じアンカーを再利用する
依存B の機能が A の機能を組み合わせた合成であるときだけ（例：復唱は音韻処理と発話に依存）。領域を共有するだけでは依存ではない（それはアンカーで分ける）。循環させない
優先度・既存所有者が先にと言ったプロジェクトは高く、任意のプロジェクトは低く（既定 0、−1000〜1000）。同じ ROI × TLF の完成したプロジェクトがあれば、その ID を付ける（「作り直す」のプロジェクトには付けない）
方針プロジェクトより先に書き、プロジェクトはそれに沿って書く（範囲がプロジェクトの要否を、優先がプロジェクトの優先度を決める）。各項目は 1〜2 文で、目標・資料が何も言わず妥当な既定もなければ空にする。粒度は、所有者の Canon に同じ分野のものがあればその粒度方針を採る。入力の方針があれば、各項目を明らかに合わないとき以外は保つ
長い一覧全体で 30 件ほどを超えるときは、1 件あたりのアンカーを 3〜6 個にし、同じ領域は 1 回だけ検索して再利用し、理由とメモを短くする。それでも各項目にプロジェクトか「読めなかった項目」を必ず付ける
順序並べない・バッチに分けない（プログラムが計算する）
質問質問してよいときだけ、範囲・粒度・先に作るプロジェクトが決まらない場合に 0〜3 個。ふつうは 0 個。質問するときは検索せずにすぐ返し、ほかの欄は空にする
その他文章にモデル名を書かない。入力・添付・RCS だけを使い、Web を検索しない。時間の予算が厳しいので、検索を増やすより、根拠のあるアンカーを少なく付ける

方針

方針は、オーケストレーターがそのミッションを進めるための取り決めです。次の 5 項目からなり、計画用のジョブが目標・資料・下書きの前の質問への回答から書きます。所有者は編集できず、変えたいときは目標や回答で伝えます。

項目内容例
範囲ミッションに含めるものと含めないもの（機能・領域・動物種・文献の時期）言語の理解と産出。読み書きは含めない
粒度回路をどの細かさで切るか。あとで 1 つの Canon に入れられるようにそろえる新皮質は BNA の領域、皮質下は DHBA の核
根拠どの証拠に基づいてプロジェクトを作るかヒトと霊長類の神経路追跡を優先し、ゲッ歯類は補助のみ
優先先に仕上げるプロジェクトと、後回しや見送りにしてよいプロジェクト音声知覚と発話を先に
判断失敗が続くプロジェクトや要判断のプロジェクトで、網羅と費用をどう比べるか同じ失敗を 2 回したプロジェクトはやめる
  • 回答との対応：下書きの前の質問への回答に拠った項目は、その旨（fromAnswers）を持ち、画面に印が出ます。
  • 使われる場面：下書きと再計画（全項目）、自律実行での回答と判断（全項目。判断の理由には拠った項目を書く。6.8）、プロジェクトのエージェント（範囲・粒度・根拠。6.6「作られたプロジェクト」）、確定時に作る新しい Canon（粒度だけを Canon の粒度方針にする。6.7）。
  • 変更：再計画は、完了したプロジェクトが方針と合わないことを示したときに、方針全体を置き換える提案を出せます。承認は要らず、すぐに反映します（6.6）。
  • 画面：ミッションの画面に「方針」のカードが出ます。空でない項目を 1 つずつ、見出しと本文で並べ、長い項目は「すべて表示」で開きます。
  • 上限：各項目 600 字。

結果の検査

LLM が書いた JSON は、そのままでは使いません。入力を指すものだけを残し、ほかは除いて、除いた件数を数えます。

  • 下書きのプロジェクト：入力のプロジェクトは rowId で、新しいプロジェクトはモデルが付けた ID で受け取ります。次の点を検査します。
    • ROI・TLF・理由の長さ、ID や ROI × TLF の重複
    • アンカーの正規化：HOMBA の ID、既知の BNA の領域のペア、既知の BNA の群の形にそろえる。単一のラベルはペアにし、/side:left などの facet は除く。1 件あたり 40 個まで
    • 依存は下書きのプロジェクトどうしだけ（自分自身は不可）。優先度は範囲内の整数（でなければなし）
    • 既存のプロジェクトは、入力にある完成したものだけ
    • プロジェクトは 200 まで、読めなかった項目は 200 件まで
  • 再計画の提案（30 件まで）：プロジェクトの追加はミッションにまだない ROI × TLF（依存は入力のプロジェクトだけ）、プロジェクトの削除は始まっていないプロジェクト（開始待ちで、まだ作られておらず、既存でもないもの）、方針の提案は現在の方針と違う文（1 件まで）です。下書きの結果に入った提案と、再計画の結果に入ったプロジェクトは捨てます。
  • RCS との照合：RCS が設定されているとき、ワーカーはプロジェクトと追加の提案から、次の HOMBA のアンカーを除いて件数に数えます。RCS が知らないものと、SABRA が BNA で覆う領域のものです。後者を除くのは、完成したプロジェクトがその領域を BNA の領域で表すため、HOMBA の ID では一致しないからです。RCS で検索できなかったアンカーは残します。
  • ランナーの再検査：ランナーは結果のファイルを使う前に、スキーマ・種類・ジョブ ID が一致することを確認し、内容をジョブの入力に対してもう一度同じ検査に通します。結果のファイルをそのまま信用することはありません。

結果の適用

ランナーはジョブを追い、完了したら、ミッションのリースの中で結果を適用します。

  • 入力のプロジェクトへの結果：そのプロジェクトの値を次のように更新します。ROI・TLF・出所は変わりません。
    • アンカー（出所は「予想」）と依存（rowId に対応させる）を書き込む
    • 優先度は、プロジェクトに値がないときだけ書く。ジョブは所有者の優先度を見て返すので、CSV の優先度の列の値は上書きしない
    • 理由は、プロジェクトに理由がなかったときだけ書く
  • 新しいプロジェクト：開始待ちのプロジェクト（出所 llm）になります。ただし同じ ROI × TLF のプロジェクトがすでにあれば、そのプロジェクトを更新します。消えたプロジェクトを指す結果や、同じプロジェクトへの 2 つ目の結果は捨てます。
  • 既存のプロジェクト：結果が示したもの、なければ所有者のプロジェクトと照合して見つけたものを付けます（照合の規則は 6.9）。「作り直す」のプロジェクトには付けません。結果が触れないプロジェクトは、そのまま残します。
  • 順序と方針：プロジェクトを自動で並べ（6.5）、順序の種類を「自動」にします。結果の方針に空でない項目があれば方針を置き換え、件数を数え直します。ミッションは 200 件までで、超えた結果のプロジェクトは除いた件数に数えます。
  • 完了：ミッションを DRAFT に戻し、下書きを完了にします。画面には、読めなかった項目（ファイル名・場所・理由）と、使わなかった部分の件数が出ます。

失敗と取り消し

  • ジョブが失敗した・取り消された・見つからない、または結果のファイルを読めないときは、下書きを失敗か取り消しにし、エラーとともにミッションを DRAFT に戻します。もう一度依頼すると、現在のプロジェクトで新しいジョブが動きます。
  • 「下書きを取り消す」は、下書き作成中のときだけ押せます。待機中か実行中のジョブを止め（Fargate のタスクも止める）、ミッションを DRAFT に戻します。

実装

  • API：依頼は POST /plans/{id}/draft { locale? }、または作成時の draft: true。取り消しは POST /plans/{id}/draft/cancel（DRAFTING のときだけ）。質問への回答は POST /plans/{id}/draft/answers { answers?: string[], skip?: boolean }（下書きが asking のときだけ。でなければ 409、すべて空欄なら 400）。
  • 下書きの状態：依頼で waiting、積むと queued、ワーカーが動くと running、質問を返すと asking（回答で waiting に戻る）、適用で done（unread の一覧と dropped の数を持つ）、または failed / cancelled。失敗の理由のコードは no_key / owner_disabled / model_not_allowed。
  • イベント：draft_requested・draft_applied・draft_failed・draft_cancelled・draft_asked・draft_answered。
  • 質問：上限は PLAN_ASK_LIMITS（1 回 3 個、2 回まで、提案の答え 4 個まで）。質問の回は下書きの状態の qa（PlanDraftRound：questions・answers・askedAt・answeredAt・skipped）。ジョブの入力は ask（planMayAsk）と qa（planQaInput。答えた回だけ、空欄は ""）。
  • ジョブ：type: "plan"、planJobKind: "draft"、projectId にはミッション ID を入れる。入力は plans/{planId}/jobs/{jobId}/input.json、結果はその隣の result.json。ワーカーのキーの解決は planRunKey。
  • 入力：未読の添付は { id, name, key } で渡す。完成したプロジェクトの印は completed。
  • ワーカー（runPlanJob）：QUEUED を条件に RUNNING にする。取り出した本文は plans/{planId}/attachments/derived/ に残す。RCS のツールは search_bna_candidates・search_homba_candidates・get_homba_term・get_sabra_definition・map_coordinates（RCS_TOOLS。HCD と共通）。依頼文は planJobPrompt、頼み直しは PLAN_RETRY_PROMPT。
  • 返答の形：PLAN_RESULT_SCHEMA（rows・unread・policy・proposals・notes・questions）。結果のファイルは PlanJobResult（スキーマ cobrac.plan-result/1、種類、ミッションとジョブの ID、モデル、言語、時刻、検査したプロジェクト・unread・方針・提案・notes・dropped）。新しいプロジェクトの出所 source は、目標なら goal、入力のプロジェクトなら input。
  • 時間の予算：PLAN_JOB_TIME_BUDGET_MS（7 分）、PLAN_JOB_LONG_TIME_BUDGET_MS（25 分）、件数のしきい値 PLAN_JOB_SHORT_ROWS（20）。打ち切ったターンの使用量はセッションのファイルから測り、SIGTERM のときはそこまでの使用量を記録する。
  • 検査：parsePlanResult。入力のプロジェクトは ref、新しいプロジェクトは id で受け取る。アンカーの正規化は normalizePlanAnchor（HOMBA:<id>、BNA:<l>-<r>、BNAG:<L2>）。上限は MAX_ROW_ANCHORS（40）・MAX_PLAN_UNREAD（200）・MAX_PLAN_PROPOSALS（30）。提案の種類は add / remove / policy。ランナーの再検査は readPlanResult。
  • 適用：アンカーの出所は anchorsSource: "predicted"。既存のプロジェクトは結果の existingProjectId、なければ matchExistingProject。並べ方は orderDraft で、ordering: "auto" にする。
