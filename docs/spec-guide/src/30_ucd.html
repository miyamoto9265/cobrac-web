第 3 部

UC Descriptor と facet

CoBRAC は、HCD のすべての回路を SABRA の単位（アンカー）に結びつけ、それより細かい集団の性質を facet として足して名前を付けます。アンカーと facet を決まった順に並べたものが UC Descriptor（機械のキー）で、そこから人が読む別名 Circuit ID を機械的に作ります。これは CoBRAC が新しく導入する概念で、WBAI の組織規則としてはまだ採択されていない提案です（3.13）。

アンカー回路が属する SABRA の単位。HOMBA:12261（VTA）、BNA:57-58（A4ul）など。必ず 1 つ以上
facetSABRA より細かい性質。軸:値 の形で、9 本の軸（part・lay・cell・nt・mol・in・out・resp・side）を決まった順に
UC Descriptor / Circuit IDHOMBA:10341/mol:DRD1+ がキー、NACs(DRD1+) が別名。同じ集団はどの BRA でも同じ

3.1 なぜ名前の規則が必要か

v0.7.0 より前の CoBRAC では、エージェントがプロジェクトごとに自由に Circuit ID を付けていました。旧サンプルには PC、GrC、MF_VN、CA3-Pyr、L-DLPFC、FG-math といった名前があり、検査は「Circuit ID に空白が無いこと」だけでした。この方法には 2 つの問題がありました。

① 同じ集団が、別の名前になる
側坐核 shell の DRD1 陽性の集団を、あるプロジェクトは NAc_shell_D1、別のプロジェクトは NACs-DRD1 と書きえます。逆に、同じ文字列が別の集団を指すこともありえます。プロジェクトをまたいで回路を集計したり、定義をそろえたりできません。
② アトラスとの対応が、名前から分からない
名前がどの領域を指すかはエージェントの説明文にしか無く、SABRA のどの単位に当たるかを機械的に確かめられません。とくに層・細胞種・投射先で切り出したサブ集団は、書き方の揺れが大きくなります。

WBAI の組織側にも、SABRA の単位より細かい回路の書き方の規則はまだありません（ISS-001 は未決）。データ準備マニュアルやオントロジーの実例も CA1_distal、Cx.L2_3PV、M1C.L5PT、BL_fear とまちまちです。一方で、層や細胞種で分けた UC が必要なこと自体は、組織の議論でも認められています。UC Descriptor と facet は、この空白を埋めるための規則です。

例えば、側坐核 shell の DRD1 陽性の集団は、どのプロジェクトでも Descriptor が HOMBA:10341/mol:DRD1+、Circuit ID が NACs(DRD1+) になります。名前が同じなら同じ集団だと分かるので、プロジェクトをまたいで回路を照合でき、Canon（第 4 部）もこの Descriptor をキーにしています。

版入ったもの
v0.7.0命名規則の導入（アンカー・facet・UC Descriptor・Descriptor から作る Circuit ID）。それまでは Circuit ID に空白が無いことだけを検査していた
v0.17.0左右を 9 本目の facet side にし、アンカーを常に左右のペアにした。Circuit ID の文字を WBAI の仮仕様の文字集合（と括弧）にそろえ、括弧の中の区切りを . にした。検査のエラーコードを WBAI の Error code List (Master) に合わせ、Master にコードの無い検査に cobrac: のローカルコードを付けた（3.8、3.10）

3.2 設計の考え方（5 つの原則）

原則内容と理由
アンカーは常に SABRA の単位SABRA より細かいものは、すべて facet に回す。こうすると、どの回路も SABRA のどこかに必ず結びつく。
UC に採番の ID を付けないSABRA が独自の ID を持たないのと同じ考え方で、既存のアトラス ID と明示的な属性だけから名前を組み立てる。正規化した Descriptor そのものがプロジェクト横断の一意なキーになり、中央で番号を払い出すレジストリは要らない。
同じ集団は、どのプロジェクトでも同じ名前プロジェクトによって変わるのは回路の役割（ROI の内外、Interface、Output Semantics、Uniform か Collection か）だけ。プロジェクト名の接頭辞も付けない。
種は名前に入れないBRA はヒトの回路（とヒトへの外挿）を扱う。動物の知見に基づく場合は、接続のエビデンスの Taxon に書く。
SABRA の単位そのものの UC が通常facet は、単位より細かい集団が HCD に必要なときだけ足す。回路を説明するために facet を足すことはしない（符号化する内容は Output Semantics に書く）。

3.3 アンカー：SABRA の単位

アンカーの形

形意味例
HOMBA:<id>SABRA の DHBA 側の単位。DHBA 名を持つ HOMBA の項に限るHOMBA:12261（VTA）
BNA:<左>-<右>BNA の新皮質の 1 領域。常に左右のペア（奇数, 奇数+1）BNA:57-58（A4ul）
BNAG:<L2 略称>BNA の新皮質の L2 の群（回など）全体。RCS の分布が広く、1 つの領域に決まらないときBNAG:MFG
A&B複数の SABRA 単位にまたがる回路HOMBA:…&HOMBA:…
  • SABRA: や DHBA: という接頭辞は作りません（SABRA は独自の ID を持たないため）。
  • BNA の担当範囲（新皮質）の中の細分は、BNA のアンカーの下に part:HOMBA:… として書きます。逆向き（DHBA のアンカーの下に BNA を part として置くこと）はしません。
  • 脊髄のように経路上に DHBA 名を持つ項が無い領域は、SABRA の単位になりません。アンカーには RCS が返す最も近い DHBA の祖先を使い、細かい部位は part に書きます。投射先・入力元（out / in）の値としては、そのまま書けます。

RCS でアンカーを決める手順

エージェントは、回路の記述を「領域を表す語」と「それ以外の語」に分け、領域の語だけで RCS を引きます。遺伝子や細胞種などの残りの語は、最初から facet になります。

RCS の結果アンカーfacet
DHBA 側で完全一致（relation '='、dhba_exact: true）その HOMBA: の項領域以外の語
DHBA 側で、クエリの方が細かい（dhba_exact: false か relation <）RCS が返す DHBA 名を持つ祖先（sabra.dhba_homba_id）part:<一致した HOMBA の項> と領域以外の語
BNA 側（atlas: BNA、新皮質）search_bna_candidates の候補のうち sabra.atlas: BNA の領域のペア。1 領域がはっきり優勢でなければ BNAG:<L2>HOMBA の項が BNA の領域より細かければ part:<HOMBA の項>
クエリの方が広い（relation >）A&B、または共通の SABRA の祖先—
候補が無い推測しない。ユーザーに質問する

BNA の領域を 1 つに決める目安は、上位の候補の p_raw が 0.5 以上で k_papers が 2 以上であることです（prompts/phases/HCD.md）。

BNA と DHBA の境界（v0.24.0）

2026-10-04 に SABRA の仕様が変わり、BNA を使うのは新皮質だけになりました。それまで BNA で表していた皮質下（扁桃体 Amyg、海馬 Hipp、大脳基底核 BG、視床 Tha の 36 ラベル）と不等皮質（海馬体・嗅内皮質など）は、現在は DHBA の項で表します。

領域以前現在の SABRA
新皮質（BNA の皮質ラベル 1–210 のうち 206 ラベル）BNABNA（変更なし）
扁桃体（mAmyg・lAmyg）BNADHBA（AMY と CEN・BLN・La などの核）
海馬（rHipp・cHipp）BNADHBA（HiF と CA1・DG・S など）。海馬全体は HOMBA:12170
大脳基底核（vCa・dCa・GP・NAC・vmPu・dlPu）BNADHBA（Ca・GP・NAC・NACs・Pu など）
視床（BNA の 8 亜領域）BNADHBA（DTH と MD・VPL・Pul・LG などの核）
嗅内皮質（A28/34）と側頭無顆粒島皮質（TI）BNADHBA（EC・TI。HOMBA では新皮質の外にある）
嗅皮質・梨状皮質などの不等皮質BNA（ラベルは無い）DHBA
  • 境界の正本は RCS の rcs/sabra.py です。RCS の get_homba_term と search_homba_candidates は新しい境界で sabra.atlas を返し、search_bna_candidates は新皮質でない領域に sabra.atlas: DHBA・sabra_unit: false を付けます。CoBRAC 側の対応表（新皮質でない BNA の領域 → それを含む DHBA の項）は BNA_DHBA_COUNTERPARTS で、RCS と同じ表です。
  • 新しく作るプロジェクトでは、新皮質でない BNA の領域（ラベル 211–246、BNA:115-116、BNA:117-118）と BNAG:Amyg・BNAG:Hipp・BNAG:BG・BNAG:Tha を、アンカーにも in / out などの値にも使えません。ワーカーの検査は、その領域を含む DHBA の項を示して直させます（例：BNA:223-224 なら HOMBA:10339 NAC、BNAG:BG なら Ca・Pu・NAC・GP）。
  • 海馬全体は HOMBA:12170（HiF）で表します。文献が特定の領域（CA1、CA3、DG、海馬台など）を挙げていれば、HiF ではなくその DHBA の項を使います。
  • BNAG:PhG（海馬傍回）は、新皮質の A35/36r・A35/36c・TL・TH と、DHBA になった A28/34・TI を含むので、新しいプロジェクトでは回全体のアンカーにできません。検査は亜領域（BNA:109-110、BNA:111-112、BNA:113-114、BNA:119-120）か DHBA の EC（HOMBA:10317）・TI（HOMBA:10330）を使うよう求めます。
  • 既存のプロジェクトは変えません。0.24.0 より前に作ったプロジェクトは、プロジェクトの sabraBoundary が無いので以前の境界のまま検査され、BNA のアンカーのまま読み込み・検査・出力でき、フォローアップでも書き直しを求めません。新しいプロジェクトは作成時に sabraBoundary: "neocortex" を持ちます。複製したプロジェクトは元の設定を引き継ぎます。版の manifest には、検査が従った境界（neocortex / legacy）と RCS が返した境界の版が残ります（第 5 部）。
  • Canon も書き換えません。保存済みの Canon の回路はそのままで、Canon に従うプロジェクトは Canon にある Descriptor（以前の境界で作られた BNA:223-224 など）をそのまま使えます（検査の対象から外す）。

3.4 facet：9 本の軸

facet は 軸:値[,値…] の形で、次の順に / でつなぎます。各軸は 1 回までで、空の軸は書きません。

順軸内容例
1partアンカーより細かい部位。より細かい HOMBA の項を優先し、無ければ短い語part:HOMBA:10341
2lay層lay:L5
3cell形態・細胞クラスcell:pyr、cell:purkinje、cell:pt
4nt伝達物質（Glu GABA Gly ACh DA NE 5HT His pep）nt:DA
5mol分子マーカーと極性（+ - ~hi ~lo）mol:DRD1+
6in入力元で定義される集団in:HOMBA:12261
7out投射先で定義される集団out:HOMBA:10339
8resp反応性・機能的なチューニングresp:rpe
9side左右（left / right の 1 値。付けなければ両側、または区別しない）side:left
facet を使うときの決まり
  • 軸は集団を選び出す性質にだけ使う。in / out は、投射で集団が定義される場合だけ（単に投射するだけなら、接続で表す）。
  • mol の値には必ず極性を付ける。遺伝子記号は公式のもの（ヒトなら HGNC）を使い、1 つの Descriptor の中で表記をそろえる。
  • part・in・out の値は SABRA の単位でなくてよい（例：脊髄 HOMBA:AA30565 は DHBA 名を持たないが、投射先には書ける）。
  • side は v0.17.0 で加わった軸で、常に最後に置く（3.8）。

コード：UC_FACET_AXES = ["part", "lay", "cell", "nt", "mol", "in", "out", "resp", "side"]（packages/shared/src/ucNaming.ts）

3.5 UC Descriptor：機械のキー

UC Descriptor = <アンカー>{&<アンカー>}{/<軸>:<値>[,<値>]}
例: HOMBA:10341/mol:DRD1+
    BNA:57-58/lay:L5/side:left
  • 置き場所：uc.json の各回路の descriptor に書きます。Circuits.csv と xlsx の Circuits シートの最後の列（UC Descriptor）、HCD グラフのノードの詳細にも出ます。
  • 比べるときは正規化します（normalizeUcDescriptor）：旧い形を現在の形に直し（3.8）、mol の値をアルファベット順に並べ、全体を小文字にします。DRD1+ と Drd1+ は同じものとして扱います。表示には大文字小文字を保った元の形を使います。
  • 一意性：1 つの HCD の中で、2 つの回路（UC と Collection を合わせて）が同じ正規化 Descriptor を持つことはできません。
  • Uniform かどうかは持たない：Descriptor は「どの集団か」だけを表し、その HCD で UC（葉）なのか Collection（分解される）なのかは含みません（3.9）。

3.6 Circuit ID：人が読む別名

Circuit ID = <アンカーの略称> [ "(" <項目> { "." <項目> } ")" ]
<項目>     = <語> | ("out-" | "in-") <相手の略称> | "left" | "right"
文字       = A-Z a-z 0-9 . _ ~ -（2026-08-06 の仮仕様）と / +（2026-08-19 に合意）、項目を囲む ( )

前半（アンカーの略称）

  • アンカーの SABRA の正式略称を、大文字小文字も含めてそのまま使います。BNA 側は BNA の新皮質の領域の略称（A4ul、A44d、A9/46d）、DHBA 側は DHBA の略称（弓状核は HOMBA の ArH ではなく DHBA の Arc）です。
  • 変換は空白を _ にすることだけです（BNA の TE1.0 and TE1.2 → TE1.0_and_TE1.2 の 1 件）。/ と + は 2026-08-19 の合意で許容文字に入ったので、A9/46d、A1/2/3ll、V5/MT+ はそのまま使います。
  • 複数の SABRA 単位にまたがる回路（BNAG:、A&B）は、暫定的に共通する BNA の L2 の略称（例 MFG）を、無ければ最初のアンカーの略称を使います。
  • 独自・慣用の略称（NAc、LC）や SABRA の単位でない細分の略称（片葉の CH10 など）は前半に置かず、括弧の中の part の項目にします。

括弧の中（項目）

  • Descriptor の facet の値 1 つにつき 1 項目を、facet の順に . で区切って並べます。facet が無ければ括弧も書きません（VTA、NAC）。
  • part は細分の部位を表す短い英単語（floc、rostral）か広く通用する略称、lay・cell・nt・mol・resp は Descriptor の語をそのまま（L5、pyr、DA、DRD1+、rpe）、out / in は out-<相手の略称> / in-<相手の略称>（out-NAC、in-VTA）です。相手が SABRA の単位でなければ HOMBA の略称を使います（脊髄は out-Sp）。
  • 項目の中の . は区切りと紛れるので _ にします。語の中の - はかまいません（遺伝子 HLA-A）。語の末尾の + / - は極性です。

使える文字と区切り

記号扱い理由
A-Z a-z 0-9 . _ ~ -使えるWBAI の 2026-08-06 の仮仕様の文字（RFC 3986 の unreserved と同じ）
/ +使える2026-08-19 に合意。BNA の正式略称（A9/46d、V5/MT+）をそのまま使うため
( )項目を囲むときだけRFC 3986 の sub-delims で、URL のパスにそのまま置ける。主要な OS のファイル名に使え、bash のブレース展開も起きない。入れ子にしない
.（括弧の中）項目の区切り許容文字に入っていて、組織の BNA.A8m.L3 型の書き方ともそろう
, : @使わない許容文字の外。, は CSV のクォートが要り、テンプレートの Graph Generator（draw.io 用 CSV）で ID が分かれる
{} [] <> ; | 空白使わないブレース展開、[U.X] 参照との紛れ、HTML との衝突、Subnodes の区切り、Markdown の表の破壊
  • Circuit ID の一意性は大文字小文字を区別して判定します。BNA と DHBA の正式略称には、大文字小文字だけが違う組が 45 組あるためです（例 CB と cb）。Descriptor の比較は小文字にしてから行います。
  • FRG からは U.<Circuit ID>（例 U.NACs(DRD1+)、本文中では [U.A4ul(L5.pt.left)]）で参照します。U. の接頭辞は先頭の U. を外すだけで読むので、括弧の中の . と衝突しません。Interface や Subnodes の ID の分割も、括弧の外の区切りだけで判定します。
  • シェルに渡すときは引用符で囲みます（'NACs(DRD1+)'）。Markdown のリンクの URL に ) を入れるときは %29 にします。正規表現に埋め込むときは ( ) . + / をエスケープします。
  • テンプレート（Template-v2-2 と v2-3）の数式を LibreOffice で再計算して確かめたところ、( ) を含む ID で壊れる箇所はありませんでした。ID は EXACT・VLOOKUP・SEARCH・SPLIT で文字列として扱われ、括弧を関数として解釈する箇所はありません。一方、以前の , 区切りの ID（Amyg(BL,out:CEN)）は Graph Generator の CSV で 2 つに分かれていました。v0.17.0 で . にそろえたので、この問題は解消しています。

3.8 左右の扱い（side）と旧い形の読み替え

0.16 までは左右をアンカーで表していました（片側の BNA 領域は単一のラベル BNA:57 が左の A4ul、DHBA 側や BNA の群は @L / @R で BNAG:FuG@L、Circuit ID も A4ul@L）。WBAI では、2026-07-14 に Circuit 名から _L / _R を外すことが決まり（DHBA と海馬の BIF に合わせ、左右の重複は別に分析する）、2026-08-06 の仮仕様で Circuit ID の文字が A-Za-z0-9._~- と決まり、08-19 に / と + を足すことで合意しました。@ はこの文字集合の外です。最初は左右を ID から外して Descriptor だけに残す案を試しましたが、同じ集団の左と右が 1 つの HCD で同じ ID になり、両立できませんでした。そこで v0.17.0（PR #64）で次の形にしました。

  • 左右は 9 本目の facet side。値は left か right の 1 つで、付けなければ「両側、または区別しない」。
  • アンカーは常に左右のペア。BNA:57 は BNA:57-58/side:left と書く。
  • Circuit ID には、左右を区別するときだけ最後の項目として書く（A4ul(left)、A8m(L3.left)、A4ul(L5.pt.out-Sp.left)）。両側なら A4ul。左右を区別しないのが既定なので、7/14 の決定とも矛盾しない。
  • 1 つの HCD に、同じ集団の左と右を別の回路として置けます（A4ul(left) と A4ul(right) は Descriptor も ID も違う）。両側の回路（A4ul）と片側の回路（A4ul(left)）を並べると、ほかの細分と同じく、両側の方を Collection にするよう求められます（cobrac:nested-uc）。
  • あわせて括弧の中の区切りを , から . に、投射の書き方を out: から out- に変えました（MVOcC(V1,L4Ca) → MVOcC(V1.L4Ca)、Amyg(BL,out:CEN) → Amyg(BL.out-CEN)）。

0.16 までに作ったプロジェクトと Canon には、旧い形の Descriptor と Circuit ID が残っています。保存済みのデータは書き換えません。読むときに現在の形へ直し、その形で比べます。

3.9 Uniform / Collection と Descriptor の関係

回路が Uniform かどうかは HCD ごとに決まります。その HCD の葉なら UC、その HCD がさらに Sub-Circuits に分解するなら Collection（Uniform = FALSE）です。Descriptor はプロジェクト横断のキーのままで Uniform かどうかを持たないので、同じ領域が粗いプロジェクトでは UC、細かいプロジェクトでは Collection になりえます（この差をそろえるのが第 4 部の Canon です）。SABRA の単位全体を 1 つの UC にするかどうかは、プロジェクトの選択です。どこで分けるかを決めて uc.json に書くのは CoBRAC エージェント（LLM）、規則に合っているかを確かめるのはワーカーの検査です。

  • データ：uc.json は ucs（常に Uniform）と任意の collections（circuitId、descriptor、names、sourceOfId、subCircuits、comments）を持ちます。collections の無いファイルもそのまま有効です。descriptor は SABRA の単位か facet つきの集団で、複数の単位をまとめただけの Collection（例 Mesolimbic）は空です。Collection の Source of ID は常に collection、comments（なぜ不均質か）は必須です。Collection は Interface・Output Semantics・機能の項目を持ちません。
  • uniformityNote：UC は任意の uniformityNote（その HCD で均質とみなす理由）を持てます。Circuits.csv では Comments の後ろに Uniform in this project: … として付きます。
  • いつ分けるか（prompts/phases/HCD.md の手順 3）：選んだ粒度で解剖学的・機能的に不均質なとき（いくつもの別領域を含む回や群、投射元・先として別に報告される部分、文献で役割が異なる部分）。領域や名前のある部分で足り、層・細胞種の証拠は必須ではありません（v0.11 の言語プロジェクトの再実行で、層・細胞種の証拠が無いために Collection が 1 つも作られなかったことから緩めました）。部分は命名規則で名付け、分けた理由を Collection の comments に書きます。分けた領域の親の Collection は推奨で必須ではなく、さらに上のまとまり（名前のあるネットワーク）は読み手の助けになるときだけ作ります。
  • 入れ子の禁止：同じアンカーで facet の値が部分集合になる 2 つ、またはアンカーだけの UC とその中の UC（同じ側の BNAG 群の BNA 領域、左右ペアの片側、& の 1 つ）を両方 UC にはできません（cobrac:nested-uc）。粗い方を collections に移します。
  • 送り手は Uniform：複数の SABRA 単位にまたがる送り手（BNAG 群や複数アンカーで facet なし）は uniformityNote が必要で、無ければ部分への分割か理由の記入を求められます（コード 203）。分割では層・細胞種の証拠は要らず、領域全体だけを報告する論文は relation < で各部分を支えます。単一の領域、左右のペア、facet つきの UC、受け手だけの回路は対象になりません。

3.10 ワーカーの検査とエラーコード

HCD の段の終わりに、ワーカーは uc.json の名前を次の順に検査し（checkUcNaming）、問題があれば修正ターンでエージェントに戻します。

  1. Descriptor の構文と意味：アンカーの形、BNA の番号（1〜246、ペアは奇数と奇数+1）、facet の順と重複、mol の極性、side の値。旧い形なら現在の形での書き直しを求める。0.24.0 以降のプロジェクトでは新皮質でない BNA の領域・群を使っていないこと（Canon にある Descriptor は除く）。
  2. Descriptor の重複：正規化した Descriptor が UC と Collection の中で重ならないこと。
  3. 括弧の中の項目：項目の数が facet の値の数と一致すること、side があるときは最後の項目がその値であること、side が無いのに left / right を書いていないこと。
  4. 前半の略称：アンカーの正式略称と大文字小文字まで一致すること（BNA は組み込みの 246 ラベルの表、HOMBA / DHBA は RCS の get_homba_term）。BNA の担当範囲の HOMBA の項や DHBA 名を持たない項をアンカーにしていれば、正しいアンカーを示して直させる。RCS に問い合わせられなかったアンカーは、この照合だけを省く。
  5. 文字：Circuit ID が許容文字と ( ) だけでできていること（Descriptor の無い Collection の ID も対象）。

あわせて、Circuit ID が UC と Collection で重ならないこと、facet の無い UC の names が SABRA の正式名で始まることも検査します。

3.11 uc.json での書き方

CoBRAC エージェントが書く uc.json の例です（テストの fixture から抜粋・一部省略）。descriptor が UC Descriptor、circuitId が Circuit ID、sourceOfId が ID の出典です。名前に関わるキーの規則は次のとおりで、ワーカーの検査（スキーマ、sourceOfIdProblem、sabraOfficialName）が確かめます。BRA の値の規則のうち、文献・接続・FRG に関わるもの（Reference ID、Pointers、relation、Output Semantics など）は第 2 部で扱います。

キー規則

names先頭は SABRA の正式名（BNA の領域名、または RCS の get_homba_term が返す DHBA 名）。facet つきの UC は正式名の後に細かい集団を書く。同義語は ; で区切って後ろに続ける。RCS に問い合わせられなかったときは照合を省く
uniformityNote任意。複数の SABRA 単位にまたがる送り手では必要（3.9）

3.12 Canon・BRA-DB・オーケストレーターでの使われ方

使う場所Descriptor・facet の役割
Canon（第 4 部）回路を正規化した Descriptor をキーにして持つ。プロジェクトの JSON は Circuit ID で接続を書くので、push や PR のときに Descriptor に解決する（Circuit ID は改名がありうるが、Descriptor は Canon の中で一意）。Descriptor の無いグループは group:<Circuit ID> がキー。「より細かい回路」（衝突 C3）の判定は facet で行い、side も facet として数える（Canon に両側の Uniform の A4ul があるときに A4ul(left) を足すと C3。左と右だけなら別の回路として共存できる）。旧い形は現在の形にして比べる（currentCanonSnapshot）：bna:29 と bna:29-30/side:left は同じ回路、A44d@L と A44d(left) は同じ Circuit ID なので C4 にならない。プロジェクトが現在の形を持ち込むと PR に改名として表示され、マージ後の Canon は現在の形になる。エージェントに渡す canon/ のファイルと、確認済みの引用のキーも現在の形で書き出す。
BRA-DB（第 5 部）Circuits.csv の最後の列（UC Descriptor）として CSV に入る。BRA-DB の Circuits は Circuit ID（circuit_id）がキーで、同じ集団は同じ ID なので、複数プロジェクトの回路が同じ行に集まる（他のプロジェクトが定義した回路は共有の語彙として扱う）。
オーケストレーター（第 6 部）計画の行に付けるアンカー（HOMBA:<id>、BNA:<l>-<r>、BNAG:<L2>）は Descriptor のアンカー部分と同じ形（facet は付けない）。完成した行のアンカーは、そのプロジェクトの uc.json の全 Descriptor から読み直す。

3.13 WBAI と決めたいこと

UC Descriptor と facet は、CoBRAC が先行して使っている提案です。組織の規則として採るかどうか、どこを変えるかは WBAI との合意が必要です。確認したい論点は次のとおりです。
