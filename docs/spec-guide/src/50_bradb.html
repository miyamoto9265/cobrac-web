第 5 部

BRA-DB（仮）on AWS

CoBRAC の AWS アカウント内に、BRA-DB と同じスキーマ（v4.6、PostgreSQL 17 + Apache AGE 1.7）のデータベースを作成しました（CDK スタック BraDb、v0.26.0 から）。CoBRAC は、完了したジョブの結果を凍結した版を、このデータベースに来歴つきで登録します。アプリ自身のデータ（DynamoDB・S3）は従来どおりで、BRA-DB はアプリのデータベースではなく登録先です。

何を入れるか凍結した版の 5 つの CSV（Project・References・Circuits・Connections・FRG）を、BRA-DB のテーブルとグラフに
どう入れるかBRA-DB の import_bra_project v3.10 に対応する処理を、1 トランザクションで。整合性を確かめ、失敗すれば戻す
何を守るか履歴を消さない。どの版（ID・内容のハッシュ）が、だれの依頼で、どのアプリで登録されたかを追記専用で残す

5.1 位置づけ：版 → 登録パッケージ → BRA-DB

BRA-DB への登録は、必ず凍結した版から行います。作業中のデータ（毎回上書きされる workspace/ など）は登録しません。流れは次のとおりです。

5.2 前提となる「版」の仕組み

完了した BRA のジョブ（初回・追加指示・リトライ）は、結果を不変の版として凍結します（v0.25.0 から）。凍結するのはワーカー（LLM を含まないプログラム）で、ジョブを完了にする前に行います。作業用のコピー（workspace/・output/・graph/）は実行のたびに上書きされ、版が履歴になります。

項目仕様
番号と ID版 n はジョブ後のプロジェクトの revision。そのため、ほかの場所に保存済みの番号（複製元の clonedFrom.revision、Canon の projectRevision、解説記事の sourceRevision）は、そのまま版を指す。全体で一意な ID は <projectId>@v<n>（Project ID は再利用されない）。親は版 n-1（複製の最初の版は、写した公開プロジェクトの版）。
凍結する内容S3 のプロジェクトの接頭辞の revisions/{n}/ に、files/（ワークスペース：HCD / FRG / CSV のデータ、レポート、判断ログ、検査結果。*.jsonl のログは除く）、output/*.xlsx、graph/*.json、bradb/（登録パッケージ。BRA-DB の登録だけが読む内部のもので、ダウンロードには出さない）、manifest.json（BraVersionManifest）。
不変性ファイルを先に、manifest を最後に条件付きの put（If-None-Match: *）で書くので、manifest がある版だけが存在し、置き換えられない。同じジョブでもう一度実行すると既存の版を返し、別のジョブが作った同じ番号の版には触れない（sys.versionConflict を記録）。凍結の失敗は記録するだけで（sys.versionFailed）、ジョブを失敗させない。バケットのポリシーが users/*/*/revisions/* の削除をすべての主体に禁じる。
manifest版 ID、親、由来（job / baseline）、作成時刻、Contributor、ジョブ（ID・種類・指示）、生成条件（アプリの版と git commit、prompts/ と HARNESS_SCHEMAS の SHA-256、モデル、推論の強さ、調査モード、固定した Canon の rev、HCD の検査が従った SABRA の境界（neocortex / legacy）と RCS が返した境界の版、検証ルール harnessRules（ルールの無いプロジェクトは 0。0.28.2 より前の版には無く、manifest は書き換えない）、Project.csv の CSV の形式、オーケストレーターの計画が作ったなら planId）、各ファイルの SHA-256 と大きさ、内容のハッシュ、親との差分の要約（表ごとに追加・削除・変更の行数。親にスナップショットが無ければ null）。
内容のハッシュcontentSha256 ＝ Project.csv・References.csv・Circuits.csv・Connections.csv・FRG.csv の順に <CSV 名>\t<その SHA-256>\n を並べた文字列の SHA-256（無いファイルは -）。BRA-DB に入るのは 5 つの CSV なので、同じデータなら名前や詰め方によらず同じハッシュになる。
登録パッケージ5 つの CSV がそろうときだけ作る。BRA-DB のインポートが読む名前（{P}_project.csv、{P}_references.csv、{P}_circuits.csv、{P}_connections.csv、{P}_frg.csv）の CSV と manifest.json（BradbPackageManifest：projectId・versionId・version・parentVersionId・contentSha256・各ファイルのハッシュ・braVersion＝CSV の形式・cobracGenerated: true・importType: "cobrac"・Contributor・生成条件 provenance・import.replace / import.allowShrink）。replace は親が同じプロジェクトの版のとき true、allowShrink は変更が Circuits か Connections の行を減らすとき true。対象は BRA-DB スキーマ v4.6、インポート v3.10 以降。
DynamoDB版の要約（BraVersionSummary：番号、ID、親の ID、由来、作成時刻、内容のハッシュ、アプリの版、git commit、差分の要約、パッケージの有無、仮説の数（記録している版だけ））を、その版を作ったジョブ（Jobs.braVersion。baseline は最後に完了したジョブ）に、最新のものをプロジェクト（Projects.latestVersion）に持つ。既存の項目に属性を足しただけで、テーブルやインデックスは変えていない。

版の仕組みより前に完成したプロジェクト

  • スナップショットが無いので、現在のデータを版 revision、由来 live（画面では「未保存」。作業用のコピーから表示）として一覧に出します。
  • 追加指示は完了したプロジェクトでしか受け付けないので、追加指示のワーカーは変更を始める前に、そのデータを版 revision、由来 baseline として凍結します（生成条件は最後のジョブが記録したものだけ。revision が無ければ 1 にする）。追加指示の結果は revision + 1 になり、baseline が親です。
  • 失敗・中止した旧いプロジェクトのリトライは baseline を凍結しません（作業用のコピーが途中まで変わっているかもしれないため）。その結果の版の親にはスナップショットが無く、差分の要約もありません。

「版」タブ

  • 版の一覧（新しい順：番号、現在の版か、由来、日時、実行の種類、モデル、変わった行の数、追加指示の文）と、選んだ版の生成条件、表（凍結したファイルを表のビューアで開く）、ほかの版との行単位の差分（既定は 1 つ前の版）、ファイルの一覧を見られます。ヘッダーには現在の版と内容のハッシュの先頭が出ます。
  • 版はダウンロードしません。タブにダウンロードは無く、GET /projects/{id}/artifacts/download は revisions/ の下のキーを拒み、ヘッダーの現在のデータのダウンロードは従来どおりです。表のビューアは凍結したファイルを GET /projects/{id}/artifacts/text で読みます。
  • API：GET /projects/{id}/versions（一覧）、…/versions/{n}（manifest とファイル）、…/versions/{n}/diff?base=（差分）。
  • 差分（diffBraCsvs）：行は BRA-DB と同じキーで照合します。References は Reference ID、Circuits は Circuit ID、Connections は（sCID, rCID, Reference ID）（同じキーが繰り返すと順に #2、#3 を付ける）、FRG は Node ID。列ごとに比べ、Project.csv はプロジェクトの行だけを比べます（Review End Lines は行数に従うため）。

典拠：packages/shared/src/braVersion.ts、packages/worker/src/versions.ts・index.ts、packages/api/src/app.ts（版のルート）

5.3 AWS の構成

BRA-DB は専用のスタック BraDb と専用の VPC で動きます（AWS アカウント 765959262011、リージョン ap-northeast-1）。インターネットからの通信を受けるものはありません。synth 時に COBRAC_BRADB=false にするとスタックを作らず、API は「この環境には BRA-DB がありません」と答えます。

リソース設定
VPC10.42.0.0/24、1 AZ。プライベートサブネット（インスタンス・登録 Lambda）と、NAT インスタンスだけを置くパブリックサブネット。S3 ゲートウェイエンドポイント（無料）
NAT インスタンスt4g.micro、Amazon Linux 2023。外向きだけ（パッケージの更新、Secrets Manager、SSM）。VPC からの通信だけを受ける。NAT Gateway より月に約 $40 安い
EC2 Dbt4g.small、Ubuntu 24.04 arm64（AMI は固定）、ルート gp3 16 GB 暗号化、IMDSv2、終了保護、SSH なし（SSM Session Manager）。セキュリティグループは 5432 番を登録 Lambda からだけ許可
データ用ボリュームgp3 20 GB、暗号化、RETAIN（スタックを消しても残る）。/dev/sdf として付け、/srv/bradb（クラスタのデータディレクトリ）にマウント
スナップショットData Lifecycle Manager：毎日 18:00 UTC、7 世代（タグ bradb-backup=daily）
Secrets Managercobrac/bradb/bra（所有者）、cobrac/bradb/cobrac_import（登録 Lambda）、cobrac/bradb/cobrac_read（読み取り専用）。起動のたびに bootstrap.sh がロールのパスワードをここから設定するので、ローテーションは次の再起動で効く
Lambda cobrac-bradb-importNode 22 arm64、プライベートサブネット、25 秒。CobracAgents の API だけが呼べる（この名前への lambda:InvokeFunction）

起動とスキーマの適用

インスタンスのユーザーデータは、起動のたびに packages/infra/bradb/bootstrap.sh を実行します。

  1. PGDG から postgresql-17 と postgresql-17-age を入れる。
  2. 初回はデータ用ボリュームをフォーマットしてマウントし、クラスタを作る（2 回目以降は登録し直す）。
  3. shared_preload_libraries = 'age' と、VPC からだけの scram-sha-256 認証を設定する。
  4. Secrets Manager の値でロールのパスワードを設定し、データベース bra_db_v4_6 を作る。
  5. packages/infra/bradb/sql/ のファイルのうち、cobrac.schema_migrations にまだ無いものを番号順に適用する（*_grants.sql は変わったら再適用。それ以外の適用済みファイルは変えてはならず、変更は新しい番号のファイルで足す）。

SQL ファイルを変えるとユーザーデータが変わるので、CloudFormation がインスタンスを停止・起動し（約 1 分の停止）、新しいファイルが起動時に適用されます。ログは /var/log/bradb-bootstrap.log です。

5.4 データベースの中身

0001_bradb_schema_v4_6.sql は、BRA-DB の DDL v4.0 とマイグレーション 01〜06（v4.1〜v4.6）の最終形を 1 つのスクリプトにしたものです。テーブル・列・制約の名前は BRA-DB のものなので、BRA-DB のツールがそのまま使えます。0002 はグラフのラベルを先に作り、0003 は CoBRAC 独自のスキーマ cobrac、0004 はロールの権限です。

5.5 登録の手順

利用者の手順

  1. プロジェクトの「版」タブで、保存済みの版を選ぶ（5 つの CSV がそろった版だけ登録できる）。
  2. 版の BRA-DB 欄で、BRA-DB がいまどの版を持っているかを確かめる。
  3. 「v<n> を BRA-DB に登録」を押す。BRA-DB にあるものより回路か接続が少ない版は、確認を求められる（確認すると allowShrink で再送）。
  4. 結果と、その版の登録の記録（状態・時刻・依頼者・警告・スキップした回路）が欄に出る。

登録できるのはプロジェクトの所有者だけです（POST /projects/{id}/versions/{n}/bradb、状態の取得は GET /projects/{id}/bradb）。API（Lambda）は版のパッケージ（revisions/{n}/bradb/）を読み、BRA-DB の VPC の中の登録 Lambda を同期で呼びます。登録に成功すると、Projects.bradb に最後に登録した版（版 ID・番号・内容のハッシュ・時刻・登録 ID）を残します。登録の記録の依頼者は、利用者の Contributor 名（無ければ表示名）です。仮説を含む版（仮説モード）は、仮説を登録する規則が決まるまで登録できません（ボタンが押せず理由が出る）。BRA-DB の無い環境では欄が出ません。

登録 Lambda の処理（registerVersion）

  1. パッケージの検証：パッケージの形式、各ファイルの SHA-256 と manifest の一致、5 つの CSV がそろっていること、内容のハッシュの再計算。合わなければ rejected（invalid）。
  2. シートの読み取り：v3.10 と同じく列名・Review End Lines・Source of ID・Node role・列挙値・Capability&Mechanism を読む。ただし、完全一致の列名を部分一致より優先し、見出しに無い列は固定位置から読まずに空とし、FRG は「Node ID」列から読み、BRA-DB の制約が拒む値（Modulation Type、Region Category、長すぎる文字列）は NULL にして警告を出し、元の値を extra に残す。
  3. トランザクション開始：プロジェクトごとの advisory lock を取り、bradb_projects に行があれば replace、無ければ create。
  4. 同じ内容なら何もしない：BRA-DB が持つ版と内容のハッシュが同じなら unchanged を記録して終わる。
  5. 回路の分類と検査：BIF / Local の分類、v3.10 の検査（Collection は接続を送れない：203、relation は = < >）。
  6. 置き換えの条件：BRA-DB でレビューコメントが付いたプロジェクトは置き換えない（review_comments）。回路か接続が減るなら、所有者の確認（allowShrink）が無い限り拒否（shrink、前後の件数つき）。
  7. 書き込み：bradb_projects（置き換えでは行と project_key を保ち version を上げる）、回路（自分の定義と所有者の無い定義を upsert。ほかのプロジェクトが定義した回路は共有の語彙として残し、スキップとして報告。自分が定義しなくなった回路は削除）、文献、プロジェクトと文献の対応、FRG のノードと履歴、接続、グラフ。
  8. 整合性の検査：書いた辺の数とグラフを照合する。端が BRA-DB に無い辺は警告（エラーではない）。食い違えば rejected（integrity）。
  9. 記録して確定：cobrac.registrations に registered を、bradb_import_log に 1 行（import_type cobrac、agent CoBRAC Agents v<app> (<git sha>)、notes に版 ID・親・内容のハッシュ・登録 ID）を追記して COMMIT。途中のエラーはすべて ROLLBACK し、rejected / failed として記録する。

5.6 履歴を失わない設計

BRA-DB の import v3.10 の --replace は、プロジェクトの行を削除して作り直すため、インポートの記録とノードの履歴も消えます。CoBRAC の登録は、これを避けるように作られています。

置き換えても残るもの
  • bradb_projects の行と project_key（version が上がる）
  • bradb_import_log と bradb_bra_node_history
  • 回路はその場で更新するので、ほかのプロジェクトからその回路への辺も残る
  • cobrac.registrations の全行（トリガーで変更・削除を拒否）
置き換えで作り直すもの
  • そのプロジェクトの接続・FRG のノード・文献との対応
  • グラフのそのプロジェクトのノードと接続の辺
  • ノードの履歴は続く：新しいノードは版 1（import）、変わったノードは版 n+1（update）、変わらないノードは版を保つ（行を足さない）
規則挙動
同じ内容BRA-DB が持つ版と内容のハッシュが同じなら何もしない（unchanged）
縮小BRA-DB より回路か接続が少ない版は、所有者が確認するまで拒否（shrink）
レビュー済みBRA-DB でレビューコメントが付いたプロジェクトは置き換えない（review_comments）。レビュー済みのデータは指示を通じて変える方針（未実装）
仮説仮説を含む版は登録しない（規則は別に決める予定）
ID は不透明BRA-DB の project_id は CoBRAC の Project ID の文字列、版 ID は <Project ID>@v<n>。どちらも分解して解釈しない（新しい ID の形式は変わりうる）

5.7 来歴をたどる

BRA-DB の行から、bradb_projects.project_id → 版 ID と内容のハッシュ（cobrac.registrations）→ S3 の凍結ファイル（revisions/{n}/）とその生成条件（manifest）まで、たどれます。読み取りには cobrac_read を使います。

-- 各プロジェクトについて、BRA-DB がいま持っている版
SELECT project_id, version_id, content_sha256, app_version, git_sha, sabra_boundary, registered_at
FROM cobrac.current_versions ORDER BY registered_at DESC;

-- 1 つのプロジェクトの登録の試みの全履歴（失敗・拒否・変化なしも残る）
SELECT registration_id, version_id, status, mode, reason, counts, requested_by, registered_at
FROM cobrac.registrations WHERE project_id = 'p7m2q9xa' ORDER BY registration_id DESC;

-- グラフ：あるプロジェクトの接続（回路 → 回路）
SELECT * FROM cypher('bradb_graph', $$
  MATCH (s)-[e:PROJECTS]->(r) WHERE e.project_id = 'p7m2q9xa'
  RETURN s.circuit_id, r.circuit_id $$) AS (sender agtype, receiver agtype);
