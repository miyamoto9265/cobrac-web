第 3 部

BRA の作り方

CoBRAC は、ROI（対象の脳領域）と TLF（トップレベル機能）を受け取り、文献に基づく HCD と FRG を作って、1 つの BRA にまとめます。第 3 部では、その作り方を説明しています。文献を読んで回路や機能を判断するのはエージェントだけです。ワーカーは決まった手順のプログラムとして依頼文を送り、返ってきたファイルを検査し、次に何を依頼するかを決めます。前半（3.1〜3.6）では作るものと仕組みを、中ほど（3.7〜3.11）では段階ごとの作業と検査を、後半（3.12〜3.16）では仮説の扱い、出力、完成した BRA の読み方を扱います。第 3 部が対象とするのは、新しいプロジェクトに適用される現行の検査規則です。古い規則で作られたプロジェクトの扱いは付録 C にまとめています。

エージェントとワーカーの分担判断してファイルを書くのはエージェント、段階を進めて検査するのはワーカーです。1 つのプロジェクトでは 1 つの会話を最後まで続けます（3.3〜3.6）。
段階ごとの作業と検査調査、HCD、FRG の順に進み、各段階でワーカーが文献と引用を照合し、問題があれば修正を依頼します。最後に HCD と FRG の整合を調整します（3.7〜3.11）。
仮説・出力・読み方仮説を許す範囲、ワーカーが作る CSV・xlsx・グラフ、解説記事、長いジョブの保存、完成した BRA を読むときの注意を扱います（3.12〜3.16）。

3.1 作るもの：HCD と FRG

1 つの BRA は、HCD と FRG という 2 つのグラフからできています。どちらも、エージェントが文献を調べて JSON のデータファイルに書き、ワーカーが検査してから表と図に変換します。

HCD（Hypothetical Component Diagram）
回路（UC）をノード、回路の間の接続をエッジとするグラフです。ROI のどの神経集団が、どこから入力を受け、どこへ出力するかを、文献の根拠付きで表します。
FRG（Function Realization Graph）
TLF を機能ノード（GN）に分解し、最下層で HCD の UC に結びつける木です。どの回路の組み合わせがどの機能を実現するかを表します。

UC（Uniform Circuit）は、その HCD が「均質な情報を符号化する最小のメゾスコピックな神経集団」とみなすものです。UC にはそれぞれ、命名規則に従った名前（Circuit ID、2.6）が付きます。どこまで細かく分けるか、細かく分けられない部分をどうまとめるかは 2.9 に記載しています。

HCD の接続には、根拠となる文献が 1 本ずつ付きます。ワーカーはその文献が実在するかを照合し、引用された文が原文にあるかを照合します（3.10）。FRG の GN には、下位のノード（GN または UC）、説明、interface、機能項目が書かれます。HCD と FRG は同じ回路を別の面から表すものであるため、最後に両者の食い違いを調べて調整します（3.11）。

利用者が受け取るのは、HCD と FRG を表にした 5 つの CSV、それをまとめた xlsx、グラフの図、エージェントが書くレポートと判断の記録です（3.13）。

典拠：prompts/phases/HCD.md、prompts/phases/FRG.md、packages/shared/src/harness.ts

3.2 全体の流れ

新しいプロジェクトでは、既定で有効な調査ステップ（3.7）の後に HCD と FRG の段階が続き、最後にワーカーが成果物を生成します。どの段階も「エージェントのターン → ワーカーの検査 → 必要なら修正ターン」の繰り返しで、段階を進めるのは常にワーカーです。調査を無効にしたプロジェクトは HCD から始まりますが、その場合も文献のツールと文献の照合は使われます。

3.3 エージェントとワーカー

エージェント

本書で「エージェント」と記すときは、BRA を作る CoBRAC エージェントを指します。中身は OpenAI の言語モデルで、モデルと推論の強さ（reasoning effort）はプロジェクトごとに選びます（4.2）。モデルは OpenAI の Codex（Codex SDK と Codex CLI）を通して動きます。Codex は、モデルにシェルでのファイルの読み書き、MCP のツール、Web 検索を使わせ、会話の履歴とその自動の圧縮を管理する実行環境です。推論そのものは、コンテナの外にある OpenAI API で行われます。

エージェントは、自分から作業を始めたり、段階を進めたりはしません。ワーカーから依頼文を 1 つ受け取ると、それに応える 1 回のターンの中で、文献を検索し、原文を読み、ファイルを編集します。ターンの中ではツールを何度でも呼べます。ターンの最後に終了の JSON を返して止まり、次の依頼を待ちます。

1 つのプロジェクトでは、調査・HCD・FRG・修正・調整のすべてのターンが、同じ会話（Codex のスレッド）で続きます。質問への回答、リトライ、完成後のフォローアップも、同じ会話を再開して行います（3.6）。会話が OpenAI の 1 回のリクエストの上限を超えたときだけ、ワーカーが新しい会話に切り替えます。そのときは、プロジェクトのファイルと判断の記録を読んで続けるよう、エージェントに指示します（8.4）。

ワーカー

ワーカーは、ジョブごとに AWS Fargate で起動する TypeScript（Node.js）のプログラムです。基本は Spot で起動し、起動できないときは On-Demand を使います。ワーカーには LLM が含まれず、次に何をするかはすべて決まったコードで決めます。中心にあるのは次のループです。

  1. 段階の依頼文を組み立ててエージェントに送る
  2. ターンの終了を待つ
  3. エージェントが書いたファイルを検査する
  4. 問題があれば問題の一覧を付けて修正を依頼し、なければ次の段階へ進む

ハーネスは、このワーカーのプログラムに、エージェントへ渡す指示書（付録 B）、JSON Schema、検査、出力への変換を合わせた全体の呼び名です。LLM はハーネスに含まれません。ハーネスが動かす対象です。

エージェントの Codex のプロセスは、ワーカーが同じコンテナの中で子プロセスとして起動します。そのため「ワーカーの中でエージェントが動く」と表現することがありますが、これは動く場所を述べたものにすぎません。ワーカーが推論するという意味ではありません。

利用者の参考資料は、ワーカーが PDF・Office のファイル・URL から文字を取り出して materials/ に置きます。エージェントはそれを、利用者の意図を知るために読みます。参考資料は、照合済みの文献の代わりにはなりません。Canon は複数の BRA でそろえる回路の定義を固定したもので、ワーカーが制約として依頼文に加えます（第 5 部）。

BRA 以外の LLM ジョブ

アプリには、BRA を作るジョブのほかに、LLM を使うジョブが 3 種類あります。どれも同じワーカーのプログラムが別の実行モード（3.6）で起動し、BRA の会話とは別の新しい会話で LLM を呼びます。これらの LLM は BRA を作ったエージェントの会話を引き継がず、ワーカーが用意したファイルや JSON だけを受け取ります。

実装

ワーカーは packages/worker にあり、段階のループは pipeline.ts の runPhases です。会話は codexThreadId としてプロジェクトに記録します。JSON Schema の定義は HARNESS_SCHEMAS、指示書は prompts/ にあります。BRA 以外のジョブの入口は index.ts の articleMain・canonReviewMain・planJobMain です。

典拠：packages/worker/src/index.ts（実行モード・ターン、articleMain・canonReviewMain・planJobMain）、codex.ts（Codex の起動と設定）、pipeline.ts（段階のループ）、litMcp.ts、rcs.ts、materials.ts、article.ts、canonReview.ts、planJob.ts、prompts/article.md、prompts/plan.md

3.4 ターンとファイルの受け渡し

ワーカーとエージェントの間で、会話のメッセージとして行き来するものは 2 つだけです。ワーカーからの依頼文と、エージェントからのターン終了の JSON です。作業の中身は、すべて作業ディレクトリのファイルで受け渡します。作業ディレクトリはワーカーのディスク上の /work で、中心はプロジェクトフォルダ /work/<ProjectID>/ です。

1 ターンの流れ

  1. ワーカー → エージェント：依頼文。プロジェクトの情報と段階の名前、段階の仕様、前回の検査で見つかった問題の一覧、返答の言語の指示を連結したテキストです（3.5）。
  2. エージェントの作業。エージェントはターンの中で lit・RCS・Web 検索を呼び、シェルでファイルを読み書きします。その間ワーカーは、ツールの呼び出しとファイルの変更をイベントとして受け取ります。また、文献の検索と RCS の呼び出しを記録し、画面に進捗を流します。ターンの途中でワーカーが指示を足すことはありません。ただし、取り消しや調査の時間切れのときは、ターンを打ち切ることがあります。
  3. エージェント → 作業ディレクトリ：ファイル。データ JSON、レポート、判断の記録を書き換えます。
  4. エージェント → ワーカー：ターン終了の JSON。形は {"status": "done" | "question", "message", "question"} です。done は「このターンの作業を終えた」というエージェントの申告で、受理を意味しません。
  5. ワーカーの検査。ワーカーはファイルを読み直して検査し、結果を検査結果のファイルに書きます。
  6. ワーカーの判定。問題があれば、問題の一覧を付けた修正依頼を送ります。受理したら次の段階の依頼を送ります（1 に戻る）。question が返ったときは、作業ディレクトリと会話を保存して停止します（3.6）。
レート制限とターンの失敗

OpenAI のレート制限に当たったとき、まず Codex 自身が再接続を試みます。それでもターンが失敗した場合は、ワーカーが一定時間待ってから、同じ会話でターンを再試行します。1 回のリクエストが大きすぎるときや、利用枠・請求の問題は、待っても解消しないため再試行しません。会話が大きすぎるときだけ、新しい会話に切り替えて続けます。回数と待ち時間は 8.4 に記載しています。

会話ではなくファイルを正本にする理由

会話が長くなって圧縮されたり、新しい会話に切り替わったりしても、生成の途中の結果はプロジェクトのファイルに残ります。そのため、正本は会話ではなくファイルに置きます。構造化したデータは JSON、自由な文章は Markdown で書きます。JSON の形は 1 か所で定義し、ワーカーがそれをエージェント用の JSON Schema のファイル（/work/schemas/*.schema.json）として書き出します。検査にも同じ定義を使います。成果物はすべて英語で書きます。例外は解説記事だけです（3.14）。

人が読む説明は、エージェントが report.md にまとめます。節は ## Overview・## HCD・## FRG・## Limitations・## References で、仮説があるときは ## Hypotheses も加えます。decision_log.md は判断の記録です。エージェントが結論を選んだ理由、採らなかった案、利用者の回答、変更の理由を追記していきます。RCS や検索の生のログを判断の記録に転記する必要はありません。呼び出しの記録は、ワーカーが別のファイルに取ります。FRG の作業にある上からの分解、最適化、下からの読みは作業の手順であり、専用のファイルはありません。その理由はレポートに書きます。

schemas/・materials/・canon/ は、プロジェクトフォルダの外（/work の直下）に置く補助の入力です。これらの資料とワーカーが書くファイルは参照用で、指示書ではエージェントによる変更を禁じています。検査は、ワーカーがデータファイルから行います。CSV はエージェントに書かせません。

実装

ターン終了の JSON の形は出力スキーマ TURN_OUTPUT_SCHEMA で、データファイルの JSON の形は HARNESS_SCHEMAS（どちらも packages/shared/src/harness.ts）で定義します。ターンの実行は codex.ts の runTurn で、レート制限での再開の回数は RATE_LIMIT_TURN_RETRIES、大きすぎるリクエストの判定は isRequestTooLarge です。

典拠：prompts/AGENTS.md「Workspace」、packages/worker/src/codex.ts（runTurn・RATE_LIMIT_TURN_RETRIES・isRequestTooLarge）、packages/shared/src/harness.ts（TURN_OUTPUT_SCHEMA・PROJECT_FILES・HCD_FILES・FRG_FILES・HARNESS_SCHEMAS）、packages/worker/src/steps.ts

3.5 依頼文の組み立て

ワーカーは作業ディレクトリに、共通の規則を書いた AGENTS.md と schemas/ を用意します。AGENTS.md は作業ディレクトリの直下に置かれ、Codex が自動で読み込みます。

ターンごとの依頼文は、次の 3 つを --- の区切りで連結したものです。

  • 利用者にも画面に表示する短い依頼
  • 内部で付ける仕様
  • 返答の言語の指示

画面に出す短い依頼には仕様を含めていませんが、エージェントにはすべて渡しています。

基礎の仕様と追加の規則

仕様は、1 つの長い文章に固定されてはいません。ワーカーはプロジェクトの設定に応じて、段階ごとの基礎の仕様に次の規則を足します。

  • HCD：ROI の規則（HCD_roi_rules.md）と、Canon の条件
  • FRG：GN の規則（FRG_gn_rules.md）と、HCD から計算した候補
  • 調査ステップを使うプロジェクト：調査の結果を使う指示（research_mode.md）
  • 仮説モード：仮説を許す範囲（HYPOTHESIS.md）

基礎の仕様と追加の規則を合わせたものが、そのプロジェクトに対する実際の指示です。指示書の全文は付録 B にあります。

ターンごとの中身

ターン画面に表示する依頼内部で加える内容
調査Project ID、ROI、TLF、Contributor、参考資料の場所、調査の開始RESEARCH.md。Project ID と、候補の数・時間・検索の回数を展開する
HCDプロジェクトの情報と Run phase HCD.HCD.md、ROI の規則、Canon の制約。必要なときは RCS が使えないことの注記
FRGプロジェクトの情報と Run phase FRG.FRG.md、GN の規則、最新の frg_candidates.json の候補
調査ステップを使う HCD・FRG各段階と同じresearch_mode.md。調査の結果の利用、追加の調査、FRG の理論と計算モデルの文献の調査
仮説モードの HCD・FRG各段階と同じHYPOTHESIS.md。許可した scope、仮説の比率の上限、調査ステップの有無を展開する。置く位置は調査の注記の後、FRG の候補の前
修正問題の数、修正の回数、最大 30 件の問題、ファイルを直す指示修正ターンの推論の強さを、プロジェクトの値と medium の低い方にする
整合の調整所見 X1・X2・X3・X8 とその意味、片方または両方を直す依頼根拠に基づいて選ぶことと、revisions の節に記録することを求める。推論の強さはプロジェクトの値のまま
質問への回答利用者の回答と、続ける指示新しい会話から再開するときだけ、プロジェクトの情報と仕様を補う
リトライ既存のファイルを読み、終わっていない段階を終える指示必要な仕様。完成したファイルは作り直さない
フォローアッププロジェクトの情報、利用者の指示、許可した仮説の scope の 1 行HCD と FRG の両方の仕様、調査ステップと仮説モードの追加の規則
新しい会話への切り替え会話が大きくなりすぎたことと、ファイルと判断の記録を読んで続ける指示HCD と FRG の両方の仕様と、各モードの追加の規則
CSVエージェントのターンはないワーカーが変換する。問題があれば JSON を直す依頼を送る

返答の言語

成果物の JSON の値、レポート、判断の記録は英語で書きます。一方、message と question は利用者が読むため、画面の言語に合わせます。

作成・回答・フォローアップ・リトライの依頼は、Web 画面の言語（en・ja・zh・zhTw・ko・de・fr・es・pt・ru）を運び、その値はジョブに保存されます。ワーカーは毎ターンの依頼文の最後に、message と question をその言語で書くよう指示する 1 行を付けます。この行は画面には出ません。言語の値がないときは、エージェントは利用者が書いた言語で返答します。言語の値を持たないリトライは、前のジョブの言語を引き継ぎます。

実装

依頼文は packages/worker/src/index.ts で組み立てます。画面に出す部分は shown、内部で付ける仕様は hidden です。プロジェクトの見出しは header、段階ごとの依頼は phasePrompt・firstPrompt、新しい会話への切り替えは freshThreadPrompt、修正依頼は fixPrompt、仕様の組み立ては rawPhaseSpec・phaseSpec です。調整の依頼は pipeline.ts の adjustmentPrompt で、1 ターン分の入力は turnInput でまとめます。言語の値はジョブの locale で、一覧は packages/shared/src/locale.ts にあります。

典拠：packages/worker/src/index.ts（header・phasePrompt・firstPrompt・freshThreadPrompt・fixPrompt・rawPhaseSpec・phaseSpec）、pipeline.ts（turnInput・adjustmentPrompt）、packages/shared/src/locale.ts、prompts/

3.6 質問・フォローアップ・リトライ

BRA を作るジョブは、最初の作成のほかに、質問への回答、完成後のフォローアップ（画面では「追加の指示」）、リトライでも起動します。どれも同じプロジェクトのファイルと同じ会話から続きます。本節では、それぞれの動きと、ワーカーの動き方を決める実行モードを説明しています。ターンの制御の詳細と、ターンが失敗したときの扱いは 8.4 に記載しています。

質問

利用者の判断が必要だとエージェントが判断したとき、エージェントはターンの最後に status: "question" を返します。それを受けてワーカーが作業ファイルと Codex の会話を S3 に保存し、ジョブとプロジェクトを「回答待ち」にして終了します。回答を待つ間は Fargate を動かし続けないため、その間のワーカーの費用はかかりません。

利用者が回答すると、API が同じジョブに回答を記録して、ジョブを待ち行列に戻します。新しいワーカーが作業ディレクトリと会話を復元し、回答を依頼文にして同じ会話を再開します。

フォローアップ

完成したプロジェクトへのフォローアップも、同じファイルと同じ会話から始まります。ワーカーは HCD と FRG の両方の仕様を依頼文で示し直し、エージェントは関係する ID、接続、インターフェース、レポートをそろえて直します。

フォローアップでは、前の受理を引き継ぎません。すべての段階を受理前の状態から検査し直し、CSV と xlsx を作り直して、成果物を新しい版にします（4.5）。指示の文章によって仮説の範囲が広がることはありません。範囲を広げられるのは画面の設定だけです（3.12）。古い形の名前を持つプロジェクトへのフォローアップの扱いは、付録 C に記載しています。

リトライ

途中で失敗したり中止したりしたプロジェクトのリトライは、受理済みの段階を引き継ぎ、まだ受理していない最初の段階から続けます。エージェントには、既存のファイルを読み、完成したファイルを作り直さないよう指示します。既存の成果物は残ります。解説記事のジョブはリトライの対象になりません。

実行モード

ワーカーの動き方は、起動のときに受け取る実行モードで決まります。BRA を作るジョブには 4 つのモードがあり、ほかに BRA 以外の LLM ジョブ（3.3）のための 3 つのモードがあります。

実行モードきっかけ動き
initial新しいプロジェクトの作成HCD の段階の依頼から始める。調査ステップを使うときは、その前に調査を行う（3.7）
resume質問への回答回答を渡し、現在の段階を続ける
followup完成後のフォローアップ指示を適用し、HCD と FRG を検査し直し、CSV と xlsx を作り直す。どの段階も受理済みにしないで始める
retry失敗・中止の後に利用者が行うリトライ、または止まったジョブの自動の再開（8.3）まだ受理していない最初の段階から続ける。既存の成果物は残す
article完成した BRA への解説記事の作成の依頼（付録 A）新しい会話で、解説記事の指示書に従って書く。Web 検索と RCS は使わず、作業ディレクトリは読むだけ（3.14）。止まったジョブは、同じモードで自動的に実行し直す
canon-reviewCanon の PR への AI レビューの依頼。ジョブが指すのは Canon で、プロジェクトには触れない新しい会話で PR の材料を読み、所見を JSON で返す。自律実行の計画の判断のジョブは、判定も返す（5.8、6.8）。止まったジョブは失敗にするだけ
planオーケストレーターの下書き・再計画と、計画の行についての判断。計画ランナーが、枠が空いたときだけ積む。ジョブが指すのは計画新しい会話で、決められた形の JSON で返す。読めない返答なら 1 回だけ依頼し直す。下書きと再計画は RCS を使え、Web 検索と lit は使わない。下書きと再計画の時間の上限は 7 分で、xlsx や PDF を読む下書きと、20 行を超える下書きは 25 分（6.4）。行についての判断（回答と解決）はツールなしで、上限は 5 分（6.8）。止まったジョブは失敗にするだけ

実装

実行モードは SQS のメッセージの mode で渡し、型は packages/shared/src/types.ts の RunMode です。canon-review と plan のジョブでは、projectId に Canon の ID または計画の ID が入ります。解説記事の依頼は POST /projects/{id}/articles です。判断のジョブは canon-review の reviewKind: "decide"、計画用のジョブの種類は planJobKind で区別します。plan の返答の形は PLAN_RESULT_SCHEMA、時間の上限は PLAN_JOB_TIME_BUDGET_MS（7 分）と PLAN_JOB_LONG_TIME_BUDGET_MS（25 分）、行のジョブでは PLAN_ROW_JOB_TIME_BUDGET_MS（5 分）です。質問のときの保存は index.ts の persistState で、プロジェクトの状態は WAITING_USER_INPUT になります。

典拠：packages/shared/src/types.ts（RunMode）、packages/shared/src/planJob.ts・planRowJob.ts、packages/worker/src/index.ts（実行モード、runAgentTurn、persistState）、pipeline.ts、packages/api/src/app.ts（回答・フォローアップ・リトライの API、付録 A）
