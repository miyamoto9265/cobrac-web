6.11 Canon と組み合わせる

計画に Canon を 1 つ決めると、完成した行をその Canon に取り込みながら進みます。行が「完了」になるのは、その行の PR を人が承認したときです。ランナーは承認・却下・回答をいっさい行いません。Canon の無い計画（段階 3 より前の計画と「なし」を選んだ計画）は、6.9・6.10 のとおりに動き、Canon を読みません。

Canon の選択と確定

  • 下書きのときだけ選べます（PUT /plans/{id} { canon }、計画のリースの中で。下書き作成中や確定後は 409）。{ mode: "none" } は外す、{ mode: "existing", canonId } は所有者が所有する削除されていない Canon だけ（プロジェクトは所有者の Canon にしか入れないので、共同編集者の Canon は選べない。ほかは 404）で META.canonId に、{ mode: "new", name }（名前は POST /canons と同じく検査）は META.canonNew = { name } に保存します。1 つの計画に Canon は 1 つまで。
  • 確定後は変えられず、読み取り専用で Canon へのリンクと最新の rev が表示されます。削除された Canon は「Canon が見つかりません」と出ます（GET /plans/{id} の canon = { canonId, name, headRevision }。削除された・所有者のものでなくなった Canon は missing: true、Canon が無ければ null）。
  • 確定のとき（リースの中）、選んだ既存の Canon がまだ所有者のものでなければ 409「この計画の Canon が見つかりません」。「新しい Canon」は、計画の粒度方針を方針にして作られます（createCanon：非公開・空・headRevision 0）。作った直後に計画に保存されるので（canonId、canonNew は null、イベント canon_created）、確定がその後で失敗しても、もう 1 つ作ることはありません。confirmed のイベントは Canon を記録します。
  • 既存のプロジェクトで済む行：そのプロジェクトがすでにこの Canon に入っていれば done。どの Canon にも入っていなければ pending のまま自分のバッチの番を待ち（種のゲートやバッチの順もほかの行と同じ）、番が来たら作らずに Canon に入れて push。ほかの Canon に入っていれば「人の判断」（other_canon）。

開始・push・承認待ち

  1. 開始（ランナー。Canon は 1 ステップに 1 回 ownedCanon で読む）：新しい行のプロジェクトは、最初のジョブを積む前に Canon に入り、その時点の最新の rev に固定されます（createProject の beforeQueue → addCanonMember。開始の途中で止まった行を戻すときも同じ）。行には canonRevision を記録します。失敗したプロジェクトのリトライは、先に最新の rev に固定し直し（pinProject。どの Canon にも入っていなければ入れる）、新しい canonRevision を記録します。プロジェクトがすでに完成している pending の行（確定時に取り込んだ既存のプロジェクト、手で完成させたもの）は、ジョブを積まず試行も数えずに、すぐ push で始めます（どの Canon にも入っていなければ最新の rev で入れる）。
  2. push：syncRow が Canon のある計画の行を完了と判断すると（プロジェクトが COMPLETED）、ランナーが push します。プロジェクトは計画の Canon に入っていなければならず（どこにも入っていなければ最新の rev で入れる。ほかの Canon なら decision / other_canon）、pushProject（POST /projects/{id}/canon/push と同じ関数）が PR を作ります。PR には planId が記録されます。エラーなら decision / push_failed で、エラーを lastError に残します。headMoved は Canon の head が行の固定（row.canonRevision、無ければプロジェクトの固定）より後であることで、PR の差分の要約と headMoved と更新の回数から行の行き先を決めます（pushOutcome、イベント row_pushed / row_decision）。
push の結果行の行き先
エラーの衝突なし（警告・要確認は人に回す）review（承認待ち）。本体の行は AI レビューを依頼（aiReview: "wanted"）。種の行は依頼しない
エラーの衝突あり、行の固定より後に Canon が進んだ、更新が 2 回（MAX_CONFORM_FOLLOWUPS）未満pending（conform: true）：Canon に合わせた更新を待つ
エラーの衝突あり、Canon は進んでいないdecision（conflicts）
2 回更新してもエラーの衝突が残るdecision（conform_limit）
push の失敗、プロジェクトがほかの Canon にいるdecision（push_failed / other_canon）

Canon に合わせた更新（conform）

更新を待つ行は、ほかの pending の行と同じく空き枠とバッチの順で始まります（自分のバッチを止めます）。始める直前に PR を読み直し、その間に人が決めていれば従います（承認 → done、却下・取り下げ → decision、置き換え → 新しい PR の review）。PR がまだ開いていれば、プロジェクトを最新の rev に固定し直し、追加指示のジョブ（queueFollowup、POST /projects/{id}/followup と同じ関数）を積みます。指示は固定の題「Canon rev N に合わせて更新」（conformTitle）で始まり、続けて古い固定から最新までに、このプロジェクトに関わって変わったこと（canonFollowStatus から canonAlignInstruction が作る文）です。行は running になり、conformAttempts が 1 増え、canonRevision が最新になります（イベント row_conform）。完成すると再び push します（新しい PR が開いている古い PR を置き換える）。回数・新しい固定・conform: false は行を確保するとき（starting）にジョブを積む前に一緒に書くので、途中で止まっても 3 回目は起きません。開始に失敗したら conform と古い固定を戻し、回数は数えたままにします。プロジェクトが計画の Canon にもう入っていない、または Canon が無くなっていれば decision にします。

画面では、更新を待つ行に開いている PR へのリンクと「Canon に合わせた更新を待っています」が、一度でも更新した行に「Canon に合わせた更新 n/2」が出ます。

PR の追跡・AI レビュー・人の判断

  • PR を追う：毎ステップ、review の行、PR のある decision の行、更新待ちの行の PR を読みます（prOutcome）。承認 → done（「人の判断」の行の PR が Canon で承認された場合も）、却下 → decision（pr_rejected）、取り下げ → decision（pr_withdrawn）、置き換え（手で push した場合など）→ 新しい PR を review で追う、開いたまま → 変化なし。一時停止中も追います。
  • AI レビュー（本体の行だけ。LLM のジョブで、所見だけを出す）：実行中の計画のステップの枠の部分で、待っている再計画のジョブの後、新しい行の前に、aiReview: "wanted" の review の行ごとに、枠が空いていれば requestAiReview（POST /canons/{id}/pulls/{no}/ai-review と同じ関数）を所有者として、オーケストレーターのモデル・所有者のキーの種類・計画の返答言語で依頼します（1 件 1 枠）。行は aiReview: "queued" と aiReviewJobId を持ちます（イベント row_ai_review）。PR が開いていなければ aiReview を消し、手で依頼したレビューが待機・実行中ならそのジョブを queued として数えます。レビューのジョブが終わったら（完了・失敗・取り消し）、aiReview を消して aiReviewJobId を残します。行には「AI レビュー待ち」（wanted）→「AI レビュー実行中」（queued）→「AI レビュー済み」（PR の画面へのリンク。decision の行にも出る）と出ます。AI レビューは指摘だけで判断はしません。計画の PR の AI レビュー（その planId の PR について所有者が実行した canon-review のジョブ）の費用は、計画の費用に入ります。
  • 人の判断（POST /plans/{id}/rows/{rowId}/resolve { action }。所有者、計画が RUNNING か PAUSED、行が decision、リースの中で。ほかは 409）：計画の画面の「人の判断」カードに理由の文とともに出ます（各操作に確認あり）。「完了にする」（done：行をそのまま完了に数え completedAt を付ける。PR はそのまま Canon に残り、自動では取り込まれない）／「もう一度 push」（push：プロジェクトが COMPLETED の行だけ。でなければ 409「完了したプロジェクトの行だけをもう一度 push できます」。行を running にして理由を消し、conformAttempts は保ち、次のステップで push）／「スキップ」（…/rows/{rowId}/skip は decision の行も受け付ける）。イベント row_resolved に操作と元の理由が残ります。
  • PR から計画へ：CanonPullRequestRecord.planId（push したプロジェクトの planId、無ければ null）は、手で push したときも含めてすべての push で記録されます。Canon の PR の一覧と PR の画面には計画の ID のチップが出て、Canon の所有者には計画へのリンクになります（計画はその人のもの）。

種のゲートと、承認待ちの上限

種のゲート
Canon のある計画では、種の行はその PR を人が承認する（または解決・スキップする）まで、後のすべてのバッチを止めます。種は同じバッチにあっても 1 件ずつ始まり、ほかの種が実行中・承認待ち・人の判断の間は始まりません。画面には「種の PR の承認を待っています」と PR へのリンク、または「種の行に人の判断が必要です」が出ます。種の PR を先に承認すると、後の行はその rev から作り始めます。
承認待ちの上限（背圧）
承認待ちの行が 20 件（PLAN_MAX_WAITING_PRS）に達すると、新しいバッチを始めません（いまのバッチの行は続く）。画面には「承認待ちの PR が 20 件あるため、次のバッチを止めています」。Canon の画面の「まとめて承認」（4.8）で、矛盾の無い PR をまとめて承認できます。再計画も、バッチの行の PR がすべて承認されてから行います。

計画の Canon が削除された・所有者のものでなくなった場合：承認待ちの行と、完成して push するはずの行は「人の判断」（push_failed、「The plan's Canon was not found.」）になり、新しい行・リトライ・Canon に合わせた更新を始めようとすると、計画は自分で一時停止し（canon_missing）何も始めません。画面には「一時停止中: この計画の Canon が見つかりません（削除された可能性があります）。新しい行は Canon に入れられないため始めません。」と出ます。実行中の行は、ほかの一時停止と同じく続いて追われます。所有者は待っている行をスキップするか、計画を中止できます。review と decision は枠を使わず、完了にも数えません。Canon のある計画は、すべての行が done か skipped になったときに完了します。

6.12 計画の一覧と、質問・要対応・一時停止・再開・中止

計画の一覧（ライブ表示）

計画の一覧（/plans）は、計画がいま何をしているかを見る画面です。実行中・一時停止・下書き作成中の計画があるあいだは、見出しの横に「ライブ」が出て、画面（プログラム）が 15 秒ごと（下書き作成中は 5 秒ごと）に GET /plans を読み直します（タブが裏にあるあいだは読まない）。

欄内容
あなたの番すべての計画から、所有者（人）の操作を待っているものを先頭にまとめる。質問・承認待ち・人の判断・要対応の行、再計画の提案、所有者以外の理由で止まった計画、確定を待つ（または失敗した）下書き。押すとその計画を開く。何も無ければ「いま、あなたの操作を待っているものはありません」
動いている計画実行中・一時停止・下書き作成中の計画を横長のレーンで出す。完了数、いまのバッチ、経過時間と見込み、費用（実績と見積もり）、バッチごとの進捗バー（完了は緑、作っている行は流れる青、質問・判断は黄、承認待ちは紫、要対応は赤。いまのバッチは枠で囲む）、いま作っている行とそのステップと経過時間、最近の動き（直近 4 件）
下書き・終わった計画下書きはカード、完了・中止した計画は折りたたんだ一覧
新しい計画右から開くパネル（Esc か背景で閉じる）。計画が 1 つも無いときは、作成のフォームが画面に出ている（6.4）

レーンの中身は API（プログラム）が返す pulse です。GET /plans は、実行中・一時停止の計画のうち新しい 12 件について、計画の詳細から、バッチごと・状態ごとの行の数、作っている行（starting / running）と操作を待つ行（question / review / decision / attention）、最新の出来事 4 件とその行、未決の提案の数、見積もりと実績を計算して付けます（保存はせず、読むたびに計算）。それより古い計画は件数だけを出します。

計画の画面の「行」では、作っている行（と質問中の行）に、そのプロジェクトのステップ（調査 → HCD ⇄ FRG → CSV → xlsx）が出ます。進捗バーはバッチごとに区切られ、行が進むと伸びます。動き（流れる帯、伸びるバー、実行中の点の脈動）は、OS で「視差効果を減らす」（prefers-reduced-motion）を選んでいると止まります。

典拠：packages/web/src/pages/PlansPage.tsx・PlanDetailPage.tsx、packages/web/src/components/PlanBar.tsx、packages/api/src/lib/planOps.ts（planPulse）、packages/api/src/app.ts（LIST_PULSE_PLANS）、packages/shared/src/plan.ts（PlanPulse）

行と計画への操作

操作挙動
質問箱エージェントが質問すると、その行だけが止まり、計画の画面の質問箱に出る。答える（POST /projects/{id}/answer と同じ）とその行だけが再開する。プロジェクトの画面で答えてもよい。
要対応「リトライ」（pending に戻す。試行回数は戻さないので、また失敗すれば再び要対応）か「スキップ」。ほかの行は進み続ける。
一時停止新しい行を始めない。実行中の行は続き、追跡も続く。Canon のある計画では push と PR の承認の反映も続く。キーが使えなくなったときや Canon が見つからないときは自動で一時停止し、理由を表示する。
再開止まったところから続ける（キーを確認し直す）。中止で止めた行は pending に戻ってプロジェクトの続きから作る。完了した行は作り直さない。
中止実行中の行のジョブとその Fargate タスクを止めて cancelled にし、新しいジョブを積まない。待っている行はそのまま。review・decision の行とその PR はそのまま残る（中止後も Canon で承認できる。再開すると再び追う）。中止した計画も再開できる。
削除下書き・完了・中止の計画を論理削除できる（下書き作成中は取り消してから）。作られたプロジェクトは残る。

6.13 同時実行数・モデル・費用

  • 同時実行数：管理者が管理者画面で、全体の上限と 1 人あたりの上限を 1〜16 で設定できます（空ならデプロイの値）。設定は Catalog テーブルの config / concurrency の項目（maxConcurrentJobs、maxConcurrentJobsPerUser、updatedAt、updatedBy）で、PUT /admin/concurrency は 1〜16 の整数か null 以外を拒みます。ディスパッチャー（Catalog の config を GetItem で読む）とランナーは 30 秒のキャッシュを通して読み、読めなければデプロイの値を使います。GET /config は効いている上限を返します。計画の実効の同時実行数は min(全体, 1 人あたり) です。1 回の実行は毎分約 14〜17 万トークンを使い、組織の gpt-6-luna の上限は毎分 20 万トークンなので、OpenAI のレート制限が実際の上限になることがあります。
  • 2 種類のモデル：オーケストレーターのモデルは計画自身のジョブ（下書き・再計画・行の PR の AI レビュー）に、エージェントのモデルと推論の強さは各行の BRA に使います。どちらも確定時に固定されます。計画用のジョブは推論の強さ medium の短い 1 ターンなので、行に比べれば費用はわずかです。
  • 見積もりと実績：見積もりは確定時に保存し（6.8）、計画の画面には「これまで」として、確定からの経過時間（完了・中止まで）と、行のプロジェクトの費用の合計を出します（既存のプロジェクトで済んだ行は数えない）。ジョブはほかのジョブと同じく記録・課金されます（承認済みの利用者はデフォルトの API キーで実行する）。
  • 費用：下書き・再計画・AI レビュー・Canon に合わせた更新は、すべて通常のジョブです（plan・canon-review・followup）。枠が空いたときだけ積み、枠より先には積みません。API とランナーは鍵を復号しません。同時実行数の枠を 1 つ使い、所有者のキー（またはデフォルトの API キー）で実行され、利用量と推定費用がジョブに記録されます。取り消し・時間切れのジョブも、それまでに使った分が記録されます。計画の画面には、確定からの経過時間と、行のプロジェクト・計画用のジョブ・計画の PR の AI レビューを合わせた費用（うち計画用のジョブの費用を別に）が出ます。
  • ジョブとプロジェクト：計画用のジョブはどのプロジェクトにも属しません（isProjectlessMode。Canon の AI レビューと同じ。projectId には計画 ID を入れる）。ディスパッチャーはチャットのメッセージを出さず、プロジェクトの状態も変えません。janitor はハートビートが途絶えたか 24 時間待機したジョブを、理由をつけて失敗にするだけで、リトライせず、プロジェクトにも触れません（ランナーがその後で下書き・再計画を失敗にする）。

6.14 排他制御と信頼性

  • リース：行の置き換え・CSV の読み込み・設定や Canon の変更・確定・下書きの依頼と取り消し・並べ替え・提案の判断・人の判断は、ランナーと同じ META のリースを取り（withPlanLease：250 ms 間隔で最大 6 回やり直す）、取れたら強い一貫性の読み取りで計画の状態を確かめ直します（行も一貫して読む）。リースを返すときは自分の時刻を書くので、古いリースの読み取りを空きと取り違えることはなく、行の書き込みの前には状態とリースがまだ保たれていることを条件で確かめます。別の変更やランナーがリースを持っていれば 409「計画を更新中です。少し待ってからやり直してください」で、何も変わりません。これにより、別のタブで行を編集しながら確定しても、確定後に行が変わることはありません（段階 1 の競合の修正）。名前や目標だけの変更は、段階 1 と同じく状態を条件にした 1 回の書き込みです。
  • 二重に作らない：行を始めるときは Project ID を予約してから状態を条件に行を確保し、確保とプロジェクトの作成の間で止まった行は、予約した ID のまま pending に戻します。更新（conform）の回数と新しい固定は行の確保と同時に書きます。
  • 結果を信用しない：計画用のジョブの result.json は、ランナーが使う前に必ず入力と照らして検証し直します。
  • 共通の関数：プロジェクトの作成・リトライ・停止・追加指示、Canon の作成・push・固定・AI レビュー・承認は、画面の API とランナーが同じ関数（lib/runs.ts・lib/canonOps.ts）を呼ぶので、計画から作ったプロジェクトも手で作ったものと同じ検査を通ります。

計画ランナーの AWS の権限（Plans・Users・Projects・Jobs・Messages・Canons テーブルの読み書き、Catalog の config の読み取りと ID の予約、S3 の plans/* と canons/* の読み書き、push と完成した行の uc.json のための users/*/workspace/* の読み取り。KMS は無く、鍵は復号できない）の詳細は第 7 部で扱います。
