6.8 自律実行での判断

新しく作る計画は、既定で自律実行で進みます（英語の画面では Autonomous run）。自律実行は計画の設定の 1 つで、Canon ではなく計画に付きます。考え方は「オーケストレーターが人の代わりに判断する」ことです。人が対応する計画（6.9）で所有者が行う判断を、自律実行ではオーケストレーターが行います。判断するのは、計画ランナーと、オーケストレーターのモデルで動く LLM のジョブです。

代わりに行う判断は、次の 5 つです。

  • 下書きの確定
  • エージェントの質問への回答
  • 計画が push した PR の承認・却下・変更の依頼
  • 要対応と要判断の行の扱い
  • 再計画の提案の承認

目標を渡せば、下書きから Canon への取り込みまで、人の操作なしに進みます。止まるのは費用の上限に達したときだけで、時間や行の数の上限はありません。PR の承認や衝突に人が対応する進め方は、所有者がオンにするオプションです（6.9）。

AI に任せないこと

自律実行でも、次の線はプログラムが守ります。LLM の答えがどうであっても、この線を越えることはありません。

人を待つ場面との対応

エージェントの質問質問箱で回答を待つエージェントは同じように質問できる。オーケストレーターが質問を読んで個別に答える（回答のジョブ。回数の上限なし）

自律実行で判断に使う LLM のジョブは 3 種類です。1 つの行の質問に答える回答のジョブと、要対応・要判断の行の扱いを選ぶ解決のジョブをまとめて行のジョブと呼びます。PR の扱いを決めるのは判断のジョブです。

設定

  • 費用の上限：1〜1000 USD の範囲で決めます。指定しなければ 20 USD です。
  • 始め方：自律実行の計画は、必ず下書きの作成から始めます。Canon を指定しなければ、計画の名前で新しい Canon を作る選択になります。
  • 変更：下書きの間は、自律実行のオン・オフと上限を変えられます。確定後は変えられません。上限を上げるときは再開の操作で行います（下の「費用の上限」）。
  • 新しい計画の画面：フォームの先頭に「自律実行」の区切りがあり、既定で費用の上限の欄と「自律実行で開始」のボタンが出ます。説明は見出しと上限の欄の (?) に置き、本文には出しません。その下の副次のチェックボックス「PR の承認や衝突にご自身で対応する」をオンにすると自律実行を使わず、ボタンは「計画を作る」「下書きを作成」に変わります（6.3）。
  • 下書きの画面：「3. 進め方」の一番上に、同じ並びの「自律実行」のカードがあります。見出しと (?) の説明、自律実行のときの上限の欄、その下の同じチェックボックスです（6.9）。
  • 表示：計画の一覧と計画の画面に「自律実行」の印が付き、確定後の設定には「自律実行: 費用の上限 $n」が出ます。

下書きと確定

  1. 下書き：人が対応する計画と同じく、計画用のジョブが方針・行・アンカー・依存を書きます（6.4）。ジョブが失敗したときは、1 回だけ自動で依頼し直します。キーがないなど所有者の側の理由で始められないときは、やり直さずに下書きに戻します。
  2. 確定：下書きを適用すると、ランナーがその処理を終えた直後に、所有者の確定と同じ処理で確定します（6.9）。計画が別の処理で使われていて確定できなければ、次の分にもう一度試します。ほかの理由で失敗したときは理由を残し、画面に「自律実行で下書きを確定できませんでした: …。内容を確かめて「確定して開始」を押してください。」と出します。所有者が手で確定すると、この表示は消えます。
  3. 後から切り替えた計画：下書きができたあとで自律実行に切り替えた計画は、自動では確定しません。所有者が確定すると、そこから自律実行で進みます。

行のジョブに共通の性質

回答のジョブと解決のジョブは、どちらも下書き・再計画と同じ種類の計画用のジョブです。次の性質を持ちます。

  • 同時実行数の枠を 1 つ使い、オーケストレーターのモデルと所有者のキーで動きます。推論の強さは medium です。費用は計画の費用に入ります。
  • 入力には、計画の名前・目標・方針（5 項目）、Canon の名前と粒度方針、行の情報、プロジェクトの情報が入ります。行の情報は、ROI・TLF・理由・バッチ・基準プロジェクトかどうか・アンカー・依存する行です。プロジェクトの情報は、状態・質問・最後のエラーと、判断ログ decision_log.md の末尾 12,000 字です。解決のジョブでは、状況と選択肢も入ります。
  • ワーカーは、指示書 prompts/orchestrator.md（付録 B）と入力をモデルに読ませ、ツールも Web 検索も使わない 1 ターンで、種類ごとに決まった形で答えさせます。形が違えば 1 回だけ頼み直します。時間の予算は、ワーカーの開始から 5 分です。超えると打ち切り、ジョブは失敗します。
  • 1 つの行で同時に動く行のジョブは 1 件だけです。
  • 失敗した・止められた・結果が読めないジョブは、間をおいて依頼し直します。待つ時間は 1・2・4…分と倍に延び、最大 60 分です。回数の上限はありません。キーの残高切れのように費用のかからない失敗が続いても、毎分ジョブを起こすことはありません。行には失敗の回数とエラーが出ます。成功すると記録を消します。
  • ジョブの間に行が別の状態に移ったとき（所有者が先に答えた・決めたとき）は、結果を使わずに捨てます。

質問への回答

  • エージェントの質問：自律実行でも、行のエージェントは人が対応する計画と同じように質問できます。
  • 依頼：質問中の行に回答のジョブを依頼します。ランナーが行を始める前に、空き枠があるときだけ、ほかのジョブより先に依頼します。
  • 答え方：所有者として決めて、はっきり答えます。聞き返したり、選択肢を並べたりはしません。根拠が支えるならエージェントの推奨を採り、そうでなければ次の条件を満たすものを選びます。
    • ROI・TLF をそのまま保つ
    • Canon の定義と、計画の方針（範囲・粒度・根拠）に合う
    • 最も保守的で、あとで直しやすい
    決めたことは判断ログに残すよう、エージェントに伝えます。答えは回答の本文と理由の 2 つです。
  • 渡し方：ジョブが終わると、次の空き枠で回答を渡します。再開したプロジェクトのジョブが枠を 1 つ使うためです。渡すのは、ジョブが読んだ質問と、現在プロジェクトが待っている質問が同じときだけです。人の回答と同じ処理で渡し、ジョブの状態を条件にして書くので、人の回答と二重になることはありません。
    • エージェントが受け取るのは回答と理由で、「Answer from the CoBRAC Orchestrator (it decides for the user in this autonomous run)」という見出しが付きます。
    • 行は実行中に戻り、AI が答えた回数が 1 増えます。行の画面には「AI の回答 n 回」と出ます。
    • 計画の履歴に、回数・ジョブ・回答と理由の冒頭が残ります。
    • プロジェクトのエージェント欄には「オーケストレーター（AI）がエージェントの質問に回答しました。」と、質問と回答が出ます。
  • 回数の上限はありません。同じ行が質問を繰り返しても答え続けます。止めるのは費用の上限だけです。

要対応と要判断の解決

  • 依頼：要対応と要判断の行に、解決のジョブを依頼します。ただし、計画の Canon が見つからないために要判断になった行は除きます。その場合は所有者が決め、計画は一時停止します。入力の状況には次のものが入ります。
    • 状態・理由・エラー
    • 自動リトライの回数、オーケストレーターがこれまでにリトライを選んだ回数、前回の解決、フォローアップの回数
    • PR の番号・状態・メモ
    • 選択肢：要対応は「リトライ」（プロジェクトが削除されていればなし）と「スキップ」。要判断は「完了にする」「もう一度 push」（プロジェクトが完成しているときだけ）「スキップ」
  • 選び方：指示書は次の基準を示します。計画の方針の「判断」と「優先」が当てはまればそれに従い、理由にそう書きます。迷ったら、失敗を繰り返す行はスキップします。答えは行動と理由の 2 つです。
    行動選ぶとき
    リトライ一時的な失敗（時間切れ、レート制限、ワーカーの消失、形式の誤り）
    スキップ同じ失敗を繰り返す。プロジェクトが削除された。PR が Canon に合わない。費用に見合わない
    完了にする完成していて計画に役立つが、Canon には取り込めない
    もう一度 push原因がなくなった
  • 反映：所有者のボタンと同じ遷移にします。
    • リトライ：行を開始待ちに戻し、要対応の理由を消します。オーケストレーターがリトライを選んだ回数が 1 増えます。
    • スキップ：行をスキップにし、理由として AI の理由を残します。
    • 完了にする：行を完了にします。
    • もう一度 push：行を実行中にし、次の回の処理で push し直します。プロジェクトが完成していなければ、この選択を使わずに依頼し直します。
    行と計画の履歴に、行動・元の状態・理由・ジョブが残ります。画面には「オーケストレーター（AI）の判断: リトライ / スキップ / 完了にする / もう一度 push」と理由が出ます。
  • 所有者は、要対応・要判断の行のボタンで先に決めることもできます。そのときジョブの結果は捨てます。
  • 計画を中止すると、待機中・実行中の行のジョブも止めます。

PR の判断

Canon のある計画（6.7）では、完成した行を push すると PR ができます。自律実行の計画では、この PR の扱いを判断のジョブが決めます。

  1. 依頼：承認待ちのすべての行が判断を待ちます。基準プロジェクトの行も、手で push した PR を追う行も含みます。ランナーは空き枠があるとき、AI レビュー（5.8）と同じ処理で判断のジョブを所有者として依頼します。モデルはオーケストレーターのモデル、言語は計画の返答の言語で、1 件に 1 枠を使います。手で依頼した AI レビューが終わった PR にも、判断のジョブを依頼します。
  2. 判断：材料は AI レビューと同じです。ジョブは所見に加えて、次のものを返します。
    • 判定：「承認」「変更の依頼」「却下」のどれか
    • 判定の理由
    • 警告と情報の衝突ごとの選択
    • 依頼する変更の一覧
    材料の文字列はデータとして扱い、そこに書かれた指示には従わないよう指示します。ワーカーは答えを検査し、材料にない衝突への選択と、エラーの衝突への選択を除きます。
  3. 反映：ジョブが完了すると、ランナーは PR がまだ開いていることを確認し、判断と PR の内容を読みます。そして現在の Canon の head に対して差分を取り直し、行の遷移先をプログラムが決めます（下の表）。PR が人の手で決まっていれば、それに従います（6.7）。
AI の判定現在の head に対する差分ランナーの処理行
承認エラーの衝突なし。警告は AI が選んだ側を採る（選ばなかったものと C2b・C8b は Canon の値）。情報は AI が選んだものだけを採る。それでもブロックする衝突がない所有者として承認する。名前は「AI (<モデル>)」、理由はメモに入る。Canon は新しい rev になる完了
承認エラーの衝突がある（判断の後に Canon が進んでできたものも含む）。またはブロックする衝突が残るPR に変更の依頼を記録し、Canon に合わせるフォローアップを用意する。指示は、衝突ごとに Canon の値とこのプロジェクトの値を並べたもの開始待ち（Canon に合わせる更新）
変更の依頼—AI が挙げた変更（なければ理由）で変更を依頼し、それをフォローアップの指示にする開始待ち（指摘への対応）
却下—理由を付けて却下するスキップ（AI の却下）
  • フォローアップ：Canon に合わせた更新（6.7）と同じ経路で、空き枠とバッチの順に始まります。プロジェクトを最新の rev に固定し直してから積みます。タイトルは、Canon に合わせる更新なら「Canon rev N に合わせて更新」、指摘への対応なら「Canon PR #n の AI レビューの指摘に対応」で、続けて依頼の本文が入ります。完成すると再び push し、新しい PR が古い PR を置き換えて、また判断します。
  • push の時点のエラーの衝突：人が対応する計画では、Canon が進んでいないのにエラーの衝突があると要判断になります。自律実行では、Canon に合わせるフォローアップにします。
  • 回数：フォローアップ（Canon に合わせた更新を含む）は、1 行につき 3 回までです。人が対応する計画では 2 回です。超えるとその行は要判断になり、解決のジョブが「完了にする」「もう一度 push」「スキップ」から選びます。
  • 判断のジョブの失敗：判断のジョブが失敗したとき、または結果が読めないときは、行のジョブと同じ間隔をおいて、上限なしで依頼し直します。
  • 競合：承認の途中で別の承認が Canon を進めたときは、次の回の処理で新しい head に対してもう一度反映します。
  • 記録：承認・却下・変更の依頼は Canon の所有者のアカウントで行い、名前は「AI (<モデル>)」になります。判断したジョブとモデルが、PR・承認・履歴・rev に残ります（5.8）。PR の画面の「AI レビュー」には「AI の判断」として、「AI が承認」「AI が変更を依頼」「AI が却下」のどれかと、理由、依頼した変更が出ます。人が依頼する AI レビューは判定を出しません。

再計画の提案

再計画のジョブ（6.6）が出した「行の追加」「行の削除」の提案を、ランナーは結果を保存したその場で反映します。提案は最新の内容を読み直してから反映し、ジョブを「済み」にするのは反映のあとです。途中で止まった処理は、次の回に同じ提案を保存し直して反映します。反映には所有者の承認と同じ処理を使い、画面では「オーケストレーターが反映」と出ます。反映できない提案は、古くなった提案として扱います。たとえば次のときです。

  • 同じ ROI × TLF の行がすでにある
  • 外す行がもう始まっている
  • 行が 200 行に達している

方針の変更は、人が対応する計画と同じく承認なしで反映します。

費用の上限

費用の上限の規則は、本節の記述が正本です。

  • 数える費用（推定の USD）：
    • 各行のプロジェクトの費用。既存のプロジェクトで済んだ行は数えません。
    • 計画用のジョブ（下書き・再計画・行のジョブ）
    • この計画の PR についての AI レビューと判断のジョブ
  • 費用の予約（フロー実行の計画）：行を始める前に、上限からこれまでの費用と、作っている行 1 件につき 0.5 行分を引き、その残りに収まる数だけ行を始めます。1 行の費用は、完了した行が 5 件になるまでは $0.39（見積もりの上限）、その後は完了した行の費用の 75 パーセンタイルです。作っている行がなければ、残りが 1 行分に満たなくても 1 行は始めます。
  • 上限に達したとき：ランナーは毎回の処理で費用を確認し、初めて上限に達したときに、その時刻と費用・上限を記録します。それ以降は新しい行・フォローアップ・解決のジョブ・再計画を始めません。実行中の行は最後まで進み、その質問への回答と PR の判断も続きます。動いているもの（開始中・実行中・質問中の行、判断を待つ PR、行のジョブ）がなくなると、計画は一時停止します。画面には「一時停止中: 自律実行の費用の上限に達したため、新しい行を始めていません。上限を上げると再開できます。」と出ます。要対応・要判断の行は、そのまま再開を待ちます。実行中の行が最後まで進むので、費用は上限を少し超えることがあります。
  • 再開：新しい上限を指定して再開します。新しい上限は 1〜1000 USD で、これまでの費用より大きくなければなりません。上限に達して止まった計画を、新しい上限なしで再開することはできません。画面では、一時停止の帯の下に「新しい費用の上限」の欄と「上限を上げて再開」が出ます。

実装

  • 設定：PlanSettings.autonomous = { maxCostUsd }。作成は POST /plans に autonomous: { maxCostUsd? } を付け、draft: true が必要です（なければ 400）。範囲は AUTONOMOUS_MAX_COST_RANGE、既定は AUTONOMOUS_DEFAULT_MAX_COST_USD。canon を省くと { mode: "new", name }。下書きの間の変更は PUT /plans/{id} { settings: { autonomous: { maxCostUsd } | null } }。Web は、チェックボックスがオンなら autonomous を送らず（下書きの画面では autonomous: null）、オフなら { maxCostUsd } を送ります。API は autonomous を付けた依頼だけを自律実行の計画にします。
  • 下書きと確定：下書きのやり直しは PlanJobState.attempt。適用時に下書きの状態へ autoConfirm: true を付け、Lambda のハンドラー（handlers/planRunner.ts の autoConfirm）が、その処理が計画のリースを返した後に confirmPlan で確定します（confirmedBy: "runner"）。ハンドラーは毎分、確定を待つ自律実行の下書きを探します。失敗の理由は autonomousError。
  • 行のジョブ：plan のジョブで、planJobKind は answer / resolve、planRowId に行を持ちます。入力 PlanRowJobInput は plans/{planId}/jobs/{jobId}/input.json、答えは同じ場所の result.json。打ち切りは PLAN_ROW_JOB_TIME_BUDGET_MS、文字数の上限は PLAN_ROW_JOB_LIMITS。ランナーは parsePlanRowResult で検査し直します。同時に 1 件の制約は row.rowJob = { kind, jobId, status, requestedAt }、依頼し直しの記録は row.orchestratorRetry（回数・最後のエラー・次に依頼できる時刻）、間隔は orchestratorRetryDelayMs。
  • 回答：ジョブが終わると rowJob.status を ready にし、answerQuestion（source: "auto"）で渡します。見出しは answerPreamble、出力は { answer, reason }。行は running に戻り autoAnswers が増え、イベント row_auto_answered が残ります。
  • 解決：除外の条件は lastError が「The plan's Canon was not found.」の行。選択肢は planRowOptions（retry / skip、done / push / skip）、状況には orchestratorRetries・previous が入ります。出力は { action, reason }。反映は applyResolution で、retry → pending（aiRetries を 1 増やす）、skip → skipped（autoSkip.reason = "ai_skipped"、error に AI の理由）、done → done、push → running。行に aiResolution = { action, reason, at, jobId }、イベント row_ai_resolved。中止では stopPlanJob で行のジョブを止めます。
  • PR の判断：行は aiReview: "wanted"。requestAiReview を kind: "decide"・planId 付きで呼び、canon-review のジョブ（reviewKind: "decide"）を積み、行の decideAttempts を 1 増やします。材料は buildCanonAiPacket、指示は canonAiDecisionPrompt、スキーマは CANON_AI_DECISION_SCHEMA（verdict は approve / request_changes / reject）。ワーカーは parseCanonAiDecision で検査し、result.json の decision に書きます。反映は applyDecision と decisionAction（エラーの衝突への incoming の選択も除く。選ばれなかった警告は canon）。承認は approvePullRequest、変更の依頼は requestPrChanges、却下は rejectPullRequest。Canon に合わせる指示は canonFixInstruction、フォローアップは queueFollowup で、row.followup.kind は fix / changes。却下の行は autoSkip.reason = "ai_rejected"。push の時点の扱いは pushOutcome(…, { autonomous: true }) → { to: "conform", fix: true }。回数の上限は AUTONOMOUS_MAX_FOLLOWUPS（人が対応する計画は MAX_CONFORM_FOLLOWUPS）、超えたときの理由は conform_limit。競合は race。名前は aiActorName、記録は via = { kind: "ai", jobId, model } で、PR の decidedVia・承認の approvals[].via・履歴の via: "ai"・rev の approvedVia に残ります。イベントは row_ai_decided・row_done。
  • 再計画の提案：applyProposals が強い一貫性で読み直し、所有者の承認と同じ applyProposal で反映します（決めた人は runner、イベント proposal_accepted の by: "runner"）。反映できない提案は stale。
  • 費用の上限：費用は planSpendUsd、判定は costLimitReached。費用の予約は rowsWithinCost、1 行の費用は perRowCostUsd（packages/shared/src/planFlow.ts）。達した時刻は costLimitAt、イベント cost_limit_reached、一時停止の理由は pausedReason: "cost_limit"。再開は POST /plans/{id}/resume { maxCostUsd }。範囲外やこれまでの費用以下なら 400、上限に達した計画を maxCostUsd なしで再開しても 400。再開すると costLimitAt を消し、イベント cost_limit_raised を残します。

行と計画が持つ自律実行の項目と、イベントの一覧は 6.12 に記載しています。

6.9 人が対応する計画

新しい計画の画面でチェックボックス「PR の承認や衝突にご自身で対応する」をオンにすると、自律実行を使わない人が対応する計画になります。この計画では、6.8 でオーケストレーターが行う判断を所有者が行います。所有者は下書きの行とバッチを整えて確定し、エージェントの質問に答え、要対応の行を扱います。PR の承認は Canon の PR の画面で（5.8）、要判断の行は計画の画面のカードで（6.7）、再計画の提案は計画の画面で（6.6）決めます。

下書きを整える画面と確定の処理は、自律実行の計画でも使います。自動の確定に失敗したときと、下書きができたあとで自律実行に切り替えたときは、所有者がこの画面で確定します（6.8）。

下書きの画面

下書きの計画の画面は、上から次の 4 つの区切りに分かれます。進捗・バッチ・時間・費用のカードは、確定したあとだけ出ます。「計画を削除」は一番下にあります。

  1. 作るもの
    • 目標を書き直せます。欄を離れると保存します。
    • 資料ファイルを追加・削除できます。できるのは下書きのときだけで、下書きの作成中や確定後はできません。資料は計画と合わせて 10 個までです。
      • 追加した CSV・TSV・テキストは、作成時と同じくすぐ行として読みます。読めない行は一覧で示し、自動の順序なら並べ直します。
      • xlsx・PDF は次の下書きのジョブが読みます。
      • ファイルの ID（f1・f2…）は、計画がこれまでに持ったファイルの数の次から振ります。削除したファイルの番号は使い直しません。
      • 追加・削除のたびに、資料から取り出した文章の目録を消します。次の下書きのジョブが、現在の資料から取り出し直すためです。
      • 資料を削除しても、その資料から読んだ行は残ります。
    • 「下書きを作成」（行がないとき）か「下書きを作り直す」（現在の行は残る）を押せます。押せないときは、その理由が横に出ます。
    • 下書きのジョブの状態、読めなかった項目、方針（読むだけ）もここに出ます。
  2. 行とバッチ
    • 行はバッチごとの表で出ます。基準プロジェクトのバッチの見出しには「基準プロジェクト」の印が付きます。
    • 各行に ROI と TLF の欄、アンカーと関係の要約、上下の移動と削除があります。行を開くと、理由・バッチ・アンカー・「作り直す」・既存のプロジェクト・重複の注意が出ます。
    • 変更した行と足した行には色が付きます。保存していない変更があるときだけ、「保存していない変更が N 件あります」と「元に戻す」「行を保存」が出ます。
    • 行が 0 件のときは、「まだ行がありません」の案内と「行を追加」「CSV を読み込む」が出ます。
    • 「N 件ずつのバッチに分ける」は「その他の操作」の中にあります。
  3. 進め方：上から順に次のものが並びます。
    • 自律実行：見出し「自律実行」（説明は (?)）、自律実行のときの費用の上限の欄（範囲の説明は (?)）、その下の副次のチェックボックス「PR の承認や衝突にご自身で対応する」
    • Canon：「なし／既存の Canon／新しい Canon」の切り替えと、Canon の選択または名前
    • モデル：オーケストレーター・エージェント・推論の強さの 3 列。API キーの注記は 1 回だけ出ます。
    • 調査モード
  4. 確定して開始：見積もり（時間と費用）が出ます。押せないときは理由が横に出ます。理由は、行が 0 件、保存していない変更がある、下書きの作成中、のどれかです。

画面の上の帯には、状況に応じて次の文が出ます。

  • 行が 0 件の下書き：「まだ何も入っていません。目標を書いて「下書きを作成」を押すか、行を追加してください。確定するまでプロジェクトは 1 件も作られません。」
  • 下書きのジョブが終わったあと：「下書きができました。行とバッチを確かめて「確定して開始」を押してください。…」

行とバッチの編集

  • 編集：下書きの間は、行の追加・削除・並べ替えと、ROI・TLF・理由・バッチの変更ができます。「N 件ずつのバッチに分ける」は、現在の並び順のまま、同時に実行できる数 N ずつに分けます。
  • 自動の順序：「自動で並べる」は、現在の行で実行順序の計算（6.5）をやり直し、自動の順序にします。ジョブは使わないので無料です。下書きの直後も自動の順序です。
  • 手動の順序：行を保存するときに、行を足す・消す・入れ替える・バッチを変えると、手動の順序になります。手動の順序では所有者のバッチがそのまま使われ、バッチごとの並べ直しと再計画（6.6）もしません。作る行の中で、自分のバッチに 1 行だけでなくなった基準プロジェクトは、基準プロジェクトの印を失います。
  • 順序の種類を保つ保存：同じ行を同じ順番とバッチのまま保存するとき（理由・ROI・TLF・「作り直す」だけの変更）は、順序の種類を保ちます。自動の順序のまま「作り直す」や既存のプロジェクトが変わったときは、同じ保存の中で並べ直します。ID を保った行は、アンカー・依存・基準プロジェクトの印・既存のプロジェクト・重複の注意を保ちます。新しい行と、ROI × TLF を変えた行は、所有者のプロジェクトと照合し直します。
  • CSV の読み込み：自動の順序の下書きでは、全体を並べ直して自動の順序のままにします。手動の順序の下書きでは、行を末尾に足します。
  • 既存のプロジェクト：同じ ROI × TLF で、完成して成果物のある自分のプロジェクトがあれば、行に「既存」とリンクが付きます。比べるときは大文字と小文字、空白を区別せず、削除したプロジェクトは数えません。既存の行は最後のバッチに並び、確定すると作らずに完了になります。見積もりにも費用にも入りません。確定までにそのプロジェクトを削除したときは、行は作られます。同じ ROI × TLF でまだ完成していないプロジェクトがあるときは、注意とリンクが出るだけで、確定すると別に作ります。
  • 作り直す：既存のプロジェクトがあっても作りたい行は、編集画面で「作り直す」に印を付けて保存します。既存のプロジェクトは外れて行が作られます。この選択は行に残るので、下書きを作り直しても「既存」に戻りません。印を外して保存すると元に戻ります。
  • 設定：オーケストレーターのモデルは、計画用のジョブ（下書き・再計画・行のジョブ）と、計画の PR の AI レビュー・判断のジョブに使います（6.11）。エージェントのモデルと推論の強さは各行の BRA に使います。調査モードの既定はオンです。どちらのモデルも「デフォルト」を選ぶと、確定時に設定のデフォルトのモデルに決まります。方針はオーケストレーターが書くもので、所有者は編集できません。
  • Canon：「なし」「既存の Canon」「新しい Canon」から選びます。既存の Canon は自分が所有するものだけで、共同編集者として参加している Canon は選べません。新しい Canon の名前の初期値は計画の名前です（6.7）。

確定

「確定して開始」を押すと、見積もりを確認してから開始します。確定では次のことを行います。

  1. 確認：行が 1 つ以上あること、所有者がジョブを実行できるキーを持つこと、選んだ各モデルを所有者の利用承認が許すことを確認します。Canon のある計画では、選んだ既存の Canon がまだ所有者のものであることも確認します。
  2. 固定：次のものを確定時の値に固定します。後のデプロイでハーネスのルールが新しくなっても、計画の行はすべて確定時のルールで作られます。
    • オーケストレーターのモデル
    • 各行のエージェントのモデル（選んだもの。なければ所有者かデプロイの既定を、利用承認に通したもの）
    • 推論の強さ、調査モード、返答の言語（UI の言語）
    • ハーネスのルール
  3. 既存の再確認：既存のプロジェクトがある開始待ちの行について、そのプロジェクトがまだ削除されず、成果物付きで完成しているかを確認し直します。外れていれば照合し直し、なければ作ります。
  4. 並べ直し：自動の順序の計画は、その時点の実効の同時実行数でもう一度並べます。既存のプロジェクトで済む行は、そのプロジェクトを結果として完了にします（Canon のある計画の扱いは 6.7）。
  5. Canon：「新しい Canon」を選んでいれば、ここで作ります。計画の方針の「粒度」を粒度方針にした、非公開で空の rev 0 の Canon です。
  6. 開始：実行の仕方と見積もりを保存して、計画を実行中にします。実行の仕方は、自動の順序ならフロー実行、手動の順序ならバッチごとです（6.5）。そのあとランナーを 1 回すぐに動かします。最初の行が、次の分を待たずに始まります。

確定は計画のリースの中で行うので、別のタブで行を編集していても、確定後に行が変わることはありません（6.12）。自律実行の計画は、下書きを適用した直後にランナーが同じ処理で確定します（6.8）。

見積もりの計算式

時間 ≒ 基準プロジェクトの数 × 48 分（1 件ずつ）＋ Σ 本体のバッチ ⌈バッチの行数 ÷ 同時実行数⌉ × 48 分 ＋ 行の 20% × 15 分（手直し）÷ 同時実行数。費用 ≒ 行数 × $0.18〜0.39。既存・スキップの行は除き、質問への回答や PR の承認を待つ時間は含みません。

フロー実行の計画（自動の順序の下書きを含む）の時間は、この式の前の 2 項の代わりに、6.5 のシミュレーションの時間を使います。手直しの項と費用は同じです。

例：141 行（基準プロジェクト 3 行、残りを 1 バッチ）なら、同時実行数 1 で約 120 時間、4 で約 32 時間、8 で約 18 時間、12 で約 13 時間、16 で約 10 時間です。

質問と要対応

場面扱い
質問箱エージェントが質問すると、その行だけが止まり、計画の画面の質問箱に出る。答えるとその行だけが再開する。答えの扱いはプロジェクトの画面で答えたときと同じで、プロジェクトの画面で答えてもよい
要対応「リトライ」か「スキップ」を選ぶ。リトライは行を開始待ちに戻すが、試行の回数は戻さないので、また失敗すれば再び要対応になる。ほかの行は進み続ける

実装

  • 作るもの：目標は PUT /plans/{id} { goal }。資料の追加は POST /plans/{id}/attachments { attachments }（POST /uploads で上げたもの）、削除は DELETE /plans/{id}/attachments/{fileId}。下書きでないときは 409。ファイル番号の基準は attachmentSeq、消す目録は attachments/derived/manifest.json。
  • 順序：「自動で並べる」は POST /plans/{id}/order（DRAFT のときだけ）で、orderDraft をやり直して ordering: "auto" にします（イベント ordered）。行の保存は PUT /plans/{id}/rows、手動の順序は ordering: "manual"。行の ID は rowId。CSV の読み込みは POST /plans/{id}/rows/import。
  • 既存と作り直し：照合は matchExistingProject、結果は existing = { projectId, name }、未完成のプロジェクトへの注意は duplicateOf。「作り直す」は rebuild: true / false。
  • 方針：PUT /plans/{id} で送ると 400「方針はオーケストレーターが決めます」。
  • 確定：POST /plans/{id}/confirm。キーがなければ 400、モデルを利用承認が許さなければ 403、既存の Canon が所有者のものでなければ 409。固定するハーネスのルールは harnessRules。既存の再確認で外れた行は、confirmed のイベントに existingGone として数えます。既存で済む行は done（projectId = そのプロジェクト、completedAt）。実行の仕方は scheduling（flow / waves。すでに決まっていればそのまま）、見積もりは planEstimateFor（バッチごとは planEstimate・estimatePlan、フロー実行は simulateFlowMinutes）で保存し、状態を RUNNING にします。
  • 質問と要対応：計画の画面で答えると POST /projects/{id}/answer と同じ処理になります。要対応のリトライは行を pending に戻します。

6.10 計画の一覧と操作

計画の一覧

計画の一覧は、計画が現在何をしているかを見る画面です。サイドバーの「CoBRAC オーケストレーター」から開きます。実行中・一時停止・下書き作成中の計画があるあいだは、見出しの横に「ライブ」が出て、15 秒ごと（下書き作成中は 5 秒ごと）に自動で読み直します。タブが裏にあるあいだは読み直しません。

欄内容
あなたの番すべての計画から、所有者の操作を待っているものを先頭にまとめる。質問・承認待ち・要判断・要対応の行、再計画の提案、所有者以外の理由で止まった計画、確定を待つ（または失敗した）下書き。押すとその計画を開く。実行中の自律実行の計画の行は出さない（オーケストレーターが決めるため）。何もなければ「いま、あなたの操作を待っているものはありません」
動いている計画実行中・一時停止・下書き作成中の計画を、横長のレーンで出す。レーンには次のものが並ぶ：完了数、現在のバッチ、経過時間と見込み、費用（実績と見積もり）、バッチごとの進捗バー、現在作っている行とその段階と経過時間、最近の動き（直近 4 件）
下書き・終わった計画下書きはカード、完了・中止した計画は折りたたんだ一覧
新しい計画右から開くパネル（Esc か背景で閉じる）。計画が 1 つもないときは、作成のフォームが画面に出ている

進捗バーの色は、完了が緑、作っている行が流れる青、質問・判断が黄、承認待ちが紫、要対応が赤です。現在のバッチは枠で囲みます。フロー実行の計画では、進捗バーをレーンごとに区切ります。自律実行の計画には、一覧でも「自律実行」の印が付きます。

「新しい計画」のパネルには、名前・目標・資料の欄と、「自律実行」の区切りがあります（6.3）。

  • 資料：ファイルか、行の貼り付けです。ファイルは外せるチップで表示します。CSV・TSV・テキストはすぐ読み、xlsx・PDF は下書きのジョブが読みます。
  • 自律実行の区切り：見出しと費用の上限の欄があり、説明は (?) に置きます。その下に副次のチェックボックス「PR の承認や衝突にご自身で対応する」があります。
  • ボタン：既定は自律実行で、「自律実行で開始」の 1 つのボタンです（6.8）。チェックボックスをオンにすると、「計画を作る」「下書きを作成」の 2 つのボタンになります。「下書きを作成」は、作ると同時に下書きを依頼します。どのボタンも、押すと計画を開きます。目標・資料・行のどれもないときは、どのボタンも押せません。

6.11 同時実行数・モデル・費用

  • 同時実行数：管理者が管理画面で、全体の上限と 1 人あたりの上限を 1〜16 で設定します。計画の実効の同時実行数は、この 2 つの小さい方です。フロー実行の計画では、オーケストレーター自身の AI のジョブはその 3 分の 1 までです（6.6）。設定の保存先と読み方、OpenAI の TPM との関係は 8.3 に記載しています。
  • 2 種類のモデル：オーケストレーターのモデルは、計画用のジョブ（下書き・再計画・行のジョブ）と、計画の PR の AI レビュー・判断のジョブに使います。エージェントのモデルと推論の強さは、各行の BRA に使います。どちらも確定時に固定されます（6.9）。計画用のジョブは推論の強さ medium の短い 1 ターンなので、行に比べれば費用はわずかです。
  • 見積もりと実績：見積もりは確定時に保存します（6.9）。計画の画面には「これまで」として、確定からの経過時間（完了・中止まで）と、費用の合計が出ます。費用は、行のプロジェクト・計画用のジョブ・計画の PR の AI レビューを合わせたもので、うち計画用のジョブの費用を別に示します。既存のプロジェクトで済んだ行は数えません。
  • 費用の記録：下書き・再計画・行のジョブ・AI レビュー・判断のジョブ・Canon に合わせた更新は、すべて通常のジョブです。枠が空いたときだけ積み、枠より先には積みません。どれも同時実行数の枠を 1 つ使い、所有者のキー（またはデフォルトの API キー）で実行され、使用量と推定費用がジョブに記録されます。取り消し・時間切れのジョブも、それまでに使った分が記録されます。API とランナーは API キーを復号しません。
  • 費用の上限：自律実行の計画の費用の上限は 6.8 に記載しています。
  • ジョブとプロジェクト：計画用のジョブは、どのプロジェクトにも属しません。Canon の AI レビューと同じ扱いです。ディスパッチャーはこのジョブについてチャットのメッセージを出さず、プロジェクトの状態も変えません。janitor は、ハートビートが途絶えたか 24 時間待機したジョブを、理由を付けて失敗にするだけです。リトライはせず、プロジェクトにも触れません。そのあとでランナーが、下書きや再計画を失敗として扱います。

実装

ジョブの種類は plan（計画用のジョブ）、canon-review（AI レビューと判断）、followup（Canon に合わせた更新）です。計画用のジョブはプロジェクトのないモード（isProjectlessMode）で、projectId には計画 ID を入れます。

排他制御と信頼性

  • リース：次の変更は、ランナーと同じ META のリースを取ってから行います（withPlanLease。250 ms 間隔で最大 6 回やり直す）。
    • 行の置き換え、CSV の読み込み、設定や Canon の変更、確定
    • 下書きの依頼と取り消し、並べ替え
    • 提案の判断、要判断の行の扱い
    リースが取れたら、強い一貫性の読み取りで計画の状態を確認し直します（行も一貫して読む）。リースを返すときは自分の時刻を書くので、古いリースの読み取りを空きと取り違えることはありません。行を書き込む前には、状態とリースがまだ保たれていることを条件にします。別の変更やランナーがリースを持っていれば、409「計画を更新中です。少し待ってからやり直してください」を返し、何も変えません。これにより、別のタブで行を編集しながら確定しても、確定後に行が変わることはありません。名前や目標だけの変更は、状態を条件にした 1 回の書き込みです。
  • 二重に作らない：行を始めるときは、Project ID を予約してから、状態を条件に行を確保します。確保とプロジェクトの作成の間で止まった行は、予約した ID のまま pending に戻します。更新（conform）の回数と新しい固定は、行の確保と同時に書きます。
  • 結果を信用しない：計画用のジョブの result.json は、ランナーが使う前に必ず入力と照らして検査し直します。
  • 共通の関数：画面の API とランナーは、次の処理に同じ関数（lib/runs.ts・lib/canonOps.ts）を使います。そのため、計画から作ったプロジェクトも、手で作ったものと同じ検査を通ります。
    • プロジェクトの作成・リトライ・停止・フォローアップ
    • Canon の作成・push・固定・AI レビュー・承認

計画ランナーの AWS の権限は 9.1 に記載しています。概要は次のとおりです。Plans・Users・Projects・Jobs・Messages・Canons テーブルの読み書き、Catalog の config の読み取りと ID の予約、S3 の plans/* と canons/* の読み書き、push と完成した行の uc.json のための users/*/workspace/* の読み取りです。KMS の権限はなく、API キーを復号できません。
