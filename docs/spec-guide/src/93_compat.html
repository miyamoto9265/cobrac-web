付録 C

古いプロジェクトの扱い

本文には現行の仕様だけを書いています。この付録では、以前のバージョンのアプリで作られたプロジェクト・Canon・計画・ジョブの記録を、いまのアプリがどう扱うかをまとめます。新しく作るものには関係しません。古いデータを読む開発者と、古いプロジェクトについて問い合わせを受けた運用者に向けた付録です。変化の理由と経緯は付録 D にあります。

作られたときの規則既存のプロジェクトは、作成時に保存した印に従って検査し続けます。フォローアップでも複製でも変わりません。
保存データは書き換えない古い形の名前や記録は、DynamoDB と S3 の上ではそのまま残します。
読むときに直す比べるときや表示するときに、現在の形へ読み替えたり、値を補正したりします。

C.1 基本の考え方

検査の規則や名前の形は、バージョンを重ねるあいだに何度か変わりました。CoBRAC は既存のプロジェクトを、原則として作られたときの規則で検査し続けます。アプリが新しくなっただけで、すべての既存の BRA に新しい制約を一律に当てはめることはしません。

  • 印を持ち続ける：プロジェクトは作成時に、検査規則の水準（harnessRules）、SABRA の境界（sabraBoundary）、調査モードなどの設定を保存します。後のフォローアップとリトライも、その設定に従います。
  • 複製は元の印を引き継ぐ：公開プロジェクトの複製は、元の調査モード、SABRA の境界、harnessRules、仮説モードの設定をそのままコピーします（4.6）。
  • 計画は確定時の規則で作る：オーケストレーターの計画は、確定したときの harnessRules を固定します。後のデプロイで規則の水準が上がっても、その計画の行はすべて確定時の規則で作られます（6.12）。
  • 保存したデータは書き換えない：古い形の名前、古い境界のアンカー、多く数えすぎた使用量は、保存先の上ではそのままです。読むときに現在の形へ直すか、補正して表示します。

主な変化と、それより前に作られたものの扱いを次の表にまとめます。詳しい扱いは右の列の節にあります。

C.2 命名

古い形の Descriptor と Circuit ID

v0.16 までは、左右をアンカーで表していました。片側の BNA 領域は単一のラベルで書き（BNA:57 が左の A4ul）、DHBA 側や BNA の群は @L / @R を付けました（BNAG:FuG@L）。Circuit ID も A4ul@L の形で、括弧の中の区切りは ,、投射は out: と書いていました。v0.17.0 からは、左右を facet side で表し、区切りを .、投射を out- と書きます（2.8）。

v0.16 までに作ったプロジェクトと Canon には、古い形の Descriptor と Circuit ID が残っています。保存済みのデータは書き換えません。読むときに現在の形へ直し、その形で比べます。

SABRA の境界が以前のままのプロジェクト

2026-10-04 の SABRA の仕様の変更で、BNA を使うのは新皮質だけになりました（2.3）。v0.24.0 より前に作ったプロジェクトは、この変更の影響を受けません。

  • プロジェクト：sabraBoundary を持たないプロジェクトは、以前の境界のまま検査します。皮質下の BNA のアンカーのまま読み込み・検査・出力ができ、フォローアップでも書き直しを求めません。新しいプロジェクトは、作成時に sabraBoundary: "neocortex" を持ちます。複製は元の設定を引き継ぎます。
  • 版：版の manifest には、検査が従った境界（neocortex / legacy）と、RCS が返した境界のバージョンが残ります（4.5）。
  • Canon：保存済みの Canon の回路は書き換えません。Canon に従うプロジェクトは、Canon にある Descriptor をそのまま使えます。以前の境界で作られた BNA:223-224 なども、境界の検査の対象から外します。Canon どうしを比べるときは、現在の形に直したスナップショットを使います（currentCanonSnapshot）。

CSV 形式のバージョン

Project.csv の BRA version は、v0.10.0 から CoBRAC-v1-1 です。CoBRAC-v1-0 からの列の変更は末尾への追加だけで、v1-0 のすべての列の位置は変わりません。追加した列は次のとおりです。

  • References.csv：Literature type と Alternative URL。
  • Circuits.csv：UC Descriptor の後ろの Sub-Circuits と Uniform。
  • Connections.csv：Pointers on figure の後ろの 2 つの関係と、論文中の表記。

グラフは v1-0 と v1-1 の CSV を列名で読みます。v0.9 以前に書かれたファイルは、次のフォローアップで通常どおり検査され、BRA の値の規則に合わない点が修正依頼として戻ります。直るまでの間も CSV は作れます。そのときは、Source of ID のリストは先頭の値を使い、複数の文献を持つ接続は文献ごとの行に分け、関係のない接続は = と Circuit ID で書きます。

C.4 ID と名前

以前の形の ID

いまのプロジェクト・Canon・計画の ID はランダムな 7 文字です（4.3）。v0.7.0 から v0.28.x までは、利用者ごとの番号を使った別の形で ID を発行していました。この形の ID はいまも有効で、どの検査も両方の形を受け付けます。BRA の版は、どちらの形でも <ProjectID>@v<n> です。

種類以前の形（v0.7.0 から）例
プロジェクト^u[0-9a-hjkmnp-tv-z]{7}-[1-9][0-9]*$u7m2q9xa-12
Canon^u[0-9a-hjkmnp-tv-z]{7}-c[1-9][0-9]*$u7m2q9xa-c1
計画なし（計画はランダムな ID だけ）—
  • 頭の u… は利用者の userKey です。利用者の項目の projectSeq / canonSeq は、この形で最後に発行した番号で、もう進めません。
  • v0.7 より前の利用者ごとの slug は、どちらの形にも当てはまりません。移行した古い ID からの転送のためにだけ解決されます。
  • v0.7 より前の古い ID は、2 人の利用者が同じ値を持ちえます。Jobs・Messages・project-index は projectId だけをキーにしているので、読み出しはすべて所有者で絞ります（8.5）。

古い ID の移行と転送

scripts/migrate-project-ids.mjs は、古い ID のプロジェクトを新しい ID の下にコピーするスクリプトです。既定では試行だけを行い、--apply を付けたときに書き込みます。実行の手順は運用手順書（docs/ops/README.md）にあります。

  • コピーするもの：legacyId（移行前の ID）を付けた Projects の項目、Jobs と Messages、フォルダ名を変えた S3 のオブジェクト。
  • 古い Projects の項目は、users/{userId}/{legacyId}/migration-backup/project-item.json に保存してから消します。このため一覧には 1 回だけ出ます。
  • --keep-old を付けると、古い Jobs・Messages の項目を控えとして残します。古い S3 のオブジェクトは消しません。
  • もう一度実行すると、移したコピーの隣に残った古い Projects の項目も消します。
  • 移行前の ID の URL は、新しい ID に転送します（GET /projects/resolve/{id}）。削除したプロジェクトは転送の対象から外れます。

画面の URL も、古いものは新しい場所へ転送します。古いチャットの URL /chat/:id はプロジェクト画面へ、/docs/CHANGELOG は「リリースノート」ページ（/releases）へ移ります。

古い名前

自動で付けた名前（nameSource = "auto"）が古い ASCII の slug のままのプロジェクトがあります。たとえば TLF が VOR、ROI が 小脳 のプロジェクトの名前が VOR になっているものです。こうしたプロジェクトは、画面でもダウンロードのファイル名でも、仮の名前（<TLF> in <ROI>）を使います。

典拠：packages/shared/src/projectId.ts・canon.ts・plan.ts、packages/api/src/lib/ownership.ts・catalog.ts、packages/api/src/app.ts、packages/web/src/App.tsx、scripts/migrate-project-ids.mjs

C.5 版と出力

版の仕組みより前に完成したプロジェクト

版の凍結は v0.26.0 から行っています（4.5）。それより前に完成したプロジェクトにはスナップショットがないので、次のように扱います。

  • 現在のデータを、版 revision、由来 live として一覧に出します。画面では「未保存」と表示し、作業用のコピーから表示します。
  • フォローアップは完了したプロジェクトでしか受け付けません。そこでフォローアップのワーカーは、変更を始める前に、そのデータを版 revision、由来 baseline として凍結します。生成条件は最後のジョブが記録したものだけで、revision がなければ 1 にします。フォローアップの結果は revision + 1 になり、baseline がその親です。
  • 失敗・中止した古いプロジェクトのリトライは、baseline を凍結しません。作業用のコピーが途中まで変わっているかもしれないためです。その結果の版の親にはスナップショットがなく、差分の要約もありません。

検査の前提が記録されていない版

  • 版の manifest に harnessRules を記録するようになったのは v0.28.2 からです。それより前に保存した版の manifest は書き換えず、「版」タブでは「不明」と表示します。
  • 規則の印を持たないプロジェクトの版には、harnessRules として 0 を記録します。
  • 仮説モードより前に保存した版には、仮説の情報（根拠の扱い、仮説の範囲、上限、件数）がありません。

Template-v2-2 形式の xlsx がないプロジェクト

Template-v2-2 形式の xlsx をワーカーが作るようになる前に完了したプロジェクトと、CoBRAC の xlsx よりファイルが古いプロジェクトには、この出力がありません（3.13）。GET /projects/{id}/artifacts/template-xlsx を呼ぶと、API の Lambda が同梱のテンプレートを使って、作業ディレクトリの CSV と JSON からその場で作って保存し、署名付き URL を返します。CoBRAC-v1-x のどの CSV も読めます。API の Lambda のメモリを 1,024 MB にしているのは、このブックをその場で作るためです（8.2）。

典拠：packages/worker/src/versions.ts、packages/api/src/lib/versions.ts、packages/shared/src/braVersion.ts、packages/web/src/components/workspace/VersionsView.tsx、packages/api/src/app.ts（template-xlsx）、CHANGELOG.md（0.26.0・0.28.2）

C.7 使用量

v0.17.0 までのワーカーは、Codex がターンの終わりに返す会話（Codex のスレッド）の累計を、ターンの分と取り違えて毎ターン足していました（経緯は D.10）。このため、修正より前に起動したワーカーが記録したジョブの使用量と費用は、全工程で実際の約 2〜3 倍になっています。保存した記録は書き換えず、API が返すときに補正します。

  • 対象：USAGE_FIX_AT（2026-10-01 18:33 UTC）より前に始まったジョブ。この時刻は v0.17.1 のワーカーのタスク定義を登録した時刻です。これ以降に作ったプロジェクトには何もしません。
  • 方法：ジョブが各ターンの後に書いた使用量の行（kind: "usage" のお知らせ）から各ターンの累計を取り出し、累計が増えた分だけを数えます。累計が減ったら、新しい会話の始まりとして 0 から数えます。プロジェクトの会話を続けるジョブ（リトライ・回答・フォローアップ）は、前のジョブの最後の累計から数えます。解説記事のジョブは独立した会話として扱います。補正した使用量に単価をかけて、費用を計算し直します。
  • 補正する画面：プロジェクトの一覧、プロジェクトのジョブの表と合計、エージェント欄の使用量の行、利用状況のまとめ、管理画面のプロジェクト一覧。対応する API は、プロジェクトの詳細、メッセージ、/users/me/usage、/admin/projects です。DB には書きません。終わったジョブの補正は、Lambda のコンテナごとに保持します。

この補正には、次の限界があります。

  • 記録されなかった分は戻せません。v0.17.1 より前は、失敗で終わったターンを 0 として記録していました。その分は復元できないので、補正後の値は実費より低くなることがあります。
  • 打ち切られたターンの分も戻せません。v0.24.1 より前は、時間切れ・取消・SIGTERM・理由を返さない異常終了で打ち切られたターンの使用量を記録していませんでした。
  • WebSocket で届く更新は補正しません。古いプロジェクトで新しいジョブが終わった直後は、画面を読み込み直すまで補正前の合計が見えます。
  • 調査ステップの指標（researchStep.usage）は補正しません。
