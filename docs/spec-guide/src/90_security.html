第 9 部

セキュリティと費用

第 9 部は開発者と運用者に向けて、CoBRAC Agents の守り方とお金のかかり方をまとめています。IAM の権限、扱う情報と保存場所、暗号化と API キー、認証と認可、ワーカーの隔離、外部への送信、ログと脅威への対策、監視と緊急停止を順に定め、最後に AWS と OpenAI・Anthropic の費用を説明しています。AWS の構成そのものは第 8 部に記載しています。リリースやデプロイの手順、緊急時の操作、撤去の手順は、本書ではなくリポジトリの docs/ops/README.md にあります。

秘密の守り方OpenAI と Anthropic の API キーは KMS で暗号化し、復号できるのはワーカーだけです。キーを使うのは Codex のプロセスか、Claude のモデルではワーカーの中の中継だけで、エージェントのシェルには渡しません。
データの範囲プロジェクトのデータは所有者の userId に結び付け、API はほかの利用者に存在そのものを見せません。公開と共有は所有者が選んだときだけです。
費用の考え方使われていないときの固定費を小さくし、ジョブが動いている間だけ Fargate Spot に払います。費用の大部分は OpenAI と Anthropic の利用料で、AWS の請求には含まれません。

9.1 IAM の権限

各 Lambda とワーカーには、その仕事に必要な権限だけを CDK で付けています。とくに API キーについては、暗号化できるのは API の Lambda だけ、復号できるのはワーカーのタスクロールだけです。主体ごとの権限は次のとおりです。

主体付いている権限付いていないもの
ワーカーのタスクロール（Codex を子プロセスで動かす）Users・Projects・Jobs・Messages の読み書き。Canons の読み取り（固定した rev）。Catalog は config の区画だけの GetItem（デフォルトの API キー）。成果物バケット全体の読み書き。KMS の Decrypt。Secrets Manager の rcs/mcp-bearer-token の読み取り（RCS を使うとき）KMS の Encrypt。Plans・WsConnections
API（http）8 つのテーブルすべての読み書き。成果物バケット全体の読み取り。書き込みは users/*（公開プロジェクトの複製の書き込み先。自分の接頭辞かどうかは API のコードが検査する）、canons/*、staging/*、plans/*、admin-docs/*（仕様書の PDF）。削除はグラフの配置（users/*/graph/*.layout.json）と staging/* だけ。KMS の Encrypt。キューへの送信。クラスター内のタスクの停止（ecs:StopTask）。登録 Lambda cobrac-bradb-import の呼び出しKMS の Decrypt（キーを平文に戻せない）

計画ランナー（planRunner）Plans・Users・Projects・Jobs・Messages・Canons の読み書き。Catalog は config の GetItem と id の PutItem（ID の予約）だけ。成果物の plans/*・canons/* の読み書きと users/*/workspace/* の読み取り。キューへの送信。クラスター内のタスクの停止KMS

計画ランナーは、行のプロジェクトを API と同じ処理で作って動かし、計画が取り消されたときはタスクを止めます。自律実行の計画では、判断のジョブ（6.8）の結果に従って、所有者に代わり Canon の PR の承認・却下・変更の依頼と、エージェントの質問への回答を行います。これらは API と同じ処理を通り、同じ検査を受けます。人が対応する計画では、承認・却下・回答は人が API で行います。

API キーに触れる経路

API の Lambda は、キーを登録するときに暗号化するだけで、復号はできません。計画ランナーには KMS の権限がまったくなく、計画用のジョブの入力（input.json）にもキーは入りません。計画用のジョブのキーは、ほかのジョブと同じくワーカーが解決して復号します。

典拠：packages/infra/lib/cobrac-stack.ts（permissions）、packages/api/src/lib/aws.ts（暗号化）、packages/api/src/lib/planRunner.ts（自律実行の判断の適用）、packages/worker/src/index.ts（復号）

9.2 扱う情報と保存場所

CoBRAC Agents は一般向けの公開サービスではなく、招待かセルフサインアップで参加する少人数の利用者を想定しています。それでも OpenAI の API キーと研究データを扱うので、保存・復号・記録の扱いを 9.2〜9.7 で定めます。

パスワードのハッシュや MFA の秘密などは Cognito が管理します。アプリが扱うのは、ブラウザの中の ID・アクセス・リフレッシュトークンだけです。

プロジェクトのデータ

プロジェクトのデータには、次のものがあります。

  • ROI・TLF と、作成時に付けた参考資料（ファイルと URL）
  • チャットの全文（利用者の指示、エージェントの出力、コマンドの結果、Web 検索の語句）
  • HCD・FRG の JSON のデータファイル、レポートと判断ログ（Markdown）、CSV、xlsx、グラフの JSON
  • Codex の会話の状態

オーケストレーターの計画（名前、目標、手入力または資料から読んだ行の ROI・TLF・理由、履歴）は、所有者の userId のもとで Plans テーブルに保存し、所有者だけが読めます（ほかの利用者には 404）。アップロードした資料そのものは計画には残さず、読み取った行だけを残します。

これらは個人情報ではありませんが、未発表の研究上の仮説や文献のメモを含むことがあります。ほかの利用者には見えません。管理者はプロジェクトの一覧を見てジョブを強制停止できますが、成果物の本体を返す API は所有者だけが呼べます。

集めないもの・返さないもの

  • 支払いの情報、住所、電話番号、生年月日は集めません。
  • API キーの平文は返しません（GET /users/me は encryptedApiKey を取り除いて返します）。
  • thread/（Codex のセッション）のダウンロード URL は返しません。

場所保存するもの
ブラウザAmplify が保持する ID・アクセス・リフレッシュトークン
Cognito ユーザープールメールアドレス、パスワードのハッシュ、確認の状態、グループ
DynamoDBUsers（プロフィールと API キーの暗号文）、Projects（メタデータと質問文）、Jobs（実行の状態とトークンの使用量）、Messages（チャットの全文。1 件 60,000 字で切る）、Plans（計画の名前・目標・行・履歴）、Canons・Catalog、WsConnections（接続 ID。約 2 時間 10 分で消える）

BRA-DB（BraDb の VPC の EC2。暗号化した EBS）登録した版：5 つの CSV の内容、Contributor 名、Project ID、ROI・TLF。登録ごとに版 ID、内容のハッシュ、生成条件、登録した人の名前

BRA-DB には、プロジェクトの所有者が登録したものだけが入ります。メールアドレス・userId・API キーは入りません（requested_by は Contributor 名です）。BRA-DB に届くのは VPC の中からだけです。インスタンスは 5432 番を登録 Lambda からしか受けず、SSH もパブリックアドレスも持たず、管理は SSM Session Manager で行います。接続はインスタンス自身の証明書による TLS で、ロールのパスワードは Secrets Manager（cobrac/bradb/*）にあります。API は、呼び出した人がプロジェクトの所有者であることを検査してから登録 Lambda を呼びます（第 7 部）。

リージョンは東京（ap-northeast-1）です。ポイントインタイムリカバリ（PITR）は無効です。WsConnections 以外のテーブル、成果物バケット、KMS の鍵、ユーザープールは、スタックを消しても残ります（RemovalPolicy.RETAIN）。

保持と削除

  • ログの保持は 14 日です。Messages と成果物には期限がありません。
  • プロジェクトの削除は論理削除で、所有者の画面から隠れるだけです（4.3）。メッセージ・ジョブ・S3 の成果物は残り、管理者のプロジェクト一覧には表示されます。Canon と計画の削除も同じく論理削除です。
  • 物理的に消す API はありません。必要なら管理者が AWS で直接消します。ただし版（revisions/）は、バケットポリシーがすべての主体に削除を禁じているので、先にポリシーを変えない限り消せません。
  • API キーを削除すると、encryptedApiKey を消して apiKeyRegistered=false にします。過去の暗号文は KMS 側には残りますが、どこからも参照されません。

典拠：packages/shared/src/types.ts（UserRecord）、packages/shared/src/orgKey.ts、packages/api/src/app.ts（/users/me・プロジェクトの削除）、packages/api/src/lib/auth.ts、packages/infra/lib/cobrac-stack.ts

9.3 暗号化と API キー

通信の暗号化

経路方式
ブラウザ ↔ CloudFrontHTTPS（HTTP は転送）
ブラウザ ↔ CognitoHTTPS
ブラウザ ↔ HTTP APIHTTPS と Bearer の ID トークン
ブラウザ ↔ WebSocketWSS。接続時にクエリの token で ID トークンを検証
Lambda・ワーカー ↔ AWS の APITLS（SDK の既定）
ワーカー ↔ OpenAIHTTPS（Codex）
ワーカー ↔ AnthropicHTTPS（ワーカーの中の中継から。Claude Code と中継の間は 127.0.0.1 の HTTP、9.5）

S3 のバケットは enforceSSL で HTTPS 以外を拒みます。署名付きのダウンロード URL も HTTPS です。

保存時の暗号化

対象方式
S3（Web と成果物）SSE-S3（S3 が管理する鍵）
DynamoDBサービスの既定の保存時暗号化
ECS の一時ディスクFargate の既定
Cognito のパスワードCognito が管理（アプリは平文を持たない）
OpenAI・Anthropic の API キーカスタマー管理の KMS キー（CMK）で暗号化。DynamoDB には base64 の暗号文だけを置く

成果物バケットには KMS による暗号化（SSE-KMS）を足していません。オブジェクトは非公開で（Block Public Access。OAC は Web のバケット側）、成果物は有効期限 15 分の署名付き URL でだけ取り出せます。

API キーと KMS

  • 鍵の種類は、カスタマー管理の対称 CMK です。年 1 回の自動ローテーションを有効にし、削除方針は RETAIN です。
  • 暗号化は API の Lambda だけが行います。暗号化コンテキストは { userId, purpose: "openai-api-key" } です。
  • 復号はワーカーだけが行い、同じコンテキストを必要とします。ほかの利用者の暗号文は、コンテキストが合わないので復号に失敗します。
  • デフォルトの API キーは、userId を含まない別のコンテキスト { purpose: "openai-api-key", scope: "default" } を使います。そのため、個人のキーとデフォルトの API キーを、互いのコンテキストで復号することはできません。
  • 平文がメモリにあるのは、キーの登録時に API の Lambda が確認の要求をしている間と、ジョブの実行中のワーカーのプロセスだけです。ワーカーは平文を Codex のプロセスに渡します。ディスク・ログ・S3 には書きません。
  • 登録時には GET https://api.openai.com/v1/models を呼び、401・403 なら登録を拒みます。返ってきたモデルの一覧を、使えるモデルとして保存します。
  • ブラウザからキーを取り出す API はありません。忘れたら OpenAI 側で発行し直し、登録を上書きします。
  • Anthropic のキー（Claude のモデル用）も同じ扱いで、コンテキストの purpose が "anthropic-api-key" です（デフォルトのキーは scope: "default" 付き）。登録時は GET https://api.anthropic.com/v1/models で確かめます。実行時の平文はワーカーのプロセスの中の中継にだけあり、Claude Code のプロセスには渡しません（9.5）。

デフォルトの API キー

管理者は、管理画面で組織の OpenAI キーをデフォルトの API キーとして登録できます。登録時には個人のキーと同じく /v1/models で確認します。保存するのは、暗号文・末尾 4 文字・そのキーで使えるモデルの一覧・登録した日時と管理者です。画面に見えるのは末尾 4 文字と日付だけです（書き込み専用）。Claude のモデルには、同じ扱いのデフォルトの Anthropic API キーを別に登録します。利用承認（Tier 1 / Tier 2）と、どのキーでジョブを実行するかの規則は 4.1 で定めます。

どのキーで実行するかは、ワーカーが起動のたびに決め直します。新しいジョブ、回答、リトライ、中断後の再開のどれでも同じです。そのため、利用承認を取り消したり、Tier を下げたり、デフォルトの API キーを消したりすると、次の起動から効きます。デフォルトの API キーを復号するのは、利用承認を受けていて自分のキーを持たない利用者のジョブで、そのジョブのモデルを Tier が許すときだけです。

アプリでは暗号化しないもの

チャットの本文、ROI・TLF、成果物、グラフの JSON、会話の状態は、S3 と DynamoDB のサービスによる暗号化だけで保存します。アプリの層での項目ごとの暗号化は、意図してしていません。管理者と AWS アカウントの権限を持つ人は、コンソールからこれらを読めます。

典拠：packages/api/src/lib/aws.ts（EncryptCommand）、packages/api/src/app.ts（キーの確認、/admin/default-api-key）、packages/worker/src/runKey.ts、index.ts（decryptApiKey）、packages/shared/src/orgKey.ts・provider.ts

9.4 認証と認可

認証

認証は Cognito で行います。

  • サインインは SRP で行います。パスワードそのものはサーバーに送りません。
  • パスワードは 10 文字以上で、英小文字と数字を含む必要があります。
  • トークンの有効期間は、ID トークンとアクセストークンが 2 時間、リフレッシュトークンが 30 日です。
  • preventUserExistenceErrors を有効にし、登録されていないメールアドレスにも同じエラーを返します。
  • アカウントの回復はメールだけです。
  • セルフサインアップを無効にしたとき（COBRAC_SELF_SIGNUP=false）は、管理者が Cognito で利用者を作ります。Cognito が仮パスワードをメールで送り、初回のサインインでログイン画面が新しいパスワードを求めます（Cognito の NEW_PASSWORD_REQUIRED）。

アカウントのメール

確認コード、再送、パスワードの再設定、メールアドレスの変更、管理者による招待のメールは、Cognito のカスタムメッセージのトリガー（packages/api/src/handlers/authMessage.ts）が書きます。どのメールにも、次のものを入れます。

  • CoBRAC Agents と運営者（WBAI）の名前、送った理由
  • コードとその有効期間
  • 心当たりがなければ無視してよいこと、サイトへのリンク

言語は、Web アプリがクライアントのメタデータとして渡す UI の言語（lang）、次に locale 属性で決めます。日本語か英語のどちらかで書き、分からなければ両方を 1 通に入れます。トリガーは Cognito から利用者の属性を受け取りますが、テーブル・バケット・鍵には触れず、ログも出しません。メールは SES から DKIM 署名付きで送ります。バウンスと苦情のあったアドレスは、SES のアカウント単位の抑制リストが送信先から外します。

管理者

  • API は要求のたびに、メールアドレスが COBRAC_ADMIN_EMAILS（GitHub の Secret）に含まれるか、Cognito のグループ admin に属しているかを検査し、そうであれば役割を admin にします。初回のサインインで作る利用者も、既存の利用者も同じです。一覧からアドレスを消しても自動では一般の利用者に戻らないので、管理画面で役割を変えます。
  • 管理者ができることは 4.1 の表にあります。仕様書（この PDF）は、GET /admin/spec が API に同梱した PDF を S3 の admin-docs/spec-<ハッシュ 16 桁>.pdf に置き、10 分間有効の署名付き URL を返します。
  • 管理者は自分自身を無効にできません。無効にされた利用者は、すべての API で 403 になります。

API の認可

  1. API Gateway の JWT オーソライザーが、ID トークンの発行者（iss）と対象（aud）を検査します。
  2. Hono がクレームから userId・メールアドレス・グループを読み、Users を読み込みます（初回は作ります）。
  3. プロジェクトの操作は、自分の userId を使った getProject(自分の userId, id) でだけ読みます。ほかの利用者の ID や削除済みのプロジェクトは 404 になります。
  4. S3 のキーは users/{自分}/{projectId}/ に固定し、..、thread/、絶対パスを拒みます。
  5. 参考資料のアップロードでは、API が呼び出した人の userId と乱数のアップロード ID からステージングのキーを作り、署名付き POST のポリシーでキー・Content-Type・大きさ（20 MB）を固定します。有効期限は 15 分です。プロジェクトの作成時に、各アップロードの存在と大きさ、合計が 50 MB 以内であることを検査し直してから、プロジェクトに移します。
  6. 管理者の経路は role === "admin" を要求します。

共有

Canon の共同編集者、プロジェクトと Canon の公開、公開プロジェクトの複製で、だれに何が見えるかは 4.6 で定めます。認可の観点では、次の点が要点です。

  • 公開は所有者が選んだときだけで、既定は非公開です。公開した内容にも、所有者のメールアドレスと userId は含めず、仮名の userKey だけを見せます。
  • 複製は、複製した人の接頭辞（users/{複製した人}/{新しい ID}/）にだけ書きます。API のロールは users/* に書けるので、自分の接頭辞かどうかは API のコードが検査します（9.1）。
  • 共同編集者が依頼した AI レビューは、その人のキーで実行し、その人の使用量に数えます。

WebSocket と CORS

  • WebSocket は、$connect の前に Lambda オーソライザーが ID トークンを検証します。購読のときも、そのプロジェクトが本人のもので、削除されていないことを検査します。接続の行には TTL があり、切断で消します。配信時に 410 Gone が返った接続は購読を外します。
  • CORS のプリフライト（OPTIONS）は JWT の認証を通りません。許可するヘッダーは Authorization と Content-Type です。オリジンは現在 * です（個人の利用と CloudFront の既定の URL のため）。独自ドメインを足すときはオリジンを絞ります。
  • 成果物バケットの CORS は、参考資料のアップロードのための POST だけを、CloudFront のドメイン、https://cobrac.site（CDK の外で付けた distribution の別名）、http://localhost:5173 から許します。ほかのホスト名で配信するときは packages/infra/lib/cobrac-stack.ts に足します。足さないと、そのオリジンからのアップロードはブラウザで失敗します。

典拠：packages/infra/lib/cobrac-stack.ts（Cognito・API・CORS）、packages/api/src/lib/auth.ts、packages/api/src/app.ts（認証の middleware、/admin/*、アップロード、公開と複製）、packages/api/src/handlers/authMessage.ts・ws.ts・broadcaster.ts、packages/shared/src/attachments.ts

9.5 ワーカーの隔離と秘密情報

エージェントは、ワーカーのコンテナの中で Web 検索と任意のコマンドを実行できます。そこで、エージェントが届く範囲から AWS の認証情報と API キーを外し、作業を本人のデータに限ります。

項目実装
実行の単位1 ジョブに 1 タスク。ディスクをほかのジョブと共有しない
OS のユーザーuid 10001 の worker（root ではない）
ネットワークパブリックサブネットとパブリック IP。受信なし。送信は許可（OpenAI・Anthropic・AWS・文献の Web）
Codex のサンドボックスコンテナそのものを境界とし、danger-full-access と approvalPolicy: never で動かす（コンテナの中では Landlock・seccomp が使えない）
使えるキーそのジョブの userId で復号したキーだけ。利用承認を受けていてキーを持たない利用者なら、デフォルトの API キー
権限タスクロールの権限は 9.1 のとおり。KMS は Decrypt だけ（Encrypt は API）

子プロセスの環境変数

タスクロールの認証情報があれば、だれの API キーでも復号できます。そこでワーカーは、子プロセスを起動するときに次の変数を環境から取り除きます（childEnv.ts の WORKER_ONLY_ENV）。対象の子プロセスは、Codex、エージェントのコマンド、pdftotext・pandoc（poppler）、xlsx の生成（Python）のすべてです。

  • AWS の認証情報（AWS_*）とコンテナの認証情報の URI
  • NCBI_API_KEY
  • RCS のトークン

Codex のプロセスにだけ、必要な RCS のトークンを戻します。Codex はこれを MCP のベアラートークンとして送ります。さらに Codex の shell_environment_policy で、エージェントのシェルのコマンドから CODEX_API_KEY・OPENAI_API_KEY と RCS のトークンを外します。Codex の設定（CODEX_HOME と信頼済みの /work/.codex）は root の所有なので、エージェントは Codex の環境で動く MCP サーバー・フック・通知のコマンドを足せません。

Claude のモデルのキーを渡さない中継

Claude のモデルのジョブでは、エージェントのコマンドが Claude Code の環境を受け継ぎます。そのため、Claude Code には本物のキーを渡しません。

  • ワーカーは自分のプロセスの中で、127.0.0.1 に中継（claudeGateway.ts）を開きます。Claude Code には中継の URL（ANTHROPIC_BASE_URL）と、実行ごとの乱数のトークン（ANTHROPIC_API_KEY）だけを渡します。トークンはワーカーが終われば意味を持ちません。
  • 中継はトークンを確かめてから、本物の Anthropic のキー（とワークスペース ID の anthropic-workspace-id ヘッダー）に差し替えます。RCS も同じ中継を通し、ベアラートークンを本物に差し替えます。
  • 中継が通すのは Messages と Models の API だけです。Messages は、そのジョブのモデルと claude-haiku-5-5（Claude Code の小さな裏方の呼び出し用）以外を 403 で拒みます。エージェントがキーを別のモデルに使うことはできません。
  • ワーカーの環境にある CLAUDE*・ANTHROPIC* の変数は、Claude Code に渡しません。

このため、Anthropic のキーと RCS のトークンはワーカーのプロセスにだけあり、Claude Code とエージェントのコマンドが持つのは実行ごとのトークンだけです。

同じユーザーのプロセスからの保護

ワーカー（PID 1）、Codex、エージェントのコマンドはどれも worker のユーザーで動きます。そのままでは、互いの /proc/<pid>/environ を読めてしまいます。そこで、イメージの中で node・Codex・git の実行ファイルを、実行だけ可能（chmod 0111）にしています。読めないファイルから起動したプロセスは dump できない扱いになり、ほかの worker のプロセスから、その環境変数とメモリを読めなくなります。

これで、エージェントは Codex のプロセスから OpenAI の API キーを読めず、PID 1 からコンテナの認証情報の URI（タスクロールと KMS に届く）も読めません。git を含めるのは、Codex が自分の環境（キーを含む）で git を実行するためです。Codex は起動時にプラグインのリポジトリを clone し、ターンごとに diff を取ります。

RCS MCP のトークン

ワーカーは起動時に Secrets Manager の rcs/mcp-bearer-token を読み、Codex のプロセスにだけ渡します（RCS_MCP_TOKEN）。エージェントのシェルのコマンドには渡さず、ブラウザにも送りません。シークレットにはカンマ区切りで受け付けるトークンが入っており（入れ替えの間は 旧,新）、ワーカーは最後のものを使います。設定がないか読めないときは、RCS なしで続けます。RCS 側の問題で BRA の作成を止めないためです。

OpenAI の API キーを使うもの

ワーカーは KMS でキーを復号し、Codex のプロセスを作るときにだけ渡します（Codex SDK の apiKey）。モデルに要求を送るのは Codex で、ワーカー自身は OpenAI を呼びません。エージェントがシェルで実行するコマンドには、キーが渡りません。キーを平文で扱うほかの場所は、API の Lambda が登録時に /v1/models で確認するときだけです。Anthropic のキーは Claude Code にも渡さず、ワーカーの中の中継だけが使います（上記）。

参考資料の URL の取得

参考資料の URL は、ブラウザではなくワーカーが取りに行きます。http(s) だけを許し、転送（最大 5 回）のどの段も公開のアドレスに解決されなければなりません。ループバック、プライベート、タスクのメタデータのエンドポイントのようなリンクローカルのアドレスは拒みます。大きさは 10 MB まで、時間は 20 秒までです。

残るリスク

プロンプトインジェクションで、作業ディレクトリやメタデータの外を読ませようとする試みには、次の 3 つで備えています。エージェントが届くプロセスから AWS の認証情報とその URI を外すこと、キーを持つプロセス（ワーカー・Codex・git）を dump できなくして /proc から環境変数を読めなくすること、データを本人のものに限ることです。ただし、別のアカウントや VPC で分けるような完全なマルチテナントの隔離ではありません。エージェントは自分のジョブのためにキーを使っており、たとえば自分のジョブのデータを外に送ることはできてしまいます。

典拠：packages/worker/Dockerfile、packages/worker/src/childEnv.ts、codex.ts（createCodex・openThread）、claude.ts・claudeGateway.ts、rcs.ts、materials.ts、packages/shared/src/attachments.ts（isPrivateAddress）

費用を抑える実装

  • Fargate Spot を優先し、容量がないときだけ On-Demand にします。
  • エージェントが質問したら（status: "question"）、タスクを終了します。回答までの計算の費用は 0 です。
  • NAT・独自ドメイン（CDK 内）・Container Insights・PITR を使いません。CloudFront は Price Class 200 です。
  • ログは 14 日で消し、未完了のマルチパートアップロードは 3 日で消します。
  • 同時実行数の上限で、気づかないうちに Spot のタスクが積み上がるのを防ぎます。管理者の設定は 1 つの上限につき 1〜16 で、17 以上は拒みます（8.3）。
  • janitor は 5 分ごとに動きます。ハートビートが 15 分途絶えたら最大 2 回まで自動でリトライし、回答待ち 7 日・キュー 24 時間で失敗にします。Spot の中断では 120 秒の猶予で保存して次の janitor で再開し、ターンの途中も 5 分ごとに保存します（8.3）。

オーケストレーターは、計画ランナーが毎分動いて、費用が膨らまないように次のように抑えます。

  • 両方の同時実行数の上限に空きがあるときだけ行を始めます（待機中のジョブも数えます）。そのため、大きな計画でも、ジョブがキューの 24 時間の時間切れまで待つことはありません。
  • 失敗した行の自動リトライは 2 回までで、その後は「要対応」になります。自律実行の計画では判断のジョブが対処を決め、人が対応する計画では人を待ちます（6.8・6.9）。
  • 所有者がジョブを動かせなくなった計画は、行を次々に失敗させずに自分で一時停止します。キーがない、アカウントが無効、選んだモデルが許されなくなった、の場合です。
  • 自律実行の計画は、計画の費用の上限に達すると新しい行を始めません（6.8）。
  • 下書きと再計画の計画用のジョブも、行と同じく空きがあるときだけ積み、両方の上限に数えます。再計画はバッチごとに最大 1 回、計画あたり約 10 回まで（MAX_REPLAN_JOBS）です。1 回目は最初のバッチが終わった後、以降は前回から行の 10 分の 1 が終わるごとに行います。再計画するのは自動の順序の計画だけで、一時停止中は動かしません。
  • ワーカーは計画用のジョブを 7 分（長い資料の下書きは 25 分）で打ち切ります。janitor は、ハートビートが途絶えたものと 24 時間キューにあるものを失敗にし、リトライしません。計画ランナーが 1 ステップで読む uc.json は 20 件までです。
  • Canon のある計画では、本体の行の PR の AI レビューと Canon に合わせるフォローアップ（行あたり最大 2 回、MAX_CONFORM_FOLLOWUPS）は、所有者のキーかデフォルトの API キーで動く通常のジョブです。行と同じ空きの判定を通り、両方の上限に数え、ほかのジョブと同じく課金されます。基準プロジェクトは AI レビューを受けません。
  • Canon に合わせるフォローアップは、PR がまだ開いているときだけ送ります（計画ランナーが直前に読み直します）。そのため、すでに承認・却下された PR に有料のフォローアップを使うことはありません。
  • 計画の PR が 20 件承認を待っている間は、新しいバッチを始めません（PLAN_MAX_WAITING_PRS）。放置された計画は、審査者の仕事を積み上げずに止まります。

9.10 OpenAI と Anthropic の費用と記録

だれが払うか

OpenAI と Anthropic の利用料は AWS の外で、各利用者の API キーか、デフォルトの API キーに請求されます。自分のキーを持たず利用承認を受けた利用者のジョブは、デフォルトの API キーで動くので（4.1・9.3）、その費用はこのキーを持つ組織に請求されます。Tier 1 の利用者は gpt-6-luna・gpt-5.6-luna・claude-haiku-5-5（下の単価表で最も安いモデル）だけを、Tier 2 の利用者はすべてのモデルを使えます。管理画面には、利用者ごとのデフォルトの API キーの費用が、累計と今月の分で出ます。アプリ自体には支出の上限がありません（自律実行の計画の費用の上限は 6.8）。デフォルトの API キーの OpenAI のプロジェクトと Anthropic のワークスペースに、月の予算を設定してください。

費用の計算

使用量は { inputTokens, cachedInputTokens, outputTokens, reasoningOutputTokens } の 4 つの数で、Claude のモデルではキャッシュへの書き込み cacheWriteTokens が加わります。推定費用 costUsd は、estimateCostUsd() が単価表から次の式で計算します。推論のトークンは outputTokens に含まれています。

(inputTokens − cachedInputTokens − cacheWriteTokens) × 入力の単価
  + cachedInputTokens × キャッシュされた入力の単価
  + cacheWriteTokens × キャッシュ書き込みの単価
  + outputTokens × 出力の単価        （単価は 100 万トークンあたり）

キャッシュ書き込みの単価がないモデルでは、入力の単価を使います。表にないモデルでは null になり、画面は $— を出します。ジョブの model は、ジョブの開始時に実際に Codex か Claude Agent SDK に渡したモデルです（4.2）。

1 ターンの使用量の数え方

Codex がターンの終わり（turn.completed）に返す使用量は、そのターンの分ではなく、会話が始まってからの累計です。後のジョブで会話を再開しても、累計は続きます。そこでワーカーは、次のように数えます（packages/worker/src/codex.ts の runTurn）。

  • ターンの使用量は、ターン後の累計からターン前の累計を引いたものです。
  • ターン前の累計は、その会話のセッションファイル（<CODEX_HOME>/sessions/…/rollout-…-<threadId>.jsonl）の最後の token_count から読みます（sessionTotalUsage）。新しい会話は 0 から数え、後のジョブで再開した会話も同じ方法で前の続きから数えます。
  • レート制限で待ってから続けたターンは、最後の累計を 1 回だけ使います。
  • 失敗（turn.failed）で終わったターンも、セッションファイルの累計から数えます。
  • 打ち切られて終わりを返さないターンも、同じ方法で数えます。停止、調査ステップの 60 分の時間切れ、SIGTERM、6 時間の上限で打ち切られたものと、失敗のターンを出さずに終わった codex exec がこれにあたります。実行中のターンが測り方を登録し、先に来た停止の経路が 1 回だけそれを使います（InFlightTurn）。測った分は打ち切られたジョブ自身の費用に足し、次の実行はそれを含む累計から始めるので、二重には数えません。

Claude のモデルでは、ターンの使用量を SDK の結果（result.usage）から取り、キャッシュの読み込み（cachedInputTokens）と書き込み（cacheWriteTokens）を分けて記録します。累計は Codex のセッションファイルと同じ形で <CODEX_HOME>/sessions/claude-usage/rollout-claude-<id>.jsonl に書くので、上の数え方がそのまま使えます。

ジョブの使用量を足した後、ワーカーは全ジョブからプロジェクトの合計を集計し直します（refreshProjectUsage）。この数え方を決めた経緯は付録 D にあり、それより前に記録したジョブの扱いは付録 C にあります。

使用量と費用の記録

ワーカーは各ジョブについて、使ったモデル、入力・キャッシュされた入力・出力・推論のトークン数、推定費用を記録します（Jobs.usage・Jobs.costUsd。プロジェクトの合計は Projects.usage・Projects.costUsd）。ジョブには、どちらのキーで実行したか（keySource：own か、デフォルトの API キーの org）も記録します。画面での見え方は 4.7 にあります。

利用者ごとの集計（GET /users/me/usage）は、全体とモデルごとの合計に、自分のプロジェクトのジョブのほか、次のものも含めます。自分の Canon と共同編集者として入っている Canon の AI レビューと、自分の計画の計画用のジョブ（plan）です。

推定は単価表で計算するので、OpenAI と Anthropic の請求書と一致しないことがあります。とくに単価表にないモデルでは一致しません。この記録は AWS の費用とは別のもので、OpenAI と Anthropic の請求と突き合わせるために使います。

BRA 1 件あたりの目安

  • gpt-6-luna・推論の強さ high・調査モード オンで BRA を 1 件作ると、実費で約 $0.13〜0.18 でした（付録 D の測定）。オーケストレーターの見積もりは、1 行あたり $0.18〜0.39、中央値 48 分で計算します（PLAN_ESTIMATE。6.9）。
  • 単価の高いモデルで推論を強くした長い HCD → FRG → CSV の実行は、1 件で数ドルから数十ドルになりえます。これは約 $10 のインフラの月額（9.9）よりはるかに大きいので、作成画面でモデルと推論の強さを下げることが、費用を抑える近道です。
  • 調査モード（既定でオン。3.7）は、HCD の前に文献の調査を足します。Fargate の時間は約 10〜60 分増えます（1 vCPU / 2 GB の Spot で約 $0.01〜0.05）。OpenAI 側では、入力が 150 万〜600 万トークン（大部分はキャッシュ）、出力が 4 万〜15 万トークン（推論の強さ high 以上）増えます（RESEARCH_ESTIMATE）。作成画面は、選んだモデルでの見積もりを表示します。手早い下書きなら、作成画面で調査モードを切ります。
  • オーケストレーターの下書き・再計画は、推論の強さ medium で RCS の照会をする短い Codex の 1 ターンです（返答が読めなければ 1 回やり直します）。時間の予算は 7 分で、xlsx・PDF の資料を読むか 20 行を超える下書きは 25 分です。BRA の実行に比べれば小さな費用です。ほかのジョブと同じく所有者のキーかデフォルトの API キーで課金され、ジョブに記録され、計画の画面に計画自身のジョブの費用として出ます。計画の PR の AI レビューの費用も、計画の費用に含めます。
