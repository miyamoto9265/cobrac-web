付録 A

API 一覧

本付録は、CoBRAC Agents の HTTP API と WebSocket のメッセージを、領域ごとにすべて挙げています。HTTP API は、API Gateway の HTTP API から 1 つの Lambda（packages/api/src/app.ts、Hono）に渡ります。WebSocket は別の API Gateway と handlers/ws.ts・broadcaster.ts が扱います。どちらも LLM は呼びません。仕組みの説明は本文の各部にあり、本付録では要求と応答の形をまとめています。

A.1 共通の規則

  • 認証：GET /health を除くすべてのルートで、Cognito の ID トークン（Authorization: Bearer …）が必要です。API Gateway の JWT オーソライザーが、発行元（ユーザープール）と対象（クライアント ID）を検証します。Lambda はトークンの claims から利用者を決め、最初のアクセスで Users の項目を作ります。無効にされた利用者には 403（account disabled）を返します。
  • CORS：プリフライト（OPTIONS）は JWT の検証を通らず、API Gateway が応答します。オリジンはすべて許し、ヘッダーは Authorization・Content-Type、メソッドは GET・POST・PUT・DELETE・OPTIONS で、結果は 1 時間保持します。/{proxy+} のルートは GET・POST・PUT・DELETE・PATCH を受けますが、アプリに PATCH のルートはありません。
  • 所有者の判定：プロジェクトと計画を使えるのは所有者だけです。ほかの利用者のもの、削除したもの、存在しない ID は、どれも同じ 404 になります。Canon は、所有者・共同編集者・管理者で使える範囲が異なります（第 5 部）。
  • キーとモデル：ジョブを始めるルート（表で「キー」と記したもの）は、実行に使えるキーがないと 400 を返します。使えるキーとは、自分のキーか、利用承認とデフォルトの API キーの組です。利用者が選んだモデルが利用承認の Tier にないときは 403 です（4.1）。
  • エラー：状態コードと、短い説明の文（多くは日本語）を本文で返します。予期しないエラーは 500 と { error } です。
コード主な意味
200・201・202成功、作成した、受け付けた（ジョブを積んだか、積む予定にした）
400入力の誤り、上限の超過、実行に使えるキーがない、状態に合わない操作の一部
401トークンがない、または無効
403無効にされたアカウント、管理者だけのルート、Tier にないモデル、PR を受け付けない Canon、コメントできない PR
404存在しない・権限がない・削除した（区別しない）、BRA-DB のない環境での登録
409状態の衝突。実行中、ほかの承認が先、同じ処理の重複、計画の更新中のリース（「計画を更新中です。少し待ってからやり直してください」）など
502API キーを OpenAI で検査できなかった

A.9 CoBRAC オーケストレーター

仕組みは第 6 部に記載しています。計画のルートはすべて所有者だけが使え、ほかの利用者には 404 を返します。計画のリースの中で行う変更は、ほかの処理がリースを持っている間は 409「計画を更新中です。少し待ってからやり直してください」になります。

GET・POST/plans一覧：自分の計画（削除していないもの）。実行中・一時停止中の計画のうち新しい 12 件には、そのときの様子 pulse を付ける。pulse は、バッチごと・状態ごとの行の数、作成中の行と操作を待つ行、最新の出来事 4 件とその行、未決の提案の数、見積もりと実績で、保存せず読むたびに計算する。

POST/plans/{id}/pause、/plans/{id}/cancel実行中の計画の一時停止 / 実行中か一時停止中の計画の中止（行のジョブも止める）所有者
POST/plans/{id}/resume{ maxCostUsd? }：一時停止中か中止した計画の再開（キーを判定し直す）。自律実行の計画には新しい費用の上限を送れる。上限は 1〜1000 USD で、これまでの費用より大きくなければ 400。費用の上限で止まった計画は、上限を上げないと 400。自律実行でない計画に上限を送ると 400所有者
POST/plans/{id}/rows/{rowId}/retry、/plans/{id}/rows/{rowId}/skip要対応の行のリトライ / 待っている行・要対応の行・要判断の行のスキップ所有者
POST/plans/{id}/rows/{rowId}/resolve{ action: "done" | "push" }：要判断の行を完了にする / 次のステップで push し直す。計画が実行中か一時停止中で、行が要判断のときだけ。ほかは 409（6.7）所有者
POST/plans/{id}/proposals/{proposalId}/accept、…/{proposalId}/reject計画が実行中か一時停止中のとき：再計画の提案の承認 / 却下。提案は、行の追加、待っている行のスキップ、粒度方針の置き換えのどれか。提案が開いていない、add で 200 行を超える、remove の行がすでに始まっている（提案は stale になる）ときは 409所有者

A.11 WebSocket

接続先は wss://…/prod?token=<ID トークン>（config.json の wsUrl）です。接続のとき、Lambda のオーソライザーが ID トークンを Cognito の鍵で検証します（tokenUse: "id"、クライアント ID）。検証に通ると、ws の Lambda が接続を WsConnections に projectId = "_" の行として記録します。行の ttl は 2 時間 10 分で、API Gateway の接続は最長 2 時間です。切断（$disconnect）では、その接続のすべての行を消します。

向きメッセージ意味
ブラウザ → サーバー{ action: "subscribe", projectId }自分の削除していないプロジェクトを購読する。成功すると { type: "subscribed", projectId } と、現在のプロジェクト { type: "project", … } が返る。見つからなければ { type: "error", message: "project not found" }
ブラウザ → サーバー{ action: "unsubscribe", projectId }購読をやめる
ブラウザ → サーバー{ action: "ping" }接続を保つ。SPA は 5 分ごとに送る
サーバー → ブラウザ{ type: "message", projectId, message }Messages に新しい行が入った（broadcaster が送る）
サーバー → ブラウザ{ type: "project", projectId, project }Projects の項目が変わった（broadcaster が送る）
サーバー → ブラウザ{ type: "subscribed", projectId }・{ type: "error", message }購読への応答
  • 配信先は、プロジェクトの所有者の接続だけです（所有者を記録していない古いメッセージの扱いは付録 C）。
  • すでにない接続（410 / GoneException）は、送るときに消します。
  • 記録のない接続からのメッセージは 401、JSON として読めないメッセージと未知の action は 400 です。
  • WebSocket を使うのはプロジェクト画面だけです。計画の画面はポーリングで読み直します（6.10）。

典拠：packages/api/src/handlers/ws.ts・broadcaster.ts、packages/shared/src/types.ts（WsClientEvent・WsServerEvent）、packages/web/src/lib/ws.ts

A.12 仮説モードの要求と応答

本節は、仮説モード（3.12）に関わる API の形をまとめています。仮説を許す範囲（scope）は、作成とフォローアップの依頼に付ける hypothesis で指定します。依頼の文章に「仮説で」と書いても、範囲は広がりません。

作成時の指定

POST /projects の本文に hypothesis: { claims, maxShare?, note? } を付けます。

欄規則
claims許す主張の配列。空でなく、重複がなく、既知の主張だけ。接続の主張は existence・direction・sign、UC の主張は population・transmitter・modulation・role
maxShare仮説の割合の上限。0.1・0.2・0.3・0.5 のどれか。省くと 0.2
note任意のメモ。改行と連続する空白を 1 つの空白にまとめ、200 文字まで

規則に合わなければ 400 を返し、本文で理由を示します。受け付けると、プロジェクトに evidenceMode: "hypothesis"、hypothesisScopes: [S1]、hypothesisMaxShare を保存します。作成時の scope S1 の対象は、HCD 全体です。

フォローアップでの指定

POST /projects/{id}/followup の本文に hypothesis: { claims, target, maxShare?, note? } を付けます。claims と note の規則は作成時と同じです。

欄規則
target必須。{ kind: "all" }（全体）か、{ kind: "items", circuitIds, gnIds }（選んだ回路と GN）。items では、回路と GN の ID を合わせて 1〜200 個。ID は空白を含まない 100 文字以内で、GN の ID は R. で始める。回路の ID の先頭の U. とバッククォートは除いて扱い、重複は 1 つにまとめる
maxShare作成時と同じ値。省くと上限は変わらない
  • 受け付けると、新しい scope S<最大の番号 + 1> を加え、evidenceMode を hypothesis にします。それまで仮説を許していなかったプロジェクトでも同じです。
  • scope の記録は { id, claims, target, note?, jobId, createdAt } です。
  • ジョブの作成とプロジェクトの更新は、1 つの DynamoDB トランザクションで行います。条件はプロジェクトがまだ COMPLETED であることです。同じフォローアップを二重に送ったときなど、その間にプロジェクトの状態が変わっていれば 409「プロジェクトの状態が変わったため送信できませんでした。再読み込みしてください」を返します。

作成のときもフォローアップのときも、エージェント欄に、加えた範囲と上限を示すお知らせ（sys.hypothesisScope）が出ます。

応答とほかのルートでの扱い

ルート仮説モードでの扱い
GET /projects/{id}プロジェクトの evidenceMode・hypothesisScopes・hypothesisMaxShare を返す。最後の検査で仮説が 0 件になったプロジェクトは evidenceMode が strict に戻るが、scope と上限は記録として残る（3.12）
POST /public/projects/{id}/cloneevidenceMode・hypothesisScopes・hypothesisMaxShare を複製に引き継ぐ
GET /projects/{id}/versions/{n}仮説を含む版、または仮説モードで仮説の件数を記録していない版には bradbBlockedReason: "hypotheses" を付ける
POST /projects/{id}/versions/{n}/bradb上と同じ版の登録は 400「仮説を含む版は、いまは BRA-DB に登録できません」

典拠：packages/shared/src/hypothesisInput.ts・hypothesis.ts・hypothesisVersion.ts、packages/api/src/lib/hypothesisSettings.ts・lib/runs.ts
