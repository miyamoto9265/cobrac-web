第 1 部

CoBRAC の概要

この部では、CoBRAC Agents が何を作り、どのような流れで作り、複数の BRA をどうそろえるかを、仕組みの細部に入らずに説明します。あわせて、BRA を 1 つ作るのにかかる時間と費用の目安と、入力したデータがどこに保存され、どこへ送られるかをまとめます。詳しい仕様は、各節で示す後の部を参照してください。

作るもの脳の領域の神経回路（HCD）と、その回路が実現する機能（FRG）を、文献の根拠付きで表した BRA のデータです。
作り方エージェントが文献を調べてデータを書き、ワーカーが規則に照らして検査します。問題があれば直させ、検査に通るまで次に進みません。
まとめ方回路の名前と定義をプロジェクトの間でそろえ、多数の BRA をまとめて作り、完成したものをデータベースに登録します。

1.1 CoBRAC がすること

BRA（Brain Reference Architecture）のデータは、脳のある領域の神経回路と、その回路が実現する機能を、文献の根拠付きで表した表とグラフです。CoBRAC Agents は、このデータの作成をブラウザから依頼し、サーバーで実行する Web アプリです。

利用者は対象の脳領域と機能を入力します。すると、CoBRAC エージェント（以下、エージェント）が文献を調べ、BRA のデータを書きます。エージェントは OpenAI のモデルを Codex で動かす LLM です。ワーカーと呼ぶプログラムが、書かれたデータを規則に照らして検査し、問題があればエージェントに返して直させます。作業はすべてサーバーで進むので、ブラウザを閉じても止まりません。利用者はブラウザで進捗を見て、エージェントの質問に答え、完成した成果物を受け取ります。

CoBRAC では、1 つのプロジェクトで 1 つの BRA を作ります。BRA は次の 2 つのグラフからなります。

HCD（Hypothetical Component Diagram）
回路をノード、回路の間の接続をエッジとするグラフです。どの脳領域のどの神経集団が、どこから入力を受け、どこへ出力するかを、文献の根拠付きで表します。ノードになる回路を UC（Uniform Circuit）と呼びます。
FRG（Function Realization Graph）
対象の機能を部分的な機能に分解し、最下層で HCD の UC に結びつける木です。どの回路の組み合わせがどの機能を実現するかを表します。

HCD と FRG の考え方は 3.1 で、回路の名前の付け方は第 2 部で説明します。

入力

項目内容
ROI（Region of Interest）対象の脳領域
TLF（Top-Level Function）その領域が担う機能。ROI と TLF はどちらか一方だけでもよい。足りない側はエージェントが調べて補う
任意の項目参考資料（ファイルと URL）、Canon、モデルと推論の強さ（4.2）、調査モード（3.7）、仮説モード（3.12）

出力

エージェントが書くのは、HCD と FRG のデータと、説明の文章だけです。表計算の形式への変換とグラフの作成は、ワーカーがプログラムで行います。

1.2 BRA ができるまでの流れ

プロジェクトを作ると、ワーカーのジョブが 1 つ登録されます。ジョブは、ワーカーの 1 回の実行のことです。利用者から見ると、BRA は次の順に作られます。

  1. 作成：利用者が作成画面で ROI と TLF を入力し、プロジェクトを作ります。ジョブは「待機中」になります。
  2. 起動：同時に動かせるジョブの数に空きがあれば、サーバーがワーカーを起動し、プロジェクトは「実行中」になります。空きがなければ、空くまで待ちます。
  3. 作成の段階：ワーカーはエージェントに作業を依頼し、段階を 1 つずつ進めます。段階は、調査（既定で有効）、HCD、FRG、CSV、xlsx の順です。FRG の後で HCD と FRG が食い違っていないかを検査し、必要なら両方を調整します。
  4. 検査と修正：ワーカーは段階ごとにエージェントが書いたファイルを検査します。問題があれば一覧にしてエージェントに返し、直させます。段階が完了になるのは、検査に通ったときだけです。
  5. 質問：エージェントが利用者に確認したいことがあると、プロジェクトは「回答待ち」になります。この間ワーカーは止まっていて、費用はかかりません。回答すると、同じ会話の続きから再開します。
  6. 仕上げ：CSV ができると「仕上げ中」になり、ワーカーが xlsx とグラフを作り、結果を版として凍結します。その後、プロジェクトは「完了」になります。

作業の進捗、エージェントの文章、検査の結果は、所有者のブラウザにその都度届きます。

完了したプロジェクトには、修正を指示するフォローアップ（画面では「追加の指示」）や、解説記事の作成を依頼できます。どちらも新しいジョブとして動きます。ジョブが「失敗」や「中止」で止まったときは、「続きからリトライ」で前回の成果物から再開できます。ワーカーの応答が途絶えたジョブは、サーバーが自動で再開します。1 つのジョブが連続して動けるのは 6 時間までです。

段階の中身とエージェントとワーカーの受け渡しは 3.2〜3.6 で、ジョブの状態遷移と自動の再開は 8.3 で説明します。

1.3 複数の BRA をそろえる仕組み

第 3 部のハーネスは、プロジェクトごとに BRA を 1 つ作ります。第 2・5・6・7 部の仕組みは、その外側で、多数の BRA を矛盾なく作り、蓄積するためのものです。第 8 部と第 9 部は、これらすべてを動かすシステムと AWS の基盤を説明します。図 1.1 は、それぞれの仕組みの関係を示します。

仕組みひとことで何を解決するか
ハーネス（第 3 部）BRA の作り方LLM に自由に書かせると、形式の誤り、架空の文献、HCD と FRG の食い違いが残る。LLM の判断とプログラムの検査を分け、検査に通るまで直させる。
UC Descriptor と facet（第 2 部）回路の名前の規則自由な名前では、同じ神経集団がプロジェクトごとに別の名前になり、照合も集計もできない。SABRA の単位と明示的な属性だけから名前を組み立て、どこでも同じキーにする。
Canon（第 5 部）回路の定義をそろえる単位同じ名前の回路でも、BRA ごとに粒度（Uniform か Collection か）や分け方が違うと統合できない。そろえる範囲を決め、その中では定義を 1 つにし、変更は審査を通す。
BRA-DB（第 7 部）完成した BRA の登録先成果物を WBAI の BRA-DB と同じスキーマで蓄積する。どの版が、どの条件で作られ、だれがいつ登録したかを失わずにたどれるようにする。
オーケストレーター（第 6 部）BRA をまとめて作る段取り数十から百を超える ROI × TLF を 1 つずつ手で起動すると、順序、同時実行数、回路の重複、Canon への取り込みを管理しきれない。計画にまとめ、順序をプログラムで計算し、自動で進める。

典拠：各部の典拠を参照

1.4 時間と費用の目安

数値の読み方

この節の数値は、2026-10 の本番の記録と比較のための実行から出した目安で、保証する値ではありません。モデル、アプリのバージョン、指示書、OpenAI 側の状態によって変わります。

時間

  • 既定のモデル（gpt-6-luna）、推論の強さ（reasoning effort）high、調査モードありの条件で、BRA を 1 つ作るのにかかった時間は平均 31 分でした（3 件で 28.6〜35.5 分）。オーケストレーターは、1 行あたり中央値 48 分として所要時間を見積もります（6.9）。
  • 時間のほとんどは、モデルの応答を待つ時間です。応答の待ち時間は、それまでの会話の長さでほぼ決まり、会話が長いほど遅くなります。そのため、ワーカーは会話を短く保つように作られています（3.15）。
  • 調査・HCD・FRG の段階は、前の段階の結果を入力にするので、並列にして縮められる時間は小さくなります。
  • 調査モードは、HCD の前に文献の調査を加えます。時間は 10〜60 分ほど増えます（3.7）。
  • エージェントの質問に回答するまでの時間は含みません。

費用

  • 費用の大部分は OpenAI の利用料です。上と同じ条件の測定では、BRA 1 つで約 $0.13〜0.18 でした。オーケストレーターの見積もりは、1 行あたり $0.18〜0.39 です。
  • 単価の高いモデルで推論を強くし、長く実行すると、1 つで数ドルから数十ドルになることがあります。費用を抑えるには、作成画面でモデルと推論の強さを下げるのが近道です。作成画面には、調査モードで増える費用の見積もりが出ます。
  • OpenAI の利用料は、利用者自身の API キーか、利用承認を受けた利用者ならデフォルトの API キーに請求されます（4.1）。アプリ自体には支出の上限がありません。
  • AWS の費用は、ジョブ 1 つで普通は数十セントを大きく下回ります。月 50 ジョブでインフラが月 $20 未満を目標にしています。BRA-DB は常時動いていて、別に月約 $34 かかります（7.6）。

単価表と費用の記録の仕方は 9.10 に、AWS の予算は 9.9 に、測定の詳細は付録 D にあります。

典拠：packages/shared/src/pricing.ts（DEFAULT_CODEX_MODEL）、research.ts（RESEARCH_ESTIMATE）、plan.ts（PLAN_ESTIMATE）。測定値は本番の記録と Codex のセッション記録から出したもので、コードの定数ではない

1.5 データの扱い

利用者向けの短い説明
  • メールアドレスとパスワードは AWS の Cognito が保持します。
  • OpenAI の API キーは AWS KMS で暗号化し、ジョブの実行中にだけ復号します。画面に再表示はしません。
  • 作った BRA のデータは自分のアカウントだけに結び付きます。公開しない限り、ほかの利用者には見えません。
  • OpenAI の費用は、自分の API キーか、利用承認を受けていればデフォルトの API キーにかかります。
  • プロジェクトを削除すると自分の画面からは消えますが、データは消去されず、管理者のプロジェクト一覧には残ります。
  • エージェントは文献を調べるために、インターネットと OpenAI にデータを送ります。
  • このサイトはプロジェクトの関係者のための作業環境で、公開の SNS ではありません。

保存するもの

  • CoBRAC は、招待かセルフサインアップで参加する少人数の利用者を想定しています。集める個人の情報は、メールアドレス、表示名、成果物の作成者欄に載る Contributor 名、OpenAI の API キーです。支払いの情報、住所、電話番号、生年月日は集めません。
  • プロジェクトのデータには、ROI と TLF、参考資料、チャットの全文、HCD と FRG のデータ、レポート、成果物が含まれます。個人情報ではありませんが、未発表の仮説や文献のメモを含むことがあるので、所有者のほかには見えないようにしています。管理者はプロジェクトの一覧を見て、ジョブを強制停止できます。成果物の本体を読めるのは所有者だけです。
  • データは東京リージョンの AWS に保存します。チャットの全文と成果物には保存の期限がありません。版は削除できないように守られています（4.5）。
  • BRA-DB には、所有者が登録した版だけが入ります。メールアドレスと API キーは入りません（第 7 部）。

外部に送るもの

送信先送るもの
OpenAIROI・TLF などのプロジェクトの情報、指示の全文、エージェントが読んだファイル（参考資料を含む）、利用者の回答とフォローアップの指示。保持と学習の扱いは OpenAI との契約と組織の設定に従う。データを保持しない設定をアプリは強制しない
検索の提供元エージェントの Web 検索の語句
文献のデータベース（PubMed、Europe PMC、Crossref など）検索の語句と、文献の DOI・PMID・タイトル。プロジェクトのほかの内容と利用者の識別子は送らない
SABRA の検索サービス（RCS）領域名と短い文脈。利用者の識別子と API キーは送らない
参考資料の URL の先利用者が指定した URL への取得の要求

機微な文献を扱うときは、OpenAI の組織の設定を確認してください。保存場所と保持の詳細は 9.2、外部への送信は 9.6、ログと脅威への対策は 9.7 にあります。
