2.13 仮説モード

既定では、BRA に入れるのは文献で支持されたデータだけです（evidenceMode が無いか strict）。仮説モードのプロジェクト（evidenceMode: "hypothesis"）に限り、文献が直接は支持しない接続や UC、またはその性質を、hypothesis キーを付けた仮説として含められます。緩めるのは「論文の文がその主張そのものを述べている」という 1 つの条件だけです。DOI / PMID とその照会、引用文の照合、1 接続 1 文献、Pointers、命名と SABRA 境界、スキーマ（additionalProperties: false のまま）、interface、Collection と均質な送り手、FRG の構造、英語、レポートの節、Canon は、いつもどおり検査します。仮説は開示するだけで、ハーネスが書くものや求めるものは、調査・実験・検証・予測を提案しません。仮説モードは harnessRules とは別の設定で、どの規則とも組み合わせられます。

誰が許可し、誰が書き、誰が検査するか

主体役割
利用者（人）作成時に「仮説モード」を選ぶか、フォローアップで「この指示で仮説を許す」をオンにして、許す主張（claims）・対象・比率の上限・メモを決める。指示の文章に「仮説で」と書いても範囲は広がらない
API（プログラム）要求を検査して scope（S1、S2…）としてプロジェクトに保存する
ワーカー（プログラム）許可範囲を依頼文に展開し（HYPOTHESIS.md）、仮説を検査し、番号（H1…）と比率を計算して hypotheses.json に書き、出力に印を付ける
CoBRAC エージェント（LLM）まず直接の根拠を探し、見つからないときだけ許可範囲の中で仮説を書く（前提の論文、推論の種類、理由）。レポートの ## Hypotheses に開示する

許可範囲（scope）

  • 作成（POST /projects の hypothesis: { claims, maxShare?, note? }）：claims は空でなく重複の無い既知の主張、maxShare は 0.1 / 0.2 / 0.3 / 0.5（省略は 0.2）、note は空白をまとめて 200 文字以内。プロジェクトは evidenceMode: "hypothesis"、hypothesisScopes: [S1（対象は HCD 全体）]、hypothesisMaxShare を持つ。
  • フォローアップ（POST /projects/{id}/followup の hypothesis: { claims, target, maxShare?, note? }）：target は { kind: "all" } か { kind: "items", circuitIds, gnIds }（合計 1〜200 個の ID）。新しい scope S<最大の番号 + 1> を足し、evidenceMode を hypothesis にする（仮説を許していなかったプロジェクトでも）。ジョブとプロジェクトの更新は 1 つの DynamoDB トランザクションで、同じフォローアップの二重送信は 409。ワーカーは指示の後に Hypotheses allowed with this instruction: <scope> (share limit n%) の 1 行を足す。
  • 範囲の判定（scopeTargetCovers）：対象の回路は、挙げた UC、挙げた Collection の UC（入れ子も展開）、挙げた GN の下のすべての階層の UC。接続は送り手か受け手が対象の回路なら範囲内、UC はそれ自身が対象か、その接続の相手が対象なら範囲内。scope が仮説を覆うのは、その仮説のすべての主張を挙げ、対象が要素を覆うとき。
  • 文献だけへの復帰：仮説モードのプロジェクトのジョブが CSV まで完了し、最後の検査で仮説が 0 件なら、ワーカーは evidenceMode を strict に戻す。scope と上限は記録として残る。
  • 複製は evidenceMode・hypothesisScopes・hypothesisMaxShare を写す。

hypothesis キー

uc.json の ucs[] と connections.json の connections[] に任意で付けます（Collection と BIF には無い）。仮説モードでないプロジェクトに見せるスキーマにはこのキーが無く、仮説モードのプロジェクトにだけキー入りのスキーマを見せます（agentHarnessSchemas）。

欄値
claims1 つ以上、各 1 回。接続：existence・direction・sign。UC：population・transmitter・modulation・role（role は印を付けるだけ）
basis直接的なものから順に：published（論文が仮説として述べる）、homology（相同性が不確かな他種の領域。他種での直接の証拠は Taxon を付けた通常の証拠）、analogy（類似の回路）、indirect（機能的結合・共活性化・損傷・向きの無い拡散 MRI など）、model（計算モデルが必要とする）、functional-need（FRG が TLF を実現するためだけに必要）
rationale空でない文。前提がなぜ仮説を支えるかと、直接の証拠を何で探して見つからなかったか。[Author, Year] の引用は通常どおり検査。予測・検証・次の手順は書かない
premisesreferences.json の Reference ID を 1 つ以上（通常どおり照会する）。接続では先頭がそのレコードの referenceIds[0]
scope仮説を許す scope の ID（S<n>）
researchCandidate調査モードだけ：探した記録である research.json の候補（C<n>、状態が not_found か weak）

ワーカーの検査

検査（hypothesisProblems）はすべてエラーとして修正のターンで戻し、メッセージは何を変えるか（欄を直す、論文を証拠として引用する、仮説を外す）を示します。仮説の検査は HCD の段の外のファイル（GN の対象の frg.json、候補の research.json、レポート）にも依存するので、HCD のファイルが変わっていなくても FRG と CSV の検査でやり直します。「安全側」と書いたものは、仕様の要求より厳しくしてある検査です。

検査メッセージが求めること
キーのスキーマ（すべてのモード）、空の rationaleキーを直す
主張・前提の重複1 回ずつ挙げる
references.json に無い前提、DOI も PMID も無い前提（安全側）照会できる前提を挙げる
接続の premises[0] が referenceIds[0] でないレコードの論文を先頭にする
existence なのに測定法が Hypothetical でない。向き・符号の仮説や仮説の無いレコードに Hypothetical（安全側）Hypothetical にする、論文の測定法に戻す、キーを足す
仮説でないレコードがすでに支える送り手 → 受け手への existence の仮説仮説のレコードを外す
同じ送り手 → 受け手への 2 つ目の存在の仮説（安全側。比率を水増ししない）1 つにまとめ、ほかの論文は前提と理由に挙げる
population なのに sourceOfId が makeshift でない。アンカーだけの UC（SABRA の単位そのもの）への population（安全側）makeshift にする、facet を足す、別の主張にする
transmitter で値が空、modulation で値が空（安全側）推定した値を書く
主張と要素を覆う scope が無い仮説を外す（scope と、どの scope も許さない主張を示す）
主張ごとには許されるが、1 つの scope がすべてを許さない1 つの scope が許す主張だけにする
scope が不明、または覆わない（ほかの scope が覆う）覆う scope を書く
調査モード：researchCandidate が無い・候補に無い・contradicted（外す）・supported（その証拠を使う）など。調査モードでないのに researchCandidate がある候補を直すか外す
比率が上限を超える仮説を減らす（比率を下げるために接続や UC を足さない）。上限の中で TLF を実現できないなら message でそう言う
レポート（下記）節・ID・文を足す

仮説を許していないプロジェクトでは、hypothesis キーを持つ UC・接続をファイルごとに 1 つのメッセージで戻し、論文と引用で支えるか外すよう求めます。利用者が文章で仮説を頼んでいた場合、エージェントは「仮説を許可」をオンにして指示を送り直す必要があると message で伝えます。そこでは Hypothetical は普通の列挙値です。文献だけのプロジェクトの依頼文・検査結果・CSV・xlsx は、仮説モードの追加の前と同じです。

比率・番号・レポート

  • 比率（hypothesisShare、プロジェクトの版全体、すべての scope の合計）：仮説の接続 ÷ すべての connections[] のレコード、仮説の UC ÷ すべての ucs[]（ROI 内部と外部。Collection は数えない）。主張の数にかかわらず要素は 1 回だけ数える。許されるのは floor(p × 全体 / 100) 個まで（p は上限の百分率。整数で計算するので、上限 20% なら 10 件中 2 件は通り、3 件は通らない）。上限は 10 / 20 / 30 / 50%、既定 20%。
  • 番号（hypothesisRecords）：H1、H2… を、まず uc.json の順の UC に、次に connections.json の順の接続に付ける。追加・削除で番号は変わりうる。CSV の注記、hypotheses.json、レポートの検査、整合の記録は同じ番号を使う。
  • レポート：仮説が 1 つ以上あれば、## Limitations の前に ## Hypotheses の節（ID・要素・主張・根拠の種類・前提・理由の表と、上限に対する 2 つの比率。functional-need は太字）を置き、すべての ID を挙げる。ROI の入力から出力まで、仮説の接続を使わない有向の経路（根拠だけの経路）が無いときは、## Limitations にそう書く（定型文 "No evidence-only path leads from the ROI inputs to the ROI outputs."）。仮説モードの Limitations には事実だけを書き、今後の研究は書かない。
  • FRG：scope の中では、FRG の手順 5 の「UC や接続を作らない」は仮説を禁じない。その追加は判断ログの revisions に [FRG->HCD][hypothesis] として記録する。仮説を証拠に置き換えるのは、指示があったときだけ（[hypothesis] H3 → evidence [Author, Year]）。

出力・ファイル・ほかの仕組みとの関係

対象扱い

画面

2.14 出力（CSV・xlsx・グラフ）

ここからはワーカーのコードだけの処理で、LLM は関与しません。CSV はエージェントに書かせず、同じデータを xlsx とグラフへ渡すので、別々に書き直した表が食い違うことがありません。

成果物作り方
CSV 5 本（{P}_CSV/）buildCsvs が JSON から Project・References・Circuits・Connections・FRG を作る（形式 CoBRAC-v1-1、2.10）。Circuits.csv の Comments には roi から noROI(...) の印、uniformityNote から Uniform in this project: … を足す。CSV の段で問題が出たら、JSON を直す依頼としてエージェントに戻す
CoBRAC 形式の xlsxcsv_to_excel.py（対話なし、--contributor・--project-id・--base-dir・--output）が CSV から作る。Capability&Mechanism のセルは Capability、テンプレートの既定の印 <<mechanism to realize the capability>>、Mechanism
Template-v2-2 の xlsxBRA Data Preparation Manual の公式テンプレート prompts/templates/Template-v2-2.bra.xlsx に同じデータを書く（buildTemplateXlsx、下記）。ダウンロード名は {名前}_{ID}.template-v2-2.bra.xlsx
グラフbuildGraphs が CSV から HCD / FRG のグラフの JSON を作る。画面のグラフと解説記事の図の元
レポートと判断ログエージェントが書いた文章をそのまま閲覧・ダウンロードできるようにする

公式テンプレートの生成だけが失敗した場合、CoBRAC 形式の xlsx とグラフでジョブが完了することがあります。必要な形式がそろっているかは、ジョブの状態だけでなく出力を確かめます。完了した結果は、ワーカーが生成条件と一緒に凍結して版にします（第 5 部）。

Template-v2-2 への書き込み

  • テンプレートが土台：11 枚のシート、見出し、数式、AdminOnly のリスト、入力規則、条件付き書式、テンプレートが取り込む WholeBIF の行（入力欄の下の IMPORTRANGE の結果）を残す。表計算のライブラリは Google 固有の部品を落とすので、XML の水準で編集する（xlsxSheet.ts、zip は fflate）。書くのは投稿者が入力するセルだけで、自動・管理用の列は数式のまま。値の分かる数式セル（References A / G〜J、Circuits AO）は Google Sheets の計算結果を表示値に入れ、fullCalcOnLoad で Excel に残りを再計算させる。
  • 行：入力欄は References 2〜29、Circuits 2〜31、Connections 2〜80、FRG 2〜198 行。足りないときは、投稿者が行うのと同じく WholeBIF の取り込みの上に行を挿入し（最後の入力行を数式ごと写す）、下の行への参照（ほかのシート、入力規則の範囲、フィルタ、リンク、名前の定義も）をずらす。テンプレートの配置の変化（IMPORTRANGE の行）を検出したら出力を失敗にする。
  • Reference ID：テンプレートは BibTeX のキーから Reference ID を作る（Schultz_1997a → Schultz, 1997a）ので、CoBRAC の ID ごとに筆頭著者と年からキーを作る（重なれば次の文字）。書き込む自由な文章の引用も同じ ID にする。
  • BibTeX：テンプレートの正規表現に合わせ、1 行 1 項目で = の前後に空白。ジョブの最後にワーカーが DOI を Crossref で、PMID だけの文献を PubMed で引き（bibliography.ts、1 要求 10 秒・合計 60 秒、失敗は次のジョブで再試行、REFERENCE_LOOKUP=off で止まる）、bibliography.json に残す。記録が無ければ references.json と reference_check.json から作る。
  • DHBA の列：テンプレート自身の WholeBIF の Circuits の行（Source of ID が DHBA）を DHBA のオントロジーとして使う（HOMBA の graph_order とは別の番号）。1 つの DHBA 項にアンカーした UC はその行、DHBA 項より細かい UC はその項の graph_order に小数を足す。BNA にアンカーした回路、ROI の行、UC Descriptor の無い回路は空。
  • 古いプロジェクト（この出力ができる前に完了したもの、CoBRAC の xlsx より古いもの）：GET /projects/{id}/artifacts/template-xlsx が API の Lambda（テンプレートを同梱）で作業場所の CSV と JSON から作って保存し、署名付き URL を返す。CoBRAC-v1-x のどの CSV も読める。

2.15 解説記事

完成した BRA を、作っていない読者に説明する記事を、利用者の求めに応じて作るジョブです。段ではなく、BRA の会話とは別の新しい会話で動く LLM のジョブ（実行モード article）です。

  • いつ：プロジェクトが完了し xlsx まで生成済み（stepStates.XLSX = done）で、動いているジョブが無いときだけ。利用者が言語（既定は画面の言語。10 言語）とモデル（既定はプロジェクトのモデル。既定の API キーでは利用者の tier のモデルだけ）を選び、「記事を作成」を押す。言語ごとに並べて持て、作り直しは新しい記事が検査に通ったときだけ置き換える。
  • ジョブ：プロジェクトは QUEUED → RUNNING → COMPLETED と進む（フォローアップが待つように）が、段の状態・revision・完了時刻・BRA の会話・作業場所は変えない。失敗や取り消しは記事のジョブの状態だけに残し、プロジェクトを COMPLETED に戻す。
  • ワーカー（プログラム）：作業場所を（会話は復元せずに）戻し、CSV から図を 3 枚描く（buildArticleFigures：全回路と接続の circuit、TLF → GN → UC の木の frg、GN ごとの接続の function-map。それぞれ幅 980 px 以内と 430 px のスマホ用、日本語か英語のラベル）。Web 検索・RCS・lit の無い新しい会話を始め、prompts/article.md と図の一覧と要約表の事実を送る。
  • LLM：成果物（meta.json・report.md・decision_log.md・HCD と FRG の JSON）だけを読み、{P}/article/<locale>.md を書く。データに無い事実を足さない。3 枚で示せない点があれば自分の SVG を最大 2 枚足せる。
  • 検査（checkArticle）：# の題が 1 つ、その後に要約表、## の節が 5 つ以上、最低の長さ、指定言語の文字、ワーカーの図をそれぞれ 1 回ずつ代替テキストとキャプション付きで埋め込む（ほかの画像は不可）、HTML や手書きの参考文献の一覧が無い、Circuit ID 間の矢印（`A` → `B`）は connections.json にある接続だけ、GN の ID が実在、節へのリンクが見出しと合う、引用は references.json の ID だけ。問題は修正の依頼として最大 3 回戻し、それでも残ればジョブは失敗。
  • 公開：ワーカーが参考文献の一覧（その言語の見出しと、引用した ID の DOI のリンク）を足し、図を article/<locale>/figures/ に、記事を article/<locale>.md と .json に置く。この実行では作業場所を S3 に戻さない。すべての SVG はワーカーとブラウザの両方で sanitizeSvg（描画要素と表示属性だけを許す）を通し、ブラウザはオブジェクト URL の <img> で見せる（記事の欄が 640 px より狭ければスマホ用の図）。
  • 古さ：記事は開始時のプロジェクトの revision を持ち、その後のフォローアップで revision が変わると「古い」と表示して作り直しを勧める。
  • 言語：記事は中心の成果物ではないので、英語だけの規則の例外です（AGENTS.md に明記）。CSV・xlsx・グラフの変換は記事を読みません。日本語は敬体で、平易な説明文にします。
  • 費用：記事のジョブの使用量も、ほかのジョブと同じくプロジェクトの使用量に足す。

2.16 長いジョブ・保存・費用

  • 保存：実行中、ワーカーは 5 分ごとに作業場所と Codex の会話を S3 に保存し、Spot の中断の SIGTERM でも保存する。ワーカーが定期的に書くハートビートが途絶えたジョブは janitor（Lambda のプログラム）が回復を試みる（第 7 部）。
  • 会話の大きさ：Codex は会話を自動で圧縮する（既定 75,000 トークン、組織の 1 分あたりトークン上限を 1 リクエストで超えないため。CODEX_AUTO_COMPACT_TOKENS）。文脈の窓は 272,000 トークンとして扱う。会話が大きすぎて再開できない場合は、新しい会話で既存のファイルと判断ログを読んで続ける（2.6）。道具の結果を小さくし、ファイルを部分的に編集し、修正ターンだけ推論レベルを下げて、文脈と費用を抑える。
  • 費用：モデルの入力・キャッシュ入力・出力の使用量と単価表（packages/shared/src/pricing.ts）から計算する。Codex はターンごとに会話の累計を報告するので、ワーカーはターンの前後の累計の差をそのターンの使用量にし、同じ会話の累計を重ねて足さない。打ち切ったターンや異常終了したターンの使用量は、Codex のセッションファイルから測る。速度と費用の測定は第 7 部にあるが、その数値は現行のすべてのジョブの保証ではない。
  • 秘密の扱い：OpenAI の API キーは暗号化して保存し、ワーカー内で復号して Codex に渡す。Codex が API の呼び出しに使うだけで、エージェントが実行するコマンドからは見えない（shell_environment_policy で除く）。RCS のトークンも同じ。エージェントのシェルには AWS の認証情報を渡さない。Fargate のタスク自体がサンドボックスで、Codex は承認なし・フルアクセスで動く。
