6.6 アンカーと実行順序の計算

実行順序は、下書きが付けたアンカーと依存と優先度から、コードが決定的に計算します（orderPlanRows、packages/shared/src/planOrder.ts）。同じ行からは同じ順序になります。

アンカー

アンカーは、その行の ROI と、主な入力元・出力先の領域を、SABRA の単位で表した ID です（第 3 部の UC Descriptor のアンカー部分と同じ形）：HOMBA:<id>（DHBA 側）、BNA:<l>-<r>（BNA の領域のペア）、BNAG:<L2>（BNA の群）。行どうしを比べるときは、BNA の群をその領域のペアに展開してから比べるので、BNAG:IFG の行と IFG の 1 領域の行はアンカーを共有します（HOMBA の項はそのまま比べる）。行には最初の 4 個と残りの数が表示されます。

計算の 3 段階

  1. ハブの値：その行とアンカーを 1 個以上共有する、ほかの行の数（画面の「ハブ n」）。
  2. 基準プロジェクトのバッチ：ほかの行に依存しない行を（ハブ, 優先度, 行 ID）の順に並べ、いちばん上の行と、ハブがその 60%（SEED_HUB_SHARE）以上の行を、最大 3 行（MAX_SEED_ROWS）まで基準プロジェクトにする。基準プロジェクトは 1 行ずつ自分のバッチ（1, 2, 3）を持ち、ほかのバッチより先に 1 件ずつ作る。どの行もアンカーを共有しないとき、または行が 1 つのときは基準プロジェクトを作らない。
    多くの行が使う回路を先に 1 回だけ組み立て、その完成したプロジェクトを後の再計画に使うため。
  3. 本体のバッチ：残りの行を依存の位相順（Kahn のアルゴリズム。同順位はハブの大きい順、優先度の高い順、行 ID）に取り出し、依存する行（と基準プロジェクト）より後で、行数が同時実行数未満で、アンカーを 2 個以上（OVERLAP_LIMIT）共有する行がいない、いちばん早いバッチに入れる。同じ回路を作る 2 つの行が同時に走らないようにするため。依存が循環していれば、循環の外の何にも依存しない最上位の行で切る。

例：言語の計画（同時実行数 3）

アンカーを領域名で略記した例です（実際は HOMBA:… / BNA:… の ID）。

R2発話IFG44・PMv・Put—2基準プロジェクト・バッチ 2

下書きの並べ方（orderDraft）

  • 作る行（スキップでも既存でもない行）を、バッチ 1 から上の 3 段階で置きます。
  • 既存のプロジェクトで済む行は、ハブの値の計算にだけ数え、置いた最後のバッチに並べます（作らない。基準プロジェクトの印も付けない）。スキップした行は自分のバッチを保ちます。
  • 行の order は作る順に従います：バッチの順（基準プロジェクトが先）、バッチの中はハブと優先度の順で、置かなかった行（既存・スキップ）は最後です。
  • 画面の各行には「ハブ n」と、アンカーを 2 個以上共有する行（「重なり」）が出ます（GET /plans/{id} がスキップ以外の行について hub と overlaps を計算して返す）。基準プロジェクトのバッチの見出しには「基準プロジェクト」と出ます。

補足：R1〜R7 のハブは R1・R2・R5 が 2、ほかが 1 です。基準プロジェクトの候補は依存の無い行なので、R5 はハブが 2 でも基準プロジェクトになりません。しきい値は max(1, ⌈2 × 0.6⌉) = 2 なので、R1 と R2 が基準プロジェクトです。本体は R5（ハブ 2）→ R3 → R4 → R6 → R7 の順に置かれ、R4 はバッチ 3 にまだ空きがあっても R3 と 2 個共有するのでバッチ 4 に、R7 はバッチ 3 が 3 行で満杯なのでバッチ 4 に入ります。

6.7 手順 3：行とバッチを整える

下書きの計画の画面は、上から次の 4 つの区切りに分かれます。進捗・バッチ・時間・費用のカードは、確定したあとだけ出ます。「計画を削除」は一番下にあります。

  1. 作るもの
    • 目標を書き直せます（欄を離れると PUT /plans/{id} { goal } で保存）。
    • 資料ファイルを追加・削除できます（下書きのときだけ。下書き作成中や確定後は 409）。追加は POST /plans/{id}/attachments { attachments }（POST /uploads で上げたもの、計画と合わせて 10 個まで）、削除は DELETE /plans/{id}/attachments/{fileId} です。
      • 追加した CSV・TSV・テキストは、作成時と同じくすぐ行として読みます。読めない行は一覧で出し、自動の順序なら並べ直します。
      • xlsx・PDF は次の下書きのジョブが読みます。
      • ID（f1・f2…）とキーの番号は、計画がこれまでに持ったファイルの数（attachmentSeq）の次から振ります。削除したものの番号は使い直しません。
      • 追加・削除のたびに、資料から取り出した文章の目録（attachments/derived/manifest.json）を消します。次の下書きのジョブが、いまの資料から取り出し直すためです。
      • 削除しても、その資料から読んだ行は残ります。
    • 「下書きを作成」（行が無いとき）か「下書きを作り直す」（今の行は残る）を押せます。押せないときは、その理由が横に出ます。
    • 下書きのジョブの状態、読めなかった項目、粒度方針（読むだけ）もここに出ます。
  2. 行とバッチ
    • 行はバッチごとの表で出ます。基準プロジェクトのバッチの見出しには「基準プロジェクト」の印が付きます。
    • 各行に ROI と TLF の欄、アンカーと関係の要約、上下の移動と削除があります。行を開くと、理由・バッチ・アンカー・「作り直す」・既存のプロジェクト・重複の注意が出ます。
    • 変更した行と足した行には色が付きます。保存していない変更があるときだけ「保存していない変更が N 件あります」と「元に戻す」「行を保存」が出ます。
    • 行が 0 件のときは「まだ行がありません」の案内と「行を追加」「CSV を読み込む」が出ます。
    • 「N 件ずつのバッチに分ける」は「その他の操作」の中にあります。
  3. 進め方：一番上に自律実行（見出し「自律実行」と説明、自律実行のときは費用の上限の欄。その下に副次のチェックボックス「PR の承認や衝突にご自身で対応する」）、次に Canon（「なし／既存の Canon／新しい Canon」の切り替えと、Canon の選択か名前）、モデル（オーケストレーター・エージェント・推論の強さの 3 列。API キーの注記は 1 回）、調査モード。
  4. 確定して開始：見積もり（時間と費用）が出ます。押せないときは理由が横に出ます（行が 0 件、保存していない変更がある、下書きの作成中）。

上の帯は次のとおりです。

  • 行が 0 件の下書き：「まだ何も入っていません。目標を書いて「下書きを作成」を押すか、行を追加してください。確定するまでプロジェクトは 1 件も作られません。」
  • 下書きのジョブが終わったあと：「下書きができました。行とバッチを確かめて「確定して開始」を押してください。…」
  • 編集：下書きの間は、行の追加・削除・並べ替え、ROI・TLF・理由・バッチの変更ができます。「N 件ずつのバッチに分ける」は、いまの並び順のまま、同時に実行できる数 N ずつに分けます。
  • 自動と手動の順序：「自動で並べる」（POST /plans/{id}/order、DRAFT のときだけ。ジョブは使わず無料）は、いまの行で 6.6 の計算（orderDraft）をやり直し、ordering: "auto" にします（イベント ordered）。下書きの直後も自動の順序です。行の保存（PUT /plans/{id}/rows）で行を足す・消す・入れ替える・バッチを変えると手動の順序（ordering: "manual"）になり、あなたのバッチがそのまま使われます（バッチ後の並べ直しと再計画もしません）。作る行の中で自分のバッチに 1 行だけでなくなった基準プロジェクトは、基準プロジェクトの印を失います。
  • 同じ行を同じ順番とバッチのまま保存する場合（理由・ROI・TLF・「作り直す」だけの変更）は、順序の種類を保ちます。自動の順序のまま「作り直す」や既存のプロジェクトが変わったときは、同じリクエストの中で並べ直します。rowId を保った行は、アンカー・依存・基準プロジェクトの印・既存のプロジェクト・重複の注意を保ちます。新しい行と ROI × TLF を変えた行は、所有者のプロジェクトと照合し直します。
  • CSV の読み込み（POST /plans/{id}/rows/import）は、自動の順序の下書きでは全体を並べ直して自動のまま、手動の順序の下書きでは行を末尾に足します。
  • 既存のプロジェクト（matchExistingProject）：同じ ROI × TLF（大文字小文字・空白を無視。削除したプロジェクトは数えない）の、完成して成果物のある自分のプロジェクトがあれば、行に「既存」（existing = { projectId, name }）とリンクが付き、最後のバッチに並び、確定すると作らずに完了になります（見積もりにも費用にも入らない）。確定までにそのプロジェクトを削除したときは、行は作られます。まだ完成していない同じ ROI × TLF のプロジェクトがあれば注意（duplicateOf）とリンクが出るだけで、確定すると別に作ります。
  • 作り直す：既存があっても作りたい行は、編集画面で「作り直す」に印を付けて保存します（rebuild: true）。既存のプロジェクトは外れて作られ、この選択は行に残るので、下書きを作り直しても「既存」に戻りません。印を外して保存（rebuild: false）すると元に戻ります。
  • 設定：オーケストレーターのモデル（下書き・再計画・行の PR の AI レビュー）、エージェントのモデルと推論の強さ（各行の BRA）、調査モード（既定オン）。どちらのモデルも「デフォルト」なら確定時に設定のデフォルトのモデルに決まります。v0.37.0 より前の計画はオーケストレーターのモデルを持たず、行のモデルを両方に使います（orchestratorModelOf）。粒度方針はオーケストレーターが書くもので、所有者は編集できません（PUT /plans/{id} で送ると 400「粒度方針はオーケストレーターが決めます」）。
  • Canon：「なし」「既存の Canon」（自分が所有する Canon。共同編集者の Canon は不可）「新しい Canon」（名前の初期値は計画の名前）から選びます（6.11）。

6.8 手順 4：確定する

「確定して開始」（POST /plans/{id}/confirm）を押すと、見積もりを確かめてから開始します。確定では次のことを行います。

  1. 確認：行が 1 つ以上あること、所有者がジョブを実行できるキーを持つこと（無ければ 400）、選んだ各モデルをティアが許すこと（403）。Canon のある計画では、選んだ既存の Canon がまだ所有者のものであること（409）。
  2. 固定：オーケストレーターのモデル、各行のエージェントのモデル（選んだもの、無ければ所有者かデプロイの既定をティアに通したもの）、推論の強さ、調査モード、返答の言語（UI の言語）、ハーネスのルール harnessRules。後のデプロイでルールが上がっても、計画の行はすべて確定時のルールで作られる。
  3. 既存の再確認：既存のプロジェクトがある pending の行を、まだ削除されず、成果物つきで完成しているか確かめ直す。外れていれば照合し直し、無ければ作る（confirmed のイベントに existingGone として数える）。
  4. 並べ直し：自動の順序の計画は、その時点の実効の同時実行数でもう一度並べる（orderDraft）。既存で済む行は done（projectId = そのプロジェクト、completedAt）にする（Canon のある計画の扱いは 6.11）。
  5. Canon：「新しい Canon」なら、ここで計画の粒度方針を方針にして作る（非公開・空・rev 0）。
  6. 開始：見積もり（planEstimate）を保存して RUNNING にし、ランナーを 1 回すぐに動かす（最初の行が 1 分待たずに始まる）。

確定はリースの中で行うので、別のタブで行を編集していても、確定後に行が変わることはありません（6.14）。自律実行の計画は、下書きを適用した直後にランナーが同じ関数で確定します（6.15）。

見積もりの計算式（estimatePlan）

時間 ≒ 基準プロジェクトの数 × 48 分（1 件ずつ）＋ Σ 本体のバッチ ⌈バッチの行数 ÷ 同時実行数⌉ × 48 分 ＋ 行の 20% × 15 分（手直し）÷ 同時実行数。費用 ≒ 行数 × $0.18〜0.39。既存・スキップの行は除き、質問への回答や PR の承認を待つ時間は含みません。

例：141 行（基準プロジェクト 3 行、残りを 1 バッチ）なら、同時実行数 1 で約 120 時間、4 で約 32 時間、8 で約 18 時間、12 で約 13 時間、16 で約 10 時間。

6.9 手順 5：実行 ― ランナーの 1 ステップ

実行はランナー（Lambda planRunner）が進めます。EventBridge の rate(1 minute) で毎分動き、確定・再開・リトライの直後にも 1 回動きます。DRAFTING・RUNNING・PAUSED の計画ごとに、計画の META に 90 秒のリース（楽観的な条件付き書き込み）を取り、取れなければその計画は飛ばします。1 ステップは次の順に進みます。

段内容
1. 行を追う（syncRow）starting / running / question の行のプロジェクトを見る。待機・実行・仕上げ中 → running、回答待ち → question、完了 → done（Canon のある計画では push、6.11）、失敗 → 試行が 2 回（MAX_ROW_AUTO_RETRIES）未満なら同じプロジェクトのまま pending（自動リトライ）、それ以上なら attention。回答待ちのまま 7 日で失敗 → リトライせず attention。計画の外で止められた・削除された → attention。
2. バッチを進める実行中の計画だけ。いまのバッチとそれより前に pending・starting・running の行が無くなったら、待つ行のある次のバッチへ activeWave を進める。question と attention の行は待たない（その行だけが止まる）。戻ることはない。
3. 行を始めるいまのバッチとそれより前の pending の行を（バッチ, 順番）の順に、空き枠の数だけ始める。空き枠 = min(全体の上限 − 全員の待機・実行・仕上げ中のジョブ, 1 人の上限 − 所有者のジョブ)。待機中のジョブも数えるので、始められないものは積まない。始める前に所有者を確認し、無効・キー無し・モデル不許可なら計画を一時停止する。新しい行は、Project ID を予約 → 行を確保（pending → starting、状態を条件に）→ POST /projects と同じ関数でプロジェクトを作る（planId・計画のハーネスのルールつき）→ running。プロジェクトのある行（自動・手動のリトライ、中止で止めた行）は、POST /projects/{id}/retry と同じ関数で成果物から続ける。開始の例外も試行に数え、最後は attention（start_failed）。1 行ごとに計画を読み直し、一時停止・中止なら止める。
4. 完了すべての行が done か skipped なら COMPLETED。
  • 所有者の確認：行を始める前に、POST /projects と同じく所有者を確かめます。アカウントが無効・キーが無い・選んだモデルをティアがもう許さないときは計画を一時停止します（owner_disabled / no_key / model_not_allowed）。所有者が選ばず既定で決まったモデルなら、ティアの既定のモデルに置き換えて続けます。
  • 枠：待機中のジョブも数えるので、始められないものは積みません（janitor は 24 時間待機したジョブを失敗にする）。実行中のジョブの上限は、ディスパッチャーが別に守ります。
  • 新しいプロジェクトのチャットには「CoBRAC オーケストレーターが開始」の通知（sys.planStarted）が出ます。計画の中止で止めたジョブには sys.planCancelled が出ます。中止の途中で始まった行は、すぐに止めます。
  • 計画が作ったプロジェクトは通常のプロジェクトと同じ画面で開け、ヘッダーに計画へのリンクが出ます。来歴として Projects.planId・Jobs.planId（行の初回とリトライのジョブ。そのプロジェクトで手で始めたリトライも含む）、版の manifest の生成条件に planId が残ります。オーケストレーターは BRA-DB には登録しません（登録は版ごとに所有者が行う、第 5 部）。

典拠：packages/api/src/lib/planRunner.ts（advancePlan・syncRow）・runs.ts（createProject・queueRetry・stopProject）、packages/shared/src/plan.ts

6.10 バッチごとの並べ直し・再計画・提案

自動の順序（ordering: "auto"）の計画では、バッチが終わるたびに残りの行を見直します。手動の順序の計画では行いません。

  1. アンカーを実物で置き換える（ランナー）：完了した行（既存で済んだ行を除く）で、アンカーがまだ used でないものについて、そのプロジェクトの users/{owner}/{projectId}/workspace/{projectId}_HCD/uc.json を読み（1 ステップ 20 件まで。1 つのバッチに入る数より多い）、読めてアンカーがあれば（anchorsOfUcJson：すべての UC と Collection の Descriptor のアンカー）、その行のアンカーを置き換える（anchorsSource: "used"）。予想と違った重なりが次の並べ直しに反映される。
  2. 並べ直す（ランナー）：いまのバッチが終わり（そのバッチとそれより前に pending・starting・running の行が無い）、後のバッチに動かせる行（isMovableRow：pending・プロジェクト無し・既存でない）があり、このバッチでまだ並べ直していなければ（lastReplanWave）、replanRows(rows, activeWave, effective) が動かせる行を、いまのアンカーとハブの値で次のバッチから並べ直す。まだ始まっていない基準プロジェクトは基準プロジェクトのまま。新しいバッチは行がまだ pending のときだけ書き、lastReplanWave をそのバッチにする（イベント replanned：バッチと動かした行）。始まった・実行中・回答待ち・完了・要対応・スキップ・中止の行と、リトライ（プロジェクトのある pending）は動かない。その後、activeWave を 6.9 のとおり進める。
  3. 再計画のジョブ（LLM のジョブ）：同じステップで、LLM に変更の提案を求める（replan = { kind: "replan", status: "waiting", wave, requestedBy: "runner" }。待機・実行中の再計画があれば求めない）。下書きと同じく枠が空いてから積み（入力の種類は replan、終わったバッチ wave とすべての行）、このステップで行を始める前に積むので、その枠を使う。一時停止中は積まない。回数を抑える（replanJobDue）：最初のバッチ（最初の基準プロジェクト＝主なハブ）が終わった直後に 1 回、その後は作る行（既存・スキップ・中止を除く）の 1 割（最低 1 行）が前回の後に終わるごとに 1 回で、1 つの計画で約 10 回（MAX_REPLAN_JOBS）まで。10 行までの計画はバッチごと。同時実行数 1 ではバッチが 1 行ずつなので、毎バッチだと行と同じ数のジョブと枠の待ちがかかるため。並べ直し（2）は毎バッチ行う。
  4. 提案を保存する（ランナー）：ジョブが完了すると、各提案を PROP#<proposalId>（状態 open、ジョブとバッチつき）として保存し、再計画を done にする（イベント proposals_received）。方針の提案はこのとき反映する（下の表）。失敗したら再計画を failed にして（イベント replan_failed）、計画はそのまま進む。計画が中止・完了したときに待機・実行中の再計画は cancelled にし、ジョブを止める（dropReplan）。

行の追加 add完了した行が共有する、または土台にしている回路で、どの行もまだ扱っていないもの行ができ（出所 llm）、動かせる行が並べ直される。同じ ROI × TLF の完成したプロジェクトがあれば作らずに完了。200 行に達していれば 409
行の削除 remove完了した行がすでに扱っている、まだ始まっていない行その行をスキップ
粒度方針 policy完了した行が、方針より細かく回路を切る必要があったなど承認は要らない。結果を保存した時点で反映され、「オーケストレーターが反映」として残る
  • 提案は、所有者が承認（POST /plans/{id}/proposals/{proposalId}/accept）するまで計画を変えません。却下は …/reject です。どちらも計画が RUNNING か PAUSED、提案が open のときだけで、ほかは 409 です。提案には decidedAt / decidedBy が残り、accepted / rejected になります（イベント proposal_accepted / proposal_rejected）。決定済みの提案は、画面の履歴の下にまとめて出ます。何も提案しないことも多くあります。
  • 追加の承認：計画が 200 行なら 409。スキップでない行に同じ ROI × TLF があれば、提案は「無効」（stale）になり 409。新しい行は pending（出所 llm、予想のアンカー、依存、既存・重複の照合つき。照合では計画自身のプロジェクトを除く）で、既存のプロジェクトがあればすぐに done です。動かせる行を replanRows でいまのバッチの後に並べ直します（いまのバッチで枠を待っている行はバッチを保ち、バッチの付かなかった新しい行は最後のバッチの後に置く）。
  • 削除の承認：行がまだ動かせる（始まっていない）ときだけで、そうでなければ提案は stale になり 409。行をスキップします。
  • 方針の提案は open になりません。結果を保存した時点で（storeProposals）accepted・decidedBy: "runner" として保存し、方針を置き換えます（イベント proposal_accepted、by = runner）。
