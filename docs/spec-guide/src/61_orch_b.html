6.5 アンカーと実行順序

実行順序は、下書きが付けたアンカー・依存・優先度から、プログラムが機械的に計算します。同じ行からは、いつも同じ順序になります。

アンカー

アンカーは、その行の ROI と、主な入力元・出力先の領域を、SABRA の単位で表した ID です。形は UC Descriptor のアンカーの部分と同じで（2.5）、次の 3 種類があります。

  • HOMBA の ID（DHBA 側の領域）
  • BNA の領域のペア
  • BNA の群

行どうしを比べるときは、BNA の群をその領域のペアに展開してから比べます。そのため、IFG の群をアンカーに持つ行と、IFG の 1 つの領域を持つ行は、アンカーを共有します。HOMBA の ID はそのまま比べます。画面の各行には、最初の 4 個のアンカーと残りの数が出ます。

計算の 3 段階

  1. ハブの値：その行とアンカーを 1 個以上共有する、ほかの行の数です（画面の「ハブ n」）。
  2. 基準プロジェクトのバッチ：ほかの行に依存しない行を、ハブ・優先度・行 ID の順に並べます。いちばん上の行と、ハブがその 60% 以上の行を、最大 3 行まで基準プロジェクトにします。基準プロジェクトは 1 行ずつ自分のバッチ（1、2、3）を持ち、ほかのバッチより先に 1 件ずつ作ります。どの行もアンカーを共有しないとき、または行が 1 つのときは、基準プロジェクトを作りません。
    多くの行が使う回路を先に 1 回だけ組み立て、その完成したプロジェクトを、あとの再計画に使うためです。
  3. 本体のバッチ：残りの行を依存の位相順（Kahn のアルゴリズム）に取り出します。同じ順位の行は、ハブの大きい順、優先度の高い順、行 ID の順です。各行は、次の条件をすべて満たす、いちばん早いバッチに入れます。
    • 依存する行（と基準プロジェクト）より後
    • バッチの行数が同時実行数未満
    • バッチの中に、アンカーを 2 個以上共有する行がいない
    同じ回路を作る 2 つの行が、同時に走らないようにするためです。依存が循環していれば、循環の外の何にも依存しない最上位の行で切ります。

例：言語の計画（同時実行数 3）

アンカーを領域名で略記した例です。実際のアンカーは HOMBA や BNA の ID です。

行TLFアンカー（略記）依存ハブ結果
R1音韻処理STG・SMG・IFG44—2基準プロジェクト・バッチ 1
R2発話IFG44・PMv・Put—2基準プロジェクト・バッチ 2
R3語彙意味アクセスMTG・ATL—1バッチ 3
R4文理解MTG・ATL・IFG45—1バッチ 4（R3 と 2 個共有）
R5復唱STG・SMG・IFG44・PMvR1・R22バッチ 3（依存があるので基準プロジェクトにならない）
R6読字FG・ITG—1バッチ 3
R7書字FG・SPL—1バッチ 4（バッチ 3 が満杯）

補足：R1〜R7 のハブは、R1・R2・R5 が 2、ほかが 1 です。基準プロジェクトの候補は依存のない行なので、R5 はハブが 2 でも基準プロジェクトになりません。しきい値は max(1, ⌈2 × 0.6⌉) = 2 なので、R1 と R2 が基準プロジェクトです。本体は R5（ハブ 2）→ R3 → R4 → R6 → R7 の順に置かれます。R4 は、バッチ 3 にまだ空きがあっても R3 と 2 個共有するので、バッチ 4 に入ります。R7 は、バッチ 3 が 3 行で満杯なので、バッチ 4 に入ります。

フロー実行

順序の種類が「自動」で確定した計画は、フロー実行で進みます。バッチは区切りではなく、始める順の目安になります。開始待ちの行は、次の 3 つの条件を満たした時点で始まります。どの行の枠が空いても、すぐに次の行で埋めます。手動の順序の計画は、バッチごとに進みます（6.6）。

条件内容画面の待ち理由
依存依存する行がすべて完了している（Canon のある計画では、PR が承認されて Canon に入っている）。依存が循環していれば、自分を含む循環の依存は無視する「○○ の後」
基準プロジェクトアンカーを共有する基準プロジェクトが、すべて完了・スキップ・中止になっている。アンカーを共有しない基準プロジェクトどうしは並行して作る「基準 ○○ の後」
重なりまだ仕事が入っていない行（開始中・実行中・質問中・承認待ちの行と、プロジェクトのある開始待ちの行）との重なりの強さが 3 未満。強さは共有するアンカー 1 個につき 1 で、どちらかの ROI（最初のアンカー）なら 2。完了した行がすでに作った回路は 0.3 倍に数える「○○ の後」
  • 始める順：Canon に合わせた更新、リトライ、基準プロジェクトの順で、そのあとは後ろに依存する行の多い順（クリティカルパス）、ハブ、優先度、バッチ、並び順の順です。条件を満たして枠を待つ行には「次に開始」と出ます。承認待ちの上限（6.7）で止まった行には「承認待ちが多いため待機」、自律実行の費用の上限（6.8）で止まった行には「費用の上限」と出ます。
  • レーン：依存と、ハブでないアンカーでつながる行のまとまりです。行の 25% 以上かつ 3 行以上が持つアンカーはハブとして扱い、つながりに数えません。行数の多い順にレーン 1、2、… と番号を付けます。レーンは表示のためのもので、実行の条件にはなりません。
  • 見積もり：上の条件で 1 行 48 分として枠に詰めるシミュレーションに、手直しの時間（6.9）を足します。図 6.2 の例（同時実行数 3）では、条件を満たすのは R1・R3・R6・R7 です。R2 は R1 と IFG44 を共有する基準プロジェクトで、R4 は R3 と強く重なり、R5 は R1・R2 に依存するためです。3 つの枠に R1・R3・R6 が入り、48 分後に R2・R4・R7、96 分後に R5 が始まります。3 回分 × 48 分に手直しを足して約 151 分で、バッチごとに進めた場合（4 回分、約 199 分）より短くなります。レーンは R1・R2・R5、R3・R4、R6・R7 の 3 つです。

下書きの並べ方

  • 作る行（スキップでも既存でもない行）を、バッチ 1 から上の 3 段階で置きます。
  • 既存のプロジェクトで済む行は、ハブの値の計算にだけ数え、置いた最後のバッチに並べます。この行は作らず、基準プロジェクトの印も付けません。スキップした行は、自分のバッチを保ちます。
  • 行の並び順は、作る順に従います。バッチの順（基準プロジェクトが先）で、バッチの中はハブと優先度の順です。置かなかった行（既存・スキップ）は最後です。
  • 画面の各行には「ハブ n」と、アンカーを 2 個以上共有する行（「重なり」）が出ます。どちらも、スキップ以外の行について API が計画を返すたびに計算します。基準プロジェクトのバッチの見出しには「基準プロジェクト」と出ます。

実装

計算は packages/shared/src/planOrder.ts の orderPlanRows で、下書きの並べ方は orderDraft です。アンカーの形は HOMBA:<id>（DHBA 側）、BNA:<l>-<r>（BNA の領域のペア）、BNAG:<L2>（BNA の群）で、BNAG:IFG の行と IFG の 1 領域の行はアンカーを共有します。定数は、基準プロジェクトのしきい値 SEED_HUB_SHARE（0.6）、基準プロジェクトの最大数 MAX_SEED_ROWS（3）、同じバッチに入れない共有の数 OVERLAP_LIMIT（2）です。行の並び順は order、基準プロジェクトの印は seed です。GET /plans/{id} は、スキップ以外の行について hub と overlaps を返します。

フロー実行は計画の scheduling: "flow"（バッチごとは "waves"）で、計算は packages/shared/src/planFlow.ts にあります。始められる行と待ち理由は flowPlan、重なりの強さは overlapScore（しきい値 STRONG_OVERLAP = 3、完了した回路の重み COVERED_WEIGHT = 0.3）、レーンは planLanes（ハブの割合 HUB_ANCHOR_SHARE = 0.25、HUB_MIN_ROWS = 3）、見積もりは simulateFlowMinutes です。GET /plans/{id} は、フロー実行の計画の行に lane と wait を付けます。

典拠：packages/shared/src/planOrder.ts（orderPlanRows・orderDraft）・planFlow.ts、packages/api/src/lib/planOps.ts

6.6 実行とバッチごとの見直し

確定した計画は、ランナーが進めます。ランナーは毎分動き、確定・再開・リトライの直後にも 1 回動きます。下書き作成中・実行中・一時停止中の計画ごとに、計画に 90 秒のリースを取り、取れなければその計画を飛ばします。本節では、行の状態を画面の名前（開始待ち・実行中・質問中・完了・要対応・スキップなど）で表記します。状態の一覧は 6.12 にあります。

ランナーの 1 ステップ

手順内容
1. 行を追う開始中・実行中・質問中の行のプロジェクトを見る。待機・実行・仕上げ中なら実行中、回答待ちなら質問中、完了なら完了（Canon のある計画では push、6.7）。失敗したときは、試行が 2 回未満なら同じプロジェクトのまま開始待ちに戻し（自動リトライ）、2 回に達していれば要対応にする。回答待ちのまま 7 日たって失敗したときは、リトライせず要対応にする。計画の外で止められた・削除されたときも要対応にする
2. バッチを進める実行中の計画だけ。現在のバッチとそれより前に、開始待ち・開始中・実行中の行がなくなったら、待つ行のある次のバッチへ進める。質問中と要対応の行は待たない（その行だけが止まる）。前のバッチに戻ることはない。フロー実行の計画では、現在のバッチを「未完了の行のあるいちばん早いバッチ」にするだけで、表示のためにしか使わない
3. 行を始める現在のバッチとそれより前の開始待ちの行を、バッチと並び順の順に、空き枠の数だけ始める（下の「枠の使い方」）。フロー実行の計画では、6.5 の条件を満たす行を、6.5 の始める順に始める。1 行ごとに計画を読み直し、一時停止・中止されていれば止める
4. 完了すべての行が完了かスキップなら、計画を完了にする

空き枠は、次の 2 つの小さいほうです。

  • 全体の上限 − 全員の待機・実行・仕上げ中のジョブの数
  • 1 人の上限 − 所有者のジョブの数

待機中のジョブも数えるので、始められないものは積みません。janitor は 24 時間待機したジョブを失敗にします。実行中のジョブの上限は、ディスパッチャーが別に守ります（8.3）。

行の始め方

  • 新しい行：Project ID を予約し、状態を条件に行を確保して（開始待ち → 開始中）、通常のプロジェクトの作成と同じ関数でプロジェクトを作り、実行中にします。プロジェクトには計画の ID と、計画のハーネスのルール（確定時に固定したもの、6.9）を付けます。開始中のまま 2 分以上残った行は、予約した ID のまま開始待ちに戻すので、二重に作ることはありません。
  • プロジェクトのある行（自動・手動のリトライ、中止で止めた行）：通常のリトライと同じ関数で、成果物から続けます。
  • 開始の失敗：開始の例外も試行に数え、試行が尽きたら要対応にします。
  • 所有者の確認：行を始める前に、通常のプロジェクトの作成と同じく所有者を確認します。アカウントが無効、キーがない、選んだモデルを利用承認の Tier がもう許さない、のどれかなら計画を一時停止します。所有者が選ばず既定で決まったモデルなら、その Tier の既定のモデルに置き換えて続けます。

枠の使い方

1 ステップの中で、ランナーは空き枠を次の順に使います。ジョブは 1 件で 1 枠を使います。

  1. 自律実行の計画で、できあがった回答をエージェントに渡す（再開したプロジェクトのジョブが枠を使う）
  2. 自律実行の計画で、回答・解決の行のジョブを依頼する（質問への回答が先）
  3. 待っている再計画のジョブを積む
  4. Canon のある計画で、PR の判断のジョブ（自律実行）か AI レビュー（人が対応する計画）を依頼する（6.7）
  5. 新しい行と、リトライ・更新を待つ行を始める

フロー実行の計画では、始められる行があるあいだ、オーケストレーター自身の AI のジョブ（行のジョブ・再計画・PR の AI レビューと判断）は、実効の同時実行数の 3 分の 1（切り上げ。6 なら 2）までしか枠を使いません。行が AI を待つあいだも、ほかの行が枠を使えるようにするためです。できあがった回答をエージェントに渡すことは、この制限を受けません。

質問と要対応の行

エージェントが質問した行や要対応になった行は、その行だけが止まり、ほかの行は進み続けます。

行自律実行の計画人が対応する計画
質問中回答のジョブがオーケストレーターの AI として質問を読み、個別に答える。回数の上限はない（6.8）所有者が計画の画面の質問箱か、プロジェクトの画面で答える（6.9）
要対応解決のジョブがエラーを読み、「リトライ」か「スキップ」を選ぶ（6.8）所有者が「リトライ」か「スキップ」を選ぶ（6.9）

自律実行の計画でも、所有者は要対応の行のボタンで先に決めたり、質問に先に答えたりできます。そのときは、ジョブの結果を使わずに捨てます（6.8）。

作られたプロジェクト

  • 新しいプロジェクトのチャットには「CoBRAC オーケストレーターの計画「…」から開始しました。」と出ます。計画の中止で止めたジョブには「CoBRAC オーケストレーターの計画が中止されたため、ジョブを停止しました。」と出ます。中止の途中で始まった行は、すぐに止めます。
  • 計画が作ったプロジェクトは、通常のプロジェクトと同じ画面で開けます。ヘッダーには計画へのリンクが出ます。
  • プロジェクトは、行を始めた時点の計画の方針を持ちます（planPolicy）。その範囲・粒度・根拠が、調査と HCD の指示に「Policy of the plan」の節として加わります。ROI・TLF と食い違うときは ROI・TLF に従って判断ログに書き、Canon があれば Canon の定義を優先します。
  • 来歴として、プロジェクトとジョブに計画の ID が残ります。ジョブは行の初回とリトライのジョブで、そのプロジェクトで手で始めたリトライも含みます。版の manifest の生成条件にも計画の ID が残ります（4.5）。
  • オーケストレーターは BRA-DB には登録しません。登録は版ごとに所有者が行います（第 7 部）。

バッチごとの見直し

順序の種類が「自動」の計画では、バッチが終わるたびに残りの行を見直します。下書きの直後は自動で、自律実行の計画はそのまま自動で進みます。所有者が行を手で並べ替えた計画（手動の順序、6.9）では見直しません。

フロー実行の計画では、手順 1 のアンカーの置き換えは同じように行いますが、手順 2 の並べ直しはしません。始める順は毎ステップ、実物のアンカーで計算し直すためです。再計画のジョブは、最初の行が完了した後に 1 回、その後は作る行の 1 割（1 行以上）が前回のあとに終わるごとに 1 回求めます。

  1. アンカーを実物で置き換える：完了した行（既存で済んだ行を除く）のうち、アンカーがまだ「実物」でないものについて、そのプロジェクトの HCD の uc.json を読みます（1 ステップ 20 件まで。1 つのバッチに入る数より多い）。読めてアンカーがあれば、すべての UC と Collection の Descriptor のアンカーで、行のアンカーを置き換えます。予想と違った重なりが、次の並べ直しに反映されます。
  2. 並べ直す：次の条件がそろえば、動かせる行を、現在のアンカーとハブの値で、次のバッチから並べ直します。
    • 現在のバッチが終わった（そのバッチとそれより前に、開始待ち・開始中・実行中の行がない）
    • 後のバッチに動かせる行（開始待ちで、プロジェクトがなく、既存でもない行）がある
    • このバッチでまだ並べ直していない
    まだ始まっていない基準プロジェクトは、基準プロジェクトのままです。新しいバッチは、行がまだ開始待ちのときだけ書きます。始まった行、実行中・質問中・完了・要対応・スキップ・中止の行と、リトライを待つ行（プロジェクトのある開始待ちの行）は動きません。そのあと、上の手順 2 のとおりバッチを進めます。
  3. 再計画のジョブ：同じステップで、LLM に変更の提案を求めます。待機中・実行中の再計画があれば求めません。下書きと同じく枠が空いてから積み、このステップで行を始める前に積むので、その枠を使います。入力は、終わったバッチとすべての行です。一時停止中は積みません。
  4. 提案を保存する：ジョブが完了すると、各提案を保存し、再計画を完了にします。方針の提案はこのとき反映します。自律実行の計画では、行の追加・削除の提案もこのとき反映します（6.8）。失敗したら再計画を失敗にして、計画はそのまま進みます。計画が中止・完了したときは、待機中・実行中の再計画を取り消し、ジョブを止めます。

再計画の回数：並べ直し（手順 2）は毎バッチ行いますが、再計画のジョブは回数を抑えます。最初のバッチが終わった直後に 1 回行います。最初のバッチは最初の基準プロジェクトで、主なハブにあたります。その後は、作る行（既存・スキップ・中止を除く）の 1 割が前回のあとに終わるごとに 1 回行います。1 割が 1 行に満たないときは 1 行とするので、1 つの計画で約 10 回までになり、10 行までの計画ではバッチごとになります。同時実行数が 1 だとバッチが 1 行ずつになるので、毎バッチにすると、行と同じ数のジョブと枠の待ちがかかるためです。Canon のある計画では、再計画は、バッチの行の PR がすべて承認されてから行います（6.7）。

再計画の提案

提案内容反映したとき
行の追加完了した行が共有する、または基にしている回路で、どの行もまだ扱っていないもの行ができ（出所 llm）、動かせる行が並べ直される。同じ ROI × TLF の完成したプロジェクトがあれば作らずに完了。200 行に達していれば反映できない
行の削除完了した行がすでに扱っている、まだ始まっていない行その行をスキップ
方針完了した行が方針と合わなかった（粒度より細かく回路を切る必要があった、根拠の求める証拠がなかった、など）。方針全体を置き換える承認は要らない。結果を保存した時点で反映し、「オーケストレーターが反映」として残る

提案を反映する時期は、進め方で違います。何も提案しないことも多くあります。

  • 自律実行の計画：行の追加・削除も、結果を保存したその場でランナーが反映します。反映には所有者の承認と同じ処理を使い、決めた人はランナーとして残ります。反映できない提案は「無効」になります（6.8）。
  • 人が対応する計画：行の追加・削除の提案は、所有者が承認するまで計画を変えません。承認・却下できるのは、計画が実行中か一時停止中で、提案が未決のときだけです。決めた提案には、決めた時刻と人が残ります。決定済みの提案は、画面の履歴の下にまとめて出ます。

行の追加・削除を反映するときの規則は、どちらの進め方でも同じです。

  • 追加：計画が 200 行なら反映できません。スキップでない行に同じ ROI × TLF があれば、提案は「無効」になります。新しい行は開始待ちで、出所は llm、予想のアンカーと依存を持ち、既存・重複の照合を受けます。照合では計画自身のプロジェクトを除き、既存のプロジェクトがあればすぐに完了にします。そのうえで、動かせる行を現在のバッチの後に並べ直します。現在のバッチで枠を待っている行はバッチを保ち、バッチの付かなかった新しい行は最後のバッチの後に置きます。
  • 削除：行がまだ動かせる（始まっていない）ときだけです。そうでなければ提案は「無効」になります。行はスキップになります。
  • 方針：未決にはならず、結果を保存した時点で、ランナーが承認したものとして保存し、方針を置き換えます。

実装

  • ランナー：Lambda planRunner を EventBridge の rate(1 minute) で動かす。1 ステップは advancePlan、行を追うのは syncRow。リースは計画の META への楽観的な条件付き書き込み。現在のバッチは activeWave。
  • フロー実行：始める行は flowCandidates（flowPlan に承認待ちの上限と費用の予約をかけたもの）、現在のバッチは flowActiveWave、AI のジョブの枠は controlSlotCap。
  • 行の状態：開始待ち pending、開始中 starting、実行中 running、質問中 question、完了 done、要対応 attention（理由 failed・question_timeout・cancelled_outside・project_deleted・start_failed）、スキップ skipped、中止 cancelled。自動リトライの回数は MAX_ROW_AUTO_RETRIES（2）。
  • 行の開始：プロジェクトの作成は POST /projects と同じ createProject（planId と計画の harnessRules 付き）、続きからの開始は POST /projects/{id}/retry と同じ queueRetry、止めるのは stopProject。一時停止の理由は owner_disabled / no_key / model_not_allowed。
  • 通知と来歴：チャットの通知は sys.planStarted・sys.planCancelled。来歴は Projects.planId・Jobs.planId と版の manifest の planId。
  • 見直し：完了した行の users/{owner}/{projectId}/workspace/{projectId}_HCD/uc.json を anchorsOfUcJson で読み、アンカーの出所を anchorsSource: "used" にする。動かせる行は isMovableRow、並べ直しは replanRows(rows, activeWave, effective)、最後に並べ直したバッチは lastReplanWave（イベント replanned：バッチと動かした行）。
  • 再計画のジョブ：replan = { kind: "replan", status: "waiting", wave, requestedBy: "runner" }。回数の判定は replanJobDue（フロー実行は flowReplanDue で、前回の完了数を replanDone に持つ）、上限は MAX_REPLAN_JOBS（10）。取り消しは dropReplan。イベントは proposals_received・replan_failed。
  • 提案：PROP#<proposalId> に、状態 open・ジョブ・バッチ付きで保存する（storeProposals）。承認は POST /plans/{id}/proposals/{proposalId}/accept、却下は …/reject。条件に合わなければ 409（200 行に達した追加、「無効」stale になった提案を含む）。決めた提案は decidedAt / decidedBy を持ち、accepted / rejected になる（イベント proposal_accepted / proposal_rejected）。方針の提案は accepted・decidedBy: "runner" で保存する（イベント proposal_accepted、by = runner）。

6.7 Canon のある計画

計画に Canon を 1 つ決めると、完成した行をその Canon に取り込みながら進みます。自律実行で作った計画は、既定で計画の名前の新しい Canon を持ちます（6.3）。行が完了になるのは、その行の PR が承認されたときです。

  • 自律実行の計画：判断のジョブが PR を判定し、ランナーがその判定を所有者の代わりに反映します（6.8）。
  • 人が対応する計画：Canon の所有者か共同編集者が PR を承認します。ランナーは承認・却下・回答をいっさい行いません。

Canon を「なし」にした計画は、6.6 のとおりに動き、Canon を読みません。

Canon の選択と確定

  • 選択：Canon は下書きの間だけ選べます。選べるのは「なし」「既存の Canon」「新しい Canon」です。既存の Canon は、所有者が所有する削除されていない Canon だけです。プロジェクトは所有者の Canon にしか入れないので、共同編集者として参加している Canon は選べません。新しい Canon の名前の初期値は、計画の名前です。1 つの計画に Canon は 1 つまでです。
  • 確定後：Canon は変えられません。計画の画面には、読み取り専用で Canon へのリンクと最新の rev が出ます。削除された Canon は「Canon が見つかりません」と出ます。
  • 確定のとき：選んだ既存の Canon がまだ所有者のものでなければ、確定できません。「新しい Canon」は、計画の方針の「粒度」を粒度方針にして、非公開・空・rev 0 で作ります。作った直後に計画に保存するので、確定がそのあとで失敗しても、もう 1 つ作ることはありません。
  • 既存のプロジェクトで済む行：そのプロジェクトの所属で扱いが変わります。
    • すでにこの Canon に入っている：完了にする
    • どの Canon にも入っていない：開始待ちのまま自分のバッチの番を待つ（基準プロジェクトのゲートやバッチの順も、ほかの行と同じ）。番が来たら、作らずに Canon に入れて push する
    • ほかの Canon に入っている：人が対応する計画では要判断にする。自律実行の計画では、確定のときに既存のプロジェクトを外し、この Canon のために作り直す（6.8）

開始と push

  1. 開始：ランナーは Canon を 1 ステップに 1 回読みます。新しい行のプロジェクトは、最初のジョブを積む前に Canon に入り、その時点の最新の rev に固定されます。開始の途中で止まった行を戻すときも同じです。行には固定した rev を記録します。
    • 失敗したプロジェクトのリトライは、先に最新の rev に固定し直し（どの Canon にも入っていなければ入れる）、新しい rev を記録します。
    • プロジェクトがすでに完成している開始待ちの行（確定のときに取り込んだ既存のプロジェクト、手で完成させたもの）は、ジョブを積まず試行も数えずに、すぐ push から始めます（どの Canon にも入っていなければ、最新の rev で入れる）。
  2. push：Canon のある計画の行のプロジェクトが完成すると、ランナーが push します。
    • プロジェクトは計画の Canon に入っていなければなりません。どこにも入っていなければ最新の rev で入れ、ほかの Canon に入っていれば要判断にします。
    • push には、プロジェクトの画面の push と同じ関数を使い、PR を作ります（5.6）。PR には計画の ID が記録されます。
    • push がエラーになれば要判断にし、エラーを行に残します。
    • 成功すれば、PR の差分の要約、Canon が進んだか、更新の回数から、行の遷移先を決めます（下の表）。「Canon が進んだ」とは、Canon の最新の rev が、行が固定した rev（なければプロジェクトが固定した rev）より後であることです。
push の結果自律実行の計画人が対応する計画
エラーの衝突なし（警告・要確認は審査に回す）承認待ち。基準プロジェクトを含むすべての行が、判断のジョブを待つ（6.8）承認待ち。本体の行は AI レビューを依頼する。基準プロジェクトは依頼しない
エラーの衝突あり。行の固定より後に Canon が進んだ開始待ちで Canon に合わせた更新を待つ（フォローアップは 1 行 3 回まで）開始待ちで Canon に合わせた更新を待つ（2 回まで）
エラーの衝突あり。Canon は進んでいない開始待ちで、Canon に合わせる修正のフォローアップを待つ（3 回まで、6.8）要判断（衝突が残る）
更新の回数を使い切っても、エラーの衝突が残る要判断（更新の上限）。自律実行の計画では、解決のジョブが扱いを選ぶ
push の失敗、プロジェクトがほかの Canon にいる要判断

Canon に合わせた更新

更新を待つ行は、ほかの開始待ちの行と同じく、空き枠とバッチの順で始まり、自分のバッチを止めます。始める直前に PR を読み直し、その間に人が決めていればそれに従います。承認されていれば完了、却下・取り下げなら要判断、置き換えられていれば新しい PR で承認待ちです。

PR がまだ開いていれば、プロジェクトを最新の rev に固定し直し、フォローアップ（画面では「追加の指示」）のジョブを積みます。画面の「追加の指示」と同じ関数です。指示は「Canon rev N に合わせて更新」という固定のタイトルで始まり、続けて、古い固定から最新までに、このプロジェクトに関わって変わったことを書きます。行は実行中になり、更新の回数が 1 増え、固定した rev が最新になります。完成すると再び push し、新しい PR が開いている古い PR を置き換えます。

  • 回数・新しい固定・更新待ちの解除は、行を確保するとき（開始中にするとき）に、ジョブを積む前にまとめて書きます。途中で止まっても、上限を超える更新は起きません。
  • 開始に失敗したら、更新待ちと古い固定を戻し、回数は数えたままにします。
  • プロジェクトが計画の Canon にもう入っていない、または Canon がなくなっていれば、要判断にします。

画面では、更新を待つ行に開いている PR へのリンクと「Canon に合わせた更新を待っています」が、一度でも更新した行に「Canon に合わせた更新 n/m」が出ます。m はフォローアップの上限で、人が対応する計画では 2、自律実行の計画では 3 です。

PR の追跡

ランナーは毎ステップ、承認待ちの行、PR のある要判断の行、更新待ちの行の PR を読みます。一時停止中も読みます。

PR の状態行
承認された完了（要判断の行の PR が Canon で承認された場合も）
却下された要判断（PR の却下）。自律実行で判断のジョブが却下したときはスキップ（6.8）
取り下げられた要判断（PR の取り下げ）
置き換えられた（手で push した場合など）新しい PR を承認待ちで追う
開いたまま変化なし

PR の審査

  • 自律実行の計画：承認待ちのすべての行（基準プロジェクトも、手で push した PR を追う行も）に、判断のジョブを依頼します。判断のジョブの判定は、現在の Canon に対して差分を取り直してからランナーが反映します。規則は 6.8 にあります。
  • 人が対応する計画の AI レビュー：本体の行の PR だけに、所見を付ける LLM のジョブを依頼します。AI レビューは指摘だけで、判断はしません（5.8）。
    • ランナーは空き枠があれば、AI レビューを待つ承認待ちの行ごとに、所有者としてレビューを依頼します（1 件 1 枠、枠の使い方は 6.6）。モデルはオーケストレーターのモデル、キーは所有者のキー、言語は計画の返答の言語です。
    • PR が開いていなければ依頼をやめます。手で依頼したレビューが待機中・実行中なら、そのジョブを計画の依頼として数えます。
    • 行には「AI レビュー待ち」→「AI レビュー実行中」→「AI レビュー済み」と出ます。「AI レビュー済み」は PR の画面へのリンクで、要判断の行にも出ます。
    • 計画の PR の AI レビューの費用は、計画の費用に入ります（6.11）。

要判断の行

要判断（画面では「人の判断」）の行は、PR を自動では Canon に取り込めなかった行です。扱いは次の 3 つから選びます。

操作動き
「完了にする」行をそのまま完了に数え、完了の時刻を付ける。PR はそのまま Canon に残り、自動では取り込まれない
「もう一度 push」プロジェクトが完成した行だけ。行を実行中に戻して理由を消し、次のステップで push する。更新の回数は保つ
「スキップ」行をスキップにする
  • 自律実行の計画：解決のジョブが理由と PR を読み、この 3 つから選びます（6.8）。ただし、計画の Canon が見つからないことによる要判断は、所有者が決めます（下の「Canon が見つからないとき」）。
  • 人が対応する計画：所有者が、計画の画面の「人の判断」カードで、理由の文を見ながら選びます。各操作には確認があります。操作できるのは、計画が実行中か一時停止中のときです。

自律実行の計画でも、所有者はこのボタンで先に決められます。

PR から計画へ

すべての PR には、push したプロジェクトの計画の ID が記録されます。手で push したときも同じで、計画のないプロジェクトでは空です。Canon の PR の一覧と PR の画面には計画の ID のチップが出て、Canon の所有者には計画へのリンクになります（計画はその人のものです）。

基準プロジェクトのゲートと承認待ちの上限

基準プロジェクトのゲート
Canon のある計画では、基準プロジェクトは、その PR が承認される（または要判断が解決されるか、スキップされる）まで、あとのすべてのバッチを止めます。基準プロジェクトは同じバッチにあっても 1 件ずつ始まり、ほかの基準プロジェクトが実行中・承認待ち・要判断の間は始まりません。画面には「基準プロジェクトの PR の承認を待っています。」と PR へのリンク、または「基準プロジェクトに人の判断が必要です。」が出ます。基準プロジェクトの PR が先に承認されると、あとの行はその rev から作り始めます。自律実行の計画では、判断のジョブによる承認（またはスキップ）でゲートが開きます。フロー実行の計画では、基準プロジェクトが止めるのはアンカーを共有する行だけです（6.5）。
承認待ちの上限
承認待ちの行が 20 件に達すると、新しいバッチを始めません。現在のバッチの行は続きます。フロー実行の計画では、プロジェクトのある行（リトライと Canon に合わせた更新）だけを始めます。画面には「承認待ちの PR が n 件あるため、次のバッチを止めています。」と出ます。Canon の画面の「まとめて承認」（5.6）で、矛盾のない PR をまとめて承認できます。再計画も、バッチの行の PR がすべて承認されてから行います。

Canon が見つからないとき

計画の Canon が削除された、または所有者のものでなくなった場合の動きです。

  • 承認待ちの行と、完成して push するはずの行は、要判断（push の失敗。理由は「The plan's Canon was not found.」）になります。
  • 新しい行・リトライ・Canon に合わせた更新を始めようとすると、計画は自分で一時停止し、何も始めません。画面には「一時停止中: この計画の Canon が見つかりません（削除された可能性があります）。新しい行は Canon に入れられないため始めません。」と出ます。
  • 実行中の行は、ほかの一時停止と同じく、続いて追われます。
  • 所有者は、待っている行をスキップするか、計画を中止できます。自律実行の計画でも、ここは所有者が決めます。

承認待ちと要判断の行は枠を使わず、完了にも数えません。Canon のある計画は、すべての行が完了かスキップになったときに完了します。

実装

  • 行の状態：承認待ち review、要判断 decision。要判断の理由は conflicts（衝突が残る）・conform_limit（更新の上限）・pr_rejected・pr_withdrawn・other_canon・push_failed。行は prNo・canonRevision・conform・conformAttempts・aiReview・aiReviewJobId・lastError を持つ。
  • Canon の選択：PUT /plans/{id} { canon }（計画のリースの中で。下書き作成中や確定後は 409）。{ mode: "none" } は外す。{ mode: "existing", canonId } は META.canonId に保存し、所有者の Canon でなければ 404。{ mode: "new", name } は名前を POST /canons と同じく検査して META.canonNew = { name } に保存する。
  • 表示：GET /plans/{id} の canon = { canonId, name, headRevision }。削除された・所有者のものでなくなった Canon は missing: true、Canon がなければ null。
  • 確定：既存の Canon が所有者のものでなければ 409「この計画の Canon が見つかりません」。新しい Canon は createCanon（非公開・空・headRevision 0）で作り、すぐに canonId を保存して canonNew を null にする（イベント canon_created）。confirmed のイベントは Canon を記録する。
  • 開始：Canon は ownedCanon で読む。新しい行は createProject の beforeQueue で addCanonMember する。リトライの固定し直しは pinProject。
  • push：pushProject（POST /projects/{id}/canon/push と同じ）。遷移先は pushOutcome(summary, headMoved, conformAttempts, { autonomous }) で決める。headMoved は Canon の head が row.canonRevision（なければプロジェクトの固定）より後であること。更新の上限は MAX_CONFORM_FOLLOWUPS（2）、自律実行では AUTONOMOUS_MAX_FOLLOWUPS（3）。エラーの衝突なしで本体の行は aiReview: "wanted"。イベントは row_pushed / row_decision。
  • 更新：queueFollowup（POST /projects/{id}/followup と同じ）。タイトルは conformTitle、本文は canonFollowStatus から canonAlignInstruction が作る。イベントは row_conform。
  • PR の追跡：prOutcome。AI レビュー：requestAiReview（POST /canons/{id}/pulls/{no}/ai-review と同じ）。行は aiReview: "queued" と aiReviewJobId を持ち（イベント row_ai_review）、ジョブが終われば（完了・失敗・取り消し）aiReview を消して aiReviewJobId を残す。費用に入るのは、その planId の PR について所有者が実行した canon-review のジョブ。
  • 要判断の扱い：POST /plans/{id}/rows/{rowId}/resolve { action }（done / push）。所有者、計画が RUNNING か PAUSED、行が decision のとき、リースの中で。ほかは 409。push はプロジェクトが COMPLETED でなければ 409「完了したプロジェクトの行だけをもう一度 push できます」。スキップは …/rows/{rowId}/skip で、decision の行も受け付ける。イベント row_resolved に操作と元の理由が残る。
  • PR の記録：CanonPullRequestRecord.planId。上限：承認待ちの上限は PLAN_MAX_WAITING_PRS（20）。Canon が見つからないとき：一時停止の理由は canon_missing。
