2.9 調査ステップ（調査モード）

調査モードは、HCD の前に文献を調べるかどうかのプロジェクトの設定です。作成画面のモデルのメニュー（「v」）のスイッチで選び、既定はオンです（プロジェクトの researchMode。各ジョブは実行時の値を記録します）。作成後は変えられず、フォローアップと再試行も同じ設定で動きます。この設定ができる前のプロジェクトは値を持たず、調査なしで動きます。オフにすると調査ステップと調査の注記がなくなりますが、lit の道具は使えます。プロジェクトのヘッダに「調査モード: オン／オフ」が出ます。

調査ステップは新しい段ではありません（HCD → FRG → CSV → xlsx の並びは同じ）。HCD の前にエージェントの調査ターンが入り、ワーカーがその被覆を検査します。

エージェントがすること

調査の単位は、ROI の主な入力、出力、内部投射の候補です。エージェントは RESEARCH.md に従い、総説を入口にし、候補ごとに領域名の同義語、種、追跡法を変えて検索します。論文の要旨または全文を読み、支持の強さと、何を調べても見つからなかったかを分けて research.json（スキーマ research.schema.json）だけに書きます。内容は、計画、最大 40 件の候補の投射、候補ごとの検索文字列、証拠（Reference ID、PMID / DOI、種、測定法、層・細胞種、知見、要旨と全文のどちらを読んだか）、被覆（トレーサー研究・霊長類・齧歯類・層と細胞種ごとに found / searched_none / not_applicable）、状態（supported / weak / not_found / contradicted）、残った不足です。

ワーカーがすること

ワーカーは、イベントの流れから lit の呼び出しと Web 検索をすべて research_queries.jsonl に記録し（ジョブ ID、段、失敗時はエラー文）、ジョブに道具ごとの検索回数（searches）を数えます。検索ログはエージェントの申告ではなく、ワーカーが記録したものです。そのうえで checkResearch が次を検査します。

  • スキーマ。候補ごとに異なる検索が 2 件以上あり、少なくとも 1 件は PubMed か Europe PMC であること
  • research.json に書かれた検索文字列が、検索ログに同じ道具で残っていること
  • 被覆の値が証拠と合うこと（found には、追跡法・霊長類・齧歯類・層と細胞種の証拠が必要）
  • supported / weak / contradicted には証拠があり、not_found には無いこと。すべての証拠に PMID か DOI があること。支持以外と not_applicable には理由があること

問題は修正のターン（最大 2 回）でエージェントに戻します。不足が残っても実行は止めず、結果を research_check.json（done、outcome：passed / gaps / budget、要約、問題）に書いて HCD に進みます。done: true の作業場所では、以後の実行で調査を飛ばします。単なる検索回数の充足と、望ましい証拠が見つかったことは別です。残った不足は HCD とレポートの Limitations に引き継ぎます。

調査の予算
項目現行の値・規則
候補数最大 40（RESEARCH_BUDGET.maxCandidates）
検索候補ごとに異なる検索を 2 件以上。少なくとも 1 件は PubMed または Europe PMC
修正最初のターンの後、最大 2 回
時間調査ステップ全体で 60 分（RESEARCH_TIME_BUDGET_MIN）。時間切れのときに走っているターンは打ち切り、それまでに書かれた内容で HCD に進む（打ち切ったターンの使用量は Codex が報告しないので、ジョブの合計から抜ける）。残り 10 分未満では新しい修正ターンを始めない
推論レベル調査の本ターンはプロジェクト値と high の高い方。修正ターンはプロジェクト値と medium の低い方（fixTurnEffort）
費用の上限金額の上限は無い。費用は時間の予算で抑え、利用量の行に出る
見積もり作成画面のスイッチの横に、+10〜60 分と、入力 150 万〜600 万トークン（85〜90% がキャッシュ）・出力 4 万〜15 万トークンを選んだモデルの単価で換算した費用を出す（researchModeEstimate）。数件の実行からの概算で、実際の値は各ジョブの利用量

文献の道具 lit

lit は、ワーカーと同じコンテナで動く MCP サーバ（packages/worker/src/litMcp.ts・litsearch.ts）で、Codex がエージェントの道具として起動します。PMID と原文の引用にも使うので、調査モードの有無にかかわらずすべての BRA の実行で使えます。Web 検索もオンのままです。

道具返すもの
search_pubmed / search_europepmc関連順の検索結果（PMID、DOI、題、著者、年、雑誌、PMC の全文があるか）。既定 8 件、max_results で 1〜25 件
get_abstract1 本の論文の書誌と要旨
find_sentences指定した語を含む文を最大 8 文。オープンアクセスの全文があれば全文、なければ要旨から

要求は文献の照合と同じ HTTP クライアント（http.ts：15 秒のタイムアウト、タイムアウト・ネットワークエラー・429・5xx で 1 / 2 / 4 秒おいて 3 回まで再試行、Retry-After に従う、3 回続けて失敗した相手は 5 分休む）を通り、エージェントが道具を並列に呼んでも相手ごとに間隔を空けます（Europe PMC 200 ミリ秒、NCBI 350 ミリ秒）。1 回の呼び出しは 65 秒まで（MCP の道具のタイムアウト 90 秒より短い）です。Europe PMC がその 45% の時間で答えないときは、get_abstract と find_sentences は PubMed から書誌と要旨を、NCBI BioC 経由で PMC から全文を取り、どのサービスが失敗したかを note に書きます。それでも失敗した道具は、失敗したサービスと代わりの道具（search_pubmed ↔ search_europepmc）を返します。

調査の後の段と測定

調査モードでは、HCD・FRG の仕様とフォローアップに research_mode.md が付きます。調査をもとに BIF と接続を作ること（支持された証拠とトレーサー研究を優先し、弱い証拠は明示し、根拠があれば細胞種・層の UC を作る）、実際に読んだ文から引用すること、不足を Limitations に書くこと、FRG で理論と計算モデルを調べること、フォローアップで新しい主張を調べることを指示します。HCD と FRG の検証器は、調査モードの有無で変わりません。

調査ステップが終わると、ワーカーは終わり方・モデル・推論レベル・開始と終了・分・ターン数・打ち切りの有無・費用と使用量・候補数・支持された数・道具ごとの検索回数（成功 / 失敗）を research_check.json の metrics とジョブの researchStep に記録し、画面に要約の行を出し、CloudWatch に [research] start / [research] end を書きます。すべてのジョブは終了時に [metrics]（使用量、費用、分、道具ごとの検索）も書きます。

典拠：prompts/phases/RESEARCH.md、prompts/research_mode.md、packages/shared/src/research.ts（checkResearch・RESEARCH_BUDGET・researchModeEstimate）、packages/worker/src/pipeline.ts（runResearch）、litMcp.ts、litsearch.ts、http.ts

この段で判断してファイルを書くのはエージェント、書かれたファイルを検査するのはワーカーです。以下の規則は、エージェントへの指示（HCD.md と追加規則）であり、同時にワーカーの検証器（checkHcd）が確かめる条件でもあります。回路の名前の規則は第 3 部、Canon による制約は第 4 部にまとめます。

8 つの手順

ROI 規則（harnessRules 1 以上）

新規プロジェクトは 0.25.0 から harnessRules: 1、0.28.0 から harnessRules: 2 です（それ以前のプロジェクトは値を持たず、従来の検査のまま。複製は元の値を写す）。rules 1 以上では HCD の仕様の後ろに HCD_roi_rules.md が付き、HCD の検査に次が加わります。

規則内容
ROI 要素meta.json の roiElements[]（name、ucs[]：ROI 内部の UC かその Collection の Circuit ID）。各要素に、ほかの要素が挙げていない ROI 内部の UC が最低 1 つ必要（1 つの UC で VWFA と後部紡錘状回を兼ねない）。すべての ROI 内部の UC はどれかの要素に属する。roi が挙げる領域の数は要素の数を超えない（括弧の外のコンマ・セミコロン・and・&・+ で区切って数え、左右を表す語だけのものは数えない）
ROI の左右roiSide（both / left / right）と roiSideSource（利用者の ROI か指示が左右を指定していれば user、それ以外は assumed）。assumed は both でなければならず、判断ログに両側である旨（"bilateral" など）を書く。both では、side facet を持つ ROI 内部の UC には反対側の対が要る（または facet を外す）。left / right では反対側の ROI 内部の UC を置かない。機能が側性化しているだけで片側に限定しない
引用の使い回し（警告のみ）同じ pointersOnLiterature（と同じ図、または図なし）が異なる回路の接続を支えている。エージェントには戻さず、quote_check.json の reused と画面に出す

UC の粒度と Collection

UC の Uniform は、その HCD が選ぶ粒度での判断です。領域内の部分が異なる投射や機能を持つなら、エージェントは根拠を示して UC を分け、分けた元の領域は必要に応じて Collection（Uniform = FALSE、uc.json の collections[]）にします。領域や名前の付いた部位の違いで十分で、層・細胞種の証拠までは要りません。分ける理由は Collection の comments に必ず書きます。複数の SABRA 単位にまたがる送り手を 1 つの UC のまま残すときは uniformityNote で理由を書きます。Collection は構成関係を表すもので、接続の送り手・受け手や FRG の葉にはしません。Collection の検査とエラーコードは 3.9・3.10 にまとめます。

接続の根拠とインターフェース

BIF は文献が述べる組織間の投射、Connection はその根拠を UC 同士へ対応させたものです。接続レコード 1 行に文献 1 本を対応させ、同じ投射を複数の論文で支える場合は論文ごとに行を作ります（同じ送り手 → 受け手 → 文献は 1 回だけ）。各行に、種、測定法、論文中の領域名、UC との包含関係、原文または図への参照を持たせます。

2.11 FRG：機能と回路を突き合わせる

上からの分解と下からの解釈

FRG は、TLF を論理的に分解する作業と、HCD の回路が何を計算するかを読む作業を合わせます。どちらもエージェントが行う判断です。回路の形を写すだけにならないよう、エージェントは上からの分解を先に（UC や候補を見ずに）考え、重複や過剰な分解を整理します。

一方、ワーカーのコードは HCD の ROI 内部の接続から候補を計算し（findFrgCandidates）、frg_candidates.json に書いて FRG の依頼文の末尾に入れます。候補は HCD の検査のたびに作り直すので、FRG の段で HCD を変えても追従します。これは機械的に列挙した候補で、意味づけはしていません。

候補内容
経路（pathways）外から入力を受ける ROI の UC から、外へ出力する UC までの道筋。強連結のまとまり（ループは 1 つのまとまり）の上で、できるだけ多くのまとまりを覆うように貪欲に選ぶ（最大 12）。両端に外部の入力と出力を付ける
連結成分（components）ROI 内部のグラフの弱連結な部分
モチーフ（motifs）ペアでは表せない 3〜4 UC の形。ループ（全員を通る有向閉路）とフィードフォワードの三角形（A → B → C かつ A → C）、最大 40。鎖・収束・発散は UC を共有するペアで表せるので除く
ペア（pairs）接続のあるすべての組（pair / reciprocal）

すべての接続には符号（興奮・抑制・修飾）を付けます（コメント、なければ送り手の伝達物質から、classifyEdgeSign）。エージェントはそれぞれの候補を、Output Semantics、機能項目、符号、文献に照らして解釈します。

FRG の 8 手順

  1. 上からの分解：UC や候補を見ずに TLF を分解する（子の数は決めない）
  2. 最適化：重複や過剰な分解を整理する
  3. 下からの読み：各経路・モチーフが何を計算するか。すべての ROI の UC を最低 1 回読む
  4. 対応づけ：結果をレポートの ## FRG に表（sub-function (GN ID) / candidate (IDs and UCs) / outcome / action）で残す
  5. 接地：GN の規則（下表）を守って UC に結びつける。対応が無ければ機能分解を直すか、根拠をもって HCD に戻る
  6. インターフェース：子のインターフェースを合わせ、GN の内部で閉じる辺を除く。上へ合成し、TLF 全体では ROI の外部入力と外部出力になるようにする
  7. 機能の詳細：Requirement、Requirement realization、Capability、Mechanism
  8. レポート
対応の結果意味取る対応
matched下位の回路が上位の副機能を実現するペア / モチーフを GN にし、上へまとめる
top-down only副機能に対応する候補が無い上位 GN として残す・親へ統合、文献のある不足を HCD へ追加、ROI 外なら除外して限界へ記録
bottom-up only回路の候補に対応する副機能が無い分解で漏れた機能を加える、または別の GN で TLF に寄与する理由を書く
mismatch必要な UC 同士がつながっていないFRG の分解、または根拠のある HCD の接続を直す

制約を満たすための数合わせで UC や接続を足すことはできません（仮説モードで範囲が許す場合は 2.13）。

GN が表すもの

GN の意味は、UC の機能を並べたものにとどまりません。UC と、その間の接続による相互作用が実現する計算です。GN が UC の機能に加えるものは、それらの相互作用（インターフェースが除く内部の辺）が計算するものです。GN の Output Semantics は、GN の外へ出力する UC の値からワーカーが導出します。GN の規則はプロジェクトの harnessRules によって異なり、既存のプロジェクトの検査は変わりません。

規則rules 0〜1（0.28.0 より前のプロジェクト）rules 2（0.28.0 以降の新規。FRG_gn_rules.md）
GN の子の UC 数最大 2最大 2。3〜4 は motifNote（ペアに分けられない理由と引用）があるときだけ。5 以上はエラー。2 以下の GN の motifNote もエラー

2.12 検証と HCD への戻り道

ワーカーがコードで確認できること

検証器はワーカーのコードで、LLM による採点ではありません。スキーマ、ID、列の値、引用の形式、接続とインターフェースの対応は決定的な検査です。文献は外部の書誌データベース、引用は取得した原文と照合します。原文との対応を確認できたことと、その論文がこの神経科学的な主張を十分に支えることは異なります。後者には人の評価が必要です。

層主な確認結果の限界
JSON Schema必須キー、型、列挙値、余分なキー（additionalProperties: false）正しい形でも内容が正しいとは限らない
HCD / FRGID、参照、内外、Collection、interface、階層、ROI 規則・GN 規則生物学的・計算論的な妥当性を完全には判定しない
SABRA記述子、略称、正式名、境界と左右（第 3 部）RCS が使えない場合の外部照合には欠落がある
BRA の値文献種別、種、測定法、式、原文・図番号、1 接続 1 文献許された値の使用と科学的根拠の強さは別
文献照合DOI / PMID を Crossref / PubMed と照合書誌の実在はその主張の保証ではない
引用照合引用が全文または要旨に存在するか図の内容や主張の含意まで自動では保証しない
調査実際の検索ログと被覆の一致検索しなかった文献の不存在を証明しない
Canon固定版との回路定義・文献の衝突（第 4 部）Canon 自体の定義にはレビューが必要
仮説許可範囲、claim、前提、比率、表示（2.13）前提の照合は仮説の実証ではない
HCD / FRG の整合X 系の所見と調整記録・調整の仕組みで、全所見ゼロの保証ではない

文献の照合

HCD・FRG の検査のたびに文献も検査し、架空の論文や誤った識別子を、ほかの問題と同じ修正のループでエージェントに戻します。

  • 引用（決定的、checkCitations）：uc.json・connections.json・frg.json・report.md の自由な文章の [Author, Year] はすべて references.json の Reference ID であること（空白や大文字小文字だけが違う場合は正確に書くよう求める）。すべての文献がレポートの ## References 以外のどこかで引用されていること。2 つの Reference ID が同じ DOI / PMID を持たないこと。
  • 照会（ネットワーク、ワーカーの ReferenceVerifier）：DOI は Crossref で、Crossref に無ければ doi.org の内容交渉（CSL JSON。DataCite・mEDRA・JaLC）で、PMID は PubMed（NCBI E-utilities esummary）で引く。記録に Reference ID の筆頭著者があること（後ろの著者ならそう報告）、出版年が ±1 年以内（オンラインと印刷）、title があれば題が似ていること（語の重なり）。DOI と PMID の両方があれば PubMed の DOI が同じこと。雑誌の違いは注記だけ。識別子の無い文献で、Crossref の検索が同じ論文（題・筆頭著者・年）を見つけたら、その DOI を提案する。
  • 状態（reference_check.json）：verified、mismatch、not_found、invalid（DOI / PMID の形でない）、no_identifier、unverified（照会に失敗）。mismatch・not_found・invalid と DOI の提案を問題として戻す。段の受理時に画面に 1 行の要約を出す。
  • 範囲：FRG の段は frg.json・レポートの ## FRG・そこだけで引用された文献を受け持ち、それ以外は HCD の段が受け持つ（HCD の問題を FRG の段で重ねて送らない）。
  • 障害時：1 要求 10 秒でタイムアウト、タイムアウト・ネットワークエラー・429・5xx で 2 回まで再試行（Retry-After は 10 秒まで従う）。3 件続けて失敗した相手は 5 分飛ばし、1 回の検査で照会に使うのは最大 3 分。照会できなかった文献は unverified で、問題にしない（障害で段を止めない）。結果は実行中キャッシュし、失敗は次の検査で再試行。PubMed は毎秒 3 件（API キーがあれば 10 件）に間隔を空ける。
  • 設定（ワーカーの環境変数。CDK では設定しない）：REFERENCE_LOOKUP=off で照会を止める（引用の検査は残る）。CROSSREF_MAILTO は Crossref の polite pool への連絡先。NCBI_API_KEY は PubMed の速度を上げる（Secrets Manager に置き、ワーカーのコンテナの secrets に加える。ワーカーはエージェントの Codex プロセスからは隠す）。どれも無くても動く。

引用文の照合

Pointers on literature は引用した論文の逐語の引用でなければなりません（BRA の手動審査のコード 273 / 274 / 279）。HCD の検査のたびに、各接続の pointersOnLiterature を論文の本文と照らします（ワーカーの QuoteVerifier、照合は packages/shared/src/quotes.ts）。形式の規則（短すぎる、位置の表記）にすでに違反する引用はその問題に任せ、DOI も PMID も無い文献は照合できません。

  • 本文の取得：Europe PMC の記録（search、resultType=core）から PMID・PMCID・オープンアクセスか・要旨を得る。オープンアクセスの論文は Europe PMC の全文（JATS。要旨・本文・付録・図の説明。参考文献・引用の印・表・数式は除く）を、失敗したら NCBI BioC 経由で PMC から読む。全文が無ければ Europe PMC・PubMed（efetch）・Crossref（abstract）・Semantic Scholar の順に最初に見つかった要旨を使う。
  • 照合：両側を文字と数字だけにする（NFKC、アクセントと大文字小文字をそろえ、ソフトハイフン・上付きや角括弧の数字の引用・括弧の著者年の引用を除く）。部分文字列として見つかるか、最もよく重なる語の窓との編集距離が文字数の 10% 以下（類似度 0.9 以上、QUOTE_MATCH_THRESHOLD）なら見つかったとする。言い換えは通らない。省略（…・[…]）や編集上の挿入（[the VTA]）はそこで分け、3 語以上の部分がすべて見つかること。
  • 上限：文献の照会と同じ HTTP クライアント。1 回の検査で最大 2 分、同時に 3 本。各論文は実行ごとに 1 回だけ取得する。
  • 設定：QUOTE_CHECK=off で止める（quote_check.json は lookup: "off"）。
引用の状態意味扱い
verified_fulltext取得した全文で原文と一致全文との一致として記録
verified_abstract要旨で一致要旨との一致として記録
not_found全文を取得できたが引用が見つからない全文のリンク・最良の類似度・最も近い箇所を付けて修正を依頼
unverifiedオープンアクセスの全文が無く要旨にも無い、識別子が無い、取得できない未検証として残す。照合済みとは扱わない（有料の論文を問題にしない）

同じ引用と図を異なる回路の接続に使い回している場合は reused の警告も記録します。図番号だけの根拠は、図の内容まで照合したことにはなりません。

後の段で変わった前段の再検証

FRG の仕様は、FRG と HCD が食い違うときに関連するファイルを直すようエージェントに求めるので、HCD のファイルは HCD の段の後でも変わりえます。そこでワーカーは、各段の検査のたびに、その段のデータファイル（HCD：meta.json・references.json・uc.json・connections.json、FRG：frg.json。レポートと判断ログは毎段変わるので除く）の SHA-256 と、その時点で残っていた問題を phase_baseline.json に記録します。FRG と CSV の検査はハッシュを比べ、変わっていないファイルは検査し直しません。変わった HCD のファイルには HCD の検査をすべて（スキーマと規則、RCS、文献、引用）やり直し、変わった FRG のファイルには CSV の段で FRG の検査をやり直します。前の段の受理時にすでに残っていた問題は送り直さず、新しい問題だけを HCD (changed after the HCD phase was checked): を付けて同じ修正依頼で戻します。HCD を直した後も古い検査結果のまま成果物を作る、という抜け道を防ぐためです。

整合チェックと調整

FRG と CSV の検査のたびに、ワーカーのコード（checkCross）が HCD と FRG の整合を計算して cross_check.json に記録し、段の受理時に画面に件数を出します。所見を出すのはコードで、どう直すかを決めるのはエージェントです。

コード所見現行の動作
X1GN の interface が、その ROI 内部の UC の HCD 接続にある外からの入力・外への出力を取りこぼす調整の契機（想定 severity：error）
X2接続から求めた ROI の入出力と noROI(input) / noROI(output) の印が一致しない調整の契機（error）
X3GN の interface が、その UC のどの接続も与えない入出力を挙げる、または自分の UC を挙げる調整の契機（error）
X4GN の 2 つの UC が ROI 内部の接続で連結していないrules 0 / 1 だけ記録（warning）。rules 2 では FRG の通常の検査で確認し、X4 は算出しない
X5ROI 内部の UC が、所属する GN の機能文に [U.<id>] で現れない記録（warning）
X6GN の requirementRealization が interface のすべての UC に触れていない記録（warning）
X8FRG が潰れている：TLF が UC だけを持つ、GN が 1 つ、ROI 内部の UC が 3 未満調整の契機（warning）
X9ROI 内部の UC が回レベルの BNA 群全体（facet の無い BNAG:）か複数の SABRA 単位（&）で、粗すぎる可能性記録（warning。調整の契機にしない）

実装に X7 はありません。X1・X3・X6 は構文が解析できた GN の interface だけを見ます。所見の severity と、パイプラインを即時に止めるかどうかは別です。記録には、所見の件数（summary）、統計（ROI 内部の UC、GN、解析できた interface、FRG の深さ、3〜4 UC の GN とそのうち候補のループ / フィードフォワードであるもの）、判断ログの revisions の行、調整の記録、仮説モードでは仮説の情報（2.13）も入ります。scripts/cross-check-artifacts.mjs は、S3 から写した作業場所に同じ検査を（読み取りだけで）実行します。

FRG の段が終わったとき（受理でも警告付きでも）に X1・X2・X3・X8 の所見があれば、ワーカーは実行ごとに 1 回だけ調整のターンを送ります（adjustmentPrompt）。所見と各検査の意味、FRG 候補、証拠からどちらを直すかを決める指示が入ります。エージェントは、HCD が正しければ FRG を直し、細かい集団や欠けた投射の根拠があれば HCD の UC を分ける・足す（粗い単位は Collection にし、新しい UC と接続には文献を付ける）。直さない判断も理由とともに残します。変わった HCD は上のとおり再検証され、調整のターンには別に 3 回の修正の枠があります。調整の後に revisions 節が無ければ、FRG の検査がそれを求めます。ほかの所見は記録だけです。
