第 8 部

システムの構成

第 8 部は開発者向けです。CoBRAC Agents を動かしている AWS の構成、部品とパッケージ、ジョブの実行と回復、ワーカーの処理、データモデル、S3 の成果物、フロントエンド、非機能の目標、開発の約束を、実装に沿って記述しています。BRA の作り方そのものは第 3 部、権限・秘密情報・費用は第 9 部で扱います。リリースとデプロイの手順は運用手順書（docs/ops/README.md）にあります。

プログラムの部品API、dispatcher、broadcaster、janitor、計画ランナーの Lambda と、Fargate 上のワーカーです。どれも LLM を呼ばず、決まったコードで判断します。
エージェントワーカーが子プロセスとして起動する Codex の中で動く LLM です。BRA を作るほか、解説記事・AI レビュー・計画用のジョブも同じ仕組みで動きます（8.4）。
人利用者はプロジェクトを作り、質問に答え、成果物を受け取ります。管理者は利用者、デフォルトの API キー、同時実行数を管理します（4.1）。

8.1 設計方針と全体構成

アプリ本体は、東京リージョン（ap-northeast-1）の 1 つの CDK スタック CobracAgents（packages/infra/lib/cobrac-stack.ts）にまとまったサーバーレス構成です。BRA-DB だけは別のスタック BraDb（bradb-stack.ts）にあります（第 7 部）。

設計方針

構成は次の 4 つの方針に基づいています。

  1. 使われていないときの固定費を小さくする。常時稼働の EC2 や NAT Gateway を置きません。例外は BRA-DB のスタックです。
  2. 費用のかかる計算には、ジョブが動いている間だけ払う。ワーカーは 1 ジョブにつき 1 つの Fargate タスクとして起動し、Spot を優先します。
  3. 質問への回答を待つ間はタスクを止める。状態を S3 に保存してタスクを終了し、回答が届いたら新しいタスクで続きから再開します。
  4. 独自ドメインと証明書を CDK で持たない。CloudFront の既定のドメインで配信します。cobrac.site は CDK の外で distribution に付けた別名で、DNS は別の AWS アカウントの Route 53 にあります。

NAT Gateway を置かない理由：東京では NAT Gateway 1 つ（1 AZ）あたり、月に約 $32 とデータ処理料が固定でかかります。ワーカーは短い時間しか動かないので、パブリックサブネットでパブリック IP を付け、インターネットゲートウェイから外に出れば足ります。ワーカーのセキュリティグループには受信の規則が 1 つもありません。

画面が使う HTTP API・WebSocket・Cognito の接続先は、CDK がデプロイのたびに config.json として Web のバケットに書きます。CloudFront はこのファイルをキャッシュしないので、環境ごとに Web をビルドし直す必要はありません。

システムの中で LLM が動くのは、ワーカーが Codex を通じて実行するジョブだけです。Lambda の部品はどれも LLM を呼びません。API が OpenAI を呼ぶのは、キーの確認で /v1/models を読むときだけです。

プロジェクトの作成から画面への通知まで

図 8.1 は主な部品と、プロジェクトを作ってから進捗が画面に届くまでの流れを示します。

  1. 利用者がブラウザでプロジェクトを作ると、SPA が Cognito の ID トークンを付けて HTTP API（POST /projects）を呼びます。API Gateway がトークンを検証し、API の Lambda がプロジェクトとジョブを QUEUED で DynamoDB に書き、SQS にジョブのメッセージを積みます。
  2. dispatcher が SQS からメッセージを受け取り、同時実行数に空きがあれば ECS の RunTask で Fargate のタスクを 1 つ起動します。空きがなければ 60 秒後に積み直します（8.3）。
  3. ワーカーが KMS で API キーを復号し、Codex CLI を子プロセスとして起動して、エージェントにターンを依頼します。エージェントは OpenAI API のモデルとして推論し、Web 検索と MCP のツールで文献と SABRA を調べ、プロジェクトフォルダに JSON を書きます。
  4. ワーカーはターンごとにファイルを検査し、状態とメッセージを DynamoDB に、作業ディレクトリと成果物を S3 に書きます。
  5. DynamoDB Streams が Projects と Messages の変更を broadcaster に渡します。broadcaster は WebSocket API を通じて、そのプロジェクトを購読している所有者のブラウザにだけ送ります。
  6. これとは別に、janitor が 5 分ごとに止まったジョブを再開するか失敗にし（8.3）、計画ランナーが毎分オーケストレーターの計画を進めます（第 6 部）。

通常のデプロイは、バージョンを上げた PR を main にマージしたときに GitHub Actions が行います（8.9）。ワーカーのコンテナイメージはデプロイ時に CodeBuild がビルドして ECR に置くので（@cdklabs/deploy-time-build）、ローカルに Docker は要りません。ローカルからの npm run deploy は緊急時だけに使う経路で、対象のアカウントで cdk bootstrap が済んでいる必要があります。手順は運用手順書にあります。

ログ

CloudWatch Logs の保持期間は、すべての Lambda とワーカーで 14 日です。ロググループ自体は DESTROY です。Logs Insights と Container Insights は使いません。ワーカーのロググループ名は、スタックの出力 WorkerLogGroup で分かります。

BRA-DB のスタック

BRA-DB は常時稼働のスタックで、次のものからなり、月に約 $34 かかります。

  • 専用の VPC（10.42.0.0/24、1 AZ）に置いた EC2（t4g.small、PostgreSQL 17 + Apache AGE 1.7）
  • 外向きの通信だけを通す NAT インスタンス（t4g.micro）
  • 登録 Lambda cobrac-bradb-import

インターネットから受ける通信はなく、5432 番ポートは登録 Lambda からしか受けません。データ用のボリュームは RETAIN で、毎日スナップショットを取って 7 世代を残します。synth のときに COBRAC_BRADB=false にすると、このスタックは作られません。構成と費用の内訳は 7.6 に記載しています。

実装の注意：NAT インスタンス（Amazon Linux 2023、NatProvider.instanceV2）は CDK の既定の初期化スクリプトを使わず、独自のスクリプトで swap（512 MB）、iptables-services、IP 転送、マスカレードを設定します。既定のスクリプトは、t4g.nano では yum install がメモリ不足で強制終了され、AL2023 には route もないためです。NAT インスタンスはユーザーデータを最初の起動で 1 回しか実行しません。そのため設定を変えたときは、新しい論理 ID（現在はNatInstanceMicro）を付けて置き換えます。データを持たないので、RETAIN ガード（8.9）の対象外です。一方、データベースのインスタンスは起動のたびに bootstrap.sh を実行します（cloud_final_modules: scripts-user always）。

8.3 ジョブの実行と回復

ジョブは、API が記録してキューに入れ、dispatcher がワーカーを起動し、ワーカーがエージェントを動かして進めます。止まったジョブを見つけて再開させるのは janitor です。本節では、ジョブの状態とその遷移、ワーカーの起動と同時実行数、実行中の監視、停止と中断、janitor の処理を扱います。ワーカーの中の処理は 8.4、BRA の中身の進み方は第 3 部（長いジョブと保存は 3.15）に記載しています。

状態

プロジェクトとジョブは同じ 7 つの状態を使います。

状態画面意味
QUEUED待機中ワーカーの起動を待っている
RUNNING実行中ワーカーのタスクが動いている。dispatcher がタスクを起動したときに、プロジェクトを先に RUNNING にする
WAITING_USER_INPUT回答待ちエージェントが質問した。タスクは終わっていて、Fargate の費用はかからない
FINALIZING仕上げ中xlsx・グラフ・版を作っている
COMPLETED完了BRA データができた。フォローアップと解説記事を受け付ける
FAILED失敗止まった。「続きからリトライ」で前回の成果物から再開できる
CANCELLED中止利用者・管理者・計画の中止で止めた。リトライできる

ジョブの状態遷移

  1. 依頼：API がプロジェクトとジョブを QUEUED で書き、SQS にメッセージを積みます。
  2. 起動：dispatcher が同時実行数を検査し、空きがあればワーカーのタスクを起動して、ジョブとプロジェクトを RUNNING にします（次の「ワーカーの起動」）。
  3. 実行：ワーカーがジョブを RUNNING にし、ターンを繰り返します（8.4）。
  4. 質問：エージェントがターンを status: "question" で終えると、ワーカーは作業ディレクトリと会話（Codex のスレッド）を S3 に保存し、ジョブとプロジェクトを WAITING_USER_INPUT にしてタスクを終えます。回答（POST /projects/{id}/answer）が届くと同じジョブが QUEUED に戻り、resume モードで同じ会話を再開します（resumeThread）。
  5. 仕上げ：HCD と FRG が受理され、JSON から CSV ができると FINALIZING になります。csv_to_excel.py、Template-v2-2 の書き出し、buildGraphs() の後に版を凍結し、COMPLETED になります。
  6. 完了後：フォローアップ（画面では「追加の指示」。POST /projects/{id}/followup）は、同じ会話で新しいジョブを作ります。解説記事（POST /projects/{id}/articles）も新しいジョブで、BRA データには触れません。
  7. 失敗：ターンの失敗、6 時間の上限、Spot の中断などで FAILED になります。応答のなくなったジョブは、janitor が自動で再開します（後述）。

実行モード（mode）ごとの動き方は 3.6 に記載しています。

ワーカーの起動

  1. dispatcher が SQS のメッセージを 1 件ずつ受け取ります。ジョブが見つからないか、もう QUEUED でなければ、メッセージを捨てます。
  2. 同時実行数を検査します。RUNNING と FINALIZING のジョブを、全体と利用者ごとに数えます。回答待ちのジョブはタスクが終わっているので数えません。どちらかが上限に達していれば、60 秒後に届くようにメッセージを積み直します。待っている間、メッセージは SQS の中にあり、費用はかかりません。
  3. Fargate Spot でタスクを起動します（RunTask）。Spot の容量がないなどで失敗したら、通常の Fargate（On-Demand）で起動し直します。タスクには cobrac:projectId・cobrac:jobId のタグを付けます。
  4. 起動できたら、タスクの ARN とハートビートの時刻をジョブに書き、プロジェクトを RUNNING にして、エージェント欄に「ワーカーを起動しました（Fargate Spot）。」を出します。On-Demand で起動したときは、その旨を括弧の中に書きます。
  5. 起動そのものに失敗したら、理由を付けて「ワーカー起動を再試行します（…）。」と出し、60 秒後に積み直します。

プロジェクトを持たないジョブ（Canon の AI レビュー、計画用のジョブ）では、エージェント欄に何も出しません。

同時実行数

同時に動かせるワーカーのタスクの数には、全体と 1 人あたりの 2 つの上限があります。

上限デプロイの値（GitHub の Variables）管理画面の設定

1 人あたりCOBRAC_MAX_CONCURRENT_JOBS_PER_USER（既定 1）1〜16 の整数。空ならデプロイの値
  • 管理画面の設定は、Catalog の config / concurrency に、変えた人と時刻とともに保存されます。0 や 17 以上の値は API が拒みます。
  • dispatcher と計画ランナーは、設定を 30 秒のキャッシュを通して読みます。そのため、変更にデプロイは要りません。設定を読めないときはデプロイの値を使います。
  • オーケストレーターは、両方の上限に空きがあるときだけ、行や計画用のジョブをキューに入れます。このときは待機中のジョブも数えます。計画の待ちは SQS ではなく DynamoDB の中にあるので、待機中のジョブの 24 時間の時間切れ（後述の janitor）に当たりません。計画用のジョブも、待機中と実行中は両方の上限に数えます（6.11）。

質問作業ディレクトリと CODEX_HOME を S3 に保存してタスクを終了する。その間 Fargate の費用はかからない。回答が届くと、新しいタスクが会話を再開する
OpenAI のレート制限Codex が再接続を試み、それでも失敗したターンはワーカーが間を置いて再試行する（8.4）

停止と中断

停止：利用者・管理者・計画が停止すると、API がジョブを CANCELLED にし、ECS の StopTask を送ります。StopTask はコンテナに SIGTERM を送り、ワーカーは状態を保存して終わります。ワーカーはハートビートのたびにジョブの状態も見ているので、SIGTERM が届かなくても 1 分以内に中止を検知します。

Spot の中断：Fargate Spot は AWS の都合で中断されることがあり、中断の 2 分前にコンテナに SIGTERM が届きます。ECS は停止の猶予（120 秒）の後にコンテナを止めます。SIGTERM を受けたワーカーは、次の順に処理します（handleStop）。

  1. 打ち切られたターンの使用量をセッションの記録から数え、ジョブの費用に足します。
  2. ジョブが実行中（RUNNING・FINALIZING）なら、エージェント欄に「ワーカーが停止されます（Fargate Spot の中断など）。ここまでの作業を保存し、ジョブは自動で再開します。」と出します。
  3. 作業ディレクトリと会話を S3 に保存します。
  4. ハートビートを古い時刻（1970 年）に書き換えます。次の janitor の実行（5 分以内）がこのジョブを自動リトライし、保存した続きから再開します。保存に失敗しても、この書き換えは行います。

停止による SIGTERM のときは、保存だけを行います。すでに終わったジョブや回答待ちのジョブには何もしません。SIGTERM が届かずにタスクが消えた場合でも、途中の保存があるので、失う作業は最大で 5 分ぶんです。

実機で確認していないこと

本番の Spot の中断は意図して起こせません。そのため、中断からの再開は単体テストと cdk synth（タスク定義の StopTimeout: 120、janitor の rate(5 minutes)）でだけ確認されています。実際の中断が起きたら、ワーカーのログの SIGTERM handled: retry と、エージェント欄の「ワーカーが停止されます…」で動作を確認します。

8.4 ワーカーの処理

ワーカーは Fargate のタスクで動く TypeScript のプログラムで、入口は packages/worker/src/index.ts です。dispatcher が環境変数（JOB_USER_ID・JOB_PROJECT_ID・JOB_ID・JOB_MODE）でジョブを指定します。JOB_PROJECT_ID は作業ディレクトリと S3 の接頭辞の名前になるので、ID の形が合わなければ起動しません。canon-review では Canon の ID、plan では計画の ID、それ以外ではプロジェクトの ID の形を求めます。

BRA のジョブの手順

  1. Users・Projects・Jobs を読み、使う API キーを選び（runKey.ts の planRunKey）、KMS で復号します。利用者自身のキーがあればそれを使い、なければ、利用承認があって Tier がジョブのモデルを許す間だけデフォルトの API キーを使います（4.1）。RCS の接続先とトークンを Secrets Manager から読みます。読めなければ RCS なしで続けます。
  2. prompts/AGENTS.md を /work にコピーし（<ProjectID> の箇所を ID に置き換える）、JSON Schema を /work/schemas/ に書きます。resume・followup・retry では、作業ディレクトリと会話を S3 から戻します。参考資料を用意し（4.2）、Canon に入っていれば、固定した rev の定義を /work/canon/ に置きます（5.5）。版のないデータへの followup の扱いは C.5 にあります。
  3. createCodex → openThread で会話を開きます。設定は、sandboxMode: danger-full-access、承認なし、ネットワークあり、Web 検索 live、lit MCP と RCS MCP です。Fargate のタスク自体がサンドボックスで、コンテナの中では Landlock も seccomp も使えません（9.5）。ターンごとにそのターンの設定で会話を開くので、調査のターンだけを高い推論の強さで実行できます。
  4. 調査モードで、作業ディレクトリの調査が終わっていなければ、調査ステップを実行します（3.7）。続いて段階を実行します（次の「ターンの制御」）。出来事を Messages に書き、ファイルが変わるたびにプロジェクトの stepStates と activeStage を更新します。activeStage は、調査中は RESEARCH、調整のターンは ADJUST、それ以外は実行中の段階の名前です。
  5. 段階を受理するたびと、質問・完了・失敗で終わる直前に、作業ディレクトリと会話を S3 に差分で同期します。ターンの実行中も 5 分ごとに保存します（8.3）。
  6. CSV がそろったら、finalize.ts が xlsx・テンプレートの xlsx・グラフ JSON を作って S3 に送り、版を凍結して、ジョブとプロジェクトを COMPLETED にします。

ターンの制御

BRA のジョブは、次の段階を順に進みます。段階を進めるのはワーカーです。

（調査）→ HCD → FRG →（HCD と FRG の整合の検査、調整のターン 1 回）→ CSV → xlsx

段階を「完了」にするのは、その段階のプログラムによる検査がファイルを受理したときだけです。ファイルがあるだけでは「実行中」にしかなりません。FRG の段階はエージェントを HCD に戻せます（3.11）。CSV と xlsx はエージェントではなくワーカーが作ります。各段階の中身は第 3 部に記載しています。

1 つの段階の中の繰り返しは次のとおりです。ループは packages/worker/src/pipeline.ts の runPhases です。ファイルの受け渡しの詳細は 3.4・3.5・3.10 に記載しています。

  1. Codex の runStreamed で 1 ターンを実行し（outputSchema 付き）、出来事を Messages に書きます。
  2. 最後の返答が status: "question" なら、状態を S3 に書いて終わります（8.3）。
  3. ターンのたびに、現在の段階を検査します（packages/shared/src/harness.ts の checkHcd / checkFrg）。検査するのは、JSON Schema、ファイルをまたぐ参照、UC の命名、インターフェース、FRG の制約、値が英語だけであること、レポートの節です。文献も同じ段階で照合します（packages/shared/src/references.ts の checkCitations、packages/worker/src/references.ts の ReferenceVerifier。3.10）。
  4. 問題があれば、その一覧を修正依頼として返します。修正ターンは 1 段階につき MAX_NUDGES（3）回までです。修正ターンは挙げた問題を直すだけなので、推論の強さを min(プロジェクトの強さ, medium)（fixTurnEffort）にして実行します。問題が残れば警告を出して先に進み、出力が使えなければジョブを失敗にします。
  5. 段階が受理されたら、次の段階の依頼を送ります。後の段階のファイルがすでに検査に通るとき（フォローアップの後など）は、作り直しません。エージェントが FRG や CSV の段階で HCD のファイルを変えたとき、または CSV の段階で FRG のファイルを変えたときは、後の段階がそれを検査し直し、新しい問題を自分の問題と一緒に返します（3.11）。
  6. CSV の段階では、buildCsvs が JSON から 5 つの CSV を機械的に作ります。エージェントは CSV を書きません。生成に失敗したら、その問題を JSON の修正依頼として返します。
  7. 連続 6 時間の実行で打ち切ります（8.3）。

ターンの失敗と再試行

  • 失敗とみなす条件：ターンが失敗するのは、turn.failed のときか、ストリームが turn.completed なしに error の出来事で終わったときだけです。Codex はレート制限の再試行を error の出来事として報告します（「Reconnecting... 2/5 (rate limit exceeded …)」）。これはお知らせとして出し、ターンは続きます。Codex は致命的でない注意も error の項目として報告します（「Model metadata for `x` not found」「Falling back from WebSockets to HTTPS transport」など）。これもお知らせとして出し、本当のエラーだけをエラーとして扱います。失敗したターンの後、codex exec は終了コード 1 で終わりますが、ワーカーはその終了ではなく、ターン自身のエラーを報告します。
  • レート制限：OpenAI のレート制限（TPM・RPM、HTTP 429）に当たると、まず Codex 自身が最大 5 回まで再接続を試みます。それでもターンが失敗したら、ワーカーが間を置いて同じ会話で続きを依頼します。待ち時間は 30 秒〜3 分で、サーバーの「try again in …」に 5 秒を足した値と、30 秒・60 秒・120 秒（回ごとに倍）の大きいほうです。この再試行は 3 回まで（codex.ts の RATE_LIMIT_TURN_RETRIES）で、待つ間もハートビートを送ります。それでも失敗すればジョブを失敗にします。
  • 再試行しない失敗：利用枠（quota）を使い切ったとき、請求の問題、1 回の依頼が大きすぎるときは、待っても直らないので再試行しません。
  • 依頼が大きすぎるとき：1 回の依頼が 1 分あたりのトークンの上限より大きいと（「Request too large … Limit …, Requested …」）、待っても通りません。会話の文脈が上限に達すると、その会話のターンはすべて拒まれます。そのため、大きすぎるとして拒まれたターンは同じ会話では再試行せず、ワーカーが新しい会話に切り替えます。新しい会話は 1 回だけ始め、プロジェクトの見出し、ここまでの作業はファイルにあるという注記、HCD と FRG の仕様を付けて、同じ依頼を送ります。
  • 会話の圧縮：会話を十分小さく保つため、Codex は CODEX_AUTO_COMPACT_TOKENS（既定 75,000、model_auto_compact_token_limit）で会話を圧縮します。この値は速さのためでもあります。文脈の大きい依頼ほど返答が遅く、ジョブの時間の大半がそうした依頼に使われていたためです（測定は付録 D）。圧縮自体は数秒で終わります。

モデルの目録と文脈の大きさ

  • Codex CLI（@openai/codex-sdk と一緒に入る）は、モデルの目録の情報を必要とします。目録にないモデルでは代わりの情報で動き、「Model metadata for `x` not found」と警告します。
  • 単価表のすべてのモデルは、入っている CLI の目録（codex debug models --bundled）になければなりません。packages/worker/test/codexCatalog.test.ts がこれを検査します。
  • gpt-5.6 という別名は目録にないので、ワーカーは OpenAI がそれを振り向ける gpt-5.6-sol を Codex に渡します。ジョブには利用者が選んだモデルを記録します（4.2）。
  • model_context_window はどのモデルも 272,000 です。OpenAI は gpt-5.6 と gpt-6 の文脈を 1,050,000 トークンとしていますが、272K を超える入力は 2 倍の料金で、Codex の目録もすべて 272,000 です。圧縮のしきい値（75,000）は、これより十分小さい値です。
  • Codex には、出力の最大トークン（これらのモデルでは 128,000）の設定はありません。
