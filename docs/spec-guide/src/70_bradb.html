第 7 部

BRA-DB への登録

CoBRAC の AWS アカウントには、WBAI の BRA-DB と同じスキーマ（v4.6、PostgreSQL 17 + Apache AGE 1.7）のデータベースがあります。この文書では、このデータベースを単に BRA-DB と呼びます。CoBRAC は、完了したジョブの結果を凍結した版を、このデータベースに来歴付きで登録します。アプリ自身のデータは DynamoDB と S3 にあり、BRA-DB はアプリのデータベースではなく、成果物の登録先です。

登録するもの凍結した版の 5 つの CSV（Project・References・Circuits・Connections・FRG）を、BRA-DB のテーブルとグラフに入れます。
登録の方法BRA-DB のインポート（v3.10）に対応する処理を 1 つのトランザクションで行います。整合性を検査し、失敗すれば元に戻します。
守るもの履歴を消しません。どの版が、だれの依頼で、どのアプリで登録されたかを、追記だけの記録に残します。

7.1 位置づけ

BRA-DB への登録は、必ず凍結した版から行います。実行のたびに上書きされる作業中のデータは登録しません。版の仕組み（番号、凍結する内容、変わらないことの保証）は 4.5 で説明します。

ワーカーは版を凍結するとき、5 つの CSV がそろっていれば、BRA-DB のインポートが読む形の登録パッケージも版の中に作ります。登録パッケージには、BRA-DB が読む名前の CSV と、版 ID・内容のハッシュ・生成条件を書いた manifest が入ります（4.5）。登録の流れは図 7.1 のとおりです。

典拠：packages/shared/src/braVersion.ts、packages/worker/src/versions.ts、packages/api/src/app.ts（版と BRA-DB のルート）

7.2 データベースの中身

データベースのスキーマは、BRA-DB の DDL v4.0 と、マイグレーション 01〜06（v4.1〜v4.6）の最終形を 1 つにまとめたものです。テーブル・列・制約の名前は BRA-DB と同じなので、BRA-DB のツールがそのまま使えます。CoBRAC はこれに、グラフのラベルを先に作る処理、CoBRAC 独自の記録のスキーマ、ロールの権限を加えています。

リレーショナルのテーブル

BRA-DB のテーブルは、スキーマ public にあります。

テーブル内容（主な列）
bradb_projectsBRA 1 つにつき 1 行。project_key（連番の主キー）、project_id（一意。CoBRAC の Project ID をそのまま文字列で）、ROI・TLF、Contributor、source_file（cobrac:<版 ID>）、cobrac_generated、version、import_status（imported / validated / published / deprecated）、シートの見出しとメタ情報
bradb_local_circuits回路。circuit_id が一意。circuit_kind（local / bif）、Source of ID、names、is_uniform、伝達物質、修飾（Excitatory / Inhibitory / Modulatory）、sub_circuit_ids、Output Semantics、approval_status（approved / provisional / unverified）、origin_project_key（定義したプロジェクト）、extra（JSONB）
bradb_literature / bradb_project_literature文献の共有のマスタ（literature_id と DOI が一意）と、プロジェクトとの対応
bradb_connections接続。送り手と受け手の Circuit ID、relation（= < >）と表記、Reference ID、Taxon、測定法、引用文と図の指示、承認状態、extra
bradb_bra_nodesFRG のノード。node_id、node_role（Requirement / Capability / Uniform / Assembly）、Capability・Requirement・Interface・Implementation・Mechanism、region_category、circuit_id、current_version
bradb_bra_node_historyノードの履歴（change_type：create / update / ai_revision / merge / import）
bradb_review_commentsBRA-DB 側のレビューコメント（open / addressed / closed）
bradb_import_logインポートの記録（import_type：manual / cobrac / cultivate / batch）
bradb_circuits（ビュー）bradb_local_circuits の互換のビュー

グラフ

Apache AGE のグラフ bradb_graph に、FRG と回路の関係を頂点と辺で持ちます。

ラベル意味
BRANode（頂点）FRG のノード（node_id・project_id・node_role）
LocalCircuit / BIFCircuit（頂点）回路（circuit_id）。BRA-DB で承認済みの BIF の回路は BIFCircuit、それ以外は LocalCircuit（インポート v3.10 と同じ分類）
SUBNODEFRG の親ノードから子ノードへ（順序付き）
PROJECTS_TOFRG のノードから、その Projected Circuits へ
MAPS_TO_LOCAL / MAPS_TO_BIFFRG の UC のノードから、対応する回路へ
PROJECTS回路から回路へ（Connections の 1 行。project_id と connection_key を持つ）
HAS_SUBCIRCUITCollection から、その Sub-Circuit へ（順序付き）

CoBRAC の記録とロール

CoBRAC 独自の記録は、スキーマ cobrac にあります。

  • 登録の記録（cobrac.registrations）：登録の試み 1 回につき 1 行を足す、追記だけの表です。Project ID、project_key、版 ID、版の番号、親の版 ID、内容のハッシュを持ちます。さらに、状態（registered / unchanged / rejected / failed）、モード（create / replace / none）、理由、件数、ノードの変化、スキップした回路、警告を持ちます。生成条件（provenance）、パッケージの manifest の全体、依頼者、時刻も記録します。UPDATE と DELETE はトリガーが拒否します。
  • いまの版（ビュー cobrac.current_versions）：各プロジェクトについて、最後に成功した登録の版、つまり BRA-DB がいま持っている版を示します。
ロール用途と権限
braBRA-DB のテーブルの所有者。BRA-DB の保守担当とマイグレーションに使う
cobrac_import登録 Lambda が使う。bradb_projects・bradb_import_log・bradb_bra_node_history・cobrac.registrations の DELETE 権限を持たないので、登録が履歴を消すことはできない。回路・接続・ノード・文献の対応は INSERT / UPDATE / DELETE、グラフは読み書きができる
cobrac_read読み取り専用（すべてのスキーマの SELECT）

実装

SQL は packages/infra/bradb/sql/ にあります。0001_bradb_schema_v4_6.sql が BRA-DB のスキーマ、0002 がグラフのラベルの作成、0003 がスキーマ cobrac、0004 がロールの権限です。

典拠：packages/infra/bradb/sql/

7.3 登録の手順

利用者の手順

  1. プロジェクトの「版」タブで、保存済みの版を選びます。登録できるのは、5 つの CSV がそろった版だけです。
  2. 版の BRA-DB 欄で、BRA-DB がいまどの版を持っているかを確認します。
  3. 「v<n> を BRA-DB に登録」を押します。BRA-DB にあるものより回路か接続が少ない版では、確認を求められます。確認すると、縮小を認める指定を付けて送り直します。
  4. 結果と、その版の登録の記録（状態、時刻、依頼者、警告、スキップした回路）が欄に出ます。

登録できるのは、プロジェクトの所有者だけです。API は版の登録パッケージを読み、BRA-DB の VPC の中にある登録 Lambda を同期で呼びます。登録に成功すると、最後に登録した版（版 ID、番号、内容のハッシュ、時刻、登録 ID）をプロジェクトに記録します。登録の記録に残る依頼者は、利用者の Contributor 名です。Contributor 名がなければ表示名を使います。

仮説を含む版は、仮説を登録する規則が決まるまで登録できません（3.12）。仮説を 1 つ以上含む版と、仮説の数が記録されていない仮説モードの版がこれにあたります。この場合はボタンが押せず、理由が出ます。BRA-DB のない環境では、BRA-DB 欄そのものが出ません（7.6）。

登録の処理

登録 Lambda は、次の順に処理します。

  1. パッケージの検査：パッケージの形式、各ファイルの SHA-256 と manifest の一致、5 つの CSV がそろっていることを検査し、内容のハッシュを計算し直します。合わなければ rejected（理由 invalid）にします。
  2. シートの読み取り：インポート v3.10 と同じく、列名、Review End Lines、Source of ID、Node role、列挙値、Capability&Mechanism を読みます。ただし、次の点を変えています。
    • 完全に一致する列名を、部分的に一致する列名より優先します。
    • 見出しにない列は、固定の位置から読まずに空とします。
    • FRG は「Node ID」列から読みます。
    • BRA-DB の制約が拒む値（Modulation Type、Region Category、長すぎる文字列）は NULL にして警告を出し、元の値を extra に残します。
  3. トランザクションの開始：プロジェクトごとの advisory lock を取ります。そのプロジェクトの行が BRA-DB にあれば置き換え（replace）、なければ新規（create）として進めます。
  4. 同じ内容の判定：BRA-DB が持つ版と内容のハッシュが同じなら、unchanged を記録して終わります。
  5. 回路の分類と検査：回路を BIF と Local に分類し、インポート v3.10 の検査を行います。Collection は接続を送れない（エラー 203）、relation は = < > のどれか、という検査です。
  6. 置き換えの条件：BRA-DB でレビューコメントが付いたプロジェクトは置き換えません（理由 review_comments）。回路か接続が減る場合は、所有者の確認がない限り拒否します（理由 shrink。前後の件数を付ける）。
  7. 書き込み：プロジェクトの行、回路、文献、プロジェクトと文献の対応、FRG のノードと履歴、接続、グラフを書きます。置き換えでは、プロジェクトの行とその連番のキーを保ち、version を上げます。回路は、自分が定義したものと所有者のいないものを upsert します。ほかのプロジェクトが定義した回路は共有の語彙として残し、スキップとして報告します。自分が定義しなくなった回路は削除します。
  8. 整合性の検査：書いた辺の数とグラフを照合します。端が BRA-DB にない辺は、エラーではなく警告にします。食い違えば rejected（理由 integrity）にします。
  9. 記録と確定：登録の記録に registered を、インポートの記録に 1 行を足して COMMIT します。インポートの記録には、import_type を cobrac、agent を CoBRAC Agents v<app> (<git sha>) とし、notes に版 ID・親・内容のハッシュ・登録 ID を書きます。途中のエラーはすべて ROLLBACK し、rejected か failed として記録します。

実装

API は POST /projects/{id}/versions/{n}/bradb（登録）と GET /projects/{id}/bradb（状態の取得）です（付録 A）。API が読むパッケージは revisions/{n}/bradb/ にあり、最後に登録した版は Projects.bradb に残します。縮小の確認は allowShrink を付けて送り直します。登録の処理は registerVersion です。

典拠：packages/api/src/lib/bradb/register.ts・sheets.ts・cypher.ts、packages/api/src/handlers/bradbImport.ts、packages/api/src/lib/hypothesisSettings.ts、packages/shared/src/hypothesisVersion.ts（bradbBlockReason）、packages/web/src/components/workspace/BradbPanel.tsx

7.4 履歴を失わない設計

BRA-DB のインポート v3.10 の置き換え（--replace）は、プロジェクトの行を削除して作り直します。そのため、インポートの記録とノードの履歴も消えてしまいます。CoBRAC の登録は、これを避けるように作られています。

置き換えても残るもの
  • プロジェクトの行と連番のキー（bradb_projects の行と project_key）。version は上がる
  • インポートの記録とノードの履歴（bradb_import_log と bradb_bra_node_history）
  • 回路。その場で更新するので、ほかのプロジェクトからその回路への辺も残る
  • 登録の記録の全行（cobrac.registrations。トリガーで変更と削除を拒否）
置き換えで作り直すもの
  • そのプロジェクトの接続、FRG のノード、文献との対応
  • グラフの、そのプロジェクトのノードと接続の辺
  • ノードの履歴は続く。新しいノードは current_version が 1（import）、変わったノードは n+1（update）になり、変わらないノードは番号を保つ（履歴の行を足さない）
規則動き
同じ内容BRA-DB が持つ版と内容のハッシュが同じなら何もしない（unchanged）
縮小BRA-DB より回路か接続が少ない版は、所有者が確認するまで拒否する（shrink）
レビュー済みBRA-DB でレビューコメントが付いたプロジェクトは置き換えない（review_comments）。レビュー済みのデータは、指示を通じて変える方針（未実装）
仮説仮説を含む版は登録しない。規則は別に決める予定（7.3）
ID の扱いBRA-DB の project_id は CoBRAC の Project ID の文字列、版 ID は <ProjectID>@v<n>。どちらも分解して解釈しない（ID の形式は変わりうる）

典拠：packages/api/src/lib/bradb/register.ts、packages/infra/bradb/sql/

7.5 来歴をたどる

BRA-DB の行からは、次の順に来歴をたどれます。

  1. プロジェクトの行の Project ID（bradb_projects.project_id）
  2. 登録の記録の版 ID と内容のハッシュ（cobrac.registrations）
  3. S3 に凍結したファイル（revisions/{n}/）と、その生成条件（manifest。4.5）

読み取りには、読み取り専用のロール cobrac_read を使います。次は問い合わせの例です。

-- 各プロジェクトについて、BRA-DB がいま持っている版
SELECT project_id, version_id, content_sha256, app_version, git_sha, sabra_boundary, registered_at
FROM cobrac.current_versions ORDER BY registered_at DESC;

-- 1 つのプロジェクトの登録の試みの全履歴（失敗・拒否・変化なしも残る）
SELECT registration_id, version_id, status, mode, reason, counts, requested_by, registered_at
FROM cobrac.registrations WHERE project_id = 'p7m2q9xa' ORDER BY registration_id DESC;

-- グラフ：あるプロジェクトの接続（回路 → 回路）
SELECT * FROM cypher('bradb_graph', $$
  MATCH (s)-[e:PROJECTS]->(r) WHERE e.project_id = 'p7m2q9xa'
  RETURN s.circuit_id, r.circuit_id $$) AS (sender agtype, receiver agtype);

典拠：packages/infra/bradb/sql/（cobrac.current_versions）

7.6 AWS の構成と費用

BRA-DB は、CoBRAC 本体とは別のスタックと専用の VPC で動きます。リージョンは東京（ap-northeast-1）です。インターネットからの通信を受けるものはありません。BRA-DB を作らない設定でデプロイした環境では、API は「この環境には BRA-DB がありません」と答えます。

リソース設定
VPC10.42.0.0/24、1 AZ。プライベートサブネット（インスタンスと登録 Lambda）と、NAT インスタンスだけを置くパブリックサブネット。S3 ゲートウェイエンドポイント（無料）
NAT インスタンスt4g.micro、Amazon Linux 2023。外向きの通信だけ（パッケージの更新、Secrets Manager、SSM）。VPC からの通信だけを受ける。NAT Gateway より月に約 $40 安い
EC2 Dbt4g.small、Ubuntu 24.04 arm64（AMI は固定）、ルートは gp3 16 GB で暗号化、IMDSv2、終了保護、SSH なし（SSM Session Manager で接続）。セキュリティグループは 5432 番を登録 Lambda からだけ許可
データ用ボリュームgp3 20 GB、暗号化、RETAIN（スタックを消しても残る）。/dev/sdf として付け、/srv/bradb（クラスタのデータディレクトリ）にマウント
スナップショットData Lifecycle Manager で毎日 18:00 UTC に取り、7 世代を残す（タグ bradb-backup=daily）
Secrets Managercobrac/bradb/bra（所有者）、cobrac/bradb/cobrac_import（登録 Lambda）、cobrac/bradb/cobrac_read（読み取り専用）。起動のたびに起動スクリプトがここからロールのパスワードを設定するので、ローテーションは次の再起動で効く
Lambda cobrac-bradb-importNode 22 arm64、プライベートサブネット、25 秒。CobracAgents の API だけが呼べる（この名前への lambda:InvokeFunction）

保守と閲覧には SSM のシェルとポート転送を使います。ポート転送で bra か cobrac_read のロールで接続できるので、BRA-DB の保守担当が利用することを想定しています。データはスナップショットから復元できます。接続・復元・インスタンスの置き換えの手順は、運用手順書（docs/ops/README.md）にあります。

起動とスキーマの適用

インスタンスは起動のたびに、ユーザーデータから起動スクリプトを実行します。

  1. PGDG から postgresql-17 と postgresql-17-age を入れます。
  2. 初回はデータ用ボリュームをフォーマットしてマウントし、クラスタを作ります。2 回目以降は既存のクラスタを登録し直します。
  3. shared_preload_libraries = 'age' と、VPC からだけの scram-sha-256 の認証を設定します。
  4. Secrets Manager の値でロールのパスワードを設定し、データベース bra_db_v4_6 を作ります。
  5. SQL のファイルのうち、適用の記録（cobrac.schema_migrations）にまだないものを番号順に適用します。権限のファイル（*_grants.sql）は、変わったら適用し直します。それ以外の適用済みのファイルは変えてはならず、変更は新しい番号のファイルで足します。

SQL のファイルを変えるとユーザーデータが変わるので、CloudFormation がインスタンスを停止して起動し直し（約 1 分の停止）、新しいファイルが起動時に適用されます。ログは /var/log/bradb-bootstrap.log です。
