7.1 設計方針と全体構成

アプリ本体は CDK のスタック CobracAgents（packages/infra/lib/cobrac-stack.ts）1 つにまとまっています。BRA-DB だけは別のスタック BraDb（bradb-stack.ts）です。構成は次の 4 つの方針で決めています。

  1. 使われていないときの固定費を小さくする。常時稼働の EC2 や NAT Gateway を置きません（例外は BRA-DB のスタック）。
  2. 費用のかかる計算は、ジョブが動いている間だけ払う。ワーカーは 1 ジョブにつき 1 つの Fargate タスクとして起動し、Spot を優先します。
  3. 質問への回答を待つ間はタスクを止める。状態を S3 に保存してタスクを終了し、回答が届いたら新しいタスクで続きから再開します。
  4. 独自ドメインと証明書を CDK で持たない。CloudFront の既定のドメインで配信します。cobrac.site は CDK の外で distribution に付けた別名で、DNS は個人アカウント（618703232062）の Route 53 にあります。

通常のデプロイは、版を上げた PR を main にマージしたときに GitHub Actions が行います（7.14）。手元からの npm run deploy は緊急時だけの経路で、対象アカウントで cdk bootstrap が済んでいる必要があります。ワーカーのコンテナイメージはデプロイ時に CodeBuild がビルドして ECR に置くので（@cdklabs/deploy-time-build）、手元に Docker は要りません。

NAT Gateway を置かない理由。東京では NAT Gateway 1 つ（1 AZ）あたり月に約 $32 とデータ処理料が固定でかかります。ワーカーは短い時間しか動かないので、パブリックサブネットでパブリック IP を付け、インターネットゲートウェイから外に出れば足ります。ワーカーのセキュリティグループには受信の規則が 1 つもありません。

画面が使う HTTP API・WebSocket・Cognito の接続先は、CDK がデプロイのたびに config.json として Web のバケットに書きます（CloudFront はこのファイルをキャッシュしません）。そのため、環境ごとに Web をビルドし直す必要はありません。

7.4 ジョブの実行と回復

1 件のジョブは、API（Lambda）が記録してキューに入れ、dispatcher（Lambda）がワーカーを起動し、ワーカー（Fargate 上の TypeScript のプログラム）が Codex のエージェント（LLM）を動かして進めます。止まったジョブを見つけて再開させるのは janitor（Lambda）です。エージェント以外はどれも LLM を含まないプログラムで、判断は決まったコードで行います。1 件の BRA の中身の進み方は第 2 部（2.16 は長いジョブと保存）、ジョブとプロジェクトのデータモデルは第 1 部で説明します。

ワーカーの起動（dispatcher）

  1. API がジョブを QUEUED で記録し、SQS に実行のメッセージを送る。
  2. dispatcher がメッセージを 1 件ずつ受け取る。ジョブが見つからないか、もう QUEUED でなければ、メッセージを捨てる。
  3. 同時実行数を確かめる。RUNNING と FINALIZING のジョブを数え、全体の上限か、その利用者の上限に達していれば、60 秒後に届くようにメッセージを積み直す（待っている間は SQS の中にあり、費用はかからない）。
  4. Fargate Spot でタスクを起動する（RunTask）。Spot の容量が無いなどで失敗したら、On-Demand で起動し直す。タスクには cobrac:projectId・cobrac:jobId のタグを付ける。
  5. 起動できたら、タスクの ARN とハートビートの時刻をジョブに書き、チャットに「ワーカーを起動しました（Fargate Spot）」（On-Demand のときはその旨）を出す。起動そのものに失敗したら「ワーカーの起動を再試行します」と出し、60 秒後に積み直す。プロジェクトの無いジョブ（Canon の AI レビュー、計画用のジョブ）ではチャットに何も出さない。

Spot の中断

Fargate Spot は AWS の都合で中断されることがあり、中断の 2 分前にコンテナに SIGTERM が届きます。ECS は停止の猶予（120 秒）の後にコンテナを止めます。SIGTERM を受けたワーカーは、次の順に処理します（handleStop）。

  1. 打ち切られたターンの使用量をセッション記録から数え、ジョブの費用に足す。
  2. 実行中（RUNNING・FINALIZING）のジョブなら、チャットに「ワーカーが停止されます…自動で再開します」と出す。
  3. 作業場所と Codex のスレッドを S3 に保存する。
  4. ハートビートを古い時刻（1970 年）に書き換える。これで次の janitor の実行（5 分以内）がジョブを再試行し、保存した続きから再開する。保存に失敗しても、この書き換えは行う。

取消のときも、ECS の StopTask が SIGTERM を送ります。この場合は保存だけを行います。すでに終わったジョブや回答待ちのジョブには何もしません。ターンの途中でも 5 分ごとに保存しているので、SIGTERM が届かずにタスクが消えた場合でも、失う作業は最大で 5 分ぶんです。

経緯と、まだ確かめていないこと

v0.18.1 までは、作業場所を S3 に保存するのはフェーズの受理・質問・完了・失敗のときだけで、SIGTERM を受けても何もしていませんでした。HCD⇄FRG の試行（2026-09-29）では、15 分ぶんの作業を失い、中断の検出にも 27 分かかりました。janitor 自体が 15 分ごとにしか動いていなかったので、再開は中断の 15〜30 分後でした。v0.18.2（PR #66）で、5 分ごとの保存、SIGTERM の処理、停止の猶予 120 秒、janitor の 5 分ごとの実行を入れました（ハートビートを古いとみなす 15 分は変えていません）。同じ版で、ワーカーの起動と janitor のメッセージを UI の言語で出すようにし（PR #68、10 言語）、公開プロジェクトの複製に元の調査モードの設定を写すようにしました（PR #67）。

本番の Spot の中断は意図して起こせないので、この変更は単体テストと cdk synth（タスク定義の StopTimeout: 120、janitor の rate(5 minutes)）でだけ確かめています。実際の中断が起きたら、ワーカーのログの SIGTERM handled: retry と、チャットの「ワーカーが停止されます…」で動作を確認します。

API キーと KMS

  • 鍵の種類：カスタマー管理の対称 CMK。年 1 回の自動ローテーション。削除方針は RETAIN。
  • 暗号化（API の Lambda だけ）：暗号化コンテキスト { userId, purpose: "openai-api-key" }。
  • 復号（ワーカーだけ）：同じコンテキストが必要です。ほかの利用者の暗号文は、コンテキストが合わないので復号に失敗します。既定の API キーは userId を含まない別のコンテキスト { purpose: "openai-api-key", scope: "default" } を使うので、個人のキーと既定のキーを互いのコンテキストで復号することはできません。
  • 平文が存在する時間：登録時の確認の要求の間だけ、API の Lambda のメモリにあります。実行時はワーカーのプロセスのメモリにあり、Codex のプロセスに渡されます。ディスク・ログ・S3 には書きません。
  • 登録時の確認：GET https://api.openai.com/v1/models を呼び、401・403 なら登録を拒みます。返ってきたモデルの一覧を、使えるモデルとして保存します。
  • ブラウザからキーを取り出す API はありません。忘れたら OpenAI 側で発行し直し、登録を上書きします。
  • Anthropic のキー（Claude のモデル用）も同じ扱いで、コンテキストの purpose が "anthropic-api-key" です。登録時は GET https://api.anthropic.com/v1/models で確かめます。実行時の平文はワーカーのプロセスの中の中継にだけあり、Claude Code のプロセスには渡しません（1.4「Claude のモデル」）。

既定の API キー

管理者は管理者画面で組織の OpenAI キーを既定の API キーとして登録できます（同じく /v1/models で確かめる）。保存するのは暗号文・末尾 4 文字・そのキーで使えるモデルの一覧・登録した日時と管理者で、画面に見えるのは末尾 4 文字と日付だけです（書き込み専用）。自分のキーを持たない利用者は、管理者に承認されると既定のキーでジョブを実行できます。承認にはティアがあり、Tier 1 は低価格のモデル（gpt-6-luna と gpt-5.6-luna）だけ、Tier 2 はすべてのモデルを使えます。自分のキーを登録している利用者は、常に自分のキーで実行し、ティアの制限を受けません。Claude のモデルには別にデフォルトの Anthropic API キーがあり、Tier 1 は claude-haiku-5-5 だけ、Tier 2 は 4 つの Claude のモデルすべてを使えます。

どのキーで実行するかは、ワーカー（プログラム）が起動のたびに決め直します（新しいジョブ、回答、再試行、中断後の再開のどれでも）。そのため、承認を取り消したり、ティアを下げたり、既定のキーを消したりすると、次の起動から効きます。既定のキーを復号するのは、承認済みでキーを持たない利用者のジョブで、そのジョブのモデルをティアが許すときだけです。

アプリでは暗号化しないもの（意図的）

チャットの本文、ROI・TLF、成果物、グラフの JSON、スレッドの状態は、S3 と DynamoDB のサービスによる暗号化だけで保存し、アプリの層での項目ごとの暗号化はしていません。管理者と AWS アカウントの権限を持つ人は、コンソールからこれらを読めます。

7.7 認証と認可

認証（Cognito）

  • サインインは SRP で行います（パスワードそのものはサーバーに送りません）。
  • パスワードは 10 文字以上で、英小文字と数字を含むこと。
  • トークンの有効期間：ID・アクセストークン 2 時間、リフレッシュトークン 30 日。
  • preventUserExistenceErrors を有効にし、登録されていないメールアドレスにも同じエラーを返します。
  • アカウントの回復はメールだけです。
  • セルフサインアップを無効にしたとき（COBRAC_SELF_SIGNUP=false）は、管理者が Cognito で利用者を作ります。Cognito が仮パスワードをメールで送り、初回のサインインでログイン画面が新しいパスワードを求めます（Cognito の NEW_PASSWORD_REQUIRED）。
  • アカウントのメール（確認コード・再送・パスワードの再設定・メールアドレスの変更・管理者による招待）は、Cognito のカスタムメッセージのトリガー（packages/api/src/handlers/authMessage.ts）が書きます。どのメールにも、CoBRAC Agents と運営者（WBAI）の名前、送った理由、コードとその有効期間、心当たりがなければ無視してよいこと、サイトへのリンクを入れます。言語は、Web アプリがクライアントのメタデータとして渡す UI の言語（lang）、次に locale 属性で決め、日本語か英語の一方、分からなければ両方を 1 通に入れます。トリガーは Cognito から利用者の属性を受け取りますが、テーブル・バケット・鍵には触れず、ログも出しません。メールは SES から DKIM 署名付きで送り、バウンスと苦情のあったアドレスは SES のアカウント単位の抑制リストが送信先から外します。

管理者

  • API は要求のたびに、メールアドレスが COBRAC_ADMIN_EMAILS（GitHub の Secret）に含まれるか、Cognito のグループ admin に属しているかを確かめ、そうなら役割を admin にします。初回のサインインで作る利用者も、既存の利用者も同じです。一覧からアドレスを消しても自動では一般の利用者に戻らないので、管理者画面で役割を変えます。
  • 管理者の機能：利用者の一覧、無効化と有効化（自分自身は無効にできない）、役割の変更、既定の API キーの承認とティア、既定の API キーの登録と削除、利用者ごとの既定のキーの費用（累計と今月）、同時実行数の設定、全プロジェクトの一覧と強制停止、仕様書（この PDF。GET /admin/spec が API に同梱した PDF を S3 の admin-docs/spec-<ハッシュ 16 桁>.pdf に置き、10 分間有効の署名付き URL を返す）。
  • 無効化された利用者は、すべての API で 403 になります。

API の認可

  1. API Gateway の JWT オーソライザーが ID トークンの発行者（iss）と対象（aud）を確かめる。
  2. Hono がクレームから userId・メールアドレス・グループを読み、Users を読み込む（初回は作る）。
  3. プロジェクトの操作は、自分の userId を使った getProject(自分の userId, id) でだけ読む。ほかの利用者の ID や削除済みのプロジェクトは 404 になる。
  4. S3 のキーは users/{自分}/{projectId}/ に固定し、..、thread/、絶対パスを拒む。
  5. 参考資料のアップロード：API が呼び出した人の userId と乱数のアップロード ID からステージングのキーを作り、署名付き POST のポリシーでキー・Content-Type・大きさ（20 MB）を固定する（有効期限 15 分）。プロジェクトの作成時に、各アップロードの存在と大きさ、合計 50 MB 以内であることを確かめ直してから、プロジェクトに移す。
  6. 管理者の経路は role === "admin" を要求する。

  • プロジェクトと Canon の公開（所有者が選ぶ。既定は非公開）：公開したプロジェクトは、サインインしたすべての利用者が /public/projects/{id} で読めます（名前、ROI、TLF、Contributor、rev、レポート、判断ログ、HCD・FRG の JSON、グラフの JSON、解説記事）。チャットの履歴と Codex のスレッド、ジョブ、トークンの使用量と費用、参考資料、BRA の xlsx、グラフの配置、所有者のメールアドレスと userId は公開しません（見えるのは仮名の userKey だけ）。公開した Canon は、名前・説明・方針・rev・メンバーの数を見せ、メンバーは自身も公開されているものだけを並べます。公開の前に確認の画面でこのことを示します。非公開に戻すと、すぐに公開の一覧から消えます。その間に作られた複製は、複製した人のものとして残ります。
  • 複製：公開プロジェクトを複製すると、作業場所（HCD・FRG・CSV のデータ、検査結果、レポート、判断ログ）、グラフの JSON、解説記事を、複製した人の新しい非公開のプロジェクト（users/{複製した人}/{新しい ID}/）に写し、Project ID を書き換えます。元のプロジェクトは読むだけです。参考資料（attachments/）は写しません。元の所有者には複製の数（Catalog の数）だけが見え、誰が複製したかは見えません。

WebSocket と CORS

  • WebSocket は、$connect の前に Lambda オーソライザーが ID トークンを検証します。購読のときも、そのプロジェクトが本人のもので、削除されていないことを確かめます。接続の行には TTL があり、切断で消し、配信時に 410 Gone が返った接続は購読を外します。
  • CORS のプリフライト（OPTIONS）は JWT の認証を通りません。許可するヘッダーは Authorization と Content-Type で、オリジンはいま * です（個人の利用と CloudFront の既定の URL のため）。独自ドメインを足すときはオリジンを絞ります。
  • 成果物バケットの CORS は、参考資料のアップロードのための POST だけを、CloudFront のドメイン、https://cobrac.site（CDK の外で付けた distribution の別名）、http://localhost:5173 から許します。ほかのホスト名で配信するときは packages/infra/lib/cobrac-stack.ts に足します。足さないと、そのオリジンからのアップロードはブラウザで失敗します。

7.8 ワーカーの隔離

エージェント（LLM）は、ワーカーのコンテナの中で Web 検索と任意のコマンドを実行できます。そこで、エージェントが届く範囲から AWS の認証情報と API キーを外し、作業を本人のデータに限ります。

項目実装
実行の単位1 ジョブに 1 タスク。ディスクをほかのジョブと共有しない
OS のユーザーuid 10001 の worker（root ではない）

Codex のサンドボックスコンテナそのものを境界とし、danger-full-access と approvalPolicy: never で動かす（コンテナの中では Landlock が使えない）
同じユーザーのプロセスからの秘密の保護ワーカー（PID 1）、Codex、エージェントのコマンドはどれも worker で動くので、本来は互いの /proc/<pid>/environ を読めてしまう。そこでイメージの中で node・Codex・git の実行ファイルを実行だけ可能（chmod 0111）にした。読めないファイルから起動したプロセスは dump できない扱いになり、ほかの worker のプロセスからその環境変数とメモリを読めなくなる。これで、エージェントは Codex のプロセスから OpenAI の API キーを、PID 1 からコンテナの認証情報の URI（タスクロールと KMS に届く）を読めない。git を含めるのは、Codex が自分の環境（キーを含む）で git を実行するため（起動時にプラグインのリポジトリを clone し、ターンごとに diff を取る）

OpenAI の API キーを使うもの

ワーカー（LLM を含まないプログラム）は KMS でキーを復号し、Codex のプロセスを作るときにだけ渡します（Codex SDK の apiKey）。モデルに要求を送るのは Codex で、ワーカー自身は OpenAI を呼びません。エージェント（LLM）がシェルで実行するコマンドには、キーが渡りません。キーを平文で扱うほかの場所は、API の Lambda が登録時に /v1/models で確かめるときだけです。

参考資料の URL の取得。URL はブラウザではなくワーカーが取りに行きます。http(s) だけを許し、転送（最大 5 回）のどの段も公開のアドレスに解決されなければなりません（ループバック、プライベート、タスクのメタデータのエンドポイントのようなリンクローカルは不可）。大きさは 10 MB まで、時間は 20 秒までです。

残るリスク。プロンプトインジェクションで作業場所やメタデータの外を読ませようとする試みには、エージェントが届くプロセスから AWS の認証情報とその URI を外し、キーを持つプロセス（ワーカー・Codex・git）を dump できなくして /proc から環境変数を読めなくし、データを本人のものに限ることで備えています。ただし、別のアカウントや VPC で分けるような完全なマルチテナントの隔離ではありません。エージェントは自分のジョブのためにキーを使っており、たとえば自分のジョブのデータを外に送ることはできてしまいます。

  • オーケストレーターの計画用のジョブ（段階 2）：下書きと再計画も行と同じく空きがあるときだけ積み、両方の上限に数える。再計画はバッチごとに最大 1 回、計画あたり約 10 回まで（MAX_REPLAN_JOBS。最初は最初のバッチが終わった後、以降は前回から行の 10 分の 1 が終わるごと）、自動の順序の計画だけで、一時停止中は動かさない。ワーカーは計画用のジョブを 7 分（長い資料の下書きは 25 分）で打ち切り、janitor はハートビートが途絶えたか 24 時間キューにあるものを失敗にし、リトライしない。ランナーが 1 ステップで読む uc.json は 20 件まで。
  • Canon のあるオーケストレーター（段階 3）：本体の行の PR の AI レビューと、Canon に合わせる更新（行あたり最大 2 回、MAX_CONFORM_FOLLOWUPS）は、所有者のキーか既定の API キーで動く通常のジョブで、行と同じ空きの判定を通り、両方の上限に数え、ほかのジョブと同じく課金される。計画の画面は、計画の PR の AI レビューの費用を計画の費用に含める。基準プロジェクトは AI レビューを受けない。更新は PR がまだ開いているときだけ送る（ランナーが直前に読み直す）ので、人がすでに承認・却下した PR に有料の更新を使うことはない。計画の PR が 20 件承認を待っている間は新しいバッチを始めない（PLAN_MAX_WAITING_PRS）ので、放置された計画は審査者の仕事を積み上げずに止まる。自動で承認することはない（第 6 部）。

1 ターンの使用量は、次のように数えます（v0.17.1 から。packages/worker/src/codex.ts）。

7.13 BRA の速度と費用（測定）

この節の位置づけ

この節は、ある時点の測定の報告です。数値は 2026-09〜10 の本番の記録と比較のための実行から出したもので（調べたのは v0.16.0 の本番の実行。変更は v0.17.1〜v0.18.2 で、どれも 2026-10-01 のリリース。gpt-6-luna、推論 high、調査モード on、日本語）、保証する値ではありません。モデル、アプリの版、プロンプト、OpenAI 側の状態で変わります。調べたのは BRA の作成にかかる時間と OpenAI の費用、遅さの原因、v0.18.0 の高速化とその前後の比較で、あわせて見つかった費用の二重計上は 7.12、Spot の中断からの再開は 7.4 にまとめています。

要点

0.16.0 の本番の実行を調べると、BRA の作成 1 件にかかる時間（平均 60 分）の 88% は、モデルの応答を待っている時間でした。1 回の応答の待ち時間は、そのリクエストのコンテキスト（それまでの会話の長さ）でほぼ決まります。コンテキストが 8 万トークン未満なら固定の待ちは約 4 秒ですが、12 万を超えると約 42 秒になります。当時は会話の圧縮を 15 万トークンで行っていたので、モデル時間の 4 分の 3 近くがこの遅い領域で使われていました。

そこで v0.18.0 では、圧縮のしきい値を 7.5 万トークンに下げ、ツールの結果とファイルの書き方を小さくし、修正ターンの推論レベルを medium にしました。同じ ROI と TLF で変更前と変更後を 3 件ずつ実行したところ、平均の所要時間は 48.6 分から 31.0 分に（36% 短縮）、実費は $0.174 から $0.134 に（23% 減）なりました。ただし件数は 3 件ずつと少なく、調査ステップで挙げる候補が減ったことなど、注意して見るべき点があります（後述の「注意点」）。

並列化で縮められる範囲が小さい理由

  • 段の順番は動かせません。FRG は HCD の UC と接続を入力にし、調整ターンは HCD と FRG の両方を見て直します。調査 → HCD → FRG → 調整の順は、依存関係のために直列になります。
  • HCD の中身も分けられません。UC の粒度、領域をまたぐ接続、インターフェースの対応、Collection が互いに依存する 1 つのグラフなので、領域ごとに別のスレッドで作ると、結合するときに整合をとり直す作業がもう一度必要になります。FRG（平均 5.5 分）も 1 本の木で、全 UC の割り当てとインターフェースの合成が要るため、分ける利点がありません。出力（CSV・xlsx・グラフ）はもともと 0.1 分です。
  • 並列にできるのは証拠を集める部分だけです。調査ステップの候補の投射は複数のスレッドに分けられますが、組織の TPM の上限は gpt-6-luna で毎分 20 万トークンで、1 本のスレッドだけで平均 14 万〜17 万トークン/分を使っています。2 本目を足すとすぐに上限に当たり、待ちが発生します。いまの TPM での短縮は 2〜4 分と見積もりました。
  • 新しいジョブ（B・C）では、Codex が「コードモード」（exec の中の JavaScript から複数のツールをまとめて呼ぶ方式）を使っているので、ツールの呼び出しはすでに部分的に並列になっています。

版番号

  • 版番号はルートの package.json の version だけが正本です。ビルド時に Vite が埋め込み、サイドバーの下に vX.Y.Z · <git の短い SHA> と表示します。CDK は同じ値を Lambda の APP_VERSION に渡し、GET /health が返します。ワーカーにも同じ値と git の commit を渡し、凍結する版の生成条件に記録します（5.2）。
  • Semantic Versioning に従います。0.x の間の目安は、patch：バグの修正、文言・表示の調整、文書、単価表の更新。minor：画面や API の追加、データモデルの追加、ワークフロー・プロンプトの変更。major：既存のデータと互換性がなくなる変更（テーブルの構造、成果物の形式）。
  • 版番号を手で編集しません（release.mjs を通す。workspace の package.json は自動でそろう）。[Unreleased] が空のまま release すると失敗するので、CHANGELOG を書かずに版を上げることはできません。

リリースの手順

  1. 変更の内容を CHANGELOG.md の ## [Unreleased] に「追加・変更・修正・削除」の見出しで書く。利用者に見える挙動を主語にし、ファイル名や関数名だけの記述にしない。
  2. 作業ブランチで npm run release -- patch --no-git（または minor・major・版番号）を実行する。ルートと全 workspace の package.json・package-lock.json の版を更新し、[Unreleased] を ## [X.Y.Z] - YYYY-MM-DD に確定する。この変更をコミットして PR に含める（--no-git を付けないと main を前提にコミットとタグを作るので、PR の運用では使わない）。
  3. PR の CI（ci.yml）が、AWS の認証なしで build・typecheck・test・release:check・cdk synth を行う。ジョブの要約に「マージでデプロイされるか」が出る。
  4. 人が PR を main にマージする。版を上げた PR のマージがデプロイの承認になる（7.15）。
  5. deploy.yml が v<version> のタグの有無を見て、タグが無い版だけをデプロイし、タグを付け、GET /health で版を確かめる。結果は Actions の実行（gh run view --log）で確かめる。

版を上げないマージ（文書だけの変更など）はデプロイされず、次のリリースにまとめて入ります。

RETAIN ガード

scripts/retain-guard.mjs は、CobracAgents と BraDb の cdk diff の出力を読み、状態を持つリソースの置き換え（replace、may be replaced）・削除（destroy、orphan、取り除き）を見つけると、デプロイの前にジョブを止めます。対象は AWS::DynamoDB::Table・AWS::DynamoDB::GlobalTable・AWS::S3::Bucket・AWS::KMS::Key・AWS::Cognito::UserPool の全部と、BRA-DB のインスタンス Db（AWS::EC2::Instance）・データ用ボリューム DataVolume（AWS::EC2::Volume）・その取り付け（AWS::EC2::VolumeAttachment）です。BRA-DB の 3 つはコンストラクトのパスで見分けるので、NAT インスタンスは置き換えられます。cdk diff の出力を解釈できない（Stack CobracAgents の行が無い）ときも止まります。終了コードは 0（安全、または許可済み）、1（危険な変更あり）、2（出力を解釈できない）で、ログにはリソースの型・パス・論理 ID だけを出し、プロパティの値は出しません。

差分を確かめたうえで続けるときは、gh workflow run deploy.yml --ref main -f allow_retain_replacement=true で実行し直します。通常の「Re-run」では入力が付かないので、再び止まります。だれがこれを決めるかは 7.15 に書きます。BRA-DB のインスタンスを置き換える手順は 5.8 にあります。

緊急停止

止めたいもの方法だれが
CI からのデプロイGitHub で deploy ワークフローを無効にする。または gha-cobrac-web-deploy の信頼ポリシーの sub を存在しない値に書き換える所有者（信頼ポリシーは手元で）
Cloud Agent や CI の AWS アクセス全体ロールの信頼ポリシーの sub を存在しない値に書き換えるか、aws:TokenIssueTime を条件にした全 Deny を付ける。後者は発行済みのセッションも止める。GitHub 側では Actions を無効にする所有者（手元で）
実行中のジョブ管理者画面から強制停止する（ECS のタスクを止める）。利用者を無効にすると、その人の API は 403 になる管理者
新規の登録COBRAC_SELF_SIGNUP=false にしてデプロイする所有者
漏れた API キーOpenAI 側で失効させ、設定画面で登録し直す。既定の API キーは管理者画面で消すか登録し直す（次のジョブの起動から効く）利用者・管理者

撤去と残る費用

cdk destroy の後も、次のものは残り、わずかな保存の費用がかかり続けます。

  • KMS の CMK（無効にしてから待機期間を経ないと消せない）
  • Cognito のユーザープール
  • DynamoDB の Users・Projects・Jobs・Messages・Canons・Catalog・Plans（WsConnections だけは消える）
  • S3 の成果物バケット（オブジェクトが残っている間は消せない。版の削除を禁じるバケットポリシーがあるので、空にする前にその文を外す）
  • BraDb のデータ用ボリュームとそのスナップショット（第 5 部）

おおまかな撤去の順序は、成果物バケットを空にする → テーブルを消す → ユーザープールを消す → KMS の鍵の削除を予約する、です。ECR のイメージと CloudWatch のロググループも確かめます。
