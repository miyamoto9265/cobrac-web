第 4 部

プロジェクトと版

CoBRAC では、1 つの BRA を 1 つのプロジェクトとして作ります。この部では、だれがどの操作をできるか、プロジェクトをどう作り何を設定できるか、画面に何が出るかを説明します。あわせて、ジョブの結果を凍結する「版」、プロジェクトの公開と複製、使用量と費用の表示もまとめます。BRA の中身の作り方は第 3 部、Canon は第 5 部、BRA-DB への登録は第 7 部で扱います。

利用者とプロジェクト利用者はプロジェクトを作り、質問に答え、成果物を受け取ります。管理者は利用者の承認とデフォルトの API キーを管理します。
版BRA のジョブが完了するたびに、ワーカーが結果を変更できない版として保存します。版は BRA-DB への登録と差分の比較の基になります。
共有と費用所有者はプロジェクトを公開でき、ほかの利用者はそれを複製できます。トークンの使用量と推定費用はジョブごとに記録され、画面に表示されます。

4.1 利用者と権限

利用者には、一般の利用者と管理者の 2 つの役割があります。どちらの役割でも、プロジェクト・Canon・計画は作った人（所有者）のものです。

役割付き方できること
一般の利用者サインアップしたときの既定自分のプロジェクトの作成・実行・閲覧・ダウンロード。API キーの登録と設定の変更。Canon と計画の作成と操作（第 5 部・第 6 部）。公開ライブラリの閲覧と複製
管理者管理者のグループに属するか、管理者として登録されたメールアドレスで API にアクセスしたとき。アクセスのたびに判定し、昇格だけを行う一般の利用者のすべての操作に加えて、全利用者の一覧、利用者の無効化と役割の変更、デフォルトの API キーの登録・置き換え・削除、利用者の利用承認と Tier の設定、全プロジェクトとデフォルトの API キーの利用額の閲覧、実行中のジョブの強制停止、同時実行数の設定、仕様書の閲覧
  • アカウントはメールアドレスとパスワードで作ります。利用者が自分でサインアップできるかどうかは、デプロイの設定で切り替えます。サインアップできない設定では、管理者が利用者を作ります（9.4）。
  • API に初めてアクセスしたとき、利用者の記録が作られます。表示名と Contributor 名の初期値は、メールアドレスの @ より前の部分です。
  • 管理者の登録からメールアドレスを外しても、自動では一般の利用者に戻りません。役割は管理画面で変えます。
  • 無効にされた利用者は、すべての API で拒否されます（403）。管理者は自分自身を無効にできません。
  • 管理者も、自分のジョブには自分の OpenAI API キーを登録して使えます。

デフォルトの API キーと利用承認

共同作業者が自分の OpenAI API キーを登録しなくてもジョブを実行できるように、管理者は組織のキーであるデフォルトの API キーを登録し、利用者に利用承認を与えます。利用承認には Tier 1 と Tier 2 の 2 段階があり、Tier によって使えるモデルが変わります。

項目仕様
保存管理画面で、どの管理者も登録・置き換え・削除できる。どの利用者にも属さない。個人のキーとは別の暗号化の条件で保存するので、個人のキーの条件では復号できず、逆もできない。登録時に個人のキーと同じく OpenAI で有効性を検査し、Tier 2 の利用者に出すモデルの一覧を保存する。書き込み専用で、API は登録の有無・末尾 4 文字・更新日時だけを返す。個人のキーをデフォルトの API キーにコピーすることはない
利用承認と Tier管理画面で利用者ごとに設定する。既存の利用者も新しい利用者も、未承認から始まる。Tier 1 で使えるのは gpt-6-luna と gpt-5.6-luna だけ（正確なモデル ID で判定）。Tier 2 ではすべてのモデルを使える
優先順位利用者自身のキーが常に優先され、Tier の制限を受けない。Tier はデフォルトの API キーで実行するジョブにだけかかる。承認済みの利用者が後で自分のキーを登録すると以後は自分のキーで実行し、削除するとデフォルトの API キーに戻る。管理者の個人のキーは、その管理者自身のジョブにだけ使う
ジョブの開始時の判定ジョブを始めるすべての依頼（作成・フォローアップ・リトライ・回答・解説記事）で、API が使うキーとモデルを決める。解説記事では記事に選んだモデルも判定する。使えるキーがない場合は 400。自分のキーがなく、承認とデフォルトの API キーの登録もそろっていない場合がこれに当たる。利用者がこのジョブのために選んだモデルが Tier にない場合は 403「このモデル（<model>）は利用できません」
選んでいないモデルの置き換え利用者がこのジョブで選んでいないモデルは、失敗させずに Tier の既定（gpt-6-luna）に置き換える。対象は、保存した既定のモデル、デプロイの既定、複製に与える既定、以前に自分のキーや別の Tier で作ったプロジェクトのモデル。そうしたプロジェクトにフォローアップ・リトライ・回答を送ると、プロジェクトのモデルを以後も Tier の既定に移し、通常の「Model: …」のお知らせを出す。モデルを選ばない解説記事は Tier の既定で実行し、プロジェクトのモデルは変えない
モデルの選択欄Tier にないモデルは既定のモデルとして保存できない。Tier 1 の利用者には Tier のモデルだけを返し、任意のモデル ID は受け付けない。作成・設定の既定・解説記事の選択欄は、そのモデルだけを出す。Tier の外の保存済みの既定は「デフォルト」と表示し、プロジェクトのヘッダーには次のジョブで使うモデルを出す
画面の言葉づかい「Tier」と「デフォルトの API キー」は管理画面にだけ出し、管理者以外には見せない。承認済みの利用者にとっては組織のキーで動くのが通常の状態で、自分のキーは任意の追加である。設定画面のキーの欄は、承認済みの利用者には「自分の OpenAI API キー（任意）」と出し、状態を次のどれかで示す：「登録は不要です。そのままジョブを実行できます。」（組織のキーで実行）、「自分のキー（末尾 …xxxx）で実行しています。」、「いまはジョブを実行できません。管理者に連絡してください。」（組織のキーが登録されていない）。自分のキーの入力欄は、登録していない間は「自分のキーを使う」の下にたたんでおく。承認されていない利用者には「OpenAI API キー」と「未登録」を出す。モデルの欄には、キーについての注記を出さない。API のエラーとワーカーのお知らせは「管理者に利用の承認を依頼してください」「いまはジョブを実行できません」「このモデル（…）は利用できません」とだけ伝える
取り消しワーカーは起動のたびに、もう一度判定する。対象は新しいジョブ・回答・リトライ・中断後の再開。承認がない、デフォルトの API キーがない、Tier が許さないモデル、のどれかに当たればジョブを失敗にし、お知らせを出す。実行中のターンは止めない
利用額ジョブには、自分のキーとデフォルトの API キーのどちらで実行したかを記録する。管理画面は、デフォルトの API キーで実行したジョブを利用者ごとに合計し、各利用者の横に出す（4.7）。アプリには支出の上限がないので、デフォルトの API キーを発行した OpenAI のプロジェクトに予算を設定する
漏えいへの備えキーは API から返さず、ログに出さず、エージェントが実行するコマンドにも渡さない。エージェントは自分のタスクの中では広い操作ができるが、キーを持つプロセスの環境は読めないようにしてある（9.5）。それでもエージェントは自分のジョブでキーを使うので、信頼できる共同作業者だけを承認し、予算を設定した OpenAI プロジェクトのキーを使う

だれが何を見られるか

対象所有者共同編集者ほかの利用者管理者
非公開のプロジェクトすべての操作—存在しないものとして 404一覧（削除済みも）と強制停止だけ
公開したプロジェクトすべての操作—公開した成果物の閲覧と複製。履歴・費用・メールアドレスは出ない（4.6）ほかの利用者と同じ
Canonすべての操作閲覧と PR の審査。設定の変更と削除は不可公開されていれば閲覧と、自分の Canon からの PR閲覧だけ
計画すべての操作—404API なし

所有者かどうかの判定は、すべて API の中で行います。ほかの利用者のプロジェクト、削除したプロジェクト、存在しない ID は、どれも同じ 404 になります。ルートごとに呼べる人は付録 A にあります。

実装

  • 役割は Users の role（user / admin）です。管理者の判定は、Cognito のグループ admin に属するか、メールアドレスが COBRAC_ADMIN_EMAILS にあるかで行います。サインアップの可否は COBRAC_SELF_SIGNUP で切り替えます。初回のアクセスで作る項目には、仮名の userKey を発行します。
  • デフォルトの API キーは、Catalog テーブルの kind: "config"・id: "default-api-key" の項目に、KMS の暗号文として保存します。暗号化コンテキストは { purpose: "openai-api-key", scope: "default" } です。userId を含まないので、個人のキーのコンテキスト { userId, purpose: "openai-api-key" } とは互いに復号できません。有効性の検査は OpenAI の /v1/models で行い、API は { registered, last4, updatedAt } だけを返します。
  • 利用承認は Users.orgAccess = { tier, approvedAt, approvedBy } です。値がないか null なら未承認です。Tier 1 のモデルは ORG_TIER1_MODELS です。/users/me/models は Tier 1 の利用者に restricted: true を返します。
  • ワーカーが取り消しで出すお知らせは sys.noApiKey・sys.orgKeyUnavailable・sys.orgKeyModel です。ワーカーが読めるのは Catalog の config パーティションだけです（dynamodb:LeadingKeys の条件付きの GetItem）。
  • ジョブは keySource（own / org。org がデフォルトの API キー）を記録します。利用者ごとの合計は GET /admin/org-usage が返します。
  • キーを守る仕組み：shell_environment_policy が CODEX_API_KEY・OPENAI_API_KEY をコマンドの環境から除きます。エージェントは自分の Fargate タスクの中で Codex のプロセスと同じ OS ユーザーとして動きますが、node・Codex・git の実行ファイルは実行専用で、そのプロセスはダンプできません。そのため /proc/<pid>/environ からキーを読めません。

典拠：packages/api/src/lib/auth.ts・orgKey.ts・runs.ts、packages/shared/src/orgKey.ts、packages/worker/src/runKey.ts・codex.ts

4.2 プロジェクトの作成と設定

プロジェクトは「新規プロジェクト」の画面で作ります。入力欄は ROI（対象の脳領域）と TLF（その領域が担う機能）の 2 つの欄を上下に組にしたもので、どちらか一方だけでも作れます。足りない側はエージェントが調べて補います。ROI の欄に Brainnetome（BNA）の略称か領域名を打つと、BNA の領域が候補に出ます。空の欄には ROI と TLF の例が順に表示され、「例を使う」で両方の欄に入ります。操作の詳細は利用マニュアルにあります。

入力欄の下で、次の項目を任意に指定できます。

項目内容
参考資料ファイルと URL。「+」から加え、チップで表示する。ファイルは入力欄にドロップしてもよい（下記）
Canonなし、既存の Canon、新しい Canon のどれか。指定しなければ設定画面で選んだ既定の Canon を使う（5.10）
仮説モード文献が直接は支持しない要素を、仮説として含めることを許す（3.12）
モデル・推論の強さ「v」のメニューで選ぶ（下記）
調査モード同じメニューで選ぶ。既定はオン（3.7）

名前と Contributor の入力欄はありません。プロジェクトは、ROI と TLF から作った仮の名前と、アカウントに設定した Contributor 名で始まります。名前は後でエージェントが付けた名前に置き換わり、プロジェクト画面で変えることもできます（4.3）。

モデルと推論の強さ

エージェントを動かす OpenAI のモデルと、推論の強さ（reasoning effort）は、次の規則で決まります。

  • モデルの決め方：プロジェクトの設定、利用者の既定、デプロイの既定、アプリの既定（gpt-6-luna）の順に、最初に値があるものを使います。プロジェクトを作るとき、API は必ず具体的なモデル名を決めて保存します。費用を計算できるようにするためで、「Codex の既定」のような不明な値は残しません。デフォルトの API キーを使う Tier 1 の利用者では、Tier にない既定は gpt-6-luna に置き換わります（4.1）。
  • 推論の強さの決め方：プロジェクトの設定、利用者の既定、デプロイの既定、Codex の既定の順です。値は minimal・low・medium・high・xhigh・max・ultra・persistent のどれかで、画面は high を推奨として示します。
  • 選べるモデル：API キーを登録するとき、そのキーで使える GPT-5.6 と GPT-6 の文章のモデルを保存します。日付付きのスナップショットと、音声・画像・検索などの派生モデルは除きます。デフォルトの API キーの利用者には、Tier 2 ならデフォルトの API キーのモデルを、Tier 1 なら Tier 1 のモデルを出します。モデルは作成と設定の画面で選べます。
  • 引き継ぎ：フォローアップとリトライは、プロジェクトの設定をそのまま使います。解説記事と AI レビューは、そのときに選んだモデルを使い、選ばなければプロジェクトか既定のモデルを使います。
  • ターンごとの強さ：調査モードでは、調査のターンの強さを少なくとも high に上げます。修正ターンでは medium を上限にします（8.4）。ほかのターンはプロジェクトの強さのままです。

参考資料

作成時に、エージェントに参考にさせる資料を添付できます。資料は参考にするだけで、検証済みの文献としては扱いません。BRA に載せる文献には、いつも公開された出典が必要です。出典は Crossref と PubMed で照合し、引用文はその出典の原文どおりでなければなりません（3.10）。

項目上限と条件
ファイル10 個まで。1 つ 20 MB、合計 50 MB まで
ファイルの形式PDF。PNG・JPEG・WebP・GIF の画像。TXT・MD・CSV・TSV・JSON のテキスト。DOCX・XLSX・PPTX
URLhttp か https で、公開されたホストのものを 20 件まで
  • ファイルはブラウザから保存先の S3 に直接送ります。プロジェクトを作るときに、API が送られたファイルの存在と大きさを検査し直してから、プロジェクトに移します。
  • ワーカーは最初の実行で一度だけ、PDF と Office の文書から本文を抜き出し、URL の中身を取得します。結果は保存して、後の実行で再利用します。抜き出しに失敗した項目には失敗の印を付けるだけで、ジョブは続けます。
  • エージェントには資料の一覧と本文を渡し、依頼文の先頭で資料があることを伝えます。画像は、新しい会話（Codex のスレッド）の最初の依頼に添付します。
  • プロジェクト画面のヘッダーには資料の一覧が出ます。ファイルは元の名前でダウンロードでき、URL は新しいタブで開きます。

実装

  • モデルのデプロイの既定は環境変数 CODEX_MODEL、アプリの既定は DEFAULT_CODEX_MODEL です。推論の強さのデプロイの既定は CODEX_REASONING_EFFORT です。選べるモデルは OpenAI の /v1/models の結果を filterCodexModels で絞り、availableModels に保存します。修正ターンの上限は fixTurnEffort（FIX_TURN_EFFORT = medium）です。
  • gpt-5.6 という別名は Codex のモデルの目録にないので、ワーカーは OpenAI がそれを振り向ける gpt-5.6-sol を Codex に渡します（CODEX_MODEL_ALIASES）。ジョブには利用者が選んだモデルを記録します。
  • 参考資料の上限は ATTACHMENT_LIMITS（packages/shared/src/attachments.ts）です。
  • アップロード：POST /uploads が名前と大きさを検査し、署名付き POST を返します。ポリシーで staging のキー・Content-Type・大きさの範囲を固定し、有効期間は 15 分です。バケットの CORS は、CloudFront のドメイン、https://cobrac.site、http://localhost:5173 からの POST を許します。staging のファイルは 1 日で消えます。
  • POST /projects は、アップロードが存在して上限内であることを検査してから attachments/files/ に移し、一覧を Projects.attachments に保存します（kind: "file"：name・key・size・contentType。kind: "url"：url）。
  • ワーカーは実行のたびに attachments/ を /work/materials/ にコピーします。最初の実行で、PDF の本文（pdftotext）、Office の本文（DOCX・PPTX・XLSX の共有文字列）、URL の中身を抜き出します。URL の中身は、HTML なら本文、PDF なら本文付きのファイル、画像ならその画像です。取得は 10 MB・20 秒・リダイレクト 5 回までで、経由するすべての遷移先が公開アドレスでなければなりません。結果は manifest.json とともに attachments/derived/ に保存します。
  • materials/INDEX.md が各項目の元・本文・状態を並べ、依頼文の先頭に Reference materials: の行が付きます。資料の扱いは prompts/AGENTS.md がエージェントに伝えます。

典拠：packages/api/src/lib/runs.ts・app.ts・lib/aws.ts、packages/worker/src/codex.ts・materials.ts、packages/shared/src/types.ts（filterCodexModels・fixTurnEffort）・research.ts・pricing.ts・attachments.ts、packages/web/src/pages/ChatPage.tsx

4.3 プロジェクトの ID・名前・削除

ID の形式

プロジェクト・Canon・計画には、作成時に乱数の ID を付けます。先頭の 1 文字が種類を表し、続く 7 文字は小文字の Crockford base32 です。Crockford base32 は i・l・o・u を含まない 32 種類の文字で、7 文字では約 3.4×1010 通りになります。

種類形例
プロジェクト^p[0-9a-hjkmnp-tv-z]{7}$p7m2q9xa
Canon^c[0-9a-hjkmnp-tv-z]{7}$c4h8w2rk
計画^n[0-9a-hjkmnp-tv-z]{7}$n4h8w2rk
  • ID は全体で一意で、一度使った ID は再利用しません。作成に失敗したプロジェクトや削除したプロジェクトの ID も同じです。
  • 以前の形式の ID を持つプロジェクトと Canon も、そのまま使えます（付録 C）。
  • BRA の版の ID は <ProjectID>@v<n> です（4.5）。
  • S3 のキーとワーカーの作業ディレクトリには、名前ではなく ID だけを使います。

名前

  • プロジェクトの名前は、入力した ROI と TLF から作った仮の名前 <TLF> in <ROI> で始まります。仮の名前はどの言語でもかまいません（例：VOR in 小脳）。
  • HCD の段階が受理されると、ワーカーはエージェントが付けた英語の名前（<TLF> in <ROI>）に置き換えます。置き換えるのは、名前がまだ仮の名前か、エージェントが付けた名前のときだけです。
  • 作成時に打った名前と、後でプロジェクト画面で変えた名前は、利用者の名前として扱い、エージェントは上書きしません。名前は正規化します。具体的には、Unicode の NFC にそろえ、前後の空白を除き、連続する空白を 1 つにします。制御文字と改行は受け付けず、長さは 1〜200 字です。
  • 名前を変えたとき、同じ名前の自分のプロジェクトがあれば注意として示します。大文字と小文字、空白の違いは区別しません。変更を止めることはありません。
  • xlsx の Project ID の列には ID が入ります。Description の列には、名前が英語のとき、その名前を先頭に付けます。

ダウンロードするファイルの名前は <名前>_<ProjectID>.bra.xlsx です。名前の部分は次のように整えます。

  1. NFC にそろえる。
  2. 制御文字、/ \ : * ? " < > |、連続する空白を _ に変え、続く _ を 1 つにする。
  3. 前後の _・.・空白を除き、80 文字で切る。
  4. 結果が空なら、ファイル名は <ProjectID>.bra.xlsx にする。

削除

プロジェクトの削除は論理削除です。プロジェクトに削除の印を付けるだけで、ジョブ・メッセージ・S3 のファイルはそのまま残り、ID も再利用しません。

  • 削除できるのは、ジョブが動いていないときだけです。待機中・実行中・回答待ち・仕上げ中のプロジェクトは、先に停止します（409）。
  • 削除すると、そのプロジェクトを Canon から外し、公開中なら公開をやめます。
  • 所有者にとって、削除したプロジェクトは存在しないのと同じです。プロジェクトの一覧、同じ名前の注意、古い ID からの転送の対象から外れ、そのプロジェクトのすべての API と WebSocket の購読は 404 か not found を返します。
  • 費用は利用者の合計に残り、削除したプロジェクトとして印が付きます（4.7）。管理画面の全プロジェクトの一覧には、削除済みとして出ます。
  • 復元の画面はありません。

実装

  • ID の検査は PROJECT_ID_REGEX / isValidProjectId、CANON_ID_REGEX / isCanonId、PLAN_ID_REGEX / isPlanId が行います。乱数はプラットフォームの暗号論的乱数です。
  • 一意性：API は乱数の ID を引き、Catalog に kind = id の行を条件付き Put（attribute_not_exists(id)）で書いて予約します。取られていれば引き直します（5 回まで）。予約できてから参考資料を移し、プロジェクトを attribute_not_exists(projectId) で Put します。Projects テーブルは userId がキーなので、この条件は呼んだ人のプロジェクトしか見ません。全体での一意性は予約の行が保ちます。予約は消さないので、ID は再利用されません。Canon（type = canon）と計画（type = plan）も同じように予約します。利用者ごとの番号 projectSeq / canonSeq は使いません。
  • GET /projects は、呼んだ人のプロジェクトを createdAt の新しい順に返し、同じ時刻なら ID の順にします。limit（既定 100）と cursor（この順の中の位置）でページを送ります。
  • 名前の出どころは nameSource です。仮の名前は provisional、エージェントの名前は auto（meta.json の name から）、利用者の名前は user です。ワーカーが置き換えるのは provisional か auto のときだけです。
  • ダウンロード名は filename*=UTF-8''… で送り、ASCII の代わりとして filename="<ProjectID>.bra.xlsx" を付けます。
  • 削除：DELETE /projects/{id} は Projects の項目に deletedAt / deletedBy を書きます。条件は、まだ削除されておらず、状態が QUEUED・RUNNING・WAITING_USER_INPUT・FINALIZING でないことです。索引は増やさず、API が印で絞ります。/users/me/usage は byProject に deleted の印を付け、/admin/projects は deletedAt 付きで返します。復元するには項目から deletedAt を消します（将来の管理用 API）。

典拠：packages/shared/src/projectId.ts・canon.ts・plan.ts、packages/api/src/lib/catalog.ts、packages/api/src/app.ts

エージェント欄

右の欄の名前は「チャット」ではなく「エージェント」です。この欄は自由な会話の場ではなく、エージェントの実行そのものを示す場であり、利用者は質問への回答とフォローアップでその実行を導くからです。

  • ログは、コーディングエージェントの画面のように読めるようにしてあります。エージェントの返答は全幅の Markdown で、利用者の依頼は「依頼」「回答」「追加の指示」のラベル付きの灰色の区画で示します。お知らせ（待機、モデル、段階の完了、ファイルの用意、使用量、エラー）は、アイコンと時刻付きの 1 行です。完了した段階とファイルは緑、エラーは赤で、詳細があれば開けます。
  • 2 つの返答の間の思考とツールの呼び出しは、「思考・実行ログ」という 1 行にまとめ、ステップの数・経過時間・TODO の進捗を出します（例：「8 ステップ · 2 分 18 秒 · TODO 2/5」）。開くとステップの一覧が出て、各ステップは全文まで開けます。終了コードが 0 でないコマンドは赤で示します。
  • 実行が待っている質問は、ログの最後に黄色の囲みで出ます。番号付きの選択肢（「1. …」）はボタンになり、押すと回答の欄に入ります。
  • 下の入力欄は、プロジェクトの状態に従って変わります。質問への回答（黄色）、フォローアップ（完了したとき）、停止ボタン付きのロック（実行中）、「続きからリトライ」付きのロック（失敗・中止したとき）です（3.6）。

画面のラベルは短くし、説明は「?」のヘルプか利用マニュアルの該当する節に置きます。キー操作、動きの表示、スクロールの振る舞いなどの細部は利用マニュアルにあります。進捗は WebSocket で届き、実行中のプロジェクトは 20 秒ごとにも読み直します。サイドバーの履歴は 30 秒ごとに読み直します。計画の画面は 6.10 で説明します。

4.5 版

BRA のジョブ（初回・フォローアップ・リトライ）が完了すると、ワーカーは結果を変更できない版として凍結します。凍結はジョブを完了にする前に行います。作業用のファイルは実行のたびに上書きされるので、プロジェクトの履歴は版が担います。BRA-DB への登録は、必ず版から行います（第 7 部）。

項目仕様
番号と ID版の番号 n は、ジョブを終えた後のプロジェクトの rev である。そのため、ほかの場所に保存した番号（複製元の番号、Canon が記録したプロジェクトの番号、解説記事の元になった番号）は、そのまま版を指す。全体で一意な ID は <ProjectID>@v<n>（Project ID は再利用されない）
親版 n-1。複製したプロジェクトの最初の版では、コピー元の公開プロジェクトの版が親になる
凍結する内容ワーカーの作業ディレクトリのデータ（HCD・FRG・CSV のデータ、レポート、判断ログ、検査結果。ログの *.jsonl は除く）、xlsx、グラフの JSON、BRA-DB の登録パッケージ、版の記録（manifest）
変更できないことファイルを先に、manifest を最後に、上書きできない方法で書く。manifest がある版だけが存在し、置き換えられない。同じジョブで凍結をもう一度行うと、既存の版を返す。別のジョブが作った同じ番号の版には触れず、そのことを記録する。凍結に失敗しても記録するだけで、ジョブは失敗にしない。版のファイルは、S3 のバケットのポリシーでだれも削除できない
生成条件版の記録には、その版を作った条件を残す：アプリのバージョンと git commit、指示書と JSON Schema のハッシュ、モデル、推論の強さ、調査モード、固定した Canon の rev、HCD の検査が従った SABRA の境界とその版、検査の規則の番号、CSV の形式、計画から作ったときはその計画。仮説モードでは、根拠のモード・仮説の範囲・上限・仮説の件数も残す（3.12）
内容のハッシュ5 つの CSV（Project・References・Circuits・Connections・FRG）から計算する。BRA-DB に入るのはこの 5 つなので、データが同じならファイルの名前や詰め方によらず同じハッシュになる
親との差分表ごとに、追加・削除・変更した行の数を要約して残す。親の版のファイルがなければ要約はない
登録パッケージ5 つの CSV がそろうときだけ作る。BRA-DB の登録だけが読む内部のもので、ダウンロードには出さない（第 7 部）

「版」タブ

  • 版の一覧を新しい順に出します。各行には、番号、現在の版かどうか、由来、日時、実行の種類、モデル、変わった行の数、フォローアップの指示の文が出ます。
  • 選んだ版について、生成条件、表（凍結したファイルを表データと同じビューアで開く）、ファイルの一覧、ほかの版との行単位の差分を見られます。差分の比較先の既定は 1 つ前の版です。
  • ヘッダーには、現在の版と内容のハッシュの先頭の文字が出ます。
  • 版はダウンロードできません。タブにダウンロードの操作はなく、ヘッダーのダウンロードはいつも現在のデータを返します。
  • 差分では、行を BRA-DB と同じキーで照合します。References は Reference ID、Circuits は Circuit ID、Connections は sCID・rCID・Reference ID の組、FRG は Node ID です。Connections で同じキーが繰り返すときは、順に #2、#3 を付けて区別します。比較は列ごとに行います。Project.csv はプロジェクトの行だけを比べます。Review End Lines の行は行数に従って変わるためです。

実装

  • 版の番号はプロジェクトの revision です。ほかの場所の番号は、複製元の clonedFrom.revision、Canon の projectRevision、解説記事の sourceRevision です。
  • 保存先は S3 のプロジェクトの接頭辞の下の revisions/{n}/ です。files/（ワークスペース）、output/*.xlsx、graph/*.json、bradb/（登録パッケージ）、manifest.json（BraVersionManifest）を置きます。書き込みは条件付きの put（If-None-Match: *）です。バケットのポリシーは users/*/*/revisions/* の削除をすべての主体に禁じます。番号の衝突は sys.versionConflict、凍結の失敗は sys.versionFailed として記録します。
  • manifest の中身：版 ID、親、由来（job / baseline）、作成時刻、Contributor、ジョブ（ID・種類・指示）、生成条件、各ファイルの SHA-256 と大きさ、内容のハッシュ、親との差分の要約（親にスナップショットがなければ null）。生成条件は、アプリのバージョンと git commit、prompts/ と HARNESS_SCHEMAS の SHA-256、モデル、推論の強さ、調査モード、固定した Canon の rev、SABRA の境界（neocortex / legacy）と RCS が返した境界の版、検査の規則 harnessRules（規則のないプロジェクトは 0）、Project.csv の CSV の形式、計画から作ったときの planId です。
  • 内容のハッシュ contentSha256 は、Project.csv・References.csv・Circuits.csv・Connections.csv・FRG.csv の順に <CSV 名>\t<その SHA-256>\n を並べた文字列の SHA-256 です。ないファイルは - とします。
  • 登録パッケージは、BRA-DB のインポートが読む名前の CSV（<ProjectID>_project.csv、_references.csv、_circuits.csv、_connections.csv、_frg.csv）と manifest.json（BradbPackageManifest）です。manifest の欄は、projectId・versionId・version・parentVersionId・contentSha256・各ファイルのハッシュ・braVersion（CSV の形式）・cobracGenerated: true・importType: "cobrac"・Contributor・生成条件 provenance・import.replace / import.allowShrink です。replace は親が同じプロジェクトの版のとき true、allowShrink は変更が Circuits か Connections の行を減らすとき true です。対象は BRA-DB のスキーマ v4.6、インポート v3.10 以降です。
  • DynamoDB には版の要約（BraVersionSummary：番号、ID、親の ID、由来、作成時刻、内容のハッシュ、アプリのバージョン、git commit、差分の要約、パッケージの有無、記録している版では仮説の数）を持ちます。その版を作ったジョブの Jobs.braVersion と、最新の版を表すプロジェクトの Projects.latestVersion です。テーブルとインデックスは増やさず、既存の項目の属性として持ちます。
  • API：GET /projects/{id}/versions（一覧）、…/versions/{n}（manifest とファイル）、…/versions/{n}/diff?base=（差分）。表のビューアは凍結したファイルを GET /projects/{id}/artifacts/text で読みます。GET /projects/{id}/artifacts/download は revisions/ の下のキーを拒みます。差分の計算は diffBraCsvs です。

典拠：packages/shared/src/braVersion.ts、packages/worker/src/versions.ts・index.ts、packages/api/src/app.ts（版のルート）

4.6 公開・複製・共同編集

プロジェクトは所有者だけのものですが、所有者は 2 つの方法でほかの利用者と共有できます。プロジェクトを公開して閲覧と複製を許す方法と、Canon に共同編集者を加える方法です。Canon の公開と、Canon から Canon への PR は 5.11 で説明します。

公開

  • プロジェクトは非公開（既定）か公開のどちらかです。切り替えられるのは所有者だけで、いつでも非公開に戻せます。
  • 公開できるのは、成果物があり、ID が現在の形式のプロジェクトです。現在の形式の ID は、乱数の形と <userKey>-<番号> の形です（付録 C）。
  • 公開する前に、何が公開され何が公開されないかを確認の画面で示します。
  • 公開したプロジェクトは、ログインしたすべての利用者が「公開ライブラリ」で一覧・閲覧できます。公開ライブラリには、公開された Canon も並びます（5.11）。
  • 非公開に戻すと、すぐに公開ライブラリから消えます。公開中に作られた複製は、複製した人のものとして残ります。
区分内容
公開するもの名前、ROI、TLF、Contributor、rev、レポート、判断ログ、HCD・FRG の JSON（回路の一覧）、グラフの JSON、解説記事。所有者は仮名の userKey で示す
公開しないものエージェント欄の履歴と会話、ジョブ、トークンの使用量と費用、参考資料、BRA の xlsx、グラフの配置、所有者のメールアドレスと利用者 ID

複製

公開されたプロジェクトは、「複製」で自分の新しい非公開のプロジェクトとしてコピーできます。元のプロジェクトは読むだけで、変わりません。

項目内容
新しいプロジェクト新しい Project ID。名前は元の名前に「 (clone)」を付けたもの。Contributor は元のまま。状態は完了。調査モード、SABRA の境界、検査の規則、仮説モードの設定を引き継ぐ。複製元の ID・その rev・所有者の userKey・名前・時刻を記録する
コピーするもの作業ディレクトリのデータ（HCD・FRG・CSV のデータ、検査結果、レポート、判断ログ）、グラフの JSON、解説記事とその図。フォルダ名と、テキストファイルの中の元の Project ID は、語単位で新しい ID に書き換える
コピーしないものエージェント欄の履歴、ジョブ、メッセージ、使用量、グラフの配置、参考資料、BRA の xlsx。xlsx は元の ID を含むので、xlsx の段階を未実行にしておき、フォローアップで作り直す
複製の数元の所有者には、プロジェクト画面と公開ライブラリで複製の数だけが見える。だれが複製したかは見えない

複製したプロジェクトの最初の版の親は、コピー元の公開プロジェクトの版です（4.5）。

Canon の共同編集者

  • 所有者は、既存のアカウントのメールアドレスを指定して共同編集者を加えます。API は登録済みの利用者からそのアドレスを探すので、所有者には、そのアドレスのアカウントがあるかどうかが分かります。
  • 共同編集者が見られるのは、Canon、参加プロジェクトの名前・ID・ROI・TLF、rev と PR（審査の資料を含む）、所有者とほかの共同編集者の表示名です。共同編集者のメールアドレスは、所有者にだけ見えます。
  • 共同編集者は、所有者のプロジェクト・エージェント欄の履歴・使用量を開けません。
  • 共同編集者が依頼した AI レビューは、その人のキーで実行し、その人の使用量に数えます（5.8）。

実装

  • 公開の切り替えは PUT /projects/{id}/visibility です。公開できる ID かどうかは isPublishableProjectId（PROJECT_ID_REGEX）で判定します。公開したプロジェクトは Catalog テーブルに kind = project の行を持ち、非公開にするか削除すると行を消します。一覧と閲覧のたびに、プロジェクトそのものの状態を検査し直します。閲覧の API は /public/projects/{id} です。
  • 複製は POST /public/projects/{id}/clone です。新しいプロジェクトの保存先は users/<複製した人>/<新しい ID>/、複製元の記録は clonedFrom です。引き継ぐ設定は sabraBoundary、harnessRules、evidenceMode・hypothesisScopes・hypothesisMaxShare などです。複製の数は Catalog テーブルの clones の行に数えます。

典拠：packages/api/src/app.ts（公開・複製のルート）、packages/shared/src/publish.ts

4.7 使用量と費用の表示

ジョブごとに、OpenAI のモデルが使ったトークンの量（使用量）と、そこから計算した推定費用を記録し、画面に表示します。費用は単価表から計算した推定値で、実際の請求額の正本は OpenAI のダッシュボードです。測り方と単価表は 9.10 にあります。

記録するもの内容
使用量入力、そのうちキャッシュされた入力、出力、そのうち推論のトークンの 4 つの量。途中で止まったターンの分も数える
モデルジョブの開始時に実際に使ったモデル（4.2）
推定費用使用量に、モデルごとの単価をかけた値。単価表にないモデルでは費用を出さず、画面は $— と表示する
キーの種類自分のキーとデフォルトの API キーのどちらで実行したか（4.1）

使用量と費用は、次の場所に出ます。

場所表示
エージェント欄使用量のお知らせの行
プロジェクト画面のヘッダーそのプロジェクトの使用量
プロジェクト一覧全プロジェクトの費用の合計
利用者ごとの集計全体・モデルごと・プロジェクトごとの合計。自分のプロジェクトのジョブに加えて、自分の Canon と共同編集者として入っている Canon の AI レビュー、自分の計画のジョブも全体とモデルごとの合計に含める。削除したプロジェクトの費用も残し、削除済みの印を付ける
計画の画面計画のここまでの費用。計画そのもののジョブの費用を別に示す（6.10）
管理画面デフォルトの API キーで実行したジョブの、利用者ごとのトークン・推定費用・UTC の今月の費用・単価のないジョブの数

古いジョブの記録には、使用量を大きく数えたものがあります。API はそうした記録を返すときに補正し、画面はどこでも補正した値を出します（9.10）。BRA を 1 つ作るときの時間と費用の目安は 1.4 にあります。

実装

  • 使用量は { inputTokens, cachedInputTokens, outputTokens, reasoningOutputTokens }、モデルは model、推定費用は costUsd（estimateCostUsd()）です。
  • 利用者ごとの集計は GET /users/me/usage（byProject に deleted の印）、管理画面の集計は GET /admin/org-usage（keySource: "org" のジョブ）です。
