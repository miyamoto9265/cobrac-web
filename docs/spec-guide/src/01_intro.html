序章

本書について

本書は Web アプリ CoBRAC Agents の設計書であり、リポジトリのコードに基づいて記述されています。回路の命名規則、BRA の作り方、プロジェクトと版、回路の定義をそろえる Canon、多数の BRA をまとめて作るオーケストレーター、BRA-DB への登録、およびそれらを動かすシステムとセキュリティを 1 冊に収めています。

0.1 本書の位置づけと読み方

本書は、表紙に記載したバージョンのコードの動作を記述したものです。仕様を変えるときは、コードと本書を同じ変更の中で修正します。それでも両者が食い違った場合は、コードを正とし、本書の誤りとして扱います。

前半（第 1〜7 部）は、CoBRAC を使う人と BRA を読む人に向けて、何をどういう規則で作るかを説明しています。後半（第 8・9 部と付録）は、開発と運用を担う人に向けて、それを実現する仕組みを説明しています。読者ごとの読み方は次のとおりです。

0.2 だれが何をするか

CoBRAC の中で働くものは、LLM、プログラム、人の 3 種類です。この区別は仕様の要です。判断するのは LLM と人で、規則に照らして検査し、手順を進めるのはプログラムです。LLM が書いたものは、必ずプログラムの検査を通ってから次に進みます。

担い手種類すること詳しくは
利用者・所有者・共同編集者・管理者人ROI と TLF、指示、参考資料を送る。エージェントの質問に答える。Canon の PR を承認する。計画を作る。管理者は利用者と API キーと上限を管理する第 4 部、5.8、第 6 部
CoBRAC エージェントLLM文献を調べ、ROI・回路・接続・機能の分解を判断して、データのファイルと説明を書く第 3 部
ワーカープログラムジョブごとに起動し、段階を進め、エージェントに依頼文を渡し、返ってきたファイルを検査して直させる。CSV・xlsx・グラフ・版を作る第 3 部、8.4
API・dispatcher・janitor・計画ランナーなどプログラムプロジェクトとジョブを記録し、ワーカーを起動し、止まったジョブを回復し、計画を進める8.2、8.3
lit・RCSプログラムエージェントが呼ぶツール。文献の検索結果や SABRA の単位の候補を返すだけで、採否は判断しない3.7、2.3

LLM が動くのは、ワーカーが Codex を通じて実行するジョブの中だけです。API や計画ランナーなどの Lambda は LLM を呼びません。LLM を使うジョブは次のとおりで、ジョブごとに会話が分かれており、互いの会話は共有しません。

LLM の仕事ジョブ使えるツール詳しくは
BRA を作る（CoBRAC エージェント）initial・followup（回答後の再開とリトライもこの会話を続ける）Web 検索、lit、RCS、作業ディレクトリでのコマンド第 3 部
解説記事を書くarticle成果物を読むシェルだけ3.14
Canon の PR の AI レビューと判断canon-review（所見を出す assist と、自律実行で判断する decide）なし5.8、6.8
計画の下書き・再計画・回答・解決plan（draft・replan・answer・resolve）下書きと再計画では RCS と添付資料の読み取り。回答と解決ではなし6.4、6.6、6.8

典拠：packages/shared/src/types.ts（JobType・planJobKind・reviewKind）、packages/worker/src/index.ts、codex.ts

0.3 用語

本書で使う主な用語を次に示します。各部に固有の細かい用語は、その部で定義しています。

用語意味
BRABrain Reference Architecture。脳の構造（HCD）と機能（FRG）を対応づけた参照アーキテクチャのデータ。CoBRAC では 1 つのプロジェクトで 1 つの BRA を作る
ROI / TLF対象の脳領域 / トップレベル機能（その領域が担う機能）。どちらか一方だけを指定してもよく、足りない側はエージェントが調べて補う
HCDHypothetical Component Diagram。回路（UC）をノード、回路間の接続（Connection）をエッジとするグラフ（3.1）
FRGFunction Realization Graph。TLF を機能ノード（GN）に分解し、最下層で HCD の UC に結びつける木（3.1）
UCUniform Circuit。均質な情報を符号化する最小のメゾスコピックな神経集団として、その HCD が扱う回路。HCD のノード（2.9）
Collectionその HCD が細かい UC に分けた回路（Uniform が FALSE）。Sub-Circuits に分解され、接続の端や FRG の葉にはならない（2.9）
GNFRG の機能ノード（Group Node、R.）。TLF を分解した部分機能
BIF組織間の解剖学的な投射を示す文献の根拠。UC 間の Connection の根拠になる
SABRA組織の混合アトラス。新皮質は BNA（Brainnetome）、それ以外は DHBA を使う。SABRA 自体は独自の ID を持たない（2.3）
HOMBA / DHBA / BNAHOMBA はヒトの脳のオントロジーで、DHBA 側の単位は DHBA 名を持つ HOMBA の項目。BNA は Brainnetome Atlas のラベルで、左が奇数、右が偶数
RCSROSETTA Candidate Search。名前から HOMBA と BNA の候補と SABRA での扱いを返す MCP サーバー（別リポジトリ rosetta-candidate-search）
CoBRAC エージェントBRA を作る LLM。OpenAI のモデルを Codex で動かす。本書で単に「エージェント」と記した場合はこれを指す
CodexOpenAI のエージェント実行環境（Codex SDK と CLI）。モデルにツールを使わせ、会話を管理する
ワーカージョブごとに AWS Fargate で動く TypeScript のプログラム
ハーネスエージェントを決まった手順で動かし、成果物を検査して直させる仕組みの全体。ワーカーのプログラム、指示書、JSON Schema、検査、変換からなる（第 3 部）
プロジェクトBRA を 1 つ作る単位。ID はシステムが付け（p + 7 文字）、変えず、再利用しない。名前は自由に変えられる（4.3）
ジョブワーカーの 1 回の実行。BRA の作成（初回・フォローアップ・回答後の再開・リトライ）のほか、解説記事、AI レビュー、計画用のジョブがある
段階BRA のジョブの区切り。HCD、FRG、CSV、xlsx の順に進む。調査モードでは、HCD の前に調査ステップが入る（3.7）
ターンエージェントが依頼文を 1 つ受け取ってから、終了の JSON（status は done か question）を返すまでの作業
会話ターンの履歴（Codex のスレッド）。BRA を作る会話は、1 つのプロジェクトに 1 つ
依頼文 / 指示書ワーカーがターンごとにエージェントに渡す文 / その元になる prompts/ のファイル（付録 B）
作業ディレクトリワーカーのディスク上の /work。プロジェクトフォルダ（/work/<ProjectID>/）と、ワーカーが置く AGENTS.md・schemas/・materials/・canon/ を含み、S3 に保存される
検査 / 照合プログラムが規則に照らして判定すること / Crossref や PubMed などの外部のデータや文献の原文と突き合わせること
受理段階の成果物が検査に通り、次の段階に進めること
修正依頼検査で見つかった問題をエージェントに返して直させる依頼。そのためのターンが修正ターン
フォローアップ完了したプロジェクトに修正を指示し、同じ会話で成果物を作り直すジョブ。画面では「追加の指示」
リトライ失敗または中止したジョブを、前回の成果物から再開するジョブ（画面の「続きからリトライ」）。API の呼び出しなどを自動でやり直すことは「再試行」と呼んで区別する
推論の強さモデルの reasoning effort（画面では「Reasoning effort」）
デフォルトの API キー組織の OpenAI API キー。管理者が利用承認（Tier 1 / Tier 2）した利用者は、自分のキーがなくてもこのキーでジョブを実行できる（4.1）
使用量ジョブが使ったトークンの量。費用はここから計算する（4.7、9.10）
版完了したジョブの結果を凍結したもの。ID は <ProjectID>@v<n>（4.5）。アプリのバージョンとは別
Canon / rev回路の定義をそろえるプロジェクトのまとまり / Canon の中身の版。PR を承認するたびに 1 つ進み、rev 0 は空の Canon（第 5 部）
PR / push / 取り込みプロジェクト（または別の Canon）の内容を Canon に入れる依頼 / PR を送ること / PR が承認されて新しい rev になること
計画 / 行 / バッチオーケストレーターの単位。計画は行（ROI × TLF）の一覧で、行はバッチごとに実行される（第 6 部）
自律実行新しい計画の既定。確定・回答・PR の判断などを、オーケストレーターが人の代わりに行う。自律実行を切った計画を「人が対応する計画」と呼ぶ（6.8、6.9）

0.4 番号の対応

CoBRAC には、意味の違う番号がいくつかあります。混同を避けるため、本節でそれらを区別します。

番号対象現行の値
アプリのバージョンWeb・API・ワーカーを含むリリース（package.json の version）表紙を参照
ハーネスの世代HCD と FRG の往復を含む実行方式（付録 D）v2
harnessRulesプロジェクトごとに保存される検査規則の水準新しいプロジェクトは 2。1 は ROI 規則まで、2 は GN 規則も含む（3.8、3.9）。古いプロジェクトの値は付録 C
BRA の CSV 形式Project.csv の BRA versionCoBRAC-v1-1
公式 xlsx出力先の BRA テンプレートTemplate-v2-2
BRA の版あるプロジェクトの成果物の履歴<ProjectID>@v1、@v2 など（4.5）
Canon の revCanon の中身の履歴rev 0、1、2…（第 5 部）

プロジェクトは、作成したときの harnessRules、SABRA の境界、調査モードなどの設定を持ち続けます。アプリが新しくなっても、既存の BRA に新しい規則が一律に適用されることはありません。古い設定のプロジェクトがどう扱われるかは付録 C にまとめています。
