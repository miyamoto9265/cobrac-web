0.2 CoBRAC Agents の概要

CoBRAC Agents は、BRA（Brain Reference Architecture）のデータ作成を、ブラウザから LLM のエージェントに行わせる Web アプリです。利用者は ROI（対象の脳領域）と TLF（トップレベル機能）を入力し、エージェントが文献を調べて次の 2 つのグラフを作ります。

HCD（Hypothetical Component Diagram）
回路（UC：Uniform Circuit）をノード、回路間の接続（Connection）をエッジとするグラフ。どの脳領域のどの神経集団が、どこから入力を受け、どこへ出力するかを、文献の根拠つきで表します。
FRG（Function Realization Graph）
TLF を機能ノード（GN、R.）に分解し、最下層で HCD の UC（U.）に結びつける木。どの回路の組み合わせがどの機能を実現するかを表します。

処理は 調査（既定で有効）→ HCD → FRG → CSV → xlsx の順に進みます。推論するのは CoBRAC エージェント（OpenAI のモデルを Codex で動かす LLM）だけで、JSON のデータファイル（uc.json・connections.json・references.json・frg.json）と説明の文章を書きます。ワーカー（AWS Fargate 上の LLM を含まないプログラム）が各段を JSON Schema と決定的な検査（命名・文献・引用文・HCD と FRG の整合など）で確かめ、問題をエージェントに差し戻して直させます。CSV と xlsx はワーカーがコードで生成します（第 2 部）。

0.3 部の関係

第 2 部のハーネスが 1 件の BRA を作ります。第 3〜6 部の仕組みは、その外側で、複数の BRA を矛盾なく作り、蓄積するためのものです。第 1 部と第 7 部は、それらすべてを動かすシステムと AWS の基盤を説明します。

仕組みひとことで何を解決するか
ハーネス（第 2 部）1 件の BRA の「作り方」LLM に自由に書かせると、形式の誤り・架空の文献・HCD と FRG の食い違いが残る。LLM の判断とプログラムの検査を分け、検査に通るまで差し戻す。
UC Descriptor・facet（第 3 部）回路の「名前」の規則自由な名前では、同じ神経集団がプロジェクトごとに別の名前になり、照合も集計もできなかった。SABRA の単位と明示的な属性だけから名前を組み立て、どこでも同じキーにする。
Canon（第 4 部）回路の「定義」をそろえる単位同じ名前の回路でも、BRA ごとに粒度（Uniform か Collection か）や分け方が違うと統合できない。そろえる範囲を決め、その中では定義を 1 つにし、変更は審査を通す。
BRA-DB（仮）（第 5 部）完成した BRA の「登録先」成果物を WBAI の BRA-DB と同じスキーマで蓄積し、どの版が、どの条件で作られ、誰がいつ登録したかを失わずにたどれるようにする。
オーケストレーター（第 6 部）BRA を「まとめて作る」段取り数十〜百件超の ROI × TLF を 1 件ずつ手で起動すると、順序・同時実行数・回路の重複・Canon への取り込みの管理が破綻する。計画にして、順序をコードで計算し、自動で進める。

0.4 用語と版番号

用語意味
BRABrain Reference Architecture。脳の構造（HCD）と機能（FRG）を対応づけた参照アーキテクチャのデータ。CoBRAC では 1 プロジェクト = 1 件の BRA
ROI / TLF対象の脳領域 / トップレベル機能。どちらか一方だけでも作成できる（エージェントが残りを調べる）
UCUniform Circuit。その HCD が均質な情報を表現するとみなす神経集団。HCD のノード
Collectionその HCD が細かい UC に分けた回路（Uniform = FALSE）。Sub-Circuits に分解され、接続の端や FRG の葉にならない
BIF組織間の解剖学的投射を示す文献の根拠。UC 間の Connection の根拠になる
GNFRG の機能ノード（Group Node、R.）。TLF を分解した部分機能
SABRA組織の混合アトラス。新皮質は BNA（Brainnetome）、それ以外は DHBA。SABRA 自体は独自の ID を持たない
HOMBA / DHBA / BNAHOMBA はヒトの脳のオントロジー（DHBA 側の単位は DHBA 名を持つ HOMBA の項）。BNA は Brainnetome Atlas のラベル（左が奇数、右が偶数）
RCSROSETTA Candidate Search。名前から HOMBA・BNA の候補と SABRA での扱いを返す MCP サーバ（別リポジトリ rosetta-candidate-search）
CoBRAC エージェントBRA を作る LLM。OpenAI のモデルを Codex で動かす。この文書の「エージェント」
ワーカージョブごとに AWS Fargate で動く TypeScript のプログラム。LLM を含まない
CoBRAC ハーネスワーカーのプログラム、指示文、JSON Schema、検証器、変換処理の全体。LLM は含まない
CodexOpenAI のエージェント実行環境（Codex SDK と CLI）。モデルにツールを使わせ、会話を管理する
ターン / 会話依頼文を 1 つ受け取ってから終了の JSON を返すまでのエージェントの作業 / ターンの履歴（Codex のスレッド。1 プロジェクトで 1 つ）
検証器ワーカーがファイルを検査するコード。LLM ではない
作業場所ワーカーのディスク上の作業ディレクトリ（/work）。プロジェクトフォルダと、ワーカーが置く AGENTS.md・schemas/・materials/・canon/ を含む。S3 に保存される
プロジェクト / ジョブ1 件の BRA の作成単位（ID は p + 7 文字）/ ワーカーの 1 回の実行（初回・回答後の再開・追加指示・再試行・解説記事など）
版（バージョン）完了したジョブの結果を凍結したもの。ID は <projectId>@v<n>
revCanon の版。PR を承認するたびに 1 つ進む。rev 0 は空の Canon
PRプルリクエスト。プロジェクト（または別の Canon）の内容を Canon に取り込む依頼
計画 / 行 / バッチオーケストレーターの単位。計画は行（ROI × TLF）の一覧で、行はバッチ（wave）ごとに実行される
番号の対応（別々の番号なので混同しない）
番号対象現行の値
