第 2 部

ハーネス：1 件の BRA の作り方

CoBRAC ハーネスは、ROI（対象の脳領域）と TLF（トップレベル機能）から 1 件の BRA を作るために、LLM のエージェントを決まった手順で動かし、その成果物をプログラムで検査・変換する仕組みです。推論するのは CoBRAC エージェント（LLM）だけで、ワーカーは LLM を含まないプログラムとして、依頼を送り、返ってきたファイルを検査し、次の依頼を決めるループを回します。この部は、ハーネスの世代 v2（新規プロジェクトの検証ルール harnessRules: 2）の現行の仕様です。

推論する主体は 1 つ文献を読み、回路や機能を判断する LLM は CoBRAC エージェントだけ。1 件のプロジェクトで 1 つの会話を続ける
ワーカーは LLM ではない段の順序・依頼文・検査・変換・保存を決まったコードで行う。次の段に進むかを決めるのもこのコード
受け渡しはファイル会話で渡るのは依頼文とターン終了の JSON だけ。データ JSON と説明はエージェント、検査結果と CSV・xlsx はワーカーが書く

2.1 登場する主体（LLM とプログラム）

推論する LLM：CoBRAC エージェント

この文書で「エージェント」と書くときは、BRA を作る CoBRAC エージェントを指します。中身は OpenAI の言語モデルで、モデルと推論レベル（reasoning effort）はプロジェクトごとに選びます（1.8）。モデルは OpenAI の Codex（Codex SDK と Codex CLI）を通して動きます。Codex は、モデルにシェルでのファイルの読み書き、MCP のツール、Web 検索を使わせ、会話の履歴とその自動圧縮を管理する実行環境です。推論そのものは、コンテナの外の OpenAI API で行われます。

エージェントは、自分で作業を始めたり段を進めたりしません。ワーカーから依頼文を 1 つ受け取ると、それに応える 1 回のターンの中で、文献を検索し、原文を読み、ファイルを編集します。ツールはターンの中で何度でも呼べます。ターンの最後に終了報告の JSON を返して止まり、次の依頼を待ちます。

1 件のプロジェクトでは、調査・HCD・FRG・修正・調整のすべてのターンが同じ会話（Codex のスレッド、codexThreadId）で続きます。質問への回答、途中からの再試行、完成後のフォローアップも、同じ会話を再開します。会話が OpenAI の 1 リクエストの上限を超えたときだけ、ワーカーが新しい会話に切り替え、プロジェクトのファイルと判断ログを読んで続けるよう指示します。

LLM ではないもの：ワーカー

ワーカーは、ジョブ 1 件ごとに AWS Fargate で起動する TypeScript（Node.js）のプログラムです（packages/worker）。基本は Spot で起動し、起動できない場合は On-Demand を使います。ワーカーは LLM を含まず、判断はすべて決まったコードで行います。中心にあるのは次のループです（runPhases）。

  1. 段の依頼文を組み立ててエージェントに送る
  2. ターンの終了を待つ
  3. エージェントが書いたファイルを検証器で検査する
  4. 問題があれば問題一覧を付けて修正を依頼し、なければ次の段へ進む

CoBRAC ハーネスは、このワーカーのプログラムに、エージェントへ渡す指示文（prompts/）、JSON Schema（HARNESS_SCHEMAS）、検証器、出力への変換処理を合わせた全体の呼び名です。LLM はハーネスに含まれず、ハーネスが動かす対象です。

エージェントの Codex プロセスは、ワーカーが同じコンテナの中で子プロセスとして起動します。そのため「ワーカーの中でエージェントが動く」と書くことがありますが、これは置き場所の話です。ワーカーが推論するという意味ではありません。

2.2 BRA の作成以外で LLM を使う仕事

アプリには、BRA を作るジョブのほかに LLM を使うジョブが 3 種類あります。どれも同じワーカーのプログラムが別の実行モードで起動し、BRA の会話とは別の新しい会話で LLM を呼びます。これらの LLM は BRA を作ったエージェントの会話を引き継がず、受け取るのはワーカーが用意したファイルや JSON だけです。

ジョブ（実行モード）LLM の役割LLM が使える道具LLM が出すもの結果を受け取る主体
BRA の作成（initial・resume・retry・followup）CoBRAC エージェント。この部の主題シェル、lit、RCS、Web 検索データ JSON、レポート、判断ログワーカーが検査・変換する
解説記事（article）完成した BRA の成果物だけを読み、指定言語の解説記事を書く（2.15）シェル（成果物の読み取り）。Web 検索・RCS・lit なし記事の Markdown（図を最大 2 枚足せる）ワーカーが形式を検査して修正を依頼し、公開する
Canon の AI レビュー（canon-review）Canon への取り込み依頼（PR）を読み、所見を出す（第 4 部）なし所見の JSON人が承認・却下を判断する。AI レビューは承認の代わりにならない
オーケストレーターの計画（plan）計画の行（ROI × TLF）、依存関係、アンカー、粒度方針を下書きし、バッチの後に変更を提案する（第 6 部）RCS、添付資料の読み取り計画の JSONワーカーが形を検査し、計画ランナー（Lambda のプログラム）が順序を計算して適用する

解説記事は 1 ターンの後に検査と修正のターンを続けます。AI レビューと計画は 1 ターンで、返答が出力スキーマの形でないときだけもう 1 回依頼します。どのジョブの使用量も、BRA のジョブと同じ単価表で費用に換算されます。

典拠：packages/worker/src/index.ts（articleMain・canonReviewMain・planJobMain）、article.ts、canonReview.ts、planJob.ts、prompts/article.md、prompts/plan.md

2.3 1 ターンの受け渡し

ワーカーとエージェントの間で、会話のメッセージとして行き来するのは 2 つだけです。ワーカーからの依頼文と、エージェントからのターン終了の JSON です。作業の中身は、すべて作業場所（ワーカーのディスク上の作業ディレクトリ /work。中心はプロジェクトフォルダ /work/<ProjectID>/）のファイルで受け渡します。

  1. ワーカー → エージェント：依頼文。プロジェクト情報と段の名前、段の仕様、前回の検査で見つかった問題の一覧、返答言語の指示を連結したテキストです（2.6）。
  2. エージェントの作業。エージェントはターンの中で lit・RCS・Web 検索を呼び、シェルでファイルを読み書きします。その間ワーカーは、ツールの呼び出しとファイルの変更をイベントとして受け取り、文献検索と RCS の呼び出しを記録し、画面に進捗を流します。ターンの途中でワーカーが指示を足すことはありません（取り消しや調査の時間切れでターンを打ち切ることはあります）。
  3. エージェント → 作業場所：ファイル。データ JSON、レポート、判断ログを書き換えます。
  4. エージェント → ワーカー：ターン終了の JSON。{"status": "done" | "question", "message", "question"} です（出力スキーマ TURN_OUTPUT_SCHEMA）。done は「このターンの作業を終えた」というエージェントの申告で、合格の意味ではありません。古い会話の [QUESTION]…[/QUESTION] の印も読めます。
  5. ワーカーの検査。ワーカーはファイルを読み直して検証器にかけ、結果を検査結果ファイルに書きます。
  6. ワーカーの判定。問題があれば問題一覧を付けた修正依頼を、合格なら次の段の依頼を送ります（1 に戻る）。question なら作業場所と会話を保存して停止します（2.7）。
レート制限とターンの失敗

Codex は、OpenAI のレート制限（429）に当たると自分で 5 回まで再接続します。それでも失敗したターンは、ワーカーが 30 秒〜3 分待って同じ会話で最大 3 回再開させます（「止まったところから続ける」依頼）。1 リクエストが大きすぎる失敗や、利用枠・請求の問題は待っても直らないので、再開しません。会話が大きすぎる場合だけ、新しい会話に切り替えて続けます。

典拠：packages/worker/src/codex.ts（runTurn・RATE_LIMIT_TURN_RETRIES・isRequestTooLarge）、packages/shared/src/harness.ts（TURN_OUTPUT_SCHEMA）

会話ではなくファイルを正本にする

会話が長くなって圧縮されたり、新しい会話に切り替わったりしても、生成の途中結果はプロジェクトのファイルに残ります。構造化したデータは JSON、自由な文章は Markdown です。JSON の形は HARNESS_SCHEMAS（packages/shared/src/harness.ts）で定義し、ワーカーがエージェント用に /work/schemas/*.schema.json として書き出し、検証器も同じ定義を使います。成果物はすべて英語で書きます（例外は解説記事だけ、2.15）。

人が読む説明は、エージェントが report.md（## Overview・## HCD・## FRG・## Limitations・## References、仮説があれば ## Hypotheses）にまとめます。decision_log.md は、エージェントが結論を選んだ理由、採らなかった案、利用者の回答、変更の理由を追記する記録です。RCS や検索の生ログを判断ログに転記する必要はありません。呼び出しの記録はワーカーが別のファイルに取ります。FRG の上からの分解・最適化・下からの読みは作業の手順で、専用のファイルはありません（理由はレポートに書きます）。

2.5 1 件の BRA ができるまで

新規作成では、既定で有効な調査ステップの後に HCD、FRG の段が続き、最後にワーカーが成果物を生成します。各段は「エージェントのターン → ワーカーの検査 → 必要なら修正のターン」の繰り返しで、段を進めるのは常にワーカーです。調査を無効にした場合は HCD から始まりますが、文献ツールと文献の検証は使われます。段の並び（HCD → FRG → CSV → xlsx）と、ワーカーが段を進めて検証する方式、ターン終了の JSON は、ハーネスの骨格として変えません。

2.6 依頼文の組み立て

ワーカーは作業場所に共通ルール AGENTS.md と schemas/ を用意します（AGENTS.md は作業場所の直下に置かれ、Codex が自動で読み込みます）。ターンごとの依頼文は、利用者にも表示する短い依頼（shown）、内部で付ける仕様（hidden）、返答言語の指示を、--- の区切りで連結したものです。仕様を画面上の短い依頼から省いていても、エージェントには渡しています。

仕様は単一の長い文章に固定されていません。ワーカーはプロジェクトの設定に応じて、HCD には ROI 規則（HCD_roi_rules.md）と Canon の条件、FRG には GN 規則（FRG_gn_rules.md）と HCD から計算した候補、調査モードには調査結果を使う指示（research_mode.md）、仮説モードには許された範囲（HYPOTHESIS.md）を足します。基礎仕様と追加規則を合わせたものが、そのプロジェクトの実際の指示です。全文は付録 B にあります。

ターン表示する依頼内部で加える内容
調査Project ID、ROI、TLF、Contributor、参考資料の場所、調査開始RESEARCH.md の Project ID と候補数・時間・検索数を展開
HCDプロジェクト情報と Run phase HCD.HCD.md、rules 1 以上なら ROI 規則、Canon 制約、必要時に RCS 利用不能の注記
FRGプロジェクト情報と Run phase FRG.FRG.md、rules 2 なら GN 規則、最新の frg_candidates.json の候補
調査モードの HCD・FRG各段と同じresearch_mode.md。調査結果の利用、追加調査、FRG の理論・計算モデルの文献調査
仮説モードの HCD・FRG各段と同じHYPOTHESIS.md。許可 scope、仮説率の上限、調査モードの有無を展開（調査の注記の後、FRG 候補の前）
検証の修正問題数、修正回数、最大 30 件の問題、ファイルを直す指示修正ターンの推論レベルをプロジェクト値と medium の低い方にする
整合の調整X1・X2・X3・X8 の所見と意味、片方または両方を直す依頼根拠に基づく選択と revisions 節への記録を要求。通常の推論レベルを使う
質問への回答利用者の回答と継続の指示新しい会話から再開する場合だけ、プロジェクト情報と仕様を補う
途中からの再試行既存ファイルを読んで未完了の段を終える指示必要な仕様。完成したファイルを作り直さない

2.7 質問・フォローアップ・再試行

質問

利用者の判断が必要だとエージェントが判断したとき、エージェントはターンの最後に status: "question" を返します。それを受けてワーカーが作業ファイルと Codex の会話を S3 に保存し、ジョブとプロジェクトを「回答待ち」（WAITING_USER_INPUT）にして終了します。回答が届くと、API が同じジョブに回答を記録して待ち行列に戻し（実行モード resume）、新しいワーカーが作業場所と会話を復元し、回答を依頼文にして同じ会話を再開します。質問への返答を待っている間は Fargate を動かし続けません。

フォローアップ

完成後の追加指示（followup）も、同じファイルと同じ会話から始まります。ワーカーは HCD と FRG の両方の仕様を依頼文で再提示し、エージェントが関連する ID、接続、インターフェース、レポートをそろえて直します。フォローアップはすべての段を受理前の状態から検証し直し（前の受理を引き継がない）、CSV と xlsx を再生成して、成果物を新しい版にします。指示の文章で仮説の範囲が広がることはありません（範囲は画面の設定だけで足す、2.13）。古い形の名前（UC Descriptor・Circuit ID）を持つプロジェクトでは、次のフォローアップで現在の形への書き直しを求めます（第 3 部）。

再試行

途中で失敗したプロジェクトの再試行（retry）は、受理済みの段を引き継ぎ、最初の未受理の段から続けます。エージェントには既存のファイルを読んで、完成したファイルを作り直さないよう指示します。解説記事のジョブは再試行の対象になりません。

典拠：packages/worker/src/index.ts（実行モード、runAgentTurn、persistState）、packages/api/src/app.ts（回答・フォローアップ・再試行の API、付録 A）

2.8 検証に通らないとき

HCD・FRG・CSV の各段では、ワーカーが問題を列挙してエージェントに修正を依頼します。上限は各段で最大 3 回（環境変数 MAX_NUDGES、既定 3）です。それでも問題が残る場合、データを読み込めない致命的な問題ならワーカーがジョブを失敗にし、読み込める場合は未解決の問題を警告として残して進みます。調整のターンの後の修正には、別に 3 回の枠があります。

完了は合格の保証ではない

ジョブの完了は、すべての検査が合格したことや、科学的な正しさを保証するものではありません。残った警告、未照合の引用、調査の不足、仮説への依存は、成果物と一緒に読む必要があります。

典拠：packages/worker/src/pipeline.ts（runPhases：maxNudges・fatal・onWarn）、packages/worker/src/env.ts
