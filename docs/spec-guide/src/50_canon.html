第 5 部

Canon

WBAI の山川さんは「整合単位」というコンセプトを提唱しました。CoBRAC はこれを Canon という仕組みとして実装しています。Canon は、回路の定義が互いに一致していなければならないプロジェクト（BRA）のまとまりです。同じ Canon の中では、同じ UC Descriptor の回路は、どのプロジェクトでも Uniform / Collection の区別、分解、Circuit ID と正式名が同じになります。

範囲どのプロジェクトどうしで定義をそろえるかを、Canon の参加プロジェクトとして決めます。1 つのプロジェクトが入れる Canon は 1 つまでです。
中身そろえるのは共有層（回路・接続・文献）です。機能や役割は、役割層としてプロジェクトごとに残します。
手続き作るときは rev に固定して制約をかけ、取り込むときは push、PR、審査、承認の順に進めます。承認するたびに新しい rev ができます。

5.1 整合単位

BRA は ROI × TLF ごとに作ります。同じ脳領域は多くの BRA に現れますが、BRA ごとに回路を独立に定義すると、同じ神経集団が BRA ごとに違う粒度になります。ある BRA では 1 つの UC、別の BRA では層ごとに分けた Collection、というようにです。分け方や名前も BRA ごとに変わるため、BRA どうしを合わせて 1 つの脳のモデルとして読むことができません。

「整合単位」は、回路の定義を互いに整合させる BRA の範囲を、1 つの単位として明示的に扱うというコンセプトです。脳全体のすべての BRA を 1 つの定義に強制的にそろえるのではなく、「この範囲の中では定義を 1 つにする」という単位を置きます。これにより、次の 2 つを両立させます。

単位の中では定義が 1 つ
同じ回路は、同じ ID・名前・粒度・分解を持ち、送り手は常に Uniform です。単位の中の BRA は、そのまま組み合わせて読めます。
単位ごとに粒度を選べる
ネットワーク水準の粗い単位と、層や細胞種の水準の細かい単位を並べて持てます。目的の違う BRA 群を、無理に 1 つの粒度へ押し込みません。

※ この節の説明は、Canon の仕様から読み取れる範囲で整合単位の考え方を整理したものです。コンセプトそのものの定義は、山川さんの原典の資料を参照してください。

第 2 部の命名規則（UC Descriptor）は「同じ集団かどうか」を判定できるようにするものです。整合単位は「同じ集団なら定義も同じであるべき範囲」を決めるものです。両者は組になって働きます。

5.2 Canon の定義

Canon の定義

Canon は、1 人のユーザーのプロジェクトのうち、回路の定義が一致していなければならないものの集合です。Canon の中では、同じ UC Descriptor は、同じ Uniform / Collection の区別と同じ分解（Sub-Circuits）を持ちます。プロジェクトをまたぐ接続では、送り手が Uniform であり続けます。Uniform かどうかは、Canon の外では HCD ごとに決まり（2.9）、Canon の中では固定されます。異なる Canon は異なる粒度を選べます。たとえば、ネットワーク水準の粗い Canon と、層の水準の細かい Canon を並べて持てます。なお「Canon」という名前は仮のものです。

中身が変わるときの原則

Canon の中身が変わるのは、PR が承認されたときだけです。承認するのは、人（所有者か共同編集者）か、所有者が自律実行を任せたオーケストレーター（6.8）です。どちらの承認も同じ検査を通り、解決していないエラーの衝突がある PR は取り込まれません（5.7）。オーケストレーターは、エラーの衝突がある PR をそもそも承認せず、プロジェクトを Canon に合わせるフォローアップに回します。

例外は、既存のプロジェクトを種にして Canon を作るときの rev 1 です。このときは作成の操作が種の承認を兼ねます（5.10）。

整合単位との対応

整合単位のコンセプトの各要素は、Canon では次のように実装されています。

5.3 Canon の基本

Canon の画面

Canon の画面は、プロジェクトの画面と同じく、ヘッダー（名前、最新の rev、粒度方針、件数、公開）の下にタブが並びます。中身がある Canon は「HCD グラフ」を、空（rev 0）の Canon は「プロジェクト」を開きます。

タブ内容
「HCD グラフ」最新の rev の共有層を、プロジェクトの HCD と同じ図で描く（Web が描く）。Uniform の回路と、接続の端になっている Collection が節点、ほかの Collection とまとまりが枠。無効になった項目は除く。ROI の色は参加プロジェクトの役割層から決め、どれか 1 つのプロジェクトで ROI 内なら ROI 内とする。回路を選ぶと push したプロジェクトが出て、1 つのプロジェクトの回路を強調できる。図の配置はブラウザに保存し、サーバーには保存しない。
「表データ」回路・接続・文献の表。CSV はブラウザで作ってダウンロードする。
「プロジェクト」参加プロジェクトと、プロジェクトごとの回路の数。
「PR」PR の一覧、まとめて承認（5.6）、別の Canon に PR を送る（5.11）。
「版の履歴」rev ごとの PR と承認者。
「設定」名前・粒度方針・説明・共同編集者。

実装

所属は Projects.canonId、最新の rev は headRevision、論理削除は deletedAt で表します。公開の設定は private / public、PR の受け付けは acceptPullRequests です。画面の URL は /canons/{id}/{view} です。

5.4 共有層と役割層

Canon の 1 つの rev は、1 つの不変な JSON です。中身は、プロジェクトをまたいで 1 つに決める共有層と、プロジェクトごとに持つ役割層に分かれます。

  • 回路は、正規化した UC Descriptor をキーにします（第 2 部）。プロジェクトの JSON では接続を Circuit ID で書くので、push のときに Descriptor に解決します。Descriptor のない UC は取り込まれず、その旨が一覧で示されます。
  • 接続は、送り手・受け手・Reference ID の組をキーにし、文献の欄と引用文の照合状態を持ちます。文献は Reference ID をキーにし、照合状態を持ちます。
  • すべてのエントリは来歴を持ちます。来歴には、どのプロジェクトのどの rev から、どの PR で入ったかを記録し、別の Canon を経由したときはその Canon と rev も記録します。あわせて、そのエントリを push したプロジェクトの一覧も持ちます。
  • エントリの状態は、有効（valid）、要注意（flagged。Collection に変わった回路に接続が残っているときなど）、無効（invalidated）のどれかです。
  • プロジェクトがエントリを使わなくなっても、Canon からは消しません。差分では「プロジェクトで使わなくなった」と表示するだけです。
  • 保存済みの回路は、アンカーの境界の変更（2.3）や古い命名の形を含んでいても書き換えません。比べるときに現在の形に直します。
  • 仮説（仮説モード、3.12）は共有層に入れません。push のときに、次のものを共有層から外し、そのプロジェクトの役割層にだけ置きます。仮説の付いた接続、仮説の集団で終わる接続、集団そのものが仮説の UC、仮説の性質です。

実装

rev のスナップショットは S3 の canons/{canonId}/rev/{n}/canon.json に置きます。経由の記録は via = <canonId>@<rev>、push したプロジェクトの一覧は sources、役割層の仮説は roles[].hypotheses です。比べるときに現在の形に直す処理は currentCanonSnapshot、プロジェクトからの変換は canonFromProject、差分は diffCanon です。

典拠：packages/shared/src/canon.ts・canonMerge.ts（canonFromProject・diffCanon）

5.5 生成時の制約

Canon に参加したプロジェクトは、1 つの rev に固定されます。参加したときは最新の rev に固定され、そのプロジェクト自身の PR が承認されると、その新しい rev に進みます。それ以外のときは、所有者が「最新の rev にする」で進めます（5.9）。

  1. Canon を渡す：ワーカーは、解説記事を除くジョブの開始時に、Canon の記録と固定した rev のスナップショットを読み取ります。そして、作業ディレクトリの中、プロジェクトフォルダの隣に、読み取り専用の canon/ を置きます。このフォルダは S3 に戻しません。空の Canon（rev 0）や見つからない Canon は、その実行では無効になるだけです。
  2. 指示する：HCD の仕様に、Canon について守ることの節が加わります。内容は下の箱のとおりです。ワークフローの骨格は変わりません。
  3. 作る：エージェントは canon/ を読み、それに従って uc.json などを書きます。
  4. 検査して差し戻す：ワーカーは HCD の検査の後で、結果を Canon と照合します。エラーの衝突のうち C1・C2c・C3・C4・C5・C6・C8 は、検査の問題として修正ターンでエージェントに戻します。C2b・C7・C8b・C9b・C12 はチャットに表示するメモにとどめ、エージェントには戻しません。C8c・C9c は、ハーネスの文献と引用文の照合に任せます（3.10）。
HCD の仕様に加わる指示
  • Canon の Circuit ID・正式名・伝達物質・修飾・Source of ID をそのまま使います。
  • Canon の Collection は Collection のまま扱い、その Sub-Circuits で接続します。単位全体についての証拠は、UC の接続に relation < で付けます。
  • Uniform の回路を分割しません。この TLF でどうしても細かく分ける必要があれば、理由を decision_log.md に書いてユーザーに質問します。
  • Canon の接続と文献を使うときは、記録をそのままコピーします。
  • 新しいエントリは粒度方針に従います。新しいエントリは、push のときに Canon への提案になります。

仮説は、この照合では証拠と同じに扱い、Canon の制約を緩めません。Canon で照合済みの文献・引用文と同じものは、もう一度照合しません。その場合は、文献と引用文の照合の記録に「Canon で照合済み」と残します。

canon/ のファイル（Circuit ID は現在の形で書き出す）

README.mdCanon の名前・ID・rev、粒度方針、ファイルの説明

5.6 push と PR

  1. push：完了した参加プロジェクトの画面で「Canon に push」を押します。押すのは所有者で、オーケストレーターの計画ではオーケストレーターが自動で行います。API は、ワークスペースの HCD・FRG・文献とその照合の記録を Canon の形に変換し、最新の rev と比べ、PR として保存します。同じプロジェクトの未処理の PR は、新しい PR に置き換えられます。PR を作らずに同じ差分だけを見ることもできます。
  2. 審査：所有者か共同編集者が、PR の画面で内容を確認します（5.8）。自律実行の計画の PR は、オーケストレーターの判断のジョブが判定します（6.8）。
  3. 判断：承認（メモは任意）、変更を依頼（メモが必要。PR は開いたまま）、却下（メモが必要）のどれかを選びます。変更の依頼と却下のメモは、送った側も履歴で読めます。送った側は PR を取り下げられます。
  4. 承認の書き込み：承認には、衝突ごとの選択が付きます。選択は「Canon の値のまま」か「取り込む側の値」です。push の後で最新の rev が進んでいれば、まず現在の最新の rev に対して判定し直します。承認すると rev n+1 を書き、最新の rev の番号を条件付きで進め、rev の記録を残します。同時に 2 つの承認があると、片方は失敗します。PR を送ったプロジェクトは、新しい rev に固定し直されます。

まとめて承認

Canon の画面の「PR」タブでは、複数の PR をまとめて承認できます。対象にできるのは、エラーの衝突も要確認の項目もなく、変更を依頼していない未処理の PR です。チェックを入れて（全選択もできます）「まとめて承認」を押すと、画面が件数の確認を出してから、選んだ PR を番号の順に 1 件ずつ承認します。一度に選べるのは 1〜50 件です。押せるのは、1 件ずつの承認と同じく、所有者か共同編集者です。

1 件ごとに、直前の承認でできた最新の Canon に対して判定し直します。必要なら差分を取り直し、判定し直したことを履歴に残します。承認の処理と記録は、1 件ずつ承認したときと同じです（衝突の選択はなし）。次のどれかに当たると、その PR で止まり、残りは承認しません。

止まる理由内容
見つからないPR がない。途中で Canon が削除されたときも、これで止まる（まだ 1 件も承認していなければ 404）
開いていないすでに処理済み
衝突がある新しい最新の rev に対して、承認を止める衝突がある（その数も返す）
承認数が足りない必要な承認の数に届かない
競合最新の rev の更新がほかの承認と重なった。承認中の予期しないエラー（ペイロードがない、AWS のエラーなど）も、これで止まる

どの場合も、それまでに行った承認は必ず結果に返ります。結果には、承認した件数と、どの PR でなぜ止まったかが出ます。

実装

  • push は POST /projects/{id}/canon/push です。変換するのはワークスペースの uc.json・connections.json・references.json・frg.json・meta.json・reference_check.json・quote_check.json で、canonFromProject で変換し diffCanon で比べます。PR の項目のほか、ペイロードと差分を canons/{canonId}/pr/{no}/ に保存します。差分だけを見るのは …/canon/preview です。
  • 承認は POST /canons/{id}/pulls/{no}/approve で、衝突ごとの選択 choices（canon か incoming）を持ちます。承認は rev を書いた後、headRevision を条件付きで進め（同時の承認は 409）、rev の記録（REV#）を残します。却下は …/reject（理由が必要）、取り下げは …/withdraw です。
  • まとめて承認は POST /canons/{id}/pulls/approve-many です。PR 番号が 1〜50 件でなければ 400 を返します。重複は除き、順番は保ちます。1 件ごとに 1 件ずつの承認と同じ関数（approvePullRequest）を、読み直した Canon に対して呼び、差分を取り直したときは rebased として記録します。
  • 止まる理由の値は not_found・closed・conflicts（数は blocking）・approvals・race です。応答は { approved: [{ prNo, revision }], stopped: { prNo, reason, blocking? } | null } です。

典拠：packages/api/src/lib/canonOps.ts（pushProject・approvePullRequest）、packages/api/src/app.ts（Canon の PR のルート）、packages/shared/src/canonMerge.ts

5.7 衝突ルール

PR の差分では、Canon の値と取り込む側の値を項目ごとに比べ、次の衝突を判定します。取り込む側の分解が Canon の分解の部分集合であることは、衝突になりません。

コード重さ内容承認での扱い
C1エラー同じ Descriptor が、片方で Uniform、もう片方で Collection取り込む側の定義を採ることでだけ解決できる
C2b警告Collection の Sub-Circuits が Canon より多い（分解が増える）確認して了承する
C2cエラーCollection の分け方が違う取り込む側の定義を採ることでだけ解決できる
C3エラーUniform の回路の隣に、同じアンカーで facet をすべて含み、さらに多く持つ（より細かい）回路がある。side も facet として数えるブロック（プロジェクト側で直す）
C4エラーCircuit ID と Descriptor が 1 対 1 でない（同じ Descriptor に別の ID、同じ ID に別の Descriptor。古い ID は現在の形で比べる）ブロック
C5エラー接続の端が Canon で Collection になっているブロック
C6エラー正式名（名前の並びの先頭）が違うブロック
C7警告伝達物質・修飾・Source of ID が違うどちらの値にするか選ぶ
C8エラー同じ Reference ID が別の DOI / PMID を指すブロック
C8b警告同じ論文が別の Reference ID で入っている確認して了承する
C8cエラー文献が照合に失敗しているブロック
C9b警告同じ接続が別の書き方になっているどちらの値にするか選ぶ
C9cエラー引用文が照合に失敗しているブロック
C12警告グループ（Descriptor のない Collection）の構成が違うどちらの値にするか選ぶ
C13情報Output Semantics が違うどちらの値にするか選べる（承認は止めない）
  • エラーは承認を止めます。ただし C1 と C2c は、取り込む側の定義を採れば解決できます。そのとき、Collection に変わった回路で終わる接続は要注意の状態になり、変わった回路を使うプロジェクトが影響として一覧されます。
  • 警告（要確認の項目）があると、それぞれを決めるまで承認できません。C7・C9b・C12 は「Canon の値のまま」か「取り込む側の値」かを選び、C2b・C8b は確認して了承します。情報（C13）は承認を止めません。
  • 自律実行のオーケストレーターは、エラーの衝突を取り込む側の定義で解決することはしません。エラーの衝突がある PR は承認せず、プロジェクトを Canon に合わせるフォローアップにします。選ばなかった警告は「Canon の値のまま」とします（6.8）。
  • これらのコードは CoBRAC の Canon に独自の体系で、BRA のエラーコード（Master）とは別のものです。

典拠：packages/shared/src/canonMerge.ts（diffCanon・blockingConflicts）、packages/shared/src/canonAiDecision.ts（decisionAction）

5.8 審査

PR の画面は、審査のための画面です。システムの検査と AI レビューが審査を補助し、承認・変更の依頼・却下は人（所有者か共同編集者）が行います。自律実行の計画の PR では、オーケストレーターがこの判断を代わりに行います（6.8）。承認を止めるかどうかは、どちらの場合も衝突ルール（5.7）が決めます。

審査の材料

PR の画面を開くと、API がそのたびに次の材料を計算して返します。材料は保存しません。

  • 差分と、その基準になった rev
  • システムの検査（下の表）
  • 差分の各項目の、両側の値
  • 図。PR が持ち込む回路、その接続が終わる Canon の回路、変わるものの Canon での隣の回路と、それらの間の Canon の接続を描きます。回路は最大 60 個です。
  • 来歴。送り元、その現在の rev、送り元がまだあるか、Canon の最新の rev を示します。
  • 履歴と、審査する人には最新の AI レビュー

PR の画面のタブ

タブ内容
「変更」いまの Canon と承認後の Canon を、同じ配置で並べた図（追加は緑、変更は青、プロジェクトで使わなくなったものは灰色の破線、衝突は赤い枠、Collection は点線）。種類ごとの差分の一覧（絞り込み付き）。行を開くと両側の値を項目ごとに比べられ、その行への検査とコメントも見られる。
「検査」決める必要のある衝突と、グループごとのシステムの検査（承認は止めない）。各検査には、重さと、BRA の Error code List (Master) のコードか cobrac: のコードが付く（下の表）。
「AI レビュー」モデル（使えるものだけ）と言語を選んで実行する。LLM が食い違いを、理由と、項目・文献へのリンク付きで挙げ、確認すべき点とコメント案を出す。判断はしない。「使う」を押すとコメント案がコメント欄に入るので、直してから送る。
「履歴」push、置き換え、判定のし直し、コメント、変更の依頼、承認（rev と衝突の選択）、却下、取り下げ、AI レビューの依頼を、だれがいつ行ったかの追記専用の記録。

判断の欄は、広い画面では右の列、スマートフォンでは下のバーに出ます。メモの欄と、「変更を依頼」「却下」（どちらもメモが必要）、「承認」（メモは任意）のボタンがあります。決めていない衝突がある間は「承認」を押せません。

変更の依頼・コメント・履歴

  • 変更の依頼：PR は開いたまま、変更を依頼された状態とそのメモを持ちます。送った側が新しく push すると、新しい PR が古い PR を置き換えます。
  • コメント：所有者、共同編集者、PR を送った人が書けます。PR 全体か、差分の 1 項目に付けられます。
  • 履歴：push、置き換え、判定のし直し（承認のときに新しい最新の rev に対して判定し直したこと）、コメント、変更の依頼、承認（rev と衝突の選択付き）、却下、取り下げ、AI レビューの依頼を、追記専用で残します。AI レビューが終わったことは、そのジョブの記録から読みます。

AI レビューのジョブ

AI レビューは、LLM のジョブが所見だけを出すものです。次の順に進みます。

  1. 依頼：審査する人（所有者か共同編集者）が、開いている PR について、モデルと言語を選んで依頼します。1 つの PR で同時に動くのは 1 件だけです。モデルは、依頼した人の API キーと利用承認で使えるかを検査します（デフォルトの API キーの Tier 1 では、許されたモデルだけ。4.1）。ワーカーでも同じ検査をします。
  2. 材料：API が、差分、衝突、検査、変わった項目の両側の値、文献を、最大 15 万文字にまとめます。それを S3 に書き、ジョブを積みます。
  3. 実行：ワーカーが LLM を 1 ターン動かします。Web 検索は使わず、コマンドもファイルも使わずに材料だけを読ませます。出力は固定のスキーマで返させます。スキーマは、要約、指摘（重さ・理由・項目・検査・Reference ID 付き）、確認すべき点、項目ごとのコメント案です。その形でなければ、1 回だけ頼み直します。
  4. 検査：ワーカーは、材料にない項目・検査・論文を指す部分を除き、件数を数えます。結果は S3 に保存し、使用量と費用はジョブに記録します。使用量は依頼した人の使用量に入り、デフォルトの API キーを使ったときはそのキーの使用量にも入ります。

出力に判定の欄はなく、指示書は承認や却下を勧めることを禁じています。ジョブの割り当てと回復の処理（8.3）は、このジョブについてプロジェクトの状態を変えません。止まったレビューのジョブはリトライせず、もう一度実行するよう促すメッセージを付けて失敗にします。

判断のジョブ

自律実行の計画が push した PR には、オーケストレーターが所有者として、AI レビューと同じ材料で判断のジョブを依頼します。判断のジョブは、所見に加えて、承認・変更の依頼・却下の判定とその理由、警告と情報の衝突ごとの選択、依頼する変更を返します。判定をどう反映するかは最後にプログラムが決め、エラーの衝突がある PR は AI がどう判定しても取り込みません。詳しくは 6.8 で説明します。PR の画面の「AI レビュー」には「AI の判断」（判定、理由、依頼した変更）が出ます。人が依頼する AI レビューは、判定を出しません。

共同編集者

  • 所有者は、Canon の画面で、相手が登録に使ったメールアドレスを入れて、既存のユーザーを共同編集者に追加します。大文字と小文字は区別しません。招待メールはありません。登録されていないアドレスは見つからない扱い（404）になり、先にサインアップしてもらうよう求めます。
  • 共同編集者は所有者が外せるほか、自分で抜けることもできます。共同編集者の一覧は、所有者にはメールアドレス付きで、共同編集者には名前だけで見えます。
  • 共同編集者は、Canon の一覧の「共有された Canon」から Canon を開きます。
だれできること
共同編集者Canon、参加プロジェクト（名前と ROI / TLF だけ。所有者のプロジェクトへのリンクはない）、rev、PR の閲覧。コメント。AI レビュー（自分の API キーかデフォルトの API キーで、自分が使えるモデルで。ジョブと費用は本人のもの）。変更の依頼・承認・却下。自分の Canon からの PR の送信（相手が非公開でも、PR を受け付けない設定でも）

管理者閲覧だけ

判断の記録

  • 承認は 1 人で足ります。PR は承認の一覧を持ち、将来は Canon ごとに必要な承認の数を設定できる構造です。いまは設定も表示もできず、1 として扱います。
  • PR には、承認・却下・取り下げをした人と時刻、変更を依頼した人と時刻を記録します。rev には承認者と時刻を記録します。
  • PR の画面には「… が承認 → rev n」「… が却下」「… が変更を依頼」の帯が、メモと時刻付きで出ます。履歴には操作ごとの人が、Canon の rev の一覧には承認者が出ます。
  • オーケストレーターによる判断（自律実行の計画の PR だけ）：承認・却下・変更の依頼は、Canon の所有者のアカウントで行います。記録上の判断者は所有者で、表示名は「AI (<モデル>)」です。判断したジョブとモデルを、PR、承認、履歴、rev のそれぞれに残します。

実装

  • 審査の材料は GET /canons/{id}/pulls/{no} が返します。項目は checks・entries・graph・provenance です。興奮性と抑制性の判定は classifyEdgeSign です。
  • 変更の依頼は POST …/pulls/{no}/request-changes { note } で、PR に reviewState = changes_requested と reviewNote を書きます。コメントは POST …/pulls/{no}/comments { text, item? } で、項目は <種類>:<キー> で指します。
  • 履歴は Canons テーブルの追記専用の項目 PEV#{prNo}#{at}#{nonce} で、種類は pushed・superseded・rebased・comment・changes_requested・approved・rejected・withdrawn・ai_requested です。
  • AI レビューの依頼は POST …/pulls/{no}/ai-review { model?, locale } です。モデルの検査は API が requireModel、ワーカーが planRunKey で行います。材料は buildCanonAiPacket が作り、canons/{id}/pr/{no}/ai/{jobId}/input.json に書きます。ジョブは type とモードが canon-review、projectId が Canon ID で、reviewPrNo・reviewLocale を持ちます。結果の検査は parseCanonAiReview、保存先は result.json です。
  • 判断のジョブは同じジョブを reviewKind: "decide"・planId 付きで積みます。指示書は canonAiDecisionPrompt、スキーマは CANON_AI_DECISION_SCHEMA、検査は parseCanonAiDecision、反映の規則は decisionAction です（6.8）。
  • 共同編集者の追加は POST /canons/{id}/editors { email }、削除は DELETE /canons/{id}/editors/{userId} です。Canons テーブルの EDITOR#{userId} の項目で表し、本人のユーザーの editorCanons に並びます。
  • 判断の記録は、PR の approvals（{ userId, name, at }）、decidedBy / decidedByName / decidedAt、reviewedBy / reviewedByName / reviewedAt、rev（REV#）の approvedBy / approvedByName / approvedAt です。必要な承認の数は将来の requiredApprovals（未設定 = 1）です。
  • オーケストレーターによる判断では、表示名を aiActorName が作り、via = { kind: "ai", jobId, model } を PR の decidedVia、承認の approvals[].via、履歴の via: "ai"、rev の approvedVia に残します。承認・却下・変更の依頼は、人と同じ関数（approvePullRequest・rejectPullRequest・requestPrChanges）を所有者として呼びます。

5.9 rev への追従

プロジェクトのヘッダーには、所属する Canon と、従っている rev が出ます（例「rev 1（最新 2）」）。API は、固定した rev と最新の rev を、そのプロジェクトが使う定義について比べ、次のどれかの状態を返します。

状態意味利用者の操作
最新最新の rev に固定されている—
新しい rev ありCanon は進んだが、このプロジェクトが使う定義は変わっていない「最新の rev にする」で固定を進める。次の実行から従う
影響する変更あり使っている回路が Collection / Uniform に変わった、Sub-Circuits や ID が変わった、使っている接続の端が Collection になった。変更の一覧と、フォローアップの文が付く「Canon に合わせる」で固定を進め、プロジェクトを直すフォローアップを送る

実装

状態は GET /projects/{id}/canon が current / behind / affected で返します。「最新の rev にする」は POST /projects/{id}/canon/pull です。

5.10 Canon の作り方

  • 空の Canon を作る：サイドバーの「Canon」で「新しい Canon」を作り、名前と粒度方針を書きます。既存のプロジェクトは「プロジェクトを追加」で入れられます。
  • プロジェクトの作成画面で選ぶ：入力欄の下の「Canon」ボタンを押すと、一覧のポップオーバーが開きます（数が多ければ検索できます）。選べるのは次の 3 つです。
    • 「なし」
    • 「既存の Canon」：最初の実行から最新の rev に従います。選んだ Canon は、ボタンに名前と rev が出ます。
    • 「既存のプロジェクトから新しく作る」：入力欄の下に設定の欄が開きます（下の手順）。
  • 既定の Canon：設定画面で既定の Canon を決めておくと、一覧で「既定」が付き、指定しなければそれが使われます。既定がなければ「なし」です。
  • API はプロジェクトを作る前に Canon の指定を検査します。プロジェクトは最初のジョブを積む前に Canon に入るので、最初の実行から Canon に従います。

既存のプロジェクトを種にして作る

  1. 名前と粒度方針を書き、種にするプロジェクトを優先する順に選びます。選べるのは、どの Canon にも入っていない、完了済みの自分のプロジェクト（複製も可）です。上が優先で、番号が付き、矢印で並べ替えられます。プレビューに rev 1 の中身が出ます。
  2. 最初の種が rev 1 の土台になり、以降の種は衝突ルールで順に合わせます。種どうしでは、C1 / C2c を先の種の定義を残して解決することもできます。そのとき、後の種には更新が必要という印が付き、その Collection への接続は要注意の状態になります。
  3. 衝突を決めきれない種は、rev 1 に対する未処理の PR にする（既定）か、外します。画面には「残りを優先順で決める」「残りを PR にして保留する」があります。
  4. プロジェクトの作成が、種の承認を兼ねます。rev 1 は PR なしで書かれ、外さなかった種と新しいプロジェクトが、rev 1 に固定された参加プロジェクトになります。

実装

POST /projects は canon として { mode: "none" } / { mode: "existing", canonId } / { mode: "new", name, policy, seeds, choices, actions } を受け取ります。既定の Canon は Users.defaultCanonId です。種のプレビューは POST /canons/seed-preview で、合成は composeSeeds です。種から書いた rev 1 は source: "seed" を持ちます。

5.11 Canon の公開・複製と Canon から Canon への PR

プロジェクトの公開と複製の規則は 4.6 で説明します。この節では Canon に関わる部分を説明します。

公開

  • Canon は非公開（既定）か公開で、切り替えられるのは所有者だけです。いつでも非公開に戻せます。
  • 公開した Canon は、公開ライブラリで、ログインしただれでも一覧・閲覧できます。出るのは、粒度方針、rev、参加プロジェクトの数、公開された参加プロジェクトです。Canon ID もここに出ます。チャットの履歴、費用、メールアドレスは出ません。
  • 公開した Canon は、所有者が止めない限り、ほかのユーザーの Canon からの PR を受け付けます。承認するのは、いつも所有者と共同編集者です。
  • 公開したものは公開の一覧の行を持ち、非公開にするか削除するとその行を消します。一覧と閲覧のたびに、Canon そのものの状態を確認し直します。

複製

公開した Canon を複製する機能はありません。複製できるのは公開プロジェクトです（4.6）。

Canon から Canon への PR

  • Canon の所有者は、Canon の画面の「別の Canon に PR を送る」から、自分の Canon の最新の rev を、別の Canon に PR として送れます。先に差分を見ることもできます。送り元は自分が所有する Canon です。空（rev 0）なら送れず（409）、同じ Canon には送れません。
  • 送り先にできるのは、自分の Canon、自分が共同編集者の Canon、PR を受け付けているほかのユーザーの公開 Canon です。ほかのユーザーの非公開の Canon は見つからない扱い（404）、PR を止めた公開 Canon は拒否（403）です。
  • PR の中身は、送り元のスナップショットそのものです。エントリは元のプロジェクトの来歴を保ち、経由した送り元の Canon と rev を記録します。役割層には、送り元のすべての参加プロジェクトが入ります。受け取った側は、プロジェクトからの push と同じ衝突ルール、選択、承認で審査します。
  • 送り元の Canon には、送ったことの記録だけを書きます。送った PR とその状態は一覧できます。送った人は PR を開いて取り下げられますが、審査はできません。同じ Canon から同じ送り先への未処理の PR は、新しい PR が置き換えます。

実装

公開の切り替えは PUT /canons/{id}/visibility、公開ライブラリは /explore、公開の一覧は Catalog テーブル（kind = canon）、PR の受け付けは acceptPullRequests です。Canon から Canon への PR は POST /canons/{target}/pulls { sourceCanonId }、差分の確認は …/pulls/preview です。ペイロードは canonFromCanon が作り、via = <送り元>@<rev> を記録します。送り元の記録は OUT#{target}#{no}、一覧は GET /canons/{id}/outgoing です。

典拠：packages/api/src/app.ts（公開・Canon から Canon へのルート）、packages/shared/src/publish.ts・canonMerge.ts

5.12 オーケストレーターとの関係

オーケストレーター（第 6 部）の計画は、1 つの計画につき 1 つの Canon を使います。自律実行の計画で Canon を指定しなければ、計画の名前で新しい Canon を作ります。計画の完成した行は自動で Canon に push されます（6.7）。

自律実行の計画では、push したすべての PR に判断のジョブを依頼し、その判定を所有者の代わりに反映します。エラーの衝突がある PR や、変更を依頼した PR は、プロジェクトを直すフォローアップに回します。フォローアップは 1 行につき 3 回までです（6.8）。人が対応する計画では、オーケストレーターは push と AI レビューの依頼までを行い、承認は人が行います。Canon が進んだときの更新は 1 行につき 2 回までです（6.9）。

どちらの計画でも、PR の承認は 5.6〜5.8 と同じ処理と検査を通ります。人は自律実行の計画の PR を Canon の画面で直接判断することもでき、その場合はオーケストレーターが次の処理でその結果に従います。

コードの場所：型 packages/shared/src/canon.ts ／ 変換・差分・衝突・合成 canonMerge.ts ／ 生成時の検査 canonConstraints.ts ／ 審査の材料 canonReview.ts・canonAiReview.ts ／ 判断の規則 canonAiDecision.ts ／ API packages/api/src/lib/canons.ts・canonOps.ts・canonReview.ts・planRunner.ts ／ AI レビューのジョブ packages/worker/src/canonReview.ts
