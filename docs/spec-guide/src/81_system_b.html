索引と Streams

  • Jobs の status-index（status + createdAt）：dispatcher と janitor が、状態ごとにジョブを探します。
  • WsConnections の project-index（projectId）：broadcaster が送り先を探します。
  • Users の userKey-index（キーだけ）：userKey を発行するときの重複の検査と、userKey から利用者を検索するのに使います。ランダムな ID の所有者は、プロジェクトの userId か、Catalog の id の行の ownerUserId で分かります。
  • Canons の owner-index（ownerUserId + createdAt）：所有者の Canon の一覧を作ります。META の項目だけがキーを持つ疎な索引です。
  • Plans の owner-index（ownerUserId + createdAt）と status-index（status + createdAt）：所有者の計画の一覧と、計画ランナーが進める下書き中・実行中・一時停止中の計画を探します。どちらも META だけの疎な索引です。
  • Streams：Projects と Messages の NEW_IMAGE を broadcaster に渡します。

メッセージの役割

role が user のメッセージは、利用者が入力した文だけです。API が meta.kind を create / answer / followup にして保存します。ワーカーがジョブの初めにエージェントに送る依頼文は、system / status のお知らせとして保存します（meta.harnessPrompt、本文は meta.details）。エージェント欄には「HCD フェーズを開始しました。」のように表示し、開くと全文が出ます。古い形式で保存した依頼文の表示は付録 C で説明します。

所有の確認

一般の利用者に見えるのは、自分の userId の下の項目だけです。Project ID は全体で一意ですが、古い形式の ID（利用者ごとの slug。付録 C）は 2 人の利用者が同じ値を持つことがあります。一方、Jobs・Messages・project-index は projectId だけをキーにしています。そのため、読み出しはすべて所有者で絞ります。

  • ジョブは userId で絞ります。
  • メッセージは userId で絞ります。userId を持たない古いメッセージは、そのジョブの所有者で絞ります。
  • WebSocket の配信は、所有者の接続にだけ送ります。

8.6 S3 の成果物

バケットの設定

成果物のバケット（Artifacts）の設定は次のとおりです。

  • 公開を全面的に止め（Block Public Access）、SSE-S3 で暗号化し、SSL を強制します（enforceSSL）。バージョニングは使わず、削除方針は RETAIN です。
  • バケットポリシーで、users/*/*/revisions/*（BRA の版）の削除をすべての主体に禁じます。
  • 未完了のマルチパートアップロードは 3 日で中止し、staging/ は 1 日で消します。
  • ブラウザからのアップロードのため、CloudFront のドメイン、https://cobrac.site、http://localhost:5173 からの POST だけを CORS で許可します。

ワーカーは S3 と差分で同期し、MD5 が同じファイルは送りません。グラフ JSON は、LLM を使わない buildGraphs() が CSV から作ります。

8.7 フロントエンド

基本

  • Vite + React 18 + React Router + Tailwind で作ります。認証は Amplify（Cognito の SRP）、Markdown の表示は react-markdown と GFM です。
  • 実行時の設定は、CloudFront が配る /config.json（apiUrl、wsUrl、userPoolId、userPoolClientId、region、appName）です。CDK が書くので、環境ごとにビルドし直さずに済みます。ローカルの開発では VITE_* を使います。
  • ルートの package.json の version を __APP_VERSION__ として、git rev-parse --short HEAD を __APP_COMMIT__ として、Vite の define で埋め込みます（8.9）。
  • WebSocket は、ID トークンをクエリに付けて接続し、プロジェクトを購読します。5 分ごとに ping を送り、切れたら待ち時間を倍にしながら（30 秒まで）つなぎ直します。API Gateway の WebSocket は 2 時間で切れるので、ポーリングも併用します（4.4）。
  • エージェント欄の Markdown（GFM）では、コマンド・思考・Web 検索を折りたたみます。

グラフの表示と編集

グラフは @xyflow/react と dagre で描きます。HCD は上から下へ、FRG は左から右へ配置します。主な機能は次のとおりです。

機能内容
色分けHCD はノードを ROI の区分（塗りと縞）で色分けし、エッジの既定のスタイルを投射の生理（興奮性・抑制性・修飾性）で決める。FRG は種類で色分けする。縮小するとラベルを大きくし、自己接続はループで描く
エッジの生理の既定抑制性は青（#2563eb）と四角の終点、興奮性は灰色と三角、修飾性は紫の破線と円。分類は Connection のコメントを優先し、なければ送り手の Transmitter / Modulation Type を使う（classifyEdgeSign）。同じ分類のすべてのエッジに同じスタイルを当てられる
閲覧ノードを選ぶと、隣接するもの（HCD）か祖先と子孫（FRG）以外を薄くする。キャンバスの外からの選択（URL、検索、詳細のリンク）では、詳細のシートの上に来るように表示を寄せる。検索欄は ID・名前・UC Descriptor でノードを順位付けする（↑ ↓ Enter、/ でフォーカス）
ツールバー検索、全体表示、元に戻す / やり直す、スタイル編集モード、メニュー（配置の向き、グリッドに合わせる、ページの設定（エッジのラベル、すべて開く / 閉じる）、PNG の書き出し、リセット）
スタイル編集モードスタイルのパネル、大きさの取っ手、接続の取っ手は、このモードでだけ出る。タッチ機器では、このモードでだけノードをドラッグできる
ノードの編集ドラッグで移動、角と辺で大きさの変更、スタイルのパネルで塗りと枠の色の変更
エッジの編集線の種類（曲線、直線、自動の直交、経由点を編集できる直交、折れ線）、色、太さ、破線、角の丸み、始点と終点の印（矢印、開いた矢印、四角、円、ひし形、棒）を変える。直交のエッジは、経路上の「+」で経由点を足し、ドラッグで曲げ、ダブルクリックで消す。選んだエッジの両端を、ノードの辺の取っ手（1 辺に 7 点）に付け替えられる。既定の線の種類は曲線
平行なエッジ同じ 2 つのノードを結ぶエッジ（帰還ループの A→B と B→A、または複数の A→B）は、20 単位ずつ離れた別のレーンに描く（lib/parallelEdges.ts）。どのエッジも自分の進む向きの右側に置き、ラベルは各レーンの外側に置く。レーンは描くたびに計算し、保存しない。利用者が経由点を描いたエッジは、自分の経路を保つ。同じノードの自己ループは外側に重ねる
配置の保存useGraphLayout が、位置・大きさ・色・エッジのスタイル（経由点と接続点を含む）を 600 ミリ秒まとめてから PUT …/layout で保存する。グラフを作り直しても、同じノード ID・エッジ ID の設定は残る。Ctrl+Z / Ctrl+Y で元に戻す / やり直す

純粋な補助関数は packages/web/src/lib/graphView.ts にあり、vitest でテストします。以前の既定（直交）で保存した配置の扱いは付録 C で説明します。

テーマ

  • ライトとダークがあり、既定は prefers-color-scheme に従います。サイドバーとログインのカードに「システム / ライト / ダーク」の切り替えがあり、ブラウザごとに保存します（localStorage の cobrac-theme）。index.html のインラインのスクリプトが、最初の描画の前にテーマを当てます。
  • Tailwind の色は CSS 変数を指し、背景・文字・枠に別の組を持ちます（packages/web/theme-palette.js）。そのため bg-white はダークでは暗い面になり、塗ったボタンの text-white は白のままです。サイドバーはどちらのテーマでも暗い色です（theme-static）。
  • グラフの塗りと線の色はライトの値で保存し、描くときに変換します（lib/graphTheme.ts）。ダークでは、塗りを同じ色相の暗い色にしてラベルを明るくし、線を明るくします。スタイルのパネルの見本は、描いた色を示します。
  • test/theme.test.tsx が、画面で使う文字と面の組、既定の塗りと見本の上のノードのラベル、キャンバスの上のエッジのコントラストを検査します。

バージョン番号

  • バージョンの正本は、ルートの package.json の version だけです。ビルド時に Vite が埋め込み、サイドバーの下に vX.Y.Z · <git の短い SHA> と表示します。CDK は同じ値を Lambda の APP_VERSION に渡し、GET /health がそれを返します。ワーカーにも同じ値と git の commit を渡し、凍結する版の生成条件に記録します（4.5）。
  • Semantic Versioning に従います。0.x の間の目安は次のとおりです。
    • patch：バグの修正、文言・表示の調整、文書、単価表の更新
    • minor：画面や API の追加、データモデルの追加、ワークフロー・プロンプトの変更
    • major：既存のデータと互換性がなくなる変更（テーブルの構造、成果物の形式）
  • バージョンを手で編集しません。必ず release.mjs を通します（workspace の package.json は自動でそろいます）。[Unreleased] が空のまま release すると失敗するので、CHANGELOG を書かずにバージョンを上げることはできません。
  • デプロイされるのは、バージョンを上げた PR を main にマージしたときだけです。このマージがデプロイの承認になります。バージョンを上げないマージ（文書だけの変更など）はデプロイされず、次のリリースにまとめて入ります。

変更するときの約束

  • 型検査（npm run typecheck）とテスト（npm test）を通してからコミットします。packages/shared の型を変えたら、api・worker・web をすべてビルドして影響を確認します。
  • インフラ（packages/infra）を変えたら、npm run cdk -- diff で差分を確認します。RETAIN のリソース（DynamoDB・S3・KMS・Cognito、BRA-DB のインスタンスとボリューム）を置き換える変更は、必ず人が確認します。デプロイの前には RETAIN ガードがこの種の変更を検出して止めます。
  • ワークフローの骨格は、相談せずに変えません。骨格とは、HCD → FRG → CSV → xlsx の順序、ワーカーが段階を進めて検査する方式、ターンの終わりの JSON {status, message, question} です。段階の指示書の文言の調整はかまいません。
  • エージェントが書く JSON のキーを変えるときは、JSON Schema（HARNESS_SCHEMAS）、検査、CSV への変換、段階の指示書の例を同時に直します。
  • 画面の文言は、10 の言語（ja・en・de・es・fr・ko・pt・ru・zh・zhTw）すべてに足します。
  • 文書の図は生成スクリプト（npm run docs:figures）で書き出し、手で編集しません。npm test が、生成結果とコミット済みのファイルの一致を検査します。プロンプトを変えたら npm run docs:prompts で文書の原文を更新し、docs:prompts:check で検査します。
  • 挙動を変えたら、関係する文書を同じ変更の中で直します。
  • 秘密情報（API キー、.env、トークン）はコミットしません。追跡するのは .env.example だけです。

ローカルでの開発と確認

  • 必要なものは Node.js 22 以上と npm 10 以上です。Docker は要りません。AWS の認証情報は緊急デプロイのときだけ要ります。
  • 通常の確認の流れは次のとおりです。
    1. npm install
    2. npm run build（shared の tsc → api の型検査・worker の tsc・web の Vite）
    3. npm run typecheck（shared のビルド結果が要る）
    4. npm test（shared の単体テストと scripts/*.test.mjs）
    5. npm run cdk -- synth（デプロイ前の確認）
  • csv_to_excel.py だけを試すときは、pip install -r prompts/requirements.txt の後に python prompts/csv_to_excel.py --contributor … --project-id … --base-dir … --output ….bra.xlsx を実行します。
  • 画面だけをローカルで動かすときは、.env.example を packages/web/.env.local にコピーし、VITE_API_URL などをデプロイ済みの環境に向けて、npm run dev:web を実行します。成果物バケットの CORS は、http://localhost:5173 からのアップロードを許しています（8.6）。
  • デプロイの後は、WebUrl を開いてサインアップし、設定画面で API キーを登録し、ROI と TLF を入れて実行すれば、動作を確認できます。
