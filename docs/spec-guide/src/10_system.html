第 1 部

システムの全体像

CoBRAC Agents は、BRA（Brain Reference Architecture）のデータ作成をブラウザから依頼し、サーバーで実行する Web アプリです。この部では、何を入れて何が出てくるか、どの部品が何をするか、だれが何をできるか、画面・ジョブ・データがどう組み立てられているかを、実装に沿って説明します。1 件の BRA の中身の作り方（ハーネス）は第 2 部、回路の命名・Canon・BRA-DB・オーケストレーター・AWS の運用は第 3〜7 部で扱います。

人利用者はプロジェクトを作り、質問に答え、成果物を受け取る。管理者は利用者・デフォルトの API キー・同時実行数を管理する
プログラムAPI・dispatcher・broadcaster・janitor・計画ランナーの Lambda と、Fargate 上のワーカー。どれも LLM を含まない
LLMBRA を作る CoBRAC エージェント（Codex で動かす OpenAI のモデル）と、解説記事・AI レビュー・計画の各ジョブ

1.1 目的と範囲

BRA のデータは、脳のある領域の神経回路と、その回路が実現する機能を、文献の根拠付きで表した表とグラフです。以前は同じ作業を、デスクトップで Cursor のエージェントに行わせていました（旧デスクトップ版。指示書・仕様書・成果物の見本はリポジトリの archive/v0/ に参照用として残っており、アプリでは使いません）。CoBRAC Agents では、AWS 上のワーカーが Codex SDK を通じて OpenAI のモデルを動かし、利用者はブラウザで進み具合を見て、質問に答え、成果物を受け取ります。作業はサーバーで進むので、ブラウザを閉じても止まりません。

入力

  • ROI（Region of Interest、対象の脳領域）と TLF（Top-Level Function、その領域が担う機能）。どちらか一方だけでも作れます。足りない側はエージェントが調べて補います。
  • 任意で、参考資料（ファイルと URL、1.12）、Canon（第 4 部）、モデル・推論の強さ（1.8）、調査モード（2.9）、仮説モード（2.13）を指定できます。

1.3 構成の全体像

CoBRAC Agents は 1 つの CDK スタック（CobracAgents）にまとまった AWS のサーバーレス構成です。BRA-DB だけは別のスタックにあります（第 5 部）。図 1.1 は主な部品と、プロジェクトを作ってから進み具合が画面に届くまでの流れを示します。

プロジェクトを作ってから画面に届くまで

  1. 利用者がブラウザでプロジェクトを作ると、SPA が Cognito の ID トークンを付けて HTTP API（POST /projects）を呼びます。API Gateway がトークンを検証し、API の Lambda（プログラム）がプロジェクトとジョブを DynamoDB に QUEUED で書き、SQS にジョブのメッセージを積みます。
  2. dispatcher（Lambda）が SQS からメッセージを受け、同時実行数に空きがあれば ECS の RunTask で Fargate のタスクを 1 つ起動します。空きが無ければ 60 秒後に積み直します。
  3. ワーカー（Fargate 上のプログラム）が KMS で API キーを復号し、Codex CLI を子プロセスとして起動して、CoBRAC エージェント（LLM）にターンを依頼します。エージェントは OpenAI API のモデルとして考え、Web 検索や MCP の道具で文献と SABRA を調べ、作業フォルダに JSON を書きます。
  4. ワーカーはターンごとにファイルを検証し、状態とメッセージを DynamoDB に、作業領域と成果物を S3 に書きます。
  5. DynamoDB Streams が Projects と Messages の変更を broadcaster（Lambda）に渡し、broadcaster が WebSocket API を通じて、そのプロジェクトを購読している所有者のブラウザに送ります。
  6. これとは別に、janitor（5 分ごと）が止まったジョブを再試行か失敗にし、計画ランナー（毎分）がオーケストレーターの計画を進めます。

LLM が動く場所

システムの中で LLM が動くのは、ワーカーが Codex を通じて実行するジョブだけです。API・dispatcher・broadcaster・janitor・計画ランナーの Lambda はどれも LLM を呼びません。LLM のジョブは次の 4 種類で、それぞれ別の会話（スレッド）です。互いの会話を共有することはありません。

項目仕様
保存管理画面で、どの管理者も登録・置き換え・削除できる。どの利用者にも属さない。Catalog テーブル（kind: "config"、id: "default-api-key"）に KMS の暗号文として、専用の暗号化コンテキスト { purpose: "openai-api-key", scope: "default" } で保存する。このコンテキストには userId が無いので、個人のキーのコンテキスト（{ userId, purpose: "openai-api-key" }）では開けず、逆も開けない。登録時に個人のキーと同じく OpenAI の /v1/models で確かめ、Tier 2 用にモデルの一覧を保存する。書き込み専用で、API は { registered, last4, updatedAt } しか返さない。個人のキーをここに写すことはない
承認と TierUsers.orgAccess = { tier, approvedAt, approvedBy }（管理画面で設定。無い・null は未承認）。既存の利用者も新しい利用者も未承認から始まる。Tier 1 は gpt-6-luna と gpt-5.6-luna だけ（正確なモデル ID。ORG_TIER1_MODELS）、Tier 2 はすべてのモデル
優先順位利用者自身のキーが常に優先され、Tier の制限を受けない（Tier はデフォルトの API キーで実行するジョブにだけかかる）。承認済みの利用者が後で自分のキーを登録すると自分のキーで実行し、削除するとデフォルトの API キーに戻る。管理者の個人のキーは、その管理者自身のジョブにだけ使う
API での確認ジョブを始めるすべての依頼（作成・フォローアップ・リトライ・回答・解説記事。記事に選んだモデルを含む）で、API がキーとモデルを決める。実行に使えるキーが無い（自分のキーも、承認と登録済みのデフォルトの API キーの組もない）と 400、利用者が明示的に選んだモデルが Tier に無いと 403「このモデル（<model>）は利用できません」。利用者がこのジョブに選んでいないモデル（保存した既定のモデル、デプロイの既定、複製に与える既定、以前に自分のキーや別の Tier で作ったプロジェクトのモデル）は、失敗させずに Tier の既定（gpt-6-luna）に置き換える。そうしたプロジェクトにフォローアップ・リトライ・回答を送ると、プロジェクトのモデルを以後も Tier の既定に移し、いつもの「Model: …」のお知らせを出す。モデルを選ばない解説記事は Tier の既定で実行し、プロジェクトのモデルは変えない。Tier に無い既定のモデルは保存できない。/users/me/models は Tier のモデルだけを返し（restricted: true、任意のモデル ID は不可）、モデルの選択欄（作成・設定の既定・記事）はそれだけを出す。Tier の外の保存済みの既定は「デフォルト」と表示し、プロジェクトのヘッダーは次のジョブで使うモデルを示す
言葉づかい管理者以外には「Tier」という言葉も番号も見せない。設定画面の状態、モデル欄の注記、ツールチップ、API のエラー、ワーカーのお知らせは「デフォルトの API キー」「このモデルは利用できません」とだけ言う。Tier が出るのは管理画面だけ
取り消しワーカーは起動のたび（新しいジョブ、回答、リトライ、中断後の再開）にもう一度確かめる。承認が無い、デフォルトの API キーが無い、Tier が許さないモデル、のどれかならジョブを失敗にしてお知らせを出す（sys.noApiKey・sys.orgKeyUnavailable・sys.orgKeyModel）。実行中のターンは止めない。ワーカーが読めるのは Catalog の config パーティションだけ（dynamodb:LeadingKeys の条件付きの GetItem）
利用額ジョブは keySource（own / org。org がデフォルトの API キー）を記録する。GET /admin/org-usage は keySource: "org" のジョブを利用者ごとに合計し（トークン、推定費用、UTC の今月の費用、単価の無いジョブの数）、管理画面が各利用者の横に出す。アプリに支出の上限は無いので、デフォルトの API キーの OpenAI プロジェクトに予算を設定する
漏れキーは API から返さず、ログに出さず、エージェントのコマンドに渡さない（shell_environment_policy が CODEX_API_KEY・OPENAI_API_KEY を除く）。エージェントは自分の Fargate タスクの中で Codex のプロセスと同じ OS ユーザーとして何でもできるが、node・Codex・git の実行ファイルは実行専用にしてあり、そのプロセスはダンプできないので、/proc/<pid>/environ からキーを読めない（第 7 部）。それでもエージェントは自分のジョブにはキーを使うので、信頼できる共同作業者だけを承認し、予算を設定したプロジェクトのキーを使う

エージェント欄

右の欄の名前は「チャット」ではなく「エージェント」です。開かれた会話ではなく、エージェントの実行そのものであり、利用者は質問への回答と追加の指示でそれを導くからです。

  • ログはコーディングエージェントのように読めます。エージェントの返答は吹き出しもアイコンも無い全幅の Markdown、利用者の依頼は「依頼」「回答」「追加の指示」のラベルの付いた控えめな灰色の区画（meta.kind）、お知らせ（待機、モデル、段階の完了、ファイルの用意、利用量、エラー）はアイコンと時刻の付いた 1 行です（時刻に触れると日付まで出る）。完了した段階とファイルは緑、エラーは赤で、詳細があれば開けます。
  • 2 つの見える返答の間の思考とツールの呼び出しは、1 行の活動の行（「思考・実行ログ」）にまとまり、ステップの数・経過時間・TODO の進み（例「8 ステップ · 2 分 18 秒 · TODO 2/5」）を出します。開くとステップの一覧が出て、各ステップは全文まで開けます。実行中のコマンドはスピナー、失敗したコマンド（終了コードが 0 でない）は赤です。エージェントが作業している間、最後の行は動いており、スピナー、光る「作業中」の文字、経過時間、最新のステップ（届くたびに滑り込む）を出します。
  • 実行が待っている質問は、ログの最後の黄色の囲みです。番号付きの選択肢（「1. …」）はボタンになり、押すと答えの欄に入ります。囲みがある間は「エージェントからの質問に回答すると作業が再開されます。」のお知らせを隠します。
  • 下の入力欄はプロジェクトの状態に従います。質問への回答（黄色）、追加の指示（完了）、停止ボタンつきでロック（実行中）、「続きからリトライ」つきでロック（失敗・中止）です。デスクトップでは Enter で送り Shift+Enter で改行（IME の変換中は送らない）、タッチ画面では Enter で改行し丸いボタンで送ります。欄は文字に合わせて伸び、説明は「?」にあります。
  • 読み手がいちばん下にいる間は新しい項目に追従し、上に戻っていると「新着 N 件」のボタンで戻れます。prefers-reduced-motion では光る文字・滑り込み・脈動・滑らかなスクロールを止めます（スピナーは止まったアイコンになる）。

画面のラベルは短くし、説明は「?」のヘルプ（HelpTip：フォーカスできるボタンで、ホバー・キーボードのフォーカス・タップで開き、Escape かほかの場所のタップで閉じ、aria-describedby で結ばれる）か、利用マニュアルの該当する節に置きます。作成・Canon・PR・公開ライブラリの画面は、その「ガイド」のリンクで利用マニュアルを開きます。

進み具合は WebSocket の購読で届き、実行中のプロジェクトは 20 秒ごとのポーリングでも読み直します。サイドバーの履歴は 30 秒ごとに読み直します。

1.6 処理の流れとジョブの一生

処理の段階

（調査）→ HCD → FRG →（HCD と FRG の整合の確認、調整のターン 1 回）→ CSV → xlsx

段階を進めるのはワーカー（プログラム）です（CoBRAC ハーネス。0.13.0 からの v2 では FRG の段階がエージェントを HCD に戻せる。2.12）。段階を「完了」にするのは、その段階の決定的な検査がファイルを受け入れたときだけで、ファイルがあるだけでは「実行中」にしかなりません。CSV と xlsx はエージェントではなくワーカーが作ります。各段階の中身は第 2 部で説明します。

状態

プロジェクトとジョブは同じ 7 つの状態を使います。

状態画面意味
QUEUED待機中ワーカーの起動を待っている
RUNNING実行中ワーカーのタスクが動いている（dispatcher が起動したときにプロジェクトを先に RUNNING にする）
WAITING_USER_INPUT回答待ちエージェントが質問した。タスクは終わっていて課金されない
FINALIZING仕上げ中xlsx・グラフ・版を作っている

ジョブの一生

  1. 依頼：API（プログラム）がプロジェクトとジョブを QUEUED で書き、SQS にメッセージを積みます。
  2. 起動：dispatcher（プログラム）は、ジョブがまだ QUEUED なら、実行中（RUNNING と FINALIZING）のジョブの数を全体と利用者ごとに数えます。どちらかが上限に達していれば 60 秒後に積み直します。空いていれば ECS RunTask でタスクを起動します（Fargate Spot。Spot が取れなければ通常の Fargate に切り替える）。タスクの ARN とハートビートの時刻をジョブに書き、「ワーカーを起動しました（Fargate Spot）」のお知らせを出し、プロジェクトを RUNNING にします。起動に失敗したら理由をお知らせに出し、60 秒後に積み直します。上限は 30 秒ごとに読み直すので、管理画面での変更はデプロイなしで効きます。回答待ちのジョブはタスクが終わっているので数えません。
  3. 実行：ワーカーがジョブを RUNNING にし、ターンを繰り返します（1.7）。
  4. 質問：エージェントがターンを status: "question" で終えると、ワーカーは作業領域とスレッドを S3 に保存し、ジョブとプロジェクトを WAITING_USER_INPUT にしてタスクを終えます（課金が止まる）。回答（POST /projects/{id}/answer）で同じジョブが QUEUED に戻り、resume モードで同じスレッドを再開します（resumeThread）。
  5. 仕上げ：HCD と FRG が通り、CSV（JSON から生成）ができると FINALIZING になり、csv_to_excel.py・Template-v2-2 の書き出し・buildGraphs() の後、版を凍結して COMPLETED になります。
  6. 完了後：追加の指示（POST /projects/{id}/followup）は同じスレッドで新しいジョブを作ります。解説記事（POST /projects/{id}/articles）も新しいジョブで、BRA データには触れません。
  7. 失敗：ターンの失敗、6 時間の上限、Spot の中断などで FAILED になります。応答の無いジョブは janitor が自動で再開します（下記）。

止める・中断される

  • 停止：API がジョブを CANCELLED にして ECS の StopTask を送ります。ワーカーは 1 分ごとにジョブの状態を見ており、中止に気づくと状態を保存して終わります。
  • Spot の中断：ECS は SIGTERM を送り、停止のタイムアウト（120 秒、Fargate の最大）の後にコンテナを止めます。ワーカーは SIGTERM を受けると、実行中のターンの利用量を数え、作業領域とスレッドを S3 に保存し、お知らせを出し、ハートビートを古い時刻（1970 年）に書き換えます。次の janitor（5 分以内）がそのジョブを再開します。
  • 途中の保存：ターンの実行中も、ワーカーは 5 分ごとに作業領域とスレッドを S3 に保存するので、中断で失う作業はその間の分だけです。
  • 6 時間の上限：ワーカーは 1 分ごとに経過時間を見て、連続 6 時間（WORKFLOW_TIMEOUT_MS）を超えるとジョブを失敗にします（「Maximum run time (6 hours) exceeded」）。リトライで続けられます。

ターンの制御

BRA のジョブでワーカーが行う 1 段階の繰り返しは次のとおりです。ループは packages/worker/src/pipeline.ts の runPhases です。詳しい受け渡しは第 2 部（2.3〜2.8）で説明します。

  1. Codex の runStreamed で 1 ターンを実行し（outputSchema つき）、出来事を Messages に書きます。
  2. 最後の返答が status: "question" なら、状態を S3 に書いて終わります（課金が止まる）。
  3. ターンのたびに、いまの段階を検証します（packages/shared/src/harness.ts の checkHcd / checkFrg）：JSON Schema、ファイルをまたぐ参照、UC の命名、インターフェース、FRG の制約、値が英語だけであること、レポートの節。文献も同じ段階で確かめます（packages/shared/src/references.ts の checkCitations、packages/worker/src/references.ts の ReferenceVerifier。2.12）。問題があれば一覧を直しの依頼として返し、1 段階につき MAX_NUDGES（3）回まで繰り返します。直しのターンは推論の強さを min(プロジェクトの強さ, medium)（fixTurnEffort）で実行します（挙げた問題を直すだけなので）。問題が残れば警告を出して進み、出力が使えなければジョブを失敗にします。
  4. 段階が受け入れられたら次の段階の依頼を送ります。後の段階のファイルがすでに通るとき（フォローアップの後など）は作り直しません。エージェントが FRG や CSV の段階で HCD のファイルを（CSV の段階で FRG のファイルを）変えたら、後の段階がそれを検証し直し、新しい問題を自分の問題と一緒に返します（2.12）。
  5. CSV：buildCsvs が JSON から 5 つの CSV を決定的に作ります。エージェントは CSV を書きません。生成に失敗したら、その問題を JSON の直しの依頼として返します。
  6. 連続 6 時間の実行で打ち切ります。

1.8 モデルと推論の強さ

  • モデルの決め方：プロジェクトの設定 → 利用者の既定 → デプロイの環境変数（CODEX_MODEL）→ DEFAULT_CODEX_MODEL（gpt-6-luna）の順です。プロジェクトを作るとき、API は必ず具体的なモデル名を決めて保存します（費用を計算できるように。不明な「Codex の既定」を残さない）。デフォルトの API キーの Tier 1 の利用者では、Tier に無い既定は gpt-6-luna になります（1.4）。
  • 推論の強さの決め方：プロジェクトの設定 → 利用者の既定 → デプロイの環境変数（CODEX_REASONING_EFFORT）→ Codex の既定の順です。値は minimal・low・medium・high・xhigh・max・ultra・persistent で、画面は high を推奨と示します。
  • 選べるモデル：キーを登録するとき、OpenAI の /v1/models を呼び、GPT-5.6 と GPT-6 の文章のモデル（日付付きのスナップショットと、音声・画像・検索などの派生を除く）を availableModels に保存します。デフォルトの API キーの利用者には、デフォルトの API キーのモデル（Tier 2）か Tier 1 のモデルを出します。作成と設定の画面で選べます。
  • 引き継ぎ：フォローアップとリトライはプロジェクトの設定を使います。解説記事と AI レビューは、そのときに選んだモデル（無ければプロジェクトか既定のモデル）を使います。
  • ターンごとの強さ：調査モード（2.9）は、調査のターンの強さを少なくとも high に上げます。ほかのターンはプロジェクトの強さのままです。直しのターンは medium を上限にします（1.7）。
  • Codex に渡す名前：gpt-5.6 という別名は Codex のモデルの目録に無いので、ワーカーは OpenAI がそれを振り向ける gpt-5.6-sol を Codex に渡します。ジョブには利用者が選んだモデルを記録します（1.14）。

作り方と順序

  • API はランダムな ID を引き、Catalog に kind = id の行を条件付き Put（attribute_not_exists(id)）で書いて予約します。取られていれば引き直します（5 回まで）。予約できてから参考資料を移し、プロジェクトを attribute_not_exists(projectId) で Put します。Projects テーブルは userId がキーなので、その条件は呼んだ人のプロジェクトしか見ません。全体での一意性を保つのは予約のほうです。予約は消さないので、作成に失敗した ID や削除したプロジェクトの ID は再利用されません。Canon（type = canon）と計画（type = plan）も同じように予約します。利用者ごとの番号 projectSeq / canonSeq はもう使いません。
  • GET /projects は、呼んだ人のプロジェクトを createdAt の新しい順（同じなら ID の順）に返します。ソートキーに番号が無くなったためです。limit（既定 100）と cursor（この順の中の位置）でページを送ります。

  • name は、入力した ROI と TLF から作った仮の <TLF> in <ROI>（どの言語でもよい。例 VOR in 小脳。nameSource = "provisional"）で始まります。HCD の段階が受け入れられると、ワーカーはエージェントが meta.json に書いた英語の name（<TLF> in <ROI>）を保存し、nameSource = "auto" にします。そうするのは nameSource が provisional か auto のときだけです。

削除（論理削除）

1.13 フロントエンド

基本

  • Vite + React 18 + React Router + Tailwind。認証は Amplify（Cognito の SRP）、Markdown は react-markdown と GFM。
  • 実行時の設定は CloudFront の /config.json（apiUrl、wsUrl、userPoolId、userPoolClientId、region、appName）です。CDK が書くので、環境ごとにビルドし直さずに済みます。ローカルの開発では VITE_* を使います。
  • 版番号：ルートの package.json の version を Vite の define で __APP_VERSION__ として、git rev-parse --short HEAD を __APP_COMMIT__ として埋め込みます。運用の規則は AGENTS.md にあります（第 7 部）。
  • WebSocket は、ID トークンをクエリに付けて接続し、プロジェクトを購読し、5 分ごとに ping を送り、切れたら待ち時間を倍にしながら（30 秒まで）つなぎ直します。API Gateway の WebSocket は 2 時間で切れるので、ポーリングも併用します（1.5）。
  • エージェント欄の Markdown（GFM）では、コマンド・思考・Web 検索を折りたたみます。

グラフの表示と編集

  • @xyflow/react と dagre（HCD は上から下、FRG は左から右）。HCD はノードを ROI の区分（塗りと縞）で色分けし、エッジの既定のスタイルを投射の生理（興奮性・抑制性・修飾性）で決めます。FRG は種類で色分けします。縮小するとラベルが大きくなり、自己接続はループで描きます。
  • 閲覧：ノードを選ぶと、隣接するもの（HCD）か祖先と子孫（FRG）以外を薄くします。キャンバスの外からの選択（URL、検索、詳細のリンク）は、詳細のシートの上に来るように表示を寄せます。検索欄は ID・名前・UC Descriptor でノードを順位付けします（↑ ↓ Enter、/ でフォーカス）。ツールバーは、検索、全体表示、元に戻す / やり直す、スタイル編集モード、メニュー（配置の向き、グリッドに合わせる、ページの設定（エッジのラベル、すべて開く / 閉じる）、PNG の書き出し、リセット）です。純粋な補助関数は packages/web/src/lib/graphView.ts にあり、vitest で確かめます。
  • スタイル編集モード（ツールバーのボタン）：スタイルのパネル、大きさの取っ手、接続の取っ手はこのモードでだけ出ます。タッチ機器では、このモードでだけノードをドラッグできます。
  • ノード：ドラッグで移動、角と辺から大きさの変更、スタイルのパネルで塗りと枠の色を変えます。
  • エッジ：（スタイル編集モードで）押すとスタイルのパネルが開きます。線の種類（曲線、直線、自動の直交、経由点を編集できる直交、折れ線）、色、太さ、破線、角の丸み、始点と終点の印（矢印、開いた矢印、四角、円、ひし形、棒）。直交のエッジは、経路上の「+」で経由点を足し、ドラッグで曲げ、ダブルクリックで消します。
  • 接続の取っ手：選んだエッジの両端の円を、ノードの辺の取っ手（1 辺に 7 点）にドラッグして始点と終点を変えます。
  • 既定の線の種類は曲線です。以前の直交の既定で保存した配置は、線の種類を持たずに曲がりだけを持つことがあり、そのエッジは曲がりを保つために直交のままにします。
  • 同じ 2 つのノードを結ぶエッジ（帰還ループの A→B と B→A、または複数の A→B）は、20 単位ずつ離れた別のレーンに描きます（lib/parallelEdges.ts）。どのエッジも自分の進む向きの右側にあり、端はノードの辺に沿ってずれ（角は越えない）、曲線は中央で離れ、直交と階段の経路は中央の区間を動かします。ラベルは各レーンの外側に置き、短い接続で端の印を隠すときは短くします（選んだときと強調したときは全文）。同じノードの自己ループは外側に重ねます。レーンは描くたびに計算して保存しません。利用者が経由点を描いたエッジは自分の経路を保ちます。
  • 抑制性の既定は青（#2563eb）と四角の終点、興奮性は灰色と三角、修飾性は紫の破線と円です。分類は Connection のコメントを優先し、無ければ送り手の Transmitter / Modulation Type を使います（classifyEdgeSign）。同じ分類のすべてのエッジに同じスタイルを当てられます。
  • 配置の保存：useGraphLayout が位置・大きさ・色・エッジのスタイル（経由点と接続点を含む）を 600 ミリ秒まとめてから PUT …/layout に保存します。グラフを作り直しても、同じノード ID・エッジ ID の設定は残ります。Ctrl+Z / Ctrl+Y で元に戻す / やり直す。

テーマ

ライトとダークがあります。既定は prefers-color-scheme に従います。サイドバー（とログインのカード）に「システム / ライト / ダーク」の切り替えがあり、ブラウザごとに保存し（localStorage の cobrac-theme）、index.html のインラインのスクリプトが最初の描画の前に当てます。Tailwind の色は CSS 変数を指し、背景・文字・枠に別の組を持つので（packages/web/theme-palette.js）、bg-white は暗い面になり、塗ったボタンの text-white は白のままです。サイドバーはどちらのテーマでも暗い色です（theme-static）。グラフの塗りと線の色はライトの値で保存し、描くときに変換します（lib/graphTheme.ts）。塗りは同じ色相の暗い色にしてラベルを明るくし、線は暗いキャンバスで読めるように明るくし、スタイルのパネルの見本は描いた色を示します。test/theme.test.tsx が、画面で使う文字と面の組、既定の塗りと見本の上のノードのラベル、キャンバスの上のエッジのコントラストを確かめます。

1.14 ワーカーの処理

ワーカーは Fargate のタスクで動く TypeScript のプログラムで、LLM を含みません。入口は packages/worker/src/index.ts です。dispatcher が環境変数（JOB_USER_ID・JOB_PROJECT_ID・JOB_ID・JOB_MODE）でジョブを指定します。ID の形が合わなければ起動しません（canon-review は Canon の ID、plan は計画の ID、ほかはプロジェクトの ID）。BRA のジョブの手順は次のとおりです。

  1. Users・Projects・Jobs を読み、キーを選び（利用者自身のキー。無ければ、承認されていて Tier がジョブのモデルを許す間はデフォルトの API キー。1.4、packages/worker/src/runKey.ts の planRunKey）、KMS で復号します。RCS の接続先とトークン（Secrets Manager）を読みます。読めなければ RCS 無しで続けます。
  2. prompts/AGENTS.md を /work に写し（{P} を ID に置き換え）、JSON Schema を /work/schemas/ に書きます。resume・followup・retry では作業領域とスレッドを S3 から戻します。参考資料を用意し（1.12）、Canon に入っていれば固定した rev の定義を /work/canon/ に置きます（4.5）。followup では、いまのデータにまだ版が無ければ（版の仕組みより前に完成したプロジェクト）、変える前にそれを版として凍結します（第 5 部）。
  3. createCodex → openThread（sandboxMode: danger-full-access、承認なし、ネットワークあり、Web 検索 live、lit MCP と RCS MCP）。Fargate のタスク自体がサンドボックスです（コンテナの中では Landlock・seccomp を使えない）。ターンごとにそのターンの設定でスレッドを開くので、調査のターンを高い推論の強さで実行できます。
  4. 調査モードで、作業領域が調査を終えていなければ調査のステップを実行し（2.9）、続いて段階を実行します（1.7）。出来事を Messages に書き、ファイルが変わるたびに stepStates と activeStage を更新します（調査中は RESEARCH、調整のターンは ADJUST、ほかは実行中の段階）。
  5. 段階を受け入れるたびと、質問・完了・失敗で待つ直前に、作業領域とスレッドを S3 に差分で同期します（ターンの実行中も 5 分ごと）。
  6. CSV がそろったら finalize.ts が xlsx・テンプレートの xlsx・グラフ JSON を作って送り、版を凍結し、ジョブとプロジェクトを COMPLETED にします。

ターンが失敗するとき

  • ターンが失敗するのは、turn.failed のときか、ストリームが turn.completed 無しに error の出来事で終わったときだけです。Codex はレート制限の再試行を error の出来事として報告します（「Reconnecting... 2/5 (rate limit exceeded …)」）。これはお知らせとして出し、ターンは続きます。Codex が error の項目として報告する致命的でない注意（「Model metadata for `x` not found」「Falling back from WebSockets to HTTPS transport」など）もお知らせとして出し、本当のエラーはエラーのままにします。
  • OpenAI のレート制限（TPM・RPM、HTTP 429。使い切った割り当ては除く）でターンが失敗したら、間を置いて同じスレッドで再開します。待ち時間はサーバーの「try again in …」に 5 秒を足したものと、30 秒・60 秒・120 秒の大きいほう（最大 3 分）で、3 回までです。待つ間もハートビートを送ります。それでも失敗すればジョブを失敗にします。
  • 1 回の依頼が 1 分あたりのトークンの上限より大きい（「Request too large … Limit 200000, Requested 202304」。gpt-6-luna は 200k）と、待っても通りません。スレッドの文脈が上限に達すると、その後のターンはすべて拒まれます。スレッドを十分小さく保つため、Codex は CODEX_AUTO_COMPACT_TOKENS（既定 75,000、model_auto_compact_token_limit）で会話を圧縮します。この上限は速さのためでもあります。本番の実行では、文脈が約 80k トークンを超える依頼は小さい依頼より返答が 15〜40 秒遅く、ジョブの時間の大半がそうした依頼に使われていました。圧縮自体は数秒です。それでも大きすぎると拒まれたターンは、同じスレッドでは再試行せず、新しいスレッドを 1 回だけ始めて、プロジェクトの見出し、ファイルがここまでの作業を持っているという注記、HCD・FRG の仕様を付けて同じ依頼を送ります。失敗したターンの後、codex exec は終了コード 1 で終わりますが、その終了ではなくターン自身のエラーを報告します。
  • モデルの目録：Codex CLI（@openai/codex-sdk と一緒に入る）はモデルの目録の情報を必要とし、無ければ代わりの情報で動いて「Model metadata for `x` not found」と警告します。単価表のすべてのモデルは、入っている CLI の目録（codex debug models --bundled）に無ければなりません（packages/worker/test/codexCatalog.test.ts が確かめる）。gpt-5.6 の別名は目録に無いので gpt-5.6-sol を渡します（1.8）。model_context_window はどのモデルも 272,000 です。OpenAI は gpt-5.6・gpt-6 の文脈を 1,050,000 トークンとしていますが、272K を超える入力は 2 倍の料金で、Codex の目録もすべて 272,000 です。圧縮（75,000）はそれより十分小さい値です。Codex には出力の最大トークン（これらのモデルでは 128,000）の設定はありません。

BRA 以外のジョブ

  • article（index.ts の articleJob、ループは article.ts）：キーを決めた後に分かれます。作業領域だけを戻し、図を描き、記事の 1 ターンと直しのターンを実行し、図と article/<locale>.md / .json を送り、プロジェクトを COMPLETED に戻します（2.15）。

秘密の守り方

ワーカーが子プロセス（Codex、エージェントのコマンド、Python、poppler）を起動するときは、AWS の認証情報（AWS_* とコンテナの認証情報の URI）、NCBI_API_KEY、RCS のトークンを環境から除きます（childEnv.ts）。タスクロールの認証情報があれば誰の API キーでも復号できるからです。RCS のトークンは Codex が MCP のベアラートークンとして送り、shell_environment_policy がエージェントのコマンドからそれと OpenAI のキーを除きます。実行ファイルを実行専用にする仕組みなど、コンテナの守り方は第 7 部で説明します。
