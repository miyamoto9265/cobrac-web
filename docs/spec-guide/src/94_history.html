付録 D

改訂の経緯

この付録は、CoBRAC ハーネスが v0 から v2 まで世代を重ねてきた理由と、アプリの版ごとに入った主な機能を記録します。世代の移り変わりは、以前は 3 本の比較記事（v0→v1、v1→v1.1、v1.1→v2）に書かれていました。この本では、それぞれの問題・変更・効果を表にした要約だけを残します。現行の仕様は本文（第 1〜7 部）にあり、この付録は経緯を確かめるためのものです。

ハーネスの世代v0（LLM が手順書を読んで進める）、v1（ワーカーがフェーズを進める）、v1.1（JSON と SABRA の名前）、v2（HCD と FRG の往復）
測った値指示のトークン数、成果物の量、1 プロジェクトあたりの費用の試算、言語野での 3 回の実行の比較
アプリの版0.1.0（2026-09-13）から 0.37 までの各マイナー版で入った主な機能

D.1 ハーネスの世代の一覧

ハーネスは、LLM の周りにあるもの全体 ― 指示（プロンプト）、制御のループ、検査、後処理 ― を指します。世代の番号はハーネスの番号で、アプリの版番号、BRA データ形式の版（xlsx の BRA version、CoBRAC-v1-0 / CoBRAC-v1-1）、検査規則の世代（harnessRules、D.7）とは別のものです。

世代アプリの版進め方を決める主体主な特徴
v0デスクトップ版（Cursor）と、アプリ 0.1.0〜0.4.2LLM（手順書を読んで自分で判断する）日本語の指示書 4 本を順に読む。フェーズの完了は文字列のマーカー。品質の検査はない
v10.5.0〜0.6.0ワーカー（プログラム）英語の短いフェーズ仕様を 1 本ずつ渡し、ターンごとに検査する。CSV はコードで作る
途中段階0.7.0〜0.7.1ワーカーUC の命名規則と RCS の照会が入る。データはまだ md の表
v1.10.8.0〜0.8.1ワーカーデータは JSON と JSON Schema。CSV は常にコード。レポートと判断ログを画面で読める
v20.13.0〜（部品は 0.9.0〜0.12.1 で順に入った）ワーカー（調整ターン 1 回を含む）調査ステップ、文献と引用文の照合、BRA 仕様への準拠、Collection、HCD と FRG の整合チェックと往復。現行の世代（第 2 部）
この付録での主体の呼び方

CoBRAC エージェント（LLM）は、OpenAI のモデルが Codex を通して動くもので、文献を調べ、判断し、ファイルを書きます（以前の比較記事と図 D.1〜D.3 では「Codex エージェント」）。ワーカー（プログラム）は ECS Fargate 上の TypeScript のプログラムで LLM を含まず、依頼を送り、返ったファイルを検査し、次の依頼を決め、CSV・xlsx・グラフを作ります（2.1）。人は利用者で、デスクトップ版では LLM への最初の依頼と xlsx の生成も人が行いました。

典拠：CHANGELOG.md（0.5.0・0.7.0・0.8.0・0.13.0）、packages/shared/src/harness.ts（HARNESS_RULES）

D.2 v0：LLM が手順書を読んで進めた時代

v0 は、Web アプリより前に AI 支援エディタの Cursor で行っていたデスクトップ版の手順と、それをそのままサーバーに載せたアプリ 0.1.0〜0.4.2 の両方を指します。流れ（TLF / ROI → HCD → FRG → CSV 5 本 → .bra.xlsx）は今と同じですが、どこまで進んだかを判断していたのは LLM でした。

作業デスクトップ版アプリ 0.1.0〜0.4.2
最初の依頼人が Cursor のチャットで、instruction_0.md を読んで従うよう LLM に頼むワーカーが「instruction_0.md を読んで従ってください」という 1 文を送る
HCD・FRG・CSVLLM が日本語の指示書 4 本（instruction_0〜3、計 13,871 トークン）を順に読み、フォルダを作り、HCD 8 本（初学者向け解説記事と Mermaid 図を含む）、FRG 5 本（表と Mermaid 図）を日本語で書き、最後に全部を英訳して CSV 5 本を手で書く。アプリでは 1 つの長いターンで全部を進め、フェーズの終わりに [STEP_COMPLETE] HCD のようなマーカーを出す
質問チャットで人に聞く返答の中の [QUESTION]…[/QUESTION]。ワーカーはタスクを止め、回答が来たら同じ会話を再開する
完了の判定人が見るワーカーは CSV があるかだけを見て、なければ同じ「続けて」を最大 3 回送る
xlsx人が python csv_to_excel.py を実行し、Contributor と Project ID を入力するワーカーが csv_to_excel.py とグラフの生成を実行する

この進め方には、次の D.3 の表の左の列に挙げる 4 つの弱点がありました。

典拠：archive/v0/（desktop/ の指示書と csv_to_excel.py、samples/ の成果物、userguide/）。サーバー版 v0 の指示は git のタグ v0.4.2 の prompts/

D.3 v0 から v1 へ：ワーカーがフェーズを進める

アプリ 0.5.0（2026-09-26）で、進め方を決める主体を LLM からワーカーに移しました。ワーカー（プログラム）が HCD・FRG・CSV のフェーズを 1 つずつ進め、LLM には英語の短いフェーズ仕様をそのフェーズの分だけ渡し、ターンが終わるたびにファイルをコードで検査して、問題の一覧をそのまま返します。CSV・xlsx・グラフはワーカーが作るので、LLM は文献の調査と科学的な解釈に集中できます。

v0 の弱点v1 での変更（ワーカーと LLM の分担）効果
① 中身を検査しないワーカーがターンごとに md の表を読み取り、ファイルと列、ID、接続の両端、Reference ID、Interface と接続の一致、FRG の制約（根は 1 つ、循環なし、GN の UC は 2 つまで、UC の親 GN は 2 つまで、ROI 内の UC はすべて FRG につながる）を検査する。問題の一覧を LLM に返し、フェーズごとに最大 3 回直させる。3 回で残れば警告を出して進む壊れた表のまま完了しなくなった。チャットで指摘を 1 件ずつ見られる
② 文字列のマーカー頼みLLM のターンの終わりを、スキーマに合う JSON {status, message, question}（構造化出力）にした。フェーズの完了は、ワーカーの検査がファイルを受理したときに決まる質問の見落としと読み違いがなくなった
③ CSV が手作業の翻訳LLM は成果物を最初から英語で書く。CSV はワーカーの buildCsvs() が md の表から作り、LLM は変換に失敗したときの予備だけ。フォルダと Project.csv もワーカーが作る翻訳と読み直しが要らなくなった
④ 指示書が文脈に残るどのフェーズでも同じルールを AGENTS.md（721 トークン、Codex が自動で読む）に移し、フェーズ仕様は今のフェーズの 1 本だけを依頼文に入れる。ワーカーが今のフェーズを知っているので、再試行や再開はちょうどその場所から始まる文脈に載る指示が約 4 分の 1 に（D.6）
（出力の削減）初学者向け解説記事（7_EasyToUnderstand.md）と Mermaid の図を廃止し、図は CSV から作る Web のグラフにした。解説記事は 0.9.0 で依頼制のジョブとして戻った（2.15）成果物の出力が約 43% 減（推定）

出力の推定は、v0 時代の 5 プロジェクト（VOR 学習、演繹推論、連想記憶、知覚速度 2 件）の最終成果物の平均から求めました。62,400 トークンから、解説記事と Mermaid 図のファイル 9,100、FRG の中の Mermaid 1,000、LLM が打ち込んだ CSV 6,300、残る日本語を英語で書いた差 10,300 を引いて、約 35,700 トークンです。LLM は同じファイルを何度も書き直していたので、これは削減の下限です。一方で v1 では修正ターンのたびに文脈が送り直されるので、初稿がひどく壊れていると v0 より高くつくこともありえます。

典拠：CHANGELOG.md（0.5.0）、packages/worker/src/pipeline.ts、packages/shared/src/harness.ts、prompts/AGENTS.md。成果物の測定は archive/v0/samples/

D.4 v1 から v1.1 へ：JSON のデータと SABRA の名前

v1 でも LLM はデータを md の表で書き、ワーカーがそれをパースし直していました。Circuit ID は自由な名前で、画面で見られるのは xlsx とグラフだけでした。0.7.0（命名規則と RCS）と 0.8.0（JSON）の 2 段階で v1.1 になりました。フェーズの骨格（ワーカーが HCD → FRG → CSV → xlsx を進めて検査し、LLM はターンの終わりに JSON を返す）は変わっていません。

v1 の弱点v1.1 での変更（版）効果
① md の表のパースが脆い。セルの | は \|、改行は <br> と書く約束で、ワーカーには列名のゆれや分割された表を救うコードが要った。最大の 3_UC.md は 14 列で長文のセルが 5 つあったLLM はデータを JSON 4 本（references.json・uc.json・connections.json・frg.json）で書き、ワーカーは JSON Schema（HARNESS_SCHEMAS）で検査する。スキーマは schemas/ に書き出し、LLM も読める。md のパーサは削除（0.8.0）問題をファイル名と JSON ポインタで返せる（uc.json: /ucs/3/implementation is required）
② 誰も読まない中間ファイル（ワーカーは存在を確かめるだけで、利用者にも見えない）1_InitialDecomposition.md・2_OptimizedFRG.md・5_Verification.md を廃止し、理由と残る論点はレポートへ。レポートは report.md 1 本（## HCD と ## FRG）、1_Thinking.md は decision_log.md になり、画面の「レポート」「判断ログ」で読める（0.8.0）md は人が読む 2 本だけになった
③ Circuit ID が自由な名前で、プロジェクトごとに変わり、アトラスとの対応もないLLM が RCS（MCP サーバー）で脳領域を照会し、UC を SABRA の単位（アンカー）に固定して UC Descriptor と Circuit ID で名付ける。ワーカーは構文、略称の一致（BNA は組み込みの表、HOMBA はワーカー自身が RCS に照会）、項目と facet の対応、重複を検査し、LLM の RCS 呼び出しをすべて rcs_mcp_calls.jsonl に残す（0.7.0）同じ神経集団に、どのプロジェクトでも同じ名前が付く（第 3 部）
④ CSV を LLM が手書きする予備が残っていたCSV フェーズから LLM のターンをなくした。問題は JSON ファイルの修正依頼として LLM に返す（0.8.0）CSV は常にコードが作る

ファイルの対応は次のとおりです。2_BIF.md の References の表 → references.json。2_BIF.md の Connections の表と 4_Connection.md → connections.json（bif[] と connections[]）。3_UC.md → uc.json（外部の UC は Comments のタグではなく roi の値で示す）。3_FinalFRG.md と 4_FunctionDetails.md → frg.json（ノードごとの 1 項目）。0.7.0 では xlsx の Circuits シートの最後の列に UC Descriptor が加わりましたが、末尾への追加だけなので BRA version は CoBRAC-v1-0 のままでした。

典拠：CHANGELOG.md（0.7.0・0.8.0）、packages/shared/src/harness.ts・jsonSchema.ts・ucNaming.ts、packages/worker/src/rcs.ts

D.5 v1.1 から v2 へ：一方通行から往復へ

v1.1 の流れは HCD → FRG → CSV → xlsx の一方通行で、受理したフェーズには戻りませんでした。FRG は「完成した HCD」から作るので、HCD の UC が粗すぎて FRG が形にならないときも、LLM は FRG の側で無理に合わせるしかありませんでした。v2 では FRG から HCD に戻る道を作り、その前後にワーカーの検査を足しました。部品は 0.9.0〜0.12.1 で順に入り、0.13.0（2026-09-29）の戻り道と調整ターンで一方通行でなくなりました。

v1.1 の弱点v2 での変更（ワーカーと LLM の分担）版
HCD に戻る道がない（数の制約が満たせないときの逃げ道は「TLF を細かく分解し直す」だけ）LLM は FRG の手順から HCD に戻って UC を分ける・足せる。ワーカーは FRG の段の後、整合チェックに X1〜X3・X8 があれば調整ターンを 1 回だけ送り、LLM はどちらを直すかを証拠で決めて decision_log.md の revisions 節に記録する（2.12）0.13.0
FRG の段で LLM が HCD を直しても検査されないワーカーが段ごとにデータファイルのハッシュを phase_baseline.json に残し、後の段で変わっていれば HCD の検査をすべてやり直す0.12.0
HCD と FRG が合っているかを誰も見ないワーカーが整合チェック X1〜X8 を cross_check.json に記録する（0.12.0 では記録だけ）。X9（粒度）と revisions 節の [instruction] タグを追加0.12.0・0.13.0
文献を知識で書き、実在を確かめないワーカーが DOI を Crossref で、PMID を PubMed で引き、第一著者・年・題名を照合する0.9.0
引用文が要約で、原文か分からないPointers on literature を原文の引用に限り（0.10.0）、ワーカーが全文か抄録と照合する（類似度 0.9 以上、0.11.0）0.10.0・0.11.0
文献を探す手段が知識と Web 検索だけHCD の前の調査ステップ（調査モード、既定でオン）と、LLM が使う文献ツール lit（PubMed・Europe PMC の検索、抄録、全文の文）。ワーカーは調査の網羅性を検査する（2.9）0.11.0
BRA の Review Tool でエラーになる値BRA 仕様の値の規則（BRA version CoBRAC-v1-1）：Source of ID は 1 値、1 行 1 文献、sCID / rCID relation、列挙値、ROI 行、Review End Line0.10.0
粗い領域が均一な送り手のままCollection（0.11.0）。複数の SABRA 単位にまたがる送り手は理由（uniformityNote）が要る（コード 203、0.13.0）0.11.0・0.13.0
公式テンプレートの形で出せないTemplate-v2-2 形式の xlsx もワーカーが作る（xlsx は 2 種類、2.14）0.11.0
プロジェクトごとに回路の定義がばらばらCanon の定義を生成時の制約にする（第 4 部）0.12.0
手元の資料を渡せない参考資料の添付（ワーカーが本文を取り出して一覧にし、LLM に渡す）0.12.0
長いジョブがレート制限や会話の大きさで落ちるレート制限は待って同じ会話で再開（最大 3 回）。会話を自動で圧縮し、それでも大きすぎるターンは新しい会話で続ける（2.16）0.12.0・0.12.1
なぜ「v2」と呼ぶか

リポジトリの作業規約（AGENTS.md）は、ワークフローの骨格 ― HCD → FRG → CSV → xlsx の順、ワーカーがフェーズを進めて検証する方式、ターン終了時の JSON ― を相談なしに変えないと定めています。0.13.0 では、所有者の承認を得てこの骨格を「HCD → FRG →（整合チェック・調整）→ CSV → xlsx」に広げました。部品の置き換えではなく流れの形が変わったので、v1.1 の次を v2 としました。ターン終了時の JSON とフェーズごとの決定的な検査は変わっていません。
