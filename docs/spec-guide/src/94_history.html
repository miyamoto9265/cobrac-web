D.3 v0 から v1 へ：ワーカーが段階を進める

v0.5.0（2026-09-26）で、進め方を決める主体をエージェントからワーカーに移しました。ワーカーが HCD・FRG・CSV の段階を 1 つずつ進めます。エージェントには英語の短い段階の仕様をその段階の分だけ渡し、ターンが終わるたびにファイルをコードで検査して、問題の一覧をそのまま返します。CSV・xlsx・グラフはワーカーが作るので、エージェントは文献の調査と科学的な解釈に集中できます。

v0 の弱点v1 での変更（ワーカーとエージェントの分担）効果
① 中身をだれも検査しない。完了は「CSV がある」ことで、列の欠けや存在しない回路 ID、壊れた FRG は xlsx を開くまで分からないワーカーがターンごとに md の表を読み取り、ファイルと列、ID、接続の両端、Reference ID、Interface と接続の一致、FRG の制約を検査する。FRG の制約は、根は 1 つ、循環なし、GN の UC は 2 つまで、UC の親 GN は 2 つまで、ROI 内の UC はすべて FRG につながる、の 5 つ。問題の一覧をエージェントに返し、段階ごとに最大 3 回直させる。3 回で残れば警告を出して進む壊れた表のまま完了しなくなった。チャットで指摘を 1 件ずつ見られる
② 進捗が文字列のマーカー頼み。出し忘れや綴り違い、長い返答に紛れた質問で表示が狂うターンの終わりを、スキーマに合う JSON {status, message, question}（構造化出力）にした。段階の完了は、ワーカーの検査がファイルを受理したときに決まる質問の見落としと読み違いがなくなった

（出力の量）初学者向け解説記事（7_EasyToUnderstand.md）と Mermaid の図を廃止し、図は CSV から作る Web のグラフにした。解説記事は v0.9.0 で依頼制のジョブとして戻った（3.14）成果物の出力が約 43% 減（推定）

D.9 速度と費用の測定（2026-10）

この節の位置づけ

この節は、ある時点の測定の報告です。数値は 2026-09〜10 の本番の記録と比較のための実行から出したもので、保証する値ではありません。モデル、アプリのバージョン、指示書、OpenAI 側の状態で変わります。調べたのは v0.16.0 の本番の実行で、変更は v0.17.1〜v0.18.2（どれも 2026-10-01 のリリース）です。条件は gpt-6-luna、推論の強さ high、調査モード on、日本語です。

調べたのは、BRA の作成にかかる時間と OpenAI の費用、遅さの原因、v0.18.0 の高速化とその前後の比較です。あわせて見つかった使用量の二重計上は D.10 に、Spot の中断からの再開は 8.3 にまとめています。現在の時間と費用の目安は 1.4 と 9.10 にあります。

要点

v0.16.0 の本番の実行を調べると、BRA の作成 1 件にかかる時間（平均 60 分）の 88% は、モデルの応答を待っている時間でした。1 回の応答の待ち時間は、そのリクエストのコンテキスト（それまでの会話の長さ）でほぼ決まります。コンテキストが 8 万トークン未満なら固定の待ちは約 4 秒ですが、12 万を超えると約 42 秒になります。当時は会話の圧縮を 15 万トークンで行っていたので、モデル時間の 4 分の 3 近くがこの遅い領域で使われていました。

そこで v0.18.0 では、3 つの変更を入れました。圧縮のしきい値を 7.5 万トークンに下げ、ツールの結果とファイルの書き方を小さくし、修正ターンの推論の強さを medium にしました。同じ ROI と TLF で変更前と変更後を 3 件ずつ実行したところ、平均の所要時間は 48.6 分から 31.0 分に（36% 短縮）、実費は $0.174 から $0.134 に（23% 減）なりました。ただし件数は 3 件ずつと少なく、調査ステップで挙げる候補が減ったことなど、注意して見るべき点があります（後述の「注意点」）。

  • 段階の順番は動かせません。FRG は HCD の UC と接続を入力にし、調整ターンは HCD と FRG の両方を見て直します。調査 → HCD → FRG → 調整の順は、依存関係のために直列になります。

  • 新しいジョブ（B・C）では、Codex が「コードモード」を使っているので、ツールの呼び出しはすでに部分的に並列になっています。コードモードは、exec の中の JavaScript から複数のツールをまとめて呼ぶ方式です。

会話の大きさと TPM

1 回の依頼が 1 分あたりのトークンの上限より大きいと、待っても通りません。当時のエラーは「Request too large … Limit 200000, Requested 202304」で、gpt-6-luna の上限は 20 万でした。会話の文脈が上限に達すると、その後のターンはすべて拒まれます。これが v0.12.1 の会話の自動圧縮と、大きすぎるターンを新しい会話で続ける仕組みのきっかけになりました（8.4）。

圧縮の上限は速さのためでもあります。本番の実行では、文脈が約 80k トークンを超える依頼は、小さい依頼より返答が 15〜40 秒遅く、ジョブの時間の大半がそうした依頼に使われていました（D.9）。

デフォルトの API キーの組織の TPM は、2026-10 初めまで gpt-6-luna・gpt-5.6-luna で毎分 20 万でした。その後、利用の tier が上がり、OpenAI の Build tier の値である毎分 200 万になりました（8.3）。

Spot の中断からの再開

v0.18.1 までは、作業ディレクトリを S3 に保存するのは、段階の受理・質問・完了・失敗のときだけでした。SIGTERM を受けても何もしていませんでした。HCD⇄FRG の試行（2026-09-29）では、15 分ぶんの作業を失い、中断の検出にも 27 分かかりました。janitor 自体が 15 分ごとにしか動いていなかったので、再開は中断の 15〜30 分後でした。

v0.18.2（PR #66）で、5 分ごとの保存、SIGTERM の処理、停止の猶予 120 秒、janitor の 5 分ごとの実行を入れました。ハートビートを古いとみなす 15 分は変えていません。同じバージョンで、ワーカーの起動と janitor のメッセージを UI の言語で出すようにし（PR #68、10 言語）、公開プロジェクトの複製に元の調査モードの設定をコピーするようにしました（PR #67）。いまの仕組みは 8.3 にあります。

典拠：packages/worker/src/interrupt.ts・codex.ts・env.ts、packages/api/src/handlers/janitor.ts、CHANGELOG.md（0.12.1・0.18.2）
