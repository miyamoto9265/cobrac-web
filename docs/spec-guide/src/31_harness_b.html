3.7 調査ステップ

調査モードは、HCD を作る前に文献を調べるかどうかを決めるプロジェクトの設定です。作成画面のモデルのメニューにあるスイッチで選び、既定はオンです。設定はプロジェクトに保存され、各ジョブは実行したときの値を記録します。作成後は変えられず、フォローアップとリトライも同じ設定で動きます。プロジェクトのヘッダーには「調査モード: オン／オフ」と表示されます。

調査モードがオンのとき、HCD 段階の前に、エージェントが調査するターンが入り、ワーカーがその結果を検査します。これを調査ステップと呼びます。ジョブの段階としては数えないので、画面に出る段階の並び（HCD → FRG → CSV → xlsx）は変わりません。オフにすると、調査ステップと調査モード用の指示書（後述）はなくなりますが、文献のツール（後述）はそのまま使えます。

エージェントの作業

調査の単位は、ROI の主な入力・出力・内部投射の候補です。エージェントは調査の指示書に従って総説を入口にし、候補ごとに領域名の同義語、種、追跡法を変えて検索します。論文の要旨か全文を読み、支持の強さを判断し、調べても見つからなかったものを区別します。結果は research.json だけに書きます。書く内容は次のとおりです。

項目内容
計画調査の進め方
候補調べる投射。最大 40 件
検索文字列候補ごとに使った検索
証拠Reference ID、PMID / DOI、種、測定法、層・細胞種、知見、要旨と全文のどちらを読んだか
被覆トレーサー研究・霊長類・齧歯類・層と細胞種のそれぞれについて found / searched_none / not_applicable
状態候補ごとに supported / weak / not_found / contradicted
残った不足調べきれなかった点

ワーカーの検査

ワーカーは、エージェントの動きを伝えるイベントの流れから、文献のツールの呼び出しと Web 検索をすべて検索ログに記録します。ログには呼び出しごとにジョブ ID と段階を、失敗したときはエラー文も残し、ジョブにはツールごとの検索回数を数えます。この検索ログはエージェントの申告ではなく、ワーカーが記録したものです。ワーカーはこれをもとに、次の点を検査します。

  • スキーマに合っていること。候補ごとに異なる検索が 2 件以上あり、少なくとも 1 件は PubMed か Europe PMC で検索していること。
  • research.json に書かれた検索文字列が、同じツールの呼び出しとして検索ログに残っていること。
  • 被覆の値が証拠と合っていること。found とするには、トレーサー研究・霊長類・齧歯類・層と細胞種のそれぞれに対応する証拠が必要です。
  • supported / weak / contradicted の候補には証拠があり、not_found の候補には証拠がないこと。
  • すべての証拠に PMID か DOI があること。支持以外の状態と not_applicable には理由が書かれていること。

問題は修正ターン（最大 2 回）でエージェントに返します。不足が残っても実行は止めず、結果を research_check.json に書いて HCD 段階に進みます。この記録には、調査が済んだか（done）、終わり方（passed / gaps / budget）、要約、問題が入ります。調査が済んだプロジェクトフォルダでは、以後の実行で調査ステップを飛ばします。

検索の回数が足りていることと、望ましい証拠が見つかったこととは別です。残った不足は、HCD とレポートの Limitations に引き継ぎます。

調査の予算
項目現行の値・規則
候補数最大 40
検索候補ごとに異なる検索を 2 件以上。少なくとも 1 件は PubMed または Europe PMC
修正最初のターンの後、最大 2 回
時間調査ステップ全体で 60 分。時間切れのときに動いているターンは打ち切り、それまでに書かれた内容で HCD 段階に進む。残りが 10 分未満なら新しい修正ターンを始めない
打ち切ったターンの使用量Codex のセッションファイルから測り、ジョブの使用量に足す（9.10）
推論の強さ調査の本ターンはプロジェクトの値と high の高い方。修正ターンはプロジェクトの値と medium の低い方
費用の上限金額の上限はない。費用は時間の予算で抑え、使用量の行に表示する

文献のツール

文献のツール（lit）は、ワーカーと同じコンテナで動く MCP サーバーで、Codex がエージェントのツールとして起動します。PMID の確認や原文の引用にも使うので、調査モードの有無にかかわらず、すべての BRA の実行で使えます。Web 検索もオンのままです。

ツール返すもの
search_pubmed / search_europepmc関連順の検索結果。PMID、DOI、タイトル、著者、年、雑誌、PMC の全文の有無。既定 8 件、指定で 1〜25 件
get_abstract1 本の論文の書誌と要旨
find_sentences指定した語を含む文を最大 8 文。オープンアクセスの全文があれば全文から、なければ要旨から

あるサービスが答えないときは、別の経路で同じ情報を取ります。書誌と要旨は PubMed から、全文は PMC から取得し、どのサービスが失敗したかを結果の注記に書きます。それでも失敗したツールは、失敗したサービスと、代わりに使えるツール（search_pubmed と search_europepmc を互いに）を返します。

調査の後の段階

調査モードでは、HCD と FRG の依頼文とフォローアップに、調査モード用の指示書が付きます。その指示は次のとおりです。

  • 調査の結果をもとに BIF と接続を作ります。支持された証拠とトレーサー研究を優先し、弱い証拠はそうと明示し、根拠があれば細胞種や層の UC を作ります。
  • 引用は、実際に読んだ文から取ります。
  • 不足は Limitations に書きます。
  • FRG 段階では、理論と計算モデルを調べます。
  • フォローアップでは、新しく加える主張を調べます。

HCD と FRG の検査は、調査モードの有無で変わりません。

調査の記録

調査ステップが終わると、ワーカーは次の値を research_check.json の測定値とジョブの記録に残し、画面に要約の行を出します。

  • 終わり方、モデル、推論の強さ、開始と終了の時刻、所要時間（分）、ターン数、打ち切りの有無
  • 費用と使用量
  • 候補数と、そのうち支持された数
  • ツールごとの検索回数（成功と失敗）

実装

  • 設定はプロジェクトの researchMode、本ターンの依頼文は prompts/phases/RESEARCH.md、スキーマは research.schema.json、調査後の指示書は prompts/research_mode.md です。
  • 検索ログは research_queries.jsonl、ジョブの検索回数は searches、調査の記録はジョブの researchStep と research_check.json の metrics です。
  • 検査は checkResearch、予算は RESEARCH_BUDGET（maxCandidates など）、見積もりは researchModeEstimate、修正ターンの推論の強さは fixTurnEffort で決めます。時間の予算は環境変数 RESEARCH_TIME_BUDGET_MIN（既定 60）で変えられます。
  • CloudWatch には調査の開始と終了に [research] start / [research] end を書きます。すべてのジョブは終了時に [metrics]（使用量、費用、所要時間、ツールごとの検索回数）も書きます。
  • 文献のツールは litMcp.ts と litsearch.ts です。検索の件数は max_results で指定します。要求は文献の照合と同じ HTTP クライアント（http.ts）を通ります。タイムアウトは 15 秒で、タイムアウト・ネットワークエラー・429・5xx のときは 1 秒、2 秒、4 秒と間を空けて 3 回まで再試行し、Retry-After に従います。3 回続けて失敗した相手は 5 分休ませます。
  • エージェントがツールを並列に呼んでも、相手ごとに間隔を空けます（Europe PMC は 200 ミリ秒、NCBI は 350 ミリ秒）。1 回の呼び出しは 65 秒までで、MCP のツールのタイムアウト 90 秒より短くしてあります。
  • get_abstract と find_sentences は、Europe PMC が持ち時間の 45% のうちに答えないと、PubMed から書誌と要旨を、NCBI BioC 経由で PMC から全文を取ります。失敗したサービスは結果の note に書きます。

典拠：prompts/phases/RESEARCH.md、prompts/research_mode.md、packages/shared/src/research.ts（checkResearch・RESEARCH_BUDGET・researchModeEstimate）、packages/worker/src/pipeline.ts（runResearch）、litMcp.ts、litsearch.ts、http.ts

3.8 HCD

HCD 段階で判断してファイルを書くのはエージェント、書かれたファイルを検査するのはワーカーです。この節の規則は、エージェントへの指示（HCD の指示書と、後ろに付く規則の指示書）であると同時に、ワーカーの検査が確認する条件でもあります。回路の名前の規則は第 2 部、Canon による制約は第 5 部にまとめます。

8 つの手順

2 BIFreferences.json、connections.json の bif組織間の投射を調べ、文献と文献種別を記録

ROI の規則

新しいプロジェクトは、検査規則の水準（harnessRules）として 2 を持ちます。複製したプロジェクトは元の値を引き継ぎます。この規則のもとでは、HCD の依頼文の後ろに ROI の規則の指示書が付き、HCD の検査に次の規則が加わります。値を持たない古いプロジェクトの扱いは付録 C にまとめます。

規則内容
ROI 要素meta.json の roiElements[] に、要素ごとの名前（name）と、属する ROI 内部の UC かその Collection の Circuit ID（ucs[]）を書く。各要素には、ほかの要素が挙げていない ROI 内部の UC が最低 1 つ必要。たとえば 1 つの UC で VWFA と後部紡錘状回を兼ねない。すべての ROI 内部の UC はどれかの要素に属する
領域の数roi が挙げる領域の数は要素の数を超えない。括弧の外のコンマ・セミコロン・and・&・+ で区切って数え、左右を表す語だけのものは数えない
ROI の左右roiSide（both / left / right）と roiSideSource を書く。後者は、利用者の ROI か指示が左右を指定していれば user、それ以外は assumed。assumed なら both でなければならず、判断ログに両側である旨（"bilateral" など）を書く
左右と UCboth では、side facet を持つ ROI 内部の UC に反対側の対が要る（または facet を外す）。left / right では反対側の ROI 内部の UC を置かない。機能が側性化しているだけでは片側に限定しない
引用の使い回し警告だけ。同じ原文の引用（と同じ図、または図なし）が異なる回路の接続を支えている場合に記録する。エージェントには返さず、引用の照合の記録（quote_check.json の reused）と画面に出す

接続の根拠とインターフェース

BIF は文献が述べる組織間の投射で、Connection はその根拠を UC 同士の接続に対応させたものです。接続のレコード 1 行には文献を 1 本だけ対応させます。同じ投射を複数の論文で支える場合は、論文ごとに行を作ります。同じ送り手・受け手・文献の組は 1 回だけです。各行には、種、測定法、論文中の領域名、UC との包含関係、原文か図への参照を持たせます。

3.9 FRG

上からの分解と下からの解釈

FRG は、TLF を論理的に分解する作業と、HCD の回路が何を計算するかを読み取る作業を合わせたものです。どちらもエージェントが行う判断です。回路の形をなぞるだけにならないよう、エージェントは上からの分解を先に、UC や候補を見ずに考え、重複や過剰な分解を整理します。

一方でワーカーは、HCD の ROI 内部の接続から対応づけの候補を計算し、FRG の依頼文の末尾に入れます。候補は HCD の検査のたびに作り直すので、FRG 段階で HCD が変わっても追従します。これはプログラムが機械的に列挙した候補で、意味づけはしていません。

候補内容
経路（pathways）外から入力を受ける ROI の UC から、外へ出力する UC までの道筋。強連結のまとまり（ループは 1 つのまとまり）の上で、できるだけ多くのまとまりを覆うように貪欲に選ぶ（最大 12）。両端に外部の入力と出力を付ける
連結成分（components）ROI 内部のグラフの弱連結な部分
モチーフ（motifs）ペアでは表せない 3〜4 UC の形。ループ（すべての UC を通る有向閉路）と、フィードフォワードの三角形（A → B → C かつ A → C）。最大 40。鎖・収束・発散は UC を共有するペアで表せるので除く
ペア（pairs）接続のあるすべての組（pair / reciprocal）

すべての接続には符号（興奮・抑制・修飾）を付けます。符号は接続のコメントから、コメントになければ送り手の伝達物質から決めます。エージェントはそれぞれの候補を、Output Semantics、機能項目、符号、文献に照らして解釈します。

8 つの手順

  1. 上からの分解：UC や候補を見ずに TLF を分解します（子の数は決めません）。
  2. 最適化：重複や過剰な分解を整理します。
  3. 下からの読み取り：各経路・モチーフが何を計算するかを読みます。すべての ROI の UC を最低 1 回読みます。
  4. 対応づけ：結果をレポートの ## FRG に表で残します。列は sub-function (GN ID) / candidate (IDs and UCs) / outcome / action です。
  5. 接地：GN の規則（後述）を守って UC に結びつけます。対応がなければ、機能の分解を直すか、根拠をもって HCD に戻ります。
  6. インターフェース：子のインターフェースを合わせ、GN の内部で閉じる辺を除きます。上へ合成し、TLF 全体では ROI の外部入力と外部出力になるようにします。
  7. 機能の詳細：Requirement、Requirement realization、Capability、Mechanism を書きます。
  8. レポートを書きます。
対応の結果意味取る対応
matched下位の回路が上位の副機能を実現するペア / モチーフを GN にし、上へまとめる
top-down only副機能に対応する候補がない上位の GN として残すか親へ統合する。文献のある不足は HCD へ追加する。ROI の外なら除外して限界に記録する
bottom-up only回路の候補に対応する副機能がない分解で漏れた機能を加えるか、別の GN で TLF に寄与する理由を書く
mismatch必要な UC 同士がつながっていないFRG の分解か、根拠のある HCD の接続を直す

制約を満たすための数合わせで、UC や接続を足すことはできません。仮説モードで許可範囲が認める場合については 3.12 で述べます。

GN が表すもの

GN の意味は、UC の機能を並べたものにとどまりません。GN は、UC と、その間の接続による相互作用が実現する計算を表します。GN が UC の機能に加えるのは、それらの相互作用、つまりインターフェースから除いた内部の辺が計算するものです。GN の Output Semantics は、GN の外へ出力する UC の値からワーカーが導きます。

新しいプロジェクト（検査規則の水準 2）では、GN に次の規則が適用されます。既存のプロジェクトの検査は、作成時の世代のまま変わりません。世代 1 以下のプロジェクトの GN の規則は付録 C にまとめます。

規則内容
GN の子の UC 数最大 2。3〜4 にできるのは、ペアに分けられない理由と引用を書いた注記（motifNote）があるときだけ。5 以上はエラー。子が 2 以下の GN に注記を書くのもエラー
GN の UC の連結エラー：GN の ROI 内部の UC が、それら同士の接続で（向きを無視して）連結していること
UC だけを子に持つ GN2 UC 以上。UC 1 つの言い換えにしない
UC の親の GN最大 2

FRG の基本の指示書には「最大 2 UC」という制約が書かれていますが、世代 2 では後ろに付く GN の規則の指示書がこれを置き換えます。3〜4 UC の注記は、FRG.csv の GN の Comments に Motif of 3 UCs: … として足します。

そのほかの FRG の規則は次のとおりです。

  • TLF の根が 1 つで、循環がなく、すべての GN に子があること。
  • ROI 内部の UC をすべて葉に含めること。外部の UC と Collection は葉にしません。
  • ID が実在し、構文が正しいこと。
  • 機能項目が書かれ、参照する ID が正しいこと。

グラフは HCD のループとフィードフォワードの三角形をモチーフとして持ち、HCD のタブで強調して表示します。

実装

候補の計算は findFrgCandidates、依頼文への整形は formatFrgCandidates で、結果は frg_candidates.json に書きます。接続の符号は classifyEdgeSign が決めます。FRG の検査は checkFrg、GN の規則の指示書は prompts/phases/FRG_gn_rules.md です。グラフのモチーフは buildGraphs が HcdGraph.motifs として出力します。

典拠：prompts/phases/FRG.md、FRG_gn_rules.md、packages/shared/src/motifs.ts（findFrgCandidates・formatFrgCandidates・classifyEdgeSign）、harness.ts（checkFrg）

3.10 検査と照合

ワーカーが確認できること

検査はワーカーのプログラムが行うもので、LLM による採点ではありません。スキーマ、ID、列の値、引用の形式、接続とインターフェースの対応は、プログラムによる機械的な検査です。文献は外部の書誌データベースと、引用は取得した原文と照合します。ただし、原文との対応を確認できたことと、その論文がこの神経科学的な主張を十分に支えることとは別です。後者には人の評価が必要です。各層で確認できないことは 3.16 にまとめます。

層主な確認
JSON Schema必須キー、型、列挙値、余分なキー（additionalProperties: false）
HCD / FRGID、参照、ROI の内外、Collection、interface、階層、ROI の規則と GN の規則（3.8・3.9）
SABRA記述子、略称、正式名、境界と左右（第 2 部）
BRA の値文献種別、種、測定法、式、原文・図番号、1 接続 1 文献（3.8）
文献の照合DOI / PMID を Crossref / PubMed と照合
引用文の照合引用が全文か要旨に存在するか
調査実際の検索ログと被覆の一致（3.7）
Canon固定した rev との、回路の定義と文献の衝突（第 5 部）
仮説許可範囲、主張、前提、比率、表示（3.12）
HCD と FRG の整合X 系の所見と調整（3.11）

検査に通らないとき

HCD・FRG・CSV の各段階では、ワーカーが問題を列挙し、エージェントに修正を依頼します。修正依頼は各段階で最大 3 回です。それでも問題が残る場合、データを読み込めない致命的な問題ならジョブを失敗にします。読み込める場合は、未解決の問題を警告として残して次の段階に進みます。HCD と FRG の調整のターン（3.11）の後の修正には、別に 3 回の枠があります。

文献の照合

HCD と FRG の検査のたびに文献も検査し、架空の論文や誤った識別子を、ほかの問題と同じ修正依頼でエージェントに返します。

  • 引用の検査：プログラムによる検査で、外部には問い合わせません。uc.json・connections.json・frg.json・report.md の自由な文章に書いた [Author, Year] は、すべて references.json の Reference ID でなければなりません。空白や大文字・小文字だけが違う場合は、正確に書くよう求めます。すべての文献は、レポートの ## References 以外のどこかで引用されている必要があります。2 つの Reference ID が同じ DOI / PMID を持つことはできません。
  • 照会：ネットワークを使う照合です。DOI は Crossref で照会し、Crossref になければ doi.org の内容交渉（CSL JSON。DataCite・mEDRA・JaLC）で照会します。PMID は PubMed（NCBI E-utilities の esummary）で照会します。
  • 一致の条件：次の 3 点を確認します。記録に Reference ID の筆頭著者がいること（後ろの著者ならそう報告します）。出版年が ±1 年以内であること（オンライン版と印刷版の差を考えるため）。タイトルがあれば、語の重なりで似ていること。DOI と PMID の両方があれば、PubMed の DOI が同じでなければなりません。雑誌の違いは注記だけにします。識別子のない文献は、Crossref の検索でタイトル・筆頭著者・年が同じ論文が見つかれば、その DOI を提案します。
  • 状態：照合の結果は、verified、mismatch、not_found、invalid（DOI / PMID の形でない）、no_identifier、unverified（照会に失敗）のいずれかです。mismatch・not_found・invalid と DOI の提案を問題として返します。段階が受理されたとき、画面に 1 行の要約を出します。
  • 受け持ち：FRG 段階は、frg.json と、レポートの ## FRG、そこだけで引用された文献を受け持ちます。それ以外は HCD 段階が受け持ち、HCD の問題を FRG 段階で重ねて送ることはしません。
  • 障害のとき：照会できなかった文献は unverified とし、問題にはしません。外部の障害で段階を止めないためです。結果は実行中キャッシュし、失敗したものは次の検査で再試行します。

引用文の照合

Pointers on literature は、引用した論文の逐語の引用でなければなりません（BRA の手動審査のコード 273 / 274 / 279）。HCD の検査のたびに、各接続に書いた原文の引用を、論文の本文と照合します。短すぎる、位置の表記で始まるなど、形式の規則にすでに違反している引用はその問題として扱い、ここでは照合しません。DOI も PMID もない文献は照合できません。

  • 本文の取得：Europe PMC の記録から、PMID・PMCID・オープンアクセスかどうか・要旨を得ます。オープンアクセスの論文は、Europe PMC の全文（JATS）を読み、失敗したら NCBI BioC 経由で PMC から読みます。全文には要旨・本文・付録・図の説明を含め、参考文献・引用の印・表・数式は除きます。全文がなければ、Europe PMC・PubMed・Crossref・Semantic Scholar の順に、最初に見つかった要旨を使います。
  • 正規化：引用と本文の両方を、文字と数字だけにそろえます。NFKC で正規化し、アクセントと大文字・小文字をそろえ、ソフトハイフン、上付きや角括弧の数字の引用、括弧の著者・年の引用を除きます。
  • 一致の判定：部分文字列として見つかるか、最もよく重なる語の窓との編集距離が文字数の 10% 以下（類似度 0.9 以上）であれば、見つかったとします。言い換えは通りません。省略（…・[…]）や編集上の挿入（[the VTA]）があればそこで分け、3 語以上の部分がすべて見つかる必要があります。
引用の状態意味扱い
verified_fulltext取得した全文で原文と一致全文との一致として記録
verified_abstract要旨で一致要旨との一致として記録
not_found全文を取得できたが、引用が見つからない全文のリンク、最良の類似度、最も近い箇所を付けて修正を依頼
unverifiedオープンアクセスの全文がなく要旨にもない、識別子がない、または取得できない未照合として残す。照合済みとは扱わない（有料の論文を問題にしない）

同じ引用と図を異なる回路の接続に使い回している場合は、警告として記録します（3.8）。図番号だけの根拠は、図の内容まで照合したことにはなりません。

実装

  • 段階ごとの修正の上限はワーカーの環境変数 MAX_NUDGES（既定 3）で決まります。致命的な問題と警告の扱いは runPhases の fatal と onWarn です。
  • 引用の検査は checkCitations、文献の照会はワーカーの ReferenceVerifier で、結果は reference_check.json に書きます。引用文の照合はワーカーの QuoteVerifier と packages/shared/src/quotes.ts で、結果は quote_check.json に書きます。一致のしきい値は QUOTE_MATCH_THRESHOLD です。
  • 文献の照会：1 要求のタイムアウトは 10 秒で、タイムアウト・ネットワークエラー・429・5xx のときは 2 回まで再試行します。Retry-After には 10 秒まで従います。3 件続けて失敗した相手は 5 分飛ばし、1 回の検査で照会に使う時間は最大 3 分です。PubMed への要求は毎秒 3 件（API キーがあれば 10 件）になるよう間を空けます。
  • 引用文の本文は、Europe PMC の search（resultType=core）で記録を得て、要旨は PubMed の efetch、Crossref の abstract からも取ります。要求は文献の照会と同じ HTTP クライアントを通り、1 回の検査で最大 2 分、同時に 3 本までです。各論文は実行ごとに 1 回だけ取得します。
  • 設定はワーカーの環境変数で、CDK では設定しません。どれもなくても動きます。
    • REFERENCE_LOOKUP=off：文献の照会を止めます。引用の検査は残ります。
    • CROSSREF_MAILTO：Crossref の polite pool に伝える連絡先です。
    • NCBI_API_KEY：PubMed の速度を上げます。Secrets Manager に保存し、ワーカーのコンテナの secrets に加えます。ワーカーはこの値をエージェントの Codex のプロセスからは隠します。
    • QUOTE_CHECK=off：引用文の照合を止めます。このとき quote_check.json は lookup: "off" になります。

典拠：packages/worker/src/pipeline.ts（runPhases：maxNudges・fatal・onWarn）、packages/worker/src/env.ts、packages/shared/src/harness.ts（checkCitations）、quotes.ts、packages/worker/src/references.ts・quotes.ts

3.11 HCD と FRG の調整

HCD と FRG は別々の段階で作りますが、両者は同じ回路を別の側から記述したものなので、食い違いが生じえます。FRG の指示書は、FRG と HCD が食い違うときに関連するファイルを直すようエージェントに求めます。そのため HCD のファイルは、HCD 段階が終わった後でも変わることがあります。ワーカーは、変わったファイルを検査し直す仕組みと、両者の整合を計算して 1 回だけ調整を依頼する仕組みを持ちます。

後の段階で変わったファイルの再検査

ワーカーは各段階の検査のたびに、その段階で検査したデータファイルのハッシュと、その時点で残っていた問題を記録します。対象のファイルは、HCD では meta.json・references.json・uc.json・connections.json、FRG では frg.json です。レポートと判断ログは毎段階変わるので対象にしません。

  • FRG と CSV の検査ではハッシュを比べ、変わっていないファイルは検査し直しません。
  • HCD のファイルが変わっていれば、HCD の検査をすべてやり直します。スキーマと規則、RCS、文献、引用が対象です。
  • FRG のファイルが変わっていれば、CSV 段階で FRG の検査をやり直します。
  • 前の段階が受理されたときにすでに残っていた問題は送り直しません。新しい問題だけを HCD (changed after the HCD phase was checked): を付けて、同じ修正依頼で返します。

HCD を直した後も古い検査結果のまま成果物を作る、という抜け道を防ぐためです。

整合の所見

FRG と CSV の検査のたびに、ワーカーは HCD と FRG の整合を計算して記録し、段階が受理されたときに画面に件数を出します。所見を出すのはプログラムで、どう直すかを決めるのはエージェントです。

コード所見現行の動作
X1GN の interface が、その ROI 内部の UC の HCD 接続にある、外からの入力・外への出力を取りこぼす調整の契機（severity：error）
X2接続から求めた ROI の入出力と、noROI(input) / noROI(output) の印が一致しない調整の契機（error）
X3GN の interface が、その UC のどの接続も与えない入出力を挙げる、または自分の UC を挙げる調整の契機（error）
X5ROI 内部の UC が、所属する GN の機能文に [U.<id>] で現れない記録（warning）
X6GN の Requirement realization が interface のすべての UC に触れていない記録（warning）
X8FRG が潰れている：TLF が UC だけを持つ、GN が 1 つ、または ROI 内部の UC が 3 未満調整の契機（warning）
X9ROI 内部の UC が、回レベルの BNA 群全体（facet のない BNAG:）か複数の SABRA 単位（&）で、粗すぎる可能性がある記録（warning。調整の契機にしない）

X4（GN の 2 つの UC が ROI 内部の接続で連結していない）は、新しいプロジェクトでは算出しません。世代 2 の規則では FRG の通常の検査がこれを確認するためです（3.9。世代 1 以下での扱いは付録 C）。X7 という所見はありません。X1・X3・X6 は、構文を解析できた GN の interface だけを見ます。所見の severity と、ジョブをすぐに止めるかどうかとは別のことです。

整合の記録には、次のものが入ります。

  • 所見の件数
  • 統計：ROI 内部の UC の数、GN の数、解析できた interface の数、FRG の深さ、3〜4 UC の GN の数とそのうち候補のループかフィードフォワードであるもの
  • 判断ログの revisions の行と、調整の記録
  • 仮説モードでは、仮説の情報（3.12）

調整のターン

FRG 段階が終わったとき、受理か警告付きかにかかわらず、X1・X2・X3・X8 の所見があれば、ワーカーは実行ごとに 1 回だけ調整のターンを送ります。依頼文には、所見と各検査の意味、FRG の候補、証拠に基づいてどちらを直すかを決めるようにという指示が入ります。

  • HCD が正しければ、エージェントは FRG を直します。
  • 細かい集団や欠けた投射の根拠があれば、HCD の UC を分けるか足します。粗い単位は Collection にし、新しい UC と接続には文献を付けます。
  • 直さないと判断した場合も、その理由を残します。

変わった HCD は、上に述べたとおり検査し直されます。調整のターンの後には、別に 3 回の修正の枠があります。ほかの所見は記録するだけです。

調整の記録の書式

調整で何を変え、何を残したかは、判断ログの ## HCD-FRG revisions の節に 1 行ずつ書きます。行の先頭の印で、どちらの側の理由による変更かを区別します。調整の後にこの節がなければ、FRG の検査が節を書くよう求めます。

## HCD-FRG revisions
- [FRG->HCD] <HCD の変更> — <FRG が必要とした理由> [Author, Year]
- [HCD->FRG] <FRG の変更> — <HCD に合わせる理由>
- [instruction] <変更> — <利用者の指示と根拠>
- [kept] <残した食い違い> — <変更しない理由>

実装

ハッシュは SHA-256 で、phaseDataHash が計算して phase_baseline.json に記録します。整合の計算は checkCross（規則は CROSS_RULES、調整の契機は ADJUSTMENT_CODES）で、結果は cross_check.json に書き、所見の件数は summary に入ります。調整の依頼文は adjustmentPrompt が作ります。scripts/cross-check-artifacts.mjs は、S3 からコピーしたプロジェクトフォルダに対して同じ検査を読み取りだけで実行します。

典拠：packages/shared/src/cross.ts（checkCross・CROSS_RULES・ADJUSTMENT_CODES）、packages/worker/src/pipeline.ts（phaseDataHash・adjustmentPrompt）、scripts/cross-check-artifacts.mjs
