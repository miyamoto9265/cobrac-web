# 仕様書の生成元

`docs/CoBRAC_仕様書.pdf` は、このディレクトリの HTML から作ります。サイトの「仕様書」（管理者だけ）はこの PDF を表示します。

## ファイル

| ファイル | 役割 |
|---|---|
| `src/*.html` | 本文。ファイル名の順に連結する。`00_cover` が表紙、`01_intro` が序章、`10`〜`90` が第 1〜9 部（1 つの部が複数のファイルに分かれることがある）、`91`〜`95` が付録 A〜E |
| `src/style.css` | A4 の版面、部ごとの色、表・囲み・図の書式 |
| `build.mjs` | Chromium（Playwright）で PDF にする。目次のページ番号は 2 回の描画で決める。`<figure data-figure="…">` に `docs/figures` の SVG を埋め込み、付録 B を `prompts/` から作る |
| `inputs.mjs` | 入力ファイル（本文、取り込む図、指示書、差し込み値を読むコード）の一覧と、そのハッシュ |
| `build.json` | 最後に作った PDF の入力のハッシュ・ページ数・バイト数 |
| `fetch-fonts.sh` | 本文のフォント（Noto Sans JP、JetBrains Mono）を npm のレジストリから `.fonts/` に取る（コミットしない） |

## 作り直しの手順

1. 挙動を変えたら、同じ変更の中で該当する節の HTML を直す。数値・上限・ファイル名はコードの定数を確認して書く。
2. 1 ファイルだけを確認するときは `node build.mjs --preview src/<ファイル>.html`（`out/preview-*.pdf`）。表紙と目次は付かない。
3. 全体を作り直す：リポジトリの直下で `npm run spec:build`（`./fetch-fonts.sh && node build.mjs`）。Playwright の Chromium、`pdftotext`、Python の `pypdf` が要る。目次のページ番号が本文と合わなければ失敗する。
4. `docs/CoBRAC_仕様書.pdf` と `docs/spec-guide/build.json` をコミットする。`npm test`（`scripts/spec-guide.test.mjs`）は、本文・取り込む図・指示書・差し込み値のコードが PDF を作った後に変わっていれば失敗する。指示書だけを直した場合も、付録 B が変わるので作り直す。
5. バージョンを上げた変更を main にマージすると、デプロイで API に同梱され、サイトの「仕様書」に出る。

## 構成

前半（序章と第 1〜7 部）は CoBRAC を使う人と BRA を読む人に向けて、何をどういう規則で作るかを書く。後半（第 8・9 部と付録）は開発と運用を担う人に向けて、それを実現する仕組みを書く。部は「概念 → 作り方 → まとめ方 → 基盤」の順に並べ、機能を追加した順には並べない。

- 本文には現行の仕様だけを書く。「v0.24.0 から」「以前は…」のような経緯は書かない。
- 古いプロジェクトのための分岐（設定の値がないときや古い形式のときの動き）は付録 C に書く。
- 変化の理由と経緯、一度きりの測定報告は付録 D に書く。バージョンごとの変更の一覧はリリースノート（`CHANGELOG.md`）に任せる。
- リリース・デプロイ・権限設定・緊急時の手順は仕様書に書かず、`docs/ops/README.md` に書く。
- 同じ事実は 1 か所にだけ書き、他の節からは「（4.3）」のように参照する。

## 書き方の約束

- 本文と箇条書きは「です・ます」。表のセルは常体か体言止め。1 つの節の中で混ぜない。
- 書き言葉で書く。書き手が主語に見える言い回し（「〜に書いています」「ここでは〜をまとめます」）は使わず、文書や節を主語にする（「本書は〜に基づいて記述されています」「〜は付録 C に記載しています」「本節では〜を扱います」）。「いま」は「現在」、文頭の「そして」は「また」「および」にする。
- 一般的な IT 用語を使い、和語に言い換えない（ツール、コピー、進捗、保存先、ローカルなど）。公開プロジェクトの機能名は「複製」。
- 担い手のラベル（「API（プログラム）が」「判断（人）」など）を本文に付けない。だれが何をするかは序章 0.2 と各部の冒頭で示し、本文では役割名だけを使う。LLM かどうかが要点になる場面では、文の中で普通に述べる。
- 直訳をしない（「決定的な検査」ではなく「プログラムによる検査」など）。
- 1 文は 120 字以内を目安にする。括弧は入れ子にせず、括弧の中に 2 文以上を入れない。長い列挙は箇条書きか表にする。「の」を 3 つ以上続けない。
- 見出しは名詞句にし、バージョン番号やコードの名前を入れない。
- 前半の部では、コードの名前を本文の主語にしない。必要なら節の最後に「実装」の段を置き、典拠の行に挙げる。
- 用語は序章 0.3 の用語集に合わせる。新しい用語は定義してから使う。
- 表記：ない、なし、付き、古い、だれ、サーバー、現在。バージョンは v0.42.0、日付は 2026-10-10。
- 節は `<h2 id="s<部>-<番号>">`（付録は `sa-1` など）で、番号を見出しに書く。目次は h1 と h2 から作る。
- 新しい図は `scripts/docs-figures*.mjs` で作って `data-figure` で取り込むか、HTML に SVG を直接書く。
