## 1. Purpose and scope

CoBRAC Agents is a web app that runs BRA (Brain Reference Architecture) data creation in the browser via the Codex SDK. The same work was previously done with Cursor Agents on the desktop.

**Input**: ROI (target brain region) and TLF (top-level function). Either field alone is enough (the agent researches and fills in the rest).

**Output**: HCD / FRG data as JSON files, a markdown report and decision log, five CSVs, `.bra.xlsx`, the same data in the official Template-v2-2.bra workbook (`.template-v2-2.bra.xlsx`), and HCD/FRG graph JSON.

**Out of scope for v1**: project sharing / co-editing, manual artifact editing in the web UI, billing plans, a mobile app, and a custom domain.

## 2. Glossary

| Term | Meaning |
| ---- | ------- |
| Project | One BRA creation unit. Identified by `projectId`: globally unique, assigned by the system, never changed or reused. New projects get a random ID, `p` + 7 lower-case Crockford base32 characters (e.g. `p7m2q9xa`); projects created earlier (from 0.7.0) keep their `<userKey>-<seq>` ID (e.g. `u7m2q9xa-12`), which stays valid. The ID says nothing about the creator or owner (that is the `userId` attribute). `name` is the editable display name (any language, 1–200 characters, may repeat) |
| userKey | Pseudonymous per-user key (`u` + 7 lower-case Crockford base32 characters) issued once on first sign-in. Shown as the owner of public projects and Canons; the prefix of the IDs issued before random IDs. It does not identify the current owner of those older IDs |
| Job | One worker run. Type is `initial` / `followup` / `article`. Resume mode is `resume` / `retry` |
| HCD | Hypothetical Component Graph. UCs (nodes) and Connections (edges) |
| FRG | Function Realization Graph. Hierarchy of TLF → GN (`R.`) → UC (`U.`) |
| Response loop | After the agent ends a turn with a question, the user answers and the job resumes |
| Follow-up | After completion, a job that sends a revision instruction on the same thread and regenerates artifacts |
| Explanatory article | Optional reading of a finished project in a language the user picks (`article/<locale>.md`). Not a core artifact (section 6.8) |
| Plan (BRA Planner, 「計画」) | A list of rows (ROI × TLF) that the system builds as projects, in waves, within the concurrency limits, after its owner confirms it. Identified by `planId` (`n` + 7 base32). Section 6.22 |
| Wave (波) | A group of rows of a plan. The next wave starts once no row of the current one waits to start or runs (section 6.22) |
| Seed wave (種の波) | The first 1–3 rows of an automatically ordered plan, the ones whose anchors most other rows share, each in its own wave so they are built one at a time before the other waves (section 6.22.1) |

## 3. System architecture

```
Browser (React SPA)
  ├─ Cognito SRP login (ID token)
  ├─ CloudFront + S3 (static hosting + /config.json)
  ├─ HTTP API (API Gateway JWT → Lambda / Hono)
  └─ WebSocket API (query token → subscribe project)

Lambda
  ├─ http        REST
  ├─ dispatcher  SQS → ECS RunTask
  ├─ ws          $connect / $disconnect / default
  ├─ broadcaster DynamoDB Streams → WebSocket
  ├─ janitor     liveness / timeout every 5 minutes
  └─ planRunner  BRA Planner: one step of every drafting, running or paused plan every minute

ECS Fargate Spot (1 vCPU / 2 GB)
  └─ Codex SDK worker (1 job = 1 task)
       ├─ DynamoDB (state and messages)
       ├─ S3 (workspace / thread / output / graph)
       ├─ KMS Decrypt (the user's own API key, or the default API key; section 4.1)
       └─ OpenAI API (the user's own key, or the default API key for approved users)
```

Package layout:

| Package | Role |
| ------- | ---- |
| `@cobrac/shared` | Types, CSV parser, `buildGraphs()`, Project ID / name rules (`projectId.ts`) |
| `@cobrac/api` | Hono app and Lambda handlers |
| `@cobrac/worker` | Codex control loop, S3 sync, xlsx / graph finalization |
| `@cobrac/web` | SPA (auth, chat, graphs, settings, admin) |
| `@cobrac/infra` | CDK stack `CobracAgents` |

## 4. Users and roles

| Role | How granted | Capabilities |
| ---- | ----------- | ------------ |
| user | Default after sign-up | Create / run / view / download own projects, register an API key, change settings |
| admin | Cognito group `admin`, or first API access with an email listed in `COBRAC_ADMIN_EMAILS` | Everything above, plus list all users, disable / change roles, register / replace / delete the default API key, approve users for it and set their tier, view all projects and default-API-key usage, force-stop running jobs |

- Accounts are email + password (Cognito). Self sign-up can be toggled with `COBRAC_SELF_SIGNUP`.
- Disabled users get 403 from the API.
- Admins also register and use their own OpenAI API keys.

### 4.1 Default API key (since 0.19)

Collaborators do not have to register an OpenAI key of their own: an admin can approve them to run jobs with the default API key, the organization's key.

- **The default API key** is registered, replaced and deleted on the admin page by any admin. It belongs to no user: it is stored in the Catalog table (`kind: "config"`, `id: "default-api-key"`) as KMS ciphertext under its own encryption context `{ purpose: "openai-api-key", scope: "default" }`, which has no `userId`, so no personal key's context opens it and it never opens a personal key. Registering checks the key with OpenAI `/v1/models` like a personal key and keeps the model list for Tier 2. It is write-only: the API returns only `{ registered, last4, updatedAt }`. No personal key is copied into it.
- **Approval and tier** (`Users.orgAccess = { tier, approvedAt, approvedBy }`, set on the admin page; absent or null = not approved). Existing and new users start unapproved. **Tier 1** may run `gpt-6-luna` and `gpt-5.6-luna` only (exact model IDs, `ORG_TIER1_MODELS` in `packages/shared/src/orgKey.ts`); **Tier 2** may run every model.
- **Precedence**: a user's own key always wins and is not tier-limited (the tier only applies to jobs that run with the default key). An approved user who later registers a key runs on their own key; deleting it goes back to the default key. An admin's personal key is used only for that admin's own jobs.
- **Enforcement**: the API resolves the key and the model of every request that starts a job (create, follow-up, retry, answer, explanatory article, including a model chosen for an article) and refuses with 400 (no key: neither an own key nor an approval with a registered default key) or 403 `このモデル（<model>）は利用できません` when the user explicitly picks a model the tier does not include. Models the user did not pick for this job are replaced by the tier's default (`gpt-6-luna`) instead of failing: their saved default model, the deployment default, the default given to a clone, and the model of a project made before (with their own key or another tier). A follow-up, retry or answer on such a project moves the project to the tier's default for good and posts the usual "Model: …" status line; an article without a chosen model runs on the tier's default and leaves the project's model alone. Saving a default model the tier excludes is refused. `/users/me/models` returns only the tier's models (`restricted: true`, no custom model ID); every model selector (create, settings default, article) lists only those, a saved default outside the tier shows as "default", and the project header shows the model its next job will run.
- **Wording**: non-admin users never see the word "Tier" or the tier number: the settings status, the model-menu note, tooltips, API errors and worker status lines say only "default API key" and "this model is not available". Tiers appear only on the admin page.
- **Revocation**: the worker checks again on every start (new job, answer, retry, restart after an interruption): no approval, no default key, or a model the tier excludes fails the job with a status message (`sys.noApiKey`, `sys.orgKeyUnavailable`, `sys.orgKeyModel`). A turn already running is not stopped. The worker may read only the `config` partition of the Catalog table (`dynamodb:GetItem` with a `dynamodb:LeadingKeys` condition).
- **Usage**: jobs record `keySource` (`own` / `org`, where `org` is the default key). `GET /admin/org-usage` sums the jobs with `keySource: "org"` per user (tokens, estimated cost, cost of the current UTC month, unpriced jobs) and the admin page shows it next to each user. There is no spending cap in the app; set a budget on the OpenAI project of the default key.
- **Exposure**: the key is never returned by the API, never logged, and kept out of agent commands (`shell_environment_policy` excludes `CODEX_API_KEY` / `OPENAI_API_KEY`). The agent runs with full access inside its own Fargate task as the same OS user as the Codex process, but the `node` / Codex / git binaries are execute-only, which makes those processes non-dumpable, so the agent cannot read the key from them through `/proc/<pid>/environ` (see security doc section 5). The agent still uses the key for its own job, so approve only trusted collaborators and use a project key with a budget.

**Agent panel** (named "Agent" rather than "Chat": it is the agent's run, which the user steers by answering its questions and by follow-up instructions, not an open conversation):

- The log reads like a coding agent's: the agent's answers are full-width markdown without bubbles or avatars; the user's prompts are quiet grey blocks labelled request / answer / follow-up (`meta.kind`); notices (queued, model, step done, files ready, usage, errors) are one-line rows with an icon and the time (full date on hover), green for finished steps and files, red for errors, expandable when they carry details.
- Thoughts and tool calls between two visible messages fold into one activity row ("Thinking & actions · 8 steps · 2m 18s · TODO 2/5") that opens the step list; each step opens to its full text, a running command shows a spinner and a failed one (non-zero exit code) is red. While the agent works, the last row is live: a spinner, a shimmering "Working" label, the elapsed time and the latest step, which slides in as steps arrive.
- The question the run waits on is an amber callout at the end of the log; numbered options in it ("1. …") become buttons that put the choice in the reply box. The "answer to resume" notice is hidden while the callout is shown.
- The composer at the bottom follows the project's state: answer the question (amber), follow-up instruction (completed), locked with a stop button (running), or locked with "Retry from here" (failed / cancelled). Enter sends and Shift+Enter adds a line on desktops (never while an IME is composing); on touch screens Enter adds a line and the round button sends. The box grows with the text. Explanations are in its "?".
- The log follows new items while the reader is at the bottom; scrolled up, a "N new" button jumps back. With `prefers-reduced-motion` the shimmer, slide-in, pulse and smooth scrolling are off (spinners stay as static icons).

**Theme**: light and dark. The default follows `prefers-color-scheme`; the sidebar (and the login card) has a system / light / dark switch that is stored per browser (`localStorage` `cobrac-theme`) and applied before the first paint by an inline script in `index.html`. Tailwind's colours point at CSS variables with separate sets for backgrounds, text and borders (`packages/web/theme-palette.js`), so `bg-white` becomes a dark surface while `text-white` on a filled button stays white; the sidebar is dark in both themes (`theme-static`). Graph fills and line colours are stored as light-theme values and mapped when drawn (`lib/graphTheme.ts`): fills become dark tints of the same hue with light labels, lines are lifted to stay readable on the dark canvas, and the style panel's swatches show the drawn colour. `test/theme.test.tsx` checks the contrast of the text / surface pairs the screens use, node labels on every default fill and swatch, and edges on the canvas. The documentation figures stay on a white card.

Screens keep short labels; explanations sit behind a "?" help tip (`HelpTip`: a focusable button whose tooltip opens on hover, keyboard focus or tap, closes on Escape or a tap elsewhere, and is linked with `aria-describedby`) or in the user guide `06_Research_mode_and_Canon.md` / `_ja.md`, which the create, Canon, pull request and public library screens link to ("Guide").

## 6. Workflow design

### 6.1 Steps

`(research) → HCD → FRG → (HCD ↔ FRG consistency check, one adjustment turn) → CSV → XLSX`

The worker (the "CoBRAC harness", v2 since app 0.13.0: the FRG can send the agent back to the HCD, see 6.13 and `docs/07_CoBRAC_Harness_v1_1_to_v2.md`; v1.1 was app 0.8.0–0.12.1, see `docs/05_CoBRAC_Harness_v1_to_v1_1.md`) drives the phases itself. A phase is marked done only when its deterministic validator accepts the files; file presence only marks it running. CSV and xlsx are produced by the worker, not the agent.

### 6.2 Job lifecycle

```
POST /projects
  → Projects/Jobs = QUEUED
  → SQS
  → dispatcher (re-queue after 60 seconds if at concurrency limit)
  → ECS RunTask (Spot, On-Demand on failure)
  → worker RUNNING
       ├─ status "question" → save to S3 → WAITING_USER_INPUT → task exits
       │     └─ POST /answer → QUEUED → resumeThread
       ├─ HCD ✓ → FRG ✓ → CSV (from the JSON files) → FINALIZING → csv_to_excel.py + Template-v2-2 export + buildGraphs → COMPLETED
       │     └─ POST /followup → new job (same thread)
       └─ failure / Spot interruption / >6h → FAILED (janitor auto-retries up to 2 times)
             Spot interruption: SIGTERM → save workspace + thread to S3 (120 s stop timeout) → heartbeat marked stale → janitor retries
```

### 6.3 Execution modes

| mode | Trigger | Prompt notes |
| ---- | ------- | ------------ |
| initial | New project | Phase HCD prompt (inlines `prompts/phases/HCD.md`); in research mode the research step comes first (section 6.11) |
| resume | Answer to a question | Pass the answer and continue the current phase |
| followup | Instruction after completion | Apply the instruction, then re-validate HCD and FRG and regenerate CSV/xlsx |
| retry | Manual resume after failure/cancel, or janitor auto-resume | Continue from the first phase not accepted yet; keep existing artifacts |
| article | `POST /articles` on finished BRA data (janitor re-runs a stalled one in the same mode) | Fresh thread, `prompts/article.md`, no web search or RCS; the workspace is read-only (section 6.8) |
| plan | A BRA Planner draft or re-plan (`planJobKind`), queued by the plan runner only when a slot is free; `projectId` is the plan ID and no project is touched (janitor fails a stalled one, never re-runs it) | Fresh thread, `prompts/plan.md` through `planJobPrompt`, RCS MCP but no web search and no `lit`, reply in `PLAN_RESULT_SCHEMA` (one retry with `PLAN_RETRY_PROMPT`), a 7-minute budget (25 minutes for a draft that reads xlsx / PDF lists or has more than 20 rows; section 6.22.1) |

Reply language: create / answer / follow-up / retry requests carry the web UI language (`locale`: `en` / `ja` / `zh` / `zhTw` / `ko` / `de` / `fr` / `es` / `pt` / `ru`), stored on the job. Every turn then ends with a hidden line telling the agent to write `message` and `question` in that language (artifacts stay English). Without `locale` the agent replies in the language the user wrote in; a retry without it keeps the previous job's language.

resume / followup / retry on a workspace made before v0.8 (markdown tables such as `3_UC.md`, no `uc.json`) fail at once with `sys.legacyWorkspace`; its xlsx and graphs stay viewable.

### 6.4 Turn control

1. Run one turn with Codex `runStreamed` (with `outputSchema`) and persist events to Messages.
2. If the final message has `status: "question"`, write state to S3 and exit (billing stops).
3. After each turn, validate the current phase (`checkHcd` / `checkFrg` in `packages/shared/src/harness.ts`): JSON Schema, cross-file references, UC naming, interfaces, FRG constraints, English-only values, and the report sections. The references are checked in the same step (`checkCitations` in `packages/shared/src/references.ts`, `ReferenceVerifier` in `packages/worker/src/references.ts`; see 6.7). On problems, send the list back as a fix prompt, up to `MAX_NUDGES` (3) times per phase. Fix turns run at reasoning effort `min(project effort, medium)` (`fixTurnEffort`): they only correct listed problems. If problems remain, continue with a warning; if the output is unusable, fail the job. The loop is `runPhases` in `packages/worker/src/pipeline.ts`.
4. When a phase is accepted, send the next phase prompt. A later phase whose files already pass (for example after a follow-up) is not rebuilt. When the agent changes HCD files during FRG or CSV (or FRG files during CSV), the later phase validates them again and sends back their new problems with its own (6.13).
5. CSV: `buildCsvs` generates the five CSVs deterministically from the JSON files. The agent never writes CSVs; if generation fails, the problems go back as a fix prompt for the JSON files.
6. Cut off after 6 hours of continuous execution.

Projects created earlier have no field and keep the earlier rule, so their stored BNA anchors stay valid; clones copy the original's field. The ROI hints on the create screen offer neocortical BNA areas only. ### 6.7 Reference checks

Every HCD / FRG check also checks the literature, so that invented papers and wrong identifiers go back to the agent in the same fix loop as the other problems.

- **Citations** (deterministic, `checkCitations`): every `[Author, Year]` in the free text of `uc.json`, `connections.json`, `frg.json` and `report.md` must be a Reference ID in `references.json` (a citation that differs only in spacing or case is asked to be written exactly); every reference must be cited somewhere other than the report's `## References` bibliography; two Reference IDs may not share a DOI or PMID. Unknown IDs in `sourceOfId` / `referenceIds` are still reported by `checkHcd`.
- **Lookups** (network, `ReferenceVerifier` in the worker): each DOI is looked up in Crossref (`api.crossref.org/works/<doi>`), and when Crossref does not know it, at doi.org by content negotiation (CSL JSON; DataCite, mEDRA, JaLC). Each PMID is looked up in PubMed (NCBI E-utilities `esummary`). The record must have the first author of the Reference ID (a later author is reported as such), a publication year within ±1 of it (online vs. print), and, when `title` is given, a similar title (word overlap). When both a DOI and a PMID are given, PubMed's DOI must be the same. A differing journal is only noted. For a reference without an identifier and with a title, a Crossref search that finds the same paper (title, first author, year) is suggested as its DOI.
- **Statuses** in `reference_check.json`: `verified`, `mismatch`, `not_found`, `invalid` (not a DOI / PMID), `no_identifier`, `unverified` (lookup failed). `mismatch`, `not_found`, `invalid` and a DOI suggestion are sent back as problems; like every other problem they become a warning after `MAX_NUDGES` fix turns. When a phase is accepted, the chat shows a one-line summary with the open references in its details.
- **Scope**: the FRG phase answers for `frg.json`, the report's `## FRG` section and the references cited only there; the HCD phase for everything else, so an HCD problem is not sent again during FRG. Only when the HCD data files change after the HCD check does the FRG / CSV phase run the HCD's reference and quote checks again (6.13).
- **Outages**: a request times out after 10 s and is retried twice on timeouts, network errors, 429 and 5xx (honouring `Retry-After` up to 10 s). A host that fails three references in a row is skipped for 5 minutes, and one check spends at most 3 minutes on lookups. References that could not be looked up are `unverified`, never a problem, so an outage does not hold up the phases. Found and missing identifiers are cached for the run; failures are retried at the next check. PubMed requests are spaced to 3 per second (10 with an API key).
- **Settings** (worker environment variables, not set by CDK): `REFERENCE_LOOKUP=off` turns the lookups off (the citation checks stay); `CROSSREF_MAILTO` sends a contact address to Crossref's polite pool; `NCBI_API_KEY` raises the PubMed rate. None is needed: Crossref, doi.org and E-utilities work without a key, and the worker reaches them through its public IP like OpenAI. To use an NCBI key, store it in Secrets Manager and add it to the worker container's `secrets` in `packages/infra/lib/cobrac-stack.ts` as `NCBI_API_KEY` (the task execution role needs `GetSecretValue` on it); the worker blanks it for the agent's Codex process.

**Quote checks** (manual review codes 273 / 274 / 279: Pointers on literature must be a verbatim quote from the cited paper). Every HCD check also compares each connection's `pointersOnLiterature` with the text of its paper (`QuoteVerifier` in the worker, matching in `packages/shared/src/quotes.ts`), so that invented or paraphrased quotes go back to the agent in the same fix loop. Quotes that already fail the format rules of 6.9 (too short, a locator) are left to those messages; references without a DOI or PMID cannot be checked.

- **Texts**, by DOI / PMID: the Europe PMC record (`search`, `resultType=core`) gives the PMID, PMCID, open-access flag and abstract. An open-access paper's full text is read from Europe PMC (`/<PMCID>/fullTextXML`, JATS: abstract, body, back matter and figure captions, without the reference list, citation markers, tables and formulas); when Europe PMC fails, from PMC through NCBI BioC (`pmcoa.cgi/BioC_json`). Without a full text, the first abstract found among Europe PMC, PubMed (`efetch`), Crossref (`abstract`) and Semantic Scholar is used.
- **Matching**: both sides are reduced to letters and digits (NFKC, so ligatures become letters; accents and case folded; soft hyphens, superscript and bracketed numeric citations and parenthesized author–year citations removed), so whitespace, punctuation, hyphenation across a line break, typographic quotes and citation markers do not matter. A quote is found when it is a substring, or else when the edit distance to the best passage (chosen among the word windows that share the most words with it) is at most 10 % of its letters (similarity ≥ `QUOTE_MATCH_THRESHOLD`, default 0.9), which absorbs OCR-like slips but not paraphrases. A quote with omissions (`…`, `...`, `[…]`) or editorial insertions (`[the VTA]`) is split there and every part of 3 or more words must be found.
- **Statuses** in `quote_check.json` (one entry per checked connection): `verified_fulltext`, `verified_abstract`, `not_found` (the full text was read and the quote is not in it), `unverified` (no open-access full text and the abstract does not have it, no identifier, or the texts could not be fetched). Only `not_found` is sent back, with the full-text link, the best similarity and the closest passage; a paywalled paper is never reported as a problem because its body cannot be read. The report also has `threshold`, `summary` and `problems`. When the HCD is accepted, the chat shows a one-line summary with the open quotes in its details.
- **Limits**: the same HTTP client as the reference lookups (10 s timeout, retries, 5-minute host cooldown, NCBI spacing); at most 2 minutes per check and 3 papers at a time. Each paper is fetched once per run (papers whose fetch failed are tried again at the next check). Semantic Scholar is used without a key and often answers 429; it is only the last abstract source.
- **Settings**: `QUOTE_CHECK=off` turns the check off (`quote_check.json` then has `lookup: "off"`); `QUOTE_MATCH_THRESHOLD` (0–1) changes the similarity. No key is needed; `CROSSREF_MAILTO` and `NCBI_API_KEY` apply as for the references.

### 6.8 Explanatory articles

The v0 HCD beginner explainer (`7_EasyToUnderstand.md`, removed in 0.5.0) comes back as an on-demand job instead of a phase:

- **When**: only when the project is `COMPLETED` with the xlsx generated (`stepStates.XLSX = done`) and no job is active. The user picks the language (default: the UI language; the 10 UI locales of `packages/shared/src/locale.ts`) and the model (default: the project's model; otherwise one of the GPT-5.6 / GPT-6 models of the registered key, the same list as the model menus, `filterCodexModels`; with the default API key only the models of the user's tier, and when the project's model is outside the tier the default is the tier's model) and presses "Create article". Several languages can exist side by side; creating one again replaces it only when the new one passes the check.
- **Job**: `type: "article"`, `articleLocale`, `model` (the chosen model or null for the project's), run mode `article`. The project goes `QUEUED → RUNNING → COMPLETED` so that follow-ups wait for it, but its steps, `revision`, `completedAt`, codex thread and workspace are not changed. A failure or cancel sets `articleJob.status` (`FAILED` / `CANCELLED`) and puts the project back to `COMPLETED`, never `FAILED`. Retry of a failed project ignores article jobs.
- **Format** (since 0.19.3): the article follows the documentation explainers (`docs/04_…`–`09_…`): a `#` title with a subtitle, a summary table (document, readers, data, related), numbered `##` sections separated by `---` (in short, terms, region and function, circuits and connections, FRG decomposition, which connections serve which function, certainty and open questions, where the data is), tables for listable facts, figures with numbered captions, and links between sections by heading anchor. The prose is plain and explanatory; Japanese is in 敬体. Contrast tables are used only where the data has two things to compare.
- **Figures**: the worker draws three figures from the workspace CSVs (`buildGraphs`, the same data as the graphs) with `buildArticleFigures` (`packages/shared/src/articleFigures.ts`): `circuit` (every circuit and connection: inputs, the ROI in layers along the forward connections, outputs; arrow colour and head by sign as in the graph viewer), `frg` (the TLF → GN → UC tree with each GN's comment) and `function-map` (per GN with UCs under it, every connection touching its UCs marked within / in / out). Each comes as `<name>.svg` (at most 980 px wide; wider circuits switch to rows) and `<name>.narrow.svg` (430 px, one column), with Japanese labels for `ja` and English otherwise; only nodes and connections of the data are drawn. The agent may add up to 2 SVGs of its own under `{P}/article/figures/` when the three cannot show a point. Every SVG goes through `sanitizeSvg` (`svgSanitize.ts`, an allow list of drawing elements and presentation attributes; scripts, styles, links, images, foreign content and event handlers are dropped) in the worker and again in the browser, which shows it through an object URL in `<img>` and shows the narrow version when the article column is narrower than 640 px (phones, or next to the Agent panel).
- **Worker**: restores the workspace (not the thread), draws the figures, starts a fresh thread without web search or RCS, and sends `prompts/article.md` with the figure list and the facts of the summary table. The agent writes `{P}/article/<locale>.md` locally; the workspace is never uploaded in this mode. `checkArticle` (`packages/shared/src/article.ts`) requires one `#` title, the summary table after it, at least 5 `##` sections, a minimum length, the requested script, each worker figure embedded once as `./figures/<name>.svg` with alt text and caption (no other images), no HTML / hand-written reference list, **arrows between Circuit IDs (`` `A` → `B` ``) only for connections of `connections.json`**, GN IDs that exist, section links that match a heading, and **citations only of `references.json` IDs** (`[Author, Year]`, one per bracket). Problems go back as fix prompts up to `MAX_NUDGES` times, then the job fails. The worker appends the reference list (localized heading, DOI links of the cited IDs) and uploads the embedded figures to `article/<locale>/figures/` (replacing the previous set), then `article/<locale>.md` and `article/<locale>.json`.
- **Metadata** (`ArticleMeta`): `locale`, `language`, `title`, `createdAt`, `sourceRevision` (project `revision` at start), `jobId`, `model`, `citedReferences`, `figures` (files under `article/<locale>/figures/`; absent in articles written before 0.19.3, which have no images and render as before). An article is **stale** when `sourceRevision` differs from the current `revision` (a later follow-up); the viewer says so and offers to recreate it.
- **Language rule**: articles are not core artifacts. The English-only checks (`readJson` in `harness.ts`, `buildCsvs`) and the CSV / xlsx / graph conversion never read them; `AGENTS.md` names them as the only exception to "every artifact in English".
- **Cost**: the job's tokens are added to the project usage like any other job.

| Terminology | `names` of an anchor-only UC must start with its SABRA official name (BNA area name, or the DHBA name from RCS `get_homba_term`; skipped when RCS could not be asked), synonyms after `;`. `[U.<id>]` / `[R.<id>]` in function items, comments and FRG details must name existing UCs / nodes | `sabraOfficialName`, `checkHcd`, `checkFrg` |

| Review End Line | `Project.csv` gets the sheet row of the last record of References / Circuits / Connections / FRG (header = row 1, so `1` when a sheet is empty); the xlsx writes them as numbers | `buildProjectCsv` |
| Hypothesis marking (`cobrac:hypothesis-marked`; hypothesis mode only, 6.23) | Measurement method `Hypothetical` exactly on the connections with an existence hypothesis (an existence hypothesis without it, and `Hypothetical` without one, go back); the Comments of a hypothesis connection or UC start with `Hypothesis (<claims>; <basis>): <rationale>`. 274 is judged on the premise. Projects that do not allow hypotheses keep `Hypothetical` as a plain enumeration value | `hypothesisProblems`, `buildCsvs`, `scripts/bra-appendix-d.mjs` |

- **`BNA` as Source of ID** is a CoBRAC extension: the BRA enumeration has no value for SABRA's BNA side, and adding it has been requested upstream (pending). Until then the Review Tool may flag these rows as 108.
- **Compatibility**: the BRA version in `Project.csv` becomes `CoBRAC-v1-1`. Column changes are appends only — References gains C Literature type and D Alternative URL; `Circuits.csv` gains Sub-Circuits and Uniform after UC Descriptor, and `Connections.csv` the two relations and notations after Pointers on figure (the xlsx already had all of these columns — Circuits D / F, Connections B / C / E / F — and now fills them from the CSV) — so every v1-0 column keeps its position. Value changes: Source of ID holds one value (`BNA` added), Connections has one row per reference and real relations / notations, the Circuits sheet has the ROI row first, FRG GN rows have Output Semantics, and Project has Review End Lines. The graph builder reads v1-0 and v1-1 CSVs alike (columns by name).
- **Older projects** (files written by 0.9 or earlier): the next follow-up validates them like any other files, so the problems above come back as fix turns (a Source of ID list, several references per connection, missing Literature type or relations, locators as pointers, values outside the lists). Until they are fixed, the CSVs are still built: a Source of ID list keeps its first value, a connection with several references becomes one Connections row per reference, and a connection without relations keeps `=` and the Circuit ID.
- The xlsx Capability&Mechanism cell is the Capability, the template's default tag `<<mechanism to realize the capability>>` and the Mechanism; the earlier CoBRAC-only tag `<<mechanism realized by grainest coding scheme>>` (not in the template or manual) is no longer written.
- Not covered yet (decisions pending): granularity rules for UCs (e.g. neocortical senders by layer / cell type) and the allowed characters of Circuit IDs. Quotes are checked against the paper's text (6.7); quotes from papers without open-access full text can only be checked against the abstract. The Template-v2-2 column layout is produced as a second workbook (6.12).

### 6.10 Collection Circuits (Uniform / Collection)

Whether a circuit is Uniform is decided **per HCD**: a circuit is a UC when it is a leaf of that HCD and a Collection (Uniform = FALSE) when the HCD decomposes it into Sub-Circuits. The UC Descriptor stays the cross-project key and carries no uniformity, so the same area may be a UC in a coarse project and a Collection in a fine one. A whole SABRA unit as a UC remains a project choice.

- **Data**: `uc.json` keeps `ucs` (always Uniform) and gains an optional `collections` array (`circuitId`, `descriptor` — the SABRA unit or faceted population, empty for a grouping of several units —, `names`, `sourceOfId`, `subCircuits`, `comments` — why the region is heterogeneous, required). Files without it stay valid. A UC may carry an optional `uniformityNote`, which `Circuits.csv` appends to its Comments as `Uniform in this project: …`. Collections have no Interface, Output Semantics or function items.
- **When** (`prompts/phases/HCD.md` step 3; loosened after the 0.11 rerun of the language project made no Collection for lack of layer / cell-type evidence): a region is split when it is anatomically or functionally heterogeneous at the chosen granularity — a gyrus or group of several distinct areas, parts reported as different projection sources or targets, parts with different roles in the literature. Areas or other named parts are enough; layer or cell-type evidence is not required. The parts are named by the UC naming rules and the split is justified (the Collection's `comments` is required). A parent Collection for a split region is recommended, not required; a higher grouping (a named network) only when it helps the reader. A region kept whole is a project choice, but a sender that spans several SABRA units needs `uniformityNote` (below).
- **Checks** (`checkHcd`, `checkFrg`; the codes are those of the BRA data Error code List (Master); `cobrac:` codes are CoBRAC checks with no Master code. Earlier versions cited the ontology appendix D numbers 128, 129 and 205 here, and 127 / 108 for checks those codes do not cover; see 6.9 and `scripts/bra-appendix-d.mjs` for the mapping):

  | Check | Error / code |
  | ----- | ------------ |
  | `subCircuits` has at least one item (schema), each a UC or Collection of `uc.json`, not the Collection itself, no cycle through Collections, not every member `makeshift` (manual) | 120 (at least one), 121 (members defined); `cobrac:collection-members` (itself, cycles, all `makeshift`) |
  | UCs have no Sub-Circuits (by construction: only `collections` have the key) | `cobrac:uc-no-sub-circuits` |
  | A Collection is neither sender nor receiver of a connection in this HCD; the feedback lists its UCs. The ontology lets a Receiver be a Collection; CoBRAC is stricter so interfaces stay UC-to-UC. Evidence reported for the whole unit is cited on the UC connection with relation `<` and the paper's notation (6.9) | 203 (Sender); `cobrac:collection-end` (Receiver, stricter than the Master) |
  | A UC and a finer UC inside it cannot both be UCs: the same anchors with a subset of its facet values, or an anchor-only UC whose anchors contain the other's (a BNA area of a `BNAG` group on the same side, one side of a left-right pair, one of several `&` anchors). The coarser one has to move to `collections` | `cobrac:nested-uc` |
  | A sender whose descriptor spans several SABRA units (a `BNAG` group or several anchors, no facets) needs `uniformityNote`; otherwise the feedback asks to split it into its parts (no layer / cell-type evidence needed; relation `<` for papers that report the whole region) or to justify it. Single areas, left-right pairs, faceted UCs and receivers only are not flagged | 203 |
  | Collection IDs share the ID space of UCs, may not start with `ROI_`, and follow the UC naming rules when they have a descriptor (descriptor unique across UCs and Collections) | — |
  | Source of ID of a Collection is always `collection` (a Collection is defined by its Sub-Circuits; `DHBA` / `BNA` / Reference IDs are for UCs) | `cobrac:collection-source` |
  | `[U.<Collection>]` is allowed only in `comments`; FRG subnodes and function texts must name UCs | — |

- **Output**: `Circuits.csv` writes each Collection after the ROI row with Uniform `FALSE` and Sub-Circuits joined by `;`; UCs keep Uniform `TRUE` and empty Sub-Circuits. **FRG**: Collections are not FRG nodes (the FRG's leaves and Projected Circuits are UCs), so `FRG.csv` has no row for them. The graph builder turns Uniform `FALSE` rows (other than the ROI row) into `HcdGraph.collections` (with `members`, nested Collections expanded) instead of nodes; a Collection that is still an edge end in unchecked files stays a node.
- Not decided: how WholeBIF should merge Uniform values that differ between projects (upstream question U20).

### 6.11 Research mode (since 0.11)

A project setting chosen once on the create screen (a switch in the model menu, **on by default**; `researchMode` on the project, each job records the value it ran with). It cannot be changed after creation, and there is no per-user default. Follow-ups and retries inherit it; projects created before it existed have no field and run without it. Off skips the research step and the research notes (the `lit` tools stay available).

- **Research step** before phase HCD (not a new phase: HCD → FRG → CSV → xlsx is unchanged). The agent gets `prompts/phases/RESEARCH.md` and writes only `{P}/research.json` (schema `research.schema.json`, in `HARNESS_SCHEMAS`): a plan, up to 40 candidate tissue-level projections, for each the queries it ran, evidence items (Reference ID, PMID / DOI, taxon, method, layer / cell type, finding, abstract or full text read), coverage of tract tracing / primate / rodent / layer-cell type (`found` / `searched_none` / `not_applicable`), a status (`supported` / `weak` / `not_found` / `contradicted`), and the remaining gaps.
- **Tools**: a `lit` stdio MCP server (`packages/worker/src/litMcp.ts`, `litsearch.ts`; started in **every** BRA run, with or without research mode, since it also serves PMIDs and verbatim quotes) with `search_pubmed`, `search_europepmc`, `get_abstract`, `find_sentences` (up to 8 sentences of the open-access full text, else the abstract, that contain given terms; searches return 8 hits unless `max_results` says otherwise). Requests go through the literature HTTP client of the checks (`http.ts`: 15 s timeout, 3 retries with 1 / 2 / 4 s backoff on timeouts, network errors, 429 and 5xx, honouring `Retry-After`; a host that fails 3 calls in a row is skipped for 5 min) and their starts are spaced per provider even when the agent calls tools in parallel (Europe PMC 200 ms, NCBI 350 ms). One call has 65 s (below the MCP tool timeout of 90 s). When Europe PMC does not answer within 45 % of that, `get_abstract` and `find_sentences` take the record from PubMed (`esearch` for a DOI / PMCID, `esummary`, `efetch` for the abstract) and the full text from PMC through NCBI BioC; the full text is also tried for author manuscripts Europe PMC shows (`inEPMC`), and through BioC when Europe PMC's `fullTextXML` fails. The result then carries a `note` naming the service that failed. A tool that still fails returns an error naming every failed service and an alternative (`search_pubmed` ↔ `search_europepmc`). Web search stays on. The worker logs every lit call and web search from the event stream to `{P}/research_queries.jsonl` (with job ID and step, and for a failed call the tool's error text), and counts them per tool on the job (`searches`). `npm run test:live -w @cobrac/worker` runs the tools against the real services.
- **Coverage check** (`checkResearch` in `packages/shared/src/research.ts`): schema; at least 2 distinct queries per candidate with at least one in PubMed / Europe PMC; every listed query must be in the search log under the matching tool; coverage values must agree with the evidence (`found` needs an evidence item with a tracing method / primate taxon / rodent taxon / layer-cell type); supported / weak / contradicted need evidence, not_found none; every evidence item needs a PMID or DOI; a note for anything not supported or not applicable. Problems go back as up to 2 fix turns. Gaps never block the run; the result goes to `{P}/research_check.json` (`done`, `outcome`: `passed` / `gaps` / `budget`, summary, problems), and a workspace with `done: true` skips the step on later runs.
- **Metrics** (for checking real runs): when the step ends, `research_check.json` `metrics` and the job's `researchStep` hold outcome, model, effort, start / end, minutes, turns, whether a turn was cut off, spend and token usage of the step, candidates, supported, and searches by tool (ok / failed); the chat shows a summary line with the full metrics in its details, and CloudWatch gets `[research] start` / `[research] end {…}` lines. Every job also logs `[metrics] {…}` (usage, cost, minutes, searches by tool) at exit. There is no USD cap; cost is bounded by the time budget and shown in the usage lines.
- **Budget**: 60 minutes of wall clock for the whole step (`RESEARCH_TIME_BUDGET_MIN`); a turn still running then is aborted and the HCD starts with what was written (the usage of an aborted turn is not reported by Codex and is missing from the job's total). A fix turn starts only with at least 10 minutes left. The survey turn runs at reasoning effort `max(project effort, high)`; its coverage fix turns, like every fix turn, at `min(project effort, medium)` (`fixTurnEffort`).
- **Later phases**: `prompts/research_mode.md` is appended to the HCD / FRG specs and to follow-ups: build the BIF and connections from the survey (prefer supported and tract-tracing evidence, flag weak ones, define cell-type / layer UCs where the evidence supports it, quote from sentences actually read, put the gaps into the limitations), search for computational models in the FRG, research new claims in follow-ups. The HCD / FRG validators are the same with or without research mode.
- **Estimate** (`researchModeEstimate`): shown next to the toggle, +10–60 minutes and the cost of 1.5–6M input tokens (85–90% cached) and 40–150k output tokens at the selected model's price (for gpt-6-luna about $0.05–0.19, gpt-6-sol about $1.1–3.8). It is a rough figure from the few completed runs; the usage line of each job is the real value.

### 6.12 Template-v2-2.bra export

Next to CoBRAC's own xlsx, every job writes the same data into the official template of the BRA Data Preparation Manual, `prompts/templates/Template-v2-2.bra.xlsx` (the Google Sheets template downloaded as xlsx), as `output/{P}.template-v2-2.bra.xlsx` (`buildTemplateXlsx`, `packages/shared/src/braTemplate.ts`). The download is `{name}_{ID}.template-v2-2.bra.xlsx`.

- **The template is the base.** Its 11 sheets, header rows, formulas, AdminOnly lists, validation, conditional formats and the WholeBIF rows it imports (IMPORTRANGE results below the input area) are kept. The workbook is edited at the XML level (`xlsxSheet.ts`, fflate for the zip) because a spreadsheet library would drop Google's parts (custom sheet views, the `__xludf.DUMMYFUNCTION` wrappers Google uses to restore its own functions on upload). Only contributor-input cells are written; automatic and admin columns keep their formulas. For formula cells whose value CoBRAC knows (References A / G–J, Circuits AO) the value Excel shows is set to what Google Sheets computes; `fullCalcOnLoad` makes Excel recalculate the rest.
- **Rows.** The input areas are References 2–29, Circuits 2–31, Connections 2–80 and FRG 2–198. When a sheet needs more, rows are inserted above the WholeBIF import as a contributor would (copies of the last input row with their formulas); every reference to the rows below moves, also from other sheets and in validation ranges, filters, hyperlinks and defined names. A layout change of the template is detected (the IMPORTRANGE row) and fails the export.
- **Mapping.**

| Sheet | Written | Kept (formulas / admin) |
| ----- | ------- | ----------------------- |
| Project | A2 Contributor, B2 Project ID, C2 List of contributors, D2 Description, B5–B8 Review End Lines (sheet row of the last record) | E2 BRA version `Template-v2-2.bra` |
| References | D DOI (empty when N/A), E BibTeX, F Literature type, K Alternative URL (only without DOI), L Contributor, M Project ID | A Reference ID, B / C links, G–J type / authors / title / journal (from the BibTeX), N–W |

Connections I, Circuits B (`[Schultz, 1997]`) and the citations in the free text that is written (comments, FRG texts, Output Semantics) use the same IDs.
- **BibTeX** is written one field per line with spaces around `=`, as the template's regular expressions expect. At the end of a job the worker looks up each DOI in Crossref and each PMID-only reference in PubMed (`bibliography.ts`, 10 s per request, 60 s in total, failures retried by the next job; off with `REFERENCE_LOOKUP=off`) and keeps the records in `{P}_CSV/bibliography.json`. A UC anchored on one DHBA term (by its acronym, the Circuit ID head) gets that row; a UC finer than a DHBA term gets the term's graph_order plus a decimal (manual: "add a decimal number to DHBA: graph_order"); circuits anchored on BNA, the ROI row and circuits without a UC Descriptor other than `DHBA` stay empty.

Any CoBRAC-v1-x CSV works (a Source of ID list keeps its first value, several references per connection become one row each, missing relations become `=` and the Circuit ID, a missing ROI row is added).

### 6.13 Re-validation of earlier phases and the HCD ↔ FRG consistency record

The FRG spec asks the agent to fix related files when the FRG and the HCD disagree, so HCD files may change after the HCD phase. Such changes are validated again, and the consistency of the two graphs is recorded. This is the first step toward letting the HCD and the FRG constrain each other.

- **Baselines** (`{P}/phase_baseline.json`, worker only): each HCD / FRG check stores a SHA-256 of that phase's data files (HCD: `meta.json`, `references.json`, `uc.json`, `connections.json`; FRG: `frg.json`; the report and the decision log change in every phase and are left out) and the problems left at that point.
- **Re-validation**: the FRG and CSV checks compare the hash. Unchanged files are not checked again. Changed HCD files get the full HCD check (schema and rules, RCS, references, quotes); changed FRG files the full FRG check in the CSV phase. Problems that were already left when that phase was accepted (with a warning after `MAX_NUDGES`) are not sent again; new ones go back in the same fix prompt, prefixed `HCD (changed after the HCD phase was checked):`. The CSV phase still writes the CSVs, so a run that ends with warnings has them. A workspace without a baseline (checked before this version) takes its current state as the baseline.
- **Consistency record** (`{P}/cross_check.json`, worker only, `checkCross` in `packages/shared/src/cross.ts`): written by every FRG and CSV check, **record-only**: nothing is sent to the agent, and the chat shows the counts when FRG and CSV are accepted. `rules` gives the intended severity of each check for when it is enforced:

| Code | Check | Intended severity |
| ---- | ----- | ----------------- |
| X1 | A GN interface leaves out a flow that the HCD connections of its ROI-internal UCs have (inputs from / outputs to circuits outside the GN) | error |
| X2 | The ROI inputs / outputs derived from the connections differ from the `noROI(input)` / `noROI(output)` tags (a tagged UC with no path to or from the ROI, or an untagged UC that connects to it) | error |
| X3 | A GN interface claims an input or output that no connection of its UCs provides, or lists one of its own UCs | error |
| X4 | The two UCs of a GN are not connected through ROI-internal connections (harness rules below 2 only; from 2 the FRG check enforces it, 6.13.1) | warning |
| X5 | A ROI-internal UC is not mentioned (`[U.<id>]`) in the function text of any GN it is attached to | warning |
| X6 | A GN's `requirementRealization` does not mention every UC of its interface | warning |
| X8 | The FRG is collapsed: the TLF has only UCs, there is a single GN, or the HCD has fewer than 3 ROI-internal UCs | warning |
| X9 | A ROI-internal UC is a whole gyrus-level BNA group (`BNAG:` anchor without facets) or spans several SABRA units (`&`): its areas may carry different inputs, outputs or Output Semantics | warning (not an adjustment trigger) |

- **Adjustment turn** (since this version): when the FRG phase ends (accepted or with warnings) and the record has X1, X2, X3 or X8 findings, the worker sends **one** adjustment turn per run (`adjustmentPrompt`): the findings, what each check means, and the instruction to decide from the evidence which side changes. The FRG spec (step 5) lets the agent split or add HCD UCs (with the coarser unit as a Collection, and literature for new UCs and connections) instead of only decomposing the TLF more finely; changed HCD files are validated again as above. The agent records each change under `## HCD-FRG revisions` in `decision_log.md` as `[FRG->HCD]`, `[HCD->FRG]`, `[instruction]` (asked for by a user instruction) or `[kept]` lines; after the adjustment turn the FRG check asks for that section when it is missing. The turn gets its own `MAX_NUDGES` fix turns, and the other findings stay record-only.
- The report also has `summary` (count per code), `stats` (ROI-internal UCs, GNs, parsed GN interfaces, FRG depth, GNs with 3–4 UCs and how many of them are a loop / feedforward motif of the candidates), `revisions` (tagged lines of the revisions section), once requested, `adjustment` (time, the counts and findings that triggered it, the revision counts before it) and, in hypothesis mode only (6.23), `hypotheses` (`count`, `evidenceOnlyPath`, `pathWithHypotheses`, `gns`; absent in other projects, so their record is unchanged). X1, X3 and X6 look only at GN interfaces that parse. `scripts/cross-check-artifacts.mjs` runs the same check on workspaces copied from S3 (read-only), including pre-0.8 workspaces through their CSVs (no GN interfaces there, so X1 / X3 / X6 are not measured).

### 6.13.1 FRG grounding: bottom-up candidates and GN rules (since 0.28.0)

A GN that holds UCs is realized by those UCs and the connections between them: what it adds to its UCs' own functions is what their interaction computes (the internal edges its interface removes). The FRG is built by meeting in the middle: a top-down decomposition of the TLF and a bottom-up reading of the circuit, made independently and then matched.

- **Candidates** (`findFrgCandidates` in `packages/shared/src/motifs.ts`; `{P}/frg_candidates.json`, worker only): every HCD check (in any phase) recomputes them from the ROI-internal connections of `connections.json`, so they follow HCD changes made during the FRG. They are:
  - **pathways**: ways from the ROI UCs that receive from outside to those that send outside, over the strongly connected blocks (a loop is one block), chosen greedily to cover as many blocks as possible (at most 12), with the outside inputs and outputs at both ends;
  - **components**: the weakly connected parts of the ROI-internal graph;
  - **motifs** of 3–4 UCs that pairs cannot express: loops (a directed cycle through all members) and feedforward triangles (A → B → C with A → C), at most 40; chains, convergences and divergences are left out because pairs sharing a UC express them;
  - **pairs**: every connected pair (`pair` or `reciprocal`).

  Every connection carries its sign (`classifyEdgeSign`: comment, then the sender's transmitter). The FRG phase prompt, its fix prompts that attach the spec, and the adjustment turn end with the candidates as text (`formatFrgCandidates`).
- **FRG spec** (`prompts/phases/FRG.md`): 1 top-down decomposition without looking at the UCs or the candidates (the number of children is not fixed), 2 optimization, 3 bottom-up reading (what each pathway / motif computes, every ROI UC at least once), 4 matching — matched / top-down only / bottom-up only / mismatch, each with its action — written as a table in the report's `## FRG`, 5 grounding with the constraints below (and the way back to the HCD), 6 interfaces, 7 function details, 8 report.
- The candidates, the eight-step spec and the motif highlight apply to every project. The **GN rules** (`checkFrg`) depend on the project's harness rules (6.6), so the checks of existing projects do not change:

| Rule | Harness rules 0–1 (projects created before 0.28.0) | Harness rules 2 (new projects from 0.28.0; `FRG_gn_rules.md`) |
| ---- | ------------- | ------------ |
| UC subnodes of a GN | at most 2 | at most 2; 3–4 only with `motifNote` (why the motif cannot be split into pairs, with citations); 5 or more is an error; `motifNote` on a GN with 2 or fewer UCs is an error |
| UCs of a GN connected | X4 warning (a path through any ROI UCs counted) | error: the ROI-internal UCs of a GN must be connected by connections among themselves (direction ignored) |
| GN with only UCs | exactly 2 UCs | at least 2 UCs |
| GN parents of a UC | at most 2 | unchanged |

  `motifNote` is added to the GN's Comments in `FRG.csv` (`Motif of 3 UCs: …`), like `uniformityNote` on Circuits. Below rule set 2 the check does not read it. The base spec `FRG.md` states the earlier constraints (a motif of 3–4 UCs becomes a GN over GNs of 2 UCs); `FRG_gn_rules.md` replaces them.
- **Graph**: `buildGraphs` adds `HcdGraph.motifs` (the loops and feedforward triangles of the graph, with the GNs whose UC subnodes are exactly those UCs) for the HCD tab's motif highlight (section 5).

### 6.14 Canons (since the Canon MVP, stage 1)

A **Canon** is a set of one user's projects whose circuit definitions must agree: within a Canon, the same UC Descriptor has the same Uniform / Collection status and the same decomposition, and cross-project connections keep Sender = Uniform. Uniformity is per HCD outside a Canon (6.10) and fixed inside one; different Canons may choose different granularity (a coarse network-level Canon next to a layer-level one). The name is provisional.

- **Stage 1 (this version)** is the container only: create, list, rename, edit the description and granularity policy, soft delete, and add / remove the owner's projects. A project is in at most one Canon (`Projects.canonId`); adding it to another returns 409. Every Canon is private and empty (`headRevision` 0).
- **IDs**: new Canons get a random ID, `c` + 7 lower-case Crockford base32 characters (e.g. `c4h8w2rk`), reserved like Project IDs (section 7.1). Canons created earlier keep their `<userKey>-c<seq>` ID (e.g. `u7m2q9xa-c1`, from the per-user counter `Users.canonSeq`, no longer advanced), which stays valid. Never changed or reused, and never matches the Project ID pattern.
- **Ownership**: only the owner sees and changes a Canon; other users get 404; admins may read. Deleting a Canon sets `deletedAt` and releases its projects (their `canonId` is cleared); its items stay. Soft-deleting a project removes it from its Canon.
- **Later stages** (design only): push a project into the Canon as a pull request with a diff and conflict check, approved by the owner (2); Canon-to-Canon pull requests (2′); project and Canon visibility and cloning public projects (1′); pulling a Canon revision as constraints for generation (3); choosing or seeding a Canon when creating a project (3′).

### 6.15 Public projects, public Canons and cloning (Canon MVP stage 1′)

- **Visibility**: a project or Canon is `private` (default) or `public`; only its owner switches it (`PUT /projects/{id}/visibility`, `PUT /canons/{id}/visibility`). A project can be published once it has artifacts and has a random or `<userKey>-<seq>` ID (not a legacy slug). Public items get a row in the **Catalog** table (`kind` = `project` / `canon`); the row is removed when the item is made private or deleted. Lists and reads always re-check the project or Canon itself.
- **Public library** (`/explore`): every signed-in user can list and read public projects (summary, circuit list, report) and public Canons (policy, revision, member count, public members). What is and is not shown is listed in `02_個人情報とセキュリティ.md` 4.2.
- **Clone** (`POST /public/projects/{id}/clone`): creates a new private project of the caller (new Project ID, `name` + " (clone)", the original Contributor, status COMPLETED, the original's `researchMode` and `sabraBoundary`, `clonedFrom` = original ID, revision, the owner's userKey and name) and copies the workspace (folder names and every whole-token occurrence of the old Project ID in text files are rewritten), graph JSON and articles with their figures. Not copied: thread, jobs, messages, usage, graph layouts, attached materials and the BRA xlsx outputs (they carry the old ID; XLSX is left pending so a follow-up rebuilds them). The original is only read; its clone count is a `clones` row in the Catalog table, shown to the owner on the project and in the library.
- **Pull requests to Canons** (used from stage 2′): a public Canon accepts pull requests from other users' Canons unless its owner turns `acceptPullRequests` off.

### 6.16 Pushing a project into a Canon and pull requests (Canon MVP stage 2)

- **Snapshot**: a Canon revision is one immutable JSON (`canons/{canonId}/rev/{n}/canon.json`) with a shared layer — circuits keyed by normalized UC Descriptor (Circuit ID, names, Uniform / Collection, Sub-Circuits, transmitter, modulation, Source of ID, Output Semantics), groupings without a descriptor (`group:<id>`), connections keyed by (sender, receiver, Reference ID) with their literature fields and quote-check status, BIF and references with their check status — and a role layer per project (ROI side, Interface, function items, FRG). Every entry keeps its origin (project, revision, PR) and the projects that pushed it. Revision 0 is the empty Canon.
- **Push** (`POST /projects/{id}/canon/push`, member projects that are COMPLETED): the API converts the workspace (`uc.json`, `connections.json`, `references.json`, `frg.json`, `meta.json`, `reference_check.json`, `quote_check.json`) with `canonFromProject`, diffs it against the head (`diffCanon`) and stores a pull request (`PR#`, payload and diff under `canons/{canonId}/pr/{no}/`). An open PR of the same project is superseded. `…/canon/preview` shows the same diff without a PR. UCs without a descriptor are left out and listed.
- **Conflict rules** (design doc 4.3): errors — C1 Uniform / Collection differs, C2c the decomposition is split differently, C3 a finer circuit next to a Uniform one, C4 Circuit ID ↔ descriptor not one to one (older IDs are compared in their current form), C5 a connection ends on a Collection, C6 official name differs, C8 the same Reference ID with another DOI / PMID, C8c / C9c reference or quote failed its check. Warnings — C2b the decomposition gains Sub-Circuits, C7 transmitter / modulation / Source of ID differ, C8b the same paper under another ID, C9b the same connection written differently, C12 a grouping differs. Information — C13 Output Semantics differs. A subset of the Canon's decomposition is not a conflict.
- **Review** (Canon owner): `approve` with `choices` (per conflict: keep the Canon's value or take the incoming one). Plain errors block; C1 and C2c can be resolved only by adopting the incoming definition (design Q10) — connections that then end on a Collection are marked `flagged`, and the projects that use the changed circuits are listed as impact. Every warning needs a choice. If the head moved since the push, the PR is re-judged against the current head first. Approval writes revision n+1, moves `headRevision` conditionally (a concurrent approval gets 409) and records `REV#`. `reject` needs a reason; the pusher can `withdraw`.
- Nothing is removed from the Canon when a project stops using an entry; the diff only lists it as "no longer in the project".

### 6.16.1 Reviewing a pull request (since 0.20.0)

The PR page is a review screen. The system and the AI assist; only the Canon's owner approves, requests changes or rejects, and the conflict rules of 6.16 still decide what blocks approval.

- **Material** (`GET /canons/{id}/pulls/{no}`, computed on every read and not stored): the diff and its base revision as before, plus `checks` (`canonReviewChecks`), `entries` (both sides of every diff item, field by field: `reviewEntries`), `graph` (`reviewGraph`: the circuits the PR brings, the Canon circuits its connections end on and the Canon neighbours of what changes, with the Canon connections among them; at most 60 circuits), `provenance` (source, its revision now, whether it still exists, the head), the audit trail and, for the owner, the latest AI review.
- **System checks** (never block approval; each has a group, a severity and the BRA Error code List (Master) code or a local `cobrac:` code): IDs — UC Descriptor syntax (`cobrac:uc-descriptor`), Circuit ID characters (`cobrac:circuit-id-chars`), Circuit ID ↔ descriptor form (`cobrac:circuit-id-form`), UCs left out without a descriptor, C4 (103). Duplicates and conflicts — the conflicts C1–C13 shown with their conflict ID, a new circuit with the same official name as an existing entry under another descriptor, existing entries on the same anchor. Connections — C5 (sender 203, receiver `cobrac:collection-end`), undefined ends (202 / 224), the reverse of a Canon connection for the same paper, opposite excitatory / inhibitory signs on the same sender and receiver (`classifyEdgeSign`), C9b. Evidence — no Reference ID (252), a Reference ID not in References (253), neither quote nor figure (271), C9c (273), C8, C8b (3), C8c, quotes and new references that were not verified. Provenance — the Canon moved since the push, the source has a newer revision, the source left the Canon or was deleted, other member projects affected, items the project no longer uses.
- **Screen**: tabs Changes (the Canon revision and "after approval" side by side as SVG with the same layout — added green, changed blue, no longer in the project grey dashed, conflicts outlined red, Collections dotted — and the structured diff by kind with filters; a row opens both sides field by field, its checks and its comments), Checks (the conflicts to decide, then the checks by group), AI review (owner only) and History. The decision panel (a column on wide screens, a bar at the bottom on phones) has a note and Request changes / Reject (note required) / Approve (note optional; disabled while conflicts are undecided).
- **Request changes** (`POST …/pulls/{no}/request-changes` `{ note }`): the PR stays open with `reviewState = changes_requested` and `reviewNote`; a new push supersedes it. **Comments** (`POST …/pulls/{no}/comments` `{ text, item? }`, the owner and the PR's sender): on the PR or on one diff item (`<kind>:<key>`). Approve takes an optional `note`.
- **Audit trail**: append-only `PEV#{prNo}#{at}#{nonce}` items in the Canons table for pushed, superseded, rebased (re-judged against a newer head at approval), comment, changes_requested, approved (with the revision and the conflict choices), rejected, withdrawn and ai_requested; the end of an AI review comes from its job. For PRs made before 0.20.0 the push and the decision are rebuilt from the `PR#` item.
- **AI review** (`POST …/pulls/{no}/ai-review` `{ model?, locale }`, the owner, open PRs, one at a time): the model is checked against the owner's key and tier (`requireModel`; Tier 1 of the default API key allows only its models), and again by the worker (`planRunKey`). The API writes the review material (`buildCanonAiPacket`: diff, conflicts, checks, both sides of the changed items, references; at most 150k characters) to `canons/{id}/pr/{no}/ai/{jobId}/input.json` and queues a job (`type` / mode `canon-review`, `projectId` = Canon ID, `reviewPrNo`, `reviewLocale`). The dispatcher and the janitor touch no project for it (a stalled review job fails instead of being retried). The worker runs one Codex turn without web search on that material with a fixed output schema (summary, flags with severity, reason, items, checks and Reference IDs, points to verify, draft comments per item) and asks once more if the reply is not that object. Parts that point at items, checks or papers not in the material are removed and counted (`parseCanonAiReview`); the result goes to `result.json` and its usage and cost to the job, so it counts in the owner's usage and in the default-key usage. The output has no verdict, and the prompt forbids recommending approval or rejection.

### 6.16.2 Co-editors and who decided (since 0.20.0)

- **Co-editors** (`EDITOR#{userId}` items in the Canons table; the user's `editorCanons` lists the Canons for "Shared with you"): the owner adds an existing user by the e-mail address they signed up with (`POST /canons/{id}/editors` `{ email }`, case-insensitive; an unknown address is 404 and asks the owner to have the person sign up first — there are no e-mail invitations) and removes them (`DELETE /canons/{id}/editors/{userId}`); a co-editor may remove themselves (leave). The owner sees co-editors' e-mail addresses; co-editors see names only.
- **What a co-editor can do**: read the Canon, its members (names, ROI / TLF; no links into the owner's projects), revisions and pull requests; comment; run AI reviews (on their own key or the default API key, with the models they may use; the job and its cost are theirs); request changes, approve and reject; send a pull request from one of their own Canons to it even when it is private or does not accept pull requests. **Owner only**: settings, member projects (push comes from member projects, which are the owner's), visibility, co-editors, deletion. Admins still only read.
- **One approval** merges a pull request. The PR keeps `approvals` (`{ userId, name, at }`), and the Canon may later get `requiredApprovals` (absent = 1; not settable and not shown yet).
- **Who decided**: the PR records `decidedBy` / `decidedByName` / `decidedAt` (approve, reject, withdraw) and `reviewedBy` / `reviewedByName` / `reviewedAt` (request changes); the revision (`REV#`) records `approvedBy` / `approvedByName` / `approvedAt`. The PR page shows a banner ("Approved by … → rev n", "Rejected by …", "Changes requested by …" with the note and time), the trail shows each actor, and the Canon's revision history shows the approver.

### 6.17 Canon → Canon pull requests (Canon MVP stage 2′)

- The owner of a Canon can send its head revision to another Canon as a pull request (`POST /canons/{target}/pulls` with `{ sourceCanonId }`; `…/pulls/preview` shows the diff first). Targets: the sender's own Canons, and public Canons of other users that accept pull requests (`acceptPullRequests`); a private Canon of someone else is 404, a public one that turned pull requests off is 403.
- The payload is the sender's snapshot as it is (`canonFromCanon`): entries keep their project origin and record `via = <sender>@<revision>`; the role layer brings every member project of the sender. The receiving owner reviews it with the same conflict rules, choices and approval as a project push (6.16). Nothing is written to the sending Canon except an `OUT#{target}#{no}` item that lets it list what it sent; the sender can open and withdraw the PR but not review it.
- An open PR from the same Canon to the same target is superseded by a new one.

### 6.18 Generating a member project under its Canon (Canon MVP stage 3)

- **Pin**: every member project follows one Canon revision (`Projects.canonRevision`). Joining pins the head; approving a project's own pull request moves its pin to the new revision (design Q9); otherwise the owner moves it with "Update to latest" (`POST /projects/{id}/canon/pull`). `GET /projects/{id}/canon` compares the pin with the head on what the project uses: `current`, `behind`, or `affected` (a used circuit became a Collection / Uniform, its Sub-Circuits or ID changed, or one of its connections now ends on a Collection) with the list and a follow-up text; "Align with Canon" moves the pin and sends that follow-up.
- **Worker**: at the start of every job (not articles) it reads the Canon META (`TABLE_CANONS`, read only) and the pinned snapshot, and writes `<workDir>/canon/` (`README.md` with the name, policy and strength, `circuits.json`, `connections.json`, `references.json`, `relevant.json`) next to the project folder; the folder is not synced back. An empty Canon (rev 0) or a missing one only disables the Canon for that run.
- **Instructions**: the HCD spec gets a "Canon for this run" section (`canonSpecNote`): use the Canon's Circuit IDs, names and properties; Collections of the Canon stay Collections and are connected through their Sub-Circuits; do not split a Uniform circuit (ask instead); copy Canon connections and references as they are; new entries follow the policy. The workflow skeleton is unchanged.
- **Check** (`canonGenerationProblems`, after the HCD checks): the Canon conflict rules C1, C2c, C3, C4, C5, C6, C8 become validator problems that go back to the agent as fix turns; C2b, C7, C8b, C9b, C12 are notes (shown in the chat, not sent back). References and quotes identical to checked ones in the Canon are not looked up again (`reference_check.json` / `quote_check.json` note "checked in Canon …").
- **No constraint strength** (after 0.12.0): every Canon is checked this way. 0.12.0 had a per-Canon `constraintMode` (`strict` / `advisory`); requests that still send it are accepted and the field is ignored, and a stored value stays in the item but is never read.

### 6.19 Choosing or seeding a Canon when creating a project (Canon MVP stage 3′)

- The create screen has a Canon button with a searchable popover: not in a Canon; an existing Canon of the user (the button shows its name and rev); or a new Canon seeded from existing projects (a panel under the composer with name, policy, the ordered seeds and the preview). `POST /projects` takes `canon` (`{ mode: "none" }` / `{ mode: "existing", canonId }` / `{ mode: "new", name, policy, seeds, choices, actions }`). Without `canon` the user's default Canon (`Users.defaultCanonId`, set on the settings page) is used, otherwise none. The plan is validated before the project is created, and the project joins its Canon before its first job is queued, so the first run already follows it.
- **Seeds**: own projects (clones included) that are COMPLETED and in no Canon (a project is in at most one Canon, Q20), in priority order. `POST /canons/seed-preview` composes them (`composeSeeds`): the first seed forms revision 1, each later seed is merged with the conflict rules of 6.16. While seeding, a C1 / C2c conflict may also be settled by keeping the earlier seed's definition (the later seed joins and is marked as needing an update; its connections to the Collection are flagged). A seed whose conflicts are not all settled becomes an open pull request against revision 1 (default) or is left out. The create screen offers "decide the rest by priority" and "keep the rest as pull requests".
- Creating the project counts as approving the seeds (Q21): revision 1 is written without a pull request (`REV#` with `source: "seed"`), the seeds that are not left out become members pinned to revision 1, and so does the new project.

### 6.20 BRA data versions (since 0.25.0)

Every COMPLETED BRA job (initial, follow-up or retry) freezes its result as an immutable **version** (`packages/shared/src/braVersion.ts`, `packages/worker/src/versions.ts`). The working copy (`workspace/`, `output/`, `graph/`) is still overwritten by each run; the versions are the history.

- **Number and ID**: version `n` is the project's `revision` after the job, so the numbers already stored elsewhere (`clonedFrom.revision`, Canon `projectRevision`, article `sourceRevision`) now name a version. The global ID is `<projectId>@v<n>` (Project IDs are never reused). **Parent**: version `n-1`; for the first version of a clone, the public project version it copied (`clonedFrom`).
- **What is frozen** (under `revisions/{n}/` of the project prefix): `files/` = the workspace (HCD / FRG / CSV data, report, decision log, checks; not the `*.jsonl` logs), `output/*.xlsx` and `graph/*.json`; `bradb/` = the BRA-DB registration package (internal: read by the BRA-DB importer, not offered for download); `manifest.json` (`BraVersionManifest`). The worker writes the files first and the manifest last with a conditional put (`If-None-Match: *`), so a version exists only once its manifest does and is never replaced. Running again for the same job returns the existing version; a version made by another job is left alone (`sys.versionConflict`). A failure to freeze is logged (`sys.versionFailed`) and does not fail the job. The bucket policy denies `s3:DeleteObject` on `users/*/*/revisions/*` to every principal.
- **Manifest**: version ID, parent, origin (`job` / `baseline`), created at, contributor, the job (ID, type, instruction), the generator (app version and git commit, SHA-256 of `prompts/` and of `HARNESS_SCHEMAS`, model, reasoning effort, research mode, pinned Canon revision, the SABRA boundary the HCD check enforced — `neocortex` or `legacy` — and the boundary version RCS reported, the harness rule set the checks followed — `harnessRules`, 0 for a project without one; absent on versions saved before 0.28.2, whose manifests are not rewritten —, the CSV format from Project.csv, and `planId` when a BRA Planner plan created the project — absent otherwise), each file's SHA-256 and size, the content hash, and the change summary against the parent (rows added / removed / changed per table; null when the parent has no snapshot).
- **Content hash** (`contentSha256`): SHA-256 of the lines `<CSV name>\t<SHA-256 of its bytes>\n` for `Project.csv`, `References.csv`, `Circuits.csv`, `Connections.csv`, `FRG.csv` in that order (`-` for a missing file). Only the five CSVs count, because they are what BRA-DB stores; the same data has the same hash however it is named or packed.
- **BRA-DB registration package** (only when all five CSVs exist): the CSVs under the names the BRA-DB import script reads (`{P}_project.csv`, `{P}_references.csv`, `{P}_circuits.csv`, `{P}_connections.csv`, `{P}_frg.csv`) and `manifest.json` (`BradbPackageManifest`: `projectId`, `versionId`, `version`, `parentVersionId`, `contentSha256`, the files with their hashes, `braVersion` = the CSV format, `cobracGenerated: true`, `importType: "cobrac"`, contributor, the generator as `provenance`, and `import.replace` / `import.allowShrink`). `replace` is true when the parent is a version of the same project; `allowShrink` when the change removes Circuits or Connections. Target: BRA-DB schema v4.6, import v3.10 or later. Registering is always done from a frozen version, and a hash that is already registered is a no-op.
- **Projects finished before versioning** have no snapshots. Their current data is listed as version `revision` with origin `live` (served from the working copy). A follow-up is accepted only on a COMPLETED project, so the worker of the follow-up first freezes that data as version `revision` with origin `baseline` (generator: only what the last job recorded; `revision` set to 1 when it was missing), then runs; the follow-up's result becomes `revision + 1` with the baseline as parent. A retry of a failed or cancelled legacy project does not freeze a baseline (its working copy may be half-changed), so its result has a parent without a snapshot and no change summary.
- **DynamoDB**: the summary (`BraVersionSummary`: number, ID, parent ID, origin, created at, content hash, app version, git commit, change summary, whether a package exists) is stored on the job that produced the version (`Jobs.braVersion`; a baseline goes on the last COMPLETED job) and the latest one on the project (`Projects.latestVersion`). These are new attributes on existing items; no table or index changes.
- **Screen**: the Versions tab of the project workspace lists the versions (newest first: number, current, origin, date, run type, model, change counts, the follow-up instruction), and for the selected one shows the generator, its tables (the table viewer on the frozen files), the row-level changes against another version (default: the one before), and the file list. The header shows the current version and the start of its content hash. Versions are not downloaded: the tab has no download, `GET /projects/{id}/artifacts/download` refuses keys under `revisions/`, and the existing downloads of the current data (header buttons) are unchanged; the frozen files are read through `GET /projects/{id}/artifacts/text` for the table viewer.
- **Diff** (`diffBraCsvs`): rows are matched by the keys BRA-DB uses — Reference ID, Circuit ID, (sCID, rCID, Reference ID) for Connections (a repeated key gets `#2`, `#3` by order), Node ID for the FRG — and compared column by column; Project.csv compares its project row only (the Review End Lines follow the row counts).


### 6.21 BRA-DB on AWS and registering versions (since 0.26.0)

BRA-DB (PostgreSQL 17 + Apache AGE 1.7, schema v4.6) runs in the `BraDb` stack (infrastructure: `03_AWSインフラと予算.md` 3.5). CoBRAC registers frozen versions in it; DynamoDB and S3 stay as they are (BRA-DB is the registration target, not the app's database).

- **Schema**: `packages/infra/bradb/sql/0001_bradb_schema_v4_6.sql` is the end state of BRA-DB DDL v4.0 + migrations 01–06 in one script (BRA-DB's own table, column and constraint names). `0002` creates every AGE label up front, `0003` CoBRAC's own schema `cobrac`, `0004` the roles' rights. Database `bra_db_v4_6`; roles `bra` (owner of BRA-DB's tables, for BRA-DB maintainers and migrations), `cobrac_import` (the registration Lambda) and `cobrac_read`.
- **Who can register**: the owner of the project, from the Versions tab (6.20), for a saved version with all five CSVs. `POST /projects/{id}/versions/{n}/bradb` reads the version's package (`revisions/{n}/bradb/`) and invokes the registration Lambda inside the BRA-DB VPC with it (synchronously). `Projects.bradb` remembers the last version registered.
- **What registration does** (`packages/api/src/lib/bradb/`, the counterpart of BRA-DB import_bra_project v3.10; one transaction, rolled back on any error or failed integrity check):
  - checks each package file against the manifest's SHA-256 and recomputes the content hash;
  - reads the sheets like v3.10 (column names, Review End Lines, Source of ID / Node role / enumerations / Capability&Mechanism), except: exact column names win over partial ones for every column, a column missing from a header is empty instead of read from a fixed position, the FRG starts at its "Node ID" column, separate Capability / Mechanism columns are read, and a value BRA-DB's constraints would reject (Modulation Type, Region Category, text longer than its column) is stored as NULL with a warning and kept in `extra`;
  - classifies circuits like v3.10 (an approved BIF circuit in BRA-DB is a BIFCircuit, everything else a LocalCircuit) and applies v3.10's checks (a Collection cannot send a connection: error 203; relations `=`, `<`, `>`);
  - writes `bradb_projects` (`cobrac_generated` true, `source_file` `cobrac:<version ID>`), `bradb_local_circuits` (own definitions upserted; circuits another project defined are shared vocabulary, kept and reported as skipped), `bradb_literature` (shared master; a DOI already used by another Reference ID is kept in `extra`), `bradb_project_literature`, `bradb_bra_nodes`, `bradb_connections`, and the graph `bradb_graph` (BRANode, LocalCircuit / BIFCircuit, SUBNODE, PROJECTS_TO, MAPS_TO_LOCAL / MAPS_TO_BIF, PROJECTS, HAS_SUBCIRCUIT). An edge whose end is not in BRA-DB is a warning, not an error; the integrity check compares the graph with the edges written;
  - appends `bradb_import_log` (`import_type` `cobrac`, `agent` `CoBRAC Agents v<app> (<git sha>)`, `notes` = version ID, parent, content hash, registration ID) and a row of `cobrac.registrations`.
- **History is never lost** (unlike `--replace` of import v3.10, which deletes the project row and with it the import log and node history):
  - replacing keeps the `bradb_projects` row and its `project_key` (and raises `version`); the project's connections, nodes and literature links, and its graph nodes and connection edges, are rebuilt; its circuits are updated in place (so other projects' edges to them stay); circuits it no longer defines are removed;
  - `bradb_bra_node_history` continues: a new node gets version 1 (`import`), a changed one version n+1 (`update`), an unchanged one keeps its version (no row); `bradb_bra_nodes.current_version` follows it;
  - `cobrac_import` has no DELETE on `bradb_projects`, `bradb_import_log`, `bradb_bra_node_history` or `cobrac.registrations`, and `cobrac.registrations` refuses UPDATE / DELETE by trigger.
- **Rules**: the same content hash as the version BRA-DB holds is a no-op (`unchanged`); fewer Circuits or Connections than BRA-DB holds is refused until the owner confirms (`code: shrink`, then `allowShrink`); a project with review comments in BRA-DB is no longer replaced (`code: review_comments`; reviewed data changes through instructions, not yet implemented).
- **Provenance**: `cobrac.registrations` (append-only) has, per attempt: project ID, `project_key`, version ID, version, parent version ID, content hash, status (`registered` / `unchanged` / `rejected` / `failed`), mode, reason, counts, node changes (added / removed / changed), skipped circuits, warnings, the generator (app version, git sha, model, SABRA boundary, …), the whole package manifest, who asked and when. `cobrac.current_versions` is the version each project holds now. A row of BRA-DB can be traced from `bradb_projects.project_id` to its version ID and content hash, and from there to the frozen files in S3.
- **Project IDs are opaque**: BRA-DB's `project_id` is the CoBRAC project ID as a string; the version ID is `<project ID>@v<n>`. Nothing parses the ID (the format of new IDs may change).
- **Screen**: the BRA-DB box of a version in the Versions tab shows which version BRA-DB holds, a "Register v<n> in BRA-DB" button, the shrink confirmation, and this version's registrations (status, time, who, warnings, skipped circuits). It is hidden when the deployment has no BRA-DB. Nothing is downloaded.

### 6.22 BRA Planner (stage 1: plans and batch runs)

A **plan** (UI 「計画」, screen 「BRA Planner」) is a list of rows (ROI × TLF) that the system builds as projects, in waves, within the concurrency limits, after its owner confirms it. Stage 1 has no Canon and no LLM drafting: rows come from a capability list (CSV / TSV / text) or are typed in, and the owner sets their order and waves by hand. Stage 2 (6.22.1) adds LLM drafting with a computed build order and re-planning after each wave; stage 3 (6.22.2) adds one Canon per plan with PRs, AI review and 「まとめて承認」. Shared code: `packages/shared/src/plan.ts`; API: `packages/api/src/lib/{plans,planOps,planRunner,runs,concurrency}.ts`, `handlers/planRunner.ts`.

- **IDs**: `n` + 7 lower-case Crockford base32 (`PLAN_ID_REGEX`, e.g. `n4h8w2rk`), reserved in the Catalog (`kind = id`, `type = plan`) like Project and Canon IDs and never reused. It matches neither `PROJECT_ID_REGEX` nor `CANON_ID_REGEX` (like any letter-led ID it also matches the pre-0.7 slug pattern of `isProjectIdLike`, but plans are never looked up as projects). Rows are `r` + 7 within their plan.
- **Data** (Plans table, section 7.1): `META` — owner, name, goal, status (`DRAFT` / `RUNNING` / `PAUSED` / `COMPLETED` / `CANCELLED`), settings (model and whether the owner chose it, reasoning effort, research mode, reply language), `harnessRules`, `activeWave`, the estimate at confirmation, row counts per state, `pausedReason`, confirmed / completed / cancelled times, the runner lease, `deletedAt`. `ROW#<rowId>` — order, wave, ROI, TLF, rationale, priority, source (`csv` with its spreadsheet row, or `manual`), state, `projectId`, the job created with it, automatic attempts, attention reason, last error, times. `EVT#<at>#<nonce>` — history (type, time, `by` = the user or `runner`, row, project, detail).
- **Rows from a capability list** (`parsePlanRowsCsv`): with a header row the columns are found by name (ROI / region / 脳領域, TLF / function / capability / 機能 / 能力, rationale / note / 理由 / 備考, wave / 波, priority / 優先度; others ignored); without one, a single column is the TLF and otherwise the columns are ROI, TLF, rationale. CSV or TSV, BOM stripped, blank lines skipped. Every other row is either taken or listed with its spreadsheet row number and the reason: no ROI and no TLF, a value too long (ROI / TLF 300, rationale 1000 characters), the same ROI × TLF as another row (case and spacing ignored; also against the rows already in the plan), a wave that is not 1–99, a priority that is not an integer, more than 200 rows per plan.
- **Draft**: rows are edited, moved, removed and added; waves are set per row or with "waves of N" (N = the effective concurrency); a CSV can be imported again (appended). Settings: model (none = the defaults), reasoning effort, research mode (default on). **Nothing is queued in a draft** (since stage 2, except the `plan` job of a draft the owner asks for, 6.22.1).
- **Confirmation** (`POST /plans/{id}/confirm`): needs at least one row, a key the owner can run jobs with (400 as for `POST /projects`) and, for a chosen model, a tier that allows it (403). It fixes, for every row, the model (the chosen one, else the user's default or the deployment default through the tier, as `POST /projects` does), reasoning effort, research mode, reply language (the UI language) and `harnessRules = HARNESS_RULES`, stores the estimate, sets `RUNNING` and runs one runner step at once (the first rows start without waiting a minute).
- **Runner** (`advancePlan`; Lambda `planRunner` on an EventBridge `rate(1 minute)` rule, and once after confirm / resume / retry). For every `RUNNING` or `PAUSED` plan, after taking a lease on its `META` item (an optimistic conditional write, 90 s; a second step meanwhile skips the plan):
  1. **Follow the projects** (`syncRow`) of rows in `starting` / `running` / `question`: queued / running / finalizing → `running`; waiting for an answer → `question` (only that row waits); completed → `done`; failed → back to `pending` with its project (an automatic retry) while it has used fewer than 2 (`MAX_ROW_AUTO_RETRIES`), otherwise `attention` (「要対応」); failed while it waited for an answer (the janitor's 7-day timeout) → `attention` without a retry; stopped outside the plan → `attention`; deleted → `attention`. A row left in `starting` for 2 minutes (the step stopped between claiming it and creating its project) goes back to `pending` with its reserved project ID, so it is never built twice.
  2. **Waves** (running plans only): `activeWave` moves to the next wave that still has waiting rows once no row of the active wave or an earlier one is `pending`, `starting` or `running`. Rows in `question` or `attention` do not hold it up, so only those rows wait. It never goes back.
  3. **Start** pending rows of the active wave and earlier ones in (wave, order), at most the free slots: min(overall limit − every queued, running and finalizing job, per-user limit − the owner's). Queued jobs count, so nothing is queued that could not start (the janitor fails jobs queued for 24 hours); the dispatcher still enforces the limits on running jobs. Before starting, the owner is checked as for `POST /projects`: a disabled account, no key, or a chosen model the tier no longer allows pauses the plan (`pausedReason` `owner_disabled` / `no_key` / `model_not_allowed`); a model the owner did not choose is replaced by the tier's default. A new row: reserve a Project ID, claim the row (`pending` → `starting` with the ID, conditional on its state), create the project with the same function as `POST /projects` (`createProject`, with `planId`, the plan's harness rules and a `sys.planStarted` notice), then `running`. A row that already has a project (an automatic retry, a manual retry, or a row stopped by a cancel) is retried with the same function as `POST /projects/{id}/retry` (`queueRetry`), continuing from its artifacts. A start that throws counts as an attempt (after the last, `attention` / `start_failed`). The step reads the plan again before each start and stops at a pause or cancel; a row started while the plan was being cancelled is stopped at once.
  4. A plan whose rows are all `done` or `skipped` becomes `COMPLETED`.
- **Pause / resume / cancel**: pause (`RUNNING` → `PAUSED`) starts nothing new; running rows continue and are still followed. Resume (`PAUSED` or `CANCELLED` → `RUNNING`) checks the owner's key again; rows stopped by a cancel go back to `pending` and continue their projects; done rows are never rebuilt. Cancel (`RUNNING` / `PAUSED` → `CANCELLED`) stops the active job of every row in flight (`stopProject`: the job and its Fargate task, the notice `sys.planCancelled`) and marks those rows `cancelled`; waiting rows stay as they are, and no new job is queued.
- **Questions and attention**: the plan screen's question inbox lists the rows in `question` with their project's question and an answer box that calls the existing `POST /projects/{id}/answer`; answering resumes only that row. A row that needs attention can be retried (back to `pending`; its attempts are not reset, so a row that fails again needs attention again) or skipped (`pending` / `attention` → `skipped`).
- **Deleting** a plan (draft, completed or cancelled) sets `deletedAt`; its projects stay.
- **Concurrency setting** (admin page, M9): Catalog `config` / `concurrency` (`maxConcurrentJobs`, `maxConcurrentJobsPerUser`: 1–16 each, or null for the deployment value; `updatedAt`, `updatedBy`). `PUT /admin/concurrency` refuses anything outside 1–16. The dispatcher (now with `GetItem` on the `config` partition of the Catalog) and the runner read it through a 30-second cache; if it cannot be read, the deployment values apply. `GET /config` returns the limits in force. The effective concurrency of a plan is min(overall, per user); the screens note that one run uses about 140–170k tokens per minute against the organisation's 200k per minute for gpt-6-luna, so the OpenAI rate limit may be the real ceiling.
- **Estimate** (`estimatePlan`, constants `PLAN_ESTIMATE`): time ≈ seed rows × 48 min + Σ over waves ceil(rows of the wave / effective concurrency) × 48 min + 20 % of the rows × 15 min of rework divided by the concurrency; cost ≈ rows × $0.18–0.39. Stage 1 has no seed rows. Waiting for answers is not included. For 141 rows (3 seed rows, the rest in one wave) this gives about 120 h at 1, 32 h at 4, 18 h at 8, 13 h at 12 and 10 h at 16. **So far**: the time since confirmation (to completion or cancellation) and the summed cost of the rows' projects; jobs are recorded and billed as any job (approved users run on the default API key).
- **Provenance**: `Projects.planId` and `Jobs.planId` (initial and retry jobs of plan rows, also retries started by hand on such a project), and `planId` in the generator of their versions' manifests (section 6.20). Every row of a plan uses the plan's `harnessRules`, fixed at confirmation, even if a later deploy raises `HARNESS_RULES`. Nothing is registered in BRA-DB.
- **Shared with the routes**: the bodies of `POST /projects`, `POST /projects/{id}/retry`, `POST /projects/{id}/cancel` and the admin stop are functions in `lib/runs.ts` (`createProject`, `queueRetry`, `stopProject`, with `requireRunKey`, `requireModel` and the model resolution) that the routes and the runner call with the owner's `UserRecord`; the routes behave as before.

### 6.22.1 BRA Planner stage 2: drafting with the LLM and the build order

Stage 2 lets a `plan` job — one Codex task with the RCS MCP, run like the AI review of a Canon pull request (6.16.1) — draft a plan from its goal and capability lists, and propose changes after each wave. The model supplies data (rows, their anchors, dependencies and priorities, a granularity policy); the build order is computed from that data by code, so it is reproducible and cheap to recompute after every wave. Shared code: `packages/shared/src/planOrder.ts` (order) and `planJob.ts` (job input, output schema, validation, prompt); API: `lib/planJobs.ts`, `lib/planRunner.ts`, `lib/planOps.ts`; worker: `packages/worker/src/planJob.ts`; instructions: `prompts/plan.md`. Plans made before stage 2 have no `ordering` (= manual) and behave as in stage 1.

- **Status `DRAFTING`**: a draft that waits for or runs its draft job; its rows cannot be edited meanwhile. The runner advances `DRAFTING`, `RUNNING` and `PAUSED` plans (`RUNNER_PLAN_STATUSES`).
- **Capability lists as files**: `POST /plans` takes `attachments` (uploads staged with `POST /uploads` as in 7.4, up to `ATTACHMENT_LIMITS.maxFiles`; types `PLAN_ATTACHMENT_EXTS` = csv, tsv, txt, xlsx, pdf; any other type is 400). CSV / TSV / text (`isDeterministicPlanAttachment`) are read at once with `parsePlanRowsCsv`: their rows get source `csv`, and the rows that cannot be read are listed with their `file`. xlsx and PDF are only stored; the draft job reads them. Every file is moved to `plans/{planId}/attachments/files/NN-<name>` and listed in `META.attachments`; every staged name and target key is checked first (no `..`, `.` or empty path segment; a name such as `list..v2.xlsx` is fine), so a bad file leaves nothing moved (400 「添付ファイルの名前が不正です」) (`kind: "file"`, `id` `f1`, `f2`…, name, `key` relative to the plan prefix, size, content type).
- **Asking for a draft** (`POST /plans/{id}/draft` `{ locale? }`, or `draft: true` with an optional `locale` in `POST /plans`; either needs a goal, an attachment or rows): the owner must be able to run jobs (400 without a key, 403 for a chosen model the owner may not use, as at confirmation). Under the plan's lease the plan goes `DRAFT` → `DRAFTING` (at creation: the plan and its rows are written as a `DRAFT` first, then switched, so a runner step never sees a drafting plan with only part of its rows) with `draft = { kind: "draft", jobId: null, status: "waiting", requestedAt, requestedBy, locale }` (event `draft_requested`), and one runner step runs at once. The request itself queues nothing.
- **Queueing a plan job** (runner): a waiting draft is queued only when `freeSlots` — jobs in `SLOT_JOB_STATUSES` (queued, running, finalizing) under the overall and the owner's limit, the same gate as for rows — leaves a slot and the owner can still run jobs. The runner writes the input (`buildPlanJobInput`: kind, goal, policy, the plan's rows as they are — with their priority, dependencies and 「作り直す」 flag —, the owner's projects that are not deleted, newest first, with `completed` = COMPLETED with artifacts, the owner's Canons with their policies, the effective concurrency, and, for a draft, the attachments the API did not read, as `{ id, name, key }`; a re-plan gets no attachments) to `plans/{planId}/jobs/{jobId}/input.json` (`planJobKey`), puts the job (`type: "plan"`, `planJobKind: "draft"`, `projectId` = `planId` = the plan ID, `QUEUED`, `keySource`, the model resolved for the owner, `reasoningEffort` = `PLAN_JOB_REASONING_EFFORT` = `medium`) and queues `{ mode: "plan" }`; the draft becomes `queued`. Without a free slot the draft stays `waiting` (nothing is queued ahead of a slot). When the owner can no longer run jobs (no key, account disabled, chosen model no longer allowed) the plan goes back to `DRAFT` with the draft `failed`, the reason as text and as `errorCode` (`no_key` / `owner_disabled` / `model_not_allowed`, shown translated on the plan page), and event `draft_failed`. The input never holds a key or other secret: the API and the runner never decrypt a key; the worker resolves (`planRunKey`) and decrypts it as for any job.
- **The job** (worker, mode `plan`, `runPlanJob`): the worker takes the job only while it is a `QUEUED` plan job, resolves and decrypts the key (failing the job when there is none), marks it `RUNNING` with a write conditional on its still being `QUEUED` (a draft cancelled meanwhile stays cancelled), reads `input.json`, copies the attachments into its materials folder and extracts the text of xlsx and PDF files as for reference materials (7.4; kept under `plans/{planId}/attachments/derived/`), and runs one Codex turn with the RCS MCP (`search_bna_candidates`, `search_homba_candidates`, `get_homba_term`, `get_sabra_definition`), without web search and without the `lit` server (when RCS is not configured, the instructions tell the model to leave `anchors` empty and say so in `notes`). The prompt (`planJobPrompt`) is the instructions of `prompts/plan.md`, the task (DRAFT or REPLAN), the reply language, the index of the attachments and the input. The reply must be the object of `PLAN_RESULT_SCHEMA` (`rows`, `unread`, `policy`, `proposals`, `notes`; every property required); when it does not parse, the worker asks once more (`PLAN_RETRY_PROMPT`). The job has a wall-clock budget of `PLAN_JOB_TIME_BUDGET_MS` (7 minutes from the worker's start), so a draft is ready within about 10 minutes of the request, with the queueing, the Fargate start-up and the runner's next step (which applies the result, at most a minute later) included. A draft that reads xlsx / PDF lists or has more than `PLAN_JOB_SHORT_ROWS` (20) input rows writes one row per item, so it gets `PLAN_JOB_LONG_TIME_BUDGET_MS` (25 minutes; `planJobBudgetMs`); a turn still running then is aborted and the job fails ("The plan job took longer than its time budget"). The worker sends a heartbeat every 45 s, writes `result.json` (`PlanJobResult`: schema `cobrac.plan-result/1`, kind, plan and job IDs, model, locale, time, the parsed rows, unread, policy, proposals, notes and `dropped`) next to the input, and records the job's usage, estimated cost and end (`COMPLETED`), or the error and usage (`FAILED`).
- **Validation** (`parsePlanResult`; agent-written JSON is never used unchecked): only what refers to the input is kept, and everything else is removed and counted in `dropped`. Draft rows: input rows by their row ID (`ref`), new rows by the model's `id`; ROI / TLF / rationale within the row limits of 6.22; no repeated `id` or ROI × TLF; anchors normalised by `normalizePlanAnchor` (`HOMBA:<id>`, `BNA:<l>-<r>` of a known BNA area — a single label becomes its pair, facets such as `/side:left` are dropped —, `BNAG:<L2>` of a known group; at most `MAX_ROW_ANCHORS` per row); `dependsOn` only on rows of the draft, never on the row itself; `priority` an integer within the priority range, else none; `existingProjectId` only a COMPLETED project of the input; at most 200 rows and `MAX_PLAN_UNREAD` unread items. Re-plan proposals (at most `MAX_PLAN_PROPOSALS`): `add` a row whose ROI × TLF is not in the plan yet (dependencies on input rows only), `remove` a row that has not started (pending, no project, not existing), `policy` a text that differs from the current policy (one at most). A draft's proposals and a re-plan's rows are dropped. When RCS is configured, the worker also removes from rows and `add` proposals the HOMBA anchors RCS reports as unknown, and those whose region SABRA covers with BNA (finished projects anchor such a region on its BNA area, so the HOMBA ID would never match) — counted in `dropped`; anchors that could not be looked up are kept. The runner checks `result.json` again before using it (`readPlanResult`: its schema, kind and job ID must match, and its content goes through `parsePlanResult` once more against the job's `input.json`), so a result file is never trusted as it is.
- **Applying a draft** (runner, under the plan's lease): the runner follows the job (`RUNNING` → draft `running`). When it is COMPLETED, the runner reads `result.json`; a result row with `ref` updates that row — anchors (`anchorsSource: "predicted"`), `dependsOn` (mapped to row IDs), the priority only when the row has none (the job sees the owner's priority and returns it; a CSV `priority` column is never overwritten), the rationale only when the row had none; its ROI, TLF and source stay. A result row without `ref` becomes a new pending row (`source: "llm"`), unless a row of the plan already has its ROI × TLF: then it updates that row; a `ref` to a row that is gone, or a second result row for the same row, is dropped. The existing project of a row is the result's `existingProjectId`, else the one `matchExistingProject` finds (below); a row the owner marked 「作り直す」 (`rebuild`) gets none. Rows the result does not mention are kept as they are. The rows are then ordered with `orderDraft` (below); the policy becomes the result's when that is not empty, `ordering` becomes `auto`, and the row counts are updated. A plan holds at most 200 rows (result rows beyond that count as dropped). The plan goes back to `DRAFT` with the draft `done`, its `unread` list and `dropped` count (event `draft_applied` with rows, unread, dropped). A job that failed, was cancelled or is missing, or a `result.json` that cannot be read, puts the plan back in `DRAFT` with the draft `failed` / `cancelled` and the error (event `draft_failed`). Asking for a draft again runs a new job on the current rows.
- **Cancelling a draft** (`POST /plans/{id}/draft/cancel`, `DRAFTING` only): stops the job if it is queued or running (the job `CANCELLED`, its Fargate task stopped); the plan goes back to `DRAFT` with the draft `cancelled` (event `draft_cancelled`).
- **Anchors** (`PlanRowRecord.anchors`): the SABRA units of the row's ROI and of the main regions expected to send it input or receive its output, written as UC Descriptor anchors: `HOMBA:<id>` (a HOMBA term, the DHBA side), `BNA:<l>-<r>` (a BNA area pair) or `BNAG:<L2>` (a BNA gyrus group). The job finds them with the RCS tools, which say which atlas covers a region; the code does not fix that split. Rows are compared after a BNA group is expanded into its BNA area pairs (`anchorKeys`), so a row anchored on `BNAG:IFG` shares anchors with one anchored on an IFG area; HOMBA terms are compared as they are (`sharedAnchors`).
- **Build order** (`orderPlanRows`, deterministic for the same rows):
  1. **Hub score**: the number of other rows sharing at least one anchor with the row (`hubScores`).
  2. **Seed wave** (種の波): among the rows that depend on no other row being placed, ranked by (hub score, priority, row ID), the best one and every row whose hub score is at least `SEED_HUB_SHARE` (60 %) of the best score, at most `MAX_SEED_ROWS` (3). Each seed row gets its own wave (1, 2, 3), so the stage-1 wave logic builds them one at a time before the other waves. There is no seed wave when no row shares an anchor with another one, or when there is a single row. The seeds are the rows whose regions the most other rows touch: building them first, alone, works out the shared circuits once before the rows that use them run in parallel, and their finished projects feed the re-plan below.
  3. **Body waves**: the other rows in topological order of `dependsOn` (Kahn's algorithm), ties by (hub score desc, priority desc, row ID); a dependency cycle is broken at the best-ranked row of a cycle that waits on nothing outside it, so a row that depends on a cycle member still comes after it. Each row goes into the earliest wave after its dependencies (and after the seed waves) that has fewer rows than the effective concurrency and holds no row sharing `OVERLAP_LIMIT` (2) or more anchors with it, so two rows that would build the same circuits never run at the same time.
- **Order of a draft** (`orderDraft`): every row that will be built (not skipped, no existing project) is placed from wave 1 with seeds chosen as above; rows with an existing project only count for the hub scores and are listed in the last placed wave (they are never built), without the seed flag; skipped rows keep their wave. The `order` field follows the build order: by wave (seeds first), within a wave by hub score and priority; rows that are not placed (existing or skipped) last.
- **「自動で並べる」** (`POST /plans/{id}/order`, `DRAFT` only): `orderDraft` over the current rows, `ordering: "auto"`, event `ordered`. **Editing rows by hand** (`PUT /plans/{id}/rows`) sets `ordering: "manual"` when rows are added, removed, moved or put in another wave: the owner's waves are kept and no re-plan runs; a seed row that no longer sits alone in its wave (among the rows to build) loses its seed flag. A save that keeps the same rows in the same order and waves (e.g. a rationale, ROI / TLF or 「作り直す」 change) keeps the ordering; when it stays `auto` and a 「作り直す」 flag or existing project changed, the rows are ordered again (`autoOrder`) in the same request. A row that keeps its `rowId` keeps its anchors, dependencies, seed flag, existing project and duplicate warning; `rebuild: true` stores the 「作り直す」 choice on the row (`PlanRowRecord.rebuild`) and drops its existing project so it is built — it is never matched again, also not by a later draft, until `rebuild: false` is sent; new rows, and rows whose ROI × TLF changed, are matched against the owner's projects. Importing a CSV (`POST /plans/{id}/rows/import`) into an `auto` draft orders all rows again (`orderDraft`) and keeps `auto`; into a manual one it appends the rows as in stage 1.
- **Existing projects and duplicates** (`matchExistingProject`: the same ROI × TLF, case and spacing ignored; deleted projects do not count): a COMPLETED project of the owner with artifacts makes the row `existing` (`{ projectId, name }`), and the row is not built; a project with the same ROI × TLF that is not finished sets `duplicateOf` (a warning only).
- **Confirmation** (in addition to 6.22): each pending row with an existing project is checked again against the owner's projects (not deleted, COMPLETED, with artifacts); when that no longer holds it is matched again and, without a match, built (the `confirmed` event counts them as `existingGone`). Then an `auto` plan is ordered again with `orderDraft` at the effective concurrency in force; rows with an existing project become `done` with `projectId` = that project and `completedAt`; the stored estimate is `planEstimate`.
- **Estimate** (`planEstimate(rows, concurrency)`, used for the stored estimate, the plan page and the confirmation instead of the stage-1 call without seed rows): skipped rows and rows done by an existing project are left out (`waveSizes` leaves out existing rows too); seed rows count one at a time (48 min each, and each one a wave in `waves`, as they are stored and built), the other waves as in 6.22.
- **Re-plan after each wave** (only for `ordering: "auto"`; runner, `RUNNING` plans, after following the projects):
  1. **Used anchors**: for done rows with a project of their own (not existing) whose anchors are not `used` yet, the runner reads `users/{owner}/{projectId}/workspace/{projectId}_HCD/uc.json` (at most 20 reads per step, more than a wave can hold); when it parses and has anchors (`anchorsOfUcJson`: those of every UC and Collection descriptor), they replace the row's anchors with `anchorsSource: "used"`.
  2. **Re-order**: once the active wave is finished (no row of it or of an earlier wave is pending, starting or running), a movable row (`isMovableRow`: pending, no project, not existing) is in a later wave, and this wave was not re-planned yet (`lastReplanWave`), `replanRows(rows, activeWave, effective)` orders the movable rows again from the next wave with the current anchors and hub scores; seed rows that have not started stay seeds. Each new wave is written only while the row is still pending; `lastReplanWave` becomes the wave (event `replanned` with the wave and the rows moved). Rows that are starting, running, waiting for an answer, done, need attention, were skipped or cancelled, and retries (pending with a project), never move. Then `activeWave` moves on as in 6.22.
  3. **Re-plan job**: the same step asks for an LLM re-plan (`replan = { kind: "replan", status: "waiting", wave, requestedBy: "runner" }`) unless one is waiting, queued or running, and only when `replanJobDue` says so: the first one right after the first wave that finishes (the first seed, the main hub), later ones once a tenth of the rows the plan builds (at least one; existing, skipped and cancelled rows left out) have finished since the wave of the last one, so a plan runs about `MAX_REPLAN_JOBS` (10) re-plan jobs at most — at concurrency 1 every body wave is a single row, and a job after every wave would cost one job and one held slot per row. Plans of up to 10 rows get one after every wave. The re-ordering of step 2 happens after every wave regardless. It is queued like a draft job (input kind `replan` with the finished `wave` and every row) when a slot is free — before the step starts rows, so it takes that slot — and never while the plan is `PAUSED`. When it completes, each proposal becomes a `PROP#<proposalId>` item (status `open`, with the job and the wave), the re-plan is `done` (event `proposals_received` with their number). When it fails, the re-plan is `failed` (event `replan_failed`) and the plan goes on. A re-plan still waiting, queued or running when the plan is cancelled or completes is ended as `cancelled` and its job stopped (`dropReplan`).
- **Proposals** (`POST /plans/{id}/proposals/{proposalId}/accept` / `…/reject`; the owner, plan `RUNNING` or `PAUSED`, proposal `open`, else 409): nothing changes until the owner accepts one. Accepting `add` (409 when the plan already has 200 rows; when a row that is not skipped already has its ROI × TLF, the proposal becomes `stale` and the request gets 409) creates a pending row (`source: "llm"`, predicted anchors, its dependencies, existing project and duplicate matched as above, the plan's own projects left out; a row with an existing project is `done` at once with that project) and places the movable rows after the active wave again with `replanRows` (rows of the active wave that still wait for a slot keep their wave; a new row that gets no wave goes after the last wave); `remove` needs the row to be still movable — otherwise the proposal becomes `stale` and the request gets 409 — and skips the row; `policy` replaces the plan's policy. The proposal records `decidedAt` / `decidedBy` and becomes `accepted` or `rejected` (events `proposal_accepted` / `proposal_rejected`).
- **Granularity policy** (`META.policy`, at most 2000 characters): written by the draft (one text for the plan's projects, in line with one of the owner's Canons when one fits), editable in a draft (`PUT /plans/{id}` `{ policy }`), changed after confirmation only by an accepted `policy` proposal.
- **Changes under the plan's lease** (fix of a stage-1 race): replacing and importing rows, changing the settings or the policy, confirming, asking for and cancelling a draft, ordering and deciding proposals take the same lease on `META` as the runner (`withPlanLease`: up to 6 more tries 250 ms apart) and re-check the status of the plan read again with a strongly consistent read once the lease is held (rows are listed consistently too; a release writes its own time, so a stale read of the lease can never be taken for a free one, and row writes are preceded by a conditional check that the status and the lease still hold), so editing rows in one tab while confirming in another can no longer leave a running plan whose rows changed after confirmation. While another change or a runner step holds the lease, the request gets 409 「計画を更新中です。少し待ってからやり直してください」 and nothing changes. A change of only the name or the goal stays a single write conditional on the status, as in stage 1.
- **Jobs outside projects**: a `plan` job belongs to no project (`isProjectlessMode`, like `canon-review`): the dispatcher posts no chat message and sets no project status; the janitor marks a plan job whose heartbeat is stale, or that has been queued for 24 hours, `FAILED` with a reason, never retries it and touches no project; the runner then fails the draft or re-plan.
- **Limits and cost**: a plan job is an ordinary job for the limits and the bill. While queued or running it takes one of the owner's slots under both limits (the runner and the dispatcher count it like a row's job); it runs on the owner's key or the default API key (`keySource`); its usage and estimated cost are recorded on the job and counted in the owner's usage and, on the default key, in the default-key usage. It is one short turn at reasoning effort `medium`, so it costs little next to a row. A job cut off by its time budget or stopped by a cancel is billed for what it used (the worker measures the cut-off turn from the session file, and on SIGTERM records the thread's usage so far). The plan page adds the plan's own jobs to the cost so far (`actual.costUsd`) and shows them separately (`planJobsCostUsd`).
- **Plan page** (`GET /plans/{id}`): also returns `proposals` (newest first), `planJobsCostUsd`, and for every row `hub` and `overlaps` (the other rows sharing at least `OVERLAP_LIMIT` anchors), computed over the rows that are not skipped.

### 6.22.2 BRA Planner stage 3: the plan's Canon

Stage 3 lets a plan build its rows into one Canon: each finished row is pushed as a pull request (6.16), body rows get an AI review (6.16.1), conflicts caused by the Canon moving on are fixed by a conform follow-up, and a row is done only when a human has approved its pull request. The runner never approves, rejects or answers anything; 「まとめて承認」 lets a reviewer approve several conflict-free pull requests at once. Plans without a Canon (every plan made before stage 3, and those that choose 「なし」) behave exactly as in 6.22 / 6.22.1 and read no Canon. Shared code: `packages/shared/src/plan.ts` (`pushOutcome`, `prOutcome`, `waitingPrs`, `conformTitle`, the `seedGate` / `holdNewWave` options of `nextActiveWave`); API: `lib/canonOps.ts`, `lib/planRunner.ts`, `lib/planOps.ts`, `lib/runs.ts` (`queueFollowup`).

- **Choosing the Canon** (`PUT /plans/{id}` `{ canon }`, `DRAFT` only, under the plan's lease; 409 while drafting or after confirmation): `{ mode: "none" }` clears it; `{ mode: "existing", canonId }` needs a Canon the plan's owner owns and has not deleted (projects can only join their owner's Canons; a co-edited Canon cannot be chosen; 404 otherwise) and stores `META.canonId`; `{ mode: "new", name }` (name checked as for `POST /canons`) stores `META.canonNew = { name }` and no `canonId`. One plan has at most one Canon. The plan page shows the choice in a draft (なし / 既存の Canon — a select of the owner's Canons that are not deleted / 新しい Canon, its name defaulting to the plan's name) and, after confirmation, read-only with a link to the Canon and its head revision, or 「Canon が見つかりません」 when it was deleted (`GET /plans/{id}` returns `canon = { canonId, name, headRevision }`, `missing: true` for a deleted Canon or one no longer the owner's, null without one).
- **Confirmation** (in addition to 6.22 / 6.22.1, inside the lease): a chosen existing Canon must still be the owner's (409 「この計画の Canon が見つかりません」). A new Canon is created now with the plan's granularity policy as its policy (`createCanon`, private, empty, `headRevision` 0) and stored on the plan at once (`canonId`, `canonNew` null; event `canon_created`), so a confirmation that fails afterwards keeps that Canon and does not make another. Rows with an existing project in a plan with a Canon: the project is already in this Canon → `done` (as in stage 2); in no Canon → `running` with `projectId` = that project (the runner pushes it on its next step, below); in another Canon → `decision` / `other_canon` (event `row_decision`). The `confirmed` event names the Canon.
- **Start** (runner, plans with `canonId`; the runner reads the Canon once per step with `ownedCanon`): a new row's project joins the Canon pinned to its head before its first job is queued (`createProject`'s `beforeQueue` → `addCanonMember(canonId, owner, projectId, head)`; also on the recovery of a start that did not finish), and the row records `canonRevision` = head. A retry of a failed project is re-pinned to the head first (`pinProject`, or joins when it is in no Canon) and records the new `canonRevision`.
- **Push** (instead of finishing a row): when `syncRow` says a row of a Canon plan is `done` (its project COMPLETED), the runner pushes it: the project must be in the plan's Canon (in none → it joins pinned to the head; in another → `decision` / `other_canon`); `pushProject` (the body of `POST /projects/{id}/canon/push`) creates the pull request, which now records `planId`; an error → `decision` / `push_failed` with the error as `lastError`. `headMoved` = the Canon head is later than the row's pin (`row.canonRevision`, else the project's). `pushOutcome(diff.summary, headMoved, conformAttempts)`:
  - no error conflicts (warnings and needs-review items included: they always go to a human) → `review` (「承認待ち」) with `prNo`; body rows get `aiReview: "wanted"`, seed rows none (event `row_pushed`);
  - error conflicts and the head moved since the pin, fewer than `MAX_CONFORM_FOLLOWUPS` (2) conform follow-ups so far → back to `pending` with `conform: true` and `prNo` (event `row_pushed`);
  - error conflicts without a head move → `decision` / `conflicts`; still error conflicts after 2 conform follow-ups → `decision` / `conform_limit` (event `row_decision` with the reason and `prNo`).
- **Conform follow-up**: a `pending` row with `conform: true` is a start candidate like any pending row (same slot gate, wave order; it also holds its wave). Starting it re-pins the project to the head and queues a follow-up job (`queueFollowup`, the body of `POST /projects/{id}/followup`) whose instruction starts with the fixed title `conformTitle(head)` = 「Canon rev N に合わせて更新」 followed by `canonAlignInstruction` with what changed for the project between its old pin and the head (`canonFollowStatus`); the row becomes `running` with `conformAttempts` + 1 and `canonRevision` = head (event `row_conform` with the revision and attempt). When the follow-up completes the row is pushed again (the new push supersedes its open pull request). A row whose project is no longer in the plan's Canon, or whose Canon is gone, goes to `decision` instead.
- **Rows in review**: every step reads the pull request of each `review` row (`prOutcome`): approved → `done` (`completedAt`, event `row_done`); rejected → `decision` / `pr_rejected`; withdrawn → `decision` / `pr_withdrawn`; superseded by `#n` (for example a push by hand) → the row follows `#n` and stays in review; open → unchanged. Rows are followed while the plan is `RUNNING` or `PAUSED`. A missing or deleted Canon sends every row that would push or is in review to `decision` / `push_failed` ("The plan's Canon was not found."); nothing else is paused.
- **AI reviews** (body rows only): in the slot section of a running plan's step — after a waiting re-plan job and before new rows — each `review` row with `aiReview: "wanted"` gets `requestAiReview` (the body of `POST /canons/{id}/pulls/{no}/ai-review`, as the owner, with the plan's model, the owner's key source and the plan's reply language) while a slot is free, one slot each; it becomes `aiReview: "queued"` with `aiReviewJobId` (event `row_ai_review`). A pull request no longer open clears `aiReview`; a review already queued or running counts as `queued`. The review produces findings only and never decides.
- **Seed gate and one seed at a time**: for Canon plans `nextActiveWave` is called with `seedGate: true`: a seed row holds every later wave until it is `done`, `skipped` or `cancelled`, i.e. until a human has approved its pull request (or resolved or skipped the row). Seed rows also start one at a time even when they share a wave: no seed starts while another seed is in flight, in review or in decision, and at most one seed starts per step. The plan page shows 「種の PR の承認を待っています」 with a link to the pull request while a seed of the active wave or an earlier one is in review.
- **Back-pressure**: while `waitingPrs(rows)` (rows in `review`) ≥ `PLAN_MAX_WAITING_PRS` (20), `holdNewWave` keeps `activeWave` where it is: rows of the active wave still start, but no new wave begins. The plan page says 「承認待ちの PR が 20 件あるため、次の波を止めています」.
- **Row states** (in addition to 6.22): `review` (「承認待ち」: its pull request is open and waits for a human) and `decision` (「人の判断」, with `decisionReason` `conflicts` / `conform_limit` / `pr_rejected` / `pr_withdrawn` / `other_canon` / `push_failed`). Neither holds a slot, and neither counts as finished: a plan with a Canon completes only when every row is `done` or `skipped`. Pause stops nothing in them; cancel turns pending and in-flight rows `cancelled` as before and leaves `review` and `decision` rows and their pull requests as they are (they can still be approved in the Canon; a resumed plan follows them again).
- **Human decisions** (`POST /plans/{id}/rows/{rowId}/resolve` `{ action }`, the owner, plan `RUNNING` or `PAUSED`, row in `decision`, under the lease; 409 otherwise): `done` counts the row as done as it is (`completedAt`; its pull request, if any, stays as it is in the Canon); `push` needs the row's project to be COMPLETED (409 「完了したプロジェクトの行だけをもう一度 push できます」) and sets the row `running` (reason cleared, `conformAttempts` kept), so the runner pushes it on its next step. Event `row_resolved` with the action and the former reason. Skip (`POST …/rows/{rowId}/skip`) now also accepts `decision` rows. The plan page lists decision rows in a 「人の判断」 card with the reason text and 「完了にする」 / 「もう一度 push」 / 「スキップ」 (each with a confirmation); review rows show a link to the pull request and the AI review state (待ち / 実行中); rows show 「Canon に合わせた更新 n/2」 once they had a conform follow-up.
- **「まとめて承認」** (`POST /canons/{id}/pulls/approve-many` `{ prNos }`; reviewers as for a single approval: the owner or a co-editor; 1–50 PR numbers, else 400; duplicates dropped, order kept): approves the pull requests one after another, each with `approvePullRequest` (the body of `POST …/pulls/{no}/approve`, without conflict choices) against the Canon read again, so each is judged against the head the previous one made (re-diffed and recorded as rebased when needed). It stops at the first one that is not found (`not_found`), not open (`closed`), has blocking conflicts against the new head (`conflicts`, with `blocking` = their number), lacks approvals (`approvals`) or lost a head race (`race`), and leaves the rest untried. Response `{ approved: [{ prNo, revision }], stopped: { prNo, reason, blocking? } | null }`. The approver is recorded exactly as by a single approval (`decidedBy`, `approvals`, the revision's `approvedBy`). The Canon page offers a checkbox on every open pull request without error conflicts or needs-review items and without a request for changes (and a select-all), and a 「まとめて承認」 button with a confirmation showing the count; the result line says how many were approved and where and why it stopped.
- **Plan on pull requests**: `CanonPullRequestRecord.planId` (the pushed project's `planId`, null otherwise) is stored by every push, by hand too; the Canon's pull request list and the pull request page show a chip with the plan ID, a link to the plan for the Canon's owner (the plan is theirs).
- **Shared with the routes** (extraction, as stage 1 did with `lib/runs.ts`): Canon creation, `loadCanonHead` / `loadCanonRevision`, the project's incoming data, opening a pull request, the push (`pushProject`), moving a pin (`pinProject`), the AI review request (`requestAiReview`) and the approval (`approvePullRequest`) are functions in `lib/canonOps.ts`, and the follow-up job is `queueFollowup` in `lib/runs.ts`; the routes (`POST /canons`, `POST /projects/{id}/canon/push` / `…/pull`, `POST /projects/{id}/followup`, `POST /canons/{id}/pulls/{no}/ai-review` / `…/approve`) keep their checks and messages and behave as before; the only visible change is `planId` on new pull requests.
- **Jobs and cost**: AI reviews and conform follow-ups are ordinary jobs (`canon-review` and `followup`) on the owner's key or the default API key, queued only when a slot is free and billed like any job; nothing is queued ahead of a slot. The API and the runner still never decrypt a key.
- **Runner access** (docs/03): Canons read / write, S3 get / put on `canons/*`, S3 get on `users/*/workspace/*` (the project's files for a push and the finished rows' `uc.json`), which replace stage 2's `owner-index` Query and `users/*_HCD/uc.json` read. No KMS.

### 6.23 Hypothesis mode (since 0.32.0, stage 1: harness and export)

A project in **hypothesis mode** ("Allow hypotheses") may include connections and UCs, or properties of them, that the literature does not directly support, each marked with a `hypothesis` key. Only one requirement is relaxed: a sentence of a paper need not state the hypothesized claim itself. Everything else is checked as always: DOIs / PMIDs and their lookups, quotes found in the cited paper, one paper per connection record, a pointer, UC naming and the SABRA boundary, the schemas (`additionalProperties: false` stays), interfaces, Collections and uniform senders, the FRG structure, English, the report sections and the Canon. The hypotheses are disclosed, never extended: nothing the harness writes or asks for proposes investigations, experiments, tests or predictions. Code: `packages/shared/src/hypothesis.ts` (pure functions) called from `checkHcd` / `buildCsvs` (`harness.ts`) and `checkCross` (`cross.ts`); worker: `pipeline.ts`, `hypothesisRules.ts`, `index.ts`.

- **Project fields** (`ProjectRecord`, read through `evidenceSettingsOf`): `evidenceMode` (`strict` / `hypothesis`; absent = `strict`, literature-supported evidence only), `hypothesisScopes` (the scopes S1, S2, … in the order they were added) and `hypothesisMaxShare` (`0.1` / `0.2` / `0.3` / `0.5`; absent or any other value = `0.2`). The mode is separate from `harnessRules`, so any rule set can use it. Stage 1 only **reads** them (the worker, when a job starts). Nothing sets them yet: the API, the screens, and the Canon and BRA-DB guards come in later stages, so until then no project can be in hypothesis mode (tests drive it through the check options and project records).
- **Scopes** (`HypothesisScope`, `normalizeScopes`): `id` (`S<n>`), `claims`, `target` (`{ kind: "all" }` = the whole HCD, or `{ kind: "items", circuitIds, gnIds }`), optional `note` (one line from the user, given to the agent quoted as data), `jobId`, `createdAt`. Unknown claims are dropped; a stored scope without a valid ID or any claim, or with a repeated ID, is left out; a target other than `items` is the whole HCD. The text of an instruction never creates or widens a scope.
  - **Membership** (`scopeTargetCovers`): the target circuits are the listed UCs, the UCs of listed Collections (nested Collections expanded) and the UCs under listed FRG GNs, all levels (read leniently from `frg.json`, also before the FRG is checked). A connection is inside when its sender or receiver is a target circuit; a UC when it is one, or when one of its connections has its other end on one. A scope covers a hypothesis when it lists every claim of the hypothesis and its target covers the element.
- **The `hypothesis` key** (`hypothesisKeySchema`): optional on `uc.json` `ucs[]` and `connections.json` `connections[]` in the `HARNESS_SCHEMAS` of every project; Collections and the BIF have none. `parseHypothesis` reads it only in hypothesis mode, so the models and CSVs of other projects never carry one.

  | Field | Value |
  | ----- | ----- |
  | `claims` | At least one, each once. Connection: `existence`, `direction`, `sign`. UC: `population`, `transmitter`, `modulation`, `role` (`role` only marks the UC) |
  | `basis` | One of, from the most to the least direct: `published` (a paper states it as a hypothesis: Literature type Hypothesis, Modeling, Opinion, …), `homology` (a homologous region in another species whose homology is uncertain; direct evidence in another species is ordinary evidence with its Taxon), `analogy` (an analogous circuit), `indirect` (functional connectivity, co-activation, lesions, undirected DW-MRI, …), `model` (a computational model requires it), `functional-need` (only the FRG needs it to realize the TLF) |
  | `rationale` | Not blank (checked after trimming): why the premises support the hypothesis and what was searched without finding direct evidence, with `[Author, Year]` citations (checked like any free text, 6.7); no predictions, tests or next steps |
  | `premises` | At least one Reference ID of `references.json`, verified like every reference; for a connection the first is the record's `referenceIds[0]`. The `premises` of a `hypothesis` key count as uses of their references in the citation check (a `premises` key anywhere else is free text, as before) |
  | `scope` | `S<n>`: the scope that allows the hypothesis |
  | `researchCandidate` | Research mode only (6.11): the `research.json` candidate (`C<n>`, status `not_found` or `weak`) that records the search; omitted otherwise |

- **Checks** (`hypothesisProblems`, in `checkHcd` when the HCD files are usable). They also depend on files outside the HCD's phase hash (GN targets on `frg.json`, candidates on `research.json`, the report), so the FRG and CSV checks run them again when the HCD files did not change (`hypothesisRecheck`; problems already left when the HCD was accepted are not sent again, new ones are prefixed `HCD (hypotheses checked again against the current files):`). Every problem is an error sent back as a fix turn, and each message says what to change (fix the field, cite a paper as evidence, or remove the hypothesis). Marked "safer side": stricter than the spec requires.

  | Check | The message asks to |
  | ----- | ------------------- |
  | Schema of the key (in every mode): claims from the element's list, basis, a rationale string, premises, scope and candidate IDs, no other keys; a blank rationale (code check) | fix the key |
  | A claim or a premise listed twice | list each once |
  | A premise not in `references.json`; a premise without DOI and PMID (safer side: it cannot be verified) | give a premise the worker can look up |
  | Connection: `premises[0]` is not `referenceIds[0]` | put the record's paper first (its taxon, pointers and quote state the premise) or cite the premise in `referenceIds` |
  | `existence` without `measurementMethod` `Hypothetical`; `Hypothetical` on a direction / sign hypothesis or on a record without a hypothesis (safer side: `Hypothetical` marks existence hypotheses only) | set `Hypothetical`, keep the paper's method, or add the key |
  | An `existence` hypothesis on a sender → receiver that a record without an existence claim already supports | remove the hypothetical record |
  | A second `existence` hypothesis record for the same sender → receiver (safer side: one hypothetical record per pair, so the share is not inflated) | keep one record and list the further papers in its premises and rationale |
  | `population` without `sourceOfId` `makeshift`; `population` on an anchor-only UC, a whole SABRA unit (safer side: only faceted populations) | set `makeshift`; add the facets or use another claim |
  | `transmitter` with an empty `transmitter`, `modulation` with an empty `modulationType` (safer side) | give the estimated value |
  | No scope covers the claims and the element | remove the hypothesis; the message lists the scopes and the claims no scope allows |
  | Each claim is allowed on the element by some scope, but no single scope allows them all (`scope` names one scope) | keep only the claims one scope allows |
  | `scope` unknown or not covering while another scope covers | write the covering scope |
  | Research mode: `researchCandidate` missing, not a candidate of `research.json`, `contradicted` (remove), `supported` (use that evidence instead), any status other than `not_found` / `weak`. Without research mode: any `researchCandidate` | fix or leave out the candidate |
  | Share above the limit (below; the message gives the counts and the number the limit allows) | reduce the hypotheses, never add connections or UCs to lower the share, and say so in `message` when the TLF cannot be realized within the limit |
  | Report (below) | add the section, the IDs or the sentence |

- **Projects that do not allow hypotheses** (`evidenceMode` absent or `strict`): `strictHypothesisProblems` sends back one message per file listing the UCs / connections that have a `hypothesis` key (any value): the project uses literature-supported evidence only, so support the element with a paper and its quote or leave it out; a request in an instruction's text does not allow hypotheses, and when the user asked for them the agent says in `message` that the instruction must be sent again with "Allow hypotheses" switched on. Before this version the key was a schema error. `Hypothetical` stays a plain enumeration value there and is not checked.
- **Share** (`hypothesisShare`, over the whole project version, all scopes together): hypothesis connections ÷ all `connections[]` records, and hypothesis UCs ÷ all `ucs[]` (ROI-internal and external; Collections not counted); each element counts once, whatever its claims. Allowed: at most `floor(p × total / 100)`, `p` being the limit as a whole percentage (`maxHypotheses`; exact integer arithmetic, so 2 of 10 pass at 20 % and 3 do not). Exactly at the limit is allowed; a total of 0 gives a ratio of 0. Limits 10 / 20 / 30 / 50 % (`HYPOTHESIS_MAX_SHARES`), default 20 %.
- **IDs** (`hypothesisRecords`): `H1`, `H2`, … first for the UCs in `uc.json` order, then for the connections in `connections.json` order; they change when hypotheses are added or removed. The CSV comments, `hypotheses.json`, the report check and the cross-check record use the same IDs.
- **Report** (at least one hypothesis and a non-empty `report.md`): a `## Hypotheses` section that names every worker ID (`H1`, … as whole words); the agent rules ask for it before `## Limitations` as a table (ID, element, claims, basis, premises, rationale; `functional-need` in bold) with the two shares against the limit. When there is **no evidence-only path** (`evidencePaths`: no directed path from a ROI input — `noROI(input)` / `noROI(input,output)` — through the ROI to a ROI output without hypothesis connections; chains through external UCs count), `## Limitations` must say so (the check looks for "evidence-only path"; the message gives the sentence `NO_EVIDENCE_PATH_SENTENCE`, "No evidence-only path leads from the ROI inputs to the ROI outputs.", followed by `HYPOTHESIS_PATH_SENTENCE`, "Every such path uses at least one hypothesis connection.", when the hypothesis connections do complete such a path). The agent rules also ask for facts only under `## Limitations` in these projects (open questions and survey gaps as what is not known, no future work), which replaces "future work" in step 8 of the HCD spec for them.
- **Export** (`buildCsvs`; no new columns, so every BRA column keeps its position):
  - The Comments of a hypothesis connection (`Connections.csv`), of a hypothesis UC (`Circuits.csv`) and of its `U.` row (`FRG.csv`) start with `Hypothesis (<claims joined by ", ">; <basis>): <rationale on one line>`, then a line break and the usual comment (with the `noROI(...)` tag and `Uniform in this project: …`). Elements without a hypothesis keep their Comments.
  - An existence hypothesis has Measurement method `Hypothetical` and a population hypothesis Source of ID `makeshift` (required by the checks, written as given).
  - A GN that depends on hypotheses (`gnHypothesisDependencies`: its UCs, all levels, include a hypothesis UC, or its two or more UCs are not connected among themselves without hypothesis connections, direction ignored, in which case every hypothesis connection between them counts) ends its Comments with `Depends on hypotheses: H2, H5` (after the motif note, `; `-separated).
  - The CoBRAC xlsx and the Template-v2-2 workbook (6.12) take these values from the CSVs. The template's Credibility rating is not written; it stays the template's own.
  - In hypothesis mode the graph builder (`GraphSources.hypothesisLines`, set by the worker for the published graphs and the article figures) reads a circuit's ROI tag and a connection's sign from the Comments without the hypothesis line (`stripHypothesisLine`, per Connections row before rows of the same pair are merged), since the rationale describes the premises, not the element. Other projects' graphs are built as before.
- **`{P}/hypotheses.json`** (worker only, hypothesis mode only; `buildHypothesesFile`, rewritten at every HCD / FRG / CSV check and validated against `HYPOTHESES_SCHEMA` before it is written, a mismatch being only logged): `checkedAt`, `mode` (`hypothesis`), `scopes`, `share` (`connections` and `ucs`, each `count`, `total`, `ratio`, `limit`), `hypotheses[]` (`id`, `element` — `{ kind: "uc", circuitId }` or `{ kind: "connection", sender, receiver, referenceId }` —, `claims`, `basis`, `scope`, `premises`, `rationale`, optional `researchCandidate`), `evidenceOnlyPath`, and `gns[]` (`id`, `hypotheses`: the IDs the GN depends on) once a usable FRG exists (absent from the HCD phase's check).
- **`{P}/cross_check.json`** (6.13): in hypothesis mode the record gains `hypotheses`: `count`, `evidenceOnlyPath`, `pathWithHypotheses` (a ROI input → output path exists when hypothesis connections count too) and `gns` (as in `hypotheses.json`). Record-only, like the findings.
- **Agent rules** (`prompts/phases/HYPOTHESIS.md`, filled by `hypothesisRules` with `{P}`, `{SCOPES}` (one line per scope, `describeScope`, with the note quoted), `{MAX_SHARE}` and `{RESEARCH_MODE}`): what is relaxed; the scopes and membership; search first (a paper that states the claim is evidence, a contradicted claim is never included, research mode records the search as a candidate); the key; connections (the quote states the premise); UCs; the FRG (inside a scope, step 5's "Do not invent UCs or connections" does not forbid a hypothesis, logged as `[FRG->HCD][hypothesis]` under `## HCD-FRG revisions`); what the worker writes; the share; the report; removing or replacing hypotheses only when an instruction asks (`[hypothesis] H3 → evidence [Author, Year]` in the decision log); and no proposals of investigations, experiments, tests or predictions anywhere. The worker appends it after the HCD / FRG phase spec (after the research-mode notes, before the FRG candidates) in phase prompts and in fix prompts that attach the spec, after the reference specs of follow-up and fresh-thread prompts, and to the adjustment turn (6.13). The research step's prompt does not get it.
- **BRA 274** (the quote must guarantee the connection) is judged on the **premise** for a hypothesis connection: its `pointersOnLiterature` quotes the sentence of the premise paper (`premises[0]` = its Reference ID) that states the premise, and the quote check (6.7) verifies it against that paper like every quote. The record is marked by its Comments line (and `Hypothetical` for existence). `scripts/bra-appendix-d.mjs` checks `cobrac:hypothesis-marked` (6.9) and counts the hypothesis quotes under 274 separately.
- **Strict projects are unchanged**: their phase, fix, follow-up, fresh-thread and adjustment prompts are byte-identical (`HYPOTHESIS.md` is not appended; `AGENTS.md`, `HCD.md`, `FRG.md`, `HCD_roi_rules.md`, `FRG_gn_rules.md` and `research_mode.md` did not change); for files without a `hypothesis` key the check results, CSVs and xlsx are identical; they get no `hypotheses.json` and no `hypotheses` in `cross_check.json`. What changes for every project: the schema files in `/work/schemas/` carry the optional key (its description tells the agent to omit it outside hypothesis mode), so a version's `schemasSha256` changes, and `promptsSha256` changes because `prompts/` has a new file (6.20).

### 7.1 Token usage and cost

- `usage` is `{ inputTokens, cachedInputTokens, outputTokens, reasoningOutputTokens }`. Codex's `turn.completed` carries the **thread's running total** (kept across resumed runs), not the turn's own tokens, so the worker adds the difference to the job: the total after the turn minus the total before it, read from the thread's session file (`<CODEX_HOME>/sessions/…/rollout-…-<threadId>.jsonl`, last `token_count` event; `runTurn` in `packages/worker/src/codex.ts`). A turn that ends in `turn.failed` is measured from the session file too. A turn that never returns — cut off by a cancel, the research step's time budget, a SIGTERM or the 6-hour run-time limit, or dropped by a `codex exec` that exits without a failed turn — is measured the same way (`InFlightTurn`: the running turn registers a measurement, and whichever stop path comes first takes it once) and added to the job that ran it; the next run on the thread starts from a session total that already includes it, so nothing is counted twice. It then re-aggregates the project from all jobs (`refreshProjectUsage`). Jobs recorded before this fix (workers started before `USAGE_FIX_AT`, 2026-10-01 18:33 UTC, 0.17.1) added the running total every turn, so their stored usage and cost are too high (about 2–3x for a full run). The stored records are not rewritten; the API corrects them when it returns them (`packages/shared/src/usageCorrection.ts`, `packages/api/src/lib/usageCorrection.ts`): from the job's usage rows (`kind: "usage"` status messages) it takes each turn's running total, counts only its increase (a total that drops starts a new conversation, and a job that continues the project conversation starts from the previous job's last total; article jobs have their own), and reprices the result. The project list, the project and its jobs, the usage summary, the admin list and the usage rows of the chat show the corrected values; corrections of finished jobs are cached per Lambda container.
- `model` is the model actually passed to Codex at job start. On project create, the API **always resolves a concrete model name** (request → user default → `CODEX_MODEL` → `DEFAULT_CODEX_MODEL` = `gpt-6-luna`). The picker lists GPT-5.6 and GPT-6 text models only. An unknown “Codex default” model is never left behind.
- `costUsd` is an **estimate** from `estimateCostUsd()` using the rate table in `packages/shared/src/pricing.ts` (USD / 1M tokens, dated `PRICING_AS_OF`). Formula: `(input − cachedInput) × input rate + cachedInput × cache rate + output × output rate` (reasoning is included in output). Models missing from the table become `null` and the UI shows `$—`.
- The rate table is a code constant. When OpenAI changes prices, update `PRICING` and redeploy. The OpenAI dashboard is the source of truth for actual charges.

**Project IDs and names**

- ID formats (`packages/shared/src/projectId.ts`, `canon.ts`). Every check accepts both current forms:

  | Kind | Issued now (random) | Issued earlier, from 0.7.0 (still valid) | Accepted by |
  | ---- | ------------------ | --------------------------------- | ----------- |
  | Project | `^p[0-9a-hjkmnp-tv-z]{7}$` (`p7m2q9xa`) | `^u[0-9a-hjkmnp-tv-z]{7}-[1-9][0-9]*$` (`u7m2q9xa-12`) | `PROJECT_ID_REGEX` / `isValidProjectId` |
  | Canon | `^c[0-9a-hjkmnp-tv-z]{7}$` (`c4h8w2rk`) | `^u[0-9a-hjkmnp-tv-z]{7}-c[1-9][0-9]*$` (`u7m2q9xa-c1`) | `CANON_ID_REGEX` / `isCanonId` |
  | Plan (BRA Planner) | `^n[0-9a-hjkmnp-tv-z]{7}$` (`n4h8w2rk`) | — | `PLAN_ID_REGEX` / `isPlanId` |

  The 7 characters are lower-case Crockford base32 (no `i l o u`) drawn from the platform CSPRNG (32⁷ ≈ 3.4×10¹⁰ values). Legacy per-user slugs (before 0.7) never match these patterns and are still resolved for redirects. A BRA version is `<projectId>@v<n>` for either form.
- Creation: the API draws a random ID and reserves it with a conditional Put of a Catalog row (`kind = id`, `attribute_not_exists(id)`); if the ID is taken it draws again (up to 5 times). Only then does it move attachments and Put the project with `attribute_not_exists(projectId)`. The reservation is what makes the ID globally unique (the Projects table is keyed by `userId`, so its own condition sees only the caller's projects). Reservations are never deleted, so an ID lost to a failed creation or a deleted project is not reused. Canons are created the same way (`type = canon`) before the Canon's META item is put. The per-user counters `projectSeq` / `canonSeq` are no longer used.
- Order: `/projects` lists the caller's projects newest first by `createdAt` (ties by ID), since the sort key no longer carries a sequence; `limit` and `cursor` (an offset into that order) page through them.
- `name` starts as a provisional `<TLF> in <ROI>` built from the ROI/TLF as typed, in any language (e.g. `VOR in 小脳`; `nameSource = "provisional"`). When the HCD phase is accepted, the worker stores the English `name` the agent wrote to `meta.json` (`<TLF> in <ROI>`) and sets `nameSource = "auto"`; it does so only while `nameSource` is `provisional` or `auto`. Older projects whose `auto` name is still the old ASCII slug (e.g. `VOR` for TLF `VOR` / ROI `小脳`) are shown, and named in downloads, with the provisional name instead. A name typed at creation or edited later is normalised (NFC, trimmed, whitespace collapsed; control characters and line breaks rejected) and sets `nameSource = "user"`; the agent never overwrites it.
- The xlsx `Project ID` column holds the ID; `Description` is prefixed with the name when it is English.
- Download file name `{name}_{ID}.bra.xlsx`: NFC, control characters, `/ \ : * ? " < > |` and whitespace runs become `_`, repeated `_` collapse, leading/trailing `_ .` and spaces are removed, cut to 80 code points; empty → `{ID}.bra.xlsx`. Sent as `filename*=UTF-8''…` with `filename="{ID}.bra.xlsx"` as the ASCII fallback. S3 keys and work directories use the ID only.
- Deleting a project is a soft delete: `DELETE /projects/{id}` sets `deletedAt` / `deletedBy` on the Projects item (conditional on the project not being deleted and not being `QUEUED` / `RUNNING` / `WAITING_USER_INPUT` / `FINALIZING`) and nothing else. Jobs, Messages and S3 objects stay as they are, the ID is never reused, and no index is added (the flag is filtered in the API). For the owner a deleted project behaves like a missing one: it is left out of `/projects`, name-duplicate warnings and legacy-ID redirects, and every `/projects/{id}/…` route and WebSocket subscribe returns 404 / not found. A running project has to be stopped first (409). `/users/me/usage` keeps its cost in the totals and flags it `deleted` in `byProject`; `/admin/projects` lists it with `deletedAt` and the admin page shows it as deleted. There is no restore screen; restoring means removing `deletedAt` from the item (a future admin API)
- Migration of legacy IDs: `scripts/migrate-project-ids.mjs` (dry run by default; `--apply` writes). Each legacy project is copied under its new ID (Projects with `legacyId`, its Jobs / Messages, S3 with renamed folders). The old Projects item is saved to `users/{userId}/{legacyId}/migration-backup/project-item.json` and deleted, so the project is listed once and old URLs redirect. `--keep-old` keeps the old Jobs / Messages items as a backup; old S3 objects are never deleted. Re-running also removes an old Projects item left next to its migrated copy.

### 7.4 Reference materials

The create screen accepts up to 10 files (PDF, PNG / JPEG / WebP / GIF, TXT / MD / CSV / TSV / JSON, DOCX / XLSX / PPTX; 20 MB each, 50 MB in total) and up to 20 http(s) URLs (`packages/shared/src/attachments.ts`).

1. Each file is sent straight from the browser to S3: `POST /uploads` checks the name and size and returns a presigned POST whose policy pins the staging key, the Content-Type and the size range. The bucket's CORS allows POST from the CloudFront domain, `https://cobrac.site` and `http://localhost:5173`.
2. `POST /projects` checks each staged upload (it must exist and fit the limits), moves it to `attachments/files/`, and stores the list in `Projects.attachments` (`kind: "file"`: name, key, size, contentType; `kind: "url"`: url). URLs must be http(s) with a public host.
3. On each run the worker mirrors `attachments/` to `/work/materials/`. The first run derives, once: PDF text (`pdftotext`), Office text (DOCX / PPTX / XLSX shared strings), and URL content (HTML as text, PDF with its text, images; at most 10 MB, 20 s, 5 redirects, every hop must resolve to a public address). The result is stored in `attachments/derived/` with a `manifest.json` and reused by later runs. A failed item is only marked as failed.
4. `materials/INDEX.md` lists every item with its original, its text and its status. The prompt header gets a `Reference materials:` line, images are attached to the first prompt of a new thread, and `prompts/AGENTS.md` tells the agent that the materials are to be consulted but are not verified literature: references still need published sources (checked against Crossref / PubMed) and quotes must be verbatim from those sources.

## 9. Frontend design

- Vite + React 18 + React Router + Tailwind.
- Runtime config is CloudFront `/config.json` (apiUrl, wsUrl, userPoolId, userPoolClientId, region). Local uses `VITE_*`.
- Graphs: `@xyflow/react` + dagre (HCD top to bottom, FRG left to right). HCD colors nodes by ROI class (fill plus a stripe) and sets default edge style from projection physiology (excitatory / inhibitory / modulatory). FRG colors by kind. Labels grow when zoomed out; self-connections are drawn as loops.
- Viewing: selecting a node dims everything except its neighbours (HCD) or its ancestors and descendants (FRG); selection from outside the canvas (URL, search, detail links) recentres the view above the detail sheet. The search box ranks nodes by ID, name and UC Descriptor (↑ ↓ Enter, `/` to focus). Toolbar: search, fit, undo/redo, style edit mode, and a menu with layout direction, grid snap, page options (edge labels, expand/collapse all), PNG export and reset. Pure helpers live in `packages/web/src/lib/graphView.ts` (vitest).
- Style edit mode (toolbar button): style panels, resize handles and connection handles appear only in this mode; on touch devices nodes are draggable only in this mode.
- Nodes: drag to move, resize from corners/edges, change fill and border in the style panel.
- Edges: click to open the style panel (in style edit mode). Line type (curve / straight / orthogonal auto / **orthogonal with waypoint editing** / polyline), color, width, dash, corner radius, and start/end markers (arrow, open arrow, square, circle, diamond, bar). Orthogonal edges add waypoints with “+” on the path, drag to bend, double-click to delete.
- Connection handles: drag the circles at both ends of the selected edge onto node-edge handles (7 points per side) to change start and end.
- Default line type is a curve. Layouts saved under the earlier orthogonal default may have bends without an explicit line type; those edges stay orthogonal so the bends are kept.
- Edges that share a pair of nodes (A→B and B→A of a feedback loop, or several A→B) are drawn on separate lanes 20 flow units apart (`lib/parallelEdges.ts`): every edge sits on the right-hand side of its own direction of travel, its ends slide along the node side (never past the corner), curves bow apart in the middle, and orthogonal / step routes move their middle segment. The labels go to each lane's outer side and are narrowed when they would cover the end markers on a short connection (full text when the edge is selected or highlighted). Repeated self loops on one node nest outside each other. Lanes are computed when drawing and never saved; an edge with user-drawn waypoints keeps its own route.
- Inhibitory default: blue (`#2563eb`) + square end. Excitatory: gray + triangle. Modulatory: purple dashed + circle. Classification prefers Connection comments, otherwise the sender’s Transmitter / Modulation Type (`classifyEdgeSign`). The same style can be applied to all edges of that class.
- Layout persistence: `useGraphLayout` saves position, size, color, and edge style (including waypoints and handles) to `PUT .../layout` with a 600ms debounce. Same node ID / edge ID is kept after graph regeneration. Ctrl+Z / Ctrl+Y undo/redo.
- Chat is Markdown (GFM). Commands / thinking / web search are collapsed.
- Version: root `package.json` `version` is injected via Vite `define` as `__APP_VERSION__`, plus `git rev-parse --short HEAD` as `__APP_COMMIT__`. Operating rules are in `AGENTS.md`.

## 10. Worker internals

Entry: `packages/worker/src/index.ts`.

1. Read Users / Projects / Jobs, choose the key (the user's own; else the default API key while the user is approved and the tier allows the job's model, section 4.1; `planRunKey` in `packages/worker/src/runKey.ts`) and decrypt it with KMS.
2. Copy `prompts/AGENTS.md` to `/work` and write the JSON Schemas to `/work/schemas/`. For resume / followup / retry, restore workspace and thread from S3.
3. `createCodex` → `openThread` (`sandboxMode: danger-full-access`, live web search, the `lit` MCP server). Each turn opens the thread with its own settings, so research turns can run at a higher reasoning effort.
4. In research mode, run the research step if the workspace has not finished it (section 6.11). Then run the phases (section 6.4). Write events to Messages and update stepStates and activeStage on every file change (activeStage is `RESEARCH` during the research step and `ADJUST` during the adjustment turn, otherwise the running step).
   - A turn fails only on `turn.failed`, or when the stream ends on an `error` event without `turn.completed`. Codex reports its own retries of a rate-limited request as `error` events ("Reconnecting... 2/5 (rate limit exceeded …)"); they are shown as status lines and the turn goes on. Non-fatal notices that Codex reports as `error` items (for example "Model metadata for `x` not found" or "Falling back from WebSockets to HTTPS transport") are also shown as status lines; real errors stay errors. A turn that still fails on an OpenAI rate limit (TPM / RPM, HTTP 429; not an exhausted quota) is resumed on the same thread after a pause (the server's "try again in …" plus 5 s, at least 30 s / 60 s / 120 s, at most 3 min), up to 3 times, with heartbeats during the pause; only then does the job fail.
   - A single request larger than the tokens-per-minute limit ("Request too large … Limit 200000, Requested 202304", 200k for gpt-6-luna) never passes with time: once a thread's context reaches the limit, every later turn on it is refused. To keep threads well below it, Codex compacts the conversation at `CODEX_AUTO_COMPACT_TOKENS` (default 75,000; `model_auto_compact_token_limit`). The limit is also about speed: in production runs a request with more than about 80k tokens of context waited 15–40 s longer for its answer than a small one, and most of a job's time went to such requests; a compaction itself takes a few seconds. If a turn is still refused as too large, it is not retried on the same thread: the worker starts a new thread once and sends the same request with the project header, a note that the files hold the work so far, and the HCD / FRG specs. After a failed turn, `codex exec` exits with code 1; the turn's own error is reported instead of that exit.
   - Model metadata: the Codex CLI (installed with `@openai/codex-sdk`) needs catalog metadata for the model, or it runs on fallback metadata and warns "Model metadata for `x` not found". Every model in the price table must be in the catalog of the installed CLI (`codex debug models --bundled`; checked by `packages/worker/test/codexCatalog.test.ts`). The `gpt-5.6` alias is not in the catalog, so the worker hands Codex `gpt-5.6-sol`, the model OpenAI routes it to; the job still records the model the user chose. `model_context_window` is set to 272,000 for every model: OpenAI lists 1,050,000 tokens for the gpt-5.6 / gpt-6 models, but input above 272K is billed at 2x, and Codex's catalog uses 272,000 for all of them. Compaction (75,000) stays well below it. Codex has no setting for the maximum output tokens (128,000 for these models).
5. Diff-sync to S3 after each accepted phase and immediately before waiting for a question, completion, or failure.
6. After CSVs are complete, `finalize.ts` uploads xlsx and graph JSON.

Mode `article` branches off after step 1 (`articleJob` in `index.ts`, loop in `article.ts`): restore the workspace only, draw the figures, one article turn plus fix turns, upload the figures and `article/<locale>.md` / `.json`, project back to `COMPLETED`.

Mode `plan` (a BRA Planner draft or re-plan, section 6.22.1) also branches off after step 1 (`planJobMain` in `index.ts`, `runPlanJob` in `planJob.ts`): no project and no workspace; it reads `plans/{planId}/jobs/{jobId}/input.json`, prepares the attached capability lists like reference materials, runs one Codex turn with the RCS MCP and `PLAN_RESULT_SCHEMA` (no web search, no `lit`; one retry when the reply does not parse; aborted after `PLAN_JOB_TIME_BUDGET_MS`), drops HOMBA anchors RCS does not know, writes `result.json` and records usage and cost on the job only.

The agent’s shell environment has `AWS_*` credentials cleared so the task role cannot leak.
