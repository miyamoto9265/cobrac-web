## 1. Purpose and scope

CoBRAC Agents is a web app that runs BRA (Brain Reference Architecture) data creation in the browser via the Codex SDK. The same work was previously done with Cursor Agents on the desktop.

**Input**: ROI (target brain region) and TLF (top-level function). Either field alone is enough (the agent researches and fills in the rest).

**Output**: HCD / FRG data as JSON files, a markdown report and decision log, five CSVs, `.bra.xlsx`, the same data in the official Template-v2-2.bra workbook (`.template-v2-2.bra.xlsx`), and HCD/FRG graph JSON.

**Out of scope for v1**: project sharing / co-editing, manual artifact editing in the web UI, billing plans, a mobile app, and a custom domain.

## 2. Glossary

| Term | Meaning |
| ---- | ------- |
| Project | One BRA creation unit. Identified by `projectId` = `<userKey>-<seq>` (e.g. `u7m2q9xa-12`): globally unique, assigned by the system, never changed or reused. `name` is the editable display name (any language, 1–200 characters, may repeat) |
| userKey | Pseudonymous per-user key (`u` + 7 lower-case Crockford base32 characters) issued once on first sign-in. Namespace of the user's Project IDs; it does not identify the current owner |
| Job | One worker run. Type is `initial` / `followup` / `article`. Resume mode is `resume` / `retry` |
| HCD | Hypothetical Component Graph. UCs (nodes) and Connections (edges) |
| FRG | Function Realization Graph. Hierarchy of TLF → GN (`R.`) → UC (`U.`) |
| Response loop | After the agent ends a turn with a question, the user answers and the job resumes |
| Follow-up | After completion, a job that sends a revision instruction on the same thread and regenerates artifacts |
| Explanatory article | Optional reading of a finished project in a language the user picks (`article/<locale>.md`). Not a core artifact (section 6.8) |

## 3. System architecture

```
Browser (React SPA)
  ├─ Cognito SRP login (ID token)
  ├─ CloudFront + S3 (static hosting + /config.json)
  ├─ HTTP API (API Gateway JWT → Lambda / Hono)
  └─ WebSocket API (query token → subscribe project)

Lambda
  ├─ http        REST
  ├─ dispatcher  SQS → ECS RunTask
  ├─ ws          $connect / $disconnect / default
  ├─ broadcaster DynamoDB Streams → WebSocket
  └─ janitor     liveness / timeout every 15 minutes

ECS Fargate Spot (1 vCPU / 2 GB)
  └─ Codex SDK worker (1 job = 1 task)
       ├─ DynamoDB (state and messages)
       ├─ S3 (workspace / thread / output / graph)
       ├─ KMS Decrypt (that user's API key only)
       └─ OpenAI API (each user's own key)
```

Package layout:

| Package | Role |
| ------- | ---- |
| `@cobrac/shared` | Types, CSV parser, `buildGraphs()`, Project ID / name rules (`projectId.ts`) |
| `@cobrac/api` | Hono app and Lambda handlers |
| `@cobrac/worker` | Codex control loop, S3 sync, xlsx / graph finalization |
| `@cobrac/web` | SPA (auth, chat, graphs, settings, admin) |
| `@cobrac/infra` | CDK stack `CobracAgents` |

## 6. Workflow design

### 6.1 Steps

`HCD → FRG → CSV → XLSX`

The worker (the "CoBRAC harness", v1.1 since app 0.8.0; see `docs/05_CoBRAC_Harness_v1_to_v1_1.md`) drives the phases itself. A phase is marked done only when its deterministic validator accepts the files; file presence only marks it running. CSV and xlsx are produced by the worker, not the agent.

### 6.2 Job lifecycle

```
POST /projects
  → Projects/Jobs = QUEUED
  → SQS
  → dispatcher (re-queue after 60 seconds if at concurrency limit)
  → ECS RunTask (Spot, On-Demand on failure)
  → worker RUNNING
       ├─ status "question" → save to S3 → WAITING_USER_INPUT → task exits
       │     └─ POST /answer → QUEUED → resumeThread
       ├─ HCD ✓ → FRG ✓ → CSV (from the JSON files) → FINALIZING → csv_to_excel.py + Template-v2-2 export + buildGraphs → COMPLETED
       │     └─ POST /followup → new job (same thread)
       └─ failure / Spot interruption / >6h → FAILED (janitor auto-retries up to 2 times)
```

### 6.3 Execution modes

| mode | Trigger | Prompt notes |
| ---- | ------- | ------------ |
| initial | New project | Phase HCD prompt (inlines `prompts/phases/HCD.md`); in research mode the research step comes first (section 6.11) |
| resume | Answer to a question | Pass the answer and continue the current phase |
| followup | Instruction after completion | Apply the instruction, then re-validate HCD and FRG and regenerate CSV/xlsx |
| retry | Manual resume after failure/cancel, or janitor auto-resume | Continue from the first phase not accepted yet; keep existing artifacts |
| article | `POST /articles` on finished BRA data (janitor re-runs a stalled one in the same mode) | Fresh thread, `prompts/article.md`, no web search or RCS; the workspace is read-only (section 6.8) |

Reply language: create / answer / follow-up / retry requests carry the web UI language (`locale`: `en` / `ja` / `zh` / `zhTw` / `ko` / `de` / `fr` / `es` / `pt` / `ru`), stored on the job. Every turn then ends with a hidden line telling the agent to write `message` and `question` in that language (artifacts stay English). Without `locale` the agent replies in the language the user wrote in; a retry without it keeps the previous job's language.

resume / followup / retry on a workspace made before v0.8 (markdown tables such as `3_UC.md`, no `uc.json`) fail at once with `sys.legacyWorkspace`; its xlsx and graphs stay viewable.

### 6.4 Turn control

1. Run one turn with Codex `runStreamed` (with `outputSchema`) and persist events to Messages.
2. If the final message has `status: "question"`, write state to S3 and exit (billing stops).
3. After each turn, validate the current phase (`checkHcd` / `checkFrg` in `packages/shared/src/harness.ts`): JSON Schema, cross-file references, UC naming, interfaces, FRG constraints, English-only values, and the report sections. The references are checked in the same step (`checkCitations` in `packages/shared/src/references.ts`, `ReferenceVerifier` in `packages/worker/src/references.ts`; see 6.7). On problems, send the list back as a fix prompt, up to `MAX_NUDGES` (3) times per phase. If problems remain, continue with a warning; if the output is unusable, fail the job. The loop is `runPhases` in `packages/worker/src/pipeline.ts`.
4. When a phase is accepted, send the next phase prompt. A later phase whose files already pass (for example after a follow-up) is not rebuilt. When the agent changes HCD files during FRG or CSV (or FRG files during CSV), the later phase validates them again and sends back their new problems with its own (6.13).
5. CSV: `buildCsvs` generates the five CSVs deterministically from the JSON files. The agent never writes CSVs; if generation fails, the problems go back as a fix prompt for the JSON files.
6. Cut off after 6 hours of continuous execution.

### 6.5 Models and reasoning effort

Resolution order: **project setting → user default → deploy environment variable → Codex default**.

- On key registration, call OpenAI `/v1/models` and store gpt-5 family models in `availableModels`.
- Selectable on the create and settings screens. Effort values: `minimal` / `low` / `medium` / `high` / `xhigh` / `max` / `ultra` / `persistent`.
- Follow-up and retry use the same project settings.
- Research mode (section 6.11) raises the effort of its research turns to at least `high`; the other turns keep the project's effort.

### 6.6 Agent contract (instructions)

- `prompts/AGENTS.md` holds the rules shared by every phase. It is copied to the workspace root, where Codex loads it automatically.
- `prompts/phases/{HCD,FRG}.md` are the phase specs. The worker inlines them into the phase prompt. The JSON Schemas of the data files (`HARNESS_SCHEMAS` in `harness.ts`) are written to `/work/schemas/*.schema.json` for the agent to read; the validator uses the same objects.
- Every artifact is written in English. The project summary goes in `{P}/meta.json` (`roi`, `tlf`, `description`, `name`); an ROI/TLF the user left empty is copied to the project.
- The final message of every turn is JSON: `{status: "done" | "question", message, question}`. The legacy `[QUESTION]...[/QUESTION]` marker is still recognized for old threads.
- Files (v0.8). Structured data is JSON, free text is markdown:

  | File | Format | Written in | Content |
  | ---- | ------ | ---------- | ------- |
  | `{P}/meta.json` | JSON | HCD 1 | `roi`, `tlf`, `description`, `name` |
  | `{P}/decision_log.md` | md | any time | Decisions the agent took itself and why (ROI/TLF validity, ROI_Input/Output, anchor choices, rejected alternatives, user answers, follow-up changes). Raw RCS calls are not copied (see `rcs_mcp_calls.jsonl`) |
  | `{P}/report.md` | md | HCD 8, FRG 6 | Report for the user: `## Overview`, `## HCD`, `## FRG`, `## Limitations`, `## References` |
  | `{P}/{P}_HCD/references.json` | JSON | HCD 2 | `references[]`: `id` (`[Author, Year]`), `doi`, `literatureType` (BRA list, since 0.10); optional `pmid`, `title`, `journal`, `alternativeUrl` |
  | `{P}/{P}_HCD/uc.json` | JSON | HCD 3–6 | `ucs[]`: `circuitId`, `descriptor`, `names`, `roi` (`internal` / `noROI(input\|output\|input,output)`), `sourceOfId` (one value since 0.10; a list before), `transmitter`, `modulationType`, `comments`, `interface`, `outputSemantics`, `requirement`, `requirementRealization`, `capability`, `mechanism`, `implementation`; optional `collections[]` (6.10): `circuitId`, `descriptor`, `names`, `sourceOfId`, `subCircuits[]`, `comments` |
  | `{P}/{P}_HCD/connections.json` | JSON | HCD 2, 4 | `bif[]` (tissue-level projections) and `connections[]` (UC-to-UC: `sender`, `receiver`, `comment`, `referenceIds[]` (exactly one since 0.10), `taxon`, `measurementMethod`, `pointersOnLiterature`, `pointersOnFigure`) |
  | `{P}/{P}_FRG/frg.json` | JSON | FRG 3–5 | `nodes[]` (TLF and GNs): `id`, `subnodes[]`, `comment`, `interface`, `requirement`, `requirementRealization`, `capability`, `mechanism` |
  | `{P}/{P}_CSV/*.csv` | CSV | worker | `Project`, `References`, `Circuits`, `Connections`, `FRG`, generated from the JSON |
  | `{P}/rcs_mcp_calls.jsonl` | JSONL | worker | Every RCS call of the agent |
  | `{P}/reference_check.json` | JSON | worker | Result of the latest reference check: status and fetched record of each reference, where each Reference ID is cited, and the problems found (6.7) |
| `{P}/quote_check.json` | JSON | worker | Result of the latest quote check: for each connection, whether its Pointers on literature was found in the cited paper's full text or abstract, the texts compared, the best similarity and the closest passage (6.7) |
  | `{P}/cross_check.json` | JSON | worker | HCD ↔ FRG consistency of the latest FRG / CSV check (record-only; 6.13) |
  | `{P}/phase_baseline.json` | JSON | worker | Hash of the HCD / FRG data files and the problems left when their phase last checked them (6.13) |
  | `{P}/{P}_CSV/bibliography.json` | JSON | worker | Crossref / PubMed record of each DOI / PMID (authors, title, container, year, volume, pages…) for the BibTeX of the Template-v2-2 export (6.12) |

  The FRG's initial decomposition and optimization are working steps without files (their rationale goes into the report), and the HCD self-check has no file of its own (open points go into the report's limitations). Diagrams are not generated; the web graphs come from the CSVs. The markdown formats used before v0.8 are not read.
- The worker writes the CSVs and runs the xlsx conversion. `Circuits.csv` Comments get the `noROI(...)` tag from `roi`.
- UCs are named after SABRA units (`prompts/phases/HCD.md` "UC naming"): each UC has a **UC Descriptor** (anchor = one SABRA unit, `HOMBA:<id>` / `BNA:<n>` / `BNA:<l>-<r>` / `BNAG:<L2>`, plus optional facets for finer populations) and a **Circuit ID** = the anchor's official abbreviation `[@L|@R][(items)]`. Most UCs are a whole SABRA unit and have no facets (`HOMBA:12261` / `VTA`). The descriptor is the cross-project key (no UC numbering). It is `descriptor` in `uc.json`; `Circuits.csv` carries it after Comments (`UC Descriptor`) and the xlsx Circuits sheet as its last column, so the BRA columns keep their positions.
- The agent reaches the RCS MCP server (`rcs-mcp` of rosetta-candidate-search: `search_homba_candidates`, `search_bna_candidates`, `get_homba_term`, `get_sabra_definition`) to anchor UCs. The worker reads the bearer token from Secrets Manager `rcs/mcp-bearer-token` at start (newest token of the comma-separated value), passes it to Codex in an env var that agent shell commands do not inherit, looks up HOMBA anchors itself for validation, and appends every RCS call of the agent to `{P}/rcs_mcp_calls.jsonl`. Without a token or URL the run continues without RCS (the anchor check of HOMBA anchors is skipped).

`csv_to_excel.py` runs non-interactively with `--contributor` / `--project-id` / `--base-dir` / `--output`.

### 6.7 Reference checks

Every HCD / FRG check also checks the literature, so that invented papers and wrong identifiers go back to the agent in the same fix loop as the other problems.

- **Citations** (deterministic, `checkCitations`): every `[Author, Year]` in the free text of `uc.json`, `connections.json`, `frg.json` and `report.md` must be a Reference ID in `references.json` (a citation that differs only in spacing or case is asked to be written exactly); every reference must be cited somewhere other than the report's `## References` bibliography; two Reference IDs may not share a DOI or PMID. Unknown IDs in `sourceOfId` / `referenceIds` are still reported by `checkHcd`.
- **Lookups** (network, `ReferenceVerifier` in the worker): each DOI is looked up in Crossref (`api.crossref.org/works/<doi>`), and when Crossref does not know it, at doi.org by content negotiation (CSL JSON; DataCite, mEDRA, JaLC). Each PMID is looked up in PubMed (NCBI E-utilities `esummary`). The record must have the first author of the Reference ID (a later author is reported as such), a publication year within ±1 of it (online vs. print), and, when `title` is given, a similar title (word overlap). When both a DOI and a PMID are given, PubMed's DOI must be the same. A differing journal is only noted. For a reference without an identifier and with a title, a Crossref search that finds the same paper (title, first author, year) is suggested as its DOI.
- **Statuses** in `reference_check.json`: `verified`, `mismatch`, `not_found`, `invalid` (not a DOI / PMID), `no_identifier`, `unverified` (lookup failed). `mismatch`, `not_found`, `invalid` and a DOI suggestion are sent back as problems; like every other problem they become a warning after `MAX_NUDGES` fix turns. When a phase is accepted, the chat shows a one-line summary with the open references in its details.
- **Scope**: the FRG phase answers for `frg.json`, the report's `## FRG` section and the references cited only there; the HCD phase for everything else, so an HCD problem is not sent again during FRG. Only when the HCD data files change after the HCD check does the FRG / CSV phase run the HCD's reference and quote checks again (6.13).
- **Outages**: a request times out after 10 s and is retried twice on timeouts, network errors, 429 and 5xx (honouring `Retry-After` up to 10 s). A host that fails three references in a row is skipped for 5 minutes, and one check spends at most 3 minutes on lookups. References that could not be looked up are `unverified`, never a problem, so an outage does not hold up the phases. Found and missing identifiers are cached for the run; failures are retried at the next check. PubMed requests are spaced to 3 per second (10 with an API key).
- **Settings** (worker environment variables, not set by CDK): `REFERENCE_LOOKUP=off` turns the lookups off (the citation checks stay); `CROSSREF_MAILTO` sends a contact address to Crossref's polite pool; `NCBI_API_KEY` raises the PubMed rate. None is needed: Crossref, doi.org and E-utilities work without a key, and the worker reaches them through its public IP like OpenAI. To use an NCBI key, store it in Secrets Manager and add it to the worker container's `secrets` in `packages/infra/lib/cobrac-stack.ts` as `NCBI_API_KEY` (the task execution role needs `GetSecretValue` on it); the worker blanks it for the agent's Codex process.

**Quote checks** (manual review codes 273 / 274 / 279: Pointers on literature must be a verbatim quote from the cited paper). Every HCD check also compares each connection's `pointersOnLiterature` with the text of its paper (`QuoteVerifier` in the worker, matching in `packages/shared/src/quotes.ts`), so that invented or paraphrased quotes go back to the agent in the same fix loop. Quotes that already fail the format rules of 6.9 (too short, a locator) are left to those messages; references without a DOI or PMID cannot be checked.

- **Texts**, by DOI / PMID: the Europe PMC record (`search`, `resultType=core`) gives the PMID, PMCID, open-access flag and abstract. An open-access paper's full text is read from Europe PMC (`/<PMCID>/fullTextXML`, JATS: abstract, body, back matter and figure captions, without the reference list, citation markers, tables and formulas); when Europe PMC fails, from PMC through NCBI BioC (`pmcoa.cgi/BioC_json`). Without a full text, the first abstract found among Europe PMC, PubMed (`efetch`), Crossref (`abstract`) and Semantic Scholar is used.
- **Matching**: both sides are reduced to letters and digits (NFKC, so ligatures become letters; accents and case folded; soft hyphens, superscript and bracketed numeric citations and parenthesized author–year citations removed), so whitespace, punctuation, hyphenation across a line break, typographic quotes and citation markers do not matter. A quote is found when it is a substring, or else when the edit distance to the best passage (chosen among the word windows that share the most words with it) is at most 10 % of its letters (similarity ≥ `QUOTE_MATCH_THRESHOLD`, default 0.9), which absorbs OCR-like slips but not paraphrases. A quote with omissions (`…`, `...`, `[…]`) or editorial insertions (`[the VTA]`) is split there and every part of 3 or more words must be found.
- **Statuses** in `quote_check.json` (one entry per checked connection): `verified_fulltext`, `verified_abstract`, `not_found` (the full text was read and the quote is not in it), `unverified` (no open-access full text and the abstract does not have it, no identifier, or the texts could not be fetched). Only `not_found` is sent back, with the full-text link, the best similarity and the closest passage; a paywalled paper is never reported as a problem because its body cannot be read. The report also has `threshold`, `summary` and `problems`. When the HCD is accepted, the chat shows a one-line summary with the open quotes in its details.
- **Limits**: the same HTTP client as the reference lookups (10 s timeout, retries, 5-minute host cooldown, NCBI spacing); at most 2 minutes per check and 3 papers at a time. Each paper is fetched once per run (papers whose fetch failed are tried again at the next check). Semantic Scholar is used without a key and often answers 429; it is only the last abstract source.
- **Settings**: `QUOTE_CHECK=off` turns the check off (`quote_check.json` then has `lookup: "off"`); `QUOTE_MATCH_THRESHOLD` (0–1) changes the similarity. No key is needed; `CROSSREF_MAILTO` and `NCBI_API_KEY` apply as for the references.

### 6.8 Explanatory articles

The v0 HCD beginner explainer (`7_EasyToUnderstand.md`, removed in 0.5.0) comes back as an on-demand job instead of a phase:

- **When**: only when the project is `COMPLETED` with the xlsx generated (`stepStates.XLSX = done`) and no job is active. The user picks the language (default: the UI language; the 10 UI locales of `packages/shared/src/locale.ts`) and presses "Create article". Several languages can exist side by side; creating one again replaces it only when the new one passes the check.
- **Job**: `type: "article"`, `articleLocale`, run mode `article`. The project goes `QUEUED → RUNNING → COMPLETED` so that follow-ups wait for it, but its steps, `revision`, `completedAt`, codex thread and workspace are not changed. A failure or cancel sets `articleJob.status` (`FAILED` / `CANCELLED`) and puts the project back to `COMPLETED`, never `FAILED`. Retry of a failed project ignores article jobs.
- **Worker**: restores the workspace (not the thread), starts a fresh thread without web search or RCS, and sends `prompts/article.md` (reader: a final-year neuroscience undergraduate; narrative information flow; no tables copied; plain Markdown, no images or HTML). The agent writes `{P}/article/<locale>.md` locally; the workspace is never uploaded in this mode. `checkArticle` (`packages/shared/src/article.ts`) requires one `#` title, at least 3 `##` sections, a minimum length, the requested script, no images / HTML / hand-written reference list, and **citations only of `references.json` IDs** (`[Author, Year]`, one per bracket). Problems go back as fix prompts up to `MAX_NUDGES` times, then the job fails. The worker appends the reference list (localized heading, DOI links of the cited IDs) and uploads `article/<locale>.md` and `article/<locale>.json`.
- **Metadata** (`ArticleMeta`): `locale`, `language`, `title`, `createdAt`, `sourceRevision` (project `revision` at start), `jobId`, `model`, `citedReferences`. An article is **stale** when `sourceRevision` differs from the current `revision` (a later follow-up); the viewer says so and offers to recreate it.
- **Language rule**: articles are not core artifacts. The English-only checks (`readJson` in `harness.ts`, `buildCsvs`) and the CSV / xlsx / graph conversion never read them; `AGENTS.md` names them as the only exception to "every artifact in English".
- **Cost**: the job's tokens are added to the project usage like any other job.

### 6.9 BRA value rules (since 0.10)

The HCD check also enforces the values the BRA Data Preparation Manual and Template-v2-2.bra prescribe (`packages/shared/src/bra.ts`), so that the output does not produce the Review Tool errors 1, 10/11, 108, 252, 271/277 and 430 by construction:

| Item | Rule | Where |
| ---- | ---- | ----- |
| Source of ID (108) | One value: `DHBA`, `BNA`, `MBA`, `UBERON`, `collection`, `makeshift` or one Reference ID. Anchor-only UC on one HOMBA/DHBA term → `DHBA`; anchor-only UC on BNA areas / groups → `BNA`; faceted or mixed-atlas UC → the one defining Reference ID or `makeshift` | `uc.json` schema + `sourceOfIdProblem` |
| sCID / rCID relation | Each connection records, for both ends, the paper's own name for the circuit (`senderInLiterature` / `receiverInLiterature`) and the relation read as `<UC> <relation> <circuit in the paper>`: `<` the UC is part of the paper's coarser circuit, `>` the UC contains the paper's finer circuit, `=` the same. A notation equal to the Circuit ID is only allowed with `=`. The CSV / xlsx write them to sCID relation, Notation of sCID in Literature, rCID relation and Notation of rCID in Literature (before 0.10: always `=` and a copy of the Circuit ID) | `connections.json` schema + `relationProblems` |
| Connection reference (252) | Exactly one Reference ID per record; the same sender → receiver is repeated per paper, each with its own Taxon, Measurement method and Pointers. The same sender → receiver → reference may appear only once | schema `maxItems: 1` + `checkHcd` |
| Pointers (271/277) | At least one of the two. Pointers on literature is a verbatim quote from the cited paper: at least `DEFAULT_BRA_RULES.minQuoteWords` words (**10, provisional**: the rule comes from reviewer feedback and is not in the manual, ontology or template), not starting with a page / section locator. Pointers on figure must be a figure number; the CSV normalizes it (`Figure 3b` → `Fig. 3B`) | `pointerProblems`, `normalizeFigurePointer` |
| Enumerations | Taxon (10 values), Measurement method (21), Transmitter (6, or empty), Modulation Type (3, or empty), Literature type (11) from Template-v2-2 AdminOnly | schemas |
| DOI (1) | A reference without DOI needs `alternativeUrl` or a PMID (the CSV then writes the PubMed URL as Alternative URL) | `checkHcd` |
| Output Semantics (430) | A UC has exactly one item `[<own Circuit ID>] content;` (a space after `]` is optional; `[Author, Year]` citations may end the content). GN rows of `FRG.csv` get the items of their UCs that project outside the GN | `parseOutputSemantics`, `buildCsvs` |
| Capability (440) | FRG rows of UCs outside the ROI get the fixed text `No need for description due to input/output circuit` (the xlsx writes it without the mechanism tags) | `buildCsvs`, `csv_to_excel.py` |
| Terminology | `names` of an anchor-only UC must start with its SABRA official name (BNA area name, or the DHBA name from RCS `get_homba_term`; skipped when RCS could not be asked), synonyms after `;`. `[U.<id>]` / `[R.<id>]` in function items, comments and FRG details must name existing UCs / nodes | `sabraOfficialName`, `checkHcd`, `checkFrg` |
| ROI row | `Circuits.csv` starts with `ROI_<ProjectID>` (Source of ID `collection`, Names = ROI, Sub-Circuits = every ROI-internal circuit: the Collections whose UCs are all ROI-internal, then the ROI-internal UCs; Uniform `FALSE`); the graph builder skips it | `buildCsvs`, `buildGraphs` |
| Review End Line | `Project.csv` gets the sheet row of the last record of References / Circuits / Connections / FRG (header = row 1, so `1` when a sheet is empty); the xlsx writes them as numbers | `buildProjectCsv` |

- **`BNA` as Source of ID** is a CoBRAC extension: the BRA enumeration has no value for SABRA's BNA side, and adding it has been requested upstream (pending). Until then the Review Tool may flag these rows as 108.
- **Compatibility**: the BRA version in `Project.csv` becomes `CoBRAC-v1-1`. Column changes are appends only — References gains C Literature type and D Alternative URL; `Circuits.csv` gains Sub-Circuits and Uniform after UC Descriptor, and `Connections.csv` the two relations and notations after Pointers on figure (the xlsx already had all of these columns — Circuits D / F, Connections B / C / E / F — and now fills them from the CSV) — so every v1-0 column keeps its position. Value changes: Source of ID holds one value (`BNA` added), Connections has one row per reference and real relations / notations, the Circuits sheet has the ROI row first, FRG GN rows have Output Semantics, and Project has Review End Lines. The graph builder reads v1-0 and v1-1 CSVs alike (columns by name).
- **Older projects** (files written by 0.9 or earlier): the next follow-up validates them like any other files, so the problems above come back as fix turns (a Source of ID list, several references per connection, missing Literature type or relations, locators as pointers, values outside the lists). Until they are fixed, the CSVs are still built: a Source of ID list keeps its first value, a connection with several references becomes one Connections row per reference, and a connection without relations keeps `=` and the Circuit ID.
- The xlsx Capability&Mechanism cell is the Capability, the template's default tag `<<mechanism to realize the capability>>` and the Mechanism; the earlier CoBRAC-only tag `<<mechanism realized by grainest coding scheme>>` (not in the template or manual) is no longer written.
- Not covered yet (decisions pending): granularity rules for UCs (e.g. neocortical senders by layer / cell type) and the allowed characters of Circuit IDs. Quotes are checked against the paper's text (6.7); quotes from papers without open-access full text can only be checked against the abstract. The Template-v2-2 column layout is produced as a second workbook (6.12).

### 6.10 Collection Circuits (Uniform / Collection)

Whether a circuit is Uniform is decided **per HCD**: a circuit is a UC when it is a leaf of that HCD and a Collection (Uniform = FALSE) when the HCD decomposes it into Sub-Circuits. The UC Descriptor stays the cross-project key and carries no uniformity, so the same area may be a UC in a coarse project and a Collection in a fine one. A whole SABRA unit as a UC remains a project choice.

- **Data**: `uc.json` keeps `ucs` (always Uniform) and gains an optional `collections` array (`circuitId`, `descriptor` — the SABRA unit or faceted population, empty for a grouping of several units —, `names`, `sourceOfId`, `subCircuits`, `comments`). Files without it stay valid. Collections have no Interface, Output Semantics or function items.
- **When** (`prompts/phases/HCD.md` step 3): when the HCD splits a SABRA unit into facet UCs, the unit becomes a Collection of them (anchor-only descriptor and Circuit ID); a higher grouping (a named network) only when it helps the reader. A whole-unit UC that is not split needs none. The guideline is not enforced beyond the check below, to keep outputs small.
- **Checks** (`checkHcd`, `checkFrg`; the codes are those of ontology appendix D):

  | Check | Error / code |
  | ----- | ------------ |
  | `subCircuits` has at least one item (schema), each a UC or Collection of `uc.json`, not the Collection itself, no cycle through Collections, not every member `makeshift` (manual) | 128 |
  | UCs have no Sub-Circuits (by construction: only `collections` have the key) | 129 |
  | A Collection is neither sender nor receiver of a connection in this HCD; the feedback lists its UCs. The ontology lets a Receiver be a Collection; CoBRAC is stricter so interfaces stay UC-to-UC. Evidence reported for the whole unit is cited on the UC connection with relation `<` and the paper's notation (6.9) | 205 (and stricter) |
  | A UC and a finer UC of the same anchors (a subset of its facet values) cannot both be UCs: the coarser one has to move to `collections` | 127 |
  | Collection IDs share the ID space of UCs, may not start with `ROI_`, and follow the UC naming rules when they have a descriptor (descriptor unique across UCs and Collections) | — |
  | Source of ID of a Collection is always `collection` (a Collection is defined by its Sub-Circuits; `DHBA` / `BNA` / Reference IDs are for UCs) | 108 |
  | `[U.<Collection>]` is allowed only in `comments`; FRG subnodes and function texts must name UCs | — |

- **Output**: `Circuits.csv` writes each Collection after the ROI row with Uniform `FALSE` and Sub-Circuits joined by `;`; UCs keep Uniform `TRUE` and empty Sub-Circuits. **FRG**: Collections are not FRG nodes (the FRG's leaves and Projected Circuits are UCs), so `FRG.csv` has no row for them. The graph builder turns Uniform `FALSE` rows (other than the ROI row) into `HcdGraph.collections` (with `members`, nested Collections expanded) instead of nodes; a Collection that is still an edge end in unchecked files stays a node.
- Not decided: how WholeBIF should merge Uniform values that differ between projects (upstream question U20).

### 6.11 Research mode (since 0.11)

A project setting chosen once on the create screen (checkbox, **on by default**; `researchMode` on the project, each job records the value it ran with). It cannot be changed after creation, and there is no per-user default. Follow-ups and retries inherit it; projects created before it existed have no field and run without it. Off skips the research step and the research notes (the `lit` tools stay available).

- **Research step** before phase HCD (not a new phase: HCD → FRG → CSV → xlsx is unchanged). The agent gets `prompts/phases/RESEARCH.md` and writes only `{P}/research.json` (schema `research.schema.json`, in `HARNESS_SCHEMAS`): a plan, up to 40 candidate tissue-level projections, for each the queries it ran, evidence items (Reference ID, PMID / DOI, taxon, method, layer / cell type, finding, abstract or full text read), coverage of tract tracing / primate / rodent / layer-cell type (`found` / `searched_none` / `not_applicable`), a status (`supported` / `weak` / `not_found` / `contradicted`), and the remaining gaps.
- **Tools**: a `lit` stdio MCP server (`packages/worker/src/litMcp.ts`, `litsearch.ts`; started in **every** BRA run, with or without research mode, since it also serves PMIDs and verbatim quotes) with `search_pubmed`, `search_europepmc`, `get_abstract`, `find_sentences` (sentences of the open-access full text, else the abstract, that contain given terms). Requests go through the literature HTTP client of the checks (`http.ts`: 15 s timeout, 3 retries with 1 / 2 / 4 s backoff on timeouts, network errors, 429 and 5xx, honouring `Retry-After`; a host that fails 3 calls in a row is skipped for 5 min) and their starts are spaced per provider even when the agent calls tools in parallel (Europe PMC 200 ms, NCBI 350 ms). One call has 65 s (below the MCP tool timeout of 90 s). When Europe PMC does not answer within 45 % of that, `get_abstract` and `find_sentences` take the record from PubMed (`esearch` for a DOI / PMCID, `esummary`, `efetch` for the abstract) and the full text from PMC through NCBI BioC; the full text is also tried for author manuscripts Europe PMC shows (`inEPMC`), and through BioC when Europe PMC's `fullTextXML` fails. The result then carries a `note` naming the service that failed. A tool that still fails returns an error naming every failed service and an alternative (`search_pubmed` ↔ `search_europepmc`). Web search stays on. The worker logs every lit call and web search from the event stream to `{P}/research_queries.jsonl` (with job ID and step, and for a failed call the tool's error text), and counts them per tool on the job (`searches`). `npm run test:live -w @cobrac/worker` runs the tools against the real services.
- **Coverage check** (`checkResearch` in `packages/shared/src/research.ts`): schema; at least 2 distinct queries per candidate with at least one in PubMed / Europe PMC; every listed query must be in the search log under the matching tool; coverage values must agree with the evidence (`found` needs an evidence item with a tracing method / primate taxon / rodent taxon / layer-cell type); supported / weak / contradicted need evidence, not_found none; every evidence item needs a PMID or DOI; a note for anything not supported or not applicable. Problems go back as up to 2 fix turns. Gaps never block the run; the result goes to `{P}/research_check.json` (`done`, `outcome`: `passed` / `gaps` / `budget`, summary, problems), and a workspace with `done: true` skips the step on later runs.
- **Metrics** (for checking real runs): when the step ends, `research_check.json` `metrics` and the job's `researchStep` hold outcome, model, effort, start / end, minutes, turns, whether a turn was cut off, spend and token usage of the step, candidates, supported, and searches by tool (ok / failed); the chat shows a summary line with the full metrics in its details, and CloudWatch gets `[research] start` / `[research] end {…}` lines. Every job also logs `[metrics] {…}` (usage, cost, minutes, searches by tool) at exit. There is no USD cap; cost is bounded by the time budget and shown in the usage lines.
- **Budget**: 60 minutes of wall clock for the whole step (`RESEARCH_TIME_BUDGET_MIN`); a turn still running then is aborted and the HCD starts with what was written (the usage of an aborted turn is not reported by Codex and is missing from the job's total). A fix turn starts only with at least 10 minutes left. Research turns run at reasoning effort `max(project effort, high)`.
- **Later phases**: `prompts/research_mode.md` is appended to the HCD / FRG specs and to follow-ups: build the BIF and connections from the survey (prefer supported and tract-tracing evidence, flag weak ones, define cell-type / layer UCs where the evidence supports it, quote from sentences actually read, put the gaps into the limitations), search for computational models in the FRG, research new claims in follow-ups. The HCD / FRG validators are the same with or without research mode.
- **Estimate** (`researchModeEstimate`): shown under the toggle, +10–60 minutes and the cost of 1.5–6M input tokens (85–90% cached) and 40–150k output tokens at the selected model's price (for gpt-6-luna about $0.05–0.19, gpt-6-sol about $1.1–3.8). It is a rough figure from the few completed runs; the usage line of each job is the real value.

### 6.12 Template-v2-2.bra export

Next to CoBRAC's own xlsx, every job writes the same data into the official template of the BRA Data Preparation Manual, `prompts/templates/Template-v2-2.bra.xlsx` (the Google Sheets template downloaded as xlsx), as `output/{P}.template-v2-2.bra.xlsx` (`buildTemplateXlsx`, `packages/shared/src/braTemplate.ts`). The download is `{name}_{ID}.template-v2-2.bra.xlsx`.

- **The template is the base.** Its 11 sheets, header rows, formulas, AdminOnly lists, validation, conditional formats and the WholeBIF rows it imports (IMPORTRANGE results below the input area) are kept. The workbook is edited at the XML level (`xlsxSheet.ts`, fflate for the zip) because a spreadsheet library would drop Google's parts (custom sheet views, the `__xludf.DUMMYFUNCTION` wrappers Google uses to restore its own functions on upload). Only contributor-input cells are written; automatic and admin columns keep their formulas. For formula cells whose value CoBRAC knows (References A / G–J, Circuits AO) the value Excel shows is set to what Google Sheets computes; `fullCalcOnLoad` makes Excel recalculate the rest.
- **Rows.** The input areas are References 2–29, Circuits 2–31, Connections 2–80 and FRG 2–198. When a sheet needs more, rows are inserted above the WholeBIF import as a contributor would (copies of the last input row with their formulas); every reference to the rows below moves, also from other sheets and in validation ranges, filters, hyperlinks and defined names. A layout change of the template is detected (the IMPORTRANGE row) and fails the export.
- **Mapping.**

| Sheet | Written | Kept (formulas / admin) |
| ----- | ------- | ----------------------- |
| Project | A2 Contributor, B2 Project ID, C2 List of contributors, D2 Description, B5–B8 Review End Lines (sheet row of the last record) | E2 BRA version `Template-v2-2.bra` |
| References | D DOI (empty when N/A), E BibTeX, F Literature type, K Alternative URL (only without DOI), L Contributor, M Project ID | A Reference ID, B / C links, G–J type / authors / title / journal (from the BibTeX), N–W |
| Circuits | Row 2 the ROI row. A Circuit ID, B Source of ID (one value; a Reference ID in the template form), C Names, D–R DHBA graph_order / name / Lv.2–14, S Sub-Circuits, U Uniform, V Transmitter, W Modulation Type, AA Comments (+ `UC Descriptor: …`), AB Contributor, AC Project ID | T, X–Z empty; AD–AM, AO |
| Connections | A sCID, B / C sCID relation / notation, D rCID, E / F rCID relation / notation, H Comments, I Reference ID, J Taxon, K Measurement method, L / M Pointers, AE Contributor, AF Project ID (one row per reference) | G, N empty; O–AD, AG–AP |
| FRG | AC Node ID, AD Subnodes, AE Circuit ID, AF Projected Circuits (`;`-separated), BA Capability&Mechanism (`<capability>\n<<mechanism to realize the capability>>\n<mechanism>`; ROI-external UCs: the fixed text and the tag), BC Implementation of Uniform Circuit (UC rows), BG Requirements Realization by Interface, BI Requirements, BK Output Semantics, BM Comments | A–AB, AG–AZ (Region Category, Interface, Implementation are formulas), BB, BD–BF, BH, BJ, BL, BN–BX |

- **Reference IDs.** The template derives the Reference ID from the BibTeX key (`Schultz_1997a` → `Schultz, 1997a`), so each CoBRAC ID gets a key from its first author and year (`[Schultz et al., 1997]` → `Schultz, 1997`); IDs that would coincide get the next letter. Connections I, Circuits B (`[Schultz, 1997]`) and the citations in the free text that is written (comments, FRG texts, Output Semantics) use the same IDs.
- **BibTeX** is written one field per line with spaces around `=`, as the template's regular expressions expect. At the end of a job the worker looks up each DOI in Crossref and each PMID-only reference in PubMed (`bibliography.ts`, 10 s per request, 60 s in total, failures retried by the next job; off with `REFERENCE_LOOKUP=off`) and keeps the records in `{P}_CSV/bibliography.json`. Without a record the BibTeX comes from `references.json` and `reference_check.json` (first author, title, journal, year).
- **DHBA columns** come from the template itself: its WholeBIF Circuits rows with Source of ID `DHBA` are the DHBA ontology as WholeBIF numbers it (HOMBA's `graph_order` is a different numbering). A UC anchored on one DHBA term (by its acronym, the Circuit ID head) gets that row; a UC finer than a DHBA term gets the term's graph_order plus a decimal (manual: "add a decimal number to DHBA: graph_order"); circuits anchored on BNA, the ROI row and circuits without a UC Descriptor other than `DHBA` stay empty.
- **Older projects** (finished before the export existed, or with a file older than the CoBRAC xlsx): `GET /projects/{id}/artifacts/template-xlsx` builds it from the workspace CSVs and JSON in the API Lambda (template bundled next to the handler), stores it and returns a presigned URL. Any CoBRAC-v1-x CSV works (a Source of ID list keeps its first value, several references per connection become one row each, missing relations become `=` and the Circuit ID, a missing ROI row is added).
- What the template has no place for (UC Descriptor, facets, `BNA`, CoBRAC's reference checks, …) and the additions to request upstream are listed separately (template additions memo).

### 6.13 Re-validation of earlier phases and the HCD ↔ FRG consistency record

The FRG spec asks the agent to fix related files when the FRG and the HCD disagree, so HCD files may change after the HCD phase. Such changes are validated again, and the consistency of the two graphs is recorded. This is the first step toward letting the HCD and the FRG constrain each other.

- **Baselines** (`{P}/phase_baseline.json`, worker only): each HCD / FRG check stores a SHA-256 of that phase's data files (HCD: `meta.json`, `references.json`, `uc.json`, `connections.json`; FRG: `frg.json`; the report and the decision log change in every phase and are left out) and the problems left at that point.
- **Re-validation**: the FRG and CSV checks compare the hash. Unchanged files are not checked again. Changed HCD files get the full HCD check (schema and rules, RCS, references, quotes); changed FRG files the full FRG check in the CSV phase. Problems that were already left when that phase was accepted (with a warning after `MAX_NUDGES`) are not sent again; new ones go back in the same fix prompt, prefixed `HCD (changed after the HCD phase was checked):`. The CSV phase still writes the CSVs, so a run that ends with warnings has them. A workspace without a baseline (checked before this version) takes its current state as the baseline.
- **Consistency record** (`{P}/cross_check.json`, worker only, `checkCross` in `packages/shared/src/cross.ts`): written by every FRG and CSV check, **record-only**: nothing is sent to the agent, and the chat shows the counts when FRG and CSV are accepted. `rules` gives the intended severity of each check for when it is enforced:

| Code | Check | Intended severity |
| ---- | ----- | ----------------- |
| X1 | A GN interface leaves out a flow that the HCD connections of its ROI-internal UCs have (inputs from / outputs to circuits outside the GN) | error |
| X2 | The ROI inputs / outputs derived from the connections differ from the `noROI(input)` / `noROI(output)` tags (a tagged UC with no path to or from the ROI, or an untagged UC that connects to it) | error |
| X3 | A GN interface claims an input or output that no connection of its UCs provides, or lists one of its own UCs | error |
| X4 | The two UCs of a GN are not connected through ROI-internal connections | warning |
| X5 | A ROI-internal UC is not mentioned (`[U.<id>]`) in the function text of any GN it is attached to | warning |
| X6 | A GN's `requirementRealization` does not mention every UC of its interface | warning |
| X8 | The FRG is collapsed: the TLF has only UCs, there is a single GN, or the HCD has fewer than 3 ROI-internal UCs | warning |

- The report also has `summary` (count per code) and `stats` (ROI-internal UCs, GNs, parsed GN interfaces, FRG depth). X1, X3 and X6 look only at GN interfaces that parse. `scripts/cross-check-artifacts.mjs` runs the same check on workspaces copied from S3 (read-only), including pre-0.8 workspaces through their CSVs (no GN interfaces there, so X1 / X3 / X6 are not measured).

### 6.14 Canons (since the Canon MVP, stage 1)

A **Canon** is a set of one user's projects whose circuit definitions must agree: within a Canon, the same UC Descriptor has the same Uniform / Collection status and the same decomposition, and cross-project connections keep Sender = Uniform. Uniformity is per HCD outside a Canon (6.10) and fixed inside one; different Canons may choose different granularity (a coarse network-level Canon next to a layer-level one). The name is provisional.

- **Stage 1 (this version)** is the container only: create, list, rename, edit the description, granularity policy and constraint mode (`strict` / `advisory`, used from stage 3), soft delete, and add / remove the owner's projects. A project is in at most one Canon (`Projects.canonId`); adding it to another returns 409. Every Canon is private and empty (`headRevision` 0).
- **IDs**: `<userKey>-c<seq>` (e.g. `u7m2q9xa-c1`) from the per-user counter `Users.canonSeq`; never changed or reused, and never matches the Project ID pattern.
- **Ownership**: only the owner sees and changes a Canon; other users get 404; admins may read. Deleting a Canon sets `deletedAt` and releases its projects (their `canonId` is cleared); its items stay. Soft-deleting a project removes it from its Canon.
- **Later stages** (design only): push a project into the Canon as a pull request with a diff and conflict check, approved by the owner (2); Canon-to-Canon pull requests (2′); project and Canon visibility and cloning public projects (1′); pulling a Canon revision as constraints for generation (3); choosing or seeding a Canon when creating a project (3′).

### 6.15 Public projects, public Canons and cloning (Canon MVP stage 1′)

- **Visibility**: a project or Canon is `private` (default) or `public`; only its owner switches it (`PUT /projects/{id}/visibility`, `PUT /canons/{id}/visibility`). A project can be published once it has artifacts and has a `<userKey>-<seq>` ID. Public items get a row in the **Catalog** table (`kind` = `project` / `canon`); the row is removed when the item is made private or deleted. Lists and reads always re-check the project or Canon itself.
- **Public library** (`/explore`): every signed-in user can list and read public projects (summary, circuit list, report) and public Canons (policy, revision, member count, public members). What is and is not shown is listed in `02_個人情報とセキュリティ.md` 4.2.
- **Clone** (`POST /public/projects/{id}/clone`): creates a new private project of the caller (new Project ID, `name` + " (clone)", the original Contributor, status COMPLETED, `clonedFrom` = original ID, revision, userKey and name) and copies the workspace (folder names and every whole-token occurrence of the old Project ID in text files are rewritten), graph JSON and articles. Not copied: thread, jobs, messages, usage, graph layouts, attached materials and the BRA xlsx outputs (they carry the old ID; XLSX is left pending so a follow-up rebuilds them). The original is only read; its clone count is a `clones` row in the Catalog table, shown to the owner on the project and in the library.
- **Pull requests to Canons** (used from stage 2′): a public Canon accepts pull requests from other users' Canons unless its owner turns `acceptPullRequests` off.

### 6.16 Pushing a project into a Canon and pull requests (Canon MVP stage 2)

- **Snapshot**: a Canon revision is one immutable JSON (`canons/{canonId}/rev/{n}/canon.json`) with a shared layer — circuits keyed by normalized UC Descriptor (Circuit ID, names, Uniform / Collection, Sub-Circuits, transmitter, modulation, Source of ID, Output Semantics), groupings without a descriptor (`group:<id>`), connections keyed by (sender, receiver, Reference ID) with their literature fields and quote-check status, BIF and references with their check status — and a role layer per project (ROI side, Interface, function items, FRG). Every entry keeps its origin (project, revision, PR) and the projects that pushed it. Revision 0 is the empty Canon.
- **Push** (`POST /projects/{id}/canon/push`, member projects that are COMPLETED): the API converts the workspace (`uc.json`, `connections.json`, `references.json`, `frg.json`, `meta.json`, `reference_check.json`, `quote_check.json`) with `canonFromProject`, diffs it against the head (`diffCanon`) and stores a pull request (`PR#`, payload and diff under `canons/{canonId}/pr/{no}/`). An open PR of the same project is superseded. `…/canon/preview` shows the same diff without a PR. UCs without a descriptor are left out and listed.
- **Conflict rules** (design doc 4.3): errors — C1 Uniform / Collection differs, C2c the decomposition is split differently, C3 a finer circuit next to a Uniform one, C4 Circuit ID ↔ descriptor not one to one, C5 a connection ends on a Collection, C6 official name differs, C8 the same Reference ID with another DOI / PMID, C8c / C9c reference or quote failed its check. Warnings — C2b the decomposition gains Sub-Circuits, C7 transmitter / modulation / Source of ID differ, C8b the same paper under another ID, C9b the same connection written differently, C12 a grouping differs. Information — C13 Output Semantics differs. A subset of the Canon's decomposition is not a conflict.
- **Review** (Canon owner): `approve` with `choices` (per conflict: keep the Canon's value or take the incoming one). Plain errors block; C1 and C2c can be resolved only by adopting the incoming definition (design Q10) — connections that then end on a Collection are marked `flagged`, and the projects that use the changed circuits are listed as impact. Every warning needs a choice. If the head moved since the push, the PR is re-judged against the current head first. Approval writes revision n+1, moves `headRevision` conditionally (a concurrent approval gets 409) and records `REV#`. `reject` needs a reason; the pusher can `withdraw`.
- Nothing is removed from the Canon when a project stops using an entry; the diff only lists it as "no longer in the project".

### 7.1 Token usage and cost

- `usage` is `{ inputTokens, cachedInputTokens, outputTokens, reasoningOutputTokens }`. The worker adds to the job on each Codex SDK `turn.completed`, then re-aggregates the project from all jobs (`refreshProjectUsage`).
- `model` is the model actually passed to Codex at job start. On project create, the API **always resolves a concrete model name** (request → user default → `CODEX_MODEL` → `DEFAULT_CODEX_MODEL` = `gpt-6-luna`). The picker lists GPT-5.6 and GPT-6 text models only. An unknown “Codex default” model is never left behind.
- `costUsd` is an **estimate** from `estimateCostUsd()` using the rate table in `packages/shared/src/pricing.ts` (USD / 1M tokens, dated `PRICING_AS_OF`). Formula: `(input − cachedInput) × input rate + cachedInput × cache rate + output × output rate` (reasoning is included in output). Models missing from the table become `null` and the UI shows `$—`.
- The rate table is a code constant. When OpenAI changes prices, update `PRICING` and redeploy. The OpenAI dashboard is the source of truth for actual charges.
| Messages | projectId | `{ISO}#{seq}` | userId (since v0.7), jobId, role, type, content, step, meta |
| WsConnections | connectionId | projectId (`_` is the connection record) | userId, ttl |
| Catalog | kind (`project` / `canon` / `clones`) | id | project / canon rows while public: ownerUserId, name, publishedAt. `clones`: count |
| Canons | canonId | `META` / `MEMBER#{projectId}` / `PR#{000001}` / `REV#{000001}` | META: ownerUserId, name, description, policy, constraintMode, visibility, acceptPullRequests, publishedAt, headRevision, memberCount, deletedAt. MEMBER: projectId, joinedAt |

GSI:

- Jobs `status-index` (status + createdAt): dispatcher / janitor
- WsConnections `project-index`: delivery targets
- Users `userKey-index` (keys only): uniqueness check when issuing a userKey, Project ID → owner lookup
- Canons `owner-index` (ownerUserId + createdAt; only META items carry ownerUserId): the owner's Canon list

Streams: NEW_IMAGE on Projects / Messages → broadcaster.

Messages with role `user` are only what the user typed (the API stores them with `meta.kind` = `create` / `answer` / `followup`). The prompt the worker sends to the agent at job start is stored as a `system` / `status` notice (`meta.harnessPrompt`, prompt text in `meta.details`, shown as e.g. "Started phase HCD." that expands to the text). Workers up to v0.8.1 stored that prompt as a `user` message with `meta.mode`; the chat renders those as the same notice (`normalizeStoredMessage`).

**Ownership**: regular users only see rows under their own `userId`. Project IDs are globally unique. Legacy IDs (per-user slugs before v0.7) could be shared by two users, and Jobs / Messages / `project-index` are keyed by `projectId` alone, so every read is filtered by owner: jobs by `userId`, messages by `userId` (or, for older messages, the owner of their job), WebSocket deliveries to the owner's connections only.

**Project IDs and names**

- Creation: `ADD projectSeq :1` on the user's Users item (atomic), then Put the project with `attribute_not_exists(projectId)`. Numbers lost to a failed creation are not reused.
- `name` starts as a provisional `<TLF> in <ROI>` built from the ROI/TLF as typed, in any language (e.g. `VOR in 小脳`; `nameSource = "provisional"`). When the HCD phase is accepted, the worker stores the English `name` the agent wrote to `meta.json` (`<TLF> in <ROI>`) and sets `nameSource = "auto"`; it does so only while `nameSource` is `provisional` or `auto`. Older projects whose `auto` name is still the old ASCII slug (e.g. `VOR` for TLF `VOR` / ROI `小脳`) are shown, and named in downloads, with the provisional name instead. A name typed at creation or edited later is normalised (NFC, trimmed, whitespace collapsed; control characters and line breaks rejected) and sets `nameSource = "user"`; the agent never overwrites it.
- The xlsx `Project ID` column holds the ID; `Description` is prefixed with the name when it is English.
- Download file name `{name}_{ID}.bra.xlsx`: NFC, control characters, `/ \ : * ? " < > |` and whitespace runs become `_`, repeated `_` collapse, leading/trailing `_ .` and spaces are removed, cut to 80 code points; empty → `{ID}.bra.xlsx`. Sent as `filename*=UTF-8''…` with `filename="{ID}.bra.xlsx"` as the ASCII fallback. S3 keys and work directories use the ID only.
- Deleting a project is a soft delete: `DELETE /projects/{id}` sets `deletedAt` / `deletedBy` on the Projects item (conditional on the project not being deleted and not being `QUEUED` / `RUNNING` / `WAITING_USER_INPUT` / `FINALIZING`) and nothing else. Jobs, Messages and S3 objects stay as they are, the ID is never reused, and no index is added (the flag is filtered in the API). For the owner a deleted project behaves like a missing one: it is left out of `/projects`, name-duplicate warnings and legacy-ID redirects, and every `/projects/{id}/…` route and WebSocket subscribe returns 404 / not found. A running project has to be stopped first (409). `/users/me/usage` keeps its cost in the totals and flags it `deleted` in `byProject`; `/admin/projects` lists it with `deletedAt` and the admin page shows it as deleted. There is no restore screen; restoring means removing `deletedAt` from the item (a future admin API)
- Migration of legacy IDs: `scripts/migrate-project-ids.mjs` (dry run by default; `--apply` writes). Each legacy project is copied under its new ID (Projects with `legacyId`, its Jobs / Messages, S3 with renamed folders). The old Projects item is saved to `users/{userId}/{legacyId}/migration-backup/project-item.json` and deleted, so the project is listed once and old URLs redirect. `--keep-old` keeps the old Jobs / Messages items as a backup; old S3 objects are never deleted. Re-running also removes an old Projects item left next to its migrated copy.

### 7.4 Reference materials

The create screen accepts up to 10 files (PDF, PNG / JPEG / WebP / GIF, TXT / MD / CSV / TSV / JSON, DOCX / XLSX / PPTX; 20 MB each, 50 MB in total) and up to 20 http(s) URLs (`packages/shared/src/attachments.ts`).

1. Each file is sent straight from the browser to S3: `POST /uploads` checks the name and size and returns a presigned POST whose policy pins the staging key, the Content-Type and the size range. The bucket's CORS allows POST from the CloudFront domain, `https://cobrac.site` and `http://localhost:5173`.
2. `POST /projects` checks each staged upload (it must exist and fit the limits), moves it to `attachments/files/`, and stores the list in `Projects.attachments` (`kind: "file"`: name, key, size, contentType; `kind: "url"`: url). URLs must be http(s) with a public host.
3. On each run the worker mirrors `attachments/` to `/work/materials/`. The first run derives, once: PDF text (`pdftotext`), Office text (DOCX / PPTX / XLSX shared strings), and URL content (HTML as text, PDF with its text, images; at most 10 MB, 20 s, 5 redirects, every hop must resolve to a public address). The result is stored in `attachments/derived/` with a `manifest.json` and reused by later runs. A failed item is only marked as failed.
4. `materials/INDEX.md` lists every item with its original, its text and its status. The prompt header gets a `Reference materials:` line, images are attached to the first prompt of a new thread, and `prompts/AGENTS.md` tells the agent that the materials are to be consulted but are not verified literature: references still need published sources (checked against Crossref / PubMed) and quotes must be verbatim from those sources.

## 9. Frontend design

- Vite + React 18 + React Router + Tailwind.
- Runtime config is CloudFront `/config.json` (apiUrl, wsUrl, userPoolId, userPoolClientId, region). Local uses `VITE_*`.
- Graphs: `@xyflow/react` + dagre (HCD top to bottom, FRG left to right). HCD colors nodes by ROI class (fill plus a stripe) and sets default edge style from projection physiology (excitatory / inhibitory / modulatory). FRG colors by kind. Labels grow when zoomed out; self-connections are drawn as loops.
- Viewing: selecting a node dims everything except its neighbours (HCD) or its ancestors and descendants (FRG); selection from outside the canvas (URL, search, detail links) recentres the view above the detail sheet. The search box ranks nodes by ID, name and UC Descriptor (↑ ↓ Enter, `/` to focus). Toolbar: search, fit, undo/redo, style edit mode, and a menu with layout direction, grid snap, page options (edge labels, expand/collapse all), PNG export and reset. Pure helpers live in `packages/web/src/lib/graphView.ts` (vitest).
- Style edit mode (toolbar button): style panels, resize handles and connection handles appear only in this mode; on touch devices nodes are draggable only in this mode.
- Nodes: drag to move, resize from corners/edges, change fill and border in the style panel.
- Edges: click to open the style panel (in style edit mode). Line type (curve / straight / orthogonal auto / **orthogonal with waypoint editing** / polyline), color, width, dash, corner radius, and start/end markers (arrow, open arrow, square, circle, diamond, bar). Orthogonal edges add waypoints with “+” on the path, drag to bend, double-click to delete.
- Connection handles: drag the circles at both ends of the selected edge onto node-edge handles (7 points per side) to change start and end.
- Default line type is a curve. Layouts saved under the earlier orthogonal default may have bends without an explicit line type; those edges stay orthogonal so the bends are kept.
- Inhibitory default: blue (`#2563eb`) + square end. Excitatory: gray + triangle. Modulatory: purple dashed + circle. Classification prefers Connection comments, otherwise the sender’s Transmitter / Modulation Type (`classifyEdgeSign`). The same style can be applied to all edges of that class.
- Layout persistence: `useGraphLayout` saves position, size, color, and edge style (including waypoints and handles) to `PUT .../layout` with a 600ms debounce. Same node ID / edge ID is kept after graph regeneration. Ctrl+Z / Ctrl+Y undo/redo.
- Chat is Markdown (GFM). Commands / thinking / web search are collapsed.
- Version: root `package.json` `version` is injected via Vite `define` as `__APP_VERSION__`, plus `git rev-parse --short HEAD` as `__APP_COMMIT__`. Operating rules are in `AGENTS.md`.

## 10. Worker internals

Entry: `packages/worker/src/index.ts`.

1. Read Users / Projects / Jobs and decrypt the API key with KMS.
2. Copy `prompts/AGENTS.md` to `/work` and write the JSON Schemas to `/work/schemas/`. For resume / followup / retry, restore workspace and thread from S3.
3. `createCodex` → `openThread` (`sandboxMode: danger-full-access`, live web search, the `lit` MCP server). Each turn opens the thread with its own settings, so research turns can run at a higher reasoning effort.
4. In research mode, run the research step if the workspace has not finished it (section 6.11). Then run the phases (section 6.4). Write events to Messages and update stepStates on every file change.
   - A turn fails only on `turn.failed`, or when the stream ends on an `error` event without `turn.completed`. Codex reports its own retries of a rate-limited request as `error` events ("Reconnecting... 2/5 (rate limit exceeded …)"); they are shown as status lines and the turn goes on. A turn that still fails on an OpenAI rate limit (TPM / RPM, HTTP 429; not an exhausted quota) is resumed on the same thread after a pause (the server's "try again in …" plus 5 s, at least 30 s / 60 s / 120 s, at most 3 min), up to 3 times, with heartbeats during the pause; only then does the job fail.
5. Diff-sync to S3 after each accepted phase and immediately before waiting for a question, completion, or failure.
6. After CSVs are complete, `finalize.ts` uploads xlsx and graph JSON.

Mode `article` branches off after step 1 (`articleJob` in `index.ts`, loop in `article.ts`): restore the workspace only, one article turn plus fix turns, upload `article/<locale>.md` / `.json`, project back to `COMPLETED`.

The agent’s shell environment has `AWS_*` credentials cleared so the task role cannot leak.
