This system is not a public consumer service. It assumes **a small number of individual users who join by invitation or self sign-up**. Even so, it handles OpenAI API keys and research data, so storage, decryption, and logging are spelled out here.

---

## 1. Information handled

### 1.1 Information that can identify a person

| Information | Source | Stored in | Purpose | Notes |
| ----------- | ------ | --------- | ------- | ----- |
| Email address | Sign-up | Cognito, DynamoDB Users | Login, admin display | Required |
| Password | Sign-up | Cognito only | Authentication | Not stored in the app or DynamoDB |
| Cognito sub (userId) | Cognito | Ownership key on all tables, S3 prefix | Identity | UUID |
| Display name / Contributor name | Settings | Users, Project.csv / xlsx | Profile, author field on artifacts | English recommended (xlsx spec) |
| OpenAI API key | Settings | Users.encryptedApiKey (KMS ciphertext) | Codex execution | Plaintext is never stored. Not returned in API responses |
| Last 4 digits of API key | Computed at registration | Users.apiKeyLast4 | “Registered” display | Not a substitute for the key itself |
| Default API key (the organization's OpenAI key) | Admin page | Catalog `config` / `default-api-key` (KMS ciphertext, last 4, date) | Jobs of approved users without their own key | Write-only: only the last 4 characters and the date are shown |
| Default-key approval and usage | Admin page | Users.orgAccess, Jobs.keySource / usage / costUsd | Approval and tier; per-user cost on the admin page | Admins only |
| Available model list | OpenAI `/v1/models` | Users.availableModels | Model picker UI | Snapshot taken at key registration |

Cognito manages password hashes, MFA secrets, and similar. The app only handles ID / Access / Refresh tokens in the browser.

### 1.2 Project data (research and work products)

ROI / TLF, reference materials attached at creation (files and URLs), full chat (user instructions, agent output, command results, web-search queries), HCD/FRG JSON data files, the report and decision log (markdown), CSV, xlsx, graph JSON, and Codex thread state.

These are not “personal information,” but they may include unpublished research hypotheses and literature notes. **Other users cannot see them** (admins can list projects and force-stop jobs. Artifact-body APIs are owner-only).

### 1.3 What we do not collect or return

- Payment details, address, phone number, date of birth
- API key plaintext (`GET /users/me` strips `encryptedApiKey`)
- Download URLs for `thread/` (Codex sessions)

## 2. Where data lives

```
Browser
  └─ Amplify: ID/Access/Refresh tokens (local)

Cognito User Pool
  └─ email, password (hash), confirmation state, groups

DynamoDB
  ├─ Users        profile + API key ciphertext
  ├─ Projects     metadata and question text
  ├─ Jobs         run state and token usage
  ├─ Messages     full chat (truncated at 60,000 characters)
  └─ WsConnections connection IDs (TTL ~2 hours)

S3 Artifacts
  ├─ users/{userId}/{projectId}/{workspace,thread,output,graph,article,attachments}/
  └─ staging/{userId}/   reference uploads before the project is created (deleted after 1 day)

CloudWatch Logs (retention 14 days)
  ├─ Lambda stdout (error messages. Implementation does not emit keys)
  └─ Worker logs (some command output also remains via Messages)

OpenAI
  └─ prompts, workspace files, web search. Subject to their terms
```

Region is **ap-northeast-1 (Tokyo)**. Point-in-time recovery (PITR) is currently off. Users / Projects / Jobs / Messages / the artifacts bucket / KMS / the User Pool survive stack deletion (`RemovalPolicy.RETAIN`).

## 3. Encryption

### 3.1 In transit

| Path | Method |
| ---- | ------ |
| Browser ↔ CloudFront | HTTPS (HTTP redirects) |
| Browser ↔ Cognito | HTTPS |
| Browser ↔ HTTP API | HTTPS + Bearer ID token |
| Browser ↔ WebSocket | WSS. ID token validated via query `token` on connect |
| Lambda / worker ↔ AWS APIs | TLS (SDK default) |
| Worker ↔ OpenAI | HTTPS (Codex SDK) |

S3 buckets use `enforceSSL`. Presigned download URLs are HTTPS as well.

### 3.2 At rest

| Target | Encryption |
| ------ | ---------- |
| S3 (frontend and artifacts) | SSE-S3 (S3-managed) |
| DynamoDB | Service-default encryption at rest |
| ECS ephemeral disk | Fargate default |
| Cognito passwords | Managed by Cognito (the app never keeps plaintext) |
| OpenAI API keys | **Encrypt with a customer-managed KMS key (CMK)**. DynamoDB stores only base64 ciphertext |

The artifacts bucket does not add KMS-SSE. Objects are private (Block Public Access; OAC is on the frontend bucket). Artifacts are fetched only via 15-minute presigned URLs.

### 3.3 KMS details for API keys

- Key type: customer-managed symmetric CMK. Annual rotation enabled. Deletion policy RETAIN.
- Encrypt (API Lambda only): `EncryptionContext = { userId, purpose: "openai-api-key" }`
- Decrypt (worker only): same context required. Another user’s ciphertext fails decryption on context mismatch. The default API key (design spec 4.1) has its own context `{ purpose: "openai-api-key", scope: "default" }` without a userId, so it and the personal keys can never be decrypted with each other's context. The worker decrypts it only for an approved user without a key, after checking that the user is still approved for the job's model.
- Plaintext lifetime: in memory only during the registration verification request. At run time it lives in the worker process memory and is passed to the Codex process. Never written to disk, logs, or S3.
- Deletion: clear `encryptedApiKey` and set `apiKeyRegistered=false`. Past ciphertext remains in KMS but is no longer referenced.
- Registration check: `GET https://api.openai.com/v1/models`. Reject on 401/403.

**There is no API to retrieve the key from the browser.** If it is forgotten, re-issue it on the OpenAI side and overwrite the registration.

### 3.4 What is not application-encrypted (intentional)

Chat bodies, ROI/TLF, artifacts, graph JSON, and thread state use only S3/DynamoDB service encryption. There is no application-level field encryption. Admins and anyone with AWS account privileges can read them from the console.

## 4. Authentication and authorization

### 4.1 Authentication

- Cognito User Pool. Sign-in uses **SRP** (the password is not sent directly to the server).
- Password policy: at least 10 characters, lowercase letter + digit required.
- Token lifetime: ID / Access 2 hours, Refresh 30 days.
- `preventUserExistenceErrors`: same error for unknown emails.
- Account recovery: email only.
- When self sign-up is disabled, an admin creates users in Cognito. Cognito mails them a temporary password; on the first sign-in the login screen asks for a new password (Cognito's `NEW_PASSWORD_REQUIRED` challenge) before the user gets in.
- Account e-mails (sign-up code, resend, password reset, e-mail change, admin invite) are written by the Cognito custom message trigger (`packages/api/src/handlers/authMessage.ts`). Each names CoBRAC Agents and its operator (a joint research team with WBAI), says why it was sent, shows the code and how long it is valid, tells the reader to ignore it if they did not ask, and links to the site. The language follows the UI language the web app passes as client metadata (`lang`), then the `locale` attribute: Japanese or English alone, both in one mail otherwise. The trigger gets the user's attributes from Cognito but has no access to tables, buckets or keys, and logs nothing. Mails are still sent from Cognito's default address (`no-reply@verificationemail.com`); a CoBRAC sender address needs a verified SES identity.

### 4.2 API authorization

1. API Gateway JWT authorizer validates the ID token iss / aud.
2. Hono reads userId / email / groups from claims and loads Users.
3. Project operations use only `getProject(own userId, id)`. Another user’s ID and a deleted project return 404.
4. S3 keys are pinned to `users/{self}/{projectId}/`. `..`, `thread/`, and absolute paths are rejected.
5. Reference uploads: the API builds the staging key from the caller's userId and a random upload ID; the presigned POST policy pins that key, the Content-Type and the size (20 MB), and expires after 15 minutes. On create the API checks each upload again (existence, size, 50 MB in total) before moving it into the project.
6. Admin routes require `role === "admin"`. An admin cannot disable themselves.
7. **Canon co-editors** (the owner's choice). The owner adds a co-editor by the e-mail address of an existing account; the API looks the address up among registered users (so the owner learns whether that address has an account). Co-editors see the Canon, the names, IDs, ROI and TLF of its member projects, its revisions and pull requests (including the review material), and the display names of the owner and the other co-editors; only the owner sees co-editors' e-mail addresses. Co-editors cannot open the owner's projects, chats or usage. Their own AI reviews run on their key and count in their usage.
8. **Public projects and Canons** (the owner's choice; private by default). A public project can be read by every signed-in user through `/public/projects/{id}`: name, ROI, TLF, Contributor, revision, the report, decision log, HCD / FRG JSON, graph JSON and articles. Never public: the chat history and Codex thread, jobs, token usage and cost, attached materials, the BRA xlsx outputs, graph layouts, the owner's e-mail and `userId` (only the pseudonymous `userKey` in the Project ID is visible). A public Canon shows its name, description, policy, revision and member count, and lists only members that are public themselves. The confirmation dialog says so before publishing. Making it private again removes it from the public library at once; clones made in the meantime stay with their new owners.
8. **Cloning** a public project copies the workspace (HCD / FRG / CSV data, checks, report, decision log), graph JSON and articles into a new private project of the cloner under `users/{cloner}/{newId}/` with the Project ID rewritten; it only reads the original. Attached reference materials (`attachments/`) are not copied. The original's owner sees how many clones exist (a counter in the Catalog table), not who made them.

### 4.3 WebSocket

- A Lambda authorizer validates the ID token before `$connect`.
- Subscribe also checks that the project belongs to that user and is not deleted.
- Connection rows have TTL. Deleted on disconnect. 410 Gone unsubscribes.

### 4.4 CORS

Preflight (OPTIONS) does not go through JWT. Allowed headers are `Authorization` and `Content-Type`. Origin is currently `*` (personal use and the default CloudFront URL). Restrict the origin if you add a custom domain.

The artifacts bucket allows only `POST` (reference uploads) from the CloudFront domain, `https://cobrac.site` (an alias of the distribution, set outside CDK) and `http://localhost:5173`. Add any further hostname there too (`packages/infra/lib/cobrac-stack.ts`); uploads from an origin that is not listed fail in the browser.

## 5. Worker isolation

| Item | Implementation |
| ---- | -------------- |
| Execution unit | 1 job, 1 task. Disks are not shared with other jobs |
| OS user | uid 10001 `worker` (non-root) |
| Network | Public subnets + public IP. No inbound; outbound allowed (OpenAI / AWS / literature web) |
| Codex sandbox | The container itself is the boundary: `danger-full-access` + `approvalPolicy: never` (in-container Landlock is not available) |
| Secrets vs. same-user processes | The worker (PID 1), Codex and the agent's commands all run as `worker`, so one could otherwise read another's `/proc/<pid>/environ`. The `node`, Codex and `git` binaries are made execute-only (`chmod 0111`) in the image, which makes the processes started from them non-dumpable: their `/proc/<pid>/environ` and memory cannot be read by another `worker` process. So the agent cannot read the OpenAI API key from the Codex process (nor the container-credentials URI from PID 1, which would otherwise reach the task role and KMS). git is covered because Codex runs it with its own environment (it clones its plugins repo and diffs each turn) |
| Child-process environment | The worker's AWS credentials and container-credentials URI, the RCS token and `NCBI_API_KEY` are removed from the environment of every process the worker spawns (Codex, `pdftotext`/`pandoc`, the xlsx builder); the Codex process gets back only the RCS token it needs. `CODEX_API_KEY` / `OPENAI_API_KEY` are additionally excluded from the agent's shell commands by `shell_environment_policy`. The Codex config (`CODEX_HOME` and the trusted `/work/.codex`) is root-owned, so the agent cannot add an MCP server, hook or notify command that would run with Codex's environment |
| Usable key | Only the one decrypted for the job’s userId (or the organisation default key for an approved user) |
| Permissions | Task role can read/write Users/Projects/Jobs/Messages, artifacts S3, **KMS Decrypt only** (Encrypt is API), and `GetSecretValue` on the RCS MCP token secret `rcs/mcp-bearer-token` |
| RCS MCP token | Read by the worker at start and given only to the Codex process (`RCS_MCP_TOKEN`); excluded from agent shell commands by `shell_environment_policy`. Never sent to the browser |

Reference URLs are fetched by the worker, not the browser: http(s) only, every redirect hop must resolve to a public address (no loopback, private, link-local such as the task metadata endpoint), at most 10 MB and 20 s.

The agent can run web search and arbitrary commands. Prompt-injection attempts to read outside the workspace or metadata are mitigated by removing the AWS credentials and credentials URI from the processes it can reach, making the key-bearing processes (`worker`, Codex, git) non-dumpable so their environment cannot be read through `/proc`, and scoping to user-owned data. This is not full multi-tenant isolation (separate accounts / VPCs): the agent still uses the key for its own job and could, for example, send its own job's data elsewhere.

## 6. Outbound transfers (OpenAI and others)

While a job runs, the following are sent to OpenAI using the user’s API key (for an approved user without a key, the default API key registered by an admin, so the data goes to the OpenAI organization that owns that key):

- ROI / TLF / Contributor / Project ID
  - The Project ID (`<userKey>-<seq>`) contains a pseudonymous user key, not the Cognito `sub` or the e-mail address. It shows only that two projects were created by the same user; it also appears in URLs and in the xlsx `Project ID` column
- Full instructions and workspace files the agent read, including reference materials (images attached to the first prompt, and the files or extracted text the agent opens)
- User answers and follow-ups
- Web-search queries issued by the agent (to the search provider)
- For an **AI review of a Canon pull request** (started by the Canon's owner): the material the review page shows — the diff, conflicts and system checks, both sides of each changed item (circuit definitions, connections with their quotes, references), the Canon's name and granularity policy, and the Project / Canon IDs and names involved. It runs on the owner's key (or the default API key, with the models the owner is approved for) in the worker; the API Lambda still cannot decrypt keys, and the model gets no tools or web search for this turn

**Retention, training, and region on the OpenAI side follow the OpenAI contract and organization settings.** This app does not enforce zero data retention. If you handle sensitive literature, check your OpenAI organization settings.

The `/v1/models` call at key registration also goes to OpenAI with the same key.

The agent sends region names and a short context (ROI, TLF, species) to the RCS MCP server (rosetta-candidate-search, same AWS account). With its AI option on, RCS forwards the query to DeepSeek for query cleaning and adjudication. No user identifiers or API keys are sent.

To check the references, the worker sends the DOIs, PMIDs and titles (with the first author) from `references.json` to Crossref (`api.crossref.org`), doi.org and NCBI E-utilities (PubMed). Nothing else from the project and no user identifiers are sent; an optional `CROSSREF_MAILTO` contact address and `NCBI_API_KEY` are sent only when configured.

To check the quotes (Pointers on literature), the worker sends the same DOIs and PMIDs (and the PMCIDs it finds) to Europe PMC (`www.ebi.ac.uk/europepmc`), NCBI (E-utilities and the BioC service for PMC full texts), Crossref and Semantic Scholar (`api.semanticscholar.org`), and downloads the papers' open-access full text or abstract. The quotes themselves are compared inside the worker and are not sent anywhere.

The agent's literature tools (`lit` MCP) send its search queries and the DOIs / PMIDs / PMCIDs it asks about to NCBI E-utilities (PubMed) and Europe PMC, and, when Europe PMC does not answer or has no full text, to the NCBI BioC service for PMC full texts. An optional `CROSSREF_MAILTO` contact address is sent with them; no user identifiers.

## 7. Logs and audit

| Location | What may remain | What does not remain |
| -------- | --------------- | -------------------- |
| Messages | Prompts, agent text, command output (head/tail trimmed when long), errors | API keys |
| CloudWatch | Exception messages, task ARN, model name | Key plaintext (not emitted by design) |
| S3 thread/ | Codex sessions (for resume) | — |

Retention: logs 14 days. Messages / artifacts are indefinite. Deleting a project only hides it from its owner (a `deletedAt` flag on the Projects item): its messages, jobs and S3 artifacts are kept and admins still see it in the project list. Physical erasure has no API; an admin has to do it in AWS.

Admin actions (disable, force-stop) have no dedicated audit table. Jobs / Messages system rows are the trail.

## 8. Threats and mitigations

| Threat | Mitigation | Residual risk |
| ------ | ---------- | ------------- |
| Viewing another user’s project | userId scope; presigned URLs only for own prefix | Admins and AWS privilege holders can see metadata |
| API key theft (DB leak) | KMS + EncryptionContext. No plaintext API | Compromise of a worker role that can decrypt |
| API key theft (logs / agent) | Not logged. The worker's AWS credentials and credentials URI are removed from child processes; `CODEX_API_KEY` / `OPENAI_API_KEY` are excluded from agent commands; and `node` / Codex / git are execute-only so the agent cannot read the key or the credentials URI from another process's `/proc/<pid>/environ` | The agent still uses the key for its own job. This matters more for the default API key: approve only trusted collaborators, give the default key an OpenAI project budget, and rotate it if misuse is suspected |
| Unauthenticated API | JWT authorizer. CORS preflight is not authenticated | `/health` is public |
| Account enumeration | Cognito `preventUserExistenceErrors` | Confirmation state of an email may still be inferred |
| Incomplete artifacts after Spot interruption | S3 persistence + janitor auto-retry | At most 2 retries; then manual |
| Questions left waiting | FAILED after 7 days | Artifacts remain in S3 |
| Self sign-up abuse | Close with `COBRAC_SELF_SIGNUP=false` | Default is open. Billing depends on the victim’s OpenAI key (jobs cannot start without a key) |

## 9. Operational notes

1. **Do not paste API keys into chat or tickets.** If leaked, revoke on OpenAI and re-register in Settings.
2. Admin emails are the GitHub Actions secret `COBRAC_ADMIN_EMAILS` (masked in deploy logs), with a copy in the local `.env` for emergency deploys. Do not commit them (`.env` is in `.gitignore`).3. Disable unused users in the admin UI. Deleting Cognito users is a console task.
4. Users / artifacts / KMS / User Pool remain after stack deletion. Empty them manually before destroying.
5. Command output can remain in CloudWatch. Do not put secrets in prompts.
6. Production can still add origin restriction, PITR, S3 KMS-SSE, and access logs (not implemented).
7. CI deploys use a GitHub OIDC role limited to `main`; there are no long-lived AWS keys in GitHub or in coding agents (see [03 §12](./03_AWSインフラと予算.md)).

## 10. Short explanation for users

- Email and password are held by AWS Cognito.
- OpenAI API keys are encrypted with AWS KMS and decrypted only while a job runs. They are not shown again in the UI.
- BRA data you create is tied only to your account. Charges go to your OpenAI account.
- Deleting a project removes it from your screens, but the data is not erased and administrators can still see it.
- The agent sends data to the internet and OpenAI for literature research.
- This is a working environment for people involved in the project, not a public social service.
