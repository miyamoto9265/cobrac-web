# FRG作成タスク概要

## 目的
本タスクでは、脳領域における情報処理を構造化して記述したFRG（Function Realization Graph）を作成します。ユーザーが指定する脳領域と機能に基づき、神経科学的知見を統合した情報処理の階層的解釈をグラフ構造で作成することが目的です。

FRG（Function Realization Graph）は、特定の脳領域(ROI)が実行する機能(TLF)の情報処理を、神経科学的証拠に基づいて記述した有向非巡回グラフです。脳の計算メカニズムを、階層化し、解釈可能性を高めることが目的です。
グラフの始点はTLFであり、グラフのリーフノードがUniform Component(後述:具体的な神経組織)に当たります。

TLFノードをUCノードに紐づける過程で、複数階層のグループノード(GN)を作成します。TLFの機能分解を適切に行いGNを作成することと、TLF-GN-UCの流れが妥当なグラフ構造を作成するのが目的です。

---

## FRGの構成要素と用語

### 1. Top Level Function（TLF）とRegion of Interest（ROI）
- **TLF（トップレベル機能）**: FRGで記述する対象となる、脳領域や神経組織で実行される計算機能
- **ROI（対象領域）**: TLFが実現される脳領域の神経組織の範囲


### 2. Uniform Component（UC）
- **定義**: UCは、FRGにおけるリーフノードで、メゾスコピックレベルで同質的な情報をコードしていると解釈される神経組織の最小単位
- **役割**: グラフ構造のリーフノードとして、実際の神経組織と接地する。

### 3. グループノード(GN)
- **定義**: 複数階層に渡って記述されるTLFの機能の部分機能。親ノードの実現に必要な部分機能であり、子ノードの組み合わせによって十分に実現される必要がある。複数階層が存在し、TLFを親とするGN（第2階層）やGNを親とするGN(第3階層以上)が存在する。
- **役割**: FRGの中間ノードとして、FRGを適切に分解し神経構造と紐づける。

---

## タスク実行手順

ユーザーが指定するTLFとUCに基づいてFRGを作成します。TLFとUCが記述されたファイルを特定してください。`instruction_0.md` に従い、instructionファイルが存在するフォルダに `{ProjectName}/` フォルダを作成し、その中に `{ProjectName}_FRG/` 作業フォルダを作成してその中で作業してください（HCD作業時に `{ProjectName}_HCD/` は既に作成済みのはずです）。

全ステップ（1〜6）の成果物が完成したら `[STEP_COMPLETE] FRG` を出力してください。

### ステップ1: TLFの段階的分解とGN作成

**目的**: 
TLFを十分に小さい部分機能(GN)にまで分解し、階層的な機能分解構造を作成する。この段階では、UCとの紐づけは行わず、純粋に機能の論理的な分解に集中する。

**作業内容**:
1. TLFが実現する機能を、その実現に必要な複数の部分機能に分解する
2. 各部分機能をGNとして定義し、機能に基づいた明確な名前を付ける
   - 命名規則1 ノード名にはスペースを使用せず、必ずKebab caseを使用する
   - 命名規則2 すべてのノード名は必ず"R."をprefixとして用いる
3. 各GNについて、さらに分解が必要かどうかを判断する
   - 分解が必要な場合: そのGNを親として、さらに子GNに分解する
   - 十分に小さい場合: そのGNをリーフノードとする
4. 分解の妥当性を確認する
   - 各親ノードの機能が、その子ノード群の組み合わせによって十分に実現されるか
   - 各GNが明確で独立した機能を表現しているか
5. 分解結果を以下の形式で1つのファイルに記述する：
   - **表形式**: 階層レベル、ノード名、機能説明を含む表
   - **Mermaid図**: 階層構造を視覚化した有向グラフ（同じ名前のノードは作らず、適切にマージする）

**成果物**: 
- `1_初期分解結果.md`: TLFからリーフノードまでの階層的な機能分解を表形式とMermaidグラフで記述

**注意事項**:
- この段階では、神経科学的な実体（UC）との対応は考慮しない
- 純粋に機能の論理的分解に集中する
- 過度に細かく分解する必要はない。後のステップで調整可能
- **Mermaidグラフでは、同じ名前のノードは重複させず、1つのノードとして表現する**

---

### ステップ2: 冗長性の削減とノードのマージ

**目的**: 
初期分解で作成されたGN群の冗長性を減らし、解釈可能性を高める。類似した機能を持つノードをマージし、グラフ構造を最適化する。

**作業内容**:
1. 初期分解結果を分析し、以下の観点で冗長性を特定する：
   - 機能が重複しているGN
   - 類似した処理を行っているGN
   - 分解が過剰で統合可能なGN
2. マージ候補のノードを特定し、統合後の機能名と説明を定義する
3. ノードのマージを実行し、親子関係を再構築する
4. マージ後のグラフ構造の妥当性を確認する
   - 各親ノードの機能が子ノード群で十分に実現されるか
   - グラフの解釈可能性が向上しているか
5. 最適化結果を以下の形式で1つのファイルに記述する：
   - **表形式**: 階層レベル、ノード名、機能説明、親ノード名、子ノード名を含む表
   - **Mermaid図**: 最適化された階層グラフ図（同じ名前のノードは作らず、適切にマージする）

**成果物**: 
- `2_最適化FRG.md`: マージ後のFRG構造を表形式とMermaidグラフで記述（親子関係を明示）

**注意事項**:
- マージは解釈可能性を損なわない範囲で行う
- 各ノードが明確で独立した機能を持つことを維持する
- 親子関係の列を追加することで、グラフの構造を明示的に記述する
- **Mermaidグラフでは、同じ名前のノードは重複させず、1つのノードとして表現する**

---

### ステップ3: UCとの紐づけとFRGの完成

**目的**: 
最適化されたGN構造を実際の神経組織（UC）と紐づけ、FRGを完成させる。各GNを複数のUCに分解することで、神経科学的実体と接地する。

**作業内容**:
1. ユーザーが指定したUCのリストを確認する
   - **重要**: UCを記述したファイルにはROI外のUCが含まれているが、**ROI内のUCのみ**を使用すること
      - 補足: ROI外のUCはそれが投射するROI内のUCが紐づけられたGNに紐づけられているものと扱うため。
2. 各GN（特に下層のGN）について、それを実現するUCを特定する
   - **重要**: 各GNは**必ず複数のUC**に分解される必要がある
   - 1つのGNに1つのUCのみが紐づく場合、そのGN自体がUCの機能そのものであることを意味するため。
3. **GN-UC接続数の制約を確認する**：
   - **制約1**: 各GNは最大2つのUCによって実現される（1つのGNから接続するUCは2つ以下）
   - **制約2**: 各UCは最大2つのGNの部分機能になる（1つのUCに接続するGNは2つ以下）
   - **違反が発生した場合の対処**: 3つ以上の接続が発生する場合は、ステップ1に戻ってTLFの分解をより細かく行う必要がある
4. UC紐づけの妥当性を確認する：
   - 各GNが複数のUCに適切に分解されているか
   - UCの組み合わせがGNの機能を十分に実現できるか
   - BIF（Brain Information Flow）に基づいたUC間の接続が妥当か
   - **GN-UC間の接続数が制約（各2つ以下）を満たしているか**
5. 必要に応じてグラフ構造を微調整する：
   - GNの追加・削除
   - 階層構造の調整
   - ノード名の変更
   - **接続数制約を満たすための調整**（制約違反が残る場合はステップ1へ戻る）

6. 完成したFRGを以下の形式で記述する：
   - 表形式（ノード名、子ノード、機能説明）およびMermaid図（TLFからUCまでの完全なFRGグラフ）を同じファイルに記述
   - 表は以下のような構造になる。
      - 一列目にはTLFは含めるがUCは含めない
      - 子ノードはセミコロン区切りで記述する(`R.Node名`;`R.Node名`)
      - 子ノードがUCの場合は、(`U.UC名`;`U.UC名`)のように記述する。

   | Node ID | Subnodes | Comment |
   | ------ | -------- | -------- |
   | `R.Node名` | `R.SubNode名`;`U.UC名` | GNの詳細説明 |



**注意事項**:
- ROI内のUCのみを使用する。UCリストにROI外のUCが記述されていても無視すること
- UCが紐づけられるのは最下層である必要はない。中間層のGNに直接UCが紐づく場合もある
- **必須条件1**: 各GNは複数のUCに分解される必要がある
- **必須条件2**: GN-UC間の接続数制約
  - 1つのGNに接続するUCは2つ以下
  - 1つのUCに接続するGNは2つ以下
  - この制約を満たせない場合は、ステップ1に戻ってTLFの分解をより細かく行う
- **Mermaidグラフでは、同じ名前のノードやUCは重複させず、きちんとマージして1つのノードとして表現する**

**成果物**: 
- `3_最終FRG.md`: UCを除く完全なFRG（表形式とMermaidグラフの両方を含む）

### ステップ4: Interfaceの追加

**目的**: 
各グループノード(GN)の機能に関与するUCを明示し、解釈可能性を上げる。

**作業内容**:
各GNは、グラフを下に辿っていけば必ずUCと紐づけられている。そのため、各GNは関与するUCのインターフェースを用いて入出力関係を定義できる。
以下のステップでインターフェースを特定する。

1. 子ノードがすべてUCのグループノードのインターフェースを定義する
   子ノードがすべてUCのグループノードでは、単に子ノードのUCのインターフェースを参照して足し合わせることで実現可能である。ここではROI外のUCも登場させて良い。
      例: R.GN_AがU.UC_BとU.UC_Cで構成されていて、各UCのインターフェースが
      U.UC_A: [U.UC_E] = U.UC_A([U.UC_F], [U.UC_G])
      U.UC_B: [U.UC_H] = U.UC_B([U.UC_F], [U.UC_I])
      のとき、R.GN_Aのインターフェースは、
      R.GN_A: ([U.UC_E], [U.UC_H]) = R.GN_A([U.UC_F], [U.UC_G], [U.UC_I])
      となる。
2. 最下層のGNのインターフェースが決まったので、再帰的にそれ以上のレイヤーのGNのインターフェースが定義できるので、同様に定義する。
   - 最上位のノード(TLF)では、
   (すべてのnon-ROI(output)) = R.TLF(すべてのnon-ROI(input))
   となるはずである。
3. これらインターフェースをFRGの表形式データに付加する。

   | Node ID | Subnodes | Comment | Interface |
   | ------ | -------- | -------- | -------- |
   | `R.Node名` | `R.SubNode名`;`U.UC名` | GNの詳細説明 | [U.UC/R.GN] = R.Node名([U.UC/R.GN], [U.UC/R.GN]) |

**成果物**: 
- `3_最終FRG.md`（更新）: インターフェースが付加されたFRG構造

### ステップ5: 機能関連項目の定義（TLFとGNの機能詳細）

**目的**: 
TLFおよび各GNが実行する機能を詳細に定義する。HCDにおけるUCの機能定義と同様の観点から、FRGのノード（TLF、GN）について計算機能を明確化する。

**項目詳細**: ROI内のGNについて、以下の5項目を作成してください(ROI外は不要、空欄)。機能関連項目内では、[R.(GN名)]のような括弧[]付きで記述してください(形式的な要請による)。各項目は記述形式やルールが複雑なので注意してください。

**作業内容**:
1. TLFおよびすべてのGNについて、以下の4項目を定義する：
- **1. Requirement** Requirementは、TLF（Top-Level Function）を分解して定義された計算機能です。この機能は、TLFを実現するために対象のGNが満たすよう要求されるものです。入力から出力への変換がどのようなものかを、自然言語で説明してください。
  - **重要**:文中にGNの機能に関与する(interfaceに登場する)Uniform Circuit名[U.(UC名)]に加えてその**Output Semantics**を明示的に記述するようにしてください。

- **2. Requirement realization by interface** Requirement realization by interfaceは、Requirementで説明された機能が、Interface（インターフェース）によってどのように実現されるかを明確に記述します。Requirementで定義された入出力関係が、interfaceと矛盾しないかを検証してください。interfaceに含まれるすべてのUC名を登場される必要があります。

- **3. Capability** Capabilityは、Requirementで記述された計算機能からOutput Semantics（出力の意味論）的要素を除去したものです。RequirementがTLFの分解に基づくタスク依存の機能であるのに対し、CapabilityはOutput Semanticsを排除することで、より一般的な計算機能を記述します。Requirementの変換を、Output Semanticsを除いて一般化し、自然言語で説明してください。
  - 計算機能が、どのような先行研究、生物学的知見、または計算モデルに基づいているのかを明示してください。関連する文献を引用してください。

- **4. Mechanism** Mechanismは、Capabilityを実現するための具体的な計算機構を記述します。Capabilityが入出力の変換内容を機能面から記述するのに対し、Mechanismではその変換が機構として「どのように行われるか」を自然言語で説明してください。

**目的**: 各UCが実行する機能を定義する。


2. 4_機能詳細.mdを作成し、以下の表形式で各ノードの機能を記述する：

| Node Name | Requirement | Requirement realization by interface | Capability | Mechanism |
| --------- | --------------- | --------------------------------------- | -------------- | ------------- |
| ノード名/TLF名    | 上記参照のこと     | 上記参照のこと                             | 上記参照のこと   | 上記参照のこと   |

3. 各項目の整合性を確認する：
   - Requirementが親ノードの要求と整合しているか
   - Requirement realization by interfaceがノードに含まれるUCのインターフェースと矛盾していないか
   - CapabilityからImplementationへの流れが論理的に一貫しているか
   - 整合しない場合は関連ファイルを修正する

**注意事項**:
- HCDにおけるUCの機能定義と同様の観点から記述する
- TLFは最上位ノードとして、そのTLF自体が実現すべき全体機能を記述する
- 各GNは親ノードの要求を満たし、子ノードで実現される機能として記述する
- UCについては記述しない（UCの機能定義はHCDで実施済み）
- 表形式で見やすく整理し、各項目を明確に記述する

**成果物**: 
- `4_機能詳細.md`: TLFとすべてのGNの機能関連項目を表形式で記述
